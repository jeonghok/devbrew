## 3. 긴 초안

**의도.** 사용자는 `/qg` 한 번으로 리뷰(테스트 리뷰 포함) → 테스트 실행 → e2e 여부 질문(하면
어떻게) → 결과를 PR 코멘트로 게시하는 흐름을 원한다. 대화하면서 범위가 넷으로 넓어졌다: e2e 단계,
게시 개편, 게시 장치 걷기, 리뷰 다이어트. 넷 다 한 작업이다.

**배경 사실(레포 읽기, Phase 0).**
- `/qg` 는 ① 스코프 → ② 차등 테스트(매 iteration, 기준선 대비) → ③ 각도 + 리뷰어 → ④ 재비판 →
  ⑤ 합성 · 판정이다. fix-loop 는 최대 5회이고 iteration 마다 Retry / Accept / Stop 을 묻는다.
- 리뷰어는 보안 각도(security-reviewer, 매번), 재비판(doc-recritic, 매번), codex(있으면), 그리고 스코프
  신호로 고르는 추가 리뷰어(code-reviewer, silent-failure-hunter, type-design-analyzer,
  pr-test-analyzer(테스트 파일이 바뀐 때만), comment-analyzer, code-architect)다.
- qg 9.0.0 이 runtime-verifier 를 지웠다. 브라우저 플로우, spec AC 런타임 검증, mutation guard 를
  잃었고, 대체하지 않고 「런타임 검증을 한다」는 주장을 거뒀다. 철학 P4 runtime tier 도 qg 가
  주장하지 않는다고 고쳤다. e2e 는 이 거둔 영역을 다른 모양(기계 executor 가 아니라 에이전트가 직접
  걷기 + 사람 감독)으로 다시 들이는 일이다 — P23 재결정이다.
- qg 6.0.0 이 파이프라인 뒤 자동 게시 offer 를 지웠다. 근거는 sentinel 의 소비자가 하나뿐이었다는
  것과, 대체 경로 `/qg-publish` 가 있다는 것이었다. 지금 `/qg` 는 끝에 「이어서 게시하려면
  `/qg-publish`」 한 줄만 낸다. 사용자 요청은 이 결정을 다른 근거(게시를 리뷰 결과 보고로 바꾼다)로
  뒤집는다.
- `/qg-publish` (publishing-pr-understanding): diff → 결정론 context blob → read-nothing 빌더가
  이해글 저술 → secret-scan(fail-closed hard-block) → 터미널 preview(표 · ASCII 다이어그램 ·
  정확성 경고 3종) → 매 실행 AskUserQuestion 동의(비가역 경고) → PR 이 있으면 마커 코멘트
  upsert(0→POST, 1→PATCH, ≥2→REFUSE, numeric id 스코프), PR 이 없으면 push + PR 생성(이해글이 본문).
  kill switch `DEVBREW_QUALITY_GATES_DISABLE_PUBLISH` 는 최내부 sink 에서 집행된다.
  `publish-active.md` 는 publish 가 만든 PR 에 파이프라인 훅이 되따라붙지 않게 막는다.
- 사용자는 「기존에는 새로운 본문 만든다」로 기억한다 — PR 부재 경로다. PR 이 있으면 지금도 코멘트
  하나를 덮어쓴다.

**사용자가 정한 것(확인됨).**
- /qg 한 번이 리뷰 → 테스트 → e2e 질문 → 결과 게시까지 이어서 간다.
- 게시는 새 PR 본문을 만드는 것이 아니라 리뷰 결과를 코멘트로 올리는 쪽으로 바뀐다.
- 게시는 /qg 실행마다 새 코멘트로, 동의를 묻지 않고 올린다.
- PR 이 없으면 게시를 건너뛰고 그 사실을 한 줄로 알리며, qg 는 push 나 PR 생성을 하지 않는다.
- 매 코멘트는 그 시점의 이해글과 그 실행의 qg 결과를 함께 담는다.
- 지금 PR 에 올리는 문서 방식이 괜찮은지 점검하고, 걷어낼 수 있는 게시 장치는 최대한 걷어낸다.
- 테스트 리뷰와 테스트 실행은 지금 장치로 충분하고 바꾸지 않는다.
- e2e 는 대상의 실제 앱·플로우를 구동하되, 기계 장치보다 에이전트가 직접 걷고 사람이 감독한다.
- e2e 는 qg 가 경로를 제안하고 사용자가 고르거나 고친 뒤, 에이전트가 걸어 판정하고 사람은 감독하다
  틀리면 뒤집는다.
- e2e 를 돌렸는데 실패하면 판정이 clean 이 될 수 없다.
- qg 리뷰는 한 번의 리뷰로 장치를 덧붙이거나 보안을 과하게 경계하거나 선제적 오버 엔지니어링을
  처방하지 않아야 한다.
- 리뷰를 반영한 수정이 원래 의도에서 드리프트하는 것을 특히 피해야 한다.

**steering.** 기계 장치보다 모델과 사람 감독을 믿는다. 이 작업 자체도 장치를 더 붙이는 쪽으로 가면
안 된다 — 리뷰 다이어트를 요구하면서 그 구현이 새 락·새 원장·새 게이트를 쌓으면 자기모순이다. 걷어낼
수 있는 것은 걷어낸다.

**열린 것(Phase 0 이 정하지 않은 것).**
- e2e 질문이 fix-loop 의 어느 시점에 오는가(매 iteration? 마지막 한 번?). e2e 가 실패하면 fix-loop
  로 돌아가는가. 사용자가 「안 한다」고 하면 판정은 무엇인가(clean 이 가능한가, 공시만 하는가).
- 걸을 것이 없는 대상(라이브러리, devbrew 플러그인 자신 같은 문서·셸 리포)에서 e2e 질문이 어떻게
  보이는가.
- 「직접 걷는다」의 도구 — 에이전트가 무엇으로 앱을 구동하는가(브라우저 MCP, Bash 등). 걷는 주체가
  Write 를 가진 오케스트레이터인지, 리뷰어처럼 쓰기 없는 agent 인지(Law 2).

- 드리프트 방지가 무엇을 기준으로 의도를 아는가(spec, plan, 커밋, PR 본문).

> 3. «(사용자 확인)» 이 없는 단락은 리포 사실이거나 열린 질문입니다. 원문이 열어 둔 선택을 닫은 자리는 없습니다.
> 4. 「테스트리뷰포함」, 「퍼블리시 스킬로」 같은 표현이 요구로 승격된 자리는 없습니다.
> 5. r2 덩어리 1·2 는 둘 다 「그대로 둔다」로 결정됐고 본문은 이와 어긋나지 않습니다.
>
> **참고 (finding 아님)**
> - 원문의 「마지막에 퍼블리시 스킬로 결과 코멘트로 올림」에서 「퍼블리시 스킬로」라는 경로가 seed 에 명시돼 있지 않습니다. 게시 장치 점검이 열려 있어 닫힘으로 보지 않았습니다.
> - 리포 사실은 이번 라운드에 다시 읽지 않았습니다.

### 냉독 (seed-readback)

> ## 무엇을 맡기려는 것으로 읽었나
>
> seed 는 다음 단계(spec-distill 인터뷰)로 넘기는 출발점이다. 내용은 `/qg` 를 고치는 작업 하나다. 고칠 것은 넷이다. (1) e2e 단계를 새로 넣는다. (2) 게시 방식을 바꾼다. (3) 게시 장치를 걷어낸다. (4) 리뷰가 처방하는 양을 줄인다(리뷰 다이어트). 이 넷을 따로 나누지 않고 한 작업으로 한다. 바뀐 뒤 `/qg` 한 번은 리뷰 → 테스트 → e2e 질문 → 결과 게시를 끝까지 이어서 간다. 테스트 쪽은 지금 장치를 그대로 둔다. 매번 도는 차등 테스트, 그리고 테스트 파일이 바뀐 때만 도는 pr-test-analyzer 다. 인터뷰는 아직 정해지지 않은 결정들을 사용자에게 물어 확정하는 자리로 읽었다.
>
> ## 방향은 이렇게 읽혔다
>
> - **e2e:** 대상의 실제 앱이나 플로우를 돌려 본다. 짜인 기계 장치에 맡기지 않고, 에이전트가 직접 걸어 보고 사람이 감독한다. 순서는 이렇다. qg 가 이 변경에 맞는 경로를 제안한다. 사용자가 고르거나 고친다. 에이전트가 걷고 판정을 낸다. 사람은 지켜보다가 판정이 틀리면 뒤집는다. e2e 를 돌렸는데 실패하면 clean 판정은 나올 수 없다. 이것은 qg 9.0.0 에서 runtime-verifier 와 함께 지운 런타임 검증을 다시 들이는 일이라고 seed 가 스스로 밝힌다.
> - **게시:** PR 본문을 만들던 방식을 PR 코멘트로 바꾼다. 실행할 때마다 새 코멘트를 동의 없이 올린다. 코멘트에는 그 시점의 「이해글」과 그 실행의 결과를 함께 담는다. PR 이 없으면 한 줄로 알리고 건너뛴다. qg 가 push 하거나 PR 을 만들지는 않는다. 이 변경은 과거 결정 둘을 뒤집는다. 하나는 6.0.0 에서 자동 게시 제안을 지운 결정이고, 다른 하나는 게시 skill 의 「매 실행 동의」 불변식이다. seed 는 이 점을 알고 적었다.
> - **걷기:** 지금 게시 장치(secret-scan, preview, 마커 upsert, `publish-active.md` 등)를 점검해서 걷을 수 있는 것은 최대한 걷는다. 다만 어느 것을 남기고 어느 것을 걷을지는 아직 정하지 않았다.
> - **리뷰 다이어트:** 리뷰 한 번이 장치를 덧붙이라거나, 보안을 과하게 경계하라거나, 미리 과설계하라는 처방을 내지 않게 한다. 특히 리뷰를 반영한 수정이 원래 의도에서 벗어나는 것(드리프트)을 막는다.
>
> ## 보낸 사람이 신경 쓰는 것으로 읽힌 것
>
> 첫째는 무게를 줄이는 것이다. 장치를 덜 두고, 처방을 덜 내고, 사람이 감독하고, 에이전트가 직접 걷는다. 둘째는 사용자가 실제로 한 말과 추론을 엄격하게 가르는 것이다. 문장마다 「(사용자 확인)」을 붙였고, 사용자가 말하지 않은 것은 따로 「말하지 않았다」고 적었다. 셋째는 사용자의 기억과 실제 동작이 어긋난 곳을 드러내는 것이다. 사용자는 지금 게시를 새 본문 작성으로 기억하지만, 실제로는 PR 이 있으면 마커 코멘트를 동의를 받아 덮어쓴다. 넷째는 과거 결정을 뒤집는다는 사실을 숨기지 않는 것이다. 마지막으로 이 리포의 규칙들을 의식하고 있다. Law 2(쓰기 권한과 판정 분리), 페르소나 편집은 보안 리뷰 대상이라는 점이 그것이다. 리뷰 다이어트를 구현하면서 정작 새 장치를 늘리게 되는 자기모순도 경계하고 있다.
>
> ## 읽으면서 「이건 모르겠다」 싶었던 곳
>
> - **「이해글」:** 무엇인지 정의가 없다. 누가 언제 만드는 문서인지, PR 본문과는 어떤 관계인지 모른다.
> - **「차등 테스트」:** 변경분(diff)에 걸린 테스트만 돌린다는 뜻으로 짐작했지만 확신은 없다.
> - **넷의 경계:** 「게시 개편」과 「게시 장치 걷기」가 어디서 갈리는지 흐리다. 코멘트로 바꾸는 것이 개편이고 장치를 빼는 것이 걷기로 읽었지만 겹친다.
> - **「6.0.0」:** 어느 플러그인의 버전인지 적혀 있지 않다. qg 로 짐작했다.
> - **「Phase 0」과 「게시 skill」:** Phase 0 은 정의 없이 나온다. 게시 skill 은 이름이 나오지 않아 어느 skill 인지 모른다.
> - **「e2e 를 돌렸는데」:** e2e 를 안 돌리는 선택지도 있다는 전제로 읽힌다. 그런데 그 선택 뒤의 판정, fix-loop 안에서 e2e 가 오는 위치, 실패하면 fix-loop 로 돌아가는지는 seed 도 열어 두었다. 결국 흐름에서 e2e 가 어디에 놓이는지 그려지지 않는다.
> - **「기계장치」:** 사용자가 피하자는 기계장치가 어디까지인지 모르겠다. 에이전트가 브라우저 MCP 로 걷는 것도 「직접 걷기」인가, 아니면 기계장치인가. 「직접」의 주어가 에이전트인지 사람인지도 처음에 헷갈렸다.
> - **긴장 하나:** 동의 없는 자동 게시와 secret-scan 같은 장치를 걷는 일이 함께 오면 보안 쪽은 어떻게 되는가. seed 는 「점검 결과로 정할 일」이라고만 한다. 장치를 걷는 방향과 리뷰가 보안을 과하게 경계하지 말라는 방향이 같은 쪽을 가리키니, 이 긴장이 어떻게 풀릴지 읽히지 않았다.
> - **새 코멘트 누적:** 실행마다 새 코멘트를 쌓으면 PR 에 코멘트가 계속 늘어난다. 사용자가 이것을 감수한 것인지는 seed 에 없다.
> - **seed 밖의 처분 줄:** seed 뒤에 붙은 처분 줄은 이 본문의 일부인지 전달 메타인지 판단하지 못했다.
