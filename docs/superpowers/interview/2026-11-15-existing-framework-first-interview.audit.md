## 3. 긴 초안

1. 요청의 뼈대 — 직접 구현보다 있는 프레임워크를 쓰고, 직접 만드는 것은 가능한 한 줄이고, 검증된 프레임워크 위에서 일한다.
2. 범위 — devbrew 한 레포의 이야기가 아니다. 이미 만든 것과 앞으로 만들 것 모두에, 그리고 devbrew 플러그인을 쓰는 어느 레포에서든 통해야 하는 일하는 방식이다(확인받음).
3. 박아 넣지 않기 — 규칙과 장치에 devbrew 전용 값이나 특정 프레임워크 이름을 박아 넣지 않는다(확인받음). 사용자의 말은 「devbrew만 대상으로 이야기하는게 아니야(하드코딩 X)」였다.
4. 프레임워크가 가리키는 것 — Claude Code 기본 기능, 남이 만들어 유지하는 플러그인과 skill, 널리 쓰이는 일반 패키지와 도구. 에이전트 조율용 프레임워크는 고르지 않았다(확인받음).
5. 계기 넷 — 직접 만든 스크립트와 테스트의 유지 부담, 직접 만든 장치에서 되풀이되는 버그, 새 장치를 만드는 데 드는 시간, 있는 것을 먼저 보라는 규칙이 있는데도 직접 만드는 쪽으로 흘러 온 것(확인받음).
6. 강도 — 맞는 프레임워크가 있으면 그 위에서 만드는 것이 기본이고, 직접 만들려면 이유를 대고 사용자 승인을 받는다(확인받음). 지금 규칙의 「검토한다」보다 세다.
7. 이번 일의 끝 — 규칙 문장과 인터뷰, 설계, 계획 단계가 프레임워크를 먼저 고르게 바꾸는 데까지. 이미 만든 장치를 조사하거나 옮기는 일은 이번에 하지 않는다(확인받음).
8. 검증 기준 — 만든 쪽이 공식으로 내는지, 널리 쓰이는지, 지금도 유지되는지 셋으로 가른다(확인받음). 셋을 모두 넘어야 하는지 하나면 되는지는 묻지 않았다. 「실험 기능 제외」 선택지는 고르지 않았다.
9. 외부 것의 승인 — 지금처럼 후보와 차이를 보이고 사용자 승인을 받은 뒤에만 쓴다(확인받음).
10. 이미 만든 것 — 이번에 옮기지 않지만, 고치는 일이 열리면 크기와 상관없이 프레임워크로 옮길 수 있는지도 함께 본다(확인받음).
11. 규칙이 지켜지지 않은 모습 — devbrew 전반과 다른 프로젝트에서 모두 겪었고, 있는 것을 검토했다고 적기는 했지만 결론은 늘 직접 만들기였다(확인받음). 구체적인 사건은 적지 않았다.
12. 지금 규칙이 있는 자리 — 레포 규칙 문서의 「있는 것 먼저」, 인터뷰 조사 단계의 「있는 것 먼저」 문단(바깥의 성숙한 패키지 · 프레임워크 · 도구를 웹으로 찾는다), 에픽을 설계로 넘기는 줄이 요구하는 설계문서의 「있는 것 검토」 절. 셋 다 「검토한다」까지이고 「있으면 쓰는 것이 기본」이라고 적은 자리는 없다.
13. 직접 만든 규모 — spec-distill 스크립트 58 · 테스트 378, quality-gates 스크립트 56 · 테스트 166, 공용 테스트 248(2026-11-15 `git ls-files` 로 센 값).
14. 원칙의 유래 — 「있는 것 먼저」는 2026-10-19 원칙 정리 설계에서 사용자 말(기존에 있던 것을 쓸 수 있는지 검토하는 성향, 외부는 검토받고 사용)로 들어왔다.
15. 철학 문서의 재사용 조항 — 새로 만든 것은 유지할 표면이 되므로 레포 안 · 밖에 있는 것을 먼저 검토하고 외부 것은 사용자가 검토한 뒤에 쓴다.
16. 지금 바깥에 기대는 것 — python · git · gh · superpowers · quality-gates · Claude Code · pr-review-toolkit(플러그인별 의존 표).
17. 두 승인을 이은 추론 — 외부 것을 쓸 때도 직접 만들 때도 승인이 필요하므로 어느 쪽이든 사용자가 고르게 된다. 사용자가 한 말이 아니라 6 과 9 를 이은 저자의 추론이다.
18. 열린 것 — 검증 기준 셋의 관계(모두 · 하나) · 실험 기능을 빼지 않은 것이 예전 로드맵의 결정(실험 기능은 기반으로 쓰지 않는다)을 바꾸는 뜻인지 · 「크기와 상관없이」가 오타 수정 같은 사소한 변경에도 걸리는지 · 어느 레포에서든 통하려면 규칙이 어디에 살아야 하는지(이 레포의 규칙 문서만 고치면 다른 레포에는 닿지 않는다) · 검토가 형식에 그친 원인(지금 규칙이 검토까지만 요구하고 결론의 기본값을 정하지 않아서라는 것은 저자의 추측).
19. 저자의 읽기 — 어떻게 지켜지게 할지는 하류가 정한다. 다만 검토했다고 적는 칸을 하나 더 만드는 것으로 끝나면 같은 일이 되풀이될 것이다.
20. 과정 — 워크트리 `feature/existing-framework-first` 를 만들어 시작했다.
