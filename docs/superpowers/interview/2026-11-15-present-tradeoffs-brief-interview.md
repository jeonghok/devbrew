# 추천의 대가와 리뷰 뒤 질문 — Interview Brief

> 이 brief는 단독 완결 산출물이다. superpowers가 있으면
> §7 대로 기본 다음 단계(brainstorming 해답공간)로 넘어가고, 없으면 이 brief 자체가 다음 단계의 입력이다. 텔레메트리는 `audit_file`에 있다.

## 0. 한눈에

이 일은 devbrew 의 skill 들이 사람에게 선택을 물을 때 화면에 싣는 글을 고치는 일이다. 사용자는 추천의 대가를 모른 채 골랐고, 리뷰 뒤 질문에서는 선택지 설명에 내용이 없고 「위에 적었다」가 가리키는 글을 찾지 못했다.

- 무엇: 추천이 있는 질문과 문장 권고에 내주는 것을 한 줄로 함께 적고, 리뷰 뒤 결정 질문을 질문 창만 보고 고를 수 있는 꼴로 바꾼다.
- 왜: 지금 규칙이 이유와 경고를 질문 위 글에 두라고 정해 두었고, 그 글은 Claude Code 버그로 화면과 기록에서 사라지는 날이 있다. 사용자가 겪은 원인이 그 규칙인지, 모델이 앞 글을 쓰지 않은 것인지, 썼는데 사라진 것인지는 확인하지 못했다. 보일 때도 지난 기록의 추천 설명 다섯에 하나만 대가를 적었다.
- 확정: 범위(문서 리뷰 셋 · 코드 리뷰 · 인터뷰 · 요청 정리 단계 · 지휘자 의견 줄 · 질문 없는 권고 글 — 공통 규칙의 변경은 skill 열 곳 모두), 추천의 이유와 대가는 질문 안에 · 설명은 한 줄(길어도 세 줄) · 앞 글은 덤, 추천이 있으면 모든 선택지에 얻음 · 내줌, 리뷰어의 긴 글은 모델이 줄인 요약으로 · 전문은 앞 글이 안 보여도 찾아갈 수 있는 자리에, 경고는 스크립트가 따로 내는 짧은 한 줄로, 질문 없는 권고 글에는 공통 규칙 한 문장으로 대가 한 구절을, 실행 중 검사 장치는 두지 않는다.
- 열림: 규칙 문장만 둘지 레포 테스트까지 둘지 · 좁은 창의 긴 설명 · 형식 채우기를 막는 법 · 코드 리뷰에서 선택지가 둘로 접힐 때 · 추천을 비우는 질문의 세부 · 새 문면 · 요약이 뜻을 바꾸지 않게 하는 법 · 리뷰 질문의 「그대로 두면 · 고치면」을 실을 칸 · 코드 리뷰 질문에 실을 것 · 리뷰어 글 전문을 둘 자리.
- 조사는 포화 판정 없이 사용자 판단으로 닫았다(판정 넷이 모두 「아직」). 남은 빈 곳 다섯은 §3 끝에 「설계가 먼저 볼 것」으로 있다.
- 다음 stage: brainstorming(설계문서 하나).

## 1. Goal · Non-goal

- Non-goal: 실행 중에 질문 도구 호출을 검사하거나 고치는 장치는 만들지 않는다 ⟨S10⟩
- Non-goal: 추천이 없는 질문에는 얻음 · 내줌을 억지로 채우지 않는다 ⟨S10⟩

✎ C1–C4 는 요청 정리 단계(Phase 0)에서 사용자가 확인한 문장이다(Phase 0 확인). S1 은 그 단계가 만든 seed 전문이다.
✎ 「방향을 정하는 자리」 가운데 devbrew 가 글을 쓰는 곳은 인터뷰 · 요청 정리 단계 · 문서 리뷰 · 코드 리뷰 · 지휘자다. 설계 · 계획 대화는 외부 skill 이 진행한다(D8).
✎ 두 문제가 한 뿌리라는 Phase 0 의 추론은 규칙 쪽에서 확인됐다 — 추천의 이유도, 리뷰의 경고와 상세도 「내용은 질문 위 글에, 질문 창에는 표시만」이라는 같은 꼴의 규칙에서 나온다. 사용자가 겪은 원인이 그것인지는 확인하지 못했다.
✎ 지난 측정의 「앞 글 0자」 65건은 모델이 안 쓴 것인지 썼는데 사라진 것인지 기록으로 가를 수 없다. 이 세션에서는 질문 앞 글이 매번 기록에 남고 화면에도 보였다(몇 번의 관찰).
✎ 「문제 · 그대로 두면 · 고치면」 셋(D11)은 문서 리뷰 뒤 질문을 두고 받은 답이다. 코드 리뷰 질문에 무엇을 실을지는 열려 있다(OQ21 · S40).
✎ 「레포 테스트까지」 · 「이름만으로 뜻이 서는 선택지」 · 「리뷰어가 쓴 글을 그대로 쓴다」는 사용자가 고른 보완안(ST1)의 세부 문장이고 사용자가 따로 고른 것은 아니다.
✎ 공통 규칙이 skill 열 곳 모두에 닿으면 범위에 넣지 않았던 skill 넷의 질문 문면도 설계와 검증에서 봐야 한다는 것은 모델의 풀이다 — 사용자가 고른 문장(S38)에는 없다.
✎ 꼽았던 권고 자리 셋은 모두 질문에 딸린 줄이다(분해 권고와 다음 단계 제안 이유는 추천 질문의 바로 앞 글, 지휘자 의견은 옮긴 질문에 붙는 줄). 질문이 따라오지 않는 권고 글은 자리를 꼽지 않고 공통 규칙 한 문장으로 닿게 한다(D26). 그런 자리를 모은 목록은 없다(K20).
✎ 이 인터뷰의 질문은 S21 뒤로 짧게 썼다 — 긴 설명이 화면에서 잘리지 않는다는 것은 쟀지만, 사용자가 원한 것은 길이를 줄이는 쪽이다.

- OQ22: 리뷰어 글의 전문(줄이기 전 지적)을 어디에 둘지 — 유추 금지. 앞 글이 안 보여도 찾아갈 수 있는 자리여야 한다(S43). 리뷰가 든 후보는 엔진이 이미 내는 출력이나 파일을 질문 본문이 한 구절로 가리키는 것이다. 경고 전체 목록도 같은 자리에 둔다(S47)

설계가 먼저 볼 것 — 마지막 판정이 남긴 빈 곳 다섯(조사하지 않고 넘긴다):
- 공통 규칙의 새 문면 후보를 실제로 적어 길이 여유를 다시 잰다(OQ18).
- 좁은 창에서 300자 넘는 설명이 보이는지 잰다(OQ13).
- 코드 리뷰가 낮춘 지적 넷 이상에서 선택지를 둘로 접은 이유를 git 기록에서 찾는다(OQ16).
- 모델이 이미 하는 줄이기(리뷰 선택지 라벨의 1–5 낱말 압축)가 뜻을 바꾼 사례를 세션 기록에서 대조한다(OQ19).
- 추천을 낸 쪽이 대가를 스스로 적을 때 형식 채우기를 줄인 선례를 찾는다(OQ15).

- 위험 K1 — 숨은 가정: 이 화면에서 질문 앞 글이 보였다는 관찰은 일반화되지 않는다 — 버그 보고는 지금 깔린 판까지 이어지고 이 세션의 관찰은 몇 번뿐이다 — 레포의 지난 인터뷰도 같은 보고를 적어 두었다 [RC31 → OQ7]
- 위험 K2 — 숨은 가정: 질문 창 안의 글은 다 보인다 — 이 컴퓨터에서는 480자 설명과 좁은 창의 넷 묶음까지 보였으나 좁은 창의 긴 설명은 재지 않았다 — 레포가 기록한 Claude Code 판은 2.1.303 이고 지금 깔린 판은 2.1.325 다 [RC32 → OQ13]
- 위험 K3 — 숨은 가정: 세션 기록에 남은 것이 사용자가 본 화면이다 — 기록은 도구에 넣은 글이지 화면이 아니다 — 지금 검사도 문서의 글자만 본다 [RC37 → OQ11]
- 위험 K4 — 숨은 가정: 범위 밖 자리는 이 변경과 따로다 — 공통 규칙은 skill 열 곳에 같은 바이트로 복제돼 있어 범위 밖 skill 의 규칙도 같은 커밋에서 바뀐다 [RC69 → OQ18]
- 위험 K5 — 숨은 가정: 리뷰 결정 질문에는 가리킬 「위」가 있다 — 절차서는 렌더 첫 줄만 앞 글에 쓰라고 하고 지적별 「그대로 두면 · 고치면」은 도구 출력에만 있다 [RC5 → OQ4]
- 위험 K6 — 실패 양식: 설명이 길면 아래쪽 선택지 설명이 잘린다는 보고가 있다 — 이 컴퓨터에서는 재현되지 않았고 좁은 창의 긴 설명은 재지 않았다
- 위험 K7 — 실패 양식: 기타 칸을 고르면 질문과 설명이 화면에서 사라진다는 보고가 있다 — 이 컴퓨터에서 한 번은 남아 있었다
- 위험 K8 — 실패 양식: 공통 규칙 한 줄만 고치면 리뷰 질문은 그대로다 — 공통 규칙이 자리마다 따로 정한 절차에 우선권을 준다 [RC2 → OQ18]
- 위험 K9 — 실패 양식: 「질문 본문에는 결정 하나와 한 줄만」 문장이 여섯 자리에서 글자째 잠겨 있고 경고를 질문에 싣는 문장이 없어야 한다는 락도 있다 — 새 규칙은 이 락들을 함께 뒤집어야 한다 [RC65 → OQ12]
- 위험 K10 — 실패 양식: 「얻음 · 내줌」이 형식 채우기가 된다 — 추천을 낸 모델이 자기 추천의 대가를 가볍게 적고, 지금 검사는 설명의 내용을 재지 못한다 [RC19 → OQ15]
- 위험 K11 — 실패 양식: 모델이 리뷰어의 글을 줄이다 뜻이 달라진다 — 지금 있는 대조 장치는 선택지 수 · 순서 · 라벨 글자만 보고 요약의 뜻은 보지 않는다 [RC92 → OQ19]
- 위험 K12 — 실패 양식: 지휘자가 옮기는 질문에서 대조 규칙과 부딪힌다 — 지휘자 의견이 선택지 설명 안에 들어가면 어긋남으로 판정한다 [RC67 → OQ18]
- 위험 K13 — 실패 양식: 엔진이 내는 「그대로 두면 · 고치면」 줄에는 길이 상한이 없고 리뷰어가 칸을 비우면 자리표가 그대로 나간다 [RC7 → OQ4]
- 위험 K14 — 실패 양식: 리뷰어에 칸이나 길이 규칙을 더하면 고칠 자리가 여럿이고(원본과 사본 · 다른 모델 리뷰어의 변환기 · 엔진의 칸 목록) 하나라도 빠지면 그 칸이 조용히 버려진다 [RC112 → OQ19]
- 위험 K15 — 실패 양식: 공통 규칙을 약 180자 넘게 늘리면 skill 하나에서 절이 앞 5,000토큰 경계 밖으로 밀린다(근사) — 재는 도구는 통과 · 실패를 내지 않는 측정이다 [RC134 → OQ18]
- 위험 K16 — 실패 양식: 코드 리뷰의 낮춘 지적 게이트는 넷 이상에서 선택지를 둘로 접어 항목별 내용이 질문 창에 설 자리가 없다 — 접은 이유는 기록에 없다 [RC113 → OQ16]
- 위험 K17 — 실패 양식: 추천을 일부러 비우는 질문은 본문에 결정의 대상 전문을 줄이지 않고 싣게 돼 있다 — 「짧게」와 부딪힌다 [RC68 → OQ17]
- 위험 K18 — 실패 양식: 이미 대가를 내는 자리(인터뷰의 추천 · 트레이드오프 한 줄)는 질문 앞 글에 서 있고 설명 칸 규칙에는 기계 검사가 없다 [RC4 → OQ4]
- 위험 K19 — 실패 양식: 리뷰어는 지적의 세 칸을 처음 보는 사람이 읽을 글로 쓰지만 길이를 묶은 칸은 하나뿐이다 — 요약할 때 어느 칸을 근거로 삼는지 정해야 한다 [RC78 → OQ9]
- 위험 K20 — 실패 양식: 질문 밖 문장 권고 자리를 모은 목록이 레포에 없다 — 찾은 셋 밖의 자리는 규칙이 닿았는지 확인할 길이 없다 [RC49 → OQ10]
- 위험 K21 — 실패 양식: 요청 정리 단계의 확인 질문은 설명 칸을 다른 용도(물은 것 · 답한 것 · 읽은 것)로 쓴다 — 대가를 적을 질문과 가려야 한다 [RC14 → OQ2]
- 위험 K22 — 실패 양식: 외부 skill 의 질문은 지난 확정대로 범위 밖이라, 설계 대화에서 대가가 빠져도 devbrew 규칙으로는 잡지 못한다 [RC45 → OQ5]
- 위험 K23 — 실패 양식: 세션 기록에 preview 칸이 있는 질문은 855개 중 1개였다 — 설명이 안 보인 원인으로 preview 를 볼 근거는 약하다 [RC52 → OQ6]
- 위험 K24 — 실패 양식: 글을 쓴 쪽이 자기 글에 대한 지적을 줄여 보여 준다 — 공통 규칙 「스크립트·subagent 가 낸 원문은 고치지 않는다」의 예외가 되고, 사용자는 줄기 전 지적을 보지 못한 채 고를 수 있다 [RC108 → OQ19]
- 위험 K25 — 실패 양식: 재측정의 기준이 된 처음 측정이 거칠다 — 어느 리뷰의 질문인지는 그 세션에서 마지막으로 부른 skill 로 나눴고 「위」를 가리키는지는 낱말 맞추기로 셌으며 손으로 연 사례는 하나다(S1) — 같은 방법으로 다시 재면 문구가 다른 자리와 새 문면은 세어지지 않은 채 「고쳐졌다」로 읽힌다
- 위험 K26 — 실패 양식: 스크립트가 낸 경고 줄이 없는 자리에서는 리뷰받은 쪽이 경고를 자기 말로 쓴다 — 리뷰어 글을 줄이는 것과 같은 예외이고 같은 위험이다(S41)
- 위험 K27 — 실패 양식: 질문 없는 권고 글 문장을 공통 규칙에 넣으면 고르지 않은 넓힘(모델이 권하는 글 전부)에 가까워진다 — 공통 규칙은 skill 열 곳에 같은 글자라 방향을 정하는 자리 밖의 글에도 닿고, 지켜졌는지 볼 자리 목록이 없다(S46 · K20)
- 위험 K28 — 실패 양식: 경고가 나오는 통로가 하나가 아니다 — 문서 리뷰 엔진의 첫 줄 말고도 설계문서 리뷰의 번호 대조 줄이 있고, 기록이나 플래그에서 경고를 읽어 스크립트가 낸 줄이 없는 자리도 있다 — 짧은 줄을 내게 고칠 스크립트가 여럿이고 줄이 없는 자리는 모델이 쓴다(S47 · K26)

✎ 사용자가 설계가 다룰 위험으로 넘긴 실패 양식 일곱(S14)은 K3 · K6 · K7 · K8 · K10 · K11 · K12 다(K3 은 이 목록에서 숨은 가정으로 적혔다).
✎ 사용자가 넘기거나 적으라고 고른 위험이 셋 더 있다 — K9(문면을 잠근 테스트)와 K16(접힌 이유의 기록 없음)은 레포 조사가 찾은 것 넷을 설계에 넘긴다는 답(S30)에 들고, K24 는 brief 에 적으라고 고른 위험이다(S39).

## 6. 사용자 원문

- **S1** 🗣 최초 요청:
  > ---
  > type: interview-seed
  > next_phase: spec-distill:pm-interview
  > audit_file: 2026-11-15-present-tradeoffs-interview.audit.md
  > ---
  >
  > 사용자가 맡긴 일은 둘이고 하나로 묶였다. 처음 요청은 「전반적으로 트레이드 오프를 같이 제시해줘야함」이었고, 회의 도중에 「리뷰어가 리뷰한뒤에 나한테 ask question하는데 설명이 비어있음 그리고 위를 보라는데 위에 아무것도 없음 설명도 부족」을 덧붙였다.
  > 리뷰 뒤 질문 문제는 추천의 대가 문제와 한 일로 묶는다. (사용자 확인)
  > 이 일의 목표는 모델이 무언가를 권하거나 리뷰 뒤에 결정을 물을 때 사용자가 그 화면에 보이는 글만으로 무엇을 고르는지와 그 대가를 알 수 있게 하는 것이다. (사용자 확인)
  >
  > 트레이드오프는 추천을 달 때 그 추천을 따르면 내주는 것을 함께 적는 것이다. (사용자 확인)
  > 대상은 인터뷰 · 설계 · 계획처럼 방향을 정하는 자리다. (사용자 확인)
  > 방향을 정하는 자리에서는 질문뿐 아니라 모델이 한쪽을 권하는 글에도 그 대가를 같이 적는다. (사용자 확인)
  > 지금까지 추천의 대가를 모르고 골랐고, 선택지를 견주기 어려웠고, 질문이 아닌 글에서는 한쪽 길만 들었다. (사용자 확인)
  > devbrew 가 띄우는 질문 전부나 모델이 권하는 글 전부로 넓히는 것, 추천이 없는 질문에도 선택지마다 얻는 것과 내주는 것을 적는 것은 선택지로 보였지만 사용자가 고르지 않았다.
  >
  > 얻는 것과 내주는 것을 문장으로 풀어 쓴 형식은 길어서, 한눈에 들어오는 더 짧은 형식이어야 한다. (사용자 확인)
  > 그 말을 듣고 이 회의의 다음 질문부터 선택지 설명을 「얻음: 겹치는 규칙을 한 번에 고친다 · 내줌: 일이 커져 인터뷰와 설계가 길어진다」처럼 한 줄로 줄여 보였다.
  > 선택지 설명은 얻음과 내줌을 한 줄에 적는 이번 형식 정도면 된다. (사용자 확인)
  >
  > 리뷰 뒤에 받는 결정 질문은 선택지 설명이 비어 있고 「위에 적었다」가 가리키는 글이 보이지 않아, 질문만 보고는 무엇을 고르는지 알 수 없었다. (사용자 확인)
  > 설명이 비었다는 것은 설명 칸이 아예 없던 경우, 있어도 한 줄뿐이던 경우, 질문 본문에 무엇이 문제인지가 없던 경우를 모두 가리킨다. (사용자 확인)
  > 어느 리뷰에서 그랬는지는 사용자가 짚지 않았고, 지난 세션 기록을 잰 결과로 정한다. (사용자 확인)
  >
  > 그래서 이 레포의 지난 세션 기록 872개에 남은 질문 827개를 쟀다.
  > 「위」를 가리킨 질문 가운데 그 앞에 모델이 쓴 글이 하나도 없던 것이 요청을 정리하는 단계(request-framing)에서 36개 중 31개, 설계문서 리뷰에서 25개 중 17개, 인터뷰에서 28개 중 14개였다.
  > 코드 리뷰의 질문 67개에는 「위」를 가리킨 것이 없었다.
  > 지휘자 세션의 질문 28개에는 「위」를 가리킨 것이 하나 있었고, 그 앞에 글이 없던 것은 없었다.
  > 직접 열어 본 한 사례에서는 seed 리뷰 뒤 질문 넷이 모두 「경고 4개 — 위에 적었다」로 끝났는데, 리뷰어 결과를 받은 뒤 그 질문까지 모델이 쓴 글이 없었다.
  > 선택지 설명 칸이 완전히 빈 질문은 기록에서 찾지 못했고, 열두 자 이하로 짧은 설명은 여러 곳에 있었다.
  >
  > 어떻게 지키게 할지(규칙 문장만 둘지 검사까지 둘지)와 화면의 어느 칸에 무엇을 실을지는 이 회의에서 정하지 않았다.
  > 사용자에게는 그것을 인터뷰와 설계가 정할 일이라고 말하고 회의를 닫았다.
  >
  > 다시 검증할 것 — 두 문제가 「질문 화면만 보고는 고를 수 없다」는 한 뿌리라는 것은 Phase 0 의 추론이다. 사용자는 묶는 데 동의했지 그 원인 진단을 확인하지 않았다.
  > 질문 창이 떠 있는 동안 그 앞에 쓴 글이 화면에 보이지 않을 수 있다는 것은 질문 도구의 설명서에 적힌 말이고, 실제 화면에서 재지 않았다.
  > 설명 칸이 아예 없던 질문은 기록에 없으므로, 사용자가 본 화면이 무엇이었는지는 다시 물어야 한다.
  > 측정은 거칠다 — 어느 리뷰의 질문인지는 그 세션에서 마지막으로 부른 skill 로 나눴고, 「위」를 가리키는지는 낱말 맞추기로 셌고, 손으로 연 사례는 하나다.
  > 범위 답은 추천의 대가 문제만 놓고 받은 것이고, 리뷰 뒤 질문 문제에도 같은 범위가 걸리는지는 묻지 않았다.
  > 요청을 정리하는 단계가 「방향을 정하는 자리」에 드는지는 묻지 않았다. 범위 질문의 선택지에 적은 예는 인터뷰 · 설계 · 계획이었는데 측정에서는 그 단계가 가장 심했다.
  > 설계 단계의 질문은 devbrew 밖의 skill(superpowers 의 brainstorming)이 띄우는데, 이 일의 규칙이 거기에 닿을 수 있는지는 보지 않았다.
  > 코드 리뷰에 「위」를 가리키는 질문이 없다는 것이 그쪽 질문은 화면만 보고 고를 수 있다는 뜻인지도 보지 않았다.
