# Conductor Context Economy — Interview Brief

> 이 brief는 단독 완결 산출물이다. 이 일은 에픽 여섯으로 나뉘었고(§7), 다음 단계는 그 로드맵의 지휘 절차다. 텔레메트리는 `audit_file`에 있다.

## 0. 한눈에

- **무엇** — devbrew 의 지휘(로드맵 지휘자와 그 아래 담당자)를 my-team 구조(역할 폴더 · 역할 문서 · 과제 폴더 INTENT.md · STATUS.md · inbox/ · 규칙 목차 → HANDBOOK)로 재설계한다. 파이프라인의 모든 단계가 팀으로 돌고, 로드맵 하나가 팀 하나다.
- **왜** — 토큰이 너무 많이 들고 맥락이 쌓여 판단이 흐려진다. agent 끼리 대화가 안 돼 공유가 빠진다. 보고는 길고 파일에 안 남으며, 도는 동안 중간 소식이 없고, 지휘 중 작업 목록이 안 뜬다(사용자 첫 요청).
- **잠정 방향**(아직 사용자가 확정한 항목은 없다 — 끝 게이트에서 확정할 것을 묻는다) — 파일 규약 + 읽기 설계(누가 · 언제 · 무엇을 · 얼마나 읽나) + 결정한 자리에서 쓰는 결정 기록을 같은 첫 단추로 둔다(반론 검토 ST1 보완). 일꾼은 하위 agent 기본 + 단계표 실행기 칸. 순서는 스크립트가 지키되 사람 승인 탈출구를 둔다. 지휘자끼리는 코드 없는 지휘자 상태 브랜치(편지함 · STATUS)로 소통하고, 현황 mod 하나가 표시와 편지함 감시를 겸하되(대화형 터미널에서만), 발신이 확인되지 않은 글은 새 턴이 아니라 알림만 한다. 바닥부터 만들지 않고 있는 장치(SDD 고침 루프 · Claude Code 세션 받은 편지함 · mod)에 맡긴다. 잘못 쌓인 맥락은 없는 것보다 나쁘다는 원칙으로 규칙 목차를 운영한다.
- **열려 있음** — 설계 질문 20개(OQ22–OQ32 · OQ39 · OQ41–OQ48, 모두 열림)를 각 에픽 설계에서 정한다. 구조를 정하는 것(역할 목록 OQ23 · 관문 다섯 칸과 2단 검수 OQ32 · 도구 제한 자리 OQ44 · 발신 확인 수단 OQ46 · devbrew 산출물을 모을 한곳 OQ47)과 형식 · 숫자 · 문장 수준의 것이 섞여 있다.
- **다음** — 로드맵 지휘(§7). 첫 걸음은 토큰 기준선(P1)과 팀 파일 규약(R1)이다.

**결정 목록**

- OQ1 [해결 ⟨S2⟩] — 이 재설계가 먼저 풀어야 할 뿌리 문제는 무엇인가 → 근거 RC4
- OQ2 [해결 ⟨S3⟩] — 지휘 중 작업 목록을 무엇으로 띄울까 — 플랫폼 작업 목록 도구 켜기 · STATUS 파일 · 둘 다 (화면에 보인 순서는 둘 다 · 도구만 켠다 · STATUS 파일만 — 답 「3」 = STATUS 파일만)
- OQ3 [해결 ⟨S4⟩] — 일꾼(담당자)을 무엇으로 돌릴까 — 하위 agent · agent 팀원 · 따로 띄운 세션 · 헤드리스 claude -p · 외부 실행기 → 근거 RC13
- OQ4 [해결 ⟨S9⟩] — 다른 기계의 지휘자끼리 글을 무엇으로 나를까 — git 원격의 파일 · 플랫폼 세션 메시지 · 둘 다 → 근거 RC8
