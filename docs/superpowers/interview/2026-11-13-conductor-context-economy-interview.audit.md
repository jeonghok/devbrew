대장(상주 1): 사람이 말로 맡기면 과제를 등록만 해요. 직접 만들지 않아요.
배정 담당(스크립트): 단계표(stages.json)를 보고 단계마다 일꾼을 불러요. 결과 파일이 생기면 다음 단계를 바로 띄워요.
일꾼(claude -p): 지시서와 과제 폴더를 받아 결과 파일을 쓰고 끝나요. 보고 메시지 없이 파일로만 남겨요.
출입증(세션 ID): 과제마다 하나. 첫 단계는 --session-id, 다음 단계부터 --resume으로 같은 세션을 이어 붙여 앞 단계 맥락을 알아요. 과제가 끝나면 그 세션은 닫고, 다음 과제는 빈 컨텍스트로 시작해요.
단계마다 다른 일꾼: 조사·교차 리뷰는 다른 모델(Codex), 테스트·형식 점검은 스크립트(토큰을 안 씀).
권한: 단계마다 --allowedTools로 쓸 명령만 허락하고, 팀 공용 규칙 폴더는 --disallowedTools로 수정을 막아요.
사람이 들어가는 곳: 설계안 승인(승인은 그 파일 내용의 해시에 묶여서 파일이 바뀌면 다시 승인), 마지막 판정(대장), 배포(사람). 자체 검수가 3번을 넘기거나 같은 단계가 2번 연속 실패하면 멈추고 메일이 와요.
과제끼리는 동시에 돌고, 무거운 빌드만 동시 2개로 묶었어요. 현황은 workers 명령으로 보고(파일만 읽어서 토큰 0), 대장 세션은 사람이 비우고 나면 시작 훅이 현황 요약을 넣어 줘요.

숫자 근거
캐시 읽기 비율: 이 구조로 돌린 실제 제작 세션 2개에서 입력 토큰의 98.5%, 99.0%(세션 기록의 usage 집계, 2026-11-03).
Claude API 가격표(platform.claude.com/docs/en/about-claude/pricing): Opus 5.5 입력 $4, 캐시 읽기 $0.20(입력의 0.05배), 100만 토큰당.
위 두 세션을 이 가격표로 계산하면 입력 비용이 캐시 없을 때의 약 12.5분의 1, 14.5분의 1이에요. 저희는 구독으로 쓰고 있어서 실제 청구액은 아니에요.

단계표·지시서 양식(복사해서 바꿔 쓰세요)
my-team/
├─ leader/            상주 대장 (CLAUDE.md: 직접 만들지 않고 등록만)
├─ pipeline/
│  ├─ engine.py       배정 담당: 단계표대로 다음 단계를 띄움
│  ├─ stages.json     단계표
│  └─ prompts/        단계별 지시서 (design.md, implement.md …)
└─ jobs/과제이름/      단계마다 결과 파일

stages.json 예
{"flow": [
  {"id": "design",    "by": "claude",      "prompt": "prompts/design.md", "out": "design.md"},
  {"id": "research",  "by": "other-model", "out": "research.md"},
  {"id": "check",     "by": "script",      "run": "python3 checks/lint.py"},
  {"id": "approve",   "by": "human",       "file": "design.md"},
  {"id": "implement", "by": "claude",      "prompt": "prompts/implement.md", "bash": ["Bash(npm test)"]}
]}

일꾼 한 번 부르기
claude -p "$(cat prompts/design.md)" --session-id 과제ID --allowedTools Read Write Edit --disallowedTools "Edit(team-rules/**)"
다음 단계: claude -p "$(cat prompts/implement.md)" --resume 과제ID --allowedTools Read Write Edit "Bash(npm test)"

지시서(prompts/design.md) 첫머리 예
이 단계 하나만 한다. 읽을 것: jobs/과제이름/INTENT.md. 쓸 것: jobs/과제이름/design.md. 다 쓰면 끝낸다.

## 3. 긴 초안

### 긴 초안 본문 (압축 직전)

D1. 출발점 — 사용자는 로드맵 지휘(epic-conductor)와 그 아래 담당자들이 토큰을 너무 많이 쓰고, 맥락이 쌓여 품질도 흐려진다고 본다. 걱정은 비용과 품질 저하 둘 다다. 하위 담당자 보고는 너무 길고, 파일에 안 남고, 중간 소식이 없고, 반려가 흐릿하다.

D2. 공유 누락 — agent 끼리 대화가 안 돼 공유가 빠지는 곳이 넷 다다: 병렬 담당자끼리 · 지휘자 → 담당자 · 단계 · 교대 사이 · 담당자 → 그 하위. 메우는 길은 과제마다 파일(목표 · 지시 원문 · 하지 않을 것 · 결정 기록)이다.

D3. 추가 지시 — 사용자가 붙인 my-team 구조(역할 폴더마다 CLAUDE.md 의 할 일 / 하지 않을 일, 공통 CLAUDE.md, 한 줄 규칙 목차 MEMORY.md(120줄 안, 새 규칙은 맨 위, 넘으면 합치고 옛것은 HANDBOOK 으로), 두 번 나온 지적이 올라가는 HANDBOOK.md, 넘기기 전 관문 5칸 QUALITY_GATES.md(테스트 · 린트 · 화면 · 문서 · 보고), 권한을 막아 둔 tools/, 대장의 STATUS.md · inbox/, 과제마다 INTENT.md, 대장이 방향을 먼저 사람에게 보여 주는 의도 싱크, 검수 두 번과 한 줄 반려(어디서 · 무엇이 · 어떤 기준), 테스트 서버까지는 대장 · 실서비스는 사람)는 첫 요청을 풀 방향이다. 사용자는 이것을 「구조째 옮김」으로 골랐고, 이름(INTENT.md · STATUS.md · inbox/ · MEMORY → HANDBOOK)을 공식 용어로 쓰며, 지금 있는 장치를 어느 정도 걷어내고 바꾼다고 했다. 역할 이름(worker · leader)은 devbrew 말로 바꾼다.

D4. 메시지 규칙 — 「메시지는 짧게, 자세한 건 파일 경로로」. 메시지는 세션이 끝나면 사라지니 기억은 파일로. 적용 대상은 agent 사이 글이다(사람에게 쓰는 글이 아니다).

D5. 대화 계약 — 글을 파일로 주고받으므로 받는 쪽이 읽고 이해했음을 확인하는 약속이 필요하다. 팀원끼리 대화 계약: 대화 형식 · 받았음과 답했음의 확인 · 글이 왔음을 아는 방법 · 우리 agent 가 보낸 글인지의 확인.

D6. 진행 문서 — STATUS 같은 진행 · 지휘 문서는 사람과 agent 둘 다 읽는다. 작업 목록이 터미널에서도 안 생기는 것이 문제이고, 지휘가 도는 동안 목록이 떠 있어야 한다.

D7. 토큰 — 세 용도 모두: 한 번 재서 줄이기 · 계속 보이기 · 리프레시 신호. 지금 레포에는 토큰을 세는 코드가 없다. Claude Code 세션 기록(하위 agent 포함)에는 턴마다 usage 가 남는다. 지휘 절차서(conducting.md)는 약 3.5만 토큰이고 지휘자가 부를 때마다 읽는다.

D8. 리프레시 — 지휘 세션의 `/compact` 는 「무거우면 권한다」뿐이고 잴 기준이 없다. 구현 담당자는 스스로 판단해 CHECKPOINT 로 돌아온다. 사용자는 적절한 순간(너무 자주는 말고) 새 세션으로 리프레시하길 원하고, 구현 담당자도 일정 순간마다 새로 보내길 원한다. 어떻게 할지는 인터뷰가 정한다. 사용자 관찰: 이제는 하위 agent 도 자동 압축이 된다.

D9. 범위 확장 — 로드맵 하나가 팀 하나이고, 여러 로드맵이 동시에 돌 때가 실제로 생긴다. 지휘자끼리 소통이 필요하고, 지휘자들은 다른 세션 · 다른 서버에 있을 수 있다. 지휘자끼리 주고받을 것: 같은 파일 건드림 · 머지 순서 · 규칙과 배운 것 · 사람 질문 줄, 그리고 D5 의 계약. 팀은 로드맵만이 아니라 파이프라인 모든 단계가 쓴다. 설계문서 하나뿐인 일도 지휘자를 거친다.

D10. 자리 — 팀 문서(INTENT · STATUS · inbox 등)는 한곳, 코드를 고치는 자리는 worktree(한 체크아웃에 둘이 쓰면 커밋이 조용히 되돌려진 사례가 있다). 팀 규칙 목차는 레포 안 파일.

D11. 영상(「클로드 코드 팀, 상주는 하나만 두고 나머지는 불러서 씁니다」 설명글) — 상주 대장 하나는 등록만, 배정 스크립트가 단계표대로 일꾼(`claude -p`)을 띄우고, 일꾼은 결과 파일만 남기고 끝(막히면 BLOCKED.md), 과제마다 세션 ID 하나로 단계를 이어 붙이고 과제 끝에 닫음, 단계마다 다른 일꾼(스크립트 · 다른 모델), 단계마다 권한, 승인은 파일 해시에 묶임, 검수 3번 초과 · 같은 단계 2연속 실패면 멈추고 메일, 무거운 빌드 동시 2개, 토큰 0 현황 명령과 세션을 비운 뒤 시작 훅의 현황 요약, 캐시 읽기가 입력의 98.5% · 99%. 사용자가 가져오기로 고른 것: 해시 승인 · 숫자 멈춤 조건 · 토큰 0 현황 · 파일로만 보고 · 단계마다 다른 일꾼 · 단계마다 권한 · 사용량 집계 측정. 「과제마다 세션 하나」는 과제 단위가 애매해 인터뷰가 정한다. 자막은 읽지 못했다.

D11b. 「한가지더」로 덧붙인 것 — 단계표는 무슨 순서로 누구에게 일을 시킬지 적은 파일 하나다. 단계별 지시서는 따로 모아 두고, 과제마다 폴더 하나(jobs)에서 일꾼이 자료를 꺼내고 결과를 넣는다. 일꾼은 다 Claude 가 아니다 — Claude(설계안 · 자체 검수 · 구현 · 회고 등) · 다른 모델(교차 리뷰) · 스크립트(점검 · 테스트) · 사람(승인 · 배포) · 대장. 구현 뒤 자체 검수 일꾼이 테스트 결과로 판정하고, 고칠 것이 있으면 구현으로 되돌리되 세 번을 넘으면 더 돌리지 않고 보고한다. 과제 여러 개는 병렬로, 빌드처럼 컴퓨터를 많이 쓰는 일만 동시 2개, 다른 일은 서버 부하를 보고 정한다. (devbrew 대조: 회고 단계는 Law 3 축적과 닿는다. 병렬 수는 지금 권장 3 고정 — 부하 기준이 없다.)

D12. 열린 것(인터뷰 몫) — 담당자 실체(하위 agent · `claude -p` · herdr 같은 방식), 리프레시 방식과 「과제」 단위, 단계 진행 담당(관리 스크립트), 지휘자끼리 통로, 대화 계약 형식. 조건: 특정 외부 도구에 하드코딩 · 의존 금지. 관리 스크립트는 지휘자의 도구 역할이고 P8 의 「결정론은 보안 · 정확성 게이트에만」은 바꾼다. superpowers 에 묶이지 않고 Matt Pocock skills · pstack 같은 작업 방식도 단계에 끼울 수 있게.

D13. 위험 · 확인 필요 — 헤드리스 `claude -p` 의 조용한 실패(rc 0)와 Skill 도구 거부(레포 기록), 역할 CLAUDE.md 를 하위 agent 가 읽는지, 「하지 않을 일」은 글이 아니라 도구 권한으로만 막힌다(Law 2), 레포 안 MEMORY.md 이름이 Claude 자동 메모리 MEMORY.md 와 겹친다, 기존 장치 제거는 major 판 올림과 CHANGELOG 기록이 따른다, 작업 목록이 안 생기는 원인은 모른다.

### 팀(로드맵) 사이 소통 — 지휘자끼리 (사용자 질문에 답한 저자 스케치, 미확인)

- 지금 있는 것: 로드맵마다 지휘 세션 하나가 표지(`conductor_ledger.py claim`)를 쥔다. 로드맵 사이를 잇는 장치는 기본 브랜치(머지된 것)와 스위트 잠금 정도이고, 지휘자끼리 직접 주고받는 길은 없다.
- 하니스에 있는 것: 같은 기계의 다른 Claude 세션에 메시지를 보내는 도구(`ListAgents` · `SendMessage`)가 있다 — 지휘자끼리의 「초인종」으로 쓸 수 있다.
- 갈래 셋
  - A 파일 게시판: 로드맵 사이 공유 파일(각 지휘자의 진행 문서 + 공용 받은편지함). 세션이 사라져도 남는다.
  - B 직접 메시지: 세션 간 메시지로 짧게 알리고 자세한 건 파일 경로로. 받은 쪽이 꺼져 있으면 사라진다.
  - C 총괄 지휘자: 로드맵 위에 한 층 더. 무겁다.
- 저자 추천: A 를 기록으로, B 를 초인종으로(사용자의 「메시지는 짧게, 자세한 건 파일로」와 같은 모양). C 는 지금 두지 않는다. 결정은 인터뷰 몫.
- 고침(사용자: 「세션이나 서버가 다를 수 있어」): B 의 세션 간 메시지는 같은 기계 안에서만 닿는다. 그래서 기록(A)은 로컬 파일이 아니라 기계를 건너 닿는 곳(git 원격 · GitHub 같은 곳 — 저자 추론)에 있어야 하고, B 는 같은 기계일 때만 쓰는 덤이다.

### 사용자가 준 영상 (라운드 7 뒤)

- 페이지 제목만 읽혔다: 「클로드 코드 팀, 상주는 하나만 두고 나머지는 불러서 씁니다」. 자막 · 설명 · 채널은 읽지 못했다(web-fetch agent, 2026-11-14 — 페이지는 제목과 바닥글뿐, 자막 사이트는 빈 응답).
- 제목이 가리키는 방향(저자 추론, 본문 미확인): 오래 사는 세션은 하나(지휘자)만 두고 담당자는 일이 있을 때 불러 쓰고 내린다 — 열린 질문 「담당자 실체 · 리프레시」에 닿는다.
- 출처: https://www.youtube.com/watch?v=cFRj6a1xQ-A
- 다시 시도(2026-11-14): 페이지를 직접 받아 설명글(사용자가 붙인 글과 같은 내용)은 읽었다. 자막은 한국어 자동 자막 트랙이 있으나 내려받기가 세 형식 모두 0바이트였다 — 유튜브가 자막 요청에 출처 증명 토큰을 요구하는 것으로 보인다(`exp=xpe`, 저자 추론). 자막 내용은 확인하지 못했다.

> - agent 사이 글은 짧게 쓰고, 자세한 것은 파일 경로로 넘기며, 받음 확인과 되읽기를 붙입니다.
> - 토큰은 재고, 지휘 중에 보이게 하고, 리프레시 신호로 씁니다.
> - 지휘 중에는 작업 목록이 늘 떠 있게 합니다.
> - P8 의 「결정론은 보안 · 정확성 게이트에만」은 고쳐서, 단계 진행을 돕는 관리 스크립트를 허용합니다.
> - superpowers 에 묶이지 않고 다른 작업 방식도 단계에 끼울 수 있게 둡니다.
>
> ## 보낸 사람이 신경 쓰는 것으로 읽힌 것
>
> 가장 크게 신경 쓰는 것은 두 가지로 보였습니다. 첫째, 맥락이 쌓이면서 생기는 비용과 판단 흐림입니다. 사용자는 둘 다 걱정한다고 했습니다. 둘째, agent 끼리 대화가 안 돼서 공유가 빠지는 문제입니다.
>
> 그 밖에 이런 것들을 신경 쓰는 것으로 읽혔습니다.
> - 보고가 길고, 파일에 남지 않고, 중간 소식이 없고, 반려가 흐릿한 문제. 반려는 한 줄로 어디서 무엇이 어떤 기준에 걸렸는지 말해야 합니다.
> - 세션이 끝나면 사라지는 메시지 대신 파일에 남는 기억
> - 사람과 agent 가 함께 읽는 진행 문서
> - 권한은 글이 아니라 도구로 막는 것
> - 외부 도구에 대한 하드코딩이나 의존을 피하는 것
> - 여러 로드맵이 동시에 도는 상황이 실제로 생기고 있다는 현실
>
> 또 문장마다 붙은 「(사용자 확인)」이 많아서, 무엇이 사용자 결정이고 무엇이 정리자의 추론인지 가르는 데 무척 신경 쓴 글로 읽혔습니다.
>
> ## 읽으면서 «이건 모르겠다» 싶었던 곳
>
> 1. **"my-team" 이 갑자기 나옵니다.** 붙여 준 팀 구조 글의 이름이라고 짐작했지만, 앞에서 그렇게 소개되지 않았습니다.
> 2. **대장과 지휘자가 같은지 모르겠습니다.** 팀 구조 설명 안에서는 대장이 승인 요청, 배정, 2차 검수를 맡습니다. 그런데 바로 이어서 "지휘자(오케스트레이터)가 HANDBOOK 으로 올린다"고 합니다. 같은 역할을 두 이름으로 부른 것인지, 대장 위에 지휘자가 또 있는 것인지 헷갈렸습니다. 영상의 "상주 대장 + 배정 스크립트"가 들어오면 지휘자가 그중 어느 쪽인지도 열려 있습니다.
> 3. **1차 검수를 누가 하는지 적혀 있지 않습니다.** 검수는 두 번이라고 했는데, 대장이 2차라는 것만 나옵니다. 자체 검수 루프가 1차인지도 모르겠습니다.
> 4. **멈춤 조건 두 개의 관계가 분명하지 않습니다.** "세 번을 넘으면 보고"와 "같은 단계 두 번 연속 실패면 멈춤"이 어떻게 맞물리는지 모르겠습니다. 숫자만 보면 두 번 멈춤이 먼저 걸려서 세 번 규칙이 발동할 일이 없어 보입니다.
> 5. **devbrew 에서 무엇에 해당하는지 모르는 낱말이 있습니다.** 관문의 「화면」 칸, 「테스트 서버 배포 / 실서비스 배포」, 동시성 기준의 「서버 부하」가 그렇습니다. 플러그인 마켓플레이스인 devbrew 에서 각각 무엇을 뜻하는지 읽어 내지 못했습니다.
> 6. **HANDBOOK.md 로 가는 길이 두 개입니다.** 120줄을 넘을 때 오래된 것을 보내는 길과, 두 번 나온 지적을 정식 규칙으로 올리는 길입니다. HANDBOOK 이 보관소인지 정식 규칙집인지 성격이 하나로 잡히지 않았습니다. "팀 규칙 목차는 레포 안 파일"이 이 MEMORY.md 를 말하는 것이라고 짐작했지만 확실하지 않습니다. 자동 메모리와 이름이 겹친다는 지적만 있고 어떻게 할지는 없습니다.
> 7. **P8 을 무엇으로 바꾸는지 적혀 있지 않습니다.** 「바꾼다」고만 했습니다. CLAUDE.md 에도 같은 문장이 있는데 그것도 함께 바뀌는지 모르겠습니다.
> 8. **다른 기계에 있는 지휘자끼리 무엇으로 글을 주고받는지 모르겠습니다.** 계약에 들어갈 항목만 나열돼 있고, 경로는 전혀 짐작할 단서가 없습니다.
> 9. **「어느 정도 걷어낸다」의 정도와 대상을 모르겠습니다.** 어떤 기존 장치를 얼마나 걷어내는지 적혀 있지 않습니다.
> 10. **「(사용자 확인)」이 없는 문장이 확정인지 모르겠습니다.** 첫 문단의 문제 진술, 토큰 세 용도 문단, 리프레시 문단이 그렇습니다. 토큰 문단은 "사용자는 셋 다 골랐다"고 써서 확정처럼 보이지만, 표시는 없습니다.
> 11. **「적절한 순간」, 「너무 자주는 하지 않고」에 기준이 없습니다.** 인터뷰가 정할 몫인지도 적혀 있지 않습니다.
> 12. **승인을 해시에 묶는 대상이 무엇인지 모르겠습니다.** 설계문서인지, 계획인지, INTENT.md 인지 알 수 없습니다.
> 13. **「작업 목록」이 무엇인지 모르겠습니다.** 터미널의 Claude Code 할 일 목록을 말하는지, STATUS.md 같은 파일을 말하는지 한 가지로 잡히지 않았습니다.
> 14. **규모가 한 건으로 다룰 만한지 모르겠습니다.** 모든 단계의 팀화, 기계를 넘는 지휘자 소통, 메모리 체계, 토큰 계측, P8 개정이 함께 담겨 있습니다. 인터뷰 결과가 설계문서 하나여야 하는지, 로드맵 여러 에픽으로 쪼개야 하는지에 대한 언급이 없습니다.
