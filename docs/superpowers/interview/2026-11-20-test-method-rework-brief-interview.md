## 0. 한눈에

이 레포를 개발할 때 쓰고 돌리는 테스트가 너무 길다 — 도는 시간, 테스트 코드의 양, 쓰고 지키는 절차 셋 다. 맷 포콕의 테스트 주도 개발 skill 을 기준으로 이것을 해소한다.

인터뷰가 잰 결과 원인은 서로 달랐다(앞 회의에서 답한 긴 것 셋은 도는 시간 · 테스트 코드의 양 · 쓰고 지키는 절차이고, 이 인터뷰가 우선순위를 물으며 보인 셋은 스위트 시간 · 글자에 묶인 테스트 · 쓰는 절차다). 스위트 시간은 테스트 수가 아니라 느린 테스트 스무 개 안팎과 두 번 · 겹쳐 도는 구조에서 든다. 글자에 묶인 테스트는 문서를 읽는 테스트의 주된 모양이지만 대부분 2초 안에 끝난다. 테스트를 먼저 통째로 쓰는 절차는 이 레포 밖 skill 이 정한다. 그래서 일을 넷으로 나눴다 — 스위트 시간(먼저, 따로) · 기준과 규칙 문서 · 문구 확인을 대신 지킬 장치 · 있는 테스트 정리. 기준과 규칙 문서는 그 문서를 쥔 진행 중인 두 에픽의 머지를 확인하는 블록(E0)이 닫힌 뒤에 연다.

확정은 스물여섯이다(§2). 규칙 문서를 고치는 에픽은 그 문서를 쥔 진행 중 에픽 둘 뒤에 열고, 같은 문서를 예약한 뒤의 둘에는 알리기만 한다. 열린 채 설계로 넘긴 결정은 여덟이다(§3 — OQ4 · OQ17 · OQ18 · OQ19 · OQ20 · OQ21 · OQ22 · OQ23). 스위트 시간은 본 부분 기준으로만 쟀다 — 겹치지 않은 한 바퀴와 python 테스트 묶음의 시간은 재지 못했다.

✎ C19–C22 · C25 는 framing 회의에서 사용자가 라벨을 고른 답이고, 문장은 그 회의의 확인 질문에서 고른 풀이다(Phase 0 확인). 그 밖은 이 인터뷰의 질문에서 고른 선택지이고, 대부분 인터뷰어가 권한 쪽이다 — 질문의 답 가운데 사용자가 직접 적은 말은 framing 의 「맷폭콕이 이야기한거」 하나뿐이다(첫 요청 문장도 사용자가 직접 친 글이다 — §6 S1).

✎ C1 의 「본문 전체」 가운데 이 레포에 그대로 안 맞는 항목이 둘 있다 — 「테스트할 자리를 사용자와 미리 합의한다」(이 레포의 계획과 구현은 하위 agent 가 사람 없이 돌린다)와 글을 시험하는 법(그 skill 은 코드를 시험하는 법만 다룬다). C5 가 이 둘을 고쳐 적는 쪽으로 정했다.

✎ C25 의 넷째 「기대값을 검사 대상과 같은 식으로 내는 테스트」는 이 인터뷰가 따로 조사하지 않았다 — 기준을 적는 일(E2)과 있는 테스트를 정리하는 일(E4)이 이 문제를 맡는다.

✎ C9 · C16 의 「느린 테스트」 숫자는 본 부분 기준이다 — 스위트가 도는 셸 테스트 310개 가운데 220개를 봤고 python 테스트 파일 96개는 못 봤으며, 관찰 내내 스위트가 둘 이상 겹쳐 돌았다.

E1 의 설계는 겹치지 않은 한 바퀴의 시간부터 다시 잰다.
