# 팀 파일 규약 · Design

> 로드맵 하나를 팀 하나로 보고, 팀의 문서를 `roadmaps/<로드맵>/` 한곳에 모은다. 과제(에픽이나 단순 작업)마다 `jobs/<과제>/` 폴더를 두고 그 안의 INTENT.md 와 results/ 로 지시와 결과를 주고받는다. 규칙은 팀의 RULES.md 와 팀 간 공유 HANDBOOK.md 두 곳에만 쌓고, 일꾼에게는 스크립트가 고른 시작 묶음으로만 닿게 한다.

## Context / Why

지금 spec-distill 의 산출물은 단계별 폴더에 흩어져 있다 — 인터뷰는 `interview_dir`, 설계문서는 `specs_dir`, 계획은 `plans_dir`, 에픽 묶음은 `roadmaps_dir/<로드맵>/`(`repo_defaults.py`). 에픽 하나를 따라가려면 네 폴더를 오가고, 단계 계산은 superpowers 가 쓰는 형식(`**Spec:**` 줄 · 설계문서 안 `## 판정` · `## 구현 대조` · `## 지휘 기록`)을 읽어 잇는다(`roadmap_status.py` `find_specs` · `branch_plans` · `progress`).

담당자에게 가는 글은 리더가 손으로 채우는 틀(`conductor-dispatch.md`)이고, 돌아오는 것은 마지막 보고 메시지다 — 판정 전체와 수용 기준 보고 전체를 메시지에 싣는다. 메시지는 세션이 끝나면 사라지고, 길고, 다시 시작한 담당자는 그것을 읽을 수 없다.

P1 측정(`docs/superpowers/roadmaps/2026-11-14-conductor-context-economy-brief/token-baseline.md`, PR #275)에서 하위 agent 는 캐시 쓰기의 92% 를 쓰고 캐시를 5분만 유지한다. 같은 백업에서 하위 agent 응답 가운데 직전 응답과 5분 넘게 벌어진 2% 가 하위 캐시 쓰기의 절반 넘게를 낸다(세션 A 57.4% · 세션 C 25.4% — 이 설계 대화에서 잰 값, 2026-11-14). 오래 기다린 담당자가 큰 맥락을 처음부터 다시 쓰기 때문이다. 다시 시작할 때 읽을 것이 작은 파일 몇 개여야 한다.

이 설계 대화에서 한 가지가 더 드러났다. 사용자가 framing 에서 붙여 넣은 폴더 구조와 행동양식은 seed 의 산문 → brief 의 번호 항목 → 에픽 묶음으로 가며 줄었고, R1 묶음에는 역할 이름 목록조차 없었다. 그 빈자리를 설계가 지어낸 이름으로 채웠고 사용자가 「내 의도가 interview지나면서 의역된거 같아서 그래」 라고 짚었다. 과제 파일은 원자료를 글자 그대로 싣고, 설계는 원자료 전체를 기준으로 대조해야 한다.

## Goals

- 팀(로드맵)의 문서가 한 폴더에 모이고, 과제 하나는 폴더 하나로 따라갈 수 있다.
- 일꾼이 시작하거나 다시 시작할 때 읽을 것이 정해져 있고 작다 — 역할 문서 · INTENT.md · 맞는 규칙 줄.
- 결과는 메시지가 아니라 과제 폴더의 파일로 남고, 리더가 산출물과 대조한 뒤에만 단계가 넘어간다.
- 사용자 원자료가 과제 파일까지 글자 그대로 닿고, 설계가 바꾼 것은 바꿨다고 표시된다.
- 규칙 파일은 쌓이기만 하지 않는다 — 바이트 예산 · 반증 삭제 · 반례 확인 뒤 승격.
- 단계 계산은 과제 폴더의 파일과 git 으로 하고, 다른 작업 방식의 형식 읽기는 변환기 한 곳에 모인다.

## Non-goals

- 지휘 절차서(단계표 · 지시서 · 실행기 칸 · 관문 다섯 칸)의 개편 — R2.
- 리더 상태 브랜치 · STATUS.md 의 내용 · 편지함의 형식과 계약 — R3. 이 설계는 그 파일들의 자리만 정한다.
- 현황 · 감시 mod — R4. 옛 기록과 도는 로드맵을 새 구조로 옮기기 — R5.
- 「인터뷰」 명칭을 「의도 싱크」로 바꾸기(skill 호출 이름 · 설정 키 · 머리 키) — 다른 로드맵으로 넘겼다(§결정 기록 B13).
- `.claude/rules` 경로 조건 규칙, 팀마다의 `tools/` 폴더, 팀 공통 CLAUDE.md, QUALITY_GATES.md 파일.

## Anti-goals

- 과제 파일이 원자료의 의역본이 되는 것. 과제 파일은 원자료를 다시 쓰지 않고 줄 범위로 가리킨다.
- 규칙 파일이 「그때는 맞았던」 줄을 품은 채 근거로 쓰이는 것.
- 파일이 있다는 것만으로 단계가 끝난 것으로 세어지는 것.
- 옛 형식 로드맵이 새 계산에서 조용히 「계획 없음」으로 세어지는 것.

## Constraints

- 경로 · 예산 · 역할 이름 같은 값은 한 곳에서 도출하거나 레포 설정에서 읽는다. 스크립트 곳곳에 리터럴을 박지 않는다.
- 플러그인은 다른 레포에도 설치된다. 팀 파일의 틀은 플러그인이 싣고, 대상 레포에는 없을 때만 깔며 `.claude/` 아래에는 쓰지 않는다.
- 역할 문서의 「하지 않을 일」은 알림이지 집행이 아니다. 막는 것은 도구 권한이고 그 자리는 R2 가 정한다 — 이 설계의 문서는 막는다고 말하지 않는다.
- 이 에픽이 머지된 뒤에도 옛 형식 로드맵(지금 도는 이 로드맵 포함)의 계산 결과는 바뀌지 않는다.
- 사용자에게 보이는 말은 「리더」다(지휘자 · 대장이 아니다). skill 이름 `epic-conductor` 는 이 설계가 바꾸지 않는다.

## Approaches

산출물을 모으는 길 셋을 견줬다.

1. **단계별 폴더를 두고 과제 폴더에 색인만.** 고칠 것이 가장 적다. 그러나 흩어짐이 그대로이고, 다시 시작하는 일꾼이 읽을 자리가 여전히 넷이다.
2. **로드맵(팀) 폴더 하나에 모으기 — 고른 길.** `roadmaps/<로드맵>/jobs/<과제>/` 에 INTENT.md · 설계 · 계획 · 결과가 함께 있다. 대가는 경로 설정과 테스트 수십 개의 고침, 그리고 옛 형식과 함께 도는 기간이다.
3. **묶음 파일을 그대로 INTENT.md 로 이름만 바꾸기.** 생성기 고침이 작다. 그러나 240줄짜리 번호 항목을 일꾼이 시작할 때마다 읽고, 원자료 의역 문제가 그대로 남는다.

사용자가 2번을 골랐다 — 「roadmaps는 가장 밖에 두도록 하자」 · 「한곳에 모으란 말도 있었으니까」. 2번 안에서 팀 폴더의 모양은 사용자가 붙여 넣은 my-team 구조에서 출발했고, 바꾼 것은 §원문 대조 표에 근거와 함께 있다.

## 설계

### §1 팀 폴더

```
REVIEW.md                        레포 맨 위 — Claude Code 공식 리뷰 지시 파일
roadmaps/                        팀들의 집 (설정 키 roadmaps_dir)
  HANDBOOK.md                    승격한 규칙 — 팀 간 공유
  leader/CLAUDE.md               역할 문서 — 팀 간 공통
  designer/CLAUDE.md
  writer/CLAUDE.md
  worker/CLAUDE.md
  <로드맵>/                      팀 하나
    roadmap.md                   에픽 지도 (머리말 layout: team)
    RULES.md                     팀 규칙 목차
    intent/                      원자료와 의도 싱크 결과
    STATUS.md · inbox/           리더의 현황 · 편지함 (내용은 R3)
    jobs/<과제>/                 과제 폴더
```

파일마다 적는 것 · 쓰는 사람 · 정본이 사는 곳을 못 박는다. 같은 경로가 여러 브랜치에 사본으로 있으므로 「어느 것을 읽나」가 정해져 있지 않으면 낡은 사본을 읽는다.

| 파일 | 무엇만 적나 | 쓰는 사람 | 정본 |
|---|---|---|---|
| `REVIEW.md` | 리뷰가 지적할 것 · 심각도 · 건너뛸 것 | 사람(PR) | 기본 브랜치 |
| `HANDBOOK.md` | 반례를 확인하고 승격한 규칙 | 리더(PR) | 기본 브랜치 |
| `<역할>/CLAUDE.md` | 그 역할의 할 일 · 하지 않을 일 | 사람(PR) | 기본 브랜치 |
| `roadmap.md` | 에픽 지도 · 결정 기록 · 재분해 이력 | 생성기 · 리더 | 기본 브랜치 |
| `RULES.md` | 이 팀에서 나온 규칙, 한 줄에 하나 | 리더 | 기본 브랜치 |
| `intent/` | 원자료(줄이지 않음) · brief | 생성기 | 기본 브랜치 |
| `jobs/<과제>/INTENT.md` | 목표 · 지시 원문 · 하지 않을 것 · 결정 기록 | 생성기(한 번) · 리더(결정 기록) | 과제 브랜치 끝, 머지 뒤 기본 브랜치 |
| `jobs/<과제>/` 의 설계 · 계획 · `results/` | 그 과제의 산출물 | 그 단계의 일꾼 | 과제 브랜치 끝, 머지 뒤 기본 브랜치 |
| `STATUS.md` · `inbox/` | (R3) | (R3) | 리더 상태 브랜치(R3) |

기본 브랜치가 정본인 파일은 스크립트가 작업 폴더가 아니라 `origin/HEAD` 에서 읽는다 — 지금 로드맵 읽기와 같은 길이다. 과제 브랜치에 있는 `RULES.md` 는 가지를 딴 날의 사본이고 읽지 않는다.

`roadmaps/` 바로 아래에는 역할 폴더와 로드맵 폴더가 함께 있다. 로드맵은 「`roadmap.md` 가 있는 폴더」로 세고, 역할 이름(`leader` · `designer` · `writer` · `worker`)은 로드맵 폴더 이름으로 받지 않는다.

`STATUS.md` 와 `inbox/` 를 팀 폴더 바로 아래에 둔 것은 작성자 제안이다 — 역할 문서가 `roadmaps/leader/` 로 나가 `leader/` 가 두 곳에 생기는 것을 피했다.

### §2 과제 폴더와 INTENT.md

과제는 에픽이거나 단순 작업(로드맵 밖 수리 · 정리)이다. 어느 쪽이든 과제 폴더 없이 도는 일은 없다.

```
jobs/<과제>/
  INTENT.md          반드시
  results/           반드시
  sources.md         에픽만 — §4
  design.md          설계를 거치는 과제만
  plan-<n>.md        계획이 있는 과제만
```

INTENT.md 의 머리와 네 칸:

```
---
type: job
job: R3
kind: epic            # epic | task
roadmap: roadmaps/<로드맵>/roadmap.md
branch:               # task 만 채운다 — 에픽의 브랜치는 로드맵 블록의 `브랜치:` 가 정본이다
paths: []             # task 만 채운다 — 에픽의 고칠 자리는 로드맵 블록의 경로 예약
---
```

머리 아래에 2단계 제목 넷이 이 순서로 온다 — 「목표」 · 「지시 원문」 · 「하지 않을 것」 · 「결정 기록」.

- **목표 · 하지 않을 것** — 에픽은 로드맵 블록의 의도 · 범위에서, 단순 작업은 리더가 사용자 말에서 옮긴다.
- **지시 원문** — 원자료의 글을 다시 싣지 않고 가리킨다. 이 과제에 닿는 부분을 `intent/original.md` 의 줄 범위로 적는다(예: `intent/original.md 23–57행 · 75–87행`). 칸의 첫 줄은 「전체 그림에서 이 과제의 자리」다 — 원자료의 어느 부분이 이 과제 몫이고 나머지가 어느 과제로 갔는지 한두 줄. 단순 작업은 받은 말을 이 칸에 그대로 적는다 — 그 말의 집이 여기다.
- **결정 기록** — 덧붙이기만 한다. 줄 꼴은 `- <종류> · <YYYY-MM-DD> · 「원문 또는 내용」` 이고 종류는 `spec 승인` · `병렬 답` · `계획 검토` · `결과 받음` · `예약 밖 변경` · `넘김 확인` · `결정` 이다. 지금 설계문서 `## 지휘 기록` 이 받던 줄이 같은 꼴로 여기 온다. 쓰는 사람은 리더 하나이고, 일꾼이 그 브랜치에서 일하는 동안은 지금처럼 쌓아 두었다가 돌아온 뒤 옮긴다(같은 worktree 에 두 writer 를 두지 않는다).

INTENT.md 는 생성기가 한 번 만들고 다시 쓰지 않는다. 로드맵을 다시 나눠 그 과제의 목표 · 범위가 바뀌면 생성기는 고칠 내용을 화면에 내고 멈춘다 — 리더가 사용자 승인 뒤 손으로 고치고 결정 기록에 한 줄을 남긴다. 스크립트와 사람이 한 파일을 번갈아 쓰면 한쪽이 덮어쓰기 때문이다.

일꾼은 INTENT.md 를 고치지 않는다. 일꾼의 결정은 결과 파일(§5)에 남는다.

**한 번만 짓는다.** INTENT.md 가 짧은 것은 지시 원문 · 설계 자료 · 결과 · 테스트 결과를 다시 싣지 않고 파일 경로로 가리키기 때문이다. 같은 내용이 두 곳에 있으면 주고받는 사이에 어긋난다 — 이 로드맵의 brief 와 묶음이 그렇게 어긋났다. 내용마다 집을 하나로 정하고 나머지는 경로로 가리킨다.

| 내용 | 집 | 다른 곳이 가리키는 법 |
|---|---|---|
| 사용자 원자료 | `intent/original.md` | INTENT.md 지시 원문 · 설계문서 원문 대조가 줄 범위로 |
| 과제의 목표 · 하지 않을 것 | INTENT.md | 설계 · 계획 · 시작 묶음이 경로로 |
| 번호 항목(제약 · 열린 질문 · 근거) | `sources.md` | 설계문서 번호 대조가 번호로 |
| 설계 · 계획 | `design.md` · `plan-<n>.md` | 같은 폴더라 따로 가리키지 않는다 |
| 진행 · 판정 · 수용 기준 보고 | 결과 파일 | 결정 기록의 받음 줄이 경로와 커밋으로 |
| 테스트 결과 | 스위트 대조가 다시 돌린 것 | 결과 파일은 테스트 출력을 싣지 않는다 |
| 리더와 사람의 결정 | INTENT.md 결정 기록 | 다른 문서는 그 줄을 다시 적지 않는다 |
| 규칙 | RULES.md · HANDBOOK.md | 시작 묶음이 그때 고른 줄을 내고 남기지 않는다 |

사본을 피하지 못한 곳이 셋이고, 각각 어긋남을 잡는 검사를 둔다.

- `intent/original.md` 는 앞단이 `intent/` 에 바로 쓰게 되기 전까지 audit · brief 에서 옮긴 사본이다 — 옮긴 구간이 출처와 바이트가 같은지 대조한다(AC5).
- `sources.md` 는 brief 의 번호 항목에서 생성기가 낸 것이다 — 사람이 고치지 않고 생성기가 다시 쓴다.
- 로드맵 블록의 의도 · 범위는 INTENT.md 의 목표 · 하지 않을 것과 같은 글이다 — 다르면 단계 계산이 알린다(AC28).

### §3 원자료 — `intent/`

`intent/original.md` 는 사용자가 준 것을 줄이지 않고 옮긴 한 벌이다. 생성기가 로드맵을 만들 때 채운다.

- framing 을 거친 일이면 그 audit 의 원문 절과 질문 전체 절(질문 · 선택지 · 사용자가 답한 것)을 글자 그대로 옮긴다.
- 인터뷰에서 나온 사용자 발화(brief 와 그 audit 의 사용자 원문 절)를 이어 붙인다.
- 머리에 출처마다 경로와 커밋을 적는다. 옮긴 구간은 출처와 바이트가 같아야 한다(AC5).

brief · audit 파일 자체를 `intent/` 로 옮기는 일은 이 설계가 하지 않는다 — 의도 싱크 skill 이 쓰는 자리를 바꾸는 일이라 이름 바꾸기와 함께 간다(§미룸). 그때까지 `intent/` 에는 `original.md` 와, brief · audit 의 지금 경로를 적은 `README.md` 가 있다.

설계하는 쪽은 `intent/original.md` 전체를 읽는다. INTENT.md 가 가리키는 줄 범위는 일꾼용이고, 설계문서의 §원문 대조 표는 전체를 기준으로 채운다.

### §4 `sources.md`

지금 에픽 묶음이 싣던 번호 항목 — 제약 · 열린 질문 · 웹 근거 · 기각 · 위험 · 인터페이스 — 과 그 번호 목록(`ids`)이다. 설계할 때와 번호 대조에만 읽는다. 일꾼의 시작 묶음에는 들어가지 않는다.

```
---
type: job-sources
job: R3
ids: [C1, D12, OQ22, …]
---
```

사용자 원문 절은 싣지 않는다 — `intent/original.md` 가 정본이다. 묶음마다 seed 전문을 되풀이 싣던 것이 사라진다.

### §5 결과 파일 — `results/`

일꾼의 보고는 메시지가 아니라 파일이다. 단계 하나의 시도 하나가 파일 하나다.

```
results/<단계>[-plan-<n>]-<시도>.md

---
type: job-result
stage: implement
plan: 1               # 계획이 있는 단계만
attempt: 2
role: worker
head: <이 결과가 가리키는 커밋>
bundle_at: <시작 묶음을 만든 기본 브랜치 커밋>
---
```

본문은 짧게 쓴다. 기계가 읽는 줄은 넷이다.

- `Task <n>/<전체>: 끝|막힘 — <커밋>` — 계획의 task 하나를 끝낼 때마다 덧붙이고 그 커밋과 함께 커밋한다.
- `Ruling: …` — 일꾼이 내린 판정.
- `AC<n>: 구현됨|미룸|빠짐 — 근거`
- `규칙 반증: <규칙 줄 머리> — <무엇을 봤나>`

결과 파일은 단계를 시작할 때 만들고 끝날 때까지 덧붙인다 — 도는 중에도 어디까지 왔는지가 파일에 있다. 막히면 지어내지 않고 `results/BLOCKED.md` 에 적고 끝낸다. 반려는 검수 결과 파일의 첫 줄에 한 줄로 쓴다 — 어디서 · 무엇이 · 어떤 기준에 걸렸나.

단계 이름은 넷으로 시작한다 — `design` · `plan` · `implement` · `review`. `team_layout.py` 한 곳에 두고 `--stage` 와 결과 파일 머리를 이 집합으로 검사한다. 「구현 끝」은 `implement` 결과에, REVIEW.md 는 `review` 에 걸린다. R2 의 단계표가 서면 이 집합의 출처를 단계표로 바꾼다 — 바꿀 곳이 한 곳이다(작성자 판단). 관문 다섯 칸을 결과 파일의 어떤 칸으로 둘지는 R2 가 정한다(§미룸).

결과 파일은 일꾼이 과제 브랜치에 커밋한다 — worktree 가 지워져도 남는다. 일꾼이 쓸 수 있는 파일이므로 그대로 판정 근거로 쓰지 않는다. 리더는 스크립트로 대조한다.

- `head` 커밋이 과제 브랜치에 실제로 있다.
- 같은 단계의 더 새 시도가 없다.
- `AC<n>:` 줄이 설계문서의 수용 기준과 맞는다(지금의 구현 대조 검사).
- 테스트는 스위트 대조가 다시 돌린다(지금 그대로).

대조가 끝나면 리더가 INTENT.md 결정 기록에 `- 결과 받음 · <날짜> · 「<결과 파일> · <커밋> · <대조 첫 줄>」` 을 남긴다. 단계는 이 줄로 넘어간다(§10).

### §6 역할 문서

`roadmaps/<역할>/CLAUDE.md` 넷이다 — leader · designer · writer · worker. 사용자가 붙인 구조의 역할에서 검수 역할은 뺐고(§8) 문서 역할 폴더는 `docs` 대신 `writer` 로 부른다(작성자 제안 — 레포의 `docs/` 와 헷갈린다).

문서는 두 칸이다 — `## 할 일` · `## 하지 않을 일`. 첫 줄에 「이 문서는 알림이다. 막는 것은 도구 권한이다」를 둔다.

- 플러그인이 틀 넷을 싣는다. 틀의 내용은 사용자가 붙인 예시에서 출발한다.
  - 할 일: 「과제마다 INTENT.md 부터」 · 「설계안 승인 뒤에 코드」 · task 하나를 끝낼 때마다 결과 파일에 진행 줄 · 받은 규칙은 쓰기 전에 지금 확인.
  - 하지 않을 일: 「실서비스 배포」 · 「다른 폴더 파일 고치기」 · 「승인 전 코딩」.
  - 리더의 틀에 적을 것 가운데 원자료의 「등록만 하고 직접 만들지 않는다」 는 아직 정해지지 않았다(§미룸).
- 생성기는 `roadmaps_dir` 에 역할 폴더가 없을 때만 틀을 깔고, 있으면 건드리지 않는다.
- 역할 문서는 저절로 실리지 않는다. 일꾼에게는 시작 묶음이 경로를 준다(§9). 세션을 그 역할 폴더에서 띄우면 Claude Code 가 저절로 읽지만 그 길을 쓸지는 실행기 칸을 정하는 R2 의 몫이다.

### §7 RULES.md 와 HANDBOOK.md

한 줄에 규칙 하나다.

```
- [테스트] 고친 곳엔 테스트 먼저 · 조건: 역할=worker, 단계=implement · 출처: R3 결정 기록 2026-11-20 · 확인: 테스트 명령을 돌려 본다
```

- 칸은 표지(`조건:` · `출처:` · `확인:` · `반례 확인:`)로 가른다. `출처` 와 `확인` 은 반드시 있고 `조건` 은 없으면 「늘」이다.
- `조건` 의 키는 `역할` · `단계` · `경로` 셋이고 값이 여럿이면 `|` 로 잇는다. `경로` 는 글롭이다.
- 같은 지적이 다시 나오면 새 줄을 쓰지 않고 그 줄의 `출처` 에 덧붙인다(`출처: A | B`).

운영:

- **쓰는 사람은 리더뿐이다.** 일꾼은 결과 파일에 `규칙 반증:` 줄을 남기고, 리더가 확인해 지운다.
- **쓰기 전에 지금 확인한다.** 규칙을 받은 쪽은 `확인` 칸대로 지금도 맞는지 본 뒤에 근거로 쓴다 — 역할 문서 틀의 할 일에 이 문장을 둔다.
- **바이트 예산.** RULES.md 8KB · HANDBOOK.md 16KB 가 기본이고 레포 설정으로 바꾼다. 넘으면 검사가 실패하고 「먼저 지우거나 승격하라」고 알린다. 합치기 · 나이로 넘기기 · 새 규칙 맨 위는 하지 않는다.
- **승격.** `출처` 가 둘 이상인 줄이 후보다(한 팀 안의 두 번이어도 된다). 리더가 반례를 찾아보고, 없으면 HANDBOOK.md 로 옮기는 PR 을 낸다. HANDBOOK.md 의 줄은 `반례 확인: <날짜> <무엇을 봤나>` 칸이 반드시 있다. 머지는 사용자가 하므로 그 자리가 사람 확인이다.
- **지우기.** 반증됐거나 낡은 줄은 지운다. 지운 이유는 커밋 메시지에 남는다.

HANDBOOK.md 머리말에 운영 원칙을 둔다 — 「잘못 쌓인 맥락은 없는 것보다 나쁘다. 이 파일의 줄은 쓰기 전에 지금 확인하고, 틀렸으면 지운다.」

`team_rules.py check` 가 형식 · 예산 · 두 파일에 걸친 같은 규칙 글의 중복을 검사하고, `candidates` 가 승격 후보를 낸다.

RULES.md 의 틀은 줄 없이 빈 채로 시작한다. 사용자가 붙인 예시 줄 여섯(「[테스트] 고친 곳엔 테스트 먼저」 등)과 INTENT.md 예시(「로그인 개선」)는 다른 팀의 규칙이라 살아 있는 규칙으로 깔지 않는다. 형식 정본 문서의 예로 글자 그대로 싣는다.

### §8 REVIEW.md

검수 역할 폴더는 두지 않는다. 검수 기준은 레포 맨 위 `REVIEW.md` 에 둔다 — Claude Code 의 관리형 Code Review 가 읽는 공식 파일이고(레포 맨 위가 기본, 하위 폴더의 것은 그 폴더 아래 변경에만 덧붙는다, 로컬 `/code-review` 는 읽지 않는다 — code.claude.com/docs/en/code-review-customize, 2026-11-14 확인), 팀 폴더 안에 두면 코드 변경의 리뷰에 닿지 않는다.

- 팀마다 다른 검수 규칙은 그 팀 RULES.md 의 줄로 둔다(`조건: 단계=<검수 단계>`).
- devbrew 의 검수 단계(통합 리뷰 · 구현 중 리뷰 · quality-gates)는 하위 agent 라 이 파일이 저절로 실리지 않는다. 시작 묶음이 검수 단계에 경로를 싣는다(§9).
- 처음 내용은 사용자 원자료의 검수 문장에서 옮긴다 — 테스트가 하나라도 실패하거나 실제로 돌려 봤을 때 잘못됐으면 반려, 반려는 어디서 · 무엇이 · 어떤 기준에 걸렸는지 한 줄.

### §9 시작 묶음

리더는 일꾼에게 줄 글을 손으로 짜지 않는다. 스크립트 하나가 만든다.

```
start_bundle.py --roadmap <로드맵> --job <과제> --role <역할> --stage <단계>
```

출력:

```
역할 문서: roadmaps/worker/CLAUDE.md
과제: roadmaps/<로드맵>/jobs/R3/INTENT.md
읽을 것: <그 단계가 읽는 과제 폴더 파일>
쓸 것: roadmaps/<로드맵>/jobs/R3/results/implement-plan-1-1.md
검수 기준: REVIEW.md            ← 검수 단계만
규칙 (<기본 브랜치 커밋>):
- [테스트] 고친 곳엔 테스트 먼저 · 확인: …
```

- 규칙 줄은 기본 브랜치의 RULES.md 와 HANDBOOK.md 에서 `조건` 이 맞는 것만 고른다. 역할 · 단계는 글자가 같으면 맞고, 경로는 과제의 고칠 자리와 글롭이 겹치면 맞는다. 조건이 없는 줄은 늘 실린다.
- 고른 규칙 줄의 합이 묶음 예산(기본 4KB, 단위는 UTF-8 바이트)을 넘으면 자르지 않고 실패한다 — 조용히 빠지는 규칙이 없게 한다.
- 같은 커밋 · 같은 입력이면 같은 바이트가 나온다. 묶음은 파일로 남기지 않고, 결과 파일 머리의 `bundle_at` 이 그 커밋을 적는다.
- `읽을 것` 은 단계 이름으로 정해지는 과제 폴더 파일이다. 어느 단계가 무엇을 읽는지의 표는 R2 의 단계표가 준다. 그 표가 없는 동안은 INTENT.md 와 과제 폴더에 있는 설계 · 계획 파일을 모두 적는다.
- 리더도 같은 스크립트를 쓴다(`--role leader`). 압축 뒤 다시 시작할 때 자기 규칙 줄을 이렇게 다시 받는다.

`쓸 것` 의 시도 번호는 그 단계의 결과 파일 가운데 가장 큰 번호 다음이다.

### §10 단계 계산

`roadmap.md` 머리말의 `layout` 이 형식을 가른다. 없으면 옛 형식이고 계산은 지금 그대로다. `team` 이면 아래 표를 쓴다. 모르는 값이면 세지 않고 「모르는 형식」으로 멈춘다(지금의 검사 불가와 같은 종료 코드).

| 단계 | 근거 |
|---|---|
| 대기 · 준비 | INTENT.md 있음. 기대는 과제가 끝났으면 준비 |
| 설계 중 | 과제 브랜치 있음, 결정 기록에 `spec 승인` 줄 없음 |
| 계획 | `spec 승인` 줄 있음, 계획 파일이 없거나 계획 뒤 커밋이 없음 |
| 구현 중 | 계획 파일이 있고 그 뒤에 커밋이 있음. 진행 `<n>/<전체>` 는 과제 브랜치 끝의 결과 파일에 있는 마지막 `Task` 줄 |
| 구현 끝 | 계획마다 `결과 받음` 줄이 있음 |
| PR · 머지됨 · 일부 머지 | 지금처럼 git 과 PR 캐시에서 |

- 설계가 없는 과제(단순 작업 · 조사 흐름)는 준비 → 진행 중(브랜치 있음) → 결과 받음 → PR · 머지됨이다.
- 결과 파일이 있는데 `결과 받음` 줄이 없으면 단계는 그대로이고 「결과 있음 · 받음 없음」을 알린다.
- 구현 중에는 task 몇 개 중 몇 번째인지를 함께 보인다. `Task` 줄이 아직 없으면 숫자 없이 「구현 중(진행 줄 없음)」 이다. 변환기가 그 작업 방식의 원장을 읽을 수 있으면 지금처럼 그 마지막 줄과 고친 시각을 덧붙인다.
- 판정 줄(`Ruling:`)은 결과 파일에서 읽는다. 넘김과 미룸은 지금처럼 설계문서의 `## 미룸` 표에서 읽는다.
- 과제 브랜치가 바꾼 파일을 그 과제의 고칠 자리와 견준다. 고칠 자리(에픽은 경로 예약, 단순 작업은 INTENT.md 머리의 `paths`) · 공유 파일 · 자기 과제 폴더 밖의 파일은 「예약 밖 변경」으로 알린다. 다른 과제가 예약한 파일을 건드리면 지금 있는 「경로 예약 위반」이 그대로 나온다. 둘 다 알림이고 종료 코드를 바꾸지 않는다.
- 단순 작업 과제(`kind: task`)는 에픽 지도 뒤에 「로드맵 밖 과제」로 따로 보인다. 에픽 지도는 고치지 않는다. `job new` 는 그 작업의 브랜치에 과제 폴더를 만들어 첫 커밋으로 둔다 — 등록만을 위한 PR 을 열지 않는다. 계산은 브랜치 끝들(로컬과 origin)을 훑어 기본 브랜치에 없는 이 로드맵의 과제 폴더를 찾고, INTENT.md 머리의 `branch` 가 그 브랜치 이름과 같은 것만 센다. 머지되면 기본 브랜치에서 읽힌다.
- 진행 숫자는 단계 글자에 넣지 않는다. 현황 화면이 단계 글자를 그대로 견주기 때문이다. 계산 결과에 따로 된 칸(끝난 수 · 전체)으로 싣고, 현황은 단계 뒤에 덧붙여 보인다.
- 브랜치가 여럿인 에픽은 지금 규칙대로 로드맵 블록의 `브랜치:` 순서가 계획 순서다 — n 번째 브랜치가 `plan-<n>.md` 를 맡는다. 「구현 끝」 은 브랜치마다 그 계획의 `결과 받음` 줄로 재고, 「일부 머지 n/m」 은 지금처럼 브랜치 수로 센다. 결정 기록은 지금 진행 중인 계획의 브랜치에 덧붙고, 다음 브랜치는 앞 브랜치(머지됐으면 기본 브랜치)에서 갈라지므로 이어받는다.

다른 작업 방식의 형식을 읽는 일은 변환기 한 곳에 둔다. superpowers 맞춤은 둘을 한다 — 설계 · 계획 skill 에 쓸 자리(`jobs/<과제>/design.md` · `plan-<n>.md`)를 알려 주는 문장을 내고, 구현 원장(`.superpowers/sdd/` 의 `Ruling:` 줄)을 결과 파일의 `Ruling:` 줄로 옮긴다. 계획 파일의 `**Spec:**` 줄은 team 형식에서는 읽지 않는다 — 계획과 설계는 같은 폴더로 이어진다. 커밋의 `Spec:` 트레일러는 그대로 두고 `jobs/<과제>/design.md` 를 가리킨다(quality-gates 가 이것으로 설계문서를 찾는다).

### §11 생성기

`roadmap_write.py create --layout team` 이 한 번에 만든다 — `roadmap.md`(머리말 `layout: team`) · `RULES.md`(빈 틀) · `intent/original.md` · `intent/README.md` · 에픽마다 `jobs/<번호>/INTENT.md` · `sources.md` · `results/.gitkeep`, 그리고 `roadmaps_dir` 에 없으면 역할 문서 넷과 `HANDBOOK.md`.

- `--layout` 을 주지 않으면 지금처럼 옛 형식(묶음 파일)을 만든다. 새 형식을 기본으로 켜는 것은 지휘 절차가 새 형식을 따르게 된 뒤이고 R2 가 한다(§미룸).
- 원자료가 먼저다. `roadmap_write.py original --brief <brief>` 가 `original.md` 를 따로 만든다(분해안을 쓰기 전에 부른다). framing audit 는 인터뷰 상태 파일의 seed 경로에서 찾고(seed 와 같은 폴더의 audit), 없으면 `--framing-audit` 로 받고, 그것도 없으면 brief 쪽 사용자 원문만 싣고 그 사실을 머리에 적는다.
- 지시 원문은 분해안이 과제마다 「`original.md` 의 어느 줄 범위」로 적는다. 생성기는 그 범위를 INTENT.md 에 적기만 하고 글을 옮겨 싣지 않는다. `create` 는 과제마다 그 범위의 글을 화면에 낸다 — 사람이 승인할 때 보라는 것이고 파일에는 남기지 않는다. 그 화면을 분해 승인 질문에 끼우는 일은 인터뷰 끝맺음 절차의 몫이라 새 형식을 켤 때 함께 한다(§미룸).
- `original.md` 는 덧붙이기만 한다. 재분해 때 새 사용자 말은 끝에 붙고 앞 줄은 밀리지 않으므로, 다시 쓰지 않는 INTENT.md 의 줄 범위가 그대로 맞는다.
- `update`(재분해)는 새 과제의 폴더는 만들고, 이미 있는 INTENT.md 는 다시 쓰지 않는다(§2). `sources.md` 는 다시 쓴다 — 사람이 덧붙이는 파일이 아니다.
- `job new --roadmap <로드맵> --name <이름> --branch <브랜치> --paths <…>` 가 단순 작업의 과제 폴더를 만든다. 지시 원문은 표준 입력으로 받은 사용자 말 그대로다.

### §12 대조 스크립트

- `check_bundle_coverage.py` — team 형식에서 번호 대조의 정답 출처는 `sources.md` 의 `ids` 다. 구현 대조(`--impl`)는 결과 파일의 `AC<n>:` 줄을 읽는다. 설계문서에 `## 원문 대조` 표가 없으면 한 줄로 알리고, 「바꿈」인데 근거 칸이 빈 행은 얕은 답으로 센다(둘 다 종료 코드를 바꾸지 않는다).
- `spec_review_bundle.py` — `--bundle` 로 그 과제의 INTENT.md 를 받는다. 설계문서 머리 `source_interview` 가 그 경로와 같아야 한다(키 이름은 이름 바꾸기 로드맵이 정할 때까지 그대로 둔다).
- `conductor_ledger.py record` — team 형식이면 줄을 INTENT.md 의 `## 결정 기록` 에 덧붙이고 어디에 썼는지 한 줄로 낸다. 옛 형식이면 지금처럼 설계문서에 쓴다.
- `references/epic-handoff.md` — team 형식의 넘김 줄을 더한다: 묶음 대신 INTENT.md 를 첨부하고, `intent/original.md` 전체와 `sources.md` 를 읽고, 설계문서에 `## 원문 대조` 표를 두고, 바꾼 것은 근거를 적거나 「작성자 제안」으로 표시하라고 지시한다.

### §13 설정과 옮겨 가는 동안

- `roadmaps_dir` 의 기본값은 바꾸지 않는다 — 다른 레포의 옛 로드맵이 깨진다. devbrew 는 레포 설정 파일에 `roadmaps_dir: roadmaps/` 를 적는다. 옛 로드맵을 그 자리로 옮기는 일은 R5 다. 그때까지 devbrew 의 옛 로드맵은 옛 자리에서 읽혀야 하므로, 설정 키 `legacy_roadmaps_dir`(없으면 안 읽음)에 적힌 자리도 로드맵 찾기가 함께 훑는다.
- 새 설정 키: `rules_budget`(기본 8192) · `handbook_budget`(기본 16384) · `bundle_rules_budget`(기본 4096) · `legacy_roadmaps_dir`. 레포 층에서만 받는다.
- 팀 형식의 경로는 새 모듈 하나(`team_layout.py`)가 `roadmaps_dir` 에서 도출한다. 다른 스크립트는 이 모듈을 부른다.
- 설정 해결자(`repo_defaults.py`)는 R2 가 예약한 파일이다. 키 넷을 더하려면 이 에픽도 그 파일을 고쳐야 한다 — R2 는 R1 뒤에 시작하므로 함께 도는 충돌은 없지만 예약 밖이라 재분해 신호로 올린다(§Metadata).

### §14 계획 나누기

크기가 커서 계획 셋으로 나눈다. 순서대로 머지한다.

1. **형식과 생성** — `team_layout.py` · 설정 키 · 형식 정본 문서 · 생성기(`create --layout team` · `update` · `job new`) · `intent/original.md` · INTENT.md 줄 범위 검사. AC1–AC8.
2. **읽기** — 단계 계산 · 알림 · 대조 스크립트 · `record` · 넘김 줄 · superpowers 변환기. AC9–AC17 · AC27 · AC28.
3. **규칙과 시작 묶음** — 역할 문서 틀 · RULES.md 와 HANDBOOK.md 의 형식과 검사 · REVIEW.md · `start_bundle.py`. AC18–AC26.

## 상류 · 하류 연계

- **받는 곳.** 분해 승인(인터뷰 끝맺음)이 `roadmap_write.py create` 를 부른다. 단순 작업은 리더가 `job new` 를 부른다.
- **넘기는 곳.** R2 — 단계표가 시작 묶음의 `--stage` · `읽을 것` 과 결과 파일의 단계 이름 · 관문 칸을 정하고, 보내는 글 틀을 시작 묶음으로 바꾼다. R3 — `STATUS.md` · `inbox/` 의 자리를 받아 내용과 브랜치를 정한다. R4 — 현황이 과제 폴더와 결과 파일을 읽는다. R5 — 옛 묶음 · 설계문서의 지휘 기록을 이 형식으로 옮긴다.
- **되돌아오는 길.** 설계가 과제의 목표 · 범위를 뒤집으면 재분해 절차(`references/redecompose.md`)로 간다. 규칙이 틀렸으면 일꾼의 `규칙 반증:` 줄 → 리더의 삭제로 돌아온다. 결과가 대조에서 어긋나면 `결과 받음` 줄이 없고 단계가 넘어가지 않는다.
- **같은 상태를 읽는 표면.** 과제 폴더를 읽는 것은 단계 계산(`roadmap_status.py`) · 현황 화면(`control_plane.py`) · 번호 대조(`check_bundle_coverage.py`) · spec 리뷰 진입(`spec_review_bundle.py`) · 시작 묶음(`start_bundle.py`)이다. 경로는 모두 `team_layout.py` 에서 온다. 이음매 담당은 리더다.

## Verification Plan

- 스크립트마다 출력 테스트. 단계 표는 단계마다 근거 하나만 다른 픽스처로 가른다.
- 변이 — 원자료 사본 대조(글자 하나 바꾸기) · 줄 범위(파일 밖 범위 · 앞 줄 지우기) · 받음 줄(지우기) · 예산(한 바이트 넘기기) · 조건 맞추기(키 바꾸기 · 뒤집기) · 형식 표시(모르는 값)마다 테스트가 빨개지는지 본다. 지우기뿐 아니라 더하기 · 뒤집기로도 흔든다.
- 옛 형식 회귀 — 변경 전후의 `control_plane.py show` · `show --tasks` · 번호 대조 출력을 지금 도는 로드맵에 대해 통째로 견준다.
- 끝에서 끝 — 임시 레포에서 `create --layout team` → `job new` → `start_bundle.py` → 결과 파일 커밋 → 대조 → `record` 의 받음 줄 → 단계가 넘어가는 것을 한 흐름으로 돈다.
- 전체 스위트는 머지 전 스위트 대조가 돌린다.

## Rejected Alternatives

- **단계별 폴더를 두고 색인만** — 흩어짐이 남는다(Approaches 1).
- **묶음을 통째로 INTENT.md 로** — 일꾼이 매번 240줄을 읽고 의역이 남는다(Approaches 3).
- **원자료 전문을 과제마다 싣기** — 희석은 없지만 일꾼이 시작할 때마다 전문을 읽는다(B10).
- **원자료 발췌를 INTENT.md 에 옮겨 싣고 기계로 같음을 지키기** — 같은 글을 두 번 짓는 것이다. 줄 범위로 가리키면 어긋날 것이 없고 검사도 가벼워진다(B14).
- **팀 CLAUDE.md 로 팀 규칙 저절로 싣기** — 그 팀 폴더의 파일을 읽는 모든 세션에 실리고, 끝난 로드맵의 낡은 규칙이 남는다(B9).
- **역할 문서를 팀마다 사본으로** — 사본이 서로 달라진다(B9).
- **`.claude/rules` 경로 조건 규칙** — 격리 worktree 의 하위 agent 에 실리지 않는다(«cc-worktrees» · S41).
- **파일이 있으면 단계 끝** — 반쪽 파일 · 옛 시도의 파일이 끝남으로 세어진다. 받음 줄로 넘긴다.
- **두 팀에서 나와야 승격** — 로드맵을 하나씩 돌릴 때 승격이 거의 일어나지 않는다(B12).
- **줄 수 상한** — 줄 수는 읽기 비용이 아니다(K3 · S36).
- **팀 폴더 안 REVIEW.md** — 코드 변경의 리뷰에 닿지 않는다(§8).
- **`roadmaps_dir` 기본값을 바꾸기** — 다른 레포의 옛 로드맵이 깨진다.
- **새 형식을 이 에픽에서 기본으로 켜기** — 지휘 절차가 아직 옛 형식을 말한다. R2 가 켠다.
