# R0 — 로드맵 · 조각 묶음 · 상태 계산의 걷는 뼈대 · Design

> 조각을 한 곳에서 보고, 조각마다 받은 번호를 하나도 흘리지 않게 하는 가장 얇은 끝에서 끝까지.

승인된 분해안(brief §7, S47)의 첫 조각 R0 이다. 이번 일의 로드맵과 조각 묶음을 손으로 만들어
걷는 뼈대로 쓰고, 공통 형식 다섯을 정하고, 그 형식을 실제로 한 번씩 지나가는 작은 스크립트 둘을
둔다. 뒤 조각(R1~R9 · R2a)은 이 뼈대 위에서 각자의 장치를 제대로 만든다.

- 입력: interview brief `docs/superpowers/interview/2026-10-11-persistent-explore-pm-decompose-interview.md`
  (audit `….audit.md`). 확정 47 · 잠정 1(D29) · 열린 질문 OQ28~OQ38.
- brainstorming 결정: `## 결정 기록` B1~B5. spec 리뷰 결정: 1라운드 D1.1 · D1.2 · B6 · B7 · 2라운드 D2.3(머지 방식 한계 공시 + 손 기록 대체) · 3라운드 B8(추가 라운드, 참고 지적 반영) · 4라운드 D4.24(첫째 부모 이력) · B9(추가 라운드 닫음).
- 재결정 규약: confirmed 항목은 근거 있으면 보고 후 재결정 가능하고 임의 변경은 금지다.
- 재결정 보고 1건: D28 의 「로드맵(… 상태)」 중 **상태**는 로드맵 파일의 칸이 아니라 계산된 값으로

## Context / Why

brief 는 모든 조각에 「원본 brief + 로드맵 + 조각 묶음」을 넘기고(D39), 조각 spec 이 번호마다 반영
또는 기각+이유를 적고(D24), 전체 조각·순서·의존·단계를 한 곳에서 보게 하라고 한다(C8 · D22).
그 장치들은 R3 · R4 · R6 에서야 제대로 생긴다(OQ38). 그 전에 만드는 조각들이 지금의 brief 넘김으로
가면 이 일이 고치려는 이음매 손실(C2)이 그 조각들에서 그대로 일어난다.

그래서 R0 은 형식을 정의만 하지 않고, 이번 일의 실제 로드맵과 묶음을 손으로 만들어 그 형식 위에서
다음 조각을 걸린다(B1). 걸어 보며 형식을 고친다.

레포에서 확인한 사실(조사 2026-10-11, 출처는 각 줄):

- 상태줄 · 패널 · 작업 목록 통합은 `plugins/` · `shared/` 에 0건이다.
- `TaskCreated` 훅 출력에는 `additionalContext` 가 없다(`docs/superpowers/specs/2026-08-05-agent-transparency-design.md`
  이벤트 표). 상태줄이 받는 `tasks[]` 는 메타데이터뿐이라는 것은 문서 근거이고 실측이 아니다.
- spec 리뷰 프로필의 정답은 「인터뷰 브리프 §2 확정 항목 — frontmatter `source_interview` 가 가리키는 파일」
  이다(`plugins/spec-distill/references/docreview-profiles/design-doc.md:3`). spec-review 는 그 파일을
  슬롯으로 넘기지 않고, 리뷰어가 `source_interview` 를 보고 스스로 Read 한다.
- qg 는 `BASE..HEAD` 커밋의 `Spec:` 트레일러 중 가장 최신 하나를 의도 출처로 읽는다
  (`plugins/quality-gates/scripts/discover-spec.sh:52-55`).
- superpowers SDD 는 `<repo-root>/.superpowers/sdd/<plan-basename>/progress.md` 에 완료 줄
  `Task <N>: complete (…)` 과 `Ruling:` 줄을 남긴다(superpowers 6.4.1 subagent-driven-development).
  계획 문서 머리에는 `**Spec:**` 줄이 있다(superpowers 6.4.1 writing-plans).
- `check_brief.py` 는 `type: interview-brief` 만 받는다. 로드맵 · 묶음 타입은 없다.
- §6 경계는 `plugins/spec-distill/scripts/section6.py` 한 곳이 정한다.

## Goals

- G1. 이번 일의 로드맵 한 장과 조각 묶음(R1~R9 · R2a)이 레포에 git 추적 파일로 있다.
- G2. brief 의 모든 번호 항목이 적어도 한 조각에 배정되고, 모든 사용자 발화가 적어도 한 조각에
  받들어진다 — 기계로 확인한다.
- G3. 조각별 단계가 손으로 쓴 칸 없이 git 에서만 계산되고, 경고가 함께 보인다. 구현 단계 · PR · 혼자
  내린 판정 줄의 회수는 R5 가 붙인다(B6).
- G4. 조각 spec 의 「번호 대조」 표와 묶음의 번호 집합을 맞춰 빠진 번호를 낸다.
- G5. R5 · R6 모양을 정할 실측 셋(M1~M3)이 기록되고, M4 · M5 를 R1 걷기에서 기록할 자리가 있다.
- G6. 조각들이 바꿀 동작을 잠근 테스트 목록과 진행 중 브랜치와의 충돌표가 있고, 그 결과가 로드맵
  의존에 들어가 있다.

## Non-goals

- 묶음 자동 생성 · 인터뷰 안의 분해 판단 — R4.
- 묶음 깊이 검사(D40 의 「답이 구체적인가」) · 축소 · 재분해 감지 · 넘김 글 정리 · spec 리뷰에 묶음을
  정해진 입력으로 넘기기 — R3.
- 상태줄 등 제대로 된 컨트롤 플레인 — R6.
- 구현 중 · 구현 끝 · PR 단계와 혼자 내린 판정 줄의 회수 · 보존 — R5(B6). SDD 는 구현이 깨끗이 끝나면
  실행 기록 폴더를 지우고 판정 줄을 마지막 메시지로만 넘긴다(superpowers 6.4.1 subagent-driven-development).
- 지휘자 skill — R5. R0 의 지휘자는 이 세션이 로드맵 「지휘 절차」 절을 따라 하는 것이고, 장치가 아니라
  절차라는 사실을 로드맵에 밝힌다.
- 외부 플러그인(superpowers) 파일 · 동작 변경(C25 · D26).
- @ 브랜치가 건드리는 파일 변경 — `finishing.md` · `proceed-gate.md` · `spec-review/SKILL.md` ·
  `request-framing/SKILL.md`.

## Constraints

- N1. 사용자 원문은 다시 치지 않는다. 묶음 §6 은 `section6.py` 로 brief §6 과 audit §6 에서 바이트 그대로 옮긴다.
- N2. 두 스크립트는 읽기만 한다. 파일을 쓰지 않고 네트워크에 나가지 않는다.
- N3. 검사 불가를 이상 없음으로 내지 않는다(종료 코드 3).
- N4. git 만 쓴다. `gh` 와 실행 기록은 읽지 않는다(B6).
- N5. 로드맵은 사용자 승인 뒤에만 커밋으로 고친다. 이력은 git 과 로드맵 「재분해 이력」 절이다.
- N6. 버전은 머지 직전에 정한다(spec-distill minor).

## 설계

### §1 산출물

`docs/superpowers/roadmaps/2026-10-11-persistent-explore-pm-decompose/` 아래:

| 파일 | 내용 |
|---|---|
| `roadmap.md` | 조각 블록(P1~P4 · R0~R9 · R2a) · 지휘 절차 · 결정 기록 · 재분해 이력 · 위험 번호표 |
| `R1.md` … `R9.md` · `R2a.md` | 조각 묶음 |
| `measurements.md` | 실측 M1~M5 |
| `locks.md` | 락 지도 · 충돌표 |

`plugins/spec-distill/scripts/` 아래:

- `roadmap_status.py` — 로드맵과 git 을 읽어 조각별 단계 · 경고를 낸다.
- `check_bundle_coverage.py` — 묶음의 번호 집합과 spec 의 「번호 대조」 표를 맞춘다.

brief 와 audit 은 R0 PR 에 함께 커밋한다 — 로드맵과 묶음이 그 둘을 가리키고, 다른 조각의 worktree 가
main 에서 읽어야 한다.

선행 항목 P1~P4 는 승인된 분해안의 「선행 3」(S47)을 로드맵 블록 단위로 나눈 것이다:

| 번호 | 선행 3 의 어느 것 | 내용 | 블록 종류 |
|---|---|---|---|
| P1 | 첫째 | 「다음 세션 @ 명령」 브랜치 머지(`feature/next-session-at-handoff`) | 브랜치 |
| P2 | 둘째 중 qg ⑤ | qg v10 ⑤ 차등 테스트 머지(`feature/qg-v10-differential`) | 브랜치 |
| P3 | 둘째 중 진입 이름 | qg 진입 이름 결정 | 결정 기록 |
| P4 | 셋째 | 옛 훅 쓰기 경로 브랜치의 고아 여부 확인 | 결정 기록 |

둘째의 「쉬운 말 PR 3」은 이미 머지됐다(#198) — 블록을 두지 않고 로드맵 결정 기록에 그 사실만 적는다.
둘째(P2 · P3)는 qg 를 건드리는 조각 앞에만 선다(S51).

### §2 번호 체계 하나

brief 에 이미 있는 번호를 그대로 쓴다: 확정 항목 `C<n>` · `D<n>` · 열린 질문 `OQ<n>` · 레포 근거 `RC<n>` ·
steelman `ST<n>` · 사용자 발화 `S<n>` · 웹 조사 항목은 그 «key».

번호가 없는 위험 줄 15개에만 `K<n>` 을 붙인다. 규칙은 brief §5 의 줄 순서다:
`위험 — 숨은 가정` 7줄이 K1~K7, `위험 — 실패 양식` 7줄이 K8~K14, `위험 — 리뷰 참고` 1줄이 K15.
로드맵 「위험 번호표」가 각 K 옆에 그 줄을 원문 그대로 인용한다. brief 는 고치지 않는다.

번호 없는 기각 줄 넷은 각자를 받드는 확정 항목으로 대조한다 — S1 뒤 절 → C48, S10 외부 부분 → D26,
S19 → C27, 재구성 기각 → C14(brief §2 ✎ 주석의 매핑).

**번호 토큰 문법** — 한 번호는 `(C|D|OQ|RC|K|ST|S)` 뒤에 숫자가 붙은 것이거나 «key» 다. 로드맵의
`항목:` · `발화:` 줄, 묶음 `ids:`, 번호 대조 표의 첫 칸은 모두 번호 여럿을 쉼표 또는 ` · ` 로 나열할 수
있고, 범위 표기(`K1~K7`)는 쓰지 않는다. 검사는 칸을 토큰으로 쪼갠 뒤 집합으로 비교한다.

생략 경고(D24 · D42) · 고아 발화 경고(D41) · 미배정 번호 경고는 모두 「집합의 차」 하나로 잰다.
따로 남는 것은 깊이 검사(D40, R3)뿐이다. brief 리뷰 조언(41df26ba#r1.1)을 이렇게 받는다.

### §3 공통 형식 다섯

**① 조각 묶음** `R<n>.md`

- frontmatter: `type: slice-bundle` · `slice: R<n>` · `roadmap: <경로>` · `source_brief: <경로>` ·
  `ids: [<번호>, …]`.
- 본문 절 번호는 brief 의 절 번호와 같은 뜻이다 — spec 리뷰 프로필이 「§2 확정 항목」을 정답으로,
  「§1 Goal」을 과설계 기준으로 읽기 때문이다:
  §0 역참조 · §1 Goal · Non-goal · §2 제약(배정된 C · D, 번호와 brief 문장) · §3 열린 질문(OQ) · §4 웹 근거(«key») ·
  §5 기각 · 위험(RC · K · ST) · §6 사용자 원문 전부 · §7 이웃 조각과의 인터페이스(받는 것 · 넘기는 것).
- §1 은 두 겹이다. 먼저 「이 조각의 Goal · Non-goal」에 로드맵 블록의 `의도:` · `범위:` 를 글자 그대로 싣고,
  그 아래 「공통 목표」에 brief §1 본문을 글자 그대로 싣는다(D39). 조각 spec 리뷰의 범위 · 과설계 판정이 일
  전체가 아니라 그 조각의 몫을 기준으로 삼게 하려는 것이다.
- §6 은 제목 `## 6. 사용자 원문` 아래에 brief §6 본문, 빈 줄 하나, audit §6 본문을 그 순서로 싣는다(본문은
  `section6.py` 의 규칙으로 뽑는다).
- `ids:` 는 §2~§5 에 실린 번호와 그 조각의 받드는 발화(S)의 합집합이다. 이 번호는 전부 조각 spec 의
  「번호 대조」 표에 나와야 한다.

**② 로드맵** `roadmap.md`

- frontmatter: `type: roadmap` · `source_brief: <경로>`.
- 조각 블록 — 줄 머리말로 기계가 읽는다:

  ```
  ### R1 — 인터뷰 탐색 개편
  - 의도: …
  - 범위: 한다 … / 안 한다 …
  - 의존: R0
  - 브랜치: feature/…
  - 묶음: R1.md
  - 경로 예약: plugins/spec-distill/skills/spec-interview/SKILL.md, …
  ```

  **번호 배정은 한 곳에만 둔다.** 묶음이 있는 블록(R1~R9 · R2a)의 번호는 묶음 `ids:` 에만 있다. 묶음이 없는
  블록은 `묶음: 없음` 이라고 적고, 번호를 블록의 `발화:` · `항목:` 줄에 둔다 — 브랜치 블록 P1 · P2 · R0 은
  여기에 더해 `spec:` 줄에 그 설계문서 경로를 적는다. 확인 · 결정 블록(P3 · P4)은 `브랜치:` 대신 `완료: 결정 기록`
  을 둔다. R1~R9 · R2a 블록의 묶음 파일이 없으면 「묶음 없음」 경고다. 사용자가 배정을 승인할 때(AC4)는
  `roadmap_status.py` 가 낸 조각별 배정 표를 함께 보인다.
- 다른 절: 「지휘 절차」(R5 전까지 이 세션이 따라 할 순서 — §5) · 「결정 기록」(P3 · P4 처럼 브랜치 없는
  항목의 결정과 그 발화 번호) · 「재분해 이력」(바꾼 것과 승인 발화 — D20 · D28) · 「위험 번호표」.
- 상태 칸은 없다(B2).

**③ 컨트롤 플레인 데이터** — `roadmap_status.py` 출력

- 조각마다: 번호 · 단계 · 단계 근거 · 경고 목록. 판정 줄은 R5 가 더한다(B6).
- 전체: 미배정 번호 · 고아 발화 · 경로 예약 겹침 · `origin/main` 마지막 수신 시각.
- 출력은 JSON(`--json`)과 사람용 글(기본) 둘이다.
- 지휘자는 조각 하나에 작업 하나를 둔다 — 제목 「R1 인터뷰 탐색 — 계획」 식. 대기 · 준비는 시작 전, 설계 중 ·
  계획은 진행 중, 머지됨 · 끝남은 완료다. 알 수 없음은 작업 상태를 바꾸지 않고 제목 끝에 「알 수 없음(이유)」을
  붙인다.

**④ spec 리뷰에 넘길 정답**

- 조각 설계문서 frontmatter: `source_interview: <그 조각 묶음 경로>` · `roadmap: <로드맵 경로>`.
- 본문 `## 번호 대조` 표 — 칸 셋: 번호 · 반영/기각 · 반영한 자리 또는 기각 이유.
- 한계(공시): 리뷰어가 `source_interview` 를 보고 스스로 열어야 묶음을 본다. 지시문에 기댄 연결이다.
  정해진 입력으로 넘기기는 R3(D45).

**⑤ 커밋 `Spec:` 표시**

- 조각 구현 커밋에 `Spec: docs/superpowers/specs/<…>-design.md`(레포 상대경로)를 붙인다. qg 가 이미 읽는다.
- 계획 문서의 `**Spec:**` 줄은 상태 계산이 계획과 spec 을 잇는 데 쓴다.
- qg ⑤ 이후 의도 출처 형식과의 정렬은 R2a · R5(OQ31).

**devbrew 밖 레포**(OQ33 의 R0 몫): 경로는 superpowers 관례 `docs/superpowers/` 아래다. 스크립트는 git 만
필요하다(N4). 새 타입 `roadmap` · `slice-bundle` 은 brief 구조 게이트가 아니라 두 스크립트가 검사한다.
머지됨 자동 판정은 merge commit 방식에서만 되고, squash · rebase 레포는 로드맵 결정 기록의 머지 기록으로
대신한다(§4 2 · D2.3). 자동 지원은 R8 이다.

### §4 상태 계산

입력은 로드맵 블록의 `브랜치:` 와 `의존:` 이다.

**로드맵을 읽는 사본** — 기본은 `origin/main` 의 로드맵이다(`git show origin/main:<로드맵 경로>`). 그래서
어느 worktree 에서 돌려도 같은 지도를 본다. 아직 main 에 없는 로드맵(R0 PR 자신 · 테스트)은 `--roadmap-file`
로 작업 트리의 파일을 준다. 승인된 로드맵 수정은 전용 작은 브랜치(`feature/roadmap-<요지>`)와 PR 로
main 에 들어가고, 머지는 사용자가 한다.

**다른 파일을 읽는 사본** — 묶음 · brief · audit 은 로드맵과 같은 사본에서 읽는다(`origin/main`, 또는
`--roadmap-file` 이 있는 작업 트리). 조각 spec 과 계획은 브랜치가 있으면 그 브랜치 끝의 트리 전체에서,
머지됐으면 `origin/main` 에서 찾는다.

**조각 spec 찾기** — 묶음이 있는 블록은 `docs/superpowers/specs/*.md` 중 frontmatter `source_interview` 가 그 조각
묶음 경로와 같은 문서다. 둘 이상이면 「spec 여럿」 경고를 내고 모두 대조한다. 묶음이 없는 브랜치 블록은 `spec:`
줄의 경로다.

**계획 찾기** — `docs/superpowers/plans/*.md` 중 `**Spec:**` 줄의 첫 백틱 경로가 조각 spec 경로와 같은 문서다.
그 뒤에 붙은 설명과 다른 백틱 경로는 보지 않는다.

**브랜치가 있다** — 로컬 `refs/heads/<브랜치>` 가 있으면 그것을, 없으면 `refs/remotes/origin/<브랜치>` 를 본다.
둘 다 없으면 브랜치가 없다. 이름은 정확히 같아야 한다.

단계는 아래 순서로 정한다. 앞 단계가 정하면 뒤는 보지 않는다.

0. `origin/main` 이나 로드맵 사본을 못 읽으면 모든 블록이 **알 수 없음(이유)** 이다.
1. **확인 · 결정 블록**(P3 · P4) — 로드맵 「결정 기록」에 그 번호와 원문 인용(줄 문법 `- <블록> · <결정|머지> · <YYYY-MM-DD> · 「원문」`)이 있으면 **끝남**, 없으면 의존
   조각이 다 머지됐을 때 **준비**, 아니면 **대기**다. 아래 2~4 는 브랜치 블록에만 적용한다.
2. **머지됨** — 다음 중 하나다:
   - `origin/main` 의 첫째 부모 이력(`--first-parent`)에 있는 머지 커밋의 둘째 부모가 브랜치 끝이고, 그 끝이 그
     머지의 첫째 부모(머지 직전 main)의 조상이 아니었다(브랜치가 남아 있을 때). 작업 브랜치가 main 을 받아온
     동기화 머지는 첫째 부모 이력에 없으므로 보지 않는다 — 그 둘째 부모(그때의 main)에서 만든 빈 브랜치가
     머지됨으로 보이지 않게 한다(D4.24).
   - `origin/main` 의 첫째 부모 이력에 있는 머지 커밋 메시지 `from <owner>/<브랜치>` 의 브랜치 부분이 로드맵의 브랜치 이름과
     **정확히** 같고, 브랜치가 지워졌거나 남은 브랜치 끝이 `origin/main` 에 다 들어 있다(머지 뒤 로컬 브랜치를 main 으로
     앞당긴 경우). 머지 뒤 커밋이 더 붙은 브랜치는 머지됨이 아니다.
   - 로드맵 「결정 기록」에 그 조각의 머지 기록과 원문 인용(줄 문법 `- <블록> · <결정|머지> · <YYYY-MM-DD> · 「원문」`)이 있다 — squash · rebase 로 머지해 머지 커밋이
     없는 레포의 대체 근거다. 이 경우를 자동으로 알아보는 일은 R8 이다(D2.3).
   조상 관계만으로는 머지됨이 아니다 — main 에서 막 만든 빈 브랜치도 main 의 조상이기 때문이다(D1.1).
   자동 판정은 merge commit 방식에서만 된다는 한계를 출력 머리에 한 줄로 밝힌다.
3. 브랜치가 없으면 의존 조각 중 하나라도 머지됨 · 끝남이 아닐 때 **대기**, 다 그렇다면 **준비**다.
4. 브랜치가 있으면 위 「계획 찾기」 · 「조각 spec 찾기」로 판정한다:
   - **계획** — 그 조각 spec 을 가리키는 계획이 있다.
   - **설계 중** — 그 밖(커밋이 아직 없는 새 브랜치 포함). spec 이 있으면 「spec 있음」을 근거로 적는다.
     승인 여부는 git 으로 알 수 없다.
   의존 조각이 머지되지 않았는데 브랜치가 있으면 단계는 그대로 계산하고 「의존 미머지 상태에서 진행 중」
   경고를 낸다 — 대기로 덮으면 순서를 어긴 진행이 가려진다.

계획 단계 다음(구현 중 · 구현 끝 · PR)은 R5 가 실행 기록 회수와 함께 붙인다(B6). 스크립트는 fetch 하지
않는다 — 지휘 절차가 계산 전에 fetch 한다.

함께 내는 경고:

- **생략** — 묶음이 있는 조각의 spec 이 있으면 `check_bundle_coverage.py` 결과의 빠진 번호. 그 검사가 3(검사
  불가)을 내면 「번호 대조 검사 불가(이유)」 경고다.
- **경로 예약 위반** — `origin/main...<브랜치>` 의 바뀐 파일 중 다른 조각만 예약한 것.
- **의존 미머지 진행** — 위 4 의 경우.
- **묶음 없음 · spec 여럿** — §3 ② · 위 「다른 파일을 읽는 사본」의 경우.
- **미배정 번호 · 고아 발화** — 번호 전체 집합(brief frontmatter `user_sourced_items` · §0 결정 목록 OQ ·
  §5 RC · §5 ST · §4 «key» · 위험 번호표 K · §6 과 audit §6 의 S)에서, 묶음 없는 블록의 `항목:` · `발화:` 와 모든
  묶음 `ids:` 의 합집합을 뺀 것.

종료 코드: 0 이상 없음 · 1 경고 있음 · 2 사용법 오류 · 3 검사 불가. 3 은 로드맵 없음 · 형식 깨짐 · 블록 하나라도
알 수 없음 · 번호 대조 검사 불가가 하나라도 있을 때다. 여럿이면 3 > 1 > 0 순으로 높은 것을 내고, 3 의 이유를
모두 출력한다.

### §5 지휘 절차와 진행 방식(로드맵에 싣는 내용)

R5 전까지 이 세션이 따른다. 지휘 세션은 `/new` 뒤 첫 줄에 `@<로드맵 경로>` 를 붙여 연다(D38).

1. `git fetch` → `roadmap_status.py` → 작업 목록을 결과에 맞춘다.
2. 준비 단계 조각을 고른다. 로드맵 블록의 `브랜치:` 이름으로 `origin/main` 에서 브랜치와 worktree 를 먼저
   만들고, 그 조각의 설계문서 · 계획은 모두 그 조각 브랜치에 커밋한다 — 상태 계산이 그 브랜치에서 찾는다.
   설계 단계(brainstorming → 설계문서 → spec-review 승인)는 이 세션에서 한 조각씩 돈다 — spec 승인은 사용자가
   조각마다 직접 한다(C48).
3. 설계문서를 커밋한 뒤 spec-review 를 부르기 **전에** `check_bundle_coverage.py` 를 돌려 결과를 사용자에게
   보인다. 빠진 번호가 있으면 spec-review 전에 고친다 — 승인 뒤에야 생략 경고가 뜨지 않게 한다.
4. superpowers 가 묻는 자리(plan 검토 · 실행 방식 · 머지 메뉴)는 그대로 사용자에게 간다(D37).
5. 구현은 조각마다 worktree 에서 돌리고, 그동안 다음 조각의 설계를 진행하는 것이 목표다. 백그라운드
   실행이 되는지는 M1 이 정한다 — 안 되면 구현도 순차로 하고 그 사실을 공시한다. SDD 가 마지막 메시지로
   내는 판정 목록(「Rulings I made」)은 그대로 사용자에게 보인다 — 보이기만 하고 멈추지 않는다(C27).
   보존과 상태 화면 표시는 R5 다(B6).
6. 조각이 머지될 때마다 남은 조각을 재평가하고, 바뀔 때만 사용자 승인 뒤 로드맵 수정을 전용 작은 PR 로
   올린다(D28 · §4 「로드맵을 읽는 사본」).
7. 구현 커밋에는 `Spec:` 트레일러를 단다.

### §7 락 지도 · 충돌표 · R1 걷기

- **락 지도**(`locks.md`) — 칸: 테스트 파일:줄 · 잠근 동작 · 바꿀 조각 · 처리(기본: 그 조각이 같은 PR 에서 고친다).
  brief RC 근거와 장치 이름으로 `git grep` 한다. 찾은 수는 하한이라고 밝히고, 조각마다 착수할 때 다시 찾는다.
- **충돌표** — 진행 중 브랜치(@ 브랜치 · qg ⑤ · 쉬운 말 수정 · 옛 훅)가 건드리는 파일 × 조각 경로 예약.
  겹치면 그 브랜치 머지 뒤로 로드맵 `의존:` 을 건다. 예: R3 → P1, R2a · R5 의 qg 연결 → P2 · P3.
- **R1 걷기** — R0 머지 직후 지휘 절차의 첫 일이다. R0 PR 안에서는 할 수 없다(R1 worktree 는 main 에서
  갈라진다). R1 을 writing-plans 가 계획을 쓰고 지휘 절차로 돌아올 때(또는 끊긴 자리)까지 걸린다. spec 승인은
  그 중간 확인점이다. M5 는 이 끝점까지, M4 는 그 사이 사용자를 기다린 자리(plan 검토 · 실행 방식 선택 포함)를
  기록하고, 머지 메뉴는 R1 이 끝날 때 M4 에 덧붙인다. 드러난 형식 수정은 재평가(D28)로 받아 사용자 승인 뒤
  맡을 조각을 정한다. 브랜치를 쌓지 않는다.
