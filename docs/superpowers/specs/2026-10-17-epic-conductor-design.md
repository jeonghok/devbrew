# R5 — 지휘자 · Design

> 한 세션이 로드맵을 따라 에픽을 끝까지 지휘하되, 사용자의 결정권과 내용 검토가 남게 한다 — 로드맵을 가장 상류의 정본으로, 컨트롤 플레인을 진입점으로, 사실마다 주인 하나.

승인된 로드맵(S47)의 에픽 R5 다. 로드맵 전체에서의 자리는 `roadmap.md` 의 `### R5` 블록이고, 이웃 R2a · R10 과 병렬로 간다(의존 R1 · R2 · R7 · R3 · R4 · R6 · P2 · P3 — 모두 머지됨). 지금까지 지휘 세션이 손으로 따라온 「지휘 절차」 1~9 를, 다시 불러도 같은 동작을 하는 장치로 만든다.

## Handoff Context

- 묶음: `docs/superpowers/roadmaps/2026-10-11-persistent-explore-pm-decompose/R5.md` — 정답 출처. 원본 brief 는 `docs/superpowers/interview/2026-10-11-persistent-explore-pm-decompose-interview.md`.
- 손으로 해 온 방식의 실측: 로드맵 `## 지휘 절차` 1~9, `measurements.md` M1 · M4 · M5, `flexibility-audit.md` 의 R5 절과 「끝에서 끝 확인에서 찾은 것」 R5 절.
- 설계 대화(2026-10-17, 지휘 세션이 직접 brainstorming)의 사용자 결정은 `## 결정 기록`, 재분해 이력 R5 줄의 사용자 원문은 `## 사용자 원문 대조` 에 원문 그대로 둔다.

## Context / Why

로드맵 R0~R7 · R3 · R4 · R6 이 머지되며 지휘에 필요한 부품(상태 계산 · 번호 대조 · 재분해 · 컨트롤 플레인)은 생겼다. 그러나 그것들을 잇는 일 — 무엇을 먼저 하고, 사람에게 언제 묻고, 하위 agent 에게 무엇을 주고, 머지 전에 무엇을 확인하고, 끝나면 무엇을 치우는지 — 은 지휘 세션의 기억과 로드맵 산문에 기댔다. 이번 병렬 묶음에서 실제로 난 일:

- spec 승인 뒤 · writing-plans 뒤 지휘 절차로 돌아온 것이 장치가 아니라 기억이었다(M5 · RC79).
- 하위 agent 가 skill 은 불렀지만 동작이 어긋났다 — 승인 게이트를 지휘자가 다시 써서 물음, 리뷰 원장이 agent 교체마다 리셋, 머지 준비를 skill 없이 처리.
- 스위트 둘이 동시에 돌아 거짓 실패, 리뷰 agent 의 공유 임시 폴더 통째 삭제, 실행 중 스크립트 덮어쓰기, 세션 재개 때 worktree 소실, worktree 38개가 정리되지 않고 남음.
- R2 가 R3 에 넘긴 번호 대조 둘(N17 · N18)이 R3 계획에서 줄었는데 아무도 몰랐다.
- 스위트 대조가 devbrew 의 「건드린 플러그인」 구조에 박혀 다른 레포에서는 돌 수 없다.

사용자가 정한 성공은 C7 그대로다 — 한 세션이 끝까지 지휘하되 PM 인 사용자의 결정권과 내용 검토가 유지된다. 그리고 「구현 다 끝난 뒤 다시 호출해도 이렇게 되게해」 — 장치는 다시 불러도 같은 자리에서 같은 동작을 해야 한다.

## Goals

- G1. 로드맵을 가장 상류의 정본으로 두고, 사실마다 주인 하나를 정해 계층(컨트롤 플레인 · 계획 · 실행 · 기록)과 객체 · 링크 · 속성으로 정리한다. 진입점은 컨트롤 플레인이다(§1).
- G2. 지휘자 skill 하나가 지휘 순환을 돈다 — 언제 다시 불러도 git(추적 문서 포함)과 기계 상태에서 상태를 다시 계산해 같은 자리에서 이어 간다(§2 · §3).
- G3. 사람 몫은 지금 답할 수 있는지 판단해 배경과 함께 하나씩 묻고, 답을 기다리는 일 위에 쌓지 않으며, 나머지는 멈추지 않고 병렬로 끝까지 간다(§3).
- G4. 하위는 자기 worktree 안에서 단일 세션과 같은 skill 을 같은 동작으로 끝까지 돈다(§4).
- G5. 머지 전 확인(스위트 대조 · 통합 리뷰 · 리뷰 뒤 반영)과 끝에서 끝 확인 + qg 한 번이 장치로 돈다(§3 · §2).
- G6. 사용자 몫 감사 · 미룸 · 넘김 조율 · 쓴 자원 정리 · /compact 시점 판단 · 알림을 지휘자가 맡는다(§5 · §3).
- G7. 로드맵 형식을 항목별로 구조화하고, 구현 이후 단계 · 판정 줄 · 조사 에픽 · 에픽 하나의 PR 여럿을 상태 계산에 더한다(§6).
- G8. 상류 · 하류 이음매와 흐름 고정 점검의 R5 행을 고친다(§7). 레포 전용 값을 박지 않는다(§9).

## Non-goals

- 상태줄 · 패널 자체(R6 이 만들었다 — 이 에픽은 거기에 단계 · 판정 줄을 채울 뿐).
- 리뷰 엔진 동작 변경 · qg 수정(R2a — qg 범위 입력 · 문서 경로 정의 · 범위 안 여러 설계문서를 의도로 읽기 · qg 의 테스트 실행 스크립트 셋을 `shared/` 로 바이트 그대로 옮기기 포함, D1.3). R5 는 R2a 가 옮긴 공유본을 쓴다.
- 인터뷰 끝 게이트의 선택지 이름 · 분해 판단(R10).
- 다른 파일에 이미 박힌 레포 전용 값의 범용화 · 의존 부재 강등(R8).
- 규칙 · 철학 문서의 원칙 이전과 낡은 개념 삭제(재분해로 생길 새 문서 정리 에픽) · 지출 조항 문면(R9).
- superpowers 파일 · 동작 변경(C25 · D26) — 부르기만 한다. 실험 기능(agent teams)과 Workflow 를 기반으로 쓰지 않는다(S31).

## Constraints

- 외부 플러그인은 건드리지 않는다(C25 · C35 · D26). superpowers 가 사람에게 묻는 자리는 설계된 대로 둔다(D37) — 다만 지휘 절차 4 의 미리 받은 답은 사용자의 재결정대로 바꾼다(`## 결정 기록`).
- 원래 있는 것을 다시 만들지 않는다(C32) — 레포 안 것은 모델 판단으로 쓰고, 레포 밖 것은 사용자 검토 뒤에만 쓴다(§8).
- 흐름을 고정하지 않는다 — 「기본은 X, 일의 모양이 다르면 모델이 고르고 이유를 적는다」. 정석 흐름(brainstorming → 계획 → 구현)의 의도는 지킨다.
- brainstorming 과 spec 승인은 사람이 터미널에서 보는 앞쪽 세션에서만 한다(M1 — 백그라운드 subagent 에는 `AskUserQuestion` 이 없다).
- 레포 전용 값(경로 · 테스트 명령 · 기본 브랜치 · 브랜치 접두 · 모델 · `gh`)을 박지 않는다(§9).
- 머지는 사용자만 한다. merge 를 쓰고 rebase · force-push 는 하지 않는다. 리뷰 모델은 사용자가 정한 것(이 레포는 opus, fable 금지) — 값은 로드맵 frontmatter 의 레포 설정에서 읽는다(D1.2).
- CLAUDE.md 의 플러그인 형태: 진입 skill 은 짧은 kebab 두 단어 · `cost_class` 선언 · subagent dispatch 자리마다 처분 줄 · 모든 훅 kill switch · 런타임 state 는 git 밖 markdown(세션을 넘는 진행 기록은 추적 문서 — D1.1) · secret 기록 금지.

## 설계

### §1 계층 · 온톨로지 · 역할표

**계층 넷.** 큰 그림에서 어디가 무엇인지 정한다.

| 층 | 무엇 | 예 |
|---|---|---|
| 컨트롤 플레인 — 진입점 | 보고 조작하는 곳. 자기 상태가 없고 아래 층에서 계산한다 | 지휘자 skill · `roadmap-status` · 상태줄 · 작업 목록 |
| 계획 — 정본 | 무엇을 왜 하나 | 로드맵 → 에픽 묶음 → 설계문서 → 계획 |
| 실행 | 실제로 일어나는 것 | 세션 · agent · worktree · 브랜치 · 커밋 · PR |
| 기록 | 무엇이 일어났고 무엇을 정했나 | 결정 기록 · 재분해 이력 · 설계문서의 판정 · 구현 대조 · 지휘 기록 절 · 지휘자 기계 상태 · SDD 원장 · 리뷰 원장 |

**역할표 — 사실마다 주인 하나.** 주인만 쓰고 나머지는 읽거나 계산한다. 고칠 때는 주인을 고친다.

| 사실 | 주인 | 갱신 | 읽는 쪽 |
|---|---|---|---|
| 에픽 · 범위 · 의존 · 흐름 · 결정 · 재분해 이력 | 로드맵(git 추적) — 가장 상류 | 인터뷰가 만들고 그 뒤는 재분해 절차로만 | 지휘자 · 상태 계산 · 에픽 넘김 줄 |
| 에픽의 번호 · 설계 · 미룸 · AC | 묶음 · 설계문서 · 계획(git 추적) | 그 에픽의 설계 · 계획 세션 | spec-review · 번호 대조 · 감사 |
| 브랜치 · 커밋 · 머지 | git | 일하는 세션 · 사용자의 머지 | 상태 계산 |
| 레포 설정: 설계문서 · 계획 폴더 · 테스트 명령 · 리뷰 모델 | 로드맵 frontmatter(git 추적, 없으면 기본값) | 재분해 · 로드맵 수정 PR | 상태 계산 · 지휘자 |
| PR · 통합 리뷰 인계 절 | GitHub(있으면) | finishing · 지휘자 · 사용자 | 지휘자 · 통합 리뷰 · 화면 |
| 구현 중 판정 · task 완료 — 실행 중 | 실행 방식의 원장(SDD 면 `.superpowers/sdd/<계획>/progress.md`) | 실행 방식 | 지휘자 → 판정 줄 |
| 판정 · 구현 대조 · 지휘 기록 — 실행 뒤 보관본 | 에픽 설계문서의 `## 판정` · `## 구현 대조` · `## 지휘 기록` 절(에픽 브랜치에 커밋 → 머지와 함께 기본 브랜치로) | 지휘자 | 상태 계산 · 감사 · 화면 |
| 넘김 · 미룸과 그 처리 여부 | 준 쪽 설계문서 `## 미룸` 표 · PR 본문 인계 절(처리 여부는 받는 쪽 설계문서 · 머지에서 계산) | 설계 세션 · 지휘자 | 지휘자 · 감사 |
| 살아 있는 agent · 자원 · 잠금 · 기다리는 질문 · PR 번호 캐시 | 지휘자 기계 상태(git 밖) — 이 기계에서만 뜻이 있는 것 | 지휘자 | 지휘자 · 컨트롤 플레인 |

판정의 주인은 실행 중에는 실행 방식의 원장이고, 실행이 끝나 그 폴더가 지워지기 전에 지휘자가 거둬 설계문서 `## 판정` 절로 옮긴다 — 그 뒤로는 그 절이 주인(보관본)이다. PR 번호는 GitHub 이 주인이고 기계 상태의 것은 캐시다. 맞추기 걸음(§3 걸음 1)에서 주인과 캐시가 어긋나면 주인을 믿고 캐시를 고친 뒤 알린다 — 예: 캐시는 「PR 열림」인데 GitHub 은 머지.

**온톨로지.** 객체마다 안정된 식별자가 있고, 링크는 이미 있는 칸이 가리키는 것이다. `plugins/spec-distill/references/roadmap-ontology.md` 에 객체 · 식별자 · 속성 · 링크(어느 칸 · 키) · 주인 · 층을 표 하나로 둔다. 링크의 예:

- 에픽 `묶음:` → 묶음 · 설계문서 frontmatter `source_interview` → 묶음 · 설계문서 `roadmap` → 로드맵
- 계획 `**Spec:**` → 설계문서 · 커밋 트레일러 `Spec:` → 설계문서
- 에픽 `브랜치:` → 브랜치 → PR(head) · 에픽 `산출물:` → 산출 파일
- 미룸 · 넘김 「받는 곳」 → 에픽 · `#<n>` · 번호 「받듦」 → 에픽 · 판정 → task · 에픽

**타고 내려가기.** 컨트롤 플레인에 식별자 하나로 내려가는 보기를 더한다 — `/spec-distill:roadmap-status <로드맵> <에픽>` 이 그 에픽의 묶음 · 설계문서 · 계획 · 브랜치 · PR · 열린 넘김 · 판정 줄 · 자원을 경로 · 번호와 함께 보인다. 줄마다 경로나 번호가 있어 다시 한 단계 내려갈 수 있다. 지휘자도 매 걸음 여기서 출발한다.

### §2 구성

**진입.** spec-distill 의 새 진입 skill `epic-conductor`(`/spec-distill:epic-conductor [<로드맵 경로>]`). 지금의 「`/new` 뒤 `@로드맵`」 열기를 대신한다. 인자가 없으면 기본 브랜치에서 git 이 추적하는 `.md` 파일 가운데 frontmatter `type: roadmap` 이고 끝나지 않은 블록이 있는 것을 찾고(폴더를 박지 않는다), 여럿이면 묻는다. `cost_class: high` — 시작할 때 한 번 규모(남은 에픽 수 · 띄울 agent 의 대략 수 · 할 일 순서)를 보이고 `AskUserQuestion` 으로 승인받는다. 그 뒤의 dispatch 는 규모만 알리고 간다(S1 「크게 쓰기 전에는 규모만 알린다」 · 레포의 선언 없는 fan-out 금지). 끄기는 `DEVBREW_SPEC_DISTILL_DISABLE=1`(플러그인 전체) — 꺼져 있으면 손으로 따르는 절차(`references/conducting.md` 의 끝 절)를 가리키고 멈춘다.

**절차 글 — 판단하는 부분.** skill 본문은 순환의 차례와 걸음마다 읽을 reference 만 둔다. 걸음의 내용은 reference 로:

- `references/conducting.md` — 지휘 순환(§3)의 걸음마다 기본값 · 판단 기준 · 부를 superpowers skill · 기록 · 기계 상태에 적을 것, 그리고 손으로 따르는 절차(지휘자를 끈 경우).
- `references/conductor-dispatch.md` — 하위에게 주는 글의 틀과 금지 항목(§4).
- `references/roadmap-ontology.md` — §1 의 표.

**스크립트 — 기계적인 부분만.** superpowers 에 없는 「에픽 사이」 일만 둔다.

- `scripts/merge_check.py` — 합친 사본(origin 기본 브랜치 + 에픽 브랜치, 임시 worktree)을 만들고, 그 레포의 스위트를 기준선과 합친 사본에서 돌려 실패를 대조한다. 동시 실행은 잠금으로 막는다. 러너 탐지 · 단위(파일 · 패키지) 실행과 단위 짝짓기는 R2a 가 qg 에서 `shared/` 로 바이트 그대로 옮긴 공유본을 링크로 쓴다(D1.3 — 그래서 계획 셋째는 R2a 머지 뒤다, §11). 무엇을 돌리나: 로드맵 frontmatter `test_command` 가 있으면 그것이 이긴다 — 레포가 자기 스위트를 가장 잘 안다(devbrew 처럼 공유본의 탐지에 걸리지 않는 테스트가 있는 레포 — 실행 비트 없는 셸 테스트 · `package.json` 없는 `node --test` — 는 이 값을 적는다). 없으면 공유본의 탐지를 쓴다. 공유본은 단위마다 종료 코드 하나만 보고 러너 출력을 해석하지 않으므로(양쪽 다 빨간 단위 안의 새 실패는 그 해상도에서 안 보인다) 이 스크립트가 그 위에 **실패 이름**을 더한다 — 이름을 뽑을 수 있게 러너를 부르는 방식을 스스로 정한다(pytest 는 `-rf` 의 `FAILED` 요약 줄, unittest 는 `FAIL:` · `ERROR:` 줄, node 는 `--test-reporter=tap` 의 `not ok` 줄, 셸 테스트는 실패 표시 줄). `test_command` 를 쓸 때는 그 명령의 출력 모양을 frontmatter `test_failure_pattern`(정규식, 선택)으로 받고, 없으면 위 모양들을 차례로 시도한다. 이름을 뽑을 수 없으면 「이름 대조 불가 — 단위 수준만」을 알린다 — 빈 집합끼리 같다고 판정하지 않는다. 합친 사본과 잠금은 기계 상태의 자원으로 적고 끝나면 지운다.
- `scripts/conductor_state.py`(계획 1) — 기계 상태 `machine.md` 의 절 · 칸 형식과 읽기 · 원자 쓰기 · 표지, 넘김 상태 계산 규칙을 한 모듈로 정한다. 화면(`control_plane.py`)과 지휘자 스크립트가 같은 모듈을 쓴다 — 읽는 쪽이 쓰는 쪽보다 먼저 나와도 형식이 갈리지 않는다.
- `scripts/conductor_ledger.py` — `conductor_state.py` 위에서 기계 상태 쓰기, 자원 목록과 정리 전 확인(수정 · 추적 안 된 파일 · git 밖 기록 나열), 「주인 모름」 worktree 목록, PR 인계 절 모으기(`gh` 가 있을 때), 실행 방식 원장의 판정 줄 거두기, 설계문서의 `## 판정` · `## 구현 대조` · `## 지휘 기록` 절 쓰기, 감사 후보 모으기(§5).
- 기존 `control_plane.py` 는 기계 상태의 PR 번호 캐시 · 진행 중 판정을 합쳐 보이고, `roadmap_status.py` 는 git 만 읽는 지금 성질을 지킨다(§6).

**기록 — 둘로 나눈다(D1.1).** 다시 불렀을 때 이어 가는 데 필요한 기록은 git 이 추적하는 주인 문서에 둔다(§1 역할표): 판정 · 구현 대조 요약 · 지휘 기록(고른 흐름 · 건너뛴 확인과 이유 · 보낸 일)은 에픽 설계문서의 `## 판정` · `## 구현 대조` · `## 지휘 기록` 절에 지휘자가 적어 에픽 브랜치에 커밋한다 — 머지와 함께 기본 브랜치로 가고, 다른 기기에서도 읽힌다. 그 브랜치에 바로 쓸 수 없는 때가 셋이다: (1) 하위 agent 가 그 브랜치에서 일하는 중 — 기록을 기계 상태에 쌓아 두고 agent 가 돌아온 뒤 한 번에 커밋한다(같은 worktree 에 두 writer 를 두지 않는다) · (2) 그 에픽이 이미 머지된 뒤(머지 뒤 넘김 확인 · 끝 단계 결과) — 다음 로드맵 수정 PR 의 본문 `## 지휘 기록` 절에 싣고, 그 PR 이 열릴 때까지는 기계 상태에 쌓아 둔다 · (3) 설계문서 없이 산출물만 내는 에픽 — 같은 세 절을 그 산출물 파일에 둔다. 넘김 · 미룸은 이미 설계문서 `## 미룸` 표와 PR 본문 인계 절에 있고, 처리 여부는 받는 쪽 설계문서와 머지에서 계산한다. 레포 설정은 로드맵 frontmatter 다(D1.2 · §6). 이 기계에서만 뜻이 있는 것 — 살아 있는 agent · 자원 · 잠금 · 기다리는 질문 · PR 번호 캐시 — 만 기계 상태 `<state-root>/conductor/<로드맵 폴더 이름>/machine.md` 에 둔다(`state_path.py state-root` 는 main 체크아웃의 `.claude/spec-distill` 이라 worktree 를 지워도 남는다). 기계 상태가 사라져도 잃는 것은 쌓인 기록(지우기 전에 커밋한다)을 빼면 다시 만들 수 있는 것뿐이다 — 기다리는 질문은 걸음 2 가 다시 모으고, PR 번호는 GitHub 에서 다시 읽고, 자원은 「주인 모름」 목록으로 다시 보인다. 기타 규칙: 기본 브랜치는 어디에도 적지 않고 `origin/HEAD` 에서 읽는다. secret 은 적지 않는다. 기계 상태 쓰기는 잠금 아래에서만 한다 — 리뷰 원장의 표지(`ledger_marker.py`)와 같은 방식으로 세션 id 를 표지로 잡고, 다른 세션이 쥐고 있으면 그 사실을 알리고 그 세션의 지휘자는 읽기 전용으로 보여 준다(표지를 넘겨받을지는 사용자가 정한다). 쓰기는 임시 파일 + 교체로 원자적으로 한다.

### §3 지휘 순환

한 번 부르면 아래를 차례로 돈다. 각 걸음은 기본값이고, 다르게 할 때는 그 에픽 설계문서의 `## 지휘 기록` 에 이유를 적는다(에픽에 매이지 않은 판단은 다음 로드맵 수정 PR 본문에). superpowers 는 부르기만 하고 고치지 않는다.

1. **맞추기.** `git fetch` → 상태 계산(`control_plane.py show --tasks`) → 작업 목록 맞추기 → 기계 상태 읽기(표지를 잡는다 — §2) → 주인과 캐시의 어긋남 고치기(§1). 살아 있는 agent 를 확인한다 — 끝났는데 보고하지 않은 것을 거두고 놀고 있는 것은 내린다. 기다림은 끊어서 하고 사이마다 살아 있는 하위를 다시 센다(SDD 의 「Waiting on dispatched subagents」 방식). 압축 · 새 세션 뒤에도 여기서 시작한다 — 무엇이 끝났는지 기억에 기대지 않는다.
2. **사람 몫 모으기.** 열린 결정마다 「지금 답할 수 있나」를 판정한다 — 앞 에픽의 결과를 봐야 답할 수 있는 것은 아직 묻지 않는다. 답할 수 있는 것은 배경과 함께 하나씩 묻는다. 사용자 몫 감사(§5)도 여기서. 답을 기다리는 동안 그 답에 기대는 일(같은 에픽의 다음 단계 · 의존 에픽 · 같은 파일 에픽)은 진행하지 않는다. brief · 설계 · 계획처럼 방향을 정하는 단계의 질문이면 특히 그렇다. 계속 가는 것은 그 답과 무관한 일뿐이고, 무관하다고 본 이유를 적는다. 판단이 서지 않으면 기다린다. 한 에픽의 spec 리뷰가 도는 동안(진입부터 승인 게이트까지) 다른 에픽에서 돌아온 질문 · 멈춤(계획의 새 결정 · BLOCKED · 설계를 뒤집는 판정)은 기록만 하고 — 받은 원문은 기계 상태 자원 폴더의 파일로 — 그 리뷰 게이트의 질문 호출에 섞지 않고 게이트와 게이트 사이나 리뷰가 끝난 뒤 묻는다. 질문마다 첫 줄에 에픽 이름을 쓴다.
3. **다음 일 고르기와 보내기.** 준비된 에픽마다 흐름을 고른다 — 기본은 설계 흐름이고, 조사 · 측정 · 결정처럼 맞지 않으면 고른 흐름 · 이유 · 산출물을 보이고 `AskUserQuestion` 으로 승인받는다(거절이면 설계 흐름). 승인되면 로드맵 `흐름:` · `산출물:` 칸은 재분해 절차로 적는다. 브랜치 · worktree 는 블록의 `브랜치:` 이름으로 먼저 만든다(하니스 기본 기능 우선 — `superpowers:using-git-worktrees`). 사람에게 묻는 단계(brainstorming 의 질문 · 절별 승인 · spec 승인)는 지휘 세션이 직접 한다 — 한 번에 한 에픽, 의존 사슬의 앞쪽부터. 사용자에게 다른 세션을 열라는 줄을 주지 않는다(같은 세션의 /compact 뒤 이어 갈 줄만 준다). **지휘 세션은 메인 체크아웃(어느 worktree 에도 속하지 않는 레포 위치)에 있는다** — 그래야 어느 에픽에도 매이지 않고 필요한 에픽 worktree 로 옮겨 가며(그 경로의 git · 파일), 하위 agent 를 그 worktree 에 붙여 보낼 수 있다. worktree 격리로 도는 세션은 다른 worktree 에 git · 파일 쓰기가 막힌다(2026-10-17 실측: `git -C <다른 worktree>` · 다른 경로 Write 거부, `git worktree add` 는 허용) — 지휘자가 worktree 안에서 불렸으면 시작할 때 그 사실을 알리고, 그 worktree 를 떠날 수 있는지(하니스의 worktree 나가기)를 먼저 재 본다. 떠날 수 없으면 다른 에픽의 spec 리뷰는 그 에픽 담당 agent 경유(§4 의 두 부분 반환)로 하고 그 사실을 알린다 — 사용자에게 새 세션을 열라고 하지 않는다. 설계문서는 지휘자가 brainstorming 끝에 써서 에픽 브랜치에 커밋한다. **spec 리뷰도 지휘 세션이 직접 돌린다** — 사람 차례가 많은 단계라 brainstorming 을 한 그 세션에서 단일 세션과 같은 skill(`spec-review --bundle`)을 부른다(리뷰어는 쓰기 권한 없는 리뷰 agent 들이고 지휘자는 저자 자리 — 단일 세션과 같다). 부르기 전에 Bash 로 그 에픽 worktree 에 옮겨 가 `pwd` 와 `git rev-parse --show-toplevel` 이 그 worktree 인지 보고, 설계문서 · `--bundle` 을 둘 다 절대경로로 준다 — skill 의 사전 검사 줄(`root=`) · codex 리뷰어의 프로젝트 폴더 · 리뷰 agent 의 시작 폴더 · 리뷰 반영 커밋이 모두 그 자리를 따른다(2026-10-18 실측: 메인 체크아웃에서 그냥 부르면 묶음과 코드를 메인 쪽 사본으로 조용히 읽고, 커밋은 메인 브랜치로 간다). 사전 검사 줄의 `root=` 가 그 worktree 가 아니면 멈춘다. 리뷰 내내 그 worktree 에 머물고 커밋도 거기서 하며, 끝나면 메인 체크아웃으로 돌아온다. 승인 게이트의 ① · ② · 기타 칸 「여기서 계속」 은 선택지를 그대로 보이되, 무엇을 골라도 지휘 세션은 다음 세션 줄의 writing-plans 를 직접 따르지 않고 그 줄을 계획 agent 의 입력으로 넘긴다 — ① 이면 이 세션의 compact 를 권하고(압축은 사용자만), ②(새 세션)면 세션을 새로 열지 않고 ① 과 같이 처리한다고 알린다. 승인 사실(날짜 · 고른 선택지 원문)은 미커밋 확인 뒤 설계문서 `## 지휘 기록` 에 한 줄로 커밋한다 — 압축 뒤 「설계 중 · spec 있음」 과 「승인됨」 을 가르는 근거다(상태 계산이 그 줄을 읽는 것은 계획 3). 리뷰 도중 압축되면 같은 설계문서 경로로 spec-review 를 다시 부른다 — 리뷰 원장이 라운드 · 상한을 잇는다. 에픽 하나의 리뷰가 끝나면 다음 에픽 전에 compact 를 권한다. spec 이 승인되면 계획 · 구현 · 머지 준비는 백그라운드 agent 가 에픽 worktree 에서 한다 — 계획 agent 는 writing-plans 로 계획을 쓰고 커밋한 뒤, writing-plans 가 끝에 묻는 글(계획 검토 · 실행 방식)을 §4 의 두 부분(쉬운 요약 + 원문)으로 지휘자에게 돌려보내고 멈춘다(걸음 4 가 받는다). 의존 · 같은 파일 겹침이 없으면 동시에 보낸다(`superpowers:dispatching-parallel-agents`) — 띄우기 전에 규모를 알린다. 실행 방식은 writing-plans 가 권하는 것(`superpowers:subagent-driven-development` · `superpowers:executing-plans`)이다.
4. **돌아오기를 장치로.** spec 이 승인되면 지휘 세션은 계획으로 들어가지 않고 계획 agent 를 보낸 뒤 다음 에픽 설계로 간다(계획은 걸음 3 의 백그라운드 agent 몫). 백그라운드 agent 는 끝나면 알림이 지휘자에게 온다 — 지휘자는 걸음 1 로 간다. 계획 agent 가 돌아오면: 상태 다시 계산 → 작업 목록 갱신(M5) → 지휘자가 계획을 읽고 「설계에 없던 결정(범위 · 인터페이스 · 파일 배치 등)」이 있는지 가른다 — 계획을 쓴 agent 가 스스로 가르지 않는다. 없으면 경로만 보이고 실행 방식(writing-plans 가 권한 것)으로 구현 agent 를 보낸다. 있으면 그 결정들을 배경과 함께 사용자에게 묻고, 답이 오기 전에는 그 에픽의 구현을 보내지 않는다(걸음 2). 가른 결과와 이유는 `## 지휘 기록` 에 적는다. 구현 agent 는 finishing 의 머지 메뉴에서 「브랜치 그대로 두기」(3번)를 골라 skill 을 그대로 끝내고 돌아온다(83020e28 — 미리 받은 답이 「Push 후 PR」 에서 바뀌었다. finishing 이 묻는 기준 브랜치는 dispatch 에 미리 적는다). 돌아오면: 그 보고에서 판정 전체와 AC 보고 «내용 전체»를 거둔다(§4 — 작업 폴더는 지워질 수 있어 경로에 기대지 않는다) → 그 내용을 기계 상태 자원 폴더의 파일로 두고 `--impl` 대조(경고를 사용자에게 보인다) → 설계문서의 `## 판정` · `## 구현 대조 — <계획 경로>` 절을 쓰고 에픽 브랜치에 커밋 · push(이것이 그 계획의 「구현 끝」 근거다 — §6) → `gh` 로 PR 을 열고 번호를 기계 상태 캐시에 적는다(`gh` 가 없으면 PR 을 열 명령을 사용자에게 준다).
5. **머지 전 확인.** PR 마다(문서만 고친 PR 도 — 모델이 읽는 skill · reference · 템플릿 · 리뷰어 프로필은 문서로 치지 않는다): 스위트 대조(`merge_check.py`) → 새 실패가 있으면 `superpowers:systematic-debugging` → 통합 리뷰(`superpowers:requesting-code-review` 로 쓰기 도구 없는 리뷰어를 로드맵 frontmatter 의 리뷰 모델로(없으면 세션 모델), 이음매가 여럿이면 여럿 동시에 — 합친 사본 · 이 PR diff · 열린 다른 에픽 diff · 앞선 인계 절을 주고 에픽 사이 이음매를 묻는다) → 지적은 「이 PR 이 고침」 · 「뒤 에픽이 고침」으로 나눠 PR 본문 `## 통합 리뷰 인계` 절에 → 고침은 `superpowers:receiving-code-review` 로 받고 좁은 재리뷰(동작 · 락 · 보안 경계 · 리뷰어 프로필 수정은 매번, PR 하나에 두 번까지, 멈출 조건은 첫 재리뷰 전에) → `superpowers:verification-before-completion` → 릴리스 번호는 이때 정하고 머지 명령 줄만 준비한다. 건너뛴 확인은 무엇을 왜 건너뛰었는지 적는다.
6. **머지 뒤.** 머지를 확인하면 열린 에픽 브랜치에 기본 브랜치를 merge 하고 대조를 다시 돌린다. 그 브랜치에서 agent 가 일하고 있으면 지휘자가 직접 merge 하지 않는다 — 그 agent 가 돌아올 때까지 기다리거나, 다음 task 경계에서 merge 하라고 그 agent 에 전한다(같은 worktree 에 두 writer 를 두지 않는다). merge 가 충돌하면 그 에픽만 멈추고 알린다. 남은 에픽을 재평가하고, 바뀔 때만 재분해 절차(`references/redecompose.md`)로 사용자 승인 뒤 로드맵 PR. 받는 에픽이 머지되면 그 넘김이 처리됐는지 확인한다(§5).
7. **끝.** 모든 에픽이 머지되면 끝에서 끝 확인 — 기본 경로와 설계 흐름이 아닌 에픽 경로를 실제 명령으로 걷는다. 그때 qg 를 한 번 — 로드맵 시작 커밋부터 지금 기본 브랜치까지(qg 의 범위 입력과, 범위 안 여러 설계문서를 모두 의도로 읽는 일은 R2a). 그 입력이 없으면 qg 없이 가고 그 사실을 알린다. 지적은 후속 PR 하나로. 넘김이 모두 처리됐는지 확인하고 쓴 자원을 정리한다.

**/compact 시점.** 지휘자가 정한다 — 에픽 하나의 spec 리뷰가 끝나 계획 agent 를 보낸 직후처럼 끊기 좋은 자리에서 맥락이 무거우면, 기록 · 기계 상태를 저장(설계문서 절은 커밋)한 뒤 `/compact` 와 이어 갈 줄(`/spec-distill:epic-conductor <로드맵>`)을 준다. 압축은 사용자만 한다.

**알림.** 사람 답이 없어 에픽이 멈췄을 때와 모두 끝났거나 더 갈 일이 없을 때만 `PushNotification`. 터미널을 보고 있으면 도구가 보내지 않는다.

### §4 하위 계약 · 구현 감시

**하위에게 주는 글**(`references/conductor-dispatch.md`, 하위가 implementer · reviewer 어느 쪽이든):

- 그 worktree 의 절대경로 · 고른 흐름과 이유 · 「이 흐름의 skill 을 단일 세션과 똑같이, 빼거나 다시 쓰지 말고 끝까지」.
- 사람에게 묻는 자리는 둘로 나눠 준다. 미리 받은 답이 있는 자리는 dispatch 에 그 답을 적어 하위가 그대로 쓴다 — 머지 메뉴는 「브랜치 그대로 두기」(3번 — Push 와 PR 은 지휘자가 구현 대조 뒤에, 83020e28), 기준 브랜치는 dispatch 에 적은 것, 실행 방식은 writing-plans 가 권한 것(지휘 절차 4). 하위는 그 자리와 쓴 답을 보고에 적는다. 그 밖의 자리(미리 받은 답이 없는 것, 그리고 계획 검토처럼 지휘자가 가를 자리)를 만나면 멈추고 (a) 사람에게 보일 쉬운 요약(무엇을 정하나 · 고르면 무엇이 달라지나 · 배경, 내부 기호는 괄호에만)과 (b) skill 이 낸 문면 · 선택지 원문을 함께 돌려보낸다. 지휘자는 배경을 먼저 쉬운 말로 쓰고 질문만 봐도 결정할 수 있게 묻는다(지휘자가 직접 쓰는 글도 `shared/style/plain-language.md` 를 따른다). 선택지의 수 · 순서 · 라벨(돌려줄 값) · skill 자신의 「(권장)」 표시와 사용자 답은 글자 그대로 두고, 각 선택지 설명은 원문의 「고르면 무엇이 달라지나」(그대로 두면 · 고치면)를 빠뜨리지 않는다. 지휘자 의견은 선택지 밖에 「지휘자 의견:」 한 줄로 따로 쓴다. 원문은 늘 붙인다. 옮길 때마다 받은 원문과 실제로 띄운 질문을 기계 상태 자원 폴더의 파일에 남기고, 에픽이 끝나면 쓰기 권한 없는 agent 가 둘의 선택지 수 · 라벨 · 순서를 대조한다(자기 채점 방지 — 계획 3). 사용자가 직접 써야 하는 답이 선택지로 안 받히면 지휘자가 게이트 밖 후속 질문을 해도 되고, 그 사실과 이유를 함께 적는다.
- 마지막 보고에 판정 전체(실행 방식의 마지막 목록 그대로)와 AC 보고 내용 전체를 싣는다 — 실행 방식이 작업 폴더를 지울 수 있어 경로만으로는 부족하다. 구현 agent 는 머지 메뉴에서 3번(그대로 두기)을 고르고, Push 와 PR 은 지휘자가 구현 대조 뒤에 한다.
- 금지 셋: 공유 임시 폴더의 glob 삭제(자기 하위 폴더만) · stash · 다른 worktree 의 git 조작. skill 안의 테스트 실행은 그대로 둔다(같은 동작) — dispatch 가 하위마다 따로 쓸 임시 폴더(`TMPDIR`)를 주어 공유 자원 경합을 줄이고, 하위가 본 실패가 진짜인지는 지휘자의 잠긴 스위트 대조만 판정한다(94c2ba92). 그 대조에서 사라지는 실패는 경합으로 보고 알린다.
- 구현 커밋에는 `Spec: <설계문서 레포 상대경로>` 트레일러를 단다 — qg 의 의도 출처가 이것을 읽는다(RC76).
- 처분 줄: dispatch 자리마다 `**처분** — consumer=orchestrator · fail-closed · disclosure=하위가 돌려보낸 사람 자리 원문(쉬운 배경 뒤 늘 첨부) · 판정 목록 · AC 보고를 빠짐없이 사용자에게 보인다`.

**리뷰 원장 이어 가기.** spec 리뷰는 지휘 세션이 같은 설계문서 경로로 다시 부르면 원장이 이어진다(압축 뒤 포함). 하위 agent 가 돌리는 다른 리뷰를 다시 돌 때는 같은 agent 를 이어 부른다(`SendMessage`). 그 agent 가 없으면 지휘자가 같은 상태 경로(리뷰 엔진의 문서별 상태 디렉토리)를 넘겨 라운드 수 · 재리뷰 상한이 초기화되지 않게 한다.

**구현 감시.** 실행 중에는 실행 방식 원장의 판정 줄(SDD 면 `Ruling: 무엇 — 왜 — 틀리면 비용`)을 지휘자가 맞추기 걸음마다 읽어 컨트롤 플레인의 「판정 줄」에 올린다(기계 상태에는 어디까지 읽었는지만 적는다). 판정이 승인된 설계의 수용 기준 · 의도를 바꾸거나 구현이 막히면(SDD 의 BLOCKED 포함) 그 에픽만 멈추고 배경과 함께 묻는다 — 다른 에픽은 계속. 설계 안의 판정은 멈추지 않고 끝에 목록 전체를 보인다(지휘 절차 5). 실행이 끝나면 원장의 유무와 상관없이 하위의 마지막 보고에서 판정 전체를 거두고, 앞서 읽은 것과 대조해 설계문서 `## 판정` 절에 보관본으로 적는다 — SDD 는 끝나면 작업 폴더를 지우므로 마지막 읽기 뒤의 판정은 보고에만 남는다. 보고에도 원장에도 판정이 없으면 「판정 줄 — 셀 수 없음」.

### §5 감사 · 넘김 조율 · 자원 정리

**사용자 몫 감사.** 후보는 스크립트가 모은다 — 설계문서 번호 대조의 「기각」 행 · `## 미룸` 표 · 판정 줄 · PR 본문의 「리뷰 뒤 반영」. 그중 실제로 사용자가 정할 것은 모델이 골라 배경과 함께 하나씩 묻는다. 도는 때: spec 승인 게이트 · 머지 전 확인 · 지휘자를 다시 불렀을 때. 줄어든 넘김: 준 쪽 설계문서의 넘김 · 미룸 항목이 받은 쪽 설계문서의 번호 대조 · AC · 미룸에 그대로 있는지 대조한다.

**넘김 조율.** 넘김 한 줄 = 항목 · 준 곳 · 받는 곳 · 상태(열림 · 처리됨 · 확인됨) · 근거. 출처는 설계문서 `## 미룸` 표와 PR 본문 `## 통합 리뷰 인계` 절이 주인이고, 상태는 받는 쪽 설계문서 · 머지에서 계산하며, 확인한 결과는 받는 에픽이 아직 머지 전이면 그 설계문서의 `## 지휘 기록` 에, 이미 머지됐으면 다음 로드맵 수정 PR 본문의 `## 지휘 기록` 절에 적는다(§2 기록). 받는 곳이 `없음` 이면 맡을 에픽을 제안하고, 그 에픽 범위에 없으면 재분해 절차로 승인 뒤 로드맵에 넣는다. 맡을 에픽이 없으면 GitHub 이슈(`#<n>`)를 받는 곳으로 쓸 수 있으나, 이슈를 새로 만드는 것은 그때마다 묻는다. 받는 에픽이 머지되면 그 설계문서의 번호 대조 · AC 보고 · 통합 리뷰로 처리 여부를 확인한다. 「받는 곳이 유효한가」 는 한 규칙(로드맵에 실재하는 에픽 또는 `#<n>`)으로 `--impl` 과 상태 계산이 같이 쓴다.

**R2 가 넘긴 번호 대조 둘.** N17 — 설계문서가 없는 묶음이나 묶음이 아닌 블록이 계획 · 머지됨 단계면 번호 대조를 건너뛴 사실을 경고하고 「셀 수 없음」으로 센다. N18 — 기각한 번호의 수와 목록을 spec-review 승인 게이트에 보이고, 사용자가 그중 하나를 「반영」으로 되돌릴 수 있게 한다(되돌리면 설계문서를 고쳐 다시 리뷰).

**쓴 자원 정리 — 브랜치는 정리하지 않는다.** 지휘자와 하위가 만드는 worktree · 읽기 사본 · 잠금 · 백그라운드 agent · 임시 폴더를 기계 상태의 `## 자원` 에 적는다(무엇 · 경로 · 에픽 · 용도 · 만든 때). 시점: 읽기 사본은 그 리뷰 뒤 · agent worktree 는 결과를 거둔 뒤 · 에픽 worktree 는 머지 확인 뒤 · 잠금은 작업 끝(주인 없는 잠금은 알리고 푼다). 지우기 전: 수정 · 추적 안 된 파일이 있으면 보이고 묻는다(`finishing-a-development-branch` 의 규칙 — `--force` 없음). git 밖 기록(SDD 원장 등)은 남길 가치가 있으면 그 에픽 설계문서의 절로 옮긴다(판정은 이미 `## 판정` 에 있다). 기계 상태에 없는 worktree 는 첫 호출에 「주인 모름」 목록으로 보이고 고른 것만 지운다.

### §6 상태 계산 · 로드맵 형식

**에픽 칸.** `범위:` 아래 `한다:` · `안 한다:` 하위 항목(들여쓰기 두 칸 `  - `)을 하나씩, 항목 끝 괄호에 근거(이력 날짜 · 문서)를 둘 수 있다. 새 선택 칸: `크기` · `병렬` · `순서 이유` · `근거` · `흐름` · `산출물`. 해석기는 지금 들여쓴 줄을 조용히 버린다 — 「앞 칸의 하위 항목」으로 읽게 바꾸고, 하위 항목이 있는 칸의 값은 항목 목록이다. 한 줄 칸은 그대로라 옛 로드맵은 바뀌기 전과 같은 결과를 낸다. 새 칸을 읽는 곳: `병렬` 은 사람이 읽는 칸이다 — 동시 보내기 판단은 지금처럼 `의존:` 과 경로 예약 겹침에서 계산하고 이 칸을 판단에 쓰지 않는다. 이 칸에는 계산으로 못 보는 직렬 이유(포트 · DB 같은 공유 실행 자원)만 사람이 적고, 동시에 갈 수 있는 에픽은 타고 내려가기 보기가 매번 계산해 보인다(사용자가 요청한 「병렬 가능 여부」 를 보이되 같은 사실의 주인을 둘로 만들지 않는다 — 계산 결과를 칸에 적으면 재분해 때 바뀌지 않은 블록에 낡은 사본으로 남는다, 계획 단계 결정 「화면에서만 계산 (권장)」) · `크기` · `순서 이유` 는 타고 내려가기 보기와 spec 승인 게이트의 로드맵 속 위치(`spec_review_bundle.py neighbors`)가 보인다 · `근거` 는 타고 내려가기 보기가 링크로 보인다 · `흐름` · `산출물` 은 아래.

**레포 설정 — 로드맵 frontmatter(D1.2).** 선택 키: `specs_dir` · `plans_dir`(설계문서 · 계획 폴더 — 없으면 superpowers 기본 `docs/superpowers/specs/` · `docs/superpowers/plans/`) · `test_command`(없으면 탐지) · `review_model`(없으면 세션 모델). 상태 계산은 기본 브랜치의 로드맵에서 git 으로 이것을 읽는다 — 「git 만 읽는다」는 그대로이고, 어느 기기에서나 같은 단계가 나온다. 지휘자가 한 번 물어 얻은 값은 다음 로드맵 수정 PR 에 frontmatter 로 올린다(그 전에는 기계 상태에 임시로). 기본값 문자열은 한 상수 모듈에만 둔다(AC29).

**재분해 이력.** `### <YYYY-MM-DD> · <사유>` 아래 `- 바뀜:`(하위 항목 가능 — 바뀜마다 그것을 승인한 사용자 말 「…」 을 그 항목 끝에 둔다) · `- 원문:` 하위 항목(사용자 말 하나에 한 줄, 「…」 그대로). 사용자 말이 없는 바뀜(설계 판정 등)은 `- 원문: 없음 — <사유>` 로 적고 판정 인용은 바뀜에 둔다 — 사용자 말이 아닌 인용을 원문 칸에 두지 않는다. `roadmap_write.py update` 가 새 꼴로 적고, 옛 한 줄 이력도 읽는다. 결정 기록 줄 형식은 그대로다.

**옮기기.** 이 로드맵을 새 형식으로 옮긴다 — 사용자 원문 「…」 인용 집합이 옮기기 전후로 같음을 테스트가 잰다. 생성기 · 렌더러 · 템플릿 · 실데이터 락(블록 순서 정규식 · 견본 테스트)을 함께 바꾼다.

**흐름 · 산출물.** 에픽 종류를 늘리지 않고 칸 둘로 푼다. `흐름:` 이 없으면 설계 흐름, 있으면 고른 흐름과 승인 원문. `산출물:` 은 설계문서 대신 낼 파일 경로 — 상태 계산은 그 파일이 브랜치에 생기면 설계문서처럼 단계를 매기고, 이웃 읽기(`spec_review_bundle.py neighbors`)도 그 파일을 읽는다.

**구현 이후 단계.** R6 이 비워 둔 「구현 중 · 구현 끝 · PR」 을 채운다. 구현 중(계획 커밋 뒤 그 브랜치에 `Spec:` 트레일러 커밋)과 구현 끝(그 브랜치의 설계문서에 그 계획의 `## 구현 대조 — <계획 경로>` 절이 커밋됨 — §3 걸음 4 가 쓴다)은 브랜치마다 · 계획마다 git 으로 계산하므로 앞 계획의 절이 뒤 계획을 「구현 끝」으로 만들지 않는다. 이것들은 git 이라 `roadmap_status.py` 가 계산한다 — 네트워크 없이 git 만 읽는 성질은 지킨다. PR 은 GitHub 이 주인이라 `control_plane.py` 가 기계 상태의 캐시(없으면 `gh` 가 있을 때 조회)로 합친다 — 둘 다 없으면 그 단계는 「알 수 없음」이다. 진행 중 판정 줄은 실행 방식 원장에서, 끝난 에픽의 판정은 설계문서 `## 판정` 절에서 읽는다 — 둘 다 없으면 「셀 수 없음」. 화면 캐시: 기계 상태와 실행 방식 원장은 캐시 열쇠에 넣지 않고 인터뷰 상태처럼 매번 읽는다(지금 `control_plane.py` 의 캐시 열쇠는 git 참조와 스크립트뿐이라, 넣지 않으면 옛 화면을 낸다).

**에픽 하나에 PR 여럿.** `브랜치:` 에 여럿을 적을 수 있다. 모두 머지되면 「머지됨」, 일부면 「일부 머지 n/m」. 브랜치는 그것을 읽는 해석기와 같은 머지로 들어가야 한다 — 먼저 등록하면 옛 해석기가 여러 이름을 한 이름으로 읽고, 첫 브랜치가 머지된 뒤에 더하면 그 사이에 「머지됨」으로 잘못 보인다. 그래서 R5 는 계획 1 PR 안에서 이 해석기(AC5)와 함께 R5 블록에 세 브랜치를 등록한다(§11).

**끝에서 끝 확인의 작은 결함.** `§n` 이 `## <n>.` 머리에서도 풀린다 · 계획 단계 판정이 백틱 없는 `**Spec:**` 경로도 받는다 · 번호 대조의 에픽 이름 규칙을 「대문자 + 숫자 + 소문자 선택」으로 · 화면의 겹침 줄이 내용을 보인다 · 「로드맵이 아직 기본 브랜치에 없음」을 진짜 검사 불가와 다른 줄 · 다른 종료 코드로.

### §7 상류 · 하류 연계와 흐름 고정 풀기

```
[상류] request-framing ─► spec-interview ─► 「나눌까?」

                                                 ▼
                         /spec-distill:epic-conductor <로드맵>   ◄─ 다시 불러도 같은 자리에서
  ┌─ 상태: git 계산 + 기계 상태 ── 같은 상태를 roadmap-status · 상태줄 · 작업 목록이 보임
  ├─ 에픽마다: brainstorming ─► 설계문서 (지휘 세션) ─► spec-review --bundle (지휘 세션) ─► 승인 (지휘 세션)

  │            보고 ─► --impl ─► 설계문서 ## 판정 · ## 구현 대조 커밋 ─► finishing(Push · PR)
```

**상류 이음매.** 인터뷰가 나눈 일의 다음 세션 줄(`skills/spec-interview/references/finishing.md` 의 「이 로드맵의 지휘 절차대로 진행하라 …」)을 지휘자 호출 한 줄로 바꾼다 — 그 한 줄만 R5 가 고치고 게이트 선택지 이름은 R10 이 고친다(경로 예약 겹침은 정보 — 통합 리뷰에서 맞춘다). 로드맵 템플릿의 `## 지휘 절차` 는 지휘자 호출 안내로 줄이고, 손으로 따르는 절차는 `references/conducting.md` 끝 절로 옮긴다.

**하류 이음매 — 흐름 고정 점검의 R5 행.**

1. 에픽 넘김 줄(`references/epic-handoff.md`): brainstorming 은 기본값, 블록에 `흐름:` 이 있으면 그 흐름 · 「묶음을 다시 나누지 않는다」 → 「나눌 근거가 보이면 재분해로 보고한다」 · 「SDD 의 마지막 전체 리뷰」 → 「고른 실행 방식의 마지막 전체 리뷰(조사 에픽은 산출물의 AC 대조)」 · 새 지시 넷 — 설계문서에 「있는 것 검토」 절(외부 후보는 사용자 승인 뒤에만), 「상류 · 하류 연계」 절, 레포 전용 값을 박지 않기. 넘김 줄은 지휘자를 끈 경우(손 절차)에 쓰고, 그 세션은 지금처럼 계획 · 구현으로 간다 — 지휘자는 넘김 줄을 사용자에게 주지 않고 같은 내용을 자기 brainstorming 입력으로 쓴다.
2. 재분해 신호(`references/redecompose.md` `## 1. 신호`): 셋으로 닫힌 목록 → 열린 목록 — 계획 · 구현 세션이 경계 오류를 찾은 경우를 예로 더한다.
3. spec-review 게이트 ③(`skills/spec-review/SKILL.md`): 로드맵 에픽의 설계문서에서 「인터뷰 다시 열기」가 늘 재분해로 가던 것을, 지적이 그 에픽 안에서 끝나면 「이 에픽 다시 설계」 도 고를 수 있게.
4. 지휘 절차 4(템플릿 · 이 로드맵): 실행 방식은 writing-plans 가 권하는 방식, 계획 검토는 새 결정이 있을 때만 기다림.
5. 진행 게이트(`references/proceed-gate.md`): 선택지 넷은 그대로, 기타 칸의 「여기서 계속」 이면 압축 없이 이 세션에서 다음 단계 — 사용자가 고른 것이라 게이트 건너뛰기가 아니다.
6. spec-review 승인 게이트의 다음 세션 줄(`skills/spec-review/SKILL.md` 의 ①/② 공통 줄): 설계문서 frontmatter 에 `roadmap:` 이 있으면(로드맵 에픽) 「계획은 지휘자가 계획 agent 로 보낸다 — 이 세션의 /compact 뒤 지휘자를 이어 부른다」(spec 리뷰를 지휘 세션이 돌리므로 「돌아갈」 세션이 따로 없다), 없으면 지금처럼 writing-plans 로 가되 「SDD 의 마지막 전체 리뷰」 를 「고른 실행 방식의 마지막 전체 리뷰」 로(사용자 결정 80a9fc4a — AC42). 인터뷰 쪽 같은 가정(`finishing.md` 의 brief 다음 세션 줄)은 R10 으로 넘긴다.

**레포 안(모델 판단으로 씀).** `roadmap_status.py` · `control_plane.py`(`show --tasks` · 판정 줄 자리 · R6 이 비워 둔 단계 이름) · `check_bundle_coverage.py`(`--plan` · `--impl`) · `spec_review_bundle.py neighbors` · `references/redecompose.md` · `references/epic-handoff.md` · `state_path.py state-root` · `ledger_marker.py`(리뷰 원장의 세션 표지 — 기계 상태 잠금에 같은 방식) · qg 의 러너 탐지 · 단위 실행 · 단위 짝짓기(`run-test-selection.sh` · `diff-test-results.py` · `compute-test-scope-candidates.sh` — R2a 가 `shared/` 로 옮긴 공유본을 레포의 심볼릭 링크 방식으로, D1.3).

이번 묶음에서 지휘 세션이 손으로 쓴 헬퍼는 레포 밖(지휘 세션의 개인 작업 폴더)에 있어 계획 작성자가 읽을 수 없다 — 옮길 로직을 여기 적는다:
- 스위트 대조(`check_pr.sh` · `run_suite.sh`): 기준선 사본에서 시작할 때 남은 merge 를 먼저 abort 하고 → `git fetch` → 대조 대상 브랜치의 SHA 를 한 줄로 찍고 → 그 사본에 브랜치를 merge 한 뒤 → 셸 테스트(실패 표시 줄) · python unittest(`FAIL:` · `ERROR:`) · node(`--test-reporter=tap` 의 `not ok`) 를 돌려 실패 이름 집합을 기준선과 양방향으로 대조한다(「이 브랜치에만 있는 실패」 · 「기준선에만 있는 실패」). 동시 실행은 `mkdir` 잠금(종료 시 trap 으로 해제)으로 막는다. 실행 중인 스크립트 파일은 고치지 않는다(bash 는 스크립트를 실행 중에 읽는다).
- 합친 읽기 사본(`ir/prep.sh`): 기본 브랜치 + 이 브랜치를 merge 한 별도 worktree 와, 아직 열린 다른 에픽 브랜치마다 기본 브랜치 대비 diff 파일을 만든다.
- 충돌 미리 보기(`ir/conflicts.sh`): `git merge-tree` 로 실제 merge 없이 충돌 파일을 본다.

맥락 메모는 레포 밖 개인 파일이라 이 문서는 그것에 기대지 않는다 — 설계 대화의 사용자 결정은 전부 `## 결정 기록` 과 `## 사용자 원문 대조` 에 원문으로 있다.

**레포 밖(사용자 승인됨 — `## 결정 기록` 「1 · 외부 후보도 씁 (권장)」).** superpowers skill — `dispatching-parallel-agents` · `using-git-worktrees` · `subagent-driven-development` · `executing-plans` · `requesting-code-review` · `receiving-code-review` · `verification-before-completion` · `systematic-debugging` · `finishing-a-development-branch`(부르기만, 고치지 않음) · Claude Code 기본 기능 — 작업 목록 · agent 의 worktree 격리 · `SendMessage` · `PushNotification` · GitHub CLI `gh`(없으면 강등). 새 패키지 · 프레임워크 의존은 넣지 않는다. 병합 대기열 서비스(Mergify · Graphite)는 사례로만 참고하고 기반으로 쓰지 않는다(S31).

### §9 레포 전용 값

지휘자 skill · reference · 새 스크립트는 레포 전용 값을 박지 않는다. 테스트 명령은 레포 파일에서 알아내고(qg 의 탐지 — pytest · unittest · 셸 · jest · vitest · npm 스크립트 · cargo · make), 못 하면 한 번 묻고 로드맵 frontmatter `test_command` 로 올린다(§6). 기본은 전체 스위트다 — 「바뀐 곳만」은 다른 소비자의 실패를 놓친 적이 있어(#154) 스위트가 너무 오래 걸리는 레포에서만 모델이 좁히고 이유를 적는다(devbrew 의 「건드린 플러그인 + shared」도 그 경우 하나일 뿐). 테스트가 없는 레포면 「스위트 대조 없음」을 알리고 통합 리뷰만. 기본 브랜치는 `origin/HEAD` 에서(풀리지 않으면 그 사실을 알리고 멈춘다), 브랜치 이름은 로드맵 블록에서, 리뷰 모델 · 설계문서 · 계획 폴더는 로드맵 frontmatter 에서(없으면 기본값 — 설계문서 `docs/superpowers/specs/` · 계획 `docs/superpowers/plans/` 는 superpowers 의 기본 경로, 그 문자열은 한 상수 모듈에만). `gh` 가 없거나 GitHub 레포가 아니면 PR 인계 절 대신 설계문서 `## 미룸` 표와 `## 지휘 기록` 을 쓰고 알린다. R5 가 고치는 두 스크립트의 박힌 값도 이 규칙으로 바꾼다 — `roadmap_status.py` 의 설계문서 · 계획 찾기, 그리고 `roadmap_status.py` · `control_plane.py` 의 기본 브랜치 참조(`refs/remotes/origin/main` 고정 → `origin/HEAD`). 지휘자의 첫 걸음이 이 둘에 기대므로 R8 로 미루지 않는다. 다른 파일에 박힌 값은 R8 로 넘긴다.

### §10 위험에 대한 답

- K2(쭉 가기와 왜곡 장치 제거가 맞는다는 가정) · RC47 · OQ10 — 판정은 숨기지 않고 판정 줄로 실시간에 가깝게 보이고(실행 방식 원장 → 화면, 끝나면 설계문서 `## 판정` 보관본), 설계를 뒤집는 판정만 그 에픽을 멈춘다(§4).
- K6 · K13(승인이 도장 찍기로) · «approval-fatigue» — 승인 게이트에 이웃 에픽 결정 · 기각 번호(N18) · 판정 목록을 함께 싣고, 승인 자리를 늘리지 않는다(계획 검토는 새 결정이 있을 때만).
- K8(암묵 결정 충돌 · 공유 파일 겹침) · RC38 · «cognition-multi-agents» · «graphite-mergequeue» — 통합 리뷰가 열린 다른 에픽 diff 와 합친 사본을 보고, 릴리스 번호는 머지 직전에, 머지 뒤 열린 브랜치에 기본 브랜치를 merge 하고 대조를 다시 돈다(§3 걸음 5 · 6).
- ST2 · OQ28 · RC63(예외 멈춤 · 반증) — 사용자 결정 「그 에픽만 멈추고 묻기」, 확정 항목의 반증은 재결정 규약(P23)으로.
- K5 · K9 성격(압축 뒤 지도 소실) — 상태를 대화가 아니라 git(추적 문서 포함) · 기계 상태에서 다시 계산한다(§3 걸음 1). spec 리뷰를 지휘 세션이 돌리므로 맥락이 커진다(R2a 리뷰 한 번이 약 82만 토큰) — 승인 사실은 설계문서 `## 지휘 기록` 한 줄, 리뷰 진행은 리뷰 원장, 기다리는 질문 원문은 기계 상태 자원 폴더의 파일에 두어 압축 뒤 다시 읽는다(§3 걸음 2 · 3).

### §11 계획 나누기

설계문서 하나에 계획 · PR 셋이고, 차례로 간다. 셋 모두 spec-distill 의 버전 · CHANGELOG · README 를 고치고, 둘째가 만드는 `references/conducting.md` 를 셋째가 채우기 때문이다. 브랜치 셋은 계획 1 PR 안에서 여러 브랜치를 읽는 해석기(AC5)와 함께 R5 블록에 등록한다(§6 — 해석기와 데이터가 같은 머지로 들어가 거짓 「머지됨」 도, 옛 해석기의 오독도 없다). 지휘자를 가리키는 진입 안내(나눈 일의 다음 세션 줄 · 템플릿의 지휘 절차 · 넘김 줄의 「지휘자로 돌아가기」 · 승인 게이트 줄의 로드맵 갈래)는 지휘자 skill 과 같은 계획 셋째에 둔다 — 아직 없는 skill 을 가리키는 릴리스가 생기지 않게.

1. **형식 · 상태**(`feature/epic-conductor`) — AC1~AC14 · AC39 · AC40 · AC43 의 기계 상태 형식과 넘김 계산 모듈 · AC38.
2. **이음매 · 흐름 풀기** — AC31 · AC32~AC35 · AC38 과 AC42 의 로드맵 아닌 갈래 · AC44 · AC45 의 손 절차 몫(2026-10-18 재결정 — 손 절차의 spec 리뷰 절차 · 경유 질문 보호). 넘김 줄에서 지휘자를 가리키지 않는 변경, 재분해 신호, 게이트 ③ · N18, 진행 게이트, 승인 게이트 줄의 「고른 실행 방식」. `references/conducting.md` 를 손 절차(지금 로드맵의 지휘 절차 1~9 를 옮긴 것)로 먼저 만든다.
3. **지휘자** — AC15~AC30 · AC31 의 「넘김 줄은 지휘자를 끈 경우에만」 · AC44 · AC45 · AC36 · AC37 · AC41 · AC42 의 로드맵 갈래 · AC43 의 기록 자리와 PR 순서 · AC38. R2a 의 `shared/` 테스트 공유본이 머지된 뒤에 시작한다(D1.3). `conducting.md` 에 지휘 순환 걸음을 채우고, 지휘자를 가리키는 진입 안내를 이때 바꾼다.

계획마다 그 계획 몫의 AC 만 대조한다 — `check_bundle_coverage.py --plan` 이 `--acs <AC 목록>` 을 받게 하고(AC40), 지휘자는 위 목록을 그대로 넘긴다. 구현 대조(`--impl`)도 같은 목록이다.

## Acceptance Criteria

- AC1 로드맵 해석기가 칸 아래 `  - ` 하위 항목을 그 칸의 항목 목록으로 읽고, 하위 항목이 없는 옛 로드맵(이 레포의 지금 로드맵 포함)은 바뀌기 전과 같은 블록 · 칸 값 · 오류를 낸다.
- AC2 새 선택 칸 `크기` · `병렬` · `순서 이유` · `근거` · `흐름` · `산출물` 을 받고, 모르는 칸 이름은 지금처럼 형식 오류다.
- AC3 재분해 이력을 `### <날짜> · <사유>` + `바뀜:` + `원문:` 하위 항목으로 `roadmap_write.py update` 가 쓰고 해석기가 읽는다. 옛 한 줄 이력도 읽는다.
- AC4 이 로드맵을 새 형식으로 옮기고, 옮기기 전후 「…」 원문 인용 집합이 같음을 테스트가 잰다. 렌더러 · 템플릿 · 실데이터 락이 새 형식을 낸다.
- AC5 `브랜치:` 에 여럿을 적을 수 있고, 모두 머지되면 「머지됨」, 일부면 「일부 머지 n/m」이다.
- AC6 `산출물:` 이 있는 블록은 그 파일이 브랜치에 생기면 설계문서처럼 단계가 매겨지고, 이웃 읽기가 그 파일을 읽는다.
- AC7 계획 커밋 뒤 브랜치에 `Spec:` 트레일러 커밋이 있으면 「구현 중」, 그 브랜치의 설계문서에 그 계획의 `## 구현 대조 — <계획 경로>` 절이 커밋돼 있으면 그 계획이 「구현 끝」이고, 앞 계획의 절은 뒤 계획을 「구현 끝」으로 만들지 않는다(둘 다 git 만 읽음).
- AC8 `control_plane.py` 가 PR 단계(기계 상태 캐시 또는 `gh`)와 판정 줄(진행 중이면 실행 방식 원장, 끝났으면 설계문서 `## 판정`)을 합쳐 보이고, 출처가 없으면 그 단계는 「알 수 없음」, 판정 줄은 「셀 수 없음」이다. 기계 상태 · 실행 방식 원장은 캐시 열쇠에 넣지 않고 매번 읽는다.
- AC9 `/spec-distill:roadmap-status <로드맵> <에픽>` 이 그 에픽의 묶음 · 설계문서 · 계획 · 브랜치 · PR · 열린 넘김 · 판정 줄 · 자원을 경로 · 번호와 함께 보인다.
- AC10 `references/roadmap-ontology.md` 가 계층 넷 · 객체 · 식별자 · 속성 · 링크 · 주인 표를 담고, 락이 표의 링크 칸 이름이 해석기 칸 · frontmatter 키에 실재함을 잰다.
- AC11 `§n` 이 `## <n>.` 머리에서도 풀리고, 계획 판정이 백틱 없는 `**Spec:**` 경로를 받고, 에픽 이름 규칙이 「대문자 + 숫자 + 소문자 선택」이고, 겹침 줄이 내용을 보이고, 「로드맵이 기본 브랜치에 없음」이 검사 불가와 다른 줄 · 종료 코드다.
- AC12 설계문서 없는 묶음 · 묶음 아닌 블록이 계획 · 머지됨이면 번호 대조를 건너뛴 경고와 「셀 수 없음」이 난다(N17).
- AC13 `--impl` 이 설계문서 `roadmap:` 을 읽어 상태 계산과 같은 받는 곳 규칙(실재 에픽 · `#<n>`)을 쓴다.
- AC14 상태 계산의 설계문서 · 계획 찾기가 로드맵 frontmatter `specs_dir` · `plans_dir` 를 git 으로 읽고, 없으면 superpowers 기본 경로를 쓴다(기본 문자열은 한 상수 모듈에만).
- AC15 진입 skill `epic-conductor`(진입 사전 검사 · `cost_class: high` · 처분 줄)가 있고, 시작할 때 규모(남은 에픽 · 띄울 agent 수 — 세션 안에서 라운드마다 도는 리뷰어 agent 포함)를 보이고 `AskUserQuestion` 으로 승인받는다. 같은 세션에서 이어 부를 때 세션 표지가 살아 있고 규모가 그대로면 승인 대신 공시만 한다. 꺼져 있으면 손 절차를 가리키고 멈춘다.
- AC16 `references/conducting.md` 가 지휘 순환 걸음 1~7 마다 기본값 · 판단 기준 · 부를 superpowers skill · 기록 · 기계 상태에 적을 것을 담고, 끝 절에 손으로 따르는 절차를 둔다.
- AC17 이어 가기에 필요한 기록(판정 · 구현 대조 · 지휘 기록)이 에픽 설계문서의 절로 에픽 브랜치에 커밋되고, 기계 상태만 `<state-root>/conductor/<로드맵 폴더>/machine.md` 에 원자 쓰기된다. 지휘자를 다시 부르면 git 과 기계 상태에서 같은 상태를 계산하고, 기계 상태를 지워도 잃는 것은 다시 만들 수 있는 것뿐이다.
- AC18 `merge_check.py` 가 합친 사본을 만들고 그 레포의 스위트를 기준선과 합친 사본에서 돌려, R2a 의 공유본으로 단위를 짝짓고 양쪽 다 빨간 단위는 실패 이름으로 대조한다(이름을 못 뽑는 러너는 「이름 대조 불가 — 단위 수준만」). 동시 실행은 잠금으로 막고, 테스트 명령을 못 찾으면 묻는 자리를 내고, 테스트가 없으면 「스위트 대조 없음」을 낸다.
- AC19 PR 인계 모으기가 블록 브랜치들의 PR 본문 `## 통합 리뷰 인계` 절을 거두고, `gh` 가 없거나 GitHub 이 아니면 설계문서 `## 미룸` 표와 `## 지휘 기록` 을 쓰고 알린다.
- AC20 자원이 기계 상태에 적히고 §5 의 시점에 정리된다. 지우기 전 수정 · 추적 안 된 파일을 보이고 묻고, `--force` 를 쓰지 않고, 브랜치를 지우지 않는다. 기계 상태에 없는 worktree 는 「주인 모름」 목록으로 보인다.
- AC21 `references/conductor-dispatch.md` 가 절대경로 · 흐름과 이유 · 같은 skill 그대로 · 미리 받은 답과 사람 자리 두 부분 반환(쉬운 요약 + 원문) · 마지막 보고의 판정 전체 · AC 보고 내용 전체 · 금지 셋 · 하위별 `TMPDIR` · `Spec:` 트레일러 · 리뷰 원장 이어 가기를 담는다.
- AC22 진행 중 판정 줄이 실행 방식 원장에서 화면으로 가고, 실행이 끝나면 하위 보고의 판정 전체를 앞서 읽은 것과 대조해 설계문서 `## 판정` 에 보관본으로 커밋한다. 설계를 뒤집는 판정 · 막힘이면 그 에픽만 멈추고 묻는다. 보고에도 원장에도 판정이 없으면 「셀 수 없음」이다.
- AC23 사람 몫 걸음이 「지금 답할 수 있나」를 판정하고 배경과 함께 하나씩 묻고, 기다리는 질문에 기대는 일을 진행하지 않으며(이유 기록), 계획 agent 가 돌아오면 지휘자가 「설계에 없던 결정」이 있는지 가려 있을 때만 묻고 그 답 전에는 구현을 보내지 않는다. spec 리뷰가 도는 동안 다른 에픽의 질문은 기록만 하고 게이트 사이 · 리뷰 끝에 묻고, 질문 첫 줄에 에픽 이름을 쓴다.
- AC24 감사 후보(기각 행 · 미룸 표 · 판정 줄 · 리뷰 뒤 반영)를 스크립트가 모으고, 줄어든 넘김(준 쪽 넘김이 받은 쪽 번호 대조 · AC · 미룸에 없음)을 찾는다.
- AC25 넘김마다 항목 · 준 곳 · 받는 곳 · 상태 · 근거를 주인 문서에서 계산해 보이고, 받는 곳 없음은 맡을 에픽 제안 · 재분해로, 받는 에픽 머지 뒤 처리 확인을 그 설계문서 `## 지휘 기록` 에 적는다.
- AC26 알림은 사람 답이 없어 멈췄을 때와 모두 끝났을 때만 보낸다.

- 로드맵을 색인으로(자세히는 묶음) · 요약 표 + 블록 — 앞의 것은 전체를 보려면 묶음을 열어야 하고 재분해 때 묶음도 고친다. 뒤의 것은 같은 내용을 두 번 담는다.
- 조사 에픽을 새 종류로 — 종류를 늘리면 생성기 · 검증 · 분해 판단의 갈래가 는다. `흐름` · `산출물` 칸 둘로 푼다.
- GitHub Projects 같은 별도 보드 — 로드맵과 같은 것을 두 번 적는다. 교훈을 따로 다루는 장치 — S44 「따로 다루지 않음」.
- qg 테스트 스크립트를 R5 가 옮김 · 작은 러너를 새로 만듦 — 앞의 것은 R2a 가 예약한 qg 폴더를 두 에픽이 동시에 고치고, 뒤의 것은 있는 것을 다시 만든다(C32). 이동은 R2a 가(D1.3).
- 지휘 기록 전부를 git 밖 원장 하나에 — 다른 기기 · `.claude` 삭제에서 넘김 · 판정 기록이 사라진다. 이어 갈 기록은 주인 문서로(D1.1).
- 계획을 사람이 있는 설계 세션에서 — 설계 세션이 계획까지 붙들면 한 세션 한 에픽 제약 때문에 다음 에픽 설계가 늦어진다. 계획은 백그라운드가 쓰고, 「새 결정」인지는 계획을 쓰지 않은 지휘자가 가른다.
- spec 리뷰를 담당 agent 가 돌리고 지휘자가 게이트를 중계 — 지휘 세션 맥락은 가볍지만, 2026-10-18 실측(R2a 10라운드)에서 배경이 빠지고 질문이 내부 기호로 왔으며 게이트 밖 후속 질문과 선택지 재작성이 생겼다. 사람 차례가 많은 단계는 사람이 있는 세션에서(재결정 2026-10-18).
- agent teams · Workflow 기반 — 실험 기능이고(«cc-agent-teams» — 재개 불가 · 계획 자동 승인), Workflow 는 명시 요청이 필요하다(S31).
