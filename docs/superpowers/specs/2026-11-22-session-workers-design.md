# 세션 담당자와 위아래 소통 · Design

> 계획부터의 담당자를 리더가 따로 띄운 세션으로 돌리고, 띄운 쪽이 닫는다. 일과 결과는 파일에 두고 메시지는 알림 한 줄이다. 약속은 꼭 필요한 넷만 두고 나머지는 풀어 둔다. 새 스크립트 없이 글로만 짓는다.

## Context / Why

지금 리더(지휘 세션)는 계획 · 구현 담당자를 전부 자기 안의 하위 agent 로 돌린다. 그래서 생기는 일이 넷이다(2026-11-22 사용자에게 보이고 「좋아 이대로 가자」 를 받은 글).

- **담당자가 안 보인다.** 무엇을 하는지 보거나 직접 말을 걸 수 없고 리더를 거쳐야 한다.
- **리더가 흐려진다.** 담당자의 긴 보고가 리더 대화에 그대로 쌓여, 지휘하다 정신을 못 차리거나 보고를 대충 넘긴다.
- **남지 않는다.** 보고가 메시지로만 와서 세션이 끝나면 사라진다.
- **비싸다.** 하위 agent 는 잠깐 쉬면 식어서 다시 부를 때 처음부터 읽는다(사용자 2026-11-18 「서브에이전트는 5분 캐시가 유지되고 메인세션은 1시간 캐시가 유지돼」 — 하위 agent 쪽 수치는 확인하지 못했다).

사용자가 손으로 세션을 띄우면 보이기는 하지만, 설계 없이 개발하거나 띄워 놓고 닫지 않는 일이 생긴다(사용자 2026-11-18 「회수를 안하는 경우가 많네」 · 「메시지 받고 그냥 개발하기도 하더라고」). R2 가 설계 없이 개발하는 것을 관문으로 막았으니, 이 에픽은 띄우고 · 주고받고 · 닫는 일을 리더의 절차로 만든다.

2026-11-22 리더가 이 방식으로 담당자 세션 여덟을 직접 띄워 보았다(조사 넷 · 시험 넷). 잰 사실은 `~/.claude/sdd-mirror/r1-leader/e1-session-trial.md` 에 있고 이 문서가 근거로 쓰는 것은 해당 절에 옮겨 적었다.

## Goals

- G1. 계획 · 구현 담당자를 리더가 따로 띄운 세션으로 돌린다 — herdr-core(`hc`)가 있으면. 없으면 지금의 하위 agent 길이 그대로 돈다.
- G2. 띄운 세션을 띄운 쪽이 닫는다 — 결과를 읽은 뒤 닫고, 내가 띄운 것이 남지 않았는지 본다.
- G3. 리더 – 담당자 – 하위 사이 창구를 층마다 하나로 정한다. 내용은 파일, 메시지는 알림.
- G4. 도는 담당자에게 답과 방향 고침이 닿는다.
- G5. 사람에게 물을 것은 담당자가 파일에 쓰고 리더가 사용자에게 가져온다. 승인은 리더 세션의 질문 창에서만 받는다.
- G6. 마지막 보고를 메시지가 아니라 결과 파일에 싣는다.
- G7. 무엇으로 돌리나(세션 · 하위 agent · 다른 모델 · 스크립트)와 모델 고르기 지침이 문서 한 곳에 있다.

## Non-goals

- 다른 서버에서 띄우기(E3) · 로드맵 사이 소통(R3 가 했다) · 단계와 교대 사이(사용자 2026-11-18 「단계와 교대 사이는 다른 에픽이 풀자」).
- 새 형식을 기본으로 켜기와 앞단 로드맵이 넘긴 셋(E4).
- 설계 대화와 spec 승인까지를 담당자에게 넘기기 — 리더가 한다(사용자 2026-11-18 「담당자한테 넘길때는 계획부터 였자나 그게 맞아 스펙까지는 지금처럼 지휘자가 하는게 맞아」).
- 쓰기 권한 없는 리뷰어(통합 리뷰어 · 옮김 대조)와 품질 게이트 담당자를 세션으로 옮기기 — 하위 agent 로 남긴다(작성자 제안 · §1).
- 리더 세션을 끊고 다시 띄울 때 담당자를 살려 두기(E2).
- Herdr 창에 담당자를 pane 으로 놓는 장치(사용자 2026-11-22 「방금 띄운게 좋았어」).
- 새 스크립트 · 걸음표의 실행기 칸 · 「내가 띄운 것 0」 의 자동 검사(사용자 2026-11-22 「1」 — 글로만).

## Anti-goals

- 담당자 세션이 설계 없이 개발한다.
- 리더나 담당자가 일을 진행시키려고 멈춘 창에 사람 대신 답한다.
- 닫지 않은 세션이 쌓인다.
- 약속을 지키려고 양식 · 금지 옵션 · 확인 절차를 쌓아 모델을 묶는다(사용자 2026-11-18 「다만 모델 제약이 되어선 안돼」 · 2026-11-22 「네이티브 기능을 금지시키는거는 좀 과하지 않나」).
- herdr 가 없는 환경에서 지휘가 돌지 않는다(C5).

## Constraints

- C4 · C5 · C38 · C42 · C50(묶음 §2) — 자리는 [번호 대조](#번호-대조).
- 사용자 2026-11-17 「herdr 권장으로는 하도록 하자 환경이 되면 까는거로」 · 「지휘에서 herdr 기본으로 쓰게 권장 하드코딩하지 말것」 — 권장하되 박지 않는다.
- 사용자 2026-11-18 「없을때 길은 서브에이전트지뭐 너무 무겁게가지말고」.
- 사용자 2026-11-22 「물론 계약이 꼭 필요한곳이 아니면 풀어두는게 맞고 알지?」.
- 레포 원칙 — 레포 전용 값(경로 · 모델 · 브랜치)을 박지 않는다 · denylist 단독 금지 · Secret 기록 금지 · 설치본이 바뀌는 PR 은 판을 올린다.
- hc 문법은 판마다 바뀔 수 있다 — 문서는 명령의 꼴만 보이고 「문법은 매번 `hc --skill` 에서 읽는다」 고 적는다.

## Approaches

2026-11-22 설계 대화에서 셋을 견줬다.

| 접근 | 얻음 | 내줌 |
|---|---|---|
| **1. 글로만** — 보내는 글 문서와 지휘 절차서의 문장으로 띄우기 · 약속 · 거두기를 적는다. 새 스크립트 없음 | 가장 가볍다. hc 판이 바뀌어도 고칠 것이 문장뿐이다 | 닫지 않은 세션 · 표와 실제의 어긋남을 기계가 잡지 못한다 |
| 2. 글 + 두 자리만 스크립트 — 띄울 때 옵션을 붙이는 자리와 「내가 띄운 것 0」 을 스크립트가 지킨다 | 가장 새기 쉬운 두 자리가 기계로 닫힌다 | hc 출력 꼴에 기대는 코드가 생긴다 |
| 3. hc 역할 틀 — `hc templates` 에 역할별 명령을 등록해 부른다 | 띄우는 명령이 한 줄로 준다 | 사용자 홈 설정에 파일을 깔아야 하고 레포 밖 상태가 생긴다 |

리더는 2 를 권했고 사용자가 1 을 골랐다 — 「1, herdr 세션이 터미널도 다루고 하던데 hc keys 금지면 이거도 못하려나」. 이어 띄울 때 hc 기능을 막는 옵션도 두지 않기로 했다 — 「네이티브 기능을 금지시키는거는 좀 과하지 않나」.

## 설계

글이 사는 곳은 둘이다 — 보내는 글 문서(`references/conductor-dispatch.md`)가 주 자리이고, 지휘 절차서(`references/conducting.md`)의 걸음 1 · 3 · 4 · 5 · 7 이 그 문서를 가리키며 자기 걸음의 문장만 맞춘다. 아래 절마다 「어느 문서의 어디」 를 적는다. 문장의 최종 글자와 절의 배치는 계획 담당자가 정한다 — 단 펜스로 보인 「세션 꼬리」(§3)의 약속 문장은 뜻을 바꾸지 않는다.

### §1 무엇으로 돌리나

보내는 글 문서 맨 앞에 절 하나(`## 무엇으로 돌리나`)를 둔다. 일의 종류마다 길 하나다.

| 일 | 길 | 근거 |
|---|---|---|
| 계획 · 구현 담당자, 수리 구현처럼 오래 도는 큰 작업 | hc 가 있으면 따로 띄운 세션(§2). 없으면 하위 agent — 지금 틀 그대로 | 사용자 2026-11-15 「세션이 기본이야」 · 2026-11-18 「없을때 길은 서브에이전트지뭐」 |
| 쓰기 권한 없는 리뷰어(통합 리뷰어 · 옮김 대조) | 하위 agent — agent 정의의 `tools:` 가 쓰기를 막는다 | 작성자 제안. 세션으로 띄웠을 때 그 제한이 걸리는지 확인하지 못했다 |
| 품질 게이트 담당자 | 하위 agent — 지금 그대로 | 작성자 제안. 머지 전 확인을 담당 세션으로 넘기는 일은 E2 범위다 |
| 다른 모델(codex) | 이 플러그인 `scripts/` 의 있는 codex 러너로만 부른다. 새 길을 짓지 않는다 | C50. 정본은 레포의 `shared/codex/` 이고 플러그인의 사본은 사본 계약 락(`shared/tests/test_copy_of_contract.sh`)이 지킨다 — 이미 한곳이다 |
| 스크립트 걸음(스위트 대조 등) | 리더가 직접 돌린다 | 지금 그대로 |

**hc 가 있다는 것.** 리더 세션이 herdr-core 터미널 안에서 돌고 있고(`$HC_TERMINAL_ID` 가 있다) `hc` 명령이 있다는 뜻이다. 둘 중 하나라도 없으면 하위 agent 길로 가고 「herdr 가 없어 하위 agent 로 보낸다」 를 한 줄 알린다. 설치를 요구하거나 멈추지 않는다.

**모델 고르기.** 같은 절에 한 문단을 둔다(작성자 제안 — 자리와 글).

- 담당자를 띄울 때마다 역할에 맞는 모델을 이름으로 싣고 고른 이유를 한 줄 알린다. 세션은 띄우는 명령에(`--model`), 하위 agent 는 dispatch 의 모델 칸에 싣는다. 싣지 않으면 세션은 그 세션의 기본 모델로, 하위 agent 는 리더의 모델로 뜬다.
- 고르는 기준은 다시 쓰지 않고 superpowers 의 `subagent-driven-development` skill 「Model Selection」 절을 가리킨다. 모델 이름은 문서에 박지 않는다.
- 판정과 측정에 들어가는 agent(통합 리뷰어 · 옮김 대조 · 냉독)는 지금 규칙 그대로다 — 모델 칸은 해결자(`review_model`)의 값만 받고 리더가 고르지 않는다.
- 생각 깊이는 다루지 않고, 한도에 걸렸을 때 등급을 내리는 규칙은 두지 않는다(사용자 2026-11-15 「생각 깊이는 고려말아」 · 「한도에 걸리면 한등급 내려 는 하지마」).

걸음표에는 칸을 더하지 않는다. 걸음표의 「누가」 칸은 역할이고, 그 역할을 무엇으로 돌리는지는 이 절이 정한다.

### §2 띄우기

보내는 글 문서에 절 하나(`## 세션 담당자`)를 둔다. 지휘 절차서 걸음 3 의 「보내기」 는 이 절을 가리킨다.

**과제 글은 파일로.** 리더는 지금 틀(계획 · 구현 · team 형식 펜스)을 채운 글 끝에 세션 꼬리(§3)를 붙여 파일 하나로 쓰고(아래에서 「보낸 글 파일」 — team 형식의 과제 파일과 다른 파일이다), 담당자에게는 「이 파일을 읽고 그대로 한다」 한 줄만 건넨다. 보낸 글 파일의 자리는 그 에픽의 옮김 폴더(`conductor_ledger.py resource-dir --kind relay --name <에픽>`)다.

**띄우는 명령의 꼴.** 2026-11-22 에 쓴 그대로다.

```
hc run --bg --json --name <이름> --label role=worker --label epic=<에픽> \
  --cwd <에픽 worktree 절대경로> claude --model <모델> "<보낸 글 파일 절대경로> 를 읽고 그대로 한다."
```

- 문서는 이 꼴을 「hc 가 있으면」 조건 안에 두고 문법은 매번 `hc --skill` 에서 읽으라고 적는다.
- hc 기능을 막는 옵션(`--disallowedTools` 로 `hc keys` 막기 등)을 붙이지 않는다.
- 이름과 라벨 붙이는 법은 풀어 둔다 — 리더가 뒤에 알아볼 수 있으면 된다.
- 담당자는 대화형 세션으로 띄운다 — 한 번 돌고 끝나는 헤드리스(`claude -p`)로 띄우지 않는다(RC13 · 작성자 제안). 사용자가 그 세션에 직접 말할 수 있어야 하고(§3), 물음으로 멈춘 세션이 답을 받아 이어 가야 한다(§4).

**어디서 일할지는 띄울 때 정한다.** `--cwd` 로 그 에픽 브랜치가 서 있는 worktree 의 절대경로를 준다. 세션은 리더의 작업 폴더에 묶이지 않으므로, 하위 agent 길의 격리 worktree · 브랜치 놓기 · 옮겨 가기는 세션 길에서 하지 않는다. 담당자가 일하는 동안 리더는 그 worktree 에 쓰지 않는다 — 기록은 지금처럼 쌓아 두었다가 돌아온 뒤 옮긴다. 틀의 자리 칸은 지금 두 갈래(격리 worktree 에서 브랜치에 서기 — 또는 받은 worktree)를 싣는데, 세션 길은 셋째 갈래로 더해 리더가 그 갈래의 문장만 채워 보낸다 — 꼬리가 앞 문장을 뒤집게 하지 않는다. 원격의 그 브랜치가 앞서 있으면 맞추는 일(`--ff-only`)은 세션 길에서도 하고, 앞 담당자의 작업 기록 백업이 있으면 지금처럼 준다. 다른 서버에서의 자리(어느 사본 · 어느 브랜치 · 어느 worktree)는 E3 가 정한다.

**띄운 뒤 적기.** 지금과 같은 표(기계 상태의 `## 살아 있는 agent` · `## 작업`)에 같은 칸으로 적는다 — 이름은 hc 이름, worktree 는 `--cwd` 의 값이다. 표의 꼴과 그 표를 읽는 명령(`ledger live-agent` · 상태 보기)은 고치지 않는다.

**단계마다 새 세션.** 계획 담당자의 세션을 구현에 이어 쓰지 않는다(RC12). 결과를 받아 닫은 세션은 다시 깨우지 않고 새 세션을 보낸다 — 파일이 맥락을 잇는다(사용자 2026-11-18 「꼭 이어서 해야하는거 아니면 휴식이런거 보다 세션을 죽이고 다시 띄우는게 좋고 그걸 위해 우리 파일 구조를 만든거자나」). 물음으로 멈춘 세션은 답이 그 세션의 일을 끝낼 때까지 닫지 않고, 계획만 고치기 · 좁은 재리뷰처럼 같은 맥락이 필요한 짧은 일은 살아 있는 그 세션에 이어 보낸다.

**리더가 끝나면 담당자도 끝난다.** hc 의 기본값이고 그대로 둔다(작성자 제안). 리더를 끊고 다시 띄울 때 담당자를 남길지는 E2 가 정한다.

잰 것(2026-11-22 · hc 0.1.21 · Claude Code 2.1.330 · macOS): 띄우는 명령은 1초 안에 주소 · 이름 · `parent` 를 돌려준다. 같은 레포의 worktree 에서는 폴더 신뢰 물음과 권한 물음이 뜨지 않았다. 세션 하나의 시작 고정 비용은 첫 응답에서 캐시 쓰기 약 4.8만 + 캐시 읽기 약 2.6만 토큰이다. 처음 보는 폴더와 다른 기계에서는 재지 않았다.

### §3 주고받기

창구는 층마다 하나다.

| 사이 | 창구 | 내용이 사는 곳 |
|---|---|---|
| 리더 ↔ 담당자 | hc 글 한 줄(`hc send`). hc 가 없는 길은 지금의 하니스 길 | 파일 — 보낸 글 파일 · 결과 파일 · 물음 파일 · 설계문서 · 계획 |
| 담당자 ↔ 담당자가 띄운 하위 agent | 하니스 안 그대로(작업 방식이 정한 길) | 하위가 쓰는 보고 파일(지금 문장 그대로) |
| 담당자 ↔ 다른 담당자 | 없다 — 리더에게 알리고 리더가 푼다 | — |

리더는 담당자의 하위 agent 에 직접 말하지 않는다.

**약속 넷.** 사용자가 2026-11-22 에 받아들인 약속은 넷이고 나머지는 풀어 둔다.

1. 일과 결과는 파일로 — 메시지는 알림 한 줄이다(이 절 · §6).
2. 띄운 쪽이 닫는다(§5).
3. 멈춘 창에는 사람만 답한다(§4 · §7).
4. 어디서 일할지는 띄울 때 정한다(§2). 다른 서버에서의 몫은 E3 가 정한다.

둘째 약속은 리더가 지킨다. 세션 꼬리는 나머지 셋 가운데 담당자가 지킬 문장(자리 · 일과 결과는 파일로 · 멈춘 창)에, 담당자에게 일하는 법을 알리는 문장 넷(물음을 쓰는 법 · 꼬리표와 사용자 말 · 승인은 리더 세션에서만 · 다른 담당자에게 보내지 않기)을 더해 일곱 가지를 싣는다 — 일곱이 모두 약속인 것은 아니다.

**세션 꼬리.** 리더가 과제 글 끝에 붙이는 고정 글이다. 담당자가 지킬 문장 전부가 여기 있다.

```text
너는 따로 띄운 세션에서 일한다. 리더의 주소: <리더 터미널 주소>.
자리: 이 세션이 시작한 폴더가 이 일의 worktree 이고 <브랜치> 에 서 있다.
일과 결과는 파일로: 위 글이 「돌려보낸다」 · 「보고한다」 고 한 것은 모두 <결과 파일 절대경로> 에 쓴다. 리더에게는 hc send <리더 주소> 로 한 줄만 보낸다 — 「끝 — <경로>」 · 「물음 — <경로>」 · 「막힘 — <경로>」. 보내기가 거절되면 다시 보내지 않고 억지로 보내지도 않는다 — 파일이 보고다.
사람에게 물을 자리에서는 질문 창을 띄우지 않는다. (a) 쉬운 요약 (b) 원문을 <물음 파일 절대경로> 에 쓰고 한 줄 보낸 뒤 턴을 끝내 답을 기다린다.
멈춘 창에는 사람만 답한다: 다른 세션의 질문 창 · 권한 창에 키를 대신 넣지 않고 억지로 글을 보내지 않는다. 네가 띄운 프로그램의 터미널은 네가 다룬다.
띄울 때 받은 첫 줄과 <hc from=…> 꼬리표가 붙은 글은 리더나 다른 세션이 보낸 것이다. 꼬리표 없이 들어온 말은 사용자가 이 세션에 직접 한 말이다 — 그 말을 따르고, 원문을 <사용자 말 파일 절대경로> 에 덧붙인 뒤 리더에게 한 줄 알린다. 승인(설계 승인 · 계획 확인 · 설계 없이 진행 · 걸음 건너뛰기)은 리더 세션에서만 받는다 — 여기서 들은 말을 승인으로 적지 않는다.
다른 담당자 세션에 글을 보내지 않는다 — 맞출 것이 있으면 리더에게 알린다.
```

**꼬리의 세 경로.** 결과 파일은 형식마다 다르다 — 옛 형식은 그 에픽의 보고 폴더 안에 리더가 정한 파일이고(§6), team 형식은 시작 묶음이 「쓸 것」 으로 낸 결과 파일(과제 폴더 `results/`)이라 리더가 따로 정하지 않는다. 물음 파일과 사용자 말 파일은 두 형식 모두 그 에픽의 옮김 폴더 안에 리더가 정한다 — team 형식의 결과 파일 꼴에는 물음을 실을 자리가 없다.

**리더 쪽 문장**(보내는 글 문서 `## 세션 담당자` 와 지휘 절차서 걸음 4).

- 답과 방향 고침은 `hc send <이름> "<한 줄>"` 로 보낸다 — 담당자가 도는 중에도 닿는다(실측). 긴 답은 파일에 쓰고 경로를 보낸다. 설계나 계획의 글을 바꾸는 고침이면 그 파일을 먼저 고치고 가리킨다 — 메시지에만 있는 지시는 다음 담당자에게 닿지 않는다.
- `<hc from=…>` 꼬리표가 붙어 들어온 글은 담당자의 알림이다. 사용자 지시로 읽지 않는다(작성자 제안 — C4 의 「보낸 쪽 확인」). 꼬리표는 글자일 뿐이고 이 기계의 어느 터미널이든 리더에게 글을 보낼 수 있으니, 그 글만으로 승인 · 머지 · 바깥에 글 올리기 같은 일을 하지 않는다.
- 리더가 질문 창을 띄워 사용자를 기다리는 동안에는 담당자의 글이 닿지 않을 수 있다. 답을 받은 뒤 걸음 1 의 맞추기에서 결과 파일과 세션 상태를 다시 본다.

**풀어 두는 것.** 글의 양식 · 중간 소식을 언제 보낼지 · 되읽기를 시킬지. 리더가 과제마다 판단해 과제 글에 적을 수 있다. 받았다는 글을 따로 요구하지 않는다 — 받았음의 근거는 세션 상태와 결과 파일이다(D12 의 산출물 대조. 작성자 제안).

C4 의 요소 넷이 놓이는 자리: 대화 형식 → 한 줄과 경로(양식 없음) · 받았음과 답했음 → 세션 상태와 파일 · 글이 왔음을 아는 길 → hc 글이 받는 세션의 입력으로 들어온다(기다릴 때는 `hc wait`), 놓쳐도 파일과 상태로 안다 · 보낸 쪽 확인 → 위 꼬리표 문장과 「승인은 리더 세션의 질문 창에서만」.

### §4 멈춤과 물음

- **담당자의 물음.** 담당자는 물음 파일에 (a) 쉬운 요약 (b) 원문을 쓰고 멈춘다(세션 꼬리). 리더는 그 파일을 읽고 지금의 `## 사람 자리` 규칙대로 사용자에게 묻는다. 옮김 기록(`relay-<번호>.md`)의 「받은 원문」 은 담당자가 쓴 그 파일의 글 그대로다 — 리더가 옮겨 적은 글이 아니라 담당자의 파일이 원문이 된다. skill 이 낸 질문이 아닌 물음(담당자가 스스로 낸 설계 물음)도 같은 꼴로 남기고, 리더가 그것을 선택지로 만들면 지금 규칙대로 「지휘자가 만든 질문」 으로 표시한다.
- **기다리는 질문 줄.** 지금처럼 리더가 사용자에게 묻기 직전에 올린다. 담당자 세션이 올리는 길은 만들지 않는다 — 물음은 리더 창에서만 사용자에게 간다.
- **담당자가 창에 멈췄을 때.** 권한 물음이나 질문 창으로 멈추면 리더는 세션 상태에서 무엇을 묻는지 읽을 수 있다(실측 — `hc get` 이 질문 글을 싣는다). 리더는 그 창에 답하지 않고, 어느 세션이 무엇을 묻고 있는지 사용자에게 알린다. 사용자가 그 세션에 붙어 답하거나 닫으라고 한다.
- **멈춘 창에는 사람만 답한다.** 리더도 담당자도 다른 세션의 질문 창 · 권한 창에 키를 대신 넣지 않고 억지로 글을 보내지 않는다. 지키는 것은 이 문장과 §7 이다. 금지 옵션은 걸지 않는다.
- **사용자가 담당자 세션에서 직접 한 말.** 담당자는 따르고 원문을 사용자 말 파일에 적어 알린다(세션 꼬리). 리더는 그 원문을 그 일의 기록 자리에 결정 줄로 옮긴다 — team 형식은 과제 파일의 결정 기록에 `결정` 줄로, 옛 형식은 설계문서의 `## 결정 기록` 에 지금 규칙대로. 승인 줄로는 적지 않는다. 그 말이 설계의 글자 · 수용 기준 · 보이는 동작을 바꾸면 리더가 설계문서에 반영하고 승인은 리더 세션에서 다시 받는다(작성자 제안 — 뒤 문장).
- **막힘이 되풀이될 때.** 같은 걸음에서 담당자가 두 번 이어 막히면 리더는 세 번째로 보내지 않고 사용자에게 간다(작성자 제안. 수 2 는 R2 가 구현 실패에 건 수와 같다 — 사용자 원문 「같은 단계가 두 번 연속 실패하면 멈추고 알리는」). 스크립트는 세지 않는다.

잰 것: 멈춘 세션에 글을 보내면 거절된다. 다른 터미널의 키를 넣는 명령(`hc keys`)은 거절되지 않고 그 질문 창에 답하며, 그 답은 세션 기록에 사람이 고른 답과 같은 꼴로 남는다(R2 의 관문이 읽는 스크립트가 `사람` 으로 읽었다). hc 의 사건 기록에도 누가 넣었는지 남지 않는다. 그래서 같은 계정 안에서는 사람이 누른 키와 프로그램이 넣은 키를 나중에 가를 수 없다.

### §5 끝과 거두기

- **끝의 근거.** 결과 파일과 세션 상태다. 「끝」 글은 알림이다. 띄운 직후의 기다리기(`hc wait`)는 첫 턴이 시작되기 전에 `idle` 로 돌아올 수 있으니 끝으로 읽지 않는다(실측).
- **거두기**(지휘 절차서 걸음 4). 결과 파일을 읽는다 → 지금 걸음 4 의 처리(판정 · 수용 기준 보고 거두기)를 그 파일로 한다 → 세션을 닫는다(`hc kill` → `hc rm`) → 표에서 그 줄을 뺀다 → 내가 띄운 살아 있는 터미널 가운데 표에 없는 것이 0 인지 본다(`hc ls` 에서 `parent` 가 내 주소인 것).
- **맞추기**(걸음 1). 돌고 있는 담당자의 원천은 둘이다 — 하니스 agent 목록과 hc 의 내 자식. 표에 있는데 원천에 없는 줄은 지우고 그 일의 결과 파일이 있는지 본다. 내 자식인데 표에 없는 터미널은 무엇인지 보고 닫거나 표에 올린다. 끝난 세션은 스스로 닫히지 않고 「살아 있음 · 끝남」 으로 남는다(실측).
- **끝**(걸음 7). 표지를 풀기 전에 내가 띄운 살아 있는 터미널이 0 인지 본다.
- 남의 세션은 건드리지 않는다 — `parent` 가 내 주소인 것만 닫는다.
- 기다릴 때는 지금처럼 끊어서 기다린다. 세션 길에서는 `hc wait --children any --timeout <초>` 를 쓰고, 돌아올 때마다(글이 왔다 · 상태가 바뀌었다 · 시간이 다 됐다) 내 자식의 상태와 결과 파일 · 물음 파일을 본 뒤 다시 기다린다. 질문 창에서 사용자 답을 받은 직후에도 한 번 본다 — 그동안 온 글은 닿지 않았을 수 있다. 얼마마다 볼지의 수는 박지 않는다(지금 절차처럼 리더가 정한다).

### §6 마지막 보고

- **옛 형식 로드맵의 세션 담당자.** 지금 `## 마지막 보고` 의 칸(판정 전체 · 수용 기준 보고 전체 · 쓴 미리 받은 답과 자리 · 커밋 목록 · 브랜치 · 남긴 파일 · 본 테스트 실패 이름)을 마지막 메시지가 아니라 결과 파일에 싣는다. 결과 파일의 자리는 리더가 과제 글에 절대경로로 적는다 — 그 에픽의 보고 폴더(`resource-dir --kind report --name <에픽>`) 안이다(작성자 제안). worktree 가 지워져도 남고, 세션 담당자는 그 폴더에 도구로도 셸로도 쓴다(2026-11-22 실측 — 격리된 하위 agent 는 도구가 거절됐던 자리다).
- **옛 형식 로드맵의 하위 agent 길.** 지금대로 마지막 메시지다. 고치지 않는다(작성자 제안 — C42 「보고는 결과 파일로만」 의 예외다. hc 가 없을 때만 가는 길이고, 그 길의 틀을 고치면 이 에픽이 「그대로 둔다」 고 한 하위 agent 길의 뜻이 바뀐다).
- **team 형식.** 세션 길이든 하위 agent 길이든 보내는 글의 펜스 뒤에 `## 마지막 보고` 절을 붙이지 않는다. 보고는 과제 폴더 `results/` 의 결과 파일 줄이다(R1). 물음은 세션 길이면 물음 파일로, 하위 agent 길이면 지금처럼 돌려보내는 글로 온다. 일꾼 역할 문서에 「구현을 끝낼 때 수용 기준마다 `AC<번호>: 구현됨 | 미룸 | 빠짐 — 근거` 줄을 결과 파일에 쓴다」 한 줄을 더한다 — 줄의 꼴은 형식 정본(`team-files.md`)에 있지만 일꾼 역할 문서에는 그 줄을 쓰라는 문장이 없어 결과 대조가 「보고에 없는 AC」 로 거절할 수 있다.
- team 형식 결과 파일에 칸이 없는 둘(담당자가 본 테스트 실패 이름 · 쓴 미리 받은 답)은 이 에픽이 칸을 만들지 않는다 — [미룸](#미룸).

### §7 머지 전 승인 기록

사람이 답했다는 근거의 구멍(§4 의 잰 것)을 닫는 마지막 문이다. 지휘 절차서 걸음 5 에서 머지 명령 줄을 내기 전에, 그 에픽에서 받은 승인을 모아 사용자에게 다시 보인다.

- 옛 형식: 설계문서 `## 지휘 기록` 의 spec 승인 줄과 병렬 답, 옮김 기록의 질문과 답.
- team 형식: 이미 있는 PR 전 확인의 `ledger human-check` 출력 — 고치지 않는다.
- 끝에 한 문장: 하신 적 없는 승인이 있으면 머지하지 말고 알려 달라.

형식 정본(`team-files.md`)의 「막지 못하는 것」 목록에 이미 「다른 세션이나 프로그램이 리더의 터미널에 키를 넣어 질문 창에 답하는 것」 이 있다. 그 줄에 hc 가 깔린 기계에서의 길 둘(키 넣기 · 억지로 보내기)과 잰 날짜를 덧붙인다.

### §8 역할 문서의 첫 줄

역할 문서 틀 넷과 이 레포의 사본 넷, 형식 정본, README 의 「첫 줄의 두 커밋을 결과 파일 머리에 옮긴다」 를 규칙을 읽은 커밋까지 옮기는 문장으로 고친다(R3 이 넘긴 것). 둘만 옮기면 결과 파일 머리에서 규칙 커밋이 빠져 거짓 「묶음 낡음」 이 뜬다. 짝은 역할마다 하나다 — 틀 `templates/team/role-<역할>.md` 와 사본 `docs/superpowers/roadmaps/<역할>/CLAUDE.md`. 지금 네 짝 모두 바이트가 같고(2026-11-22 대조) 고친 뒤에도 같게 둔다.

## 인터뷰와 달라진 것

- **D9 · OQ3 · S4 — 일꾼의 기본.** 인터뷰는 「하위 agent 를 기본으로 하고 단계표의 실행기 칸으로 … 고른다」 였다. 사용자가 2026-11-15 에 세션을 기본으로 다시 정했다. 실행기 칸은 만들어진 적이 없고 이 에픽도 만들지 않는다 — §1 의 절 하나가 대신한다.
- **«herdr».** 인터뷰는 「특정 도구 의존이라 실행기 칸의 선택지로만」 이었다. 사용자가 2026-11-17 에 권장으로 다시 정했다. 지금의 herdr 는 인터뷰 때의 터미널 멀티플렉서가 아니라 herdr-core(`hc`)다. 없으면 하위 agent 로 도는 것은 그대로라 C5 는 지킨다.
- **받음 확인.** 인터뷰 §5 는 「받음 확인 · 대화 계약은 유지」 였다. 받았다는 글은 요구하지 않고 세션 상태와 결과 파일을 근거로 삼는다(작성자 제안 — 사용자 2026-11-22 의 계약 기준과 D12).

## 있는 것 검토

찾은 곳: 이 레포(`plugins/spec-distill` · `shared/` · `docs/`)의 띄우기 · 보내기 · 보고에 닿는 글과 스크립트, 이 기계에 깔린 hc 의 설명서(`hc --skill` · `herdr-app --skill`), 하니스의 agent 도구 목록. 웹은 찾지 않았다 — 고를 도구를 사용자가 이미 정했고 그 도구를 직접 재 보았다.

결론과 승인: hc 를 권장 길로 쓴다 — 사용자 2026-11-15 「세션이 기본이야 … herdr라면 이 스킬을 쓰는걸 권장하고」 · 2026-11-17 「herdr 권장으로는 하도록 하자 환경이 되면 까는거로」 · 2026-11-22 「방금 띄운게 좋았어」. 직접 만드는 것은 없다.

## 상류 · 하류 연계

- **받는 것.** R1 의 과제 폴더와 결과 파일 · R2 의 걸음표 · 관문 · 시작 묶음 · 보내는 글 틀 · R3 의 기다리는 질문 줄.
- **넘기는 것.** E2 — 리더를 끊고 다시 띄울 때의 담당자(기본값은 함께 끝남) · 머지 전 확인을 담당 세션으로 · 지휘 절차서를 걸음별로 쪼갤 때 이 에픽이 더한 문장의 자리. E3 — 넷째 약속의 다른 서버 몫과 의존 표의 hc 행. E4 — team 형식의 결과 파일 칸과 검수 쪽 넘김. R5 — 다시 잴 때 세션 시작 고정 비용을 기준선과 견준다.
- **되돌아오는 길.** 글로만이 새면(닫지 않은 세션이 쌓인다 · 머지 전 확인에서 한 적 없는 승인이 나온다 · 표와 hc 가 자주 어긋난다) 접근 2 의 두 자리를 스크립트로 올릴지 사용자에게 다시 묻는다.
- **같은 상태를 읽는 표면.** 돌고 있는 담당자 — 기계 상태의 표 · `hc ls` · 하니스 agent 목록 셋이 읽는다. 원천은 뒤의 둘이고 표는 사본이다(§5).
- **이음매.** 앞단 로드맵의 「앞단 다시 짜기」 에픽이 보내는 글 문서와 지휘 절차서를 함께 고친다 — 머지 순서와 충돌은 통합 리뷰가 본다. 이 에픽의 경로 예약에 없는 파일(README 는 공유 파일)은 [Files to Modify](#files-to-modify) 에 표시했다.

## Acceptance Criteria

- AC1. 보내는 글 문서에 「무엇으로 돌리나」 절이 있고 §1 의 다섯 길(담당자 · 쓰기 없는 리뷰어 · 품질 게이트 담당자 · 다른 모델 · 스크립트)과 모델 고르기 문단을 싣는다. 모델 고르기 문단은 superpowers 의 Model Selection 절을 가리키고 모델 이름을 싣지 않는다.
- AC2. hc 가 없으면 하위 agent 길로 가고 한 줄 알린다는 문장이 있고, 하위 agent 길의 지금 틀(계획 · 구현 · 이어 부르기)은 뜻이 바뀌지 않는다.
- AC3. 띄우는 명령의 꼴이 「hc 가 있으면」 조건 안에 있고, 문법을 `hc --skill` 에서 읽으라는 문장이 있으며, hc 기능을 막는 옵션이 문서 어디에도 없다.
- AC4. 세션 꼬리 펜스가 보내는 글 문서에 있고 §3 세션 꼬리의 일곱 가지(자리 · 일과 결과는 파일로 · 물음 · 멈춘 창 · 꼬리표와 사용자 말 · 승인은 리더 세션에서만 · 다른 담당자)를 모두 싣는다. 약속 넷이 놓이는 자리는 §3 의 「약속 넷」 이 적는다.
- AC5. 리더가 `<hc from=…>` 꼬리표가 붙은 글을 사용자 지시로 읽지 않는다는 문장이 보내는 글 문서나 지휘 절차서에 있다.
- AC6. 지휘 절차서 걸음 1 · 4 · 7 이 §5 를 싣는다 — 원천 둘 · 거두기 순서(결과 파일 읽기 → 닫기 → 표에서 빼기 → 내가 띄운 것 0) · 띄운 직후의 `idle` 을 끝으로 읽지 않기 · 남의 세션을 건드리지 않기.
- AC7. 담당자가 쓴 물음 파일의 글이 옮김 기록의 받은 원문이 된다는 문장과, skill 이 낸 질문이 아닌 물음의 기록 꼴이 `## 사람 자리` 에 있다.
