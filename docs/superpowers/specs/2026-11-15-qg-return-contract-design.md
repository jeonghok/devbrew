# R5 — intent-critic 돌려주는 꼴 계약 · qg 안쪽 뒤처리 · Design

> `intent-critic` 단계가 리뷰 끝에 남기는 결과 파일(`intent-return.md`) 하나만 읽고도 부르는 쪽이 질문을 사람에게 옮길 수 있게 그 꼴을 계약으로 굳힌다. 함께 R1 · R2 설계가 미룬 qg 안쪽 행 가운데 오류 없이 틀리는 것과 몇 줄로 멈춤 · 죽음을 막는 것을 고치고, 만나기 어려운 것은 이유를 적어 닫는다. 질문을 보관하는 일과 에픽 · 로드맵 질문에 답을 남기는 일은 부르는 쪽(R3)의 몫이다.

## Context / Why

R1 · R2 가 머지된 뒤 `intent-critic` 단계는 리뷰 끝에 세션 폴더의 `intent-return.md` 에 결과를 남긴다. 절차 문서는 이 파일을 「부른 흐름이 읽는 계약」 이라 부르지만, 지금 꼴로는 부르는 쪽이 질문을 옮길 수 없다(조사: 지휘 자원 폴더 `files/report/design-research/r5-research.md`, 2026-11-15 main `e3136e55` 기준).

- **질문이 없다.** 질문마다 정체 문자열 · 상태 · 답 · 답 파일 · 근거의 종류만 있다. 질문 글 · 의심하는 대상 · 본 관찰은 `intent-questions.yaml` 에만 있고, 그 파일로 가는 길(세션 폴더 경로)도 꼴에 없다. `_rows` 가 질문 글을 만들어 놓고 `_write_return` 이 쓰지 않는다.
- **서로 다른 일이 한 상태다.** 「아직 묻지 않음」 하나에 넷이 뭉쳐 있다 — 물었는데 답하지 않음 · 답 기록 실패 · 범위 모드라 묻지 않음 · 묻기 전에 실행이 끊김. 기록에 실패한 답은 `answer: "-"` 로 나가서, 사용자가 「잘못 골랐다」 고 답한 사실이 꼴에서 사라진다(공시 줄에만 남는다).
- **「없음」 의 뜻을 알 수 없다.** `status: ran` 에 질문이 비면 「질문 없음」 · 「근거 없어 모두 걸러짐」 · 「모두 걸러짐」 을 가르지 못한다. 가르는 결과 줄은 `result.md` 에만 있다. `status` 는 한국어 사유 글이라 닫힌 어휘가 아니고, 실패(「리뷰 트리를 만들지 못함」)가 건너뜀과 같은 머리로 나간다.
- **수명이 적힌 것보다 짧다.** R1 설계는 범위 모드의 묻지 않은 질문이 「다음 실행이나 24시간 뒤」 사라진다고 적었다. 실제로는 같은 세션에서 qg 를 한 번 더 부르는 순간 세션 폴더가 통째로 지워지고(`setup-qg.sh`), 24시간 정리는 그 뒤 다른 세션이 qg 를 시작할 때만 돈다. 범위 모드 질문은 답 파일도 생기지 않아 세션 폴더가 유일한 사본이다.
- **R1 · R2 가 미룬 qg 안쪽 행이 31개다.** 조사가 행마다 지금 코드에서 사실인지 확인하고 갈랐다 — 계약에 닿는 것 6 · 오류 없이 틀리는 것 5 · 만나기 어려운 가장자리 17 · 글 다듬기 3. 이미 고쳐진 행은 없다.

왜 지금인가 — R3(지휘자 경유 입구)은 이 꼴을 읽어 질문을 옮기는 에픽이고 옆 로드맵의 지휘 절차 개편 설계를 기다린다. qg 쪽 계약은 지휘 절차 파일을 건드리지 않으므로 먼저 굳혀 둘 수 있다(2026-11-15 재분해, PR #289).

## Goals

- G1. `intent-return.md` 하나만 읽고 질문을 사람에게 옮길 수 있다 — 질문 글 · 의심하는 대상 · 관찰 · 근거의 종류 · 상태 · 답이 한 파일에 있다.
- G2. 질문의 상태가 부르는 쪽이 할 일을 가른다 — 다시 답을 받아야 하는 것 · 사유를 고쳐야 하는 것 · 아직 묻지 않은 것.
- G3. 「없음」 · 「건너뜀」 · 「실패」 를 닫힌 어휘로 가른다 — 글자 비교 없이.
- G4. 읽을 세션 파일과 그 수명이 문서에 실제 동작대로 적힌다.
- G5. 미룬 행 가운데 오류 없이 틀리는 것과, 몇 줄로 멈춤 · 죽음을 막는 것을 고친다.
- G6. 미룬 행이 다시 떠돌지 않는다 — 하는 것 · 하지 않는 것(이유) · 넘기는 것(받는 곳)으로 모두 닫는다.

## Non-goals

- 지휘 절차 파일 · 지휘자의 자동 호출 · 질문을 옮기고 보관하는 일(R3).
- 범위 모드(에픽 · 로드맵 리뷰) 질문에 답을 기록하는 길(R3 — `## 미룸`).
- qg 본문(`SKILL.md`) 흐름과 README(R4).
- 걷기 · 실행. 리뷰어가 무엇을 의심하는지(페르소나의 판단 규칙)도 바꾸지 않는다.
- qg 판정(통과 · 막힘). `intent-critic` 의 질문은 지금처럼 판정에 들지 않는다.

## Anti-goals

- 꼴을 넓히다가 리뷰한 트리의 글이 새 지시처럼 읽히는 길을 여는 것 — 질문 글 · 관찰은 지금 `result.md` 에 싣는 것과 같은 정리(한 줄로 만들기)를 거친 값만 싣는다.
- 묶거나 빼면서 세지 않는 것 — 새로 빼거나 한데 묶는 항목은 모두 수를 공시한다.
- 가장자리를 닫는다며 상한을 새로 둬서 보이는 동작을 바꾸는 것.

## Constraints

- 경로 예약(로드맵 R5 블록) 안에서 고친다 — `intent_critic.py` · `intent_answers.py` · `intent_origin.py` · `other_teams.py` · `agents/intent-critic.md` · `skills/quality-pipeline/references/`. 테스트 · `plugin.json` · `CHANGELOG.md` 는 어느 에픽이나 함께 고치는 파일이다. `SKILL.md` · `README.md`(R4 예약)는 건드리지 않는다. 예외 하나 — qg 본문(`skills/quality-pipeline/SKILL.md`) 제목의 판 표기 한 줄은 major 판 올림에 맞춰 고친다(제목의 major 가 shipped major 와 같은지 보는 락 때문이다 · 사용자 허락 2026-11-16). 본문의 다른 줄은 건드리지 않는다.
- 리뷰어 정의(`agents/intent-critic.md`)는 이 설계로 고칠 것이 없다. 고치게 되면 페르소나 파일이라 보안에 민감한 변경으로 리뷰한다.
- `intent_critic.py` 의 반복문에서 일찍 빠지는 갈래는 회계 처분을 갖는다(배선 검사가 본다 — R1 계획의 판정 C11).
- 스크립트 · 테스트가 걸리는 레포 락(UTF-8 명시 · 금지 토큰 · 20줄 중복 · CHANGELOG 연속)을 지킨다.
- 시간 한도 같은 새 기본값은 스크립트의 이름 붙은 상수 하나로 두고, 이미 있는 값(`gh` 호출의 한도)과 같은 것을 쓴다 — 레포 전용 값을 박지 않는다.

## Approaches

| 길 | 무엇 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **가 (고름)** | qg 는 결과 파일 하나를 스스로 완결되게 하고 수명을 명시한다. 보관은 부르는 쪽 | qg 는 리뷰에만 집중한다(U3). 옆 로드맵이 만들 「기다리는 질문」 의 자리와 겹치지 않는다. 변경이 작다 | R3 가 붙기 전까지 손으로 돌린 에픽 · 로드맵 리뷰의 질문은 지금처럼 다음 qg 호출에 사라진다 |
| 나 | qg 가 리뷰 끝에 묻지 않은 질문을 docs 답 자리에 파일로 남긴다 | 질문이 바로 살아남는다 | 머지 뒤 리뷰라 커밋할 브랜치가 없어 추적되지 않는 파일이 작업 폴더에 생긴다. 지휘자 쪽 설계 전에 파일 꼴과 답하는 길을 미리 정해 다시 고칠 위험이 있다 |
| 다 | 지금 꼴을 두고 부르는 쪽이 `intent-questions.yaml` 을 함께 읽게 문서화한다 | 코드 변경이 가장 작다 | 내부 파일이 계약이 된다. 뭉친 상태 · 사라지는 「잘못 골랐다」 는 그대로다 |

사용자가 「가」 를 골랐다(U2). 「다」 는 Context 의 둘째 · 셋째 문제를 풀지 못해 뺐다.

## 설계

### §1 돌려주는 꼴 2판

파일 이름(`intent-return.md`) · 펜스(`qg-intent-return`) · 쓰는 자리(`_write_return` 하나)는 그대로다. 칸을 더하고, 값의 어휘를 닫는다. 지금 있는 칸은 이름과 순서를 지키고 새 칸은 아래 자리에 둔다.

```
contract: 2
status: ran
reason: "-"
reason_text: "-"
outcome: questions
result_line: "intent-critic — 질문 2개를 물었다 · 답 1개(잘못 골랐다 1개) · 답하지 않음 1개"
none_reason: "-"
mode: pr
reviewed_head: "1a2b3c4d"
reviewed_base: "9f8e7d6c"
session_dir: "/abs/path/.claude/quality-gates/<session-id>"
answers_dir: docs/qg-intent-answers
answers_dir_source: default
commit: "5e6f7a8"
breadth: narrow
other_teams: other-teams.md
overlaps: 0
questions:
  - n: 1
    id: "docs/…/brief.md#D19#범위 축소"
    state: 답함
    answer: 잘못 골랐다
    answer_text: "-"
    wrong_choice: true
    failure: "-"
    file: "docs/qg-intent-answers/20261115T010203Z-abcdef012345.md"
    evidence: "돌려서 봄"
    question: "…"
    target_source: "docs/…/brief.md"
    target_id: "D19"
    label: "…"
    quote: "…"
    observation:
      - "…"
      - "…"
```

새 칸과 바뀐 값:

| 칸 | 값 | 뜻 |
|---|---|---|
| `contract` | `2` | 꼴의 판. 읽는 쪽은 모르는 판이면 읽지 않고 그 사실을 알린다. 이 칸이 없는 파일은 1판이다 |
| `status` | `ran` · `uncountable` · `skipped` · `failed` 가운데 하나 | 닫힌 어휘. 「리뷰 트리를 만들지 못함」 은 `failed` 다 |
| `reason` | `skipped` 면 `kill-switch` · `halted` · `trivia` · `empty-diff` · `no-evidence` 가운데 하나, `failed` 면 `tree-failed`, 그 밖은 `-` | 닫힌 부호. 건너뛰거나 실패한 까닭 |
| `reason_text` | 사람이 읽는 사유 글(지금 `status` 에 붙던 글). `uncountable` 이면 공시 줄의 첫 줄 | 옮길 때 그대로 보일 글 |
| `outcome` | `ran` 이면 `questions` · `none` · `no-evidence` · `all-filtered` 가운데 하나, 그 밖은 `-` | 질문이 왜 있고 없는지. `render` 의 결과 줄이 이미 가르는 갈래와 같은 집합이다. `none` 은 둘을 함께 뜻한다 — 리뷰어가 낸 질문이 없던 실행, 그리고 낸 질문이 모두 이미 답한 질문이라 걸러진 실행(앞서 「잘못 골랐다」 고 답한 것 포함). 거른 목록은 R4 가 꼴에 싣기 전까지 `result.md` 에만 있다 |
| `result_line` | `render` 가 낸 결과 줄(또는 건너뜀 줄) 그대로 | 사람에게 보인 한 줄 |
| `none_reason` | 리뷰어가 질문이 없다고 낸 이유(리뷰어 출력의 `none_reason`), 없으면 `-` | 「왜 질문이 없나」. 호출이 둘이면 둘을 ` / ` 로 잇는다 |
| `reviewed_head` · `reviewed_base` | `prepare` 가 받은 리뷰 커밋과 범위의 기준 rev 를 그때 커밋 해시로 풀어 둔 값(풀지 못하면 `-`) | 어느 리뷰의 질문인지. PR 범위의 리뷰 커밋은 글자 `HEAD` 로 오고 답 커밋이 `HEAD` 를 옮기므로 `prepare` 때 풀어 둔다. `commit` 은 지금처럼 답 커밋이다. 답 파일의 `target`(트리 정체)과는 다른 값이다 — 꼴의 질문과 답 파일은 `file` 칸으로 잇는다(D10) |
| `session_dir` | 세션 폴더의 절대경로 | `other_teams` 값과 다른 세션 파일의 기준 |
| 질문 `n` | 1부터 | 한 실행 안에서 유일한 번호. 정체(`id`)는 한 실행 안에서 겹칠 수 있다. 물을 질문이 정해질 때 매기고, 질문 창 · 답 입력의 머리 줄 · 답 기록 · 이 파일이 같은 번호를 쓴다(§2 · D13) |
| 질문 `state` | §2 의 다섯 | |
| 질문 `answer` | 기록에 실패한 답도 고른 답을 싣는다 | 실패한 「잘못 골랐다」 가 사라지지 않는다 |
| 질문 `answer_text` | 직접 쓴 답이면 그 원문의 줄 목록, 선택지를 골랐으면 `-` | 직접 쓴 답은 원문 첫머리가 라벨과 맞지 않으면 `answer` 가 「지금은 모르겠다」 로 떨어진다. 기록에 실패하거나 스위치로 막혀 답 파일이 없을 때도 사용자가 쓴 글이 사라지지 않게 원문을 함께 싣는다. 줄마다 글 칸과 같은 정리를 거친다(D15) |
| 질문 `wrong_choice` | `true` · `false` | YAML 판에 따라 달리 읽히던 `yes` · `no` 를 대신한다. 기록에 실패했어도 고른 답이 「잘못 골랐다」 면 `true` |
| 질문 `failure` | 답 기록 실패의 사유, 아니면 `-` | |
| 질문 `question` · `target_source` · `target_id` · `label` · `quote` · `observation` | `intent-questions.yaml` 의 같은 칸. `observation` 은 관찰 줄 전부의 목록이다(D14) | 절차가 질문 창을 짓는 데 쓰는 칸 전부. 질문 창은 지금처럼 관찰의 첫 줄만 쓴다. 답 파일이 관찰 전부를 기록하고 다시 묻기 판정이 그것을 보므로, 나중에 답을 기록할 쪽이 같은 답 파일을 만들 수 있게 전부 싣는다 |

- 글 칸은 모두 지금 `id` · `file` 처럼 따옴표로 감싸 한 줄로 쓴다. 싣기 전의 정리는 공시 줄에 쓰는 정리(`intent_critic.py` 의 `_one_line`) 수준이다 — 줄바꿈뿐 아니라 줄 가름 글자(U+2028 등) · 제어 글자 · 글 방향을 바꾸는 글자까지 접는다. 결과 표의 칸 정리(`_cell` — 줄바꿈과 세로선만 바꾼다)로는 모자란다. Anti-goals 의 「정리」 는 이 수준을 뜻한다. `observation` 은 줄마다 이 정리를 거친다.
- 근거 없어 리뷰어를 부르지 않은 실행은 `status: skipped` · `reason: no-evidence` 이고, 리뷰어를 불렀는데 좁은 리뷰에서 모두 걸러진 실행은 `status: ran` · `outcome: no-evidence` 다 — 리뷰어를 불렀는지가 다르므로 둘을 합치지 않는다.
- `result.md` 의 `## intent-critic` 표 상태 칸도 같은 다섯 값을 쓴다(한 어휘).
- 버전: 있던 칸(`status` · `state` · `wrong_choice`)의 값이 바뀌므로 quality-gates major bump 다.

### §2 질문의 상태 다섯

| 상태 | 언제 | 부르는 쪽이 할 일 |
|---|---|---|
| `답함` | 답 파일이 기록됐다 | `wrong_choice: true` 면 행선을 정한다 |
| `답 기록 실패` | 입력에 그 질문의 답이 있었는데 기록하지 못했다. `answer` 에 고른 답, `failure` 에 사유 | 사유를 고친다. `wrong_choice: true` 면 그 사실을 잃지 않는다 |
| `답하지 않음` | 물었고 답 기록이 돌았는데 그 질문의 답이 입력에 없었다 | 다음에 다시 묻는다 |
| `묻지 않음` | 범위 모드이거나, 답 기록이 돌지 않았다(묻기 전에 끊김) | 묻는다 |
| `상한 넘어 남김` | 지금과 같다 | 지금과 같다 |

로드맵 R5 블록은 「상태 넷」 이라 적었다 — 새로 가르는 셋과 「답함」 을 센 것이고, 이미 있던 「상한 넘어 남김」 을 더하면 값은 다섯이다.

`답하지 않음` 과 `묻지 않음` 을 가르는 기준은 「질문 창을 보였는가」 다. 지금 절차 I5 는 답한 질문이 하나도 없으면 `record` 를 건너뛰어서, 물었는데 아무것도 답하지 않은 실행과 묻기 전에 끊긴 실행을 가를 수 없다. I5 를 고쳐 질문 창을 보인 실행은 답이 하나도 없어도 `record` 를 빈 입력으로 돌린다 — `record` 가 돈 사실이 「물었다」 의 표지다(D9). `render` 결과 줄의 「답하지 않음 k개」 와 꼴의 `state` 는 같은 판정에서 나온다 — 지금 결과 줄은 답 기록이 돌았는지 보지 않고 세므로 함께 맞춘다. 표지를 어디에 남길지는 계획이 정한다.

결과 줄(`result_line` 으로도 나간다)의 낱말은 `state` 값과 같은 글자를 쓴다. 묻지 않은 질문만 있는 실행의 결과 줄은 「물었다」 로 시작하지 않는다 — 범위 모드는 「intent-critic — 질문 k개 묻지 않음(범위 모드)」(지금의 「아직 묻지 않음」 을 바꾼다), PR 범위에서 답 기록이 돌지 않은 실행은 「intent-critic — 질문 k개 묻지 않음(묻기 전에 끝남)」 이다. 지금 코드는 뒤 갈래를 「질문 k개를 물었다 · 답 0개」 로 낸다.

**질문 번호(D13).** 물을 질문이 정해질 때(`filter`) 질문마다 번호를 매겨 질문 기록에 남긴다. 질문 창의 머리 · 답 입력의 머리 줄 · `record` · 결과 파일의 `n` 이 같은 번호다. `record` 는 번호로 답을 질문에 붙이고, 머리 줄의 정체가 그 번호의 질문과 맞는지 확인한다 — 맞지 않으면 붙이지 않고 「정체가 맞지 않는 답 머리」 로 센다(§5 의 4a 와 같은 공시). 그때 그 번호의 질문은 `답 기록 실패` 로 남는다 — `answer` 에 머리 줄의 고른 답, `failure` 에 「정체가 맞지 않는 답 머리」 를 싣는다. 번호로 그 질문을 가리킨 답은 「입력에 그 질문의 답이 있던」 것으로 친다(§5 의 4b · D15) — 정체를 잘못 옮겨 적은 「잘못 골랐다」 가 사라지지 않는다. 번호가 물은 질문 어느 것도 가리키지 않는 머리는 공시만 한다. 지금 코드는 정체만으로 붙여서, 정체가 같은 두 질문 가운데 둘째에만 한 답이 첫째에 붙는다. 번호 없는 머리 줄은 받지 않는다 — 절차 문서와 스크립트가 같은 판으로 나간다.

### §3 자리와 수명

- **자리는 그대로다.** `intent-return.md` 와 `other-teams.md` 는 세션 폴더에 산다. qg 는 묻지 않은 질문의 새 보관 자리를 만들지 않는다(U2 · U3).
- **수명을 실제대로 적는다.** 세션 폴더는 같은 세션의 다음 qg 시작에 지워진다. 그 세션이 qg 를 다시 부르지 않으면, 폴더가 정리 기한(기본 24시간)보다 오래된 뒤 어느 세션이든 qg 를 시작할 때 지워진다. 이 문장을 `state-file-format.md` 와 절차 문서 I7 에 적는다. 머지된 R1 설계문서는 고치지 않는다.
- **가져갈 것은 최대 둘이다.** 나중에 쓸 부르는 쪽은 qg 를 다시 부르기 전에 `intent-return.md`(완결)와, 다른 팀 기록이 필요하면 `session_dir` 아래 `other_teams` 값의 파일을 가져간다. I7 에 이 문장을 적는다.
- 사람이 직접 돌린 실행에서는 I7 이 지금처럼 `intent-return.md` 를 그대로 보인다 — 이제 질문 글이 함께 보인다.

### §4 끄기 스위치

- `gate` · `prepare` 의 스위치 판정(`_killed`)이 단계 스위치(`DEVBREW_QUALITY_GATES_DISABLE_INTENT_CRITIC`)와 함께 플러그인 전역 스위치(`DEVBREW_QUALITY_GATES_DISABLE=1`)를 읽는다. 변수 하나를 더 읽을 뿐이고 새 이름 붙은 스위치(`DEVBREW_SKIP_HOOKS=quality-gates:<이름>`)는 열지 않는다 — 이 단계에는 이미 이름 붙은 단계 스위치가 있다. 같은 폴더의 판정 정본 함수(`kill_switch_active.py`)는 이름 붙은 스위치까지 읽으므로 쓰지 않고, qg 의 다른 스크립트(`setup-qg.sh` · `publish-comment.sh`)처럼 변수를 직접 읽는다(D11).
- `record` 도 같은 판정을 먼저 한다 — 어느 스위치든 켜져 있으면 답 파일을 쓰지 않고 커밋하지 않으며 그 사실을 한 줄로 낸다. 세션 폴더 밖에 쓰는 하위 명령은 `record` 뿐이다. 그때 입력에 답이 있던 질문은 `답 기록 실패` 로 남는다 — `failure` 에 스위치 사유, `answer` 에 고른 답을 싣는다(§2 · AC3 — 스위치 때문에 「잘못 골랐다」 가 사라지지 않는다). `record` 의 스위치 판정은 `gate` · `prepare` 의 꺼짐 처리(건너뜀 꼴 쓰기)를 하지 않는다 — 꼴은 뒤의 `render` 가 쓴다.
- `config` · `filter` · `render` 는 스위치를 읽지 않는다. 셋은 세션 폴더 밖에서는 읽기만 한다 — `config` 는 git 으로 base 쪽 설정과 리뷰 트리의 설정 파일을, `filter` 는 리뷰 트리의 답 자리와 인용한 파일을 읽는다. 리포를 바꾸지 않고 다른 브랜치 · 네트워크를 읽지 않는다. 막을 것은 밖에 쓰는 `record` 와 다른 브랜치 · 네트워크를 읽는 `prepare` 다.
- 건너뜀 줄과 꼴의 `reason: kill-switch` 는 지금과 같고, `reason_text` 가 어느 스위치였는지 밝힌다.
- README 는 고치지 않는다 — 전역 스위치가 플러그인 전체를 끈다는 설명은 이미 있다.

| 다른 팀 바이트 공시(7a) | 공시하는 바이트가 리뷰어에게 실제로 보낸 줄이 아니라 기록 원문 기준이다 | 실제로 보낸 다른 팀 줄의 바이트를 공시한다 |

## Acceptance Criteria

- **AC1** `intent-return.md` 는 `contract: 2` 를 갖고, 질문마다 `n` · `question` · `target_source` · `target_id` · `label` · `quote` · `observation` 을 싣는다 — 절차가 질문 창을 짓는 데 쓰는 칸 전부가 이 파일에 있다. `observation` 은 관찰 줄 전부다. `n` 은 한 실행 안에서 유일하고 질문 창 · 답 입력의 머리 줄 · 답 기록이 같은 번호를 쓴다 — 정체가 같은 두 질문 가운데 둘째에만 답하면 둘째만 `답함` 이고 그 답 파일의 질문 글은 둘째 질문의 것이다. 글 칸에는 줄 가름 글자 · 제어 글자 · 글 방향을 바꾸는 글자가 그대로 실리지 않는다.
- **AC2** 질문 `state` 는 §2 의 다섯 값 가운데 하나다. 여섯 갈래(답함 · 답 기록 실패 · 답하지 않음 · 범위 모드의 묻지 않음 · 답 기록이 돌지 않은 PR 범위의 묻지 않음 · 상한 넘어 남김)마다 그 값이 나오는 테스트가 있다. 질문 창을 보였는데 답이 하나도 없는 실행의 질문은 `답하지 않음` 이다 — 절차 I5 가 그 실행에서도 `record` 를 돌린다. 결과 줄의 「답하지 않음 k개」 는 `state` 가 `답하지 않음` 인 질문의 수와 같다. 묻지 않은 질문만 있는 실행(범위 모드 · 답 기록이 돌지 않은 PR 범위)의 결과 줄은 「물었다」 로 시작하지 않고 「묻지 않음」 을 쓴다.
- **AC3** 기록에 실패한 답은 `state: 답 기록 실패` 이고 `answer` 에 고른 답, `failure` 에 사유를 싣는다. 고른 답이 「잘못 골랐다」 면 `wrong_choice: true` 다. 직접 쓴 답이면 기록에 성공했든 실패했든 그 원문이 `answer_text` 에 실린다.
- **AC4** `wrong_choice` 는 글자 `true` · `false` 로 나간다.
- **AC5** `status` 는 `ran` · `uncountable` · `skipped` · `failed` 가운데 하나이고 `reason` 은 §1 의 닫힌 부호다. 리뷰 트리를 만들지 못한 실행은 `failed` · `tree-failed` 다. 건너뛴 까닭 다섯과 실패 하나마다 그 부호가 나오는 테스트가 있다.
- **AC6** `status: ran` 이면 `outcome` 이 `questions` · `none` · `no-evidence` · `all-filtered` 가운데 하나이고 `result_line` 이 `render` 가 낸 결과 줄과 글자로 같다. 리뷰어가 낸 `none_reason` 이 있으면 꼴에 실린다.

- **`config` · `filter` · `render` 도 스위치를 읽게 한다** — 셋은 세션 폴더 밖에서는 리뷰 트리와 설정을 읽기만 한다. 막을 것은 밖에 쓰는 것(`record`)과 다른 브랜치 · 네트워크를 읽는 것(`prepare`)이다.
- **상한 새로 두기(7b · 7c · 6d)** — `## 미룬 행 대조` 의 「하지 않음」.

## 결정 기록

- **D1** 에픽 · 로드맵 리뷰의 질문 보관은 부르는 쪽이 한다. qg 는 결과 파일을 완결되게 하고 수명을 명시한다 — 사용자(U2 「그래」).
- **D2** 계약에 닿는 것 · 오류 없이 틀리는 것 · 몇 줄로 멈춤과 죽음을 막는 것 · 전역 스위치 읽기는 한다 — 지휘자가 정해 보였고 사용자가 같은 답으로 승인했다(U2).
- **D3** 만나기 어려운 행은 다시 미루지 않고 「하지 않음 — 이유」 로 닫는다. 실제로 만나면 그때 연다 — 같은 승인(U2).
- **D4** 범위 모드 질문에 답을 기록하는 길은 R3 로 넘긴다 — 같은 승인(U2).
- **D5** 꼴의 값 어휘: `status` · `reason` · `outcome` 은 영문 부호로 닫고, 질문 `state` 는 지금의 한국어 값을 이어 다섯으로 닫는다 — 지휘자 결정(있는 값과 결과 표의 어휘를 잇는다).
- **D6** `wrong_choice` 는 `true` · `false` — 지휘자 결정(YAML 판마다 달리 읽히지 않는 값).
- **D7** 판 올림은 major — 지휘자 결정(있던 칸의 값이 바뀐다. 레포 규칙).
