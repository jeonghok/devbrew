# 스위트 시간 줄이기 · Design

> 바꾼 것이 머지되기까지 전체 스위트 때문에 서 있는 시간을 줄인다. 먼저 스위트가 파일마다 걸린 시간을 남기게 하고 싸고 확실한 것(스위트 안에서 테스트를 또 돌리는 것 · 같은 일을 되풀이하는 느린 테스트)을 고친 뒤, 잰 숫자로 머지 전 대조의 두 바퀴 구조를 고칠지 정한다.

## Context / Why

사용자가 말한 아픈 곳은 「개발 시간이 늦어짐」이다(2026-11-21). 스위트 한 바퀴 자체가 아니라, 구현이 끝난 PR 이 머지 준비까지 스위트 때문에 서 있는 시간이다.

지금 PR 하나는 그 길에서 스위트를 적어도 세 바퀴 돈다 — 구현 담당자가 끝에 한 바퀴, 머지 전 대조(`merge_check.py`)가 기준 사본과 합친 사본에서 한 바퀴씩. 그 사이 기본 브랜치가 움직이면 대조를 다시 돈다. 한 바퀴는 다른 세션의 스위트와 겹쳐 돌 때 75분쯤이다(11월 14일 기록 · RC6). 2026-11-21 00:21 에는 다른 로드맵의 대조 하나가 1시간 47분째 돌고 있었다.

지금 구조는 셋 다 그때의 사고를 막으려고 생겼고 시간을 재고 고른 것은 없다.

| 구조 | 생긴 때 | 이유 |
|---|---|---|
| 대조가 스위트를 두 번 돈다 | 2026-10-18(3892f86d) | 원래 실패하던 테스트와 이 브랜치가 새로 깬 테스트를 이름으로 가른다 |
| 스위트는 한 번에 하나, 잠금 아래 | 2026-10-19(b23cf9ff) | 스위트 둘이 동시에 돌아 거짓 실패가 났다 |
| 테스트 하나가 스위트 안에서 테스트 124개를 또 돈다 | 2026-05-14(29d7ae8d) | 그때는 전체 러너가 없었다(러너는 2026-10-18) |

조사(2026-11-21 · 겹쳐 돌 때의 값)로 본 느린 여덟은 합쳐 약 1,450초다.

| 테스트 | 걸린 시간 | 시간이 드는 곳 |
|---|---|---|
| `plugins/quality-gates/tests/test_codex_backward_compat.sh` | 460–480초 | 스위트가 이미 도는 같은 플러그인 테스트 124개를 다시 돈다. 견줄 원장(`codex-blessed-red.txt`)은 0건이다 |
| `shared/tests/test_docreview_mutations.sh` | 약 340초 | 변이 119개마다 깨끗한 사본의 대조 실행을 다시 돈다(겨냥 케이스는 89개). python 호출 4,222회 |
| `shared/tests/test_docreview_state.sh` | 약 167초 | 케이스마다 python 을 스무 번쯤 새로 띄운다(2,692회) |
| `shared/tests/test_docreview_route.sh` | 약 100초 | 같다(1,427회) |
| `shared/tests/test_docreview_advice.sh` | 약 104초 | 같다(1,234회) |
| `shared/tests/test_copy_of_contract.sh` | 약 112초 | 한 구간이 89% — `shared/*.py` 61개마다 추적 python 파일 310개를 처음부터 다시 파싱한다 |
| `plugins/spec-distill/tests/test_finish_pr_merge.sh` | 약 95초 | 같은 펜스를 bash 와 zsh 에서 138번 돌린다 — 케이스마다 갈리는 단언이라 줄일 실행이 없다 |
| `plugins/spec-distill/tests/test_control_plane.sh` | 약 75초 | 절반 넘게가 「멈추지 않는다」를 재려고 실제로 기다리는 시간이다 |

여덟에 없는 무거운 것도 있다. python 테스트 묶음은 폴더마다 프로세스 하나로 도는데, 97분 기록에서 `plugins/spec-distill/tests` 가 한 번에 146–646초, `plugins/quality-gates/tests` 가 113–123초였다. 인터뷰는 이 묶음을 재지 못했다(OQ23).

숫자는 전부 스위트가 둘씩 겹쳐 돌 때의 부분 기록이다(K13). 겹치지 않은 한 바퀴는 아무도 재지 못했고, 스위트는 파일마다 걸린 시간을 남기지 않는다.

## Goals

- G1. PR 하나가 구현 끝에서 머지 준비까지 스위트에 쓰는 시간이 1시간 30분 안이다 — 사용자가 고른 목표이고(「그래 그렇게 가고 …」 2026-11-21), 재는 잣대는 §2 다.
- G2. 스위트가 대상(셸 파일 · python 폴더와 모듈 · node 파일)마다 걸린 시간과 그 바퀴가 다른 스위트와 겹쳤는지를 남긴다.
- G3. 느린 여덟 가운데 같은 일을 되풀이하는 것을 고친다 — 각 테스트가 지키던 것은 그대로다.
- G4. 잰 숫자로 머지 전 대조의 두 바퀴 구조를 고칠지 정한다 — 넘으면 고친다.

## Non-goals

- 스위트의 테스트를 함께 돌리기와 바뀐 것에 닿는 테스트만 돌리기(S27). 테스트 파일 하나 안에서 케이스를 함께 돌리는 것도 이번에는 하지 않는다.
- 문구 테스트 정리(E4)와 테스트 수 · 줄 수 목표(S17).
- python 테스트 묶음을 고치기 — 이번에는 재기만 한다. 그 폴더는 앞단 로드맵의 진행 중 에픽(F5)이 쥐고 있다.
- 지휘 로드맵의 진행 중 계획이 고치는 느린 넷(`test_human_gate.sh` · `test_human_gate_e2e.sh` · `test_team_status.sh` · `test_roadmap_status.sh`).
- 로드맵마다 따로인 스위트 잠금을 하나로 합치기(스위트가 겹쳐 도는 원인 — 지휘 로드맵의 스크립트다).

## Anti-goals

- 시간을 줄이려고 테스트가 잡던 것을 조용히 잃는다.
- 대조가 원래 실패를 새 실패로, 또는 새 실패를 원래 실패로 낸다.
- 시간 기록이 스위트의 표준 출력 · 종료 코드를 바꾼다 — 대조는 그 출력의 `FAILED …` 줄을 글자로 읽는다(`.devbrew.md` 의 `test_failure_pattern`).
- 재지 못한 것을 0 이나 통과로 적는다.

## Constraints

- 스위트 시간을 가장 먼저 · 무겁게 푼다(C2). 진행 중 에픽과는 시간 쪽부터 따로 간다(C11). 숫자 목표는 시간에만 둔다(C14).
- 손보는 것은 느린 테스트 소수와 두 번 도는 구조다(C9). 느린 테스트는 진행 중 에픽과 안 겹치는 여덟부터다(C16).
- 대조 구조를 고칠 때는 플러그인 스크립트를 고치고 판을 올리며, 새 실패와 원래 실패를 가르는 결과를 지킨다(C17 — 여는 조건은 [인터뷰와 달라진 것](#인터뷰와-달라진-것)).
- 테스트를 고치는 일은 리뷰어 프로필을 고치는 일만큼 조심한다(CLAUDE.md). 고친 테스트마다 고치기 전에 잡던 것을 고친 뒤에도 잡는지 한 번 보인다.
- 셸은 macOS 의 bash 3.2 에서 돈다(연관 배열 없음). python 은 3.9 다.
- 계획 1 은 테스트 폴더와 `tools/` 만 고친다 — 설치본에 실리지 않아 플러그인 판을 올리지 않고, 그 이유를 PR 본문에 적는다. 계획 2 는 `plugins/spec-distill/scripts/merge_check.py` 를 고치므로 spec-distill 판을 올린다.
- 경로 · 테스트 명령 · 기본 브랜치는 박지 않는다 — 러너는 지금처럼 `git rev-parse --show-toplevel` 에서 시작하고, 대조는 해결자가 낸 테스트 명령을 쓴다.

## Approaches

| 길 | 무엇을 하나 | 얻는 것 | 내주는 것 |
|---|---|---|---|
| 1. 구조는 그대로, 한 바퀴만 짧게 | 시간 기록 · 느린 테스트 · 스위트 안의 스위트 | 머지 관문을 안 건드린다 | 세 바퀴가 그대로다 |
| 2. 한 바퀴도 줄이고 대조도 한 바퀴로 | 1 에 더해 대조가 합친 쪽만 돌고 실패한 것만 기준에서 다시 돈다 | 바퀴 수가 셋에서 둘로 준다 | 어림만 보고 머지 관문을 고친다. 「고쳐짐」 목록이 사라진다 |
| 3. 1 을 먼저 머지하고 재 본 뒤 2 를 연다 | PR 둘 — 둘째는 잰 숫자가 목표를 넘을 때만 | 숫자를 보고 관문을 고친다 | 고쳐야 하는 것으로 나오면 그만큼 늦게 시작한다 |

사용자가 길 3 을 골랐다(「권장으로」 2026-11-21). 고른 뒤 지휘 세션이 어림을 한 번 바로잡아 알렸다 — 계획 1 이 덜어 내는 것은 한 바퀴에 10–12분쯤이고(겹쳐 돌 때 75분 → 63–65분), 길 2 까지 가도 겹쳐 돌 때는 약 2시간 10분이다. 길 3 은 그대로다.

## 설계

### §1 시간 기록

`tools/suite/run-all.sh` 와 `tools/suite/run_unittest_dir.py` 가 환경 변수 `SUITE_TIMING_FILE` 을 읽는다. 값이 없으면 지금과 글자까지 같은 동작이다. 값이 있으면 그 경로에 탭으로 가른 줄을 덧붙인다.

| 줄 | 칸 |
|---|---|
| 시작 | `start` · 시작 시각(epoch 초) · 그때 도는 다른 스위트 수 |
| 대상 | 걸린 초 · 종류(`sh` · `py` · `node`) · 대상 경로 |
| python 모듈 | 걸린 초 · `pymod` · `<폴더>/<모듈 파일>` — 그 모듈 테스트들의 합 |
| 끝 | `end` · 끝 시각 · 그때 도는 다른 스위트 수 |

- 줄은 대상이 끝날 때마다 덧붙인다 — 중간에 죽은 바퀴도 그때까지의 줄이 남는다.
- 「다른 스위트 수」 는 이 실행 자신과 그 자식을 뺀, 명령줄에 스위트 러너 파일 이름이 있는 프로세스 무리의 수다.
- 표준 출력과 종료 코드는 값이 있든 없든 같다. 기록 파일을 쓰지 못하면 표준 오류에 한 줄 알리고 바퀴는 끝까지 돈다.
- python 폴더는 지금처럼 폴더마다 프로세스 하나다. 모듈별 시간은 러너 안에서 테스트의 시작 · 끝을 받아 모듈로 합친다(3.9 에는 내장 시간 보고가 없다).
- 기록을 읽는 도구는 만들지 않는다 — 가장 느린 것 스물은 정렬 한 줄로 본다.

대조(`merge_check.py`)는 테스트 명령을 환경을 물려 돌리므로, 변수를 준 채 대조를 부르면 합친 사본의 바퀴도 같은 파일에 남는다.

### §2 기준선과 판단 규칙

계획 1 안에서 두 바퀴를 잰다 — 둘 다 공유 스위트 잠금 아래다.

- 「앞」 바퀴: 시간 기록만 들어간 커밋에서. 느린 테스트를 고치기 전의 숫자이고, python 묶음과 한 바퀴 전체의 첫 실측이다(OQ23).
- 「뒤」 바퀴: 구현 끝의 전체 스위트.

구현 담당자의 마지막 보고는 바퀴마다 합계 · 종류별 합 · 가장 느린 스물 · 시작과 끝의 다른 스위트 수를 싣는다. 지휘자는 머지 전 대조를 변수를 준 채 돌려 합친 사본의 바퀴를 하나 더 얻고, 세 바퀴의 숫자를 이 문서의 `## 기준선` 절에 적는다.

판단은 「뒤」 쪽 바퀴(구현 끝 · 합친 사본) 가운데 시작과 끝의 다른 스위트 수가 모두 0 인 바퀴의 합계 N 으로 한다.

| 잰 결과 | 다음 |
|---|---|
| 3 × N 이 90분 이하 | 계획 2 를 열지 않는다. 대조 구조는 그대로다 |
| 3 × N 이 90분을 넘는다 | 계획 2 를 연다(§4) — 다시 묻지 않는다 |
| 겹치지 않은 바퀴를 얻지 못했다 | 그 사실과 겹친 숫자를 사용자에게 보이고 계획 2 를 연다 — 인터뷰가 정한 쪽(S22)으로 떨어진다 |
| 계획 2 뒤에도 2 × N 이 90분을 넘는다 | 미뤄 둔 길(함께 돌리기 · 닿는 테스트만 · [미룸](#미룸)의 행)을 사용자에게 묻는다(S27) |

어느 쪽이든 지휘자는 숫자를 사용자에게 보인다. 사용자가 목표 숫자를 바꾸면 그 말을 따른다. 계획 2 를 열 때는 로드맵 블록에 둘째 브랜치를 더하는 로드맵 수정을 재분해 절차로 올린다.

### §3 느린 테스트

**스위트 안의 스위트 — `test_codex_backward_compat.sh` 의 셋째 확인.** 지금은 같은 폴더의 테스트 가운데 제외 여섯을 뺀 전부를 다시 돌려, 실패한 것이 원장에 지문까지 맞게 등재돼 있는지와 등재됐는데 통과하는 것이 없는지를 본다. 고친 뒤에는 원장에 등재된 테스트만 다시 돌린다.

- 등재된 테스트: 지금과 같은 두 판정(지문 대조 · 등재됐는데 통과하면 실패)을 받는다.
- 등재되지 않은 테스트의 실패: 전체 러너가 그 테스트를 직접 돌려 자기 `FAILED` 줄로 낸다. python 테스트 17개도 러너가 찾는 꼴이다(전부 `unittest.TestCase`).
- 등재가 0건이면 다른 테스트를 하나도 띄우지 않고 「등재 0건」 을 한 줄로 낸다.
- 다시 돌리지 않게 되어 뜻을 잃는 것(제외 목록 · 그 크기 핀 · 제외 항목 알람 · 실행 수 바닥)은 걷고, 그것을 설명하던 주석도 함께 걷는다. 첫째 · 둘째 확인은 그대로다.
- 잃는 것: 이 파일만 따로 돌려서는 그 폴더의 테스트가 전부 통과하는지 알 수 없다 — 그것은 전체 러너의 일이 된다.

**`test_copy_of_contract.sh` — 임포트 색인을 한 번 만든다.** 추적 python 파일을 한 번만 파싱해 파일마다 임포트한 최상위 이름 집합을 만들고, `shared/*.py` 모듈마다의 소비자와 임포트로만 쓰이는 정본의 소비자를 그 색인에서 답한다. 임포트를 알아보는 술어(`import a.b` 의 첫 성분 · `from m import` · `from .m import` · `from . import m`)와 자기 · 사본 제외는 같은 뜻으로 둔다. 소비자를 실제로 실행해 보는 프로브와 코퍼스 도출은 건드리지 않는다 — 이 락의 초록에 `test_no_new_duplication.sh` 가 이빨을 맡기고 있고, 두 락의 코퍼스 도출이 같아야 그 맡김이 선다.

**`test_docreview_mutations.sh` — 깨끗한 사본의 대조 실행을 케이스마다 한 번만.** 같은 케이스를 겨냥한 변이가 여럿이면 첫 실행의 결과를 케이스 이름으로 된 파일에 두고 다시 쓴다(연관 배열 없이). 「깨끗한 사본에서 초록이어야 그 변이를 잰 것으로 친다」는 판정은 그대로다. 변이 사본의 실행은 줄이지 않는다.

**`test_docreview_state.sh` · `test_docreview_route.sh` · `test_docreview_advice.sh` — 바이트코드 캐시를 그 실행의 임시 폴더에.** 세 테스트는 스크립트를 변이하지 않는다. 케이스 모음이 켜 둔 「바이트코드를 쓰지 않는다」 를 세 테스트에서만 풀고 캐시 자리를 그 실행의 임시 폴더로 준다(`PYTHONPYCACHEPREFIX`) — 레포 안에는 캐시가 생기지 않고 실행이 끝나면 사라진다. 변이 매트릭스는 지금처럼 바이트코드를 쓰지 않는다(같은 길이의 변이가 낡은 캐시에 가려지는 것을 막는 장치다). 이 변경은 재 보고 넣는다 — 같은 조건에서 앞뒤로 한 번씩 돌려 세 테스트의 합계가 10% 이상 줄 때만 넣고, 아니면 넣지 않고 잰 숫자를 보고에 적는다.

**손대지 않는 둘.** `test_finish_pr_merge.sh` 는 줄일 실행이 없고 남는 길이 두 셸을 함께 돌리기뿐이다. `test_control_plane.sh` 는 기다리는 상한을 줄이면 부하 아래에서 시간 문턱이 흔들린다(RC19 의 사고와 같은 꼴). 둘 다 이번에는 그대로 두고 [미룸](#미룸)에 올린다.

계획 1 이 덜어 내는 것의 어림(겹쳐 돌 때): 스위트 안의 스위트 약 460초 · 임포트 색인 약 50초 · 변이 매트릭스 약 40초 · 바이트코드 캐시 0–70초 — 합쳐 한 바퀴에 10–12분.

### §4 대조를 한 바퀴로 — 조건부(계획 2)

§2 의 규칙이 열 때만 한다. 여는 계획의 첫 과제가 아래 자리를 그때의 코드에서 다시 확인한다.

- `merge_check.py` 의 테스트 명령 경로(`compare_command`)가 합친 사본을 먼저 돈다.
- 합친 사본이 종료 코드 0 이고 실패 이름이 없으면 기준 사본에서 테스트 명령을 돌리지 않는다. 판정은 「새 실패 없음」 이고 「기준 사본은 돌리지 않았다」 를 알림 줄로 낸다.
- 합친 사본에 실패 이름이 있으면, 그 이름 목록을 파일로 써서 환경 변수(`SUITE_ONLY_FAILED_FILE`)로 건넨 채 기준 사본에서 같은 테스트 명령을 돈다. 목록을 아는 명령은 그 실패가 속한 대상만 돌고, 모르는 명령은 전부 돈다 — 어느 쪽이든 「합친 쪽 실패 가운데 기준에도 있는 것」 이 가려지므로 새 실패와 원래 실패의 판정은 같다.
- 실패했는데 이름을 뽑지 못하면 지금처럼 기준 사본을 전부 돈다.
- 「기본 브랜치에만 있는 실패(고쳐짐)」 줄은 「재지 않았다」 로 낸다 — 0개로 내지 않는다. 판정과 종료 코드는 그 줄을 쓰지 않는다(지금도 그렇다).
- `tools/suite/run-all.sh` 가 그 변수를 읽어 목록에 나온 대상(셸 파일 · python 폴더 · node 파일)만 돈다. 이름의 꼴(`<대상>: <이름>`)은 러너 자신이 낸 것이라 러너가 가른다.
- 테스트 명령이 없는 경로(러너 탐지 · `compare_detected`)는 건드리지 않는다.
- 새 설정 키를 만들지 않는다 — 닫힌 설정 키 집합과 그 해결자는 지휘 로드맵의 에픽이 쥐고 있다.
- 지휘 절차서의 대조 설명(「양방향으로 대조한다」)이 새 동작과 어긋난다. 그 파일은 지휘 로드맵의 에픽이 쥐고 있으므로, 계획 2 를 여는 로드맵 수정에서 그 한 자리의 예약을 지휘 로드맵과 맞춘다(§5).

### §5 알림

- 계획 1 은 지휘 로드맵의 예약 파일을 건드리지 않는다. PR 본문에 「지휘 로드맵의 느린 넷은 건드리지 않았다」 를 한 줄로 적는다.
- 계획 2 를 열면 PR 본문 `## 지휘 로드맵에 알림` 절에 바뀐 구조(합친 쪽 먼저 · 실패만 기준에서 다시 · 「고쳐짐」 은 재지 않음 · 변수 이름)를 적고, 지휘자가 그 글을 지휘 로드맵의 받는 에픽(머지 전 확인을 담당 세션으로 옮기는 대기 중 에픽 — RC45)에 알린다(C17).

## Acceptance Criteria

계획 1 몫은 AC1–AC13, 계획 2 몫은 AC14–AC20 이다.

- AC1. `SUITE_TIMING_FILE` 없이 돌린 스위트 러너의 표준 출력과 종료 코드가 고치기 전과 같다 — 작은 임시 레포에서 전부 통과하는 경우와 실패가 있는 경우 둘 다.
- AC2. 변수를 주면 기록 파일에 시작 줄 하나 · 대상마다 한 줄 · 끝 줄 하나가 남고, 대상 줄 수가 돌린 셸 테스트 수 + python 폴더 수 + node 파일 수와 같다. 표준 출력과 종료 코드는 AC1 과 같다.
- AC3. 다른 스위트 러너가 도는 중에 시작하면 시작 줄의 수가 1 이상이고, 없으면 0 이다. 자기 자신과 자기 자식은 세지 않는다.
- AC4. 기록 파일을 쓸 수 없으면 표준 오류에 알림 한 줄이 나오고, `FAILED` 줄과 종료 코드는 그대로다.
- AC5. python 폴더를 돌리면 모듈마다 합친 시간 줄(`pymod`)이 남고, 그 러너의 표준 출력은 변수가 없을 때와 같다.
- AC6. `test_codex_backward_compat.sh` 는 원장에 등재된 테스트만 다시 돌린다 — 등재 0건이면 다른 테스트 파일을 하나도 띄우지 않는다. 통과하는 테스트를 등재한 사본에서는 실패하고, 등재한 실패 테스트의 지문이 다르면 실패하고, 같으면 통과한다.
- AC7. 그 파일에서 걷어 낸 것(제외 목록 · 크기 핀 · 알람 · 실행 수 바닥)을 가리키는 주석과 문서 인용이 `docs/archive/` 밖에 남지 않는다.
- AC8. `test_copy_of_contract.sh` 의 단언 수와 축별 계측이 고치기 전과 같다. 모듈마다의 소비자 집합이 고치기 전 방식의 결과와 같다는 대조를 한 번 해 보고에 싣는다. 임포트 술어의 한 갈래를 빼는 변이를 넣으면 실패한다.
- AC9. `test_docreview_mutations.sh` 의 변이 수 · 잡힌 변이 수 · 측정 불가 수 · 단언 수가 고치기 전과 같다. 깨끗한 사본의 대조 실행은 케이스마다 한 번이다. 깨끗한 사본에서 빨간 케이스를 겨냥한 변이는 지금처럼 「측정 불가」 로 나온다.
- AC10. 바이트코드 캐시 변경은 세 테스트의 합계가 같은 조건의 앞뒤 실행에서 10% 이상 줄 때만 들어간다 — 잰 두 숫자가 보고에 있다. 들어갔으면 세 테스트를 돌린 뒤 레포 안에 새 `__pycache__` 가 없고 단언 수가 같다. 변이 매트릭스의 설정은 그대로다.
- AC11. `test_finish_pr_merge.sh` 와 `test_control_plane.sh` 는 한 글자도 바뀌지 않는다.
- AC12. 「앞」 · 「뒤」 바퀴의 합계 · 종류별 합 · 가장 느린 스물 · 시작과 끝의 다른 스위트 수가 구현 담당자의 마지막 보고에 실린다.
- AC13. 전체 스위트의 실패 이름 집합이 「앞」 바퀴와 「뒤」 바퀴에서 같다.
- AC14. 합친 사본이 전부 통과하면 대조가 기준 사본에서 테스트 명령을 돌리지 않고, 판정 「새 실패 없음」 · 종료 코드 0 · 「기준 사본은 돌리지 않았다」 알림을 낸다.
- AC15. 합친 사본에 원래 실패 하나와 새 실패 하나가 있으면, 대조가 기준 사본에서 실패 목록을 건넨 테스트 명령을 돌려 둘을 지금과 같은 이름 · 같은 줄(새 실패 · 양쪽 다 실패) · 같은 종료 코드로 낸다.
- AC16. 실패 목록을 모르는(전부 도는) 테스트 명령에서도 AC15 의 판정이 같다.
- AC17. 합친 사본이 실패했는데 이름을 뽑지 못하면 지금처럼 기준 사본을 전부 돈다.
- AC18. 기준 사본을 전부 돌지 않은 대조는 「기본 브랜치에만 있는 실패」 를 「재지 않았다」 로 낸다.
- AC19. 스위트 러너가 건네받은 실패 목록의 대상만 돈다 — 셸 파일 · python 폴더 · node 파일 각각. 목록이 없으면 전부 돈다.
- AC20. spec-distill 의 판과 CHANGELOG 가 올라가고, 지휘 절차서의 대조 설명이 새 동작과 맞다.

## Verification Plan

- 새 동작(§1 · §4)은 임시 레포를 만들어 실제 러너 · 실제 대조 스크립트를 돌리는 테스트로 본다.
- 고친 테스트 넷(스위트 안의 스위트 · 임포트 색인 · 변이 매트릭스 · 바이트코드 캐시)은 고치기 전후의 단언 수 · 계측을 견주고, 테스트마다 고치기 전에 잡던 것 하나를 고친 뒤에도 잡는지 사본에 변이를 넣어 보인다(AC6 · AC8 · AC9).
- 과제 경계마다 바꾼 파일을 코퍼스로 읽는 락을 돈다. 전체 스위트는 공유 잠금 아래 「앞」 · 「뒤」 두 번이고 실패 이름 집합이 같아야 한다(AC13).
- 지휘자의 머지 전 대조는 기록 변수를 준 채 돈다.

## Rejected Alternatives

- **길 1 만 · 길 2 를 바로** — [Approaches](#approaches). 사용자가 길 3 을 골랐다.
- **기준 사본의 결과를 기본 브랜치 커밋마다 저장해 다시 쓰기** — 기본 브랜치가 머지마다 움직여 로드맵 셋이 함께 가는 지금은 적중이 드물고, 흔들리는 테스트의 한 번 결과가 굳는다.
- **기준 사본과 합친 사본을 동시에 돌리기** — 스위트 둘의 동시 실행이 거짓 실패를 낸 사고 때문에 잠금이 생겼다.
- **구현 담당자의 마지막 바퀴를 대조의 합친 쪽으로 쓰기** — 다른 트리(브랜치 대 합친 사본)이고, 하위가 본 실패는 지휘자의 잠긴 대조만 판정한다는 규칙과 어긋난다.
- **스위트 안의 스위트를 파일째 지우기** — 첫째 · 둘째 확인과 원장 판정은 지키는 것이 있다.
- **문서 리뷰 엔진 케이스의 값 읽기를 한 프로세스로 묶기** — 케이스 모음 5,870줄을 고쳐 쓰는 일이고 얻는 것은 많아야 30% 안팎이다. 테스트를 잘못 고칠 위험이 더 크다.
- **변이를 함께 돌리기 · 두 셸을 함께 돌리기 · 기다리는 상한 줄이기** — 앞의 둘은 함께 돌리기(S27)이고 셋째는 시간 문턱을 약하게 한다.
- **시간을 표준 출력에 싣기** — 대조와 레포 설정이 그 출력을 글자로 읽는다.
- **기록을 읽는 보고 스크립트 만들기** — 정렬 한 줄이면 된다.
