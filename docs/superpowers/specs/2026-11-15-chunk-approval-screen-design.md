# 덩어리 승인 화면 · Design

> seed 리뷰에서 저자가 고친 곳을 사용자가 승인하는 화면을 읽기 쉽게 고친다 — 로드맵 에픽 F2.

## Context / Why

request-framing 은 seed 리뷰 라운드 사이에 저자(모델)가 seed 를 고친 곳을 전부 사용자 앞에 놓고 「그대로 둔다 / 되돌린다」 를 받는다(`### 저자 편집 공시`). seed 는 헤딩이 없어 리뷰 엔진의 얼림 검사가 편집을 막지 못하므로, 이 화면이 저자 편집을 사람이 보는 유일한 자리다.

사용자는 이 화면을 쓴 직후 「이거 덩어리 승인하는과정 내가 보기 어려우니까 개선하자」 라고 했고(S1), 무엇이 어려웠는지 묻는 질문에서 넷을 골랐다(S21): 「문단 전체가 두 번 나온다 (권장), 어느 지적 때문인지 안 보인다 (권장), 덩어리마다 질문이 따로다, 추천이 없다」.

지금 그렇게 되는 까닭:

- 덩어리는 `seed_edit_diff.py` 가 줄 단위로 비교해 만든다. seed 는 문단 하나가 한 줄이라, 문장 하나만 바뀌어도 문단 전체가 `-` 줄과 `+` 줄로 두 번 나온다.
- 덩어리와 리뷰 지적을 잇는 기록이 없다.
- skill 글이 「덩어리마다 질문 하나」 · 「추천을 달지 않는다」 · 「덩어리 본문은 줄임 없이 싣는다」 를 규칙으로 적고, 테스트가 그 글자를 잠근다.

## Goals

- G1. 화면이 바뀐 문장만 보인다 — 뺀 문장 · 더한 문장 · 그대로인 문장 수.
- G2. 덩어리마다 고친 이유(어느 지적 때문인지, 또는 대응하는 지적이 없다는 사실)가 보인다.
- G3. 덩어리 처분을 한 질문으로 묶는다.
- G4. 사용자가 고치기로 처분한 지적에 대응하는 덩어리에만 「그대로 둔다」 를 권한다.

## Non-goals

- 리뷰 엔진의 판정 규칙 · 처분 흐름(라운드 게이트 · `fix` 의 적용 질문)을 바꾸지 않는다.
- 되돌리는 단위를 바꾸지 않는다 — 지금처럼 덩어리(줄 범위)째 되돌린다.
- 기준 사본의 수명(공시 → 되돌리기 → 기록 → 교체)과 `seed_edit_diff.py` 의 `init` · `revert` · `accept` 계약을 바꾸지 않는다.
- 기준 사본이 없을 때의 길(seed 전문을 보이고 「이대로 둔다 / 멈춘다」)을 바꾸지 않는다.
- brief · 설계문서 리뷰의 화면은 다루지 않는다 — 그쪽은 엔진의 얼림 검사가 편집을 잰다.

## Anti-goals

- 바뀐 문장이 화면에서 하나라도 빠진다 — 읽기 쉬워졌어도 공시가 아니게 된다.
- 권장이 붙은 덩어리가 보이지 않거나 자동으로 통과한다.
- 저자가 스스로 고친 곳(대응하는 지적 없음)에 권장이 붙는다.
- 사용자가 아무것도 고르지 않았을 때 저자 편집이 통과한다.

## Constraints

- C9(사용자) — 덩어리 승인 과정이 보기 어려우니 개선한다.
- D27(사용자) — 고칠 것은 넷이다(위 S21).
- 추천 표시 규칙(CLAUDE.md 가 가리키는 정본 `shared/style/plain-language.md` 와 전수 검사 표 `shared/tests/fixtures/ask-sites.tsv`) — 추천이 있으면 첫 자리 · 라벨 끝 「(권장)」, 없으면 표시 없음. 이 자리는 지금 그 표에 「비움」 으로 올라 있다.
- Law 2 — 저자가 자기 편집의 승인 여부를 가르지 않는다. 권장의 근거는 저자의 판단이 아니라 사용자가 이미 한 처분이어야 한다.
- 질문 도구의 한계 — 질문 하나에 선택지 2–4개, 호출 하나에 질문 4개.
- 사용자 문구 · 저자 문구는 셸 인자에 직접 쓰지 않는다(지금 skill 의 규칙 — 파일로 넘긴다).

## Approaches

| 길 | 무엇 | 얻는 것 · 잃는 것 | 결과 |
|---|---|---|---|
| A. 스크립트가 문장을 가른다 | 덩어리 안에서 문장 단위 비교를 스크립트가 하고, 화면 글 전체를 스크립트가 낸다 | 바뀐 문장이 빠지지 않음을 테스트로 잠근다. 스크립트 · 테스트를 고쳐야 한다 | 고름 |
| B. 모델이 화면을 추린다 | 스크립트는 그대로, skill 글에 「달라진 문장만 보여라」 | 가장 싸다. 저자가 자기 편집에서 무엇을 보일지 고르게 되고, 문장이 빠져도 잡을 장치가 없다 | 뺌 |
| C. 덩어리 자체를 문장 단위로 | 문장 하나씩 되돌린다 | 가장 정밀하다. 되돌리기 · 기준 사본 계약과 테스트를 다시 짜야 하고 문장만 되돌린 문단이 어색하게 남는다. 에픽 크기를 넘는다 | 뺌 |

사용자는 방법을 따로 고르지 않았다 — 추천 질문에 「추천으로 가자」 라고 답했고, 저자는 그 말을 추천 방식 「가」(아래 설계 3)를 고른 것으로 읽었다. 방법 A 는 저자의 판단이다.

## 설계

### 1. 화면 조립 — 새 모듈 `seed_edit_screen.py`

`seed_edit_diff.py hunks` 는 지금처럼 덩어리(JSON)를 내고 공시를 기록한다. 그 JSON 을 받아 사람이 볼 화면을 조립하는 일은 새 모듈이 맡는다 — 입력 셋, 출력 하나.

- 입력: ① `hunks` 가 쓴 덩어리 JSON ② 저자가 쓴 이유 파일(설계 2) ③ 리뷰 원장 폴더(읽기만).
- 출력(JSON): `text`(게이트 앞 글에 그대로 실을 화면 글) · `hunks[]`(덩어리마다 `id` · `reason` · `recommend` · `removed_sentences` · `added_sentences` · `kept`) · `questions[]`(설계 4 의 질문 묶음 — 질문마다 선택지 라벨을 순서대로).
- 덩어리 JSON 을 읽기만 한다 — 공시 기록(`.shown`) · seed · 기준 사본을 건드리지 않는다.

문장 가르기:

- 덩어리의 `removed` 줄들과 `added` 줄들을 각각 문장으로 나눈다. 나누는 규칙은 `seed_provenance.py` 의 문장 나누기(`SENT_SPLIT_RE` · `_sentence_units`)를 그대로 쓴다 — «(사용자 확인)» 표시가 앞 문장에 붙는 처리까지 같다.
- 두 문장 목록을 순서대로 비교해 한쪽에만 있는 문장을 「뺀 문장」 · 「더한 문장」 으로, 양쪽에 있는 문장은 수만 센다.
- 문장으로 가른 결과가 양쪽이 같은데 줄은 다르면(공백만 바뀜 · 문장 부호 없는 줄 등) 그 덩어리는 줄 전체를 지금 꼴(`-` · `+`)로 보이고 「문장으로 가르지 못함 — 줄 전체를 보인다」 를 붙인다.
- 불변식: 덩어리마다 「뺀 문장 + 그대로인 문장」 이 기준 쪽 문장 목록과, 「더한 문장 + 그대로인 문장」 이 지금 쪽 문장 목록과 같다. 모듈이 조립 뒤 스스로 확인하고, 어긋나면 그 덩어리를 줄 전체 꼴로 떨어뜨린다.

화면 글의 꼴(예):

```
저자 편집 3곳 — 달라진 문장만 보입니다

1) 기준 4행 → 현재 4행 · 2문장 바뀜(그대로 5문장)
   고친 이유(저자가 댐): 지적 1677e331#r3.1 — 사용자가 「적용」 으로 처분
   뺀 문장: …
   더한 문장: …
2) 기준 7행 앞(없음) → 현재 7행 · 1문장 더함
   고친 이유(저자가 댐): 대응하는 지적 없음 — 저자가 스스로 고침
   더한 문장: …
```

### 2. 고친 이유 — 저자가 대고, 기계는 처분만 확인한다

- 저자는 `hunks` 출력을 본 뒤 덩어리마다 이유를 이유 파일(원장 자리 `$STATE_DIR` 안, Write 도구로)에 적는다 — 줄마다 `<덩어리 번호><탭><지적 id 들(쉼표) | 없음>`. 한 덩어리에 지적과 스스로 고친 것이 섞였으면 `없음` 을 함께 적는다.
- 이유 파일에 없는 덩어리는 「대응하는 지적 없음」 으로 다룬다. 이유 파일이 아예 없어도 화면은 나온다 — 전부 「없음」 이다.
- 기계가 확인하는 것은 **그 지적에 사용자의 고치는 쪽 처분이 있는가** 뿐이다:
  - 확인됨 — 원장의 `fix` 항목이고 사용자가 「적용」 을 골랐다(원장 상태 `intent_passed` · `applied`), 또는 `decide` 항목이고 사용자가 채택했다.
  - 확인 안 됨 — 원장에 없는 id · 사용자가 「적용하지 않음」 · 거부한 항목 · 아직 처분 전인 항목. 화면에 「저자가 댄 지적 <id> 은 원장에서 확인되지 않는다」 로 보인다.
  - 사용자가 답한 열린 질문(`ask` — audit 의 `답` 줄)에 따른 편집은 이유로 보이되 확인됨으로 치지 않는다 — 답을 어떻게 seed 에 옮길지는 저자의 풀이다.
- 지적과 그 편집이 실제로 맞는지는 기계가 가리지 못한다. 화면은 이유 줄에 늘 「저자가 댐」 을 붙인다.
- 원장의 어느 칸이 「사용자가 적용 · 채택」 을 뜻하는지는 계획의 첫 과제(다시 확인)가 지금 코드에서 못박는다 — 원장을 읽는 길은 `docreview_state.py` 의 읽기 함수를 그대로 쓰고 원장에 쓰지 않는다.

### 3. 권장 — 확인된 덩어리에만

- 덩어리가 댄 지적이 하나 이상이고 **전부** 확인됨이면 그 덩어리의 「그대로 둔다」 에 「(권장)」 을 단다. `없음` 이 섞였거나 하나라도 확인 안 됨이면 달지 않는다.
- 권장의 근거 문장은 질문 위 글(화면 글)의 이유 줄이다 — 선택지 설명에 저자의 평가를 더하지 않는다.
- 기준 사본이 없을 때의 질문(「이대로 둔다 / 멈춘다」)은 지금처럼 추천이 없다.

### 4. 질문 — 한 묶음, 고른 것만 승인

- 덩어리가 둘 이상이면 여러 개 고르기 질문으로 묻는다: 「그대로 둘 곳을 고르세요. 고르지 않은 곳은 되돌립니다.」 선택지는 덩어리마다 하나(「<k>번 그대로 둔다」, 권장이면 끝에 「(권장)」), 권장이 붙은 것을 앞에 둔다. 선택지 설명은 그 덩어리의 한 줄 요약(몇 문장 바뀜 · 이유 줄)이다.
- 덩어리가 하나면 하나 고르기 질문이다: 「그대로 둔다 / 되돌린다」. 확인된 덩어리면 「그대로 둔다 (권장)」 을 첫 자리에 둔다.
- 덩어리가 넷을 넘으면 넷씩 나눠 질문을 여럿 싣는다(한 호출에 질문 넷까지, 넘치면 다음 호출). 선택지가 하나만 남는 질문은 만들지 않는다 — 풀이 확인 질문과 같은 나누기 규칙(예: 5 → 3+2). 나뉜 질문 전부에 답해야 처분이 끝난다.
- 답은 라벨 끝의 「(권장)」 꼬리를 뗀 이름으로 읽는다. 고른 덩어리는 「그대로 둔다」, 고르지 않은 덩어리는 「되돌린다」 로 처분 펜스의 `PAIRS` 에 옮긴다 — 처분 펜스(되돌리기 → 기록 → 기준 사본 교체)는 그대로다.
- 덩어리의 사용자 문구 파일(`said-hunk-<k>.txt`)에는 고른 덩어리면 사용자가 고른 라벨을, 고르지 않은 덩어리면 정해진 글자 「고르지 않음」 을 적는다 — audit `## 2` 의 `— 고르지 않음` 과 같은 표지이고 사용자의 말로 꾸미지 않는다. 「기타」 로 적은 말이 있으면 그 말을 그대로 적고, 그 말이 어느 덩어리를 어떻게 하라는 것인지 분명하지 않으면 처분하지 않고 다시 묻는다.
- 화면 글은 질문 위 글에 한 번 싣는다. 질문 본문에는 결정 한 줄만 둔다 — 지금의 「덩어리 본문을 질문 텍스트에 줄임 없이 싣는다」 를 대신한다.

### 5. skill 글과 락

- `### 저자 편집 공시` 의 공시 펜스는 `hunks` 뒤에 화면 조립을 한 번 더 부르고 그 `text` 를 낸다. 화면 조립이 실패하면(종료 코드 0 아님) 지금 꼴(덩어리의 `render`)을 그대로 내고 「화면 조립 실패 — 줄 전체를 보인다」 를 알린다 — 공시는 막히지 않는다.
- 규칙 문장 셋을 바꾼다: 「덩어리마다 질문 하나」 → 설계 4 · 「추천을 달지 않는다」 → 설계 3 · 「줄임 없이 싣는다」 → 「바뀐 문장은 하나도 빼지 않는다」. 새 문장은 무엇을 하는지만 적고 이력을 적지 않는다.
- 그 글자를 잠근 테스트(`test_framing_review_contract.sh`)와 추천 전수 검사 표의 이 자리 행(`ask-sites.tsv` — 「비움」)을 새 규칙에 맞춘다.

## 있는 것 검토

- `plugins/spec-distill/scripts/seed_edit_diff.py` — 덩어리 계산 · 공시 기록 · 되돌리기 · 기준 사본 교체. 그대로 쓴다. `compute_hunks` 의 `removed` · `added` 가 화면 조립의 입력이다.
- `plugins/spec-distill/scripts/seed_provenance.py` 의 `SENT_SPLIT_RE` · `_sentence_units` · `norm` — seed 문장 나누기가 이미 있다. 새로 짜지 않고 가져다 쓴다. 이 파일은 고치지 않는다.
- `plugins/spec-distill/scripts/docreview_state.py` 의 `load_state` — 원장 읽기. 읽기만 한다.
- `plugins/spec-distill/skills/request-framing/SKILL.md` `### 확인 질문` — 「고른 것만 확인」 · 넷씩 나누기 · 하나뿐이면 단일 선택. 설계 4 가 같은 규칙을 따른다.
- `plugins/spec-distill/scripts/seed_review_log.py log --kind 편집` — 처분 기록. 그대로 쓴다.
- 묶음의 근거 RC22(덩어리 승인 규칙 넷이 skill 본문에 있고 둘에는 이유가 함께 적혀 있다)는 지금도 맞다 — 기본 브랜치 `b2a409ab` 의 skill 본문 933–935행에서 확인했다. 넷째 규칙(공시마다 번호 다시)은 바꾸지 않는다.
- 레포 밖 후보: 없음 — 문장 비교는 표준 라이브러리 `difflib` 로 한다(이미 쓰고 있다).

## 상류 · 하류 연계

- 받는 곳: 리뷰 원장(엔진이 쓴다 — 읽기만) · `hunks` 의 덩어리 JSON · 저자의 이유 파일.

- 같은 상태를 읽는 표면: 확정 게이트 직전 검사 2 가 같은 공시 절차를 다시 쓴다 — 같은 화면 · 같은 질문 꼴이 된다.

- 옆 로드맵(지휘 재설계)의 경로 예약과 겹치는 것: `plugins/spec-distill/CHANGELOG.md` 와 설계문서 폴더. 판 번호와 CHANGELOG 는 먼저 머지되는 쪽이 낮은 번호를 쓴다.
- 레포 전용 값: 원장 자리 · 설계문서 폴더 · 테스트 명령은 박지 않는다 — skill 의 `## 상태` 블록과 해결자(`repo_defaults.py`)가 낸 값을 받는다.

## Acceptance Criteria

- AC1. 한 문단(한 줄)에서 문장 하나만 바뀐 seed 로 화면을 만들면, 화면 글에 뺀 문장 하나와 더한 문장 하나만 나오고 그대로인 문장은 수로만 나온다.
- AC2. 덩어리마다 「뺀 문장 + 그대로인 문장」 이 기준 쪽 문장 목록과, 「더한 문장 + 그대로인 문장」 이 지금 쪽 문장 목록과 같다 — 넣기 · 지우기 · 바꾸기 · 여러 줄 덩어리 · «(사용자 확인)» 이 붙은 문장에서.
- AC3. 문장으로 가른 결과가 같은데 줄이 다른 덩어리(공백만 바뀜)는 줄 전체가 보이고 「문장으로 가르지 못함」 이 붙는다.
- AC4. 이유 파일이 댄 지적이 원장에서 사용자가 적용을 고른 `fix` 면 그 덩어리의 `recommend` 가 참이고 화면에 그 지적과 처분이 보인다.
- AC5. 이유 파일에 없는 덩어리 · `없음` 이 섞인 덩어리 · 원장에 없는 id · 사용자가 적용하지 않기로 한 지적 · 처분 전인 지적 · `ask` 의 답에 따른 편집은 `recommend` 가 거짓이다. 원장에서 확인되지 않은 id 는 화면에 그렇다고 보인다.
- AC6. 이유 파일이 없거나 원장을 읽지 못해도 화면이 나온다 — 전부 권장 없음이고, 원장을 읽지 못한 사실이 화면에 보인다.
- AC7. `questions[]` — 덩어리 하나면 단일 선택(「그대로 둔다」 · 「되돌린다」), 둘 이상이면 여러 개 고르기이고 권장이 붙은 선택지가 앞에 온다. 다섯이면 3+2 로 나뉘고 선택지 하나짜리 질문은 없다.
- AC8. 화면 조립은 seed · 기준 사본 · 공시 기록(`.shown`) · 원장을 바꾸지 않는다.
- AC9. skill 본문 `### 저자 편집 공시` 가 화면 조립을 부르고, 고르지 않은 덩어리를 「되돌린다」 로 옮기며, 「고르지 않음」 표지를 정하고, 화면 조립 실패 때 줄 전체 꼴로 떨어진다고 적는다. 옛 규칙 문장 셋(「덩어리마다 질문 하나」 · 「추천을 달지 않는다 — 어느 덩어리가」 · 「줄이면 공시가 아니다」)은 본문에 없다.
- AC10. 처분 펜스가 여러 개 고르기 답에서 온 `PAIRS`(고른 것 「그대로 둔다」 · 고르지 않은 것 「되돌린다」)로 되돌리기 · 편집 줄 기록 · 기준 사본 교체를 지금과 같이 한다.
- AC11. 추천 전수 검사(`test_ask_recommendation.sh`)와 skill 계약 테스트(`test_framing_review_contract.sh`)가 새 규칙으로 통과하고, 새 규칙 문장을 지우면 실패한다.
- AC12. spec-distill 의 판 번호가 오르고 CHANGELOG 에 이 변경이 적힌다.

## Rejected Alternatives

- 모델이 화면을 추린다(B) — 저자가 공시 내용을 고르게 된다.
- 덩어리를 문장 단위로(C) — 되돌리기 계약을 다시 짜야 하고 에픽 크기를 넘는다.
- 모든 덩어리에 권장 — 저자가 자기 편집을 스스로 승인하는 꼴이다(Law 2).
- 권장 없이 사실만 보인다 — 사용자가 고른 「추천이 없다」 가 남는다.
- 「되돌릴 곳을 고르세요」(고르지 않으면 그대로) — 아무것도 고르지 않으면 저자 편집이 통과한다.
- 덩어리마다 질문을 두고 넷씩 한 호출에 묶기 — 질문 수가 그대로다.
- 이유를 기계가 추론하기(편집 위치와 지적의 인용 구절 대조) — seed 에는 고정된 자리가 없어 맞춘다는 보장이 없고, 틀린 연결에 권장이 붙는다.

## 남는 한계

- 「이 편집이 그 지적 때문」 이라는 연결은 저자의 말이다. 저자가 다른 편집을 확인된 지적 밑에 대면 권장이 붙는다 — 사용자는 화면의 바뀐 문장과 지적을 보고 가른다. 잔여는 리뷰 엔진의 탐지 리뷰어가 다음 라운드에서 본다.
- 한 문단에 여러 편집이 섞이면 하나만 되돌릴 수 없다 — 그 문단을 되돌리고 저자가 남길 편집을 다시 한다.
