# 지휘자 상태 브랜치 · 편지함 · Design

> 지휘자끼리 서로의 지금 상태를 모르는 것은 편지가 안 와서가 아니라 아무도 계산해 보지 않아서다. 겹치는 파일 · 머지 순서 · 판 번호는 git 에서 계산해 보이고, 계산되지 않는 것(예고 · 배운 것 · 질문)만 편지로 남긴다. 지휘자마다 코드 없는 상태 브랜치 하나에 계산한 현황과 편지를 두고, 편지로는 지휘자가 아무것도 정하지 않는다.

## Context / Why

로드맵 하나가 팀 하나이고, 로드맵은 이 레포에서 가장 큰 일의 단위다(사용자 「우리 내에서 가장 큰 단위니까」). 로드맵 여럿이 동시에 돌고, 지휘자는 다른 세션이나 다른 서버에 있을 수 있다. 사용자는 지휘자끼리 넷을 주고받아야 한다고 했다 — 같은 파일을 건드리려는 것, 머지 순서, 규칙과 배운 것, 사람에게 묻는 질문의 줄.

지금은 이렇다.

- **로드맵 사이를 보는 계산이 없다.** 경로 예약 겹침은 한 로드맵 안의 블록끼리만 견준다(`roadmap_status.py` 의 `overlaps`). 다른 로드맵의 예약 · 열린 브랜치 · 올린 판 번호는 지휘자가 스스로 보지 않는다. 2026-11-19 에 앞단 로드맵의 PR 이 머지돼 기본 브랜치가 움직인 것을 이 로드맵의 지휘자는 받아 온 뒤에야 알았고, 그 때문에 100분짜리 스위트 대조를 다시 돌았다. 같은 판 번호를 두 브랜치가 올려 조용히 합쳐진 일도 있었다(PR #297).
- **글은 오갈 수 있지만 남지 않는다.** 2026-11-18 에 앞단 로드맵의 지휘 세션이 이 세션에 「PR 이 예약 파일과 겹친다 · 머지 순서는 이렇다」 를 하니스의 세션 간 메시지로 보냈다. 같은 기계여서 닿았고, 받은 쪽이 메모에 옮겨 적지 않았다면 세션과 함께 사라졌다.
- **STATUS.md 와 inbox/ 는 자리 이름뿐이다.** R1 이 팀 폴더에 자리를 정했지만(`team_layout.py` 의 상수 둘) 읽고 쓰는 코드가 없다. 지휘 현황은 이 기계에만 있는 파일(`machine.md`)에서 계산한다.
- **R1 이 걸어 둔 계약이 임시로 남아 있다.** 리더가 쓰는 것(규칙 고침 · 아직 옮기지 않은 결정 줄 · STATUS · 편지)은 리더 상태 브랜치에 산다고 정했지만(R1 설계 §15) 그 브랜치가 없어 규칙 고침은 작은 PR 로, 대기 줄은 기계 상태에 쌓는다.

사용자는 2026-11-17 에 담당자와 리더 사이 대화는 세션 도구(herdr)로 풀리니 「복잡한 방식보다 로드맵간 대화만 해소하면 될듯함」 이라고 했고, 설계 대화(2026-11-19)에서 「서로의 지금 상태를 모른다 · 질문이 세 군데서 따로 온다 · 고쳐 준 버릇이 늦게 닿는다」 는 짐작에 「그래」 라고 답했다.

## Goals

- 지휘자가 편지를 쓰지 않아도, 상태를 맞출 때마다 다른 로드맵과 닿는 것(겹침 · 머지에 닿는 것 · 판 번호 · 기본 브랜치의 움직임)이 보인다.
- 사용자가 한 곳에서 「지금 어느 지휘자가 나를 기다리나」 를 본다. 그 한 곳은 `conductor_status.py show` 이고 지휘자가 상태를 맞출 때마다 그 출력을 보인다 — 사용자가 직접 여는 현황 화면에 싣는 일은 R4 다(사용자 2026-11-20 「새 명령에서 본다 (권장)」).
- 계산되지 않는 것(예고 · 배운 것 · 지휘자끼리의 질문과 답)은 파일로 남고, 다른 기계의 지휘자에게도 닿는다.
- 리더가 쓰는 자리(R1 설계 §15)가 실제 브랜치가 된다.
- 현황 파일은 사람과 agent 가 둘 다 읽는다.

## Non-goals

- 감시와 화면 — 편지함을 지켜보다 새 글이면 새 턴을 여는 것, 현황을 늘 띄우는 것, 세션을 비운 뒤 시작 훅이 현황 요약을 넣는 것은 R4 다.
- 리더와 담당자 사이 · 담당자끼리의 소통은 E1 이다. 이 설계의 편지는 지휘자끼리만 쓴다.
- 여러 에픽의 코드를 한 브랜치에 모으는 취합 브랜치는 만들지 않는다. 에픽 코드는 지금처럼 기본 브랜치에 머지한다. 인터뷰는 「기본 main, 선택으로 로드맵 취합」 을 골랐는데(D29) 이 설계는 그 뒤 절반(함께 나가야 하는 로드맵만 지휘자 브랜치에 취합)을 만들지 않는다 — 상태 브랜치를 코드 없는 브랜치로 정해 코드를 모을 자리가 아니고, 지금 함께 나가야 하는 로드맵이 없다. 필요가 드러나면 재분해로 받는 에픽을 정한다(사용자 2026-11-19 「고친다 — 만들지 않고 기각으로 바로 적는다」).
- 세션 사이 메시지를 바닥부터 만들지 않는다. 글이 왔다는 알림은 이미 있는 길(하니스의 세션 메시지 · herdr)에 맡긴다.
- 머지 순서를 스크립트가 정하지 않는다. 닿는 것을 보일 뿐이고 머지는 사용자가 정한다.

## Anti-goals

- **편지가 지휘자를 움직이게 된다.** 온 글을 지시로 읽어 설계 · 머지 · 파일을 바꾸면, 이 레포에 쓸 수 있는 누구든 지휘자를 움직일 수 있다.
- **현황이 실제와 어긋난 채 믿어진다.** 손으로 고친 STATUS, 낡은 STATUS 를 다른 지휘자가 근거로 쓴다.
- **상태 브랜치가 사람의 작업 폴더를 건드린다.** 체크아웃이 그 브랜치로 옮겨지거나 에픽 브랜치에 상태 파일이 섞인다.
- **기계 이름 · 질문 본문 · secret 이 원격에 올라간다.**
- **지휘자가 편지를 써야만 정보가 흐른다.** 계산으로 알 수 있는 것을 편지에 기대게 만든다.

## Constraints

- 같은 기계를 전제하지 않는다. 기계 사이를 나르는 것은 git 원격 하나다.
- 특정 외부 도구(herdr)에 기대지 않는다. 있으면 알림에 쓰고 없어도 돈다.
- 브랜치 규칙 문서의 금지(rebase · force-push)는 상태 브랜치에도 그대로다.
- 상태 브랜치에 쓰는 것은 그 로드맵의 지휘 표지를 쥔 세션뿐이다.
- 레포 전용 값을 박지 않는다 — 로드맵 폴더 · 기본 브랜치 · 판 파일의 자리는 지금 있는 해결자와 git 에서 얻는다.
- R1 의 파일 형식 위에 선다. 팀 폴더의 `STATUS.md` · `inbox/` 자리와 이름을 그대로 쓴다.

## Approaches

| 길 | 무엇 | 치르는 값 |
|---|---|---|
| 1 — 계산을 먼저, 편지는 얇게 | 상태 브랜치에 계산한 STATUS 와 편지. 겹침 · 머지에 닿는 것 · 판 번호는 git 에서 계산해 보이고 편지는 계산되지 않는 것만 | 계산 스크립트 하나가 는다 |
| 2 — 인터뷰 안 그대로, 편지함 중심 | 넷을 모두 편지로. 받음 · 답함 줄, 서명 커밋이나 허용 목록, 시작 훅이 밀린 글을 읽기 | 지휘자가 써 보내야만 정보가 흐른다. 서명 키 관리. 가장 무겁다 |
| 3 — 브랜치 없이 | 로드맵 사이 계산 보기만 더하고 편지는 세션 메시지에 약속만 | 글이 파일로 남지 않고 다른 기계에 닿지 않는다. STATUS 결정과 R1 의 리더가 쓰는 자리가 임시로 남는다 |

사용자가 길 1 을 골랐다(2026-11-19 「권장」). 서로의 상태를 모르는 것은 계산으로 풀리고, 「복잡한 방식보다」 라는 말과 맞으며, 인터뷰의 STATUS 결정과 R1 의 계약을 그대로 채운다.

## 설계

「작성자 제안」 이라고 적은 것은 사용자가 정한 것이 아니라 이 문서를 쓴 리더가 고른 것이다.

### §1 상태 브랜치

- **이름.** `conductor/<로드맵 이름>`. 로드맵 이름은 로드맵 폴더의 이름이다(예: `conductor/2026-11-14-conductor-context-economy-brief`). 사용자 2026-11-19 「둘다 권장으로」.
- **뿌리.** 기본 브랜치와 이력을 나누지 않는 브랜치다. 코드가 없고 기본 브랜치에 머지하지 않는다.
- **사는 것.** 파일은 팀 폴더의 경로 그대로 둔다(R1 이 정한 자리 — `<로드맵 폴더>/STATUS.md` · `<로드맵 폴더>/inbox/`). 같은 경로를 쓰면 R1 의 경로 함수(`Team.status` · `Team.inbox` · `Team.rules`)를 그대로 쓴다.

  ```
  <로드맵 폴더>/
    STATUS.md                      계산한 현황 (§2)
    inbox/<받는 로드맵 이름>/<글>.md   이 지휘자가 보낸 글 (§4)
    received.md                    이 지휘자가 받았다고 적은 줄 (§4)
    pending.md                     아직 과제 브랜치로 옮기지 못한 결정 줄 (§5 · team 형식)
    RULES.md                       팀 규칙 파일의 리더 쪽 사본 (§5 · team 형식)
  ```

- **쓰는 길.** 새 스크립트 `conductor_branch.py` 하나가 이 브랜치의 모든 쓰기를 맡는다. 작업 폴더를 쓰지 않고 git 의 바닥 명령으로 커밋을 만든다 — 어느 체크아웃의 HEAD · index · 파일도 바뀌지 않는다(작성자 제안 — 지금 스크립트 가운데 체크아웃 없이 커밋을 쓰는 것은 없다. 작업 폴더를 하나 더 두는 길은 Rejected Alternatives).
  - 쓰기 한 번이 커밋 하나다. 로컬 ref 는 읽었던 끝이 그대로일 때만 옮긴다. 끝이 달라져 있으면(같은 기계의 다른 쓰기가 끼어들었다) 달라진 끝에서 다시 읽어 아래 「다시 만든다」 의 규칙으로 다시 만든다.
  - 쓴 뒤 origin 에 올린다. origin 이 없거나 올리지 못하면 로컬 커밋을 남기고 「아직 안 올라옴」 을 낸다 — 다음 쓰기가 함께 올린다.
  - 올리기가 거절되면(원격이 앞섰다 — 다른 기계가 같은 로드맵의 브랜치에 썼다) 받아 와서 원격 끝 위에 이번 쓰기를 다시 만들고 「다른 곳에서 이 브랜치에 썼다 — <커밋> · <때>」 를 알린다. 그 전에 원격에 닿지 못해 로컬에만 있던 앞 커밋도 차례로 함께 다시 얹는다 — 그것들을 버리면 그동안 쓴 편지와 받음 줄이 사라진다. 다시 얹는 편지의 이름이 편지함 전체에서 겹치면 다음 빈 번호로 바꾼다(사용자 2026-11-20 「이대로 둔다 (권장)」). 올라간 커밋은 고치지 않고 force-push 하지 않는다. 원격 브랜치를 지우는 올리기에만 수를 센 끝과 같을 때만 지우는 조건을 건다 — 이력을 덮는 올리기는 아니다(사용자 2026-11-20 「여덟 모두 권장대로」). 「다시 만든다」 는 파일 종류마다 다르다 — 계산물(`STATUS.md`)은 다시 계산해 덮고, 줄 파일(`pending.md` · `received.md`)과 규칙 사본은 원격 끝의 글을 다시 읽어 같은 고침(줄 더하기 · 빼기)을 적용한다. 통째로 덮지 않는다. 다시 올린 것도 거절되면 세 번까지 되풀이하고, 그래도 안 되면 로컬 커밋을 남긴 채 멈춰 알린다.
  - 표지를 쥔 세션이 아니면 쓰지 않는다(지금 기계 상태 쓰기와 같은 규칙 · 종료 코드 5).
- **만드는 때.** 지휘자가 상태를 맞추는 걸음에서 `ensure` 가 없으면 만든다. 켜고 끄는 것은 §8.
- **없애는 때.** 로드맵의 에픽이 모두 끝나면(지휘 순환의 끝 걸음) 지휘자가 사용자에게 확인받고 로컬과 원격의 브랜치를 지운다. 사용자 「로드맵이 끝나면 지움」 에 「확인받고」 를 더한 것은 작성자 제안이다 — 원격 브랜치를 지우는 일은 되돌리기 어렵다. 지우기는 `conductor_branch.py delete` 가 한다 — 먼저 넷의 수(상대가 아직 받지 않은 보낸 글 · 내가 답하지 않은 온 질문 · 남은 대기 줄 · 안 올린 규칙 고침)를 내고, 지휘자가 그 수를 확인 질문에 함께 보이며, 확인 표시에 수를 센 끝을 실어 주어야(`--confirmed <수를 센 끝>` — 수와 함께 낸 그 끝이다) 지운다. 로컬 끝이나 원격 끝이 수를 센 끝과 다르면 지우지 않고 다시 센다(사용자 2026-11-20 「수를 보이고 확인받는다 (권장)」 · 끝을 싣는 꼴은 「셋 모두 구현에 맞춘다 (권장)」).
- **한 로드맵을 두 기계가 지휘할 때.** 지휘 표지는 기계 안의 파일이라 기계 사이에서는 막지 못한다. 이 설계는 알리기만 한다 — STATUS 머리의 지휘 세션 칸이 내 세션과 다르고 그 STATUS 가 이 세션이 표지를 잡은 때보다 뒤에 쓰였으면 「다른 세션이 이 로드맵의 현황을 쓰고 있다」 를 낸다. 표지를 잡기 전에 이전 세션이 쓴 것(지휘 세션을 새로 띄워 넘겨받은 경우)은 세지 않는다. 막는 일은 미룸(E3).

### §2 STATUS.md

스크립트(`conductor_status.py sync`)가 계산해 쓴다. 손으로 고치지 않는다. 사람과 agent 가 같은 파일을 읽는다 — 절 이름과 줄 꼴이 고정이라 스크립트가 다시 읽을 수 있다.

```
# STATUS — <로드맵 제목>

- 로드맵: <로드맵 경로>
- 계산: 2026-11-19 02:30 +0900 · 기준 커밋 89e28166 · 지휘 세션 3dc23458

## 열린 PR
- R1 · #298 · feature/team-file-rules

## 기다리는 질문
- R2 · 계획 검토 · 2026-11-19 02:05 +0900

## 작업

## 편지
- 보낸 글 1 · 아직 받지 않은 보낸 글 1 · 답 기다리는 글 0 · 받은 글 2

## 안 올린 규칙 고침
- 0줄
```

- **재료.** 에픽 단계는 지금의 상태 계산(`roadmap_status.py` 의 JSON), 열린 PR · 작업 · 담당자 수는 기계 상태, 편지 수는 상태 브랜치, 규칙 고침은 §5.
- **계산할 수 있는 것은 STATUS 에 기대지 않는다.** 다른 지휘자의 STATUS 에서 읽는 것은 그 기계에서만 아는 것 — 기다리는 질문 · 작업과 담당자 — 뿐이다. 열린 PR 줄은 에픽 · 번호 · 브랜치다 — 머지 전 확인을 마쳤는지는 남기는 기록이 없어 싣지 않는다(작성자 제안). 겹침 · 판 번호 · 브랜치의 움직임은 읽는 쪽이 git 에서 직접 계산한다(§3). 설계 대화에서 보인 칸 가운데 「잡은 판 번호」 를 STATUS 에서 빼고 §3 의 계산으로 옮긴 것은 작성자 제안이다.
- **쓰는 때.** 지휘자가 상태를 맞출 때마다(`sync`), 사용자에게 질문을 걸기 직전(`waiting add` — 줄을 올리면서 STATUS 까지 쓴다), 답을 받은 뒤(`sync`). 계산 줄 말고 달라진 것이 없으면 커밋하지 않는다 — 다만 마지막으로 쓴 STATUS 의 계산 시각이 한 시간 넘게 낡았으면 달라진 것이 없어도 커밋한다(읽는 쪽이 낡은 현황과 변함없는 현황을 가를 수 있게 · 작성자 제안).
- **기다리는 질문.** 지휘자가 사용자에게 질문을 걸 때 `conductor_status.py waiting add --epic <에픽> --kind <종류> --via <질문 창|턴 끝>` 으로 올리고 답을 받으면 `waiting clear` 로 내린다. 줄은 기계 상태의 새 절 「지금 묻는 질문」(에픽 · 종류 · 건 길 · 언제부터 · 세션)에 산다 — 지금 있는 「기다리는 질문」 절(다른 일에 기대어 미뤄 둔 질문이고 본문을 싣는다)과 다른 절이고 그 절은 그대로 둔다(작성자 제안). 싣는 것은 에픽 · 종류(설계 대화 · spec 승인 · 계획 검토 · 흐름 승인 · 걸음 건너뜀 · 옮긴 질문 · 머지 · 그 밖 — 사람 줄이 있는 질문은 사람 줄의 종류와 같은 이름을 쓴다 · 사용자 2026-11-20 「R2 이름에 맞춘다 (권장)」) · 언제부터뿐이다 — 질문 본문과 선택지는 싣지 않는다. 건 길이 질문 창인 줄은 `waiting add` 뒤에 그 세션이 돌리는 첫 `sync` 가 내린다(그 세션이 다시 돌고 있다는 것이 답을 받았다는 뜻이다). `waiting add` 자신은 줄을 내리지 않는다 — 질문 직전에는 `sync` 를 따로 돌리지 않는다. 건 길이 턴 끝인 줄은 지휘자가 내린다 — 잊으면 「언제부터」 가 오래된 줄로 드러난다. 같은 (에픽, 종류)를 같은 세션이 질문 창으로 다시 걸면 언제부터를 새로 적는다(작성자 제안). 사용자 2026-11-19 「ok」(보이기만 — 질문은 지금처럼 각 지휘자가 자기 차례에 묻는다).
- **싣지 않는 것.** secret · 질문 본문 · 사람 이름 · 기계 이름 · 이 기계의 절대경로. 지휘 세션 칸은 세션 번호의 앞 여덟 자다.
- **어긋남.** 머리의 계산 시각과 기준 커밋이 낡음을 드러낸다. 읽는 쪽은 「n시간 전 계산」 을 함께 보인다.

### §3 로드맵 사이 보기

`conductor_status.py show --roadmap <내 로드맵>` 한 명령이 내 STATUS 와 아래 보기를 낸다. 읽기만 하고 모델을 부르지 않는다(사용자 원문의 「파일만 읽어서 토큰 0」). 받아 오는 일(`git fetch`)은 지휘자가 상태를 맞출 때 이미 한다.

```
다른 로드맵과 닿는 것 (계산 02:31)
- 예약 겹침: CLAUDE.md — 앞단 F6(설계 중) · 이 로드맵 R2(계획)
- 바꾼 파일 겹침: plugins/spec-distill/skills/epic-conductor/SKILL.md — 앞단 feature/official-switches-state · 이 로드맵 feature/conductor-walk-table
- 판 번호: spec-distill — 기본 브랜치 8.23.0 · 8.24.0 을 둘이 잡았다(앞단 feature/… · 이 로드맵 feature/…) — 먼저 머지되는 쪽이 그 번호, 뒤쪽은 다시 잡는다
- 기본 브랜치의 움직임: feature/conductor-stage-table 보다 3 커밋 앞섬 · 그 가운데 이 로드맵의 예약 경로를 바꾼 것 1(CLAUDE.md)

사용자를 기다리는 질문 (오래된 순)
- 앞단 · F4 · 계획 검토 · 01:40부터   (STATUS 20분 전 계산)

- 앞단 → 예고 · plugins/spec-distill/scripts/control_plane.py · conductor/…:…/inbox/…/2026-11-19-01.md
```

- **대상.** 기본 브랜치에 있는 로드맵 파일 가운데 끝나지 않은 것 전부(지금 `conductor_ledger.py roadmaps` 가 찾는 길).
- **예약 겹침.** 서로 다른 로드맵의 끝나지 않은 블록 쌍마다 경로 예약을 견준다. 한 로드맵 안에서 쓰는 지금의 함수(`overlaps`)와 같은 규칙이고 공유 파일(판 파일 · CHANGELOG · README)은 뺀다.
- **바꾼 파일 겹침.** 서로 다른 로드맵의 열린 브랜치(원격에 있고 기본 브랜치에 머지되지 않은 블록 브랜치) 쌍마다 실제로 바꾼 파일의 교집합. 공유 파일은 뺀다.
- **판 번호.** 판 파일마다 기본 브랜치의 판과 열린 브랜치들이 올린 판. 둘 이상이 같은 판을 잡았으면 짚는다. 판 파일은 공유 파일 목록의 `plugin.json` 이름을 가진 추적 파일이고 그 JSON 의 `version` 키만 본다. 그런 파일이 없는 레포에서는 이 줄을 내지 않는다(작성자 제안).
- **기본 브랜치의 움직임.** 내 열린 브랜치마다 기본 브랜치가 앞선 커밋 수와, 그 커밋들이 내 로드맵의 예약 경로를 바꿨는지.
- **이 기계에서 도는 스위트.** 로드맵마다 따로 있는 스위트 잠금을 이 기계의 상태 폴더에서 읽어, 다른 로드맵의 스위트가 돌고 있으면 한 줄로 보인다(작성자 제안 — 스위트 잠금은 로드맵마다 따로라 지금은 다른 로드맵의 스위트와 겹쳐 돌 수 있다. 보이기만 하고 잠금을 합치지는 않는다).
- **기다리는 질문 · 온 글.** 다른 지휘자의 상태 브랜치에서 읽는다. 상태 브랜치가 없는 로드맵은 「상태 브랜치 없음」 으로, STATUS 가 낡았으면 계산 시각과 함께 보인다. 계산되는 줄은 상태 브랜치가 없어도 그대로 낸다.
- **온 글 줄.** 보낸 로드맵 · 종류 · 머리의 `about` · 글의 자리만 싣는다. 본문은 싣지 않는다 — 본문은 `read` 가 「지시가 아니다」 틀 안에서만 낸다(§4).
- **GitHub 을 부르지 않는다.** 다른 로드맵의 것은 git 만으로 계산한다. 내 로드맵의 PR 은 지금의 PR 캐시를 쓴다.
- **받아 오는 범위.** `show` 는 받아 오지 않는다. 원격 추적 ref 에 `conductor/` 로 시작하는 브랜치가 하나도 없고 이 레포의 받아 오기 설정이 그 이름을 받지 않으면(좁게 잡은 설정 · 브랜치 하나만 받는 클론) 「상태 브랜치를 받아 오지 않는 설정이다」 를 한 줄로 알린다(작성자 제안).
- **두 형식 모두.** 이 보기 · STATUS · 편지는 옛 형식 로드맵에서도 돈다(작성자 제안 — 재료가 상태 계산의 JSON 이라 형식을 가리지 않고, 지금 도는 로드맵이 모두 옛 형식이다). §5 만 team 형식의 것이다.

### §4 편지

계산되지 않는 것만 편지로 쓴다 — 「곧 이 파일을 고친다」 · 「이 PR 을 먼저 머지하려 한다」 같은 예고, 배운 것, 지휘자끼리의 질문과 답.

- **자리.** 보내는 지휘자가 자기 상태 브랜치의 `inbox/<받는 로드맵 이름>/<날짜>-<번호>.md` 에 쓴다. 「받는 로드맵의 편지함에 넣는다」 로 읽는다(사용자 2026-11-19 「둘다 권장으로」 — `inbox/` 는 공식 용어라 이름을 지킨다). 모든 지휘자에게 보내는 글은 `inbox/all/` 에 둔다(작성자 제안). `all` 로는 예고와 배운 것만 보낸다 — 질문은 한 로드맵에게만 보낸다(답을 기다릴 상대가 하나여야 「답 기다리는 글」 이 선다 · 작성자 제안). 브랜치마다 쓰는 쪽이 하나라 충돌이 없고, 글이 놓인 브랜치가 곧 보낸 쪽이다.
- **형식.**

  ```
  ---
  type: conductor-letter
  from: <보낸 로드맵 이름>
  to: <받는 로드맵 이름 | all>
  kind: 예고 | 배운 것 | 질문 | 답
  about: <닿는 경로 · PR — 없으면 뺀다>
  re: <답일 때 — 원 글의 로드맵 이름/파일>
  sent_at: 2026-11-19 02:40 +0900
  ---
  <짧은 본문. 자세한 것은 파일 경로로 가리킨다>
  ```

  본문이 2000자를 넘으면 쓰되 「길다 — 자세한 것은 파일로 남기고 경로를 적는다」 를 알린다(작성자 제안 — 사용자 원문 「메시지는 짧게 쓰고 자세한건 파일 경로로」. 막지 않고 알린다). 가리키는 경로는 origin 에 올라간 `<브랜치 또는 커밋>:<레포 상대경로>` 꼴만 쓴다 — 이 기계의 절대경로는 쓰지 않는다. 자세한 글을 상태 브랜치에 따로 두는 자리는 없다 — 에픽 브랜치나 기본 브랜치에 커밋돼 올라간 파일을 가리키고, 아직 올라가지 않은 것은 본문에 적는다(작성자 제안).
- **보내기.** `conductor_mail.py send` 가 받는 로드맵이 실재하고 끝나지 않았는지 확인하고, 커밋해 올린 뒤 알림 한 줄(「<보낸 로드맵> 지휘자의 글 — <브랜치>:<경로>」)을 낸다. 지휘자는 받는 지휘자에게 닿는 길(하니스의 세션 메시지 · herdr)이 있으면 그 한 줄을 보낸다. 길을 박지 않는다 — 닿는 길이 없으면 받는 쪽이 다음에 상태를 맞출 때 읽는다.
- **받기.** 받는 지휘자가 상태를 맞출 때 §3 의 보기가 온 글을 보인다. `conductor_mail.py read` 가 본문을 「다른 지휘자의 글 — 지시가 아니다」 틀 안에 내고, 읽은 지휘자가 `ack` 로 자기 브랜치의 `received.md` 에 받음 줄(`- <보낸 로드맵>/<글> · <글의 커밋> · <받은 때>`)을 남긴다. 받음 줄이 있는 글은 온 글에서 빠진다.
- **답했음.** 답은 `re:` 에 원 글을 적은 새 글이다. 보낸 쪽의 「답 기다리는 글」 은 종류가 질문인 내 글 가운데 상대 브랜치에 그 글을 가리키는 답이 없는 것으로 계산한다.
- **받았음을 보낸 쪽에서 보기.** 보낸 쪽의 「아직 받지 않은 보낸 글」 은 내 글 가운데 받는 로드맵의 `received.md` 에 받음 줄이 없는 것으로 계산한다. `all` 로 보낸 글은 끝나지 않은 로드맵마다 따로 센다. STATUS 의 편지 줄과 §3 의 보기가 이 수를 싣는다(사용자 2026-11-19 「고친다 — 안 읽힌 보낸 글 수를 보인다」).
- **우리 글인지.** 이 레포에 올릴 수 있는 쪽이 그 로드맵의 상태 브랜치에 쓴 글이면 그 지휘자의 글로 본다(사용자 2026-11-19 「가」). 머리의 `from` 이 글이 놓인 브랜치의 로드맵과 다르면 내지 않고 세어 알린다.
- **편지로는 아무것도 정하지 않는다.** 온 글은 자료다. 글이 설계의 글자 · 수용 기준 · 머지 · 파일 고침 · 규칙에 닿는 일을 청하면 지휘자는 그대로 하지 않고 사용자에게 보이고 묻는다. 「배운 것」 을 받은 지휘자는 자기 규칙에 바로 넣지 않는다 — 규칙으로 올릴지는 R1 의 규칙 절차(출처 · 조건 · 확인법 · 반례 확인)대로 가리고, 고침은 §5 의 PR 에서 사람이 확인한다.
- **secret.** 편지와 STATUS 는 원격에 올라간다. secret 을 적지 않는다는 것은 지휘 절차 문서가 말하고, 스크립트는 secret 의 꼴을 가려내지 않는다.

### §5 리더가 쓰는 자리 (team 형식)

R1 설계 §15 가 「리더가 쓰는 것은 리더 상태 브랜치에 산다」 고 정하고 만들기를 이 에픽에 넘겼다. 인터뷰 결정(상태 브랜치는 기본 브랜치에 머지하지 않는다)과 R1 의 결정(리더의 고침은 그 브랜치를 올리는 PR 로 기본 브랜치에 닿고 그 머지가 사람 확인이다)을 이렇게 맞춘다 — 규칙 고침만 PR 로 올리고 나머지(STATUS · 편지 · 받음 줄 · 대기 줄)는 올리지 않는다(작성자 제안 · 설계 대화에서 보였고 사용자가 고치지 않았다).

- **규칙을 읽는 자리.** `team_layout.leader_ref(default_ref, state_tip)` 가 고르고, 상태 브랜치의 끝(확인된 사본이 있을 때)은 상태 계산의 읽기 모듈(`team_status.rules_tip`)이 계산해 넘긴다 — 상태 브랜치가 켜져 있고 거기에 `RULES.md` 사본이 있으면 그 끝을, 아니면 지금처럼 기본 브랜치를 낸다(작성자 제안). 사본은 상태 브랜치를 만들 때 두지 않는다 — 리더가 규칙을 처음 고칠 때 기본 브랜치의 글에서 생기고, 기본 브랜치의 글과 같아지면(그 고침이 머지되면) `sync` 가 지운다. 안 올린 고침이 있는 동안에만 있으므로, 리더가 고치지 않은 동안 기본 브랜치의 규칙이 바뀌어도 낡은 사본을 읽지 않는다(작성자 제안).
- **규칙을 읽은 커밋.** 결과 파일 머리에 `rules_at`(규칙을 읽은 커밋) 칸을 더한다. 시작 묶음의 「맞추는 명령」 줄이 그 값을 싣고 `job sync` 가 적는다. 「묶음 낡음」 은 규칙 글을 `rules_at` 에서, 공통 문서와 역할 문서를 지금처럼 `bundle_at` 에서 견준다. `rules_at` 이 없는 옛 결과 파일은 지금처럼 `bundle_at` 으로 견준다. 이것 없이 값만 바꾸면 거짓 「묶음 낡음」 이 뜬다(R1 계획 3 판정).
- **규칙 고침.** 리더는 규칙 줄을 더하거나 지울 때 상태 브랜치의 `RULES.md` 를 고친다(`conductor_branch.py` 의 쓰기 — 사본이 없으면 기본 브랜치의 글로 만든 뒤 고치고, 출발한 기본 브랜치 커밋을 함께 적어 둔다. 출발 커밋은 상태 브랜치의 `<로드맵 폴더>/rules-base.md` 에 적고, 명령은 `conductor_branch.py rules-add` · `rules-drop` · `rules-reset` 이다 — 작성자 제안). 다음 시작 묶음부터 그 글이 실린다.
- **기본 브랜치에 올리기.** 상태 브랜치의 `RULES.md` 가 기본 브랜치와 다르면 STATUS 가 「안 올린 규칙 고침 n줄」 을 보인다. 지휘자는 에픽 PR 의 머지 전 확인 자리에서 그것을 함께 알리고, `conductor_branch.py rules-branch` 가 기본 브랜치에서 딴 작은 브랜치에 그 파일만 바꾼 커밋을 만든다. PR 을 여는 것과 머지 전 확인은 지금 절차 그대로이고 머지는 사용자가 한다(사용자 2026-11-19 「둘다 그렇게 가자」). 사본이 생긴 뒤 기본 브랜치의 `RULES.md` 가 다른 손으로 바뀌면 `sync` 가 「규칙 사본이 기본 브랜치와 갈라졌다」 를 알리고, `rules-branch` 는 만들지 않고 멈춰 둘의 차이를 보인다.
- **남이 올린 줄.** 상태 브랜치에는 이 레포에 올릴 수 있는 누구나 쓸 수 있다. 원격에서 받아 온 커밋 가운데 이 기계의 지휘 세션이 만들지 않은 것이 규칙 사본이나 `pending.md` 를 바꿨으면, 그 내용을 시작 묶음에 싣거나 결정 기록으로 옮기기 전에 지휘자가 차이를 사용자에게 보이고 확인받는다. 확인 전에는 규칙은 기본 브랜치의 글을 쓰고(`leader_ref` 가 기본 브랜치를 낸다) 대기 줄은 확인한 끝까지의 줄만 옮긴다. 이 기계가 쓰거나 사용자가 확인한 끝은 기계 상태에 적어 둔다. 편지의 「자료일 뿐」 과 같은 약속을 같은 브랜치의 나머지 파일에 거는 것이다(사용자 2026-11-19 「고친다 — 확인받은 뒤에만 쓴다」). 확인은 `conductor_branch.py confirm` 이 보인 끝을 `--confirmed <끝>`(40자 전체)으로 받아 기록한다. 이 기계가 쓴 커밋은 쓰기의 바닥이 기계 상태 `확인한 끝` 절에 적는다(작성자 제안). 남의 규칙 고침을 물리는 길은 `rules-reset` 이다 — 사본을 지워 기본 브랜치의 규칙으로 돌아간다(사용자 2026-11-20 「여덟 모두 권장대로」).
- **대기 줄.** team 형식이고 상태 브랜치가 켜져 있으면 `conductor_ledger.py` 의 `add --section "쌓인 기록"` · `pending` · `flush` 가 기계 상태 대신 상태 브랜치의 `pending.md` 를 읽고 쓴다. 줄 꼴(에픽 · 절 · 글)과 `flush` 가 옮기는 곳(과제의 INTENT.md 결정 기록)은 그대로다. 옛 형식 로드맵과 꺼져 있을 때는 지금대로 기계 상태에 쌓는다. 상태 브랜치가 아직 없으면 기계 상태에 쌓고 알리며, `pending` · `flush` 는 두 자리를 함께 읽는다(작성자 제안). 상태 브랜치 자리에서는 사람 줄을 넣지 않고 `flush` 는 사람 줄을 건너뛰어 센다(사용자 2026-11-20 「여덟 모두 권장대로」).

### §6 브랜치 규칙 문서

`docs/git-workflow/branch-strategy.md` 를 고친다.

- 이름 정규식에 둘째 갈래를 더한다 — `^(feature|fix|docs|chore)/[a-z0-9][a-z0-9.-]*$|^conductor/[a-z0-9][a-z0-9.-]*$`. 맨 앞 그룹에는 넣지 않는다.
- 접두 표에 한 줄 — `conductor/<로드맵 이름>` · 지휘자 상태 브랜치.
- 짧은 절 하나 — 코드가 없다 · PR 로 머지하지 않는다 · 스크립트만 쓴다(손으로 커밋하지 않는다) · 이 브랜치로 체크아웃하지 않는다 · 「2–4 단어 · 50자 이하」 를 받지 않는다(이름이 로드맵 폴더에서 나온다) · 로드맵이 끝나면 지운다 · rebase 와 force-push 금지는 같다.
- **다른 레포.** `ensure` 는 만들기 전에 그 레포 기본 브랜치의 브랜치 규칙 문서(project-init 이 두고 그 훅이 읽는 문서의 이름 정규식)를 읽는다. 규칙이 `conductor/<로드맵 이름>` 을 받지 않으면 브랜치를 만들지 않고 「이 레포의 브랜치 규칙이 conductor/ 를 받지 않는다 — 규칙 문서에 갈래를 더하거나 state_branch 를 끈다」 를 알리며, 꺼진 때처럼 계산되는 줄만 낸다. 규칙 문서가 없는 레포에서는 그대로 만든다(사용자 2026-11-19 「고친다 — 규칙이 안 받으면 만들지 않음」). 규칙 문서는 있는데 쓸 규칙을 읽지 못하거나 레포 설정 파일에 오류가 있으면 받는지 알 수 없으므로 만들지 않고 알린다(사용자 2026-11-20 「이대로 둔다 (권장)」). 다른 플러그인의 스크립트는 부를 수 없으므로 같은 문서를 읽는 작은 읽기를 이 플러그인에 둔다 — 문서의 자리를 어떻게 정하는지는 계획이 정한다.

브랜치 이름을 확인하는 훅(`plugins/project-init/hooks/post-tool-use.py`)은 이름 규칙을 이 문서의 정규식에서 읽으므로 문서만 고치면 `conductor/` 를 안다. 다른 이름을 고치라고 권할 접두는 정규식의 맨 앞 그룹에서만 뽑으므로(`derive_prefixes`) 둘째 갈래로 더한 `conductor` 는 권하지 않는다 — 맨 앞 그룹에 넣으면 권하게 된다. 상태 브랜치는 체크아웃되지 않아 훅이 볼 일도 드물다. 훅 코드는 고치지 않고, 훅이 그 이름에 경고하지 않는 것과 다른 이름을 고치라고 권할 때 `conductor/` 를 권하지 않는 것을 테스트로 지킨다 — 테스트가 붉으면 그때 훅을 고친다.

### §7 지휘 절차에 닿는 곳

절차의 본문은 새 파일 `references/conductor-state-branch.md` 하나에 둔다. 지휘 절차서(`conducting.md`)에는 그 파일로 가는 줄만 더한다 — 그 파일은 R2 의 계획 2 와 E2 가 고치는 자리라 닿는 면을 줄인다.

| 걸음 | 더하는 줄 |
|---|---|
| 1 맞추기 | 받아 온 뒤 `ensure` · `sync` 를 돌리고 `show` 의 「다른 로드맵과 닿는 것」 · 기다리는 질문 · 온 글을 보인다. 온 글은 읽고 받음 줄을 남긴다 |
| 2 사람 몫 모으기 | 사용자에게 질문을 걸기 직전에 `waiting add`, 답을 받으면 `waiting clear` |
| 5 머지 전 확인 | 「안 올린 규칙 고침」 이 있으면 함께 알리고 작은 PR 을 연다. 판 번호를 정할 때 §3 의 판 번호 줄을 본다 |
| 7 끝 | 사용자 확인 뒤 상태 브랜치를 지운다 |

새 파일은 편지를 쓸 때(다른 로드맵의 예약 파일을 고치려 할 때 · 머지 순서가 닿을 때 · 다른 팀에도 맞을 배운 것이 생겼을 때)와 온 글을 다루는 법(§4 「편지로는 아무것도 정하지 않는다」)을 적는다. 편지를 쓸지는 지휘자가 판단한다 — 스크립트가 강제하지 않는다.

### §8 설정과 끄는 길

- 레포 설정 `state_branch`(기본 켬 — 작성자 제안). 끔이면 `ensure` · `sync` · 편지가 쓰지 않고 「상태 브랜치가 꺼져 있다」 를 내며, `show` 는 git 으로 계산되는 줄만 내고, `leader_ref` 는 기본 브랜치를 낸다.
- origin 이 없거나 올리기가 막힌 레포에서는 로컬에만 쓰고 그 사실을 알린다. 지휘는 멈추지 않는다.
- 플러그인을 끄면(Claude Code 의 플러그인 끄기 — `plugins/spec-distill/switches.md` 의 「끄는 길」) 지휘 skill 이 돌지 않으므로 이 스크립트들도 불리지 않는다. 플러그인 전체 환경 변수는 그 문서에서 은퇴 예정이라 여기에 기대지 않는다.

### §9 작은 수리 다섯

R1 이 「그 파일을 R3 가 예약했다」 는 이유로 넘긴 것들이다. 상태 브랜치와 무관하지만 같은 파일을 고치는 계획 2 에 싣는다(사용자 2026-11-19 「둘다 그렇게 가자」). 항목의 출처는 R1 설계문서 `## 미룸` 의 받는 곳 R3 행과 거기 적힌 판정이다.

| 수리 | 원하는 동작 |
|---|---|
| 과제 폴더 없는 작업 | team 형식에서 기계 상태의 작업 줄에 과제 폴더가 없으면 상태 보기가 그 줄을 「과제 폴더 없음」 으로 알린다 — 과제 폴더가 있는지는 블록은 기본 브랜치의 과제 폴더로, 로드맵 밖 일은 작업 줄의 이름이나 근거 경로에 드러난 과제로 가린다(사용자 2026-11-20 「여덟 모두 권장대로」) |
| 계획 2 리뷰의 작은 지적 넷 | 「예약 밖 변경」 알림이 길면 앞의 몇 줄과 「외 n개」 로 줄인다(몇 줄인지는 계획이 제안하고 계획 확인에서 정한다) · team 형식에서 판정이 없을 때의 문구가 설계문서가 아니라 결과 파일을 가리킨다 · 현황의 단계 묶음(`BUCKETS`)과 작업 상태 표(`TASK_STATUS`)의 단계 이름이 어긋나면 테스트가 붉다 · 글 출력(`roadmap_status.py`)이 로드맵 밖 과제를 보인다 |
| 단순 작업의 PR 단계 | PR 캐시 채우기가 로드맵 블록의 브랜치뿐 아니라 단순 작업 과제의 브랜치도 채운다 |
| 판정 줄의 꼴 | `Ruling:` 줄을 가려내는 규칙을 함수 하나에 둔다. 지금 셋(부분 문자열로 찾는 둘 · 줄 시작으로 찾는 하나)이 실제 원장에서 다르게 가르는 줄이 있는지 계획의 첫 과제가 재고, 있으면 어느 쪽으로 맞출지 계획 확인에서 묻는다 |
| 「묶음 낡음」 의 빈 곳 | 구현 밖 단계에서 읽지 못한 결과 파일을 말없이 건너뛰지 않고 「묶음 낡음을 재지 못했다」 로 알린다. 결과 받음 쪽 알림과 같은 파일을 두 번 알리지 않는다 |

## 계층과 온톨로지

진입점은 로드맵이다. 로드맵에서 따라 내려간다.

| 객체 | 주인(쓰는 쪽) | 사는 곳 | 가리키는 것 |
|---|---|---|---|
| 상태 브랜치 | 그 로드맵의 지휘 표지를 쥔 세션(`conductor_branch.py` 로만) | `conductor/<로드맵 이름>` — 로컬과 origin | 로드맵 폴더의 이름 |
| STATUS.md | 스크립트(`conductor_status.py sync`) | 상태 브랜치의 `<로드맵 폴더>/STATUS.md` | 로드맵 · 기준 커밋 · 지휘 세션 |
| 기다리는 질문 줄 | 지휘자(`waiting add` · `clear`) | 기계 상태의 「지금 묻는 질문」 절 → STATUS | 에픽 |
| 로드맵 사이 보기 | 없음 — 읽을 때마다 계산 | 화면 | 로드맵들의 블록 · 열린 브랜치 · 판 파일 · 다른 지휘자의 STATUS 와 편지 |

## Verification Plan

- **쓰기의 바닥.** 임시 레포와 빈 원격으로 — 만들기, 쓰기, 올리기, 표지 없는 세션의 거절, 읽었던 끝이 달라졌을 때, 원격이 앞섰을 때의 다시 만들기, origin 없음. 쓰기 앞뒤로 작업 폴더의 HEAD · index · `git status` 가 같은지 본다. 얕은 클론과 worktree 안에서도 본다.
- **STATUS.** 같은 재료에서 두 번 계산해 계산 줄 말고 같은지, 쓴 것을 다시 읽어 같은지, 싣지 않는 것(질문 본문 · 기계 이름 · 절대경로)이 재료에 있어도 나오지 않는지.
- **로드맵 사이 계산.** 로드맵 둘 · 셋을 가진 임시 레포에서 예약 겹침 · 바꾼 파일 겹침 · 같은 판 · 기본 브랜치의 움직임을 각각 있는 경우와 없는 경우로. 공유 파일 빼기. 끝난 로드맵 빼기. 상태 브랜치가 없는 로드맵 · 낡은 STATUS.
- **편지.** 보내고 · 보이고 · 읽고 · 받음 줄 뒤 빠지는 것, 답과 「답 기다리는 글」, `from` 이 브랜치와 다른 글, 없는 로드맵으로 보내기, `all`. 두 기계를 흉내 낸 클론 둘 사이에서 origin 을 거쳐 닿는지.
- **흔들어 보기.** 표지 확인 · `from` 대조 · 공유 파일 빼기 · 끔 설정의 조건을 하나씩 뒤집거나 지우는 변이마다 테스트가 붉어지는지 본다. 통과가 정답인 단언에는 양성 대조를 둔다.
- **리더가 쓰는 자리.** 규칙을 고친 뒤 새 묶음이 새 글을 싣는지, 고치기 전에 받은 묶음의 결과에만 「묶음 낡음」 이 뜨는지, `rules_at` 없는 옛 결과 파일, 대기 줄의 두 자리, 규칙 브랜치 만들기와 기본 브랜치가 다르게 바뀐 경우.
- **문서 락.** `branch-strategy.md` 의 정규식과 훅, 지휘 절차서의 줄 넷, 새 절차 파일의 「자료다」 문장.
- **옛 동작.** 옛 형식 로드맵과 꺼진 설정에서 출력이 그대로인지(AC20).
- **스위트.** PR 마다 머지 전 스위트 대조.

## Rejected Alternatives

- **편지함 중심(길 2)** — 지휘자가 써 보내야만 정보가 흐른다. 서명 키를 기계마다 관리해야 한다.
- **브랜치 없이(길 3)** — 글이 남지 않고 다른 기계에 닿지 않으며 STATUS 결정과 R1 의 계약이 임시로 남는다.
- **받는 쪽 브랜치에 쓰기** — 한 브랜치에 쓰는 쪽이 여럿이 되어 올리기가 서로 거절된다. 누가 썼는지도 브랜치로 알 수 없다.
- **상태 브랜치를 작업 폴더로 꺼내 두고 쓰기** — 작업 폴더가 하나 더 늘어 주인 모를 폴더 목록과 정리에 걸리고, 세션이 다시 뜰 때 사라지는 일이 있었다.
- **브랜치 목록에 안 보이는 git 참조** — GitHub 화면에서 STATUS 를 읽을 수 없고 받아 오는 설정이 따로 든다.
- **허용 목록 · 서명 커밋** — 목록과 키의 관리가 는다. 편지로 아무것도 정하지 않으면 얻는 것이 작다(사용자 「가」).
- **질문을 양보하기** — 급한지를 지휘자가 판단해야 하고 멈춘 일이 더 오래 멈춘다(사용자 「ok」).
- **고칠 때마다 규칙 PR** — PR 이 잦아진다(사용자 「둘다 그렇게 가자」).
- **상주 서버가 있는 편지 도구(mcp_agent_mail)** · **모든 팀이 함께 쓰는 데이터 브랜치** — 인터뷰가 기각했다.
- **STATUS 에 겹침과 판 번호까지 싣기** — 계산할 수 있는 것을 남의 파일에서 읽으면 낡은 값을 믿게 된다.

## 미룸

R1 설계문서의 미룸 표에서 받는 곳이 R3 인 행 열하나를 가른다. 이 설계가 받은 것은 열이다 — 상태 브랜치 만들기 · 대기 줄 · 읽을 ref · 올리는 때(§1 · §5), `STATUS.md` · `inbox/` 의 내용과 계약(§2 · §4), 규칙을 읽은 커밋 칸 둘(§5), 작은 수리 다섯(§9), 원자료 대조표의 R3 몫(원문 대조). 나머지 하나와 이 설계가 새로 미루는 것은 아래다. 스위트 잠금을 로드맵 사이에서 하나로 합치는 일은 미루는 것이 아니라 하지 않는 것이다(§3 은 보이기만 한다) — 필요가 드러나면 재분해로 받는 에픽을 정한다.
