# brief 재구조화 — 설계

> **검증 대상과 인계 대상이 같은 파일이면 검증이 인계물을 부풀린다.**

`interview-brief` 의 payload 는 압축된 판정만 담고, 확산 원자료는 sidecar audit 으로 옮긴다.
게이트는 payload 에 **부재·등식 검사**를 두고, payload 와 audit 을 **교차로** 묶는다 —
`interview-seed` 가 존재 검사를 피하는 이유를 물려받되, 그 자리를 형태 검사가 아니라 교차 검사가
맡는다. `references/compression.md` 가 brief 의 채택을 이름으로 예약해 두었다.

## 1. 무엇을 만드는가

### 1.1 정체

`spec-distill` 의 `conducting-interview` 가 만드는 두 파일(payload + audit)의 **내용 분할선**을
옮기고, `check_brief.py` 의 검사들을 그 새 분할선에 맞춰 재배치한다. 파일 개수도 파서 형식도
바뀌지 않는다.

### 1.2 왜 — 원인은 규약 부재가 아니라 게이트 배치

오늘 payload 는 audit 보다 크다(직전 brief 실측: payload 27,590자 / audit 8,438자). 확산물이
압축물보다 작다.

원인은 게이트가 어디를 보느냐다. `check_brief.py gate` 의 16개 검사 중 **11개가 payload 내부**,
2개가 audit 내부, 3개만 교차다. 검증하고 싶은 것이 전부 payload 로 끌려왔고, payload 는 동시에
하류가 받는 인계물이다.

**이 인과는 사용자의 관측 가설이고 측정되지 않았다** — payload 의 실제 토큰 수도, 그것이 하류를
흔든 정도도 재지 않았다(§10 「효과 측정」). 부피가 아니라 distractor 형상이 원인일 수 있다.
그 가능성을 열어 둔 채로 진행한다.

### 1.3 진짜 goal

검증 대상(audit)과 인계 대상(payload)을 가른다. payload 가 **자립 완결**이면서 작아지게 한다.
**분량 감축은 결과이지 목표가 아니다** — 수치 상한을 두지 않고, 감소량을 성공 지표로 삼지 않는다.

**Non-goal**

- `user_sourced_items` 의 파서 형식 전환(frontmatter YAML → 본문 절).
- 출처 표기 자체의 제거. URL 은 audit 으로 가되 payload 는 출처 «키» + 직접인용을 유지한다.
- payload 분량의 수치 상한.
- `interview-seed` 쪽 코드 변경. `compression.md` 문단 하나만 갱신한다.

### 1.4 seed 와의 관계

`references/compression.md` 는 두 산출물이 공유하는 계약이고, 그 안에 이 작업이 이름으로
예약돼 있다 — *"오늘 이 계약을 게이트로 집행하는 것은 seed 뿐이다. `interview-brief` 는 이
규약을 원칙으로 상속하되 게이트로 강제받지 않는다. […] brief 는 그 재구조화(별도 설계) 이후에
채택한다."*

**통일 방향은 brief → seed 다.** seed 는 이미 목표 형태이고 바꿀 것이 없다.

| 축 | seed | brief 오늘 | brief 이후 |
|---|---|---|---|
| 사용자 원문 | audit `§1 원문`, append-only | payload §6 | audit §6, append-only |
| 외부 URL | payload 에 0개 | §4·§5 에 필수 | payload 에 0개 |
| 확산 원문 | audit §3 긴 초안 | payload §4·§5 에 서사 | audit §7 |
| 리뷰어 raw | audit §4 | audit §5 | 불변 |

**갈라진 채로 두는 것**도 같은 파일이 허가한다 — *"메시지형 payload 에는 존재 검사를 두지
않는다. 문서형 payload 는 절 존재 검사를 가질 수 있되 확산물의 원문·근거·전량을 payload 에
요구해서는 안 된다."* seed 는 메시지형(절 없음), brief 는 문서형(§0–§7 유지). **절 구조는
갈라져도 되고, 「원문·근거·전량을 payload 에 요구하지 않는다」는 갈라지면 안 된다.**

## 2. 결과물의 모양

### 2.1 payload

절 번호와 제목은 **전부 불변**이다(§0–§7). `SECTIONS` 상수를 건드리지 않는다.

| 자리 | 바뀜 |
|---|---|
| frontmatter `user_sourced_items` | `STATEMENT_MAX` **삭제**. 항목 필드·파서 형식 불변 |
| §0 한눈에 / §1 Goal·Non-goal / §3 Open Questions | 불변 |
| §2 제약 | 문법 불변(`- 🗣 confirmed **C1** — <statement> ⟨S2⟩`), 길이 자유 |
| §4 External Landscape | `<요지> «<출처키>» — "<직접인용 1문장>" — [취함\|피함\|중립] — <이유>`. **외부 URL 없음** |
| §5 기각 · Blind Spots | 판정 한 줄 + `verdict: <token>` + `ST<N>`. **외부 URL 없음**, 긴 서사 없음 |
| §6 사용자 원문 | **`S1` 하나만** |
| §7 Next Action | 하류의 경로 분류를 선점하지 않는 문면 |

### 2.2 audit

5절 → **7절**. 신설 절은 **뒤에 덧붙인다** — 앞에 끼우면 `AUDIT_SECTIONS` 번호가 밀려
`coverage_ledger_failures()` 가 조용히 빈 문자열을 읽는다(그 함수가 주석으로 경고하는 함정).

| 절 | 내용 |
|---|---|
| §1–§5 | Coverage Ledger / Budget / Steelman 원문 / 게이트 실행 기록 / 프로세스 로그 — 불변 |
| **§6 사용자 원문** (신설) | `S1` 제외 전량. **append-only**. `check_verbatim_coverage.py` 의 대조 대상 |
| **§7 확산 원자료** (신설) | landscape URL(출처키와 짝지어) · web sweep 전문 · blind-spot premortem 전문 |

**「확정 원장」 절은 만들지 않는다.** SUPERSEDED 는 전 리포에서 실체가 YAML 인라인 주석 한 곳
뿐이고 기제도 게이트 검사도 없다. 없는 기제를 위해 필수 절을 파는 것은 §3 이 채택한 원칙
(존재 검사가 산출물을 양식으로 만든다)의 정면 위반이다. 재결정 이력은 payload §5 의 `재결정`
항목과 audit §5 프로세스 로그가 이미 나른다.

### 2.3 「외부 URL」의 경계

경계는 **두 축**이다 — 「무엇이 URL 인가」와 「누가 썼는가」.

**축 1 — `https?://` 만 나간다.** `check_brief.py:450` 같은 리포 내부 `file:line` 참조는 payload 에
남는다. `compression.md` 가 링크를 깎는 이유는 *"링크가 권위로 읽혀 하류를 끌고 가는 것"* 인데,
리포 경로는 외부 권위가 아니라 **고칠 대상을 가리키는 손가락**이고 하류가 실제로 열어야 하는
것이다. `check_seed.py` 의 URL 검사도 같은 경계를 쓴다(`URL_RE = re.compile(r'https?://')`).

**축 2 — 모델이 저술한 것만 나간다. §6 사용자 원문은 예외다.**

이 예외가 없으면 게이트가 **동시 만족 불가능**해진다. §2.1 이 `S1`(최초 요청 **원문**)을 payload
§6 에 남기고, `check_verbatim_coverage.py` 의 L2 는 정규화 후 그 항목이 state 의 `text` 를
**포함**할 것을 요구하는데, `normalize()` 는 `[텍스트](url)` 형태의 마크다운 링크만 벗기고
**맨 URL 은 남긴다**. 사용자의 최초 요청에 맨 URL 이 하나만 있으면 — payload 에 남기면 N1a 가
red, 지우면 L2 가 `not_contained` exit 1. 유일한 탈출로인 P21 `<REDACTED>` 치환은 보안 컨트롤을
URL 세탁에 쓰는 것이고, 그 statement 의 L2 를 advisory 로 강등시킨다.

**예외가 정당한 이유는 편의가 아니다.** URL 을 깎는 근거(*"링크가 권위로 읽혀 하류를 끌고
간다"*)는 **모델이 web sweep 으로 가져온 링크**를 겨눈다. 사용자가 자기 요청에 직접 쓴 URL 은
사용자가 하류에 전하려 한 것이고, 그것을 지우는 것은 압축이 아니라 **원문 훼손**이다. §6 은
전문 보존 구역이라 애초에 압축의 대상이 아니다.

그래서 N1a 의 코퍼스는 **payload 에서 §6 을 뺀 나머지**다. §6 안의 URL 은 세지 않는다.

**이 예외는 기계로 봉해지지 않은 통로를 하나 연다 — 기록한다.** L2 는 **containment**(`want in
have`)라 payload §6 의 `S1` 본문이 state 의 원문보다 **더 많이** 담아도 통과한다. 그래서 landscape
URL 하나를 `S1` 에 덧붙이면 N1a(코퍼스 제외) · N1b(앵커 집합 불변) · L2(포함) 를 **전부** 통과한다.
막는 것은 `reviewing-brief` 의 「§6 기존 항목 본문 변경 금지」 규범 하나뿐이고 기계 집행이 없다.
§3.4 ① 기각의 대가(«키» 미해석)를 §10 에 적은 것과 **같은 취급**이며, §10 에 함께 적는다.

## 3. 게이트 — 부재와 존재

### 3.1 배치 전수표

16 → **19**.

| # | 검사 | 오늘 코퍼스 | 바뀜 |
|---|---|---|---|
| 1 | `find_missing_sections` (payload) | payload §0–§7 | 불변 |
| 2 | `frontmatter_errors` | payload fm | 불변 |
| 3 | `user_sourced_errors` | payload fm | `STATEMENT_MAX` 검사만 삭제 |
| 4 | `confirmed_zero_unsentineled` | payload fm | 문구 교정(§9) |
| 5 | `bijection_c_errors` | payload fm ↔ payload §6 | **교차화** — 앵커 집합 = payload §6 **∪** audit §6. **단방향은 그대로 유지한다**: 「모든 `evidence: S<N>` 이 해석된다」만 요구하고 역방향(모든 앵커가 인용될 것)은 요구하지 않는다. 이 단방향성 덕에 audit §6 전량이 인용 의무로 끌려오지 않는다 — 「bijection 이니 양방향이겠지」로 구현하면 안 된다 |
| 6 | `attribution_block_missing` | payload §6 | **이사** — 대상이 audit §6 |
| 7 | `bijection_b_errors` | payload §2 ↔ payload fm | 불변 (단일 파일 유지) |
| 8 | `resolve_audit` | payload fm → 경로 | 불변 |
| 9 | `find_missing_sections` (audit) | audit §1–§5 | **§6·§7 추가** |
| 10 | `audit_pairing_errors` | payload fm ↔ audit fm | 불변 |
| 11 | `bijection_a_errors` | payload §5 ↔ audit §3 | 불변 (이미 교차) |
| 12 | `landscape_present` | payload §4 | **sentinel 경로를 조인다**(§3.2) |
| 13 | `landscape_uncited` → `landscape_unkeyed` | payload §4 | **술어만 바꾸고 ∀ 는 유지한다** — 항목마다 URL 대신 «출처키» 를 요구한다. URL 요구는 N2 로 간다 |
| 14 | `skepticism_malformed` | payload §5 | **URL 요구만 삭제.** verdict·statement·ST 요구는 유지 |
| 15 | `tried_discarded_ok` | payload §5 | 불변 |
| 16 | `coverage_ledger_failures` | audit §1 | 불변 |
| **N1a** | `payload_url_free` **(신설·부재)** | payload 중 **모델이 저술한 부분** | 외부 URL(`https?://`) 0개. **§6 사용자 원문은 명시 예외**(§2.3) |
| **N1b** | `payload_verbatim_is_s1_only` **(신설·등식)** | payload §6 | 앵커 집합 **== `{S1}`** |
| **N2** | `landscape_keys_declared` **(신설·교차)** | payload §4 → audit §7 | **payload §4 의 «출처키» 집합 ⊆ audit §7 이 선언한 키 집합.** 공집합은 자동 만족 |

**N1 을 두 축으로 갈라 적는 이유.** 「외부 URL 0개」는 **부재** 술어이고 「§6 == `{S1}`」은
**등식** 술어다. 한 이름으로 묶으면 §3.2 의 양성 짝 논증이 어느 축에 걸리는지가 흐려진다 —
양성 짝이 필요한 것은 **N1a 뿐이다**. N1b 는 스스로 양성이다: §6 을 비우면 `∅ ≠ {S1}` 이라
N1b 자신이 red 를 낸다.

**`⊆` 가 아니라 `==` 다.** `⊆ {S1}` 로 쓰면 빈 §6 이 통과하고, 그때 이를 잡아 줄 것으로 기대할
#5 는 **항목이 0건인 payload 에서 공허하다**(§3.2). `==` 로 못 박아 그 구멍을 닫는다.

**audit §6 에 「비어 있지 않다」 형태 검사를 새로 두지 않는다.** 그런 검사는 출하 템플릿의
placeholder 로 충족되므로 실brief 를 막지 못하면서 T-TPL 만 깬다 — 얻는 것 없이 잃기만 한다.

그 대신 **이미 있는 세 검사가 무엇을 술어로 갖는지 정확히 적는다.** 앞 판본이 여기서 「둘 다
내용을 대조한다」고 썼는데 **거짓이었다** — 셋 중 내용을 보는 것은 하나뿐이다.

| 검사 | 술어 | 언제 도는가 | 무엇을 못 잡나 |
|---|---|---|---|
| **#5** `bijection_c_errors` | **인용된 `evidence:` id 의 앵커 존재** (부분집합) | **게이트** | 모든 항목이 `S1` 만 인용하면 audit §6 이 통째로 비어도 통과 · 부분 이관에서 인용 안 된 발화 |
| **L1** (`check_verbatim_coverage`) | **state 원장 id 전량의 앵커 존재** | **게이트 밖** — 리뷰 진입과 재리뷰 | state 부재·파싱 실패·발화 0건이면 **exit 3(degrade 후 계속)** |
| **L2** (같은 스크립트) | **원문 내용의 containment** — 셋 중 유일한 내용 검사 | 게이트 밖 | 초과 담기(§2.3) · P21 토큰이 걸리면 exit 3 |

**따라서 「전량이 옮겨졌는가」를 게이트 시점에 확인하는 것은 원리적으로 불가능하다** — 무엇이
사용자 발화 전량인지는 state 원장만 알고, 게이트는 state 를 받지 않는다. `check_verbatim_coverage.py`
가 별도 스크립트로 존재하는 이유가 그것이다. 이 사실을 §10 에 gap 으로 적는다.

**N2 는 존재 검사가 아니라 조건부 교차 검사다.** 「audit §7 이 비어 있지 않다」로 두면 갓 만든
audit 도, 웹이 꺼진 audit 도 red 가 된다. 대신 **payload 가 landscape 를 실었다는 사실을 조건으로**
건다 — payload §4 에 항목이 있다는 것은 sweep 이 실제로 있었다는 뜻이고, 그러면 그 원자료가
audit §7 에 있어야 한다.

**개수가 아니라 «집합»인 이유 — 개수는 세 번 틀린다.**

| 형상 | 개수 결속(`≤`)이면 | 집합 포함(`⊆`)이면 |
|---|---|---|
| web-off brief (§4 에 URL 없는 항목 1건 — 리포 픽스처의 실제 형상) | `1 ≤ 0` → **RED** | 키가 없으면 공집합 ⊆ 무엇이든 → **통과** |
| 두 §4 항목이 **같은 출처**를 인용 | `2 ≤ 1` → **RED** | 집합이라 중복이 접힌다 → **통과** |
| §7 이 sweep 을 **산문 전문**으로 적음 | 「항목」의 계수 단위가 미정 → 집행 불가 | 선언된 **키**만 세므로 산문 형태와 무관 |

이 리포가 같은 판단을 이미 했다 — `bijection_a_errors` 의 docstring: *"개수 비교가 아니라 **id
집합 비교**다. 실제 steelman 항목은 다단락 블록이지 단일 불릿이 아니어서 «무엇을 한 항목으로 셀
것인가»가 미정이고, 그러면 집행이 불가능하다."* §7 도 전문 구역이라 같은 조건이다.

**§3.4 ① 재결정 (P23).** 그 절은 「payload 각 항목의 출처 «키» 가 audit 에서 실제로 해석되는지까지
검사한다」를 **기각**했다. 이 N2 는 그 기각을 **부분적으로 뒤집는다** — 키 집합의 **포함 관계**는
검사하되 「어느 키가 어느 원자료인가」는 여전히 검사하지 않는다. 뒤집는 근거: 그 기각의 이유는
「bijection 을 늘리면 결함이 대상만 옮겨 재발한다」였는데, 더 약한 술어(∃ · 개수)를 두 번 시도해
**두 번 다 정당한 형상을 red 로 만들었다.** 약한 술어가 더 안전하다는 전제가 반증됐다.

**web kill switch 로 완화할 필요가 없다** — 조건이 구조적으로 면제한다. 완화를 코드로 넣으면
스위치 소비자가 늘고 그 공시 문면이 또 낡는다.

**그리고 N2 는 payload↔audit 교차 검사다** — C13 이 요구한 모양이 여기서 실제로 성립한다.
§3.4 ① 이 기각한 것은 **키 동일성 해석**(각 키가 audit 에서 풀리는가)이고, N2 는 그보다 훨씬 약한
**존재 결속**(landscape 를 실었으면 원자료도 실어라)이다. 둘은 다른 검사다.

**출하 템플릿 쌍이 새 게이트를 통과해야 한다 — 그러나 이 설계는 그 결과를 미리 판정하지 않는다.**

`test_check_brief.sh` 의 T-TPL 이 *"shipping 되는 템플릿 쌍은 자기 게이트를 통과해야 한다"* 를
단언하고 그 주석이 실제 사고를 기록한다(*"게이트가 첫 인터뷰마다 거짓 오류 벽을 내던 실제 결함"*).
그러므로 **템플릿 쌍이 통과하는 형태를 찾는 것은 구현의 의무**이고, §8 의 **I9** 가 그것을
관측으로 만든다.

**이 설계가 템플릿 결과를 산문으로 예측하지 않는 이유는 실측이다** — 앞 판본들이 세 라운드 연속
예측했고 세 번 다 틀렸다. 「예시 불릿을 두지 않는다 → 통과」(틀림, T-TPL 이 깨졌다) → 「placeholder
를 실으면 통과」(틀림, §6 금지가 `evidence: S2` 를 dangling 시켰다) → …. **결과를 예측하는 문장은
검증되지 않은 채 문서에 사실로 박히고, 다음 라운드의 결함이 된다.**

설계가 정할 수 있는 것은 **제약**이고, 여기 두 가지가 있다:

- **audit §6 의 placeholder 는 `S<숫자>` 형태의 앵커를 갖지 않는다.** 앵커 정규식이 양쪽 다
  `S\d+` 를 요구하므로 메타변수 표기(`**S<N>**`)는 애초에 앵커가 아니고, 구체 숫자를 쓰면
  실제 앵커 집합에 들어가 실brief 의 원장 대조를 오염시킬 수 있다. **메타변수 표기를 쓴다.**
- **placeholder 치환 토큰은 P21 패턴(`<REDACTED>`·`<PLACEHOLDER>` 류)을 쓰지 않는다.** 그 앵커가
  실brief 의 원장 id 와 일치하는 경우에 한해 L2 를 위반 대신 exit 3(판정 불가)로 강등시킨다 —
  좁은 경로지만 피하는 데 드는 비용이 0 이다.

**placeholder 관례 자체는 이 리포의 확립된 것이다** — 오늘
audit 템플릿의 `- floor:root_problem — closed — <evidence>` 와 payload 템플릿의
`- ... — https://example.com — [취함] — 이유` 가 정확히 그 형태이고, `test_check_brief.sh` 의
T-TPL 이 *"템플릿은 placeholder 를 싣고 출하되고 … 그게 정상이다"* 라고 주석으로 못 박고 있다.
**형태 검사는 placeholder 가 충족시키고, 진짜 이빨은 내용 대조가 낸다.**

**동반 변경 — `check_verbatim_coverage.py`.** 코퍼스가 `state ↔ payload §6` 에서
`state ↔ (payload §6 ∪ audit §6)` 이 된다. **#5 와 같은 합집합 규칙을 쓴다** — `S1` 은
payload 에, `S2` 이상은 audit 에 있으므로 한쪽만 보면 반대쪽 전량이 「없는 원문」이 된다.

이 스크립트는 오늘 `<payload> <state>` 2인자다. **audit 을 3번째 인자로 명시 전달한다** —
유추(stem 유도·frontmatter 추적)를 쓰지 않는다. 두 컴포넌트가 상반된 규칙을 갖는 것처럼 보이는
것을 여기서 정리한다:

| 층 | 규칙 | 이유 |
|---|---|---|
| `check_brief.py` 의 `resolve_audit()` | **유도한다**(`<stem>.audit.md` 만 받는다) | 이것은 audit 을 *찾는* 것이 아니라 payload 가 **어느 audit 을 자기 것이라 부를지 고르지 못하게** 거절하는 것이다. 유도는 제한이다 |
| 번들 빌더 · `check_verbatim_coverage.py` | **유추하지 않는다**(경로를 인자로 받는다) | 재료를 어디서 가져올지의 유추는 실패했을 때 **조용하다** — 잘못된 재료로 검증을 태우는 것이 없는 것보다 나쁘다 |

`parse_payload_section6` 은 `## 6.` 이 없으면 `ParseError` 를 던진다. 합집합 구현은 **양쪽 절이
각각 없을 수 있음**을 다뤄야 한다(payload §6 은 항상 있고 audit §6 은 N2 가 보장하지만, 게이트
순서상 이 스크립트가 먼저 도는 경로가 있다) — 한쪽 부재를 조용한 코퍼스 축소로 처리하면
「원문 완전성 통과」가 거짓이 된다.

**append-only 의 기계 집행이 코퍼스를 따라간다.** 오늘 payload §6 의 append-only 는 규범만이
아니라 이 스크립트가 기계로 집행한다(앵커 중복 → 구조 위반 exit 1 · L2 원문 포함 검사).
코퍼스가 합집합이 되면 그 집행도 합집합 위에서 돌아야 한다 — **`S5` 가 payload 와 audit 양쪽에
있으면 중복 위반**이다. 이것을 명시하지 않으면 §5.3 이 권한 표의 행(규범)만 옮기고 기계 집행은
payload 에 남아, §5.1 이 비판한 「규범으로만 성립」 상태를 이 설계가 스스로 만든다.

### 3.2 이빨 — 부재 락의 양성 짝

**양성 짝이 필요한 것은 N1a 하나다.** N1a 는 부재 술어라 **대상 절을 통째로 지우면 공허하게
통과**한다. 그것을 막는 것은 N1a 자신이 아니라 이미 있는 세 검사다.

| 우회 시도 | 막는 검사 |
|---|---|
| §4 절 통째 삭제 | #1 `find_missing_sections` |
| §4 헤딩만 두고 항목 전부 삭제 | #12 `landscape_present` |
| §5 기각 항목 전부 삭제 | #15 `tried_discarded_ok` |

**셋 중 하나라도 빠지면 N1a 는 삭제로 우회된다.** 이 관계를 §7.1 이 mutation 으로 고정한다.

**N1b 는 이 표의 대상이 아니다.** 등식 술어라 스스로 양성이다 — §6 을 비우면 `∅ ≠ {S1}` 이라
N1b 가 직접 red 를 낸다. 이 자리를 #5 `bijection_c_errors` 에 귀속시키면 **틀린 귀속**이 되고,
잘못 귀속된 RED 는 통과보다 나쁘다: mutation 이 초록/빨강만 보고 어느 검사가 물었는지를 오인해,
정작 그 검사를 지워도 매트릭스가 여전히 RED 를 낸다.

**#5 가 §6 축을 방어하지 못하는 경우는 하나뿐이고, 그 하나가 결정적이다.**
`bijection_c_errors` 는 `evidence:` 필드를 가진 항목만 순회한다. `evidence` 는 **필수 필드**이므로
(`check_brief.py:306` 의 `REQUIRED_ITEM_FIELDS`, `test_check_brief.sh:391–401` 이 그 RED 를
message 까지 단언) 항목이 하나라도 있으면 이 순회는 비지 않는다.

공허해지는 것은 **항목이 0건일 때**다. `user_sourced_errors` 는 `user_sourced_items` **키의
부재**만 red 로 내고, 키가 있는데 항목이 0건이면 루프가 돌지 않아 통과한다(sentinel 이 있으면
`confirmed_zero_unsentineled` 도 통과). 그 상태에서 #5 는 공집합을 순회하고 §6 을 비워도 아무도
막지 않는다 — **N1b 의 등식만이 막는다.**

**그 상태를 시험하는 픽스처가 리포에 없다.** §7.2 가 신설한다. 픽스처 없이 `==` 를 쓰면 결론만
옳고 근거도 커버리지도 없다.

**`landscape_present()` 의 sentinel 경로를 조인다.** 오늘 이 함수는 §4 본문에
`N/A`·`비활성`·`생략`·`web-disabled` 중 한 단어만 있어도 `True` 를 낸다. 오늘은 URL 요구가
그것을 덮어서 무해했으나, N1 체제에서는 이것이 **N1 의 공허 우회로를 여는 유일한 문**이 된다
(§4 에 "생략" 한 단어만 쓰면 URL 도 항목도 없는 payload 가 통과). sentinel 경로를
`DEVBREW_SPEC_DISTILL_DISABLE_WEB=1` 일 때만 인정하도록 좁힌다.

### 3.3 `_web_disabled()` 의 이사

| | 오늘 | 이후 |
|---|---|---|
| **완화하는 것** | payload §4 인용 요구 + payload §5 verdict URL 요구 (**둘**) | **하나** — #12 의 sentinel 경로뿐. §3.2 의 조임이 만든 그 자리다 |
| payload URL 금지(N1a) | (없음) | **완화하지 않는다** |
| payload §4 «키» 요구(#13) | (없음) | **완화하지 않는다** — 웹이 꺼져도 출처를 말로 댈 수 있다 |
| audit §7 결속(N2) | (없음) | **완화 대상이 아니다** — 술어가 «키» 집합의 포함이라, 웹이 꺼져 URL·키가 없으면 **공집합 ⊆ 무엇이든**으로 자동 만족된다. 리포의 실제 web-off 형상(§4 에 URL 없는 항목이 **있는** 상태)에서도 그렇다 |

**공시 문면이 이 셋을 정확히 말해야 한다.** `WEB_DISABLED_ADVISORY` 는 오늘 「§4 인용 요구 + §5
verdict URL 요구가 완화됨」이라 적는데, 이관 후에는 그 둘 다 존재하지 않는다. **완화 범위를
잘못 적은 공시는 없는 것보다 나쁘다** — 보안 컨트롤이 일어나지 않은 완화를 일어났다고 보고하는
것이고, 그 문면을 잠근 기존 락은 문면이 틀려도 GREEN 을 유지한다. §7.1 이 이 자리에 행을 둔다.

N1a 를 완화하지 않는 근거는 `check_seed.py` 의 URL 검사 주석이 이미 적었다 — *"web kill switch
와 무관하다. 웹이 꺼져 있어도 금지는 유지된다 — 완화할 대상이 애초에 없다."* 웹이 꺼졌다고
payload 에 URL 을 넣을 이유가 생기지 않는다.

**정정 — 이것은 순수한 「이사」가 아니다.** 오늘 `landscape_uncited()` 는 **∀**(payload §4 의
*모든* 항목이 URL 을 가져야 한다)이고, N2 는 **∃**(audit §7 에 URL 항목이 *하나라도* 있으면
된다)다. 둘을 그대로 맞바꾸면 인용 없는 payload §4 항목 여덟 개 + audit URL 한 개가 통과한다 —
강도 하락이다. 그래서 **∀ 는 payload 쪽에 남긴다**: #13 이 `landscape_unkeyed` 로 바뀌어
항목마다 «출처키» 를 요구한다(∀ 보존). audit 으로 가는 것은 **URL 이라는 술어뿐**이고, 그
술어는 ∃ 로 약해진다 — 「sweep 이 실제로 있었다」의 존재 증거로만 쓴다.

**그래도 남는 손실이 있고, 여기에 적는다.** payload §4 의 «출처키» 가 audit §7 에서 실제로
해석되는지는 **아무 게이트도 묶지 않는다.** 키를 지어내도 통과한다. 이것을 묶는 것이 §3.4 ① 의
교차 bijection 이고 그것을 기각했으므로, 그 대가가 이 한 줄이다. §10 에도 같은 항목으로 남긴다.

**내구성 — 조임(§3.2 의 `landscape_present` sentinel)은 환경 의존을 하나 새로 만든다.**
`_web_disabled()` 는 게이트를 *실행하는 프로세스의* 환경변수를 읽는데, 오늘 `landscape_present()`
는 환경과 무관하다. 조임 이후에는 web-off 로 저술된 brief 가 훅·재리뷰·다른 세션에서 게이트를
다시 탈 때 그 환경변수 없이 **RED** 가 되고, 그 사실이 아티팩트 어디에도 없다. audit §4 게이트
실행 기록이 이미 exit code 를 적고 있으므로 **거기에 web-disabled 사유를 함께 남긴다** — 저술
시점의 환경을 아티팩트가 나르게 해서, 나중 실행이 자기 환경으로 남의 brief 를 판정하지 않게 한다.

### 3.4 검토한 대안 둘

**① 교차 bijection 신설** — payload 각 항목의 출처 «키» 가 audit 에서 실제로 해석되는지까지
검사한다. 가장 강한 보장이지만 bijection 이 3 → 5 로 늘고, 게이트가 ~20 이 된다. 채택하지
않은 이유: 이 리포에 이미 세 개의 「같은 것을 두 곳에 손으로 적어서 생긴 감시 장치」가 있고,
재구조화가 그것을 늘리는 방향이면 결함이 대상만 옮겨 재발한다. seed 는 같은 문제를 bijection
**없이** 푼다.

**② 정본 1파일 + 분할 생성기** — 모델이 정본 하나만 쓰고 스크립트가 payload·audit 을 생성한다.
드리프트가 구조적으로 불가능해지고 게이트가 전부 단일 파일로 돌아온다. 채택하지 않은 이유:
(a) §0·§1·§3 은 저술물이라 생성 불가여서 「정본」이 사실상 두 파일의 합본이 되고, (b) 생성기가
새 load-bearing 부품이 되며 그 버그는 조용하고, (c) 리포 안에 레퍼런스가 없다. **기각이지
미평가가 아니다** — 인터뷰의 OQ7 은 이로써 닫힌다.

## 4. 번들 빌더와 리뷰 층

**문제** — 충실도 축에 리뷰어가 둘인데 서로 다른 재료를 본다. `brief-critic` 은
`build_brief_inline_blob.py` 의 blob 을 inline 으로 받고, codex 쪽은
`build_brief_codex_prompt.py:95` 가 `payload_path.read_text()` 로 파일을 직접 읽는다. §6 이
audit 으로 가면 둘 다 대조 대상을 잃고 「fail-closed 합집합」의 보장이 사라진다.

**해법** — `build_seed_inline_blob.py` 의 **구조**를 이식한다: 명시적 경로들을 받아 번들 하나를
조립하고, **그 번들을 codex 러너의 `<payload>` 인자로 그대로 넘긴다.** docstring 이 이유까지 적어
두었다 — *"조립 로직이 두 소비자에 각각 따로 있으면 한쪽만 고쳐질 때 두 리뷰어가 다른 재료를
보는 drift 가 생긴다."*

**이식하는 것은 구조이지 그 파일의 실패 처리 정책이 아니다.** `build_seed_inline_blob.py` 는
원문 절을 찾지 못하면 **stderr 로 경고하고 그대로 조립한다**(86–88줄) — fail-open 이다. 여기서는
그 정책을 채택하지 않는다: 아래 rc 표대로 **rc 2 · 무디스패치**다. 이 문단이 없으면 지목된
레퍼런스를 그대로 따른 구현이, 이 설계가 닫으려는 바로 그 fail-open(*"원문 없이 충실도를 물으면
「왜곡 없음」이 나온다"*)을 재생산한다.

**빌더는 둘이다. 기존 것을 대체하지 않는다.** `build_brief_inline_blob.py` 는 `reviewing-brief`
SKILL 에서 **critic 축과 readback 축 둘 다**에 쓰인다. 하나로 대체하면 냉독까지 번들을 받아
아래 표가 주장하는 수정이 통째로 뒤집힌다. 지점은 §8 도출 규칙 ① 로 찾는다.

```
build_brief_bundle.py <payload> <audit>      ← 신설 (payload + audit §6)
        ├──▶ brief-critic (tools: [] — inline)
        └──▶ run_brief_codex_reviewer.sh fidelity <bundle>

build_brief_inline_blob.py <payload>          ← 기존, 계약 불변 (payload-only)
        └──▶ brief-readback (tools: [] — inline)
```

**호출 지점은 §8 의 도출 규칙 ① 로 정한다 — 이 문서는 열거하지도 줄 번호를 적지도 않는다.**
축의 이름만 남긴다:

- **번들을 받는 축** = `run_brief_codex_reviewer.sh` 를 **`fidelity`** 로 부르는 지점 전부 +
  `brief-critic` 을 dispatch 하는 지점 전부. 재리뷰 라운드가 dispatch 를 **리터럴로 반복하지
  않고 앞 블록을 참조**할 수 있으므로, 도출은 리터럴 개수가 아니라 **그 블록이 실행되는 경로**를
  세야 한다.
- **payload-only blob 을 유지하는 축** = `brief-readback` 을 dispatch 하는 지점 전부.
- **대상이 아닌 축** = `run_brief_codex_reviewer.sh` 를 **`direction`** 으로 부르는 지점. 그
  리뷰어는 도구를 갖고 스스로 audit 을 연다.

이 축을 하나라도 빠뜨리면 재리뷰 라운드의 codex 가 원문 없는 payload 를 계속 받아, 이 절이
닫으려는 fail-open 이 되살아나고 `reviewing-brief` SKILL 의 *"codex #2 는 항상 최종 문서를
본다"* 가 거짓이 된다.

**번들만 바꾸는 것으로는 부족하다 — codex 가 읽는 «지시문» 도 같이 바뀐다.**
`scripts/brief-codex-fidelity-checklist.md` 는 codex 프롬프트에 그대로 실려 *"The ground truth
is §6 사용자 원문"* 과 *"Every finding MUST quote the §6 anchor"* 를 지시한다. 이 문면을 두면
codex 는 **payload §6**(= `S1` 하나)을 원문으로 알고 판정한다 — 번들에 audit §6 을 넣어도
소용없다. **fidelity 체크리스트**의 「§6」이 **번들이 싣는 audit §6** 을 가리키도록 고친다.
같은 클래스의 다른 자리(예: critic agent 정의의 ground-truth 문장)는 §8 도출 규칙 ② 가 잡는다.

**단, 축을 공유하는 문면은 「번들의 audit §6」으로 고치면 안 된다.**
`build_brief_codex_prompt.py` 의 프롬프트 템플릿에 있는 **비신뢰-verbatim 경계 문장은 두 축이
함께 쓴다**(축마다 달라지는 것은 체크리스트 파일뿐이다). direction 축은 번들이 아니라 raw
payload 를 받으므로, 그 문장을 audit §6 만 가리키게 고치면 direction 프롬프트가 자기 문서에 없는
절을 가리키게 되고 **실제로 그 문서에 있는 비신뢰 원문(payload §6 의 `S1`)에서 injection 경계
표시가 사라진다.** 그렇다고 그대로 두면 반대쪽이 샌다 — 아래 「두 §6 을 라벨로 가른다」가 그
해법이다: **두 축 모두에서 참이면서 두 위치를 함께 덮는 문면**으로 고친다.

**번들 안에서 두 §6 을 라벨로 가른다 — 이것이 이 절의 전제다.** payload §6 과 audit §6 은
**번호도 제목도 같다**(`## 6. 사용자 원문`). 그냥 이어 붙이면 한 문서에 같은 헤딩이 둘이라
「번들의 §6」이 무엇을 가리키는지 정해지지 않고, 먼저 나오는 것은 `S1` 하나짜리 payload §6 이라
이 절이 닫으려는 fail-open 이 그대로 남는다.

형제 `build_seed_inline_blob.py` 의 `assemble()` 이 **재료마다 라벨을 붙인다**는 구조를 이식한다.
다만 **그 파일의 라벨 형태는 그대로 쓸 수 없다** — 형제는 라벨을 `## ` 마크다운 헤딩으로 다는데,
seed payload 는 메시지형이라 절이 없어서 충돌하지 않는 반면 **brief payload 는 자기
`## 6. 사용자 원문` 을 갖는다.** 형제를 문자 그대로 이식하면 이 절이 닫으려는 동명 충돌이
그대로 재생산된다. 구조를 이식하되 형태는 이 문서가 정한다. 세 가지를 못 박는다:

**(ㄱ) 라벨 토큰은 마크다운 헤딩이 아니다.** 헤딩이면 payload 자신의 절 헤딩들과 같은 네임스페이스에
들어가 「몇 번째 `##` 인가」가 다시 문제가 된다.

```
<<<PAYLOAD>>>
…brief payload 전문 (frontmatter 3키 redact)…
<<<AUDIT-VERBATIM>>>
…audit §6 의 항목 전량 (S1 제외)…
```

**(ㄴ) 실린 절의 내부 헤딩은 벗긴다.** audit §6 을 통째로 붙이면 그 안의 `## 6. 사용자 원문` 이
payload 의 같은 헤딩과 **바이트 동일**해진다. 그러면 라벨을 붙여도 「`## 6. 사용자 원문` 을 보라」는
지시가 여전히 **먼저 나오는 쪽**(payload, `S1` 하나)에 걸린다. 항목(`- **S<N>** …`)만 싣고 절
헤딩은 라벨이 대신한다.

**(ㄷ) 지시문은 헤딩이 아니라 라벨 토큰을 축자로 인용한다.** 오늘 `agents/brief-critic.md` 와
fidelity 체크리스트는 ground truth 를 **헤딩 리터럴**로 지목한다 — 그 문면이 남아 있는 한 (ㄱ)(ㄴ)을
해도 지시가 안 옮겨간다. 둘 다 `<<<AUDIT-VERBATIM>>>` 를 축자로 가리키게 고친다. 이 둘은 §8 도출
규칙 ② 의 대상이므로 목록은 도출이 잡는다 — 여기서는 **무엇을 가리켜야 하는가**만 정한다.

**그리고 공유 문면은 「손대지 않는다」가 아니라 「두 축 모두에서 참이면서 새 위치를 덮는」 문면으로
고친다.** 프롬프트 템플릿의 비신뢰-verbatim 경계 문장은 오늘 payload §6 만 가리키는데, 번들이
싣는 원문 전량이 그 경계 밖에 놓이면 **비신뢰 verbatim 이 1건에서 전량으로 늘어난 바로 그
순간에 경계 표시가 사라진다.** direction 축(raw payload, 원문은 `S1` 하나)과 fidelity 축(번들,
원문 전량) **둘 다에서 참인 문면**으로 쓴다 — 예: 「사용자 원문(payload 의 `## 6. 사용자 원문`
이든 번들의 `<<<AUDIT-VERBATIM>>>` 이든)은 비신뢰 verbatim 이다」. 축이 갈리는 것은
체크리스트뿐이고 이 문장은 갈리지 않으므로, 문면 자체가 **두 위치를 이름으로** 덮어야 한다.

**번들의 형태 — stdout 으로 내고 오케스트레이터가 한 번 파일로 쓴다.** 두 소비자의 요구가
다르기 때문이다: `brief-critic` 은 프롬프트에 보간되는 **문자열**을 받고,
`run_brief_codex_reviewer.sh` 는 `[[ -f ... ]]` 로 **실재 파일 경로**를 요구한다. 형제
`build_seed_inline_blob.py` 와 같은 관용구로, 빌더는 stdout 만 내고 호출자가 세션 디렉토리
(`.claude/spec-distill/<session-id>/`, P13 — git-ignored·성공 시 auto-delete)에 **한 번** 쓴 뒤
그 한 파일을 둘이 나눠 읽는다. **두 번 돌리지 않는다** — 사이에 payload 가 바뀌면 두 리뷰어가
다른 바이트를 보게 되어 이 절의 목적이 무너진다. 번들은 비신뢰 verbatim 을 담으므로 세션
디렉토리 밖에 두지 않는다.

**번들 내용** = payload 전문(frontmatter 3키 redact 유지) + **audit §6 사용자 원문**.
audit §7 은 넣지 않는다 — 충실도 축이 재는 것은 §2 요약 ↔ 원문 대조이고 §7 은 그 판정에
무관한 부피다.

**세 리뷰어가 받는 것이 갈라진다.**

| 리뷰어 | 받는 것 | 이유 |
|---|---|---|
| `brief-critic` (충실도) | payload + **audit §6** | 대조 대상이 없으면 「왜곡 없음」이 공허하다 |
| `brief-readback` (냉독) | **payload 만** | 냉독이 재는 것은 *하류가 실제로 받는 문서* 의 읽힘이다 |
| `brief-direction-reviewer` (방향성) | 경로(도구 보유) | 불변 — 스스로 audit 을 연다 |

**오늘 냉독은 하류가 절대 보지 않을 문서를 재고 있다.** payload 에 §6 전량이 있으므로 냉독의
「이해된다」는 원문을 함께 읽고 내린 판정이다. 이 변경으로 냉독이 처음으로 정확한 것을 잰다.

**번들 빌더의 종료 코드** — 기존 표(0/2/3)에 사유가 하나 는다.

| rc | 뜻 | 호출자 동작 |
|---|---|---|
| 0 | 정상 | dispatch |
| 2 | payload 부재·읽기 실패 | dispatch 하지 않는다 |
| **2 (신규 사유)** | **audit 부재·읽기 실패·§6 절 없음** | **dispatch 하지 않는다** — 원문 없이 충실도를 물으면 「왜곡 없음」이 나온다 |
| 3 | 위생 미달 | degrade 기록 후 계속 |

3번(`.audit.md` 문자열 잔존) 의 스캔 범위는 **payload 부분으로 한정**한다. 번들이 audit 내용을
의도적으로 싣게 됐으므로 전체를 스캔하면 정상 동작이 매번 exit 3 을 낸다.

**seed 빌더가 명시적으로 거부한 것을 그대로 물려받는다** — *"자동 유추(seed frontmatter 의
`audit_file:` 을 따라가기)는 하지 않는다."* 번들 빌더는 audit 경로를 **인자로** 받는다.
`resolve_audit()` 의 stem 유도와 왜 반대인지는 §3.1 의 「유도 vs 유추」 표가 한 곳에서 정한다 —
여기 다시 적지 않는다(두 곳에 적으면 갈라진다).

## 5. 핸드오프와 저술 규약

### 5.1 `finishing.md`

이 파일은 이 설계와 모순되는 저술 지시를 **여러 곳에** 담고 있다. **몇 곳인지는 이 설계가
세지 않는다** — §8 도출 규칙 ②·③ 이 잡는다. 앞 판본들이 「유일한」·「둘」이라고 센 것이 두 번
연속으로 반증됐고, 세는 행위 자체가 그 결함의 원인이었다.

고쳐야 하는 **종류**는 셋이다:

- **statement 의 분량 상한을 지시하는 곳** — `STATEMENT_MAX` 를 지우면 스킬이 게이트가 더는
  요구하지 않는 상한을 계속 지시하게 된다.
- **원문의 거처를 지시하는 곳** — 「`user_statements` 의 발화 **전부를 payload §6 에** 전문
  보존한다」 → 「`S1` 만 payload §6 에, 나머지 전량은 **audit §6** 에」.
- **게이트가 무엇을 집행하는지 서술하는 곳** — 「원문 보존은 요구인데 게이트 어디에도 이 요구가
  없어 아무것도 red 가 되지 않는다」는 서술과, 게이트 개수를 인용한 문장. **이 이관은 그 서술을
  참으로 만들지 않는다** — §3.1 술어표대로 「전량이 옮겨졌는가」는 게이트 시점에 여전히 확인되지
  않는다(§10 의 넷째 gap). 바뀌는 것은 **게이트 개수**와 **원문의 거처**뿐이므로 그만큼만 고친다.
  **이 자리는 도출 ①–④ 어느 규칙도 못 잡는다** — `§N` 도 절 제목도 파일 이름도 식별자도 없다.
  그래서 §7.1 이 그 문장에 락을 하나 걸어 ⑤ 가 찾을 수 있게 만든다.

> 오늘: `user_statements` 의 발화 **전부를 payload §6 에 전문 보존**하고 `S<N>` 앵커를 답니다.
> 이후: `S1` 만 payload §6 에, 나머지 전량은 **audit §6** 에 전문 보존한다(append-only).

`전문 보존` 이라는 문구는 전 리포에서 이 줄과 템플릿, 둘에만 있고 **이를 잠근 테스트가 없다.**
고치는 것은 공짜지만 고친 뒤의 규칙도 잠기지 않은 채 남으므로, §7.1 이 락을 하나 새로 단다.

**`S1` 의 배치와 번호 공식을 지시하는 부분은 문면이 불변**이다(`$ARGUMENTS` → `S1` → §6 맨 앞).
`S1` 이 payload 잔류 예외이므로 그 지시가 그대로 참이고, 그 문장을 리터럴로 잠근 기존 락들도
**GREEN 을 유지하며 그대로 옳다.**

**단, 무인자 분기에서는 그 근거가 성립하지 않는다.** `$ARGUMENTS` 가 없으면 `S1` 은 최초 요청이
아니라 **첫 사용자 답변**이다. 그러면 §2.1 이 `S1` 을
payload 에 남기는 근거(「최초 요청이 framing 이라 하류가 그것만은 봐야 한다」)가 그 분기에서는
성립하지 않는다. 동작은 깨지지 않으므로 이 설계는 그대로 가되, **payload 잔류 예외의 근거가
seed·인자 있는 호출에만 적용된다는 것을 명시**한다 — 무인자 인터뷰에서 `S1` 은 그냥 첫 답변이고,
그것을 payload 에 남기는 것은 규칙의 단순성 때문이지 그 내용이 특별해서가 아니다.

**233줄 `/compact` 리터럴** — 최소화한다.

> `/compact interview brief at <brief-path> — 이 경로와 아래 '재결정 규약' 문장만 유지하고,
> round-by-round 인터뷰 대화·web sweep 원문·steelman 중간 추론은 drop. 재결정 규약: confirmed
> 항목은 근거 있으면 보고 후 재결정 가능하고 임의 변경은 금지다. 다음 단계:
> Skill superpowers:brainstorming <brief-path>.`

절 이름 열거와 audit 경로 보존 명령을 뺀다. brief 는 디스크의 파일이고 하류가 다시 읽으므로
본문을 context 에 붙잡아 둘 이유가 없다. 방향성 리뷰가 지적한 *"「이름으로 보존 명령」이 C1 을
규범으로만 성립하게 만든다"* 가 이로써 사라진다.

### 5.2 `compression.md`

「오늘 이 계약을 게이트로 집행하는 것은 seed 뿐이다」 문단이 이 작업의 착지일에 거짓이 된다.
**같은 커밋에서** brief 도 채택했다는 사실과, 두 산출물의 차이(메시지형/문서형)가 어디서 오는지로
고쳐 쓴다.

### 5.3 관할 이동

인터뷰가 지목한 것(*"원문의 append-only 가드가 payload 편집 권한 표의 행이라, 원문이 audit 으로
가면 그 관할이 없어진다"*)은 **관할을 옮기면** 해소된다. 존재 이유(*critic 이 지적 → 원문을
지적에 맞게 고쳐 통과* 라는 laundering 차단)는 그대로다.

**§6 관할은 `reviewing-brief/SKILL.md` 한 곳이 아니라 여러 면에 걸쳐 있다.** 수정 권한 표만
옮기면 나머지가 payload 를 가리킨 채 남는다. 특히 위험한 것은 **닫힌 열거로 쓰인 「orchestrator
의 허용 행위」 목록**이다 — 닫힌 열거라 audit 파일 편집이 목록에 없으면 원문 append 가 규약상
금지된 채 남는다. 그리고 방향성 재결정 절차의 *"결정 발화를 §6 에 새 `S<N>` 으로 추가한다"* 도
목적지가 바뀐다.

대상은 열거하지 않는다 — **§8 도출 규칙 ②·③** 이 잡는다(`§6` 리터럴과 「원문은 payload 에
있다」류 서술을 담은 모든 파일).

**단, 관할 이동은 「전량 이동」이 아니라 「`S1` 잔류 예외를 따라가는 분할」이다.** payload §6 에는
`S1` 이 남으므로 **그 항목의 편집 권한 행도 payload 표에 남는다** — 「기존 항목 본문 변경 금지」가
바로 그 행이고, §2.3·§10 이 기록한 URL 통로를 막는 **유일한** 장치다. 관할을 통째로 audit 으로
옮기면 그 통로의 가드가 규범 차원에서도 0 이 된다. audit 표는 `S2` 이상의 append-only 를 맡고,
payload 표는 `S1` 의 불변을 맡는다.

**규범만 옮기면 안 된다 — 기계 집행이 함께 따라가야 한다.** 오늘 이 권한 표는 append-only 를
*선언*하고, 실제로 집행하는 것은 `check_verbatim_coverage.py` 다(앵커 중복 → 구조 위반 exit 1 ·
L2 원문 포함 검사). 그 집행이 payload §6 에 남은 채 표의 행만 audit 으로 가면, 이 설계가
§5.1 에서 비판한 「규범으로만 성립」 상태를 스스로 만든다. §3.1 의 「append-only 의 기계 집행이
코퍼스를 따라간다」가 그 요구이고, 이 절은 그 요구의 규범 쪽 절반이다 — **둘은 §8 의 I1 이 묶는다**
(같은 계약의 두 표현).

| 번들 빌더에 audit 경로를 안 주고 부른다 | rc 2 · **무디스패치** | 원문 없이 충실도를 묻는 경로가 막혔다 |
| 번들에서 audit §6 라벨 토큰을 지운다 | 체크리스트 앵커가 **해석 불가** | 라벨이 load-bearing 이라는 양성 대조 |
| 번들 위생 스캔을 payload 부분이 아니라 전체에 건다 | 정상 동작이 **매번 exit 3** | 스캔 범위 한정이 실재한다 |
| 번들 빌더를 두 번 돌려 서로 다른 바이트를 두 소비자에 준다 | **탐지된다** | 「한 번만 쓴다」가 규범이 아니라 관측 가능하다 |
| `finishing.md` 에서 「audit §6 에 전문 보존」 문장 삭제 | RED | §5.1 의 새 규칙에 락을 단다 |

**통과가 정답인 단언은 모양으로 이빨을 판별할 수 없다** — 검사를 통째로 지워도 GREEN 이라
똑같이 보인다. 그래서 마지막 세 행은 「변경 전 RED → 변경 후 GREEN」과 「남은 요구는 여전히
RED」 두 짝을 함께 기록한다. 4행(`bijection_c_errors` 무력화 후에도 RED)도 같은 종류의 양성
대조다 — 귀속이 옳다는 것을 초록/빨강 하나로는 못 보이므로 검사를 빼고 다시 잰다.

### 7.2 픽스처 이관

| | 수 |
|---|---|
| brief payload 픽스처 | **74** |
| audit 사이드카가 없는 것 | 15 — 3건은 의도적(`borrowed-audit`·`dup-auditfile`·`empty-auditfile`), **12건은 신설** |
| 테스트 코드가 heredoc 으로 직접 만드는 payload | 도출 규칙 ② 로 잡는다 |
| **신설** | 2 — ① **항목 0건 payload**(`user_sourced_items:` 키만 있고 항목 없음 + sentinel) — N1b 의 `==` 가 실제로 무는 유일한 상태이고 오늘 리포에 없다 · ② **§6 `S1` 에 맨 URL 을 담은 payload** — §2.3 축 2 의 예외를 시험한다 |
| **삭제** | `statement-160` · `-161` 픽스처 **와 그것을 소비하는 단언 블록**(한 쌍이다) |

**테스트 쪽 대상도 §8 의 도출 규칙이 정한다.** 특히 **`AUDIT_SECTIONS` 를 코퍼스로 삼아 도는
루프**는 절이 5 → 7 로 느는 만큼 함께 늘어야 한다 — 안 늘면 새 audit §6·§7 은 제거-mutation
커버리지가 0 이고, §3.1 이 스스로 경고한 「번호가 밀려 조용히 빈 문자열을 읽는다」 축에 이빨이
안 생긴다. **`SECTIONS`(payload) 를 도는 루프는 대상이 아니다** — §2.1 이 payload 절 구성을
동결했다.

죽는 픽스처와 그것을 **소비하는 단언 블록**은 한 쌍이다. 픽스처만 지우면 파일 부재로 RED 가
난다 — 도출 규칙 ① 이 이 쌍을 잡는다(그 픽스처 이름을 언급하는 모든 지점). 픽스처의 **audit
사이드카**도 같은 쌍이다.

**그리고 이 이관은 「통과가 정답인 기존 단언」을 뒤집을 수 있다.** 실측된 예가 하나 있다 —
`test_check_brief.sh` 의 T-TPL 은 *"shipping 되는 템플릿 쌍은 자기 게이트를 통과해야 한다"* 를
단언하고, 그 주석이 **「게이트가 첫 인터뷰마다 거짓 오류 벽을 내던 실제 결함」**을 기록한다.
이 락은 두 템플릿 이름을 축자로 담아 **도출 ① 이 그 파일을 회수한다** — 그러나 파일을 열어도
그 안에서 **어느 단언이 뒤집히는지**는 읽어서 알 수 없다. 그것이 §8 ⑤(스위트 실행)의 몫이다. §3.1 이 audit 템플릿에 placeholder 항목을 싣기로 한 것과
N2 를 조건부 교차로 만든 것이 이 락을 지키기 위한 결정이다.

**`docs/superpowers/interview/` 의 기존 brief 4쌍은 옮기지 않는다 — dogfood 1쌍만 옮긴다.**

실태: payload 넷이 각각 `S` 앵커를 11·14·19·28 개 갖고(N1b 가 red 를 낼 형상), audit 넷은
`## 6.`·`## 7.` 이 **하나도 없다**(#9 가 red 를 낼 형상). 즉 넷 다 새 포맷 기준으로는 red 다.

**그래도 옮기지 않는 근거는 「다시 검사되지 않는다」이다.** `check_brief.py gate` 의 호출 지점을
전수로 보면 셋뿐이고(인터뷰 종료 검증 · 리뷰 파이프라인의 재검증 둘) **전부 「방금 쓴 파일」을
대상으로 한다.** 훅도 명령도 옛 brief 를 다시 게이트에 태우지 않는다. 스위트도
`docs/superpowers/interview/` 를 돌지 않으므로 도출 ⑤ 에도 안 잡힌다.

**이 결정의 대가를 적는다**: 누군가 옛 brief 에 게이트를 손으로 걸면 **원인 불명 RED** 가 난다.
그 사람이 이 문단을 못 찾으면 이 설계의 결함으로 오인한다. 그래서 이월 목록(§10)이 아니라
**여기, 이관을 서술하는 절에** 적는다. 되돌리려면 「전부 옮긴다」로 바꾸고 도출 범위에
`docs/superpowers/interview/` 를 추가하면 된다.

**변환은 기계로, 검수는 손으로.** 74건을 손으로 옮기면 옮기다 잘린 문장이 나온다(이 설계를 낳은
인터뷰에서 실제로 발생했다). 변환 스크립트는 일회용이고 리포에 남기지 않는다.

**앞 설계의 「픽스처 120건」과 이 문서의 74건은 같은 것을 세지 않았다.** 앞 문서는 §4 URL 축과
probe 축을 더했는데 probe 축은 phase0 에서 이미 실행돼 소멸했고, URL 축은 §6 축의 부분집합이다
(실측: URL+§4/§5 픽스처 61건이 §6 보유 74건에 전부 포함).

### 7.3 작업 순서

1. 착수 전 전 스위트 baseline 을 **파일로** 캡처한다(선재 RED 를 회귀로 오인하지 않기 위해).
2. 변경을 **커밋한 뒤** mutation 한다. 커밋 전에 변이하면 `git checkout --` 가 「마지막 변이」가
   아니라 HEAD 로 되돌려 그 전 편집까지 함께 날린다.
3. 각 변이는 `PYTHONDONTWRITEBYTECODE=1` 로 실행한다. 같은 길이의 변이는 stale `.pyc` 를 못
   넘겨 거짓 GREEN 과 거짓 RED 를 둘 다 만든다.
4. 변이 후 복원은 커밋 대비로 확인한다.

## 8. 대상 도출과 변경 단위의 불변식

**이 설계는 대상 파일을 열거하지 않는다. 줄 번호도 적지 않는다.**

앞 세 판본이 손으로 열거해 **세 라운드 연속으로** 같은 결함을 냈다 — round 1 은 blob 빌더와
`check_verbatim_coverage.py` 의 호출부를, round 2 는 codex 충실도 러너의 재실행 호출부와 audit
헤딩 루프를, round 3 은 §6 을 앵커로 삼는 계약 산문(codex 체크리스트 · 권한 표의 닫힌 열거 ·
스킬 산문)과 테스트 안의 호출부를 빠뜨렸다. round 2 가 「도출 규칙」을 넣고도 실패한 이유는
**규칙을 두 축에만 걸고 나머지는 「작성 시점 실측 스냅샷」이라는 이름으로 열거를 남겨 뒀기
때문**이다. 스냅샷은 열거의 다른 이름이고, 그 라벨이 그것을 검증 대상에서 빼주지 않는다.

> **대상 = 「payload / audit 의 구조에 대한 사실」을 담은 모든 파일 + 이름이 바뀌는 게이트 표면.**
> **① 인자·시그니처** — 계약이 바뀌는 **파일 이름**(스크립트든 픽스처든)을 언급하는 모든 지점.
> **② 절 번호·절 제목 리터럴** — `§N` 또는 절 제목 문자열을 담은 스킬·체크리스트·agent 정의·
> 프롬프트 템플릿, 그리고 절 제목을 리터럴로 도는 셸 루프. **코드 모양으로 잡지 않는다** —
> 루프 변수명 열거는 게이트 자신의 절-순회를 놓친다. 상수를 쓰는 쪽은 ④ 가 잡는다.
> **③ 구조를 서술하는 산문** — 「원문은 payload §6 에 있다」류의 사실 주장. ② 의 결과에 포함된다.
> **④ 게이트 내부 식별자** — 이름이 바뀌거나 삭제되는 검사 함수·상수. **이것은 payload/audit 의
> «구조에 대한 사실» 이 아니라서 ①②③ 이 정의상 놓친다** — 그래서 네 번째로 이름을 붙인다.
> **⑤ 통과가 정답인 기존 단언 중 이 변경으로 뒤집히는 것.** ①–④ 는 그 락이 «어느 파일에 있는지»
> 까지는 찾지만 **«어느 단언이 뒤집히는지»는 못 찾는다** — 그것은 실행해야 안다.
> **이 축은 grep 이 아니라 스위트 실행으로 도출한다.**
>
> **목록은 계획이 도출한다.** 설계는 도출 명령만 남긴다.

**도출의 리포 범위는 `plugins/spec-distill` 과 `shared/` 둘이다.** `shared/codex` 가 프롬프트
빌더의 **바이트 동일 사본 계약**(∀ 계약, `shared/tests/test_copy_of_contract.sh`)을 지므로 경계
밖이 아니다. 픽스처 디렉토리는 ② 의 코퍼스에서만 제외한다(내용이 아니라 대상이므로).

계획이 그대로 실행할 도출 명령(리포 루트에서):

**아래는 리포 루트에서 실제로 실행해 출력을 확인한 형태다.** 경로를 변수에 담지 않고
(`SCOPE='a b'` 후 `grep ... $SCOPE` 는 **zsh 에서 단어분할되지 않아** 조용히 아무것도 못 찾는다 —
실측), BRE 의 `\|` 도 쓰지 않는다(**POSIX BRE 가 아닌 GNU 확장**이라 다른 grep 에서 리터럴
매칭이 되어 조용히 0건을 낸다). 설계가 「그대로 실행할 명령」이라 부르는 것은 실제로 도는
형태여야 하고, 이 문서는 그 자리에서 두 번 틀렸다.

```bash
# ① 파일 이름을 언급하는 모든 지점. 코퍼스는 «설계가 고른 목록»도 «내가 고른 디렉토리»도 아니라
#    **git 이 추적하는 전부**다 — 손으로 고른 코퍼스는 그 자체가 이 결함의 재발이었다.
git ls-files plugins/spec-distill | xargs -n1 basename | sort -u > /tmp/names.txt
while read -r b; do
  echo "== $b"
  grep -rnF "$b" plugins/spec-distill shared
done < /tmp/names.txt
#    `-rn`(지점)이지 `-rl`(파일)이 아니다 — I7 의 「항목」이 (파일, 계약) 쌍이라 한 파일이 두
#    계약을 언급하면 두 항목이다.
#    **자기제외 필터를 걸지 않는다.** `grep -v "/$b:"` 류는 동명 basename(여러 곳의 `SKILL.md`·
#    `README.md`·`codex_prompt_common.py`)에서 정당한 cross-file 참조를 통째로 버린다 —
#    사본 계약을 서술하는 줄이 정확히 그 형태다. 자기 매치는 triage 가 버리면 된다.

# ② 절 제목은 «추출»이 아니라 **게이트 상수 ↔ 템플릿 헤딩 대조**로 얻는다. 추출 + 하한 가드는
#    부분 실패를 통과시키고, `len(list(a)+list(b)) == len(a)+len(b)` 같은 자기-항등 단언은
#    빈 입력에서도 참이라 아무것도 안 지킨다(앞 판본이 실제로 그랬다).
python3 -c "
import sys, re, pathlib
sys.path.insert(0, 'plugins/spec-distill/scripts')
import check_brief as cb
tpl = ''.join(pathlib.Path(f).read_text(encoding='utf-8') for f in
      ['plugins/spec-distill/templates/interview-brief-template.md',
       'plugins/spec-distill/templates/interview-audit-template.md'])
found = {ttl.strip() for _, ttl in re.findall(r'(?m)^## (\d+)\. (.+?)\s*\$', tpl)}
const = {ttl for _, ttl in list(cb.SECTIONS) + list(cb.AUDIT_SECTIONS)}
assert found == const, f'템플릿-only={found-const} 상수-only={const-found}'
print('\n'.join(sorted(const)))" > /tmp/titles.txt
#    확장자 whitelist 를 걸지 않는다 — `tests/test_stale_terms.sh` 헤더가 그것을
#    「header-satisfiable 함정」이라 명시하고 폐기했다. `.txt`·확장자 없는 production 파일도 대상이다.
grep -rn '§[0-9]' plugins/spec-distill shared | grep -v '/tests/fixtures/'
grep -rnFf /tmp/titles.txt plugins/spec-distill shared | grep -v '/tests/fixtures/'

# ④ 이름이 바뀌거나 사라지는 게이트 표면 **과 절 상수 자체**. 절 목록을 도는 루프는 코드
#    모양(`for hdr in` 류)으로 잡지 않는다 — 변수명 열거라 게이트 자신의 `for num, title in
#    sections:` 를 놓친다. 셸 쪽 루프는 절 제목 리터럴을 담아 ② 가 이미 잡는다.
grep -rnE 'landscape_uncited|STATEMENT_MAX|WEB_DISABLED_ADVISORY|attribution_block_missing|SECTIONS' \
  plugins/spec-distill shared

# ⑤ «통과가 정답인 기존 단언» 중 이 변경으로 뒤집히는 것 — 변경 전후로 스위트를 돌려
#    GREEN→RED 로 뒤집힌 단언을 전부 목록화한다. grep 으로 대체되지 않는다.
```

**⑤ 는 grep 이 아니라 실행이다.** 착수 전 baseline 을 파일로 캡처하고(§7.3 ①), 각 단위 종료마다
같은 스위트를 돌려 **GREEN→RED 로 뒤집힌 단언**을 뽑는다. 뒤집힌 것마다 판정한다 — 의도된
변경이면 그 단언을 갱신하고, 아니면 설계 결함이다.

**①–④ 도 그 파일을 찾기는 한다** — `test_check_brief.sh` 의 T-TPL 블록은 두 템플릿 이름을 축자로
담아 ① 이 회수하고, 같은 파일의 절 제목 리터럴을 ② 도 낸다. ⑤ 가 유일하게 더 주는 것은 **파일이
아니라 「어느 단언이 뒤집혔는가」**다. 파일을 열어도 200줄 안에서 어느 `ok`/`no` 가 뒤집힐지는
읽어서 알 수 없고, 그것이 T-TPL 처럼 **절 번호도 절 제목도 개명 식별자도 없는** 락일 때 특히
그렇다.

**실행 확인 (작성 시점)** — ① 은 305 이름을 코퍼스로 돌아 `interview-audit-template.md` 를 부르는
`test_brief_review_ng3.sh` 까지 회수한다(디렉토리를 손으로 고르던 앞 판본은 이 파일을 못 봤다).
② 는 **개수가 아니라 제목 집합**을 대조한다 — 개수 등식이면 `## 2. Budget` → `## 2. 예산`
개명이 통과하면서 이후 grep 이 개명된 헤딩을 전량 놓친다(앞 판본이 그랬다). 양성 대조 둘을
확인했다: 상수를 하나 줄이면 터지고, **제목 하나를 개명해도 터진다**. ④ 는 절 상수 자체를 잡아 그 소비자로 가는 입구를 낸다.
이 숫자들은 **기계적 소속의 관측**이지 대상 목록이 아니다. 이관 후 audit 이 7절이 되면 13 은
15 가 되는데, ② 는 리터럴을 핀하지 않고 **양쪽을 대조**하므로 그 변화를 따라간다.

**다섯 도출 결과의 합집합이 이 변경의 대상 집합이다.** 계획의 첫 작업이 이 도출이며, 설계가 미리
센 숫자는 없다.

### 이 설계는 PR 을 배정하지 않는다

앞 판본들이 PR1/PR2/PR3 을 손으로 배정했고, 그 배정이 **세 라운드 연속으로 틀렸다** — 호출부를
다른 PR 에 두고(round 1·3), 러너 재실행 지점을 빠뜨리고(round 4), 마지막에는 **같은 문면을
PR1 과 PR2 에 동시에 배정**했다(round 5, 앞 라운드의 수정이 만든 모순). 결정론 병합이 정체
판정을 낸 세 id 중 둘이 이 축이다.

**실패하는 것이 「어느 PR 인가」이고, 그것은 계획이 도출로 정하는 일이다.** 설계가 배정하지
않으면 배정을 틀릴 수 없다 — round 3 에서 열거를 지운 것이 이 클래스에 유일하게 먹혔던 수단이고,
같은 수를 한 층 위에 적용한다.

대신 설계는 **분해가 만족해야 하는 불변식**만 남긴다. 각 불변식은 제안된 분해에 대해
기계적으로 검사 가능하다.

| | 불변식 | 어기면 |
|---|---|---|
| **I1** | **한 계약의 모든 표현은 한 단위다.** 표현의 목록을 손으로 열거하지 않는다 — 도출 ①–⑤ 의 결과 중 그 계약을 언급하는 **전부**가 그 계약의 표현이다(템플릿 · 게이트 · 저술 지시 · **픽스처** · 문서 · 락) | 스킬이 자기 게이트가 거절할 것을 쓰라고 지시하는 중간 상태. **픽스처를 빼면** 그 단위 종료 시 74건이 통째로 RED |
| **I2** | 시그니처가 바뀌는 파일과 **그 호출 지점 전부**(테스트 안의 호출 포함)는 한 단위다 — 도출 ① | 단위 종료 시점에 모든 호출이 인자 부족으로 죽는다 |
| **I3** | **절 구조에 대한 사실을 담은 문면**은 그 구조를 바꾸는 단위와 한 단위다 — 도출 ②③. 스킬·체크리스트·agent 정의·README 를 구분하지 않는다 | 문서가 실장을 거짓으로 서술한 채 GREEN |
| **I4** | **이름이 바뀌는 게이트 표면**과 그 이름을 인용하는 락은 한 단위다 — 도출 ④ | 락이 없는 이름을 잡아 조용히 RED, 또는 조용히 무의미 |
| **I5** | **삭제되는 픽스처**와 그것을 소비하는 단언은 한 단위다 — 도출 ① | 파일 부재로 RED |
| **I6** | **dogfood 는 마지막 단위다** — 대상은 **이 설계를 낳은 brief 1쌍**이고 나머지 옛 brief 는 이관 대상이 아니다(§7.2) | 코드 착지 전에 옮기면 게이트가 red |
| **I7** | **분할·완비** — 도출 ①–④ 결과의 각 **항목**은 **정확히 한** 단위에 든다(∪ = 도출 집합, ∩ = ∅) | 한 대상이 두 단위에 동시 배정되거나(이 문서가 실제로 저지른 것), 어느 단위에도 안 들어가 조용히 누락된다. I1–I6 은 **「함께 간다」형이라 이 둘을 배제하지 못한다** |
| **I8** | **각 단위의 경계에서 전 스위트 GREEN** — 착수 전 baseline 대비. **도출 ⑤ 의 결과를 그 자리에서 판정한다** | I1–I7 을 전부 만족하면서도 깨진 중간 상태가 남는다. 이것이 앞의 일곱을 실제로 집행하는 유일한 관측이다 |
| **I9** | **게이트 검사 집합을 바꾸는 단위는 같은 단위에서 출하 템플릿 쌍을 재도출하고 T-TPL 을 관측한다** | 신설 검사가 출하 템플릿을 깨는 것이 **세 라운드 연속 block** 이었다. 그때마다 설계가 결과를 산문으로 예측했고 세 번 다 틀렸다 — **예측을 관측으로 바꾸는 것이 이 불변식이다** |

**I7 의 「항목」은 `(파일, 계약)` 쌍이다.** 파일이 아니다 — 이 설계 자신이
`skills/reviewing-brief/SKILL.md` 와 `README.md` 를 「두 계약에 걸친다」고 적었으므로, 파일 단위로
읽으면 I1(한 계약의 모든 표현은 한 단위)과 I7(∩ = ∅)이 **동시 만족 불가능**해진다. 그래서 도출
① 이 파일이 아니라 **지점**을 낸다.

**두 가지는 I7 의 분할 대상이 아니다.**
- **매 단위 필수 편집** — `plugin.json` bump 과 `CHANGELOG.md` 항목은 devbrew 규약이 *모든* 단위에
  요구하므로 정의상 모든 단위에 든다. 분할하려 들면 규약과 충돌한다.
- **도출 ⑤** — 그 결과는 스위트를 돌려야 나오므로 **착수 전에 존재하지 않는다.** ∪ 에 넣으면 I7 의
  사전 기계 검사가 원리적으로 불가능해진다. ⑤ 는 분할의 원소가 아니라 **I8 이 각 단위 경계에서
  수행하는 의무**다.

**몇 단위가 되는지, 어떤 이름을 갖는지는 계획이 정한다 — 이 설계는 개수도 이름도 적지 않는다.**
도출 결과 위에서 I1–I9 를 만족하는 분해를 만들고, 만족 여부를 각 단위마다 점검한다.

**I7 은 순수한 기계 검사가 아니다.** 도출 ①–④ 가 내는 것은 `(파일, 줄, 매치)` 이고 I7 의 원소는
`(파일, 계약)` 이라, 그 사이의 사상은 **판단**이다 — 한 파일의 열 줄이 한 계약인지 두 계약인지는
grep 이 정하지 않는다. 그리고 ② 는 의도적 과포함이라 완비(∪ = 도출 집합)를 문자 그대로 요구하면
**노이즈까지 어느 단위엔가 배정**해야 한다.

그래서 계획은 도출 결과를 **triage** 한다: 각 히트를 「이 변경의 계약에 걸리는가」로 판정하고,
**버린 것을 이유와 함께 목록으로 남긴다.** 버림 자체는 허용하되 **조용한 버림은 금지**다 —
판단이 원장에 남으면 다음 세션이 그 판단을 재검토할 수 있고, 안 남으면 이 문서가 다섯 층에 걸쳐
지운 그 동작이 되살아난다. I7 이 적용되는 것은 **triage 를 통과한 집합**이다.

I8·I9 는 실행이라 관측이다.

**각 단위는 `plugin.json` 을 bump 한다**(devbrew 규약 — 안 하면 cache key 가 조용히 stale).

### 리뷰 round 3 이 고친 것 — 층위 수정

round 3 은 `Stagnation_signal: true` 를 냈고 근거를 **클래스 수준**으로 밝혔다: 「계약이 걸린
지점을 손으로 열거하고 하나를 빠뜨린다」가 세 라운드 연속이었다. findings 는 7 → 5 → 8, `block`
은 0 → 1 → 2 로 **발산**했다. 사람 게이트에서 「라운드를 더 도는 대신 층위를 고친다」가 선택됐다.

**층위 수정 — 이 문서에서 줄 번호와 파일 목록을 전부 지웠다.**

| 앞 판본 | 무엇이 문제였나 | 이 판본 |
|---|---|---|
| 도출 규칙 둘 + 「작성 시점 실측 스냅샷」 | **스냅샷은 열거의 다른 이름**이고, 그 라벨이 검증을 면제해 주지 않는다. 세 판본의 스냅샷이 세 번 다 틀렸다 | §8 의 **단일 규칙 + 도출 명령**. 설계는 대상 수를 세지 않는다 |
| 규칙이 「호출 지점」·「헤딩 루프」 두 축만 덮음 | round 3 의 실패는 **§6 을 앵커로 삼은 계약 산문**(codex 체크리스트 · 닫힌 열거 권한표 · 스킬 서술) — 규칙 밖이었다 | 세 모습(**인자·절 리터럴·구조 서술**)을 한 규칙 아래로 |

**block 둘도 함께 닫았다.**

| block | 무엇이었나 | 고친 것 |
|---|---|---|
| N1a ↔ L2 동시 만족 불가 | `normalize()` 가 맨 URL 을 안 벗겨, 최초 요청에 URL 이 있으면 남겨도 red 지워도 exit 1 | N1a 의 코퍼스를 **payload 에서 §6 을 뺀 나머지**로. §6 verbatim 은 명시 예외(§2.3 축 2) |

나머지 넷(§6 관할 문면 · attribution 이사의 소유 컴포넌트 · kill switch 공시 진위 · §9 표의
행 이탈)도 같은 라운드에서 반영했다.

### 리뷰 round 4 가 고친 것 — 층위 수정의 검증과 잔여

round 4 는 층위 수정을 **직접 시험했다**: §8 의 `grep` 명령을 실제로 실행해 앞 세 라운드가

per-issue 정체를 독립 판정**했다(PR 경계 · 호출부 열거, 각각 `raised_count 3`). 클래스가 닫힌 게
아니라 **한 층 내려갔다** — 「어느 파일인가」에서 「그 파일 안 어느 자리인가」로.

### 리뷰 round 8 이 고친 것 — 결과를 미리 판정하지 않는다

round 8 은 **세 라운드 연속 같은 자리(§3.1)에서 내 수정이 다음 라운드의 block 을 만들고 있다**는
것을 지적했다: round 6 이 T-TPL 충돌을 잡자 round 7 이 그 수정의 근거가 거짓임을 잡았고,
round 8 은 그 수정이 **다시 T-TPL 을 깬다**는 것을 잡았다.

공통 원인이 하나다 — **설계가 게이트 결과를 산문으로 예측했다.** 「예시 불릿을 두지 않으면 통과」
(틀림) → 「placeholder 를 실으면 통과」(틀림) → 「§6 금지해도 통과」(틀림, `evidence: S2` 가
dangling). 예측은 검증되지 않은 채 사실로 박히고 다음 라운드의 결함이 된다.

**층위 수정: 결과를 예측하는 문장을 전부 지우고, 관측을 불변식으로 승격했다.**

**기계가 안 막는 것 넷 — 이름으로 적는다.**

- **payload §4 의 «출처키» 가 audit §7 에서 해석되는지.** 키를 지어내도 게이트는 통과한다.
  이것을 묶는 것이 §3.4 ① 의 교차 bijection 이고 그것을 기각했으므로 이 줄이 그 대가다. #13 이
  ∀ 로 「키가 있는가」까지는, N2 가 「몇 건인가」까지는 보장하지만 **「어느 키가 어느 원자료인가」**
  는 보장하지 않는다.
- **payload §6 `S1` 에 없던 URL 이 덧붙는 것.** §2.3 축 2 의 예외가 여는 통로다. L2 가
  containment 라 원문보다 더 담아도 통과하고, 막는 것은 「기존 항목 본문 변경 금지」 규범뿐이다.
  기계 집행이 없다.
- **audit §7 의 내용.** §7 에는 대조할 원장이 없으므로 **내용 검사가 원리적으로 존재할 수 없다.**
  N2 는 «키» 집합의 포함이라 「payload 가 든 출처가 audit 에 선언돼 있다」까지만 보고, 그 선언
  아래 실제 원자료가 있는지는 못 본다.
  §6 에는 state 원장이 있어 L2 가 내용을 보지만 §7 에는 그런 것이 없다 — 비대칭이고, 없앨 방법이
  이 설계의 범위 안에 없다.
- **「원문 전량이 옮겨졌는가」를 게이트 시점에.** 무엇이 전량인지는 state 원장만 알고 게이트는
  state 를 받지 않는다. 게이트가 보는 것은 **인용된 부분집합**(#5)뿐이고, 전량 대조(L1)는
  리뷰 진입에서 돌며 state 가 없으면 degrade 한다(§3.1 술어표). 이것은 이 설계가 만든 결함이
  아니라 **게이트와 원장이 다른 층에 있다는 구조적 사실**이고, `check_verbatim_coverage.py` 가
  별도 스크립트인 이유다.

넷 다 **저술자가 악의를 갖지 않는다**는 가정에 기대고 있다. 이 파이프라인의 저술자는 모델이고,
그 모델은 같은 세션에서 리뷰를 받으므로 이 가정을 통째로 없앨 수는 없다 — 그러나 가정에
기대고 있다는 사실 자체는 숨기지 않는다.

**이 설계도 모델 다양성 없이 확정됐다.** 앞 설계가 *"이 설계의 리뷰도 Claude 단독으로
받았다"* 고 적었는데, 이 설계를 낳은 인터뷰의 codex 실호출 6회와 이 문서의 리뷰 라운드마다의 1회씩이
**전부** 실패했다(한도 소진, 2026-09-17 21:03 까지 — 성공 0). **연속 두 설계가
같은 상태다.**

그리고 라운드가 거듭될수록 그 위험이 실물로 드러났다 — 적발된 것의 **절반 이상**이 **fail-open·조용한-0건 계열**이고
(∀→∃ 강도 하락 · PR 경계 · seed 빌더 fail-open · append-only 집행 소실 · codex 지시문 잔존 ·
kill switch 허위 공시), 이 리포의 이력상 그 계열이 Claude 단독 리뷰가 가장 자주 놓친 축이다.
이번에는 Claude 리뷰가 여러 라운드에 걸쳐 잡았다 — 다만 **한 라운드로는 못 잡았다**는 것이
그만큼 중요한 관측이다. 특히 round 7 이 적발한 것 중 하나는 **앞 라운드의 수정이 심은 자기-항등
단언**(`len(a+b) == len(a)+len(b)`)이었다 — 가드처럼 생겼지만 빈 입력에서도 참이라 아무것도
지키지 않았고, 그것이 고치겠다고 나선 결함보다 나빴다.

**리뷰가 수렴하지 않았다 — 그리고 미리 정한 정지 규칙이 발동했다.**

findings 7 → 5 → 8 → 8 → 9 → 10 → 11, `block` 0 → 1 → 2 → 3 → 2 → 3 → 4. 결정론 병합의
per-issue 정체 판정이 round 4 에 처음 발동해 round 6 에 네 id 가 됐는데, **넷이 전부 같은
클래스**다 — 「계약이 걸린 지점을 손으로 정하고 하나를 틀린다」.

그 클래스는 **다섯 층으로 내려갔고 층마다 같은 수단으로 닫혔다**:

| 층 | 무엇을 손으로 정했나 | 상태 |
|---|---|---|
| 어느 **파일**인가 | 대상 파일 목록 | **닫힘** (round 3 이 열거를 도출로. round 4·5 가 도출이 저자보다 많이 찾는 것을 독립 확인) |
| 그 파일 안 어느 **자리**인가 | 「§6 권한 세 면」류의 계수 | **닫힘** (round 5 가 계수를 전수 삭제) |
| 그 자리가 어느 **PR** 인가 | PR1/PR2/PR3 배정 | **닫힘** (round 6 이 배정을 삭제하고 불변식만 남김) |
| **몇 개**의 단위인가 | Handoff 의 「세 PR」 | **닫힘** (round 7 이 개수를 삭제) |
| 어느 **검사가 무엇을 잡는가** | 「#5·L1 이 내용을 대조한다」·「⑤ 만 T-TPL 을 찾는다」·「T-TPL 이 §6 placeholder 를 요구한다」 | **round 8 에서 삭제** — 귀속 주장을 지우고 각 검사의 실제 술어만 표로 남겼다(§3.1) |

**정지 규칙의 판정** — 이 문서가 정한 조건(「네 번째 재발이면 라운드가 아니라 범위 축소」)은
round 5 와 round 6 에서 두 번 충족됐고 두 번 다 사람 게이트에 올렸다. 사용자는 두 번 다 **범위
축소를 거부하고 수정을 지시**했다 — round 5 후에는 「설계에서 PR 분해를 지운다」, round 6 후에는
「축소하지 말고 제대로 고쳐라」. **범위는 인터뷰가 확정한 그대로다**(C4·C12·C13·C14·C15·C23 전부
유효).

네 층이 전부 같은 수단으로 닫혔다: **고치는 것이 아니라 지우는 것.** 「이번엔 제대로 세겠다」로
간 시도는 다섯 번 전부 실패했고, 「세지 않는다」로 간 시도는 네 번 전부 성공했다.

**남은 위험은 다른 종류다.** round 6 의 무거운 둘(T-TPL 충돌 · 분할 불변식 부재)은 손 계수가
아니라 **신설 검사가 기존 락·기존 관례와 부딪히는 것**이었다. 그 축은 §8 ⑤(스위트 실행)로만
찾을 수 있고, 이 설계는 그것을 도출 규칙으로 승격했다 — 그러나 **이 문서 안에서 실행된 적은
없다**(계획의 첫 작업이다).

**열린 선택 — codex 리뷰를 착수 선결 조건으로 승격할 것인가.** 승격하면 구현이 2026-09-17 까지
막힌다. 승격하지 않으면 fail-open 계열 결함이 남은 채 74건 픽스처 이관이 진행된다. 이 선택은
설계가 정하지 않는다 — 착수 시점에 사람이 정한다.

**측정하지 않은 것** — payload 의 실제 토큰 수, 그것이 하류를 흔든 정도, 그리고 이 재구조화
이후의 개선. §1.2 의 인과는 가설로 남는다. 이관 후 before/after 글자 수는 **관측으로 기록하되
검증으로 쓰지 않는다** — 열화 예측자가 raw 토큰 수가 아니라 distractor 형상이라는 문헌이 있고,
부피 감소를 성공 지표로 삼으면 재는 것을 잘못 고른 것이 된다.

## Handoff Context

이 변경은 여러 세션에 걸친다. **몇 개의 단위로 나뉘는지는 이 문서가 정하지 않는다** — §8 의
I1–I8 을 만족하는 분해를 계획이 도출한다. 앞 판본이 여기에 「세 PR」이라 적어 두는 바람에,
§8 이 배정을 그만둔 뒤에도 개수만 살아남아 다음 세션을 오도할 뻔했다.
`/compact` 를 지나면 대화가 사라지므로 **다음 세션이 이 문서만 읽고 이어갈 수 있어야 하는 것**을
남긴다.

### TL;DR

payload 는 압축된 판정만, audit 은 원자료. 신설 게이트 검사는 **셋뿐**이다 — **N1a**(payload
모델-저술부에 외부 URL 0개, §6 verbatim 은 예외) · **N1b**(payload §6 앵커 **== `{S1}`**) ·
**N2**(payload §4 항목 수 ≤ audit §7 의 URL 항목 수, 조건부 교차). **audit 쪽 「존재 검사」는
두지 않는다** — 출하 템플릿의 placeholder 로 충족돼 실brief 를 못 막으면서 T-TPL(「출하 템플릿
쌍은 자기 게이트를 통과한다」)만 깬다.

오늘 §4 의 ∀ 인용 요구는 **술어만 «출처키» 로 바뀌어 payload 에 남는다**(#13). `STATEMENT_MAX` 를
지운다. 충실도 리뷰어 둘이 같은 번들을 보되 **냉독은 payload-only 로 남긴다**.

**게이트가 원리적으로 못 하는 것**: 「원문 전량이 옮겨졌는가」. 무엇이 전량인지는 state 원장만
알고 게이트는 state 를 받지 않는다 — 그 확인은 `check_verbatim_coverage.py` 의 몫이고 게이트 밖
이다. §10 에 gap 으로 적혀 있다.

### 이 문서 밖에 있으면 안 되는 암묵 컨텍스트

- **왜 부재 검사인가.** 존재 검사가 산출물을 양식으로 만들고, 양식이 내용을 미리 판 구멍 모양으로
  강제한다. `check_seed.py` 의 docstring 과 앞 설계의 Handoff Context 가 같은 말을 한다.
  `test_seed_one_sentence.sh` 가 seed 쪽에서 이 금지를 동작으로 잡는다.
- **N1 은 두 검사다.** N1a(부재: URL 0개)와 N1b(등식: §6 == `{S1}`). **N1a 의 가치는 N1a 안에
  없다** — #1·#12·#15 셋이 삭제 우회로를 막아야 이빨을 갖는다. "이 검사는 약하니 지우자" 류
  리팩터가 이 배치에서 특히 위험하다. **N1b 는 스스로 양성이라 그 표의 대상이 아니다** — 이
  구별을 잃으면 §7.1 의 RED 귀속이 통째로 흔들린다.
- **`bijection_c_errors` 가 §6 축을 못 막는 경우는 「항목 0건」 하나다.** `evidence` 는 필수
  필드라 항목이 있으면 순회가 비지 않는다. 첫 판본은 여기에 §6 축 방어를 귀속시켰고(틀림),
  둘째 판본은 「evidence 없는 payload 는 합법」이라 적었다(역시 틀림). 세 번째가 맞다.
- **이 문서는 대상 파일도 줄 번호도 열거하지 않는다.** §8 의 도출 규칙과 그 안의 `grep` 명령이
  정본이다. 앞 판본들이 손으로 센 목록이 **네 번** 틀렸고, 「작성 시점 실측 스냅샷」이라는 라벨은
  그 열거를 검증에서 면제해 주지 않았다.
- **모든 숫자가 위험한 것은 아니다 — 선은 「소속 판정이 기계적인가」다.** §7.2 의 픽스처 74건 ·
  사이드카 없는 15건은 `grep -l` 한 줄로 소속이 갈리는 집합이라 안전하고, 실제로 네 라운드
  내내 맞았다. 틀린 것은 전부 **판단으로 소속이 갈리는 집합**이었다 — 「모순되는 저술 지시가
  둘」·「호출부 2곳」·「§6 권한 세 면」. **판단으로 도출되는 집합의 크기를 적고 싶어지면 그것이
  이 결함의 재발이다.** 기계적 집합의 수는 적어도 된다.
- **§6 은 payload 에서 URL 금지의 예외다.** 사용자가 자기 요청에 쓴 URL 을 지우면 `L2` 원문 포함
  검사와 동시 만족이 불가능해진다(`normalize()` 는 맨 URL 을 안 벗긴다). 예외를 지우려면 그
  검사부터 봐야 한다.
- **`landscape_present()` 는 원래 시시한 검사였다.** N1 이 들어오는 순간 그것의 sentinel 구멍이
  치명적이 된다. §3.2 의 조임을 빼먹으면 전체가 공허해진다.
- **`S1` 은 payload 에 남는다.** 그래서 `S1` 배치를 지시하는 문면과 그것을 잠근 락들이 불변이고,
  bijection C 와 `check_verbatim_coverage.py` 의 앵커 집합이 **합집합**이어야 한다. 한쪽만 보는
  구현이 가장 그럴듯하게 틀린다.
- **번들 빌더는 audit 경로를 인자로 받는다.** 게이트의 stem 유도와 층이 다르다 — 유추 실패의
  침묵이 잘못된 재료로 리뷰를 태우는 것보다 나쁘다.
- **codex 는 이 계정에서 돌지 않는다**(2026-09-17 까지). 감지기는 `available: true` 를 내지만
  실호출이 실패하고, 러너가 모델을 핀하지 않아 400 이 quota 를 가린다. 이 설계와 그 앞 설계
  둘 다 Claude 단독으로 확정됐다.
