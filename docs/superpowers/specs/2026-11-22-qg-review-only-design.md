# R4 — qg 리뷰 전념 · Design

> qg 는 한 번 보고 판정과 고칠 목록을 내고 끝난다. 지휘 중에는 에픽 PR 을 머지하기 앞에 qg 가 코드를 보고, 막는 지적은 지휘자가 구현 담당자에게 돌려보내 같은 브랜치에서 고치게 한 뒤 고친 커밋만 다시 본다. 「잘못 골랐다」 면 머지를 멈추고 그 에픽 안에서 고친다.

## Context / Why

지금 qg(`/quality-gates:quality-pipeline`)는 막는 지적이 나오면 「고치고 다시 돌기」 를 물어, 고르면 qg 를 돌리던 그 턴이 코드를 고치고 리뷰를 다시 돈다(기본 다섯 번, 사용자가 더 연다). 이 길은 지휘 흐름과 갈라져 있다.

- 지휘자를 거친 qg 는 늘 이미 있는 커밋 범위를 보는 방식으로 불려 고치는 선택지가 없다. 그런데 자동으로 부르는 자리가 에픽이 머지된 «뒤» 라, 코드 지적은 「후속 PR 하나의 고칠 목록」 으로 밀린다(`qg-review.md` 「판정과 코드 리뷰 지적」).
- 직접 부른 qg 만 스스로 고친다. 고친 것은 구현 담당자도, 계획도, 설계의 수용 기준 대조도 거치지 않는다.
- 옆 로드맵(conductor-context-economy)이 세운 걸음표에는 구현 뒤 · 머지 앞의 「검수」 걸음과, 반려가 구현으로 돌아가는 길이 이미 있다. qg 는 그 걸음에 닿아 있지 않다.

사용자는 2026-11-14 에 이 에픽을 이렇게 세웠다 — 「아니 qg의 리뷰이후 액션인 고치는게 지휘와 갈라지다보니 qg자체 개발을 하지 말라는 의미였어」 · 「qg는 리뷰에만 집중해」 · 「1, 어떻게 네이티브하게 녹여낼지 특히 다른 세션에서 만들고 있는 설계를 두고 거기에 녹이면 좋겠네」.

## Goals

- **G1** qg 는 리뷰만 한다 — 한 실행은 한 번 보고 판정과 고칠 목록을 내고 끝나며, 저장소의 코드를 고치지 않는다.
- **G2** 지휘 중 qg 가 코드를 보는 때는 에픽 PR 의 머지 앞이다. 머지된 뒤에는 자동으로 돌지 않는다.
- **G3** 막는 지적은 지휘자가 그 코드를 쓴 구현 길로 되돌려 같은 브랜치에서 고치게 하고, 고친 커밋만 qg 로 다시 본다.
- **G4** 머지 앞 의도 점검에서 「잘못 골랐다」 가 나오면 머지를 멈추고 그 에픽 안에서(설계부터) 고친다.
- **G5** 새 장치를 세우지 않는다 — 옆 로드맵의 걸음표, 걸음 5 의 「리뷰 뒤 반영」, qg 의 범위 호출처럼 이미 있는 길에 잇는다.

## Non-goals

- intent-critic 리뷰어 본체 — 무엇을 의심하고 어떤 근거로 묻는지, 돌려주는 꼴의 칸(R1 · R2 · R5 가 세웠다). 질문 글의 길이와 묻는 틀에 싣는 것은 §4 가 줄인다(U11).
- 옆 로드맵의 팀 구조 자체(걸음표의 걸음 · 관문 · 시작 묶음의 규칙).
- qg 의 답 기록과 다른 팀 읽기(R6 · R8) · 리뷰 대상에 심은 글 막기와 공유 스위트 잠금(R7).
- qg 호출 줄에 새 인자를 더하는 것 · 돌려주는 꼴(`intent-return.md` 2판)의 판을 올리는 것.
- 머지된 에픽을 다시 열어 고치는 길.

## Anti-goals

- qg 밖에 또 하나의 「고치고 다시 도는 반복」 을 숨겨 세우는 것 — 되돌리기는 횟수가 정해진 지휘 걸음이고, 넘으면 사람에게 간다.
- 구현 담당자가 자기 코드의 qg 를 스스로 부르는 것 — 부르는 쪽은 지휘자 하나다(묶음 S28 의 「지휘자는 늘 같은 qg 입구를 같은 입력으로 부른다」).
- 막는 지적이 남은 채 말없이 머지 준비로 넘어가는 것.

## Constraints

- **Law 2.** qg 의 리뷰어는 지금처럼 읽기 전용이다. 고치기 반복이 사라지면 qg 가 저장소에 쓰는 자리는 intent-critic 답 파일과 그 커밋 하나다.
- **리뷰어 정의는 보안 민감 파일이다.** `security-reviewer.md` 에서 바꾸는 것은 frontmatter `input_slots` 의 `iteration` 입력 칸 선언을 지우는 것 하나다 — 그 파일의 본문에는 반복을 가리키는 낱말이 없고, 그 칸을 채우던 qg 본문의 dispatch 줄도 함께 지운다. `code-recritic.md` 에서 바꾸는 것은 반복을 가리키는 낱말뿐이다. 두 파일 모두 규칙 · 임계치 · 처방 문장은 건드리지 않는다. `intent-critic.md` 에서 바꾸는 것은 `question` 칸의 지시(질문 한 문장과, 있으면 직접 확인 한 줄)와 출력 예시의 `question` 줄뿐이다(§4) — 근거 규칙 · 상한 · 주입 경계 문장은 건드리지 않는다.
- **없앤 것은 공시한다.** 고치기 반복은 사용자가 명시 결정한 제거(U1 · U2)라 deprecation 창 없이 지우고 quality-gates `CHANGELOG.md` 의 Removed 에 적는다. 판정 줄의 칸이 바뀌므로 major 다.
- **은퇴하는 kill switch 는 없다.** qg 본문 `## kill switch` 절의 일곱 스위치 가운데 고치기 반복만을 끄는 것은 없다(계획의 첫 과제가 다시 확인한다 — 있으면 CHANGELOG Removed 와 README 에 공시한다).
- **플러그인 경계.** spec-distill 은 quality-gates 를 skill 호출로만 부르고 그 스크립트를 직접 부르지 않는다. quality-gates 가 없으면 지금처럼 「품질 게이트 없이 간다」 로 알리고 진행한다.
- **다른 로드맵과 겹침.** 끝나지 않은 옆 에픽 가운데 이 에픽의 예약 파일을 함께 예약한 것은 아래와 같다(2026-11-22 기본 브랜치의 로드맵들에서 확인).
  - 앞단 로드맵(framing-interview-constraint-audit)의 F7 둘째 계획(스위치 은퇴 — 브랜치 `feature/switch-retirement`): qg 본문 · qg README · qg 스크립트와 테스트 · `conducting.md` · 지휘자 skill 본문.
  - 같은 로드맵의 F5(구현 중 — `feature/front-stage-restructure`): qg README · 스크립트 · 테스트 · agent 정의 · spec-distill README · `dependencies.md`.
  - 옆 로드맵(conductor-context-economy)의 E1(설계 중 — `feature/session-workers`)과 E2(`feature/conductor-step-guides`): `conducting.md` · 지휘자 skill 본문 · `conductor-dispatch.md`.
  - test-method-rework 의 E1(PR #319 열림 — `feature/suite-time-cut`): qg 테스트.

  먼저 머지되는 쪽 위에서 뒤쪽이 맞춘다 — 계획의 첫 과제가 그때의 기본 브랜치에서 이 에픽이 고칠 자리(qg 본문의 진입 단계 문장과 끄는 길 절 · `conducting.md` 의 걸음 5 · 6 과 team 형식 절 · 지휘자 skill 본문의 규모 공시 · 손대는 qg 테스트)를 다시 읽는다.
- **레포 전용 값을 박지 않는다.** 기본 브랜치 · 테스트 명령 · 모델 · 폴더는 지금 해결자가 내는 값을 쓴다.

## Approaches

갈린 곳은 하나다 — qg 의 반복이 없어진 뒤, 구현 담당자가 고친 것을 누가 어떻게 다시 확인하나.

1. **매번 처음부터 다시 본다.** 고칠 때마다 qg 전체(리뷰어 여럿 · 차등 테스트)를 다시 돌린다. 가장 확실하고 가장 비싸다.
2. **고친 부분만 다시 본다.** 첫 리뷰는 전체, 그 뒤는 지난 리뷰의 끝 커밋부터 고친 뒤의 끝까지만 qg 로 본다. qg 가 이미 커밋 범위를 받으므로 새로 만들 것이 적다. 고침이 다른 곳을 깨뜨린 것은 리뷰가 아니라 머지 전 스위트 대조가 잡는다.
3. **다시 보지 않는다.** qg 는 한 번, 고침은 구현 담당자와 머지 전 스위트 대조 · 통합 리뷰에 맡긴다. 가장 싸지만 고침이 지적을 풀었는지를 qg 가 확인하지 않는다.

**고른 것: 2** — 사용자(U7 「2」). 3 은 지금 qg 가 주던 「고친 것을 다시 확인한다」 를 잃고, 1 은 같은 코드를 통째로 여러 번 보는 비용이 든다.

길이 하나라 작성자가 정한 것(D7–D9): qg 에서 반복 장치를 남김없이 걷어낸다(반쯤 남기면 모델이 읽는 본문에 죽은 갈래가 남는다) · 돌려보내는 주체는 지휘자다 · 머지 앞 리뷰의 자리는 걸음표의 「검수」 걸음(옛 형식 로드맵은 걸음 5)이다.

## 설계

### §1 qg — 한 번 보고 끝난다

한 실행의 흐름은 Preflight → trivia 판단 → 리뷰 → 리뷰 축 합성 → 차등 테스트 → 합성 · 판정 → e2e 질문과 걷기 → 최종 판정 → 게시 → intent-critic 이다. 지금 흐름에서 반복 고리만 빠진다.

걷어내는 것:

- 본문의 `## Fix-loop` 절 전부 — 분류표(Step 5) · 고치기 결정 질문 · 상한 도달 질문(Max-iter) · 고침의 파일 쓰기 · 오류 처리 절 · 제외 결과 줄 펜스.
- 범위로 부른 실행의 끝내기 질문(「지금 판정으로 끝내기」 · 「멈추기」).
- 반복 번호와 상한(`iteration N` · `CAP`), 세션 폴더의 `excluded.md` · `extra-iterations.md` · `classification.md`.
- e2e 걷기 직후 게이트의 선택지 가운데 코드를 고치거나 리뷰를 다시 도는 것(「고치고 다시 돌기」 · 「리뷰·테스트부터 다시」 · 「한 번 더 돌기」)과 「멈추기」.
- 판정 줄의 「제외 패치」 · 반복 번호 칸과 결과의 `accepted with findings iter N` · `aborted iter N`, 게시의 `skipped: aborted` 갈래.

남는 것(바꾸지 않는다): 리뷰어 구성과 재비판 · 낮춘 지적 게이트(되올려 다시 합성하기 — 코드를 고치지 않는다) · 차등 테스트 · e2e 질문과 걷기, 「다시 걷기」 · 최종 판정의 판정값과 우선순위 · 게시 · intent-critic 단계와 돌려주는 꼴.

막는 지적이나 차등 결함으로 끝난 실행:

- 묻지 않는다. 판정 줄, 고칠 목록, 「고친 뒤 다시 부른다」 한 줄로 끝난다.
- 고칠 목록은 지금 표면화(Step 4.5)가 보이는 지적과 `**고칠 방법:**` 을 막는 지적 · 제안 · 차등 회귀로 갈라 실은 것이고, `result.md` 에 한 절로 남는다. 새 파일을 만들지 않는다.
- 게시는 판정 그대로 한다(범위로 부른 실행은 지금처럼 달지 않고 공시한다). 막는 지적이나 차등 결함으로 끝난 직접 호출도 그 판정을 PR 코멘트로 게시한다 — 「멈추기」 로 게시를 피하던 길은 없어진다(사용자 확인 — 결정 기록 D1.1). 사용자가 받아들였는지를 묻던 자리가 없어지므로 게시 글에 「받아들임」 표시도 없다.
- 걷는 사이 코드가 바뀐 걷기는 e2e 칸에 무효로 남기고 끝낸다 — 리뷰를 다시 돌려면 qg 를 다시 부른다.

본문의 Law 2 문단은 「저장소에 쓰는 자리는 intent-critic 답 파일과 그 커밋 하나」 로 고쳐 쓴다. 세션 상태 폴더 · 일회용 worktree 는 저장소 쓰기가 아니라는 것을 같은 문단이 한 구절로 가른다(넘겨받은 행 7).

판은 quality-gates major 다.

### §2 지휘 — 머지 앞 리뷰 자리

`qg-review.md` 의 자리 넷 가운데 「에픽 머지 뒤」 가 「머지 앞」 으로 바뀐다.

| 칸 | 머지 앞 |
|---|---|
| 언제 | 구현 담당자가 돌아와 구현 대조와 PR 열기(걸음 4)가 끝난 뒤, 걸음 5 의 스위트 대조 앞 |
| 시작 | 그 PR 의 바탕 — 기본 브랜치에서 갈라진 커밋(`git merge-base origin/HEAD <브랜치>`). 앞 계획 브랜치에 쌓은 PR 이면 그 앞 브랜치의 끝 |
| 끝 | 보낼 때의 브랜치 끝 |
| 원문 | 에픽 묶음 |
| 「잘못 골랐다」 | §4 |
| 기록이 실리는 곳 | 에픽 브랜치(에픽 PR 과 함께 머지) — 구현 담당자가 돌아온 뒤라 그 브랜치에 쓸 수 있다 |

- 단위는 에픽이다(U10) — 에픽마다 설계에 한 번(spec 승인 앞), 에픽 PR 에 한 번(머지 앞)이다. 에픽에 PR 이 여럿이면 PR 마다 보낸다(리뷰가 머지보다 앞이어야 한다). 지휘자가 스스로 여는 PR(로드맵 수정 · 지휘자 수리 · 기록만 담은 PR)에는 자동으로 걸지 않는다.
- 통합 리뷰 뒤 반영의 고침은 qg 를 다시 거치지 않는다 — 그 고침은 통합 리뷰의 좁은 재리뷰와 완료 전 확인이 본다.
- 머지 앞 리뷰를 보낸 뒤 그 PR 의 되돌리기(§3)가 끝날 때까지 지휘자는 그 에픽 브랜치에 기본 브랜치를 합치지 않는다 — 걸음 6 의 「열린 에픽 브랜치마다 기본 브랜치를 merge」 와 걸음 4 의 「구현 agent 가 돌아오면 에픽 브랜치에 기본 브랜치를 merge」 둘 다 그 브랜치에서는 되돌리기가 끝난 뒤로 미룬다. 걸음 4 의 합치기는 구현 담당자가 처음 돌아온 때(머지 앞 리뷰를 보내기 전)에만 하고, 되돌리기를 고치고 돌아온 때에는 하지 않는다.
- 걸음 5 의 기본 순서는 PR 캐시 새로 채우기 → 머지 앞 qg 리뷰와 되돌리기(§3) → 스위트 대조 → 통합 리뷰 → 리뷰 뒤 반영 → 완료 전 확인이다. qg 를 스위트 대조 앞에 두는 것은 고침이 끝난 트리를 대조하려는 것이다. qg 담당자와 스위트 대조를 같은 때 돌리지 않는 지금 규칙은 그대로다.
- 걸음 6(머지 뒤)에서 qg 담당자를 보내는 문장과 「에픽 머지 뒤」 자리를 지운다. 머지된 PR 의 범위를 내는 스크립트는 사용자가 머지된 에픽의 리뷰를 이름으로 청할 때만 쓰인다 — 그 길은 그대로 둔다.
- 「spec 승인 앞」 · 「로드맵 끝」 · 「이름으로 청함」 자리는 그대로다. 이름으로 청한 「spec 승인 뒤 · 머지 전 에픽」 은 구현 담당자가 아직 일하는 중이면 지금 줄대로(재분해 신호 · 기록 브랜치), 구현이 끝난 뒤면 이 「머지 앞」 줄대로 한다.
- 담당자에게 보내는 글의 미리 받은 답에서 「범위 모드의 끝내기 질문」 줄을 뺀다(그 질문이 없어진다). 「낮춘 지적」 질문의 「그대로 둔다」 는 남는다.
- team 형식 로드맵: 리더가 곧 지휘 세션이다 — qg 를 부르는 길은 옛 형식과 같다(`qg-review.md` 의 담당자). 걸음표 「검수」 행의 도구 칸에 qg 를 통합 리뷰어 옆에 ` · ` 로 더한다 — 도구 칸은 걸음표 검사가 보지 않는 보여 주기 칸이다(검사는 칸 수 · 머리 행 · 단계 · 관문만 본다). 리더가 쓰는 검수 결과 파일의 첫 줄(반려 여부 한 줄)과 지적 목록에 qg 의 막는 지적이 들어가고, 반려는 지금 규칙대로 시작 묶음의 다음 시도로 구현 걸음에 돌아간다. 걸음 · 관문 · 시작 묶음의 코드는 고치지 않는다.
- team 형식에서도 §3 의 규칙은 같고, 달라지는 것은 실어 나르는 자리뿐이다 — 지적 목록은 보내는 글이 아니라 검수 결과 파일로 가고(다음 시도가 가장 새 검수 결과 파일을 읽는다), 지적별 처리는 다음 시도의 구현 결과 파일에 적게 한다(그 지시는 과제 결정 기록의 한 줄로 적어 시작 묶음이 싣게 한다). 고치지 않은 막는 지적을 사용자에게 묻는 것과 좁은 재리뷰는 옛 형식과 같다(작성자 제안 — spec 리뷰 1라운드의 참고 지적).
- team 형식의 검수 걸음은 PR 이 아직 열리지 않은 때다(PR 이 열리면 걸음이 머지로 넘어간다). 그래서 옛 형식이 PR 본문 `## qg 리뷰` 에 적는 것 — 리뷰 범위와 판정 줄, 지난 리뷰의 끝 커밋, 돌려보낼 막는 지적 목록, 재리뷰 횟수, 멈출 조건 — 을 team 형식에서는 리더가 쓰는 검수 결과 파일(검수 시도마다 하나)의 지적 목록 아래에 적고 거기서 세며, PR 이 열리면 그 내용을 본문 `## qg 리뷰` 절로 옮긴다(사용자 결정 — 결정 기록 D28). 검수 결과 파일의 형식이 그 자리를 막는지는 계획의 첫 과제가 형식 정본에서 확인하고, 막으면 과제 결정 기록의 줄로 적는다 — 어느 쪽도 형식 정본을 고치지 않는다.
- team 형식의 상한도 §3 의 「두 번까지」 다 — 좁은 재리뷰를 위 검수 결과 파일의 기록으로 세고, 두 번째 뒤에도 막는 지적이 남으면 같은 선택지 셋으로 사용자에게 묻는다. 시작 묶음의 연속 실패 멈춤은 받음 줄이 없는 시도만 실패로 세어, 이미 받아진 뒤 qg 가 반려한 시도를 세지 않는다 — 상한으로 쓰지 않는다(사용자 결정 — 결정 기록 D24. D15 를 바꿨다).
- spec-distill `dependencies.md` 의 quality-gates 행과 README 의 자리 설명을 새 자리 이름에 맞춘다.

### §3 고칠 일 되돌리기와 좁은 재리뷰

담당자가 돌아오면 지휘자는 지금처럼 판정 줄 · 지적 목록 · 낮춘 지적 표 · intent-critic 결과 줄 · 질문 전부를 보인다. 그 뒤가 달라진다.

- **돌아온 즉시 목록을 적는다.** 질문을 묻기 전에, 담당자의 마지막 보고에 실린 막는 지적 · 차등 결함 목록(고칠 방법 포함, 합쳐지기 전 목록)을 PR 본문 `## qg 리뷰` 절에 글자 그대로 적는다(team 형식은 §2 의 검수 결과 파일). 돌려보내는 글은 그 절에서 싣는다 — 답을 기다리는 사이 세션이 압축되거나 바뀌어도 돌려보낼 목록이 남는다(사용자 결정 — 결정 기록 D30).
- **의도 점검 질문이 함께 오면 질문부터 묻는다.** 같은 리뷰가 막는 지적 · 차등 결함과 의도 점검 질문을 함께 돌려주면 지휘자는 질문을 먼저 묻고, 답을 받은 뒤에 돌려보낸다. 「잘못 골랐다」 가 하나라도 있으면 돌려보내지 않고 §4 로 간다 — 그때의 막는 지적은 PR 본문 `## qg 리뷰` 에 「돌려보내지 않음」 으로 적어 설계 대화의 입력에 함께 넣고, 고친 설계의 구현이 다시 받는 머지 앞 리뷰가 본다. 없으면 아래대로 돌려보낸다(사용자 결정 — 결정 기록 D26).
- **막는 지적 · 차등 결함이 있으면** 묻지 않고 구현 길로 돌려보낸다. 걸음 5 의 「리뷰 뒤 반영」 과 같은 길이다 — 고침은 `superpowers:receiving-code-review` 로 받고, 그 구현 담당자가 아직 살아 있으면(격리 worktree 가 남아 있으면) 이어 부르고 아니면 새 구현 담당자를 같은 브랜치로 보낸다. 보내는 글에 지적 목록을 글자 그대로 싣고(경로로 넘기지 않는다), 마지막 보고에 지적마다 처리 하나 — 고친 커밋 · 반박과 그 사유 · 손대지 않음 — 를 적게 한다. 합성 표가 한 행으로 합친 지적은 담당자 보고의 합쳐지기 전 목록으로 센다.
- **제안은 보이기만 한다.** 사용자가 고르면 그 제안을 같은 되돌리기에 넣는다.
- **막는 지적 없이 끝난 리뷰에서도** 사용자가 제안을 고르거나 낮춘 지적을 되올리면 그것만으로 되돌리기를 새로 연다 — 같은 길로 돌려보내고, 고친 커밋을 좁은 재리뷰로 다시 보며, 그 재리뷰를 「두 번까지」 에 센다(사용자 결정 — 결정 기록 D32).
- **낮춘 지적은 표로 보이고**, 사용자가 되올리라고 하면 qg 를 다시 돌리지 않고 다음 되돌리기에 원래 심각도로 넣는다. 그 고침은 좁은 재리뷰가 본다.
- **설계에 닿는 지적은 고치지 않는다.** 지휘자는 미리 가르지 않고 막는 지적 전부를 보낸다. 가르는 쪽은 구현 담당자다 — 고치려면 설계문서의 글자 · 수용 기준 · 사용자에게 보이는 동작을 바꿔야 하는 지적은 고치지 않고 돌려보내고, 지휘자가 사용자에게 옮긴다(지금 `conductor-dispatch.md` 의 사람 자리 규칙 — 새 질문 자리가 아니다). 이 설계가 더하는 질문 자리는 아래 「고치지 않은 막는 지적」 과 「두 번까지」 의 둘이다.
- **고치지 않은 막는 지적.** 구현 담당자가 돌아오면 지휘자는 돌려보낸 막는 지적마다 그 보고의 처리를 본다. 반박했거나 손대지 않은 막는 지적이 하나라도 있으면 그 지적은 좁은 재리뷰가 통과해도 풀린 것으로 세지 않는다(좁은 재리뷰는 고친 커밋만 본다) — 담당자의 사유와 함께 사용자에게 묻는다. 선택지는 「다시 돌려보낸다」 · 「반박을 받아들이고 남긴 지적으로 적는다」 · 「이 에픽을 멈춘다」 이고 설명은 얻음 · 내줌 한 줄씩이다. 고친 커밋이 하나도 없이 돌아온 때도 같다. 머지 준비로 가는 것은 막는 지적이 모두 고쳐졌거나 사용자가 남기기로 한 뒤다.
- **좁은 재리뷰.** 고친 커밋이 올라오면 qg 를 `range <지난 리뷰의 끝>..<고친 뒤의 끝>` 으로 다시 보낸다. 지난 리뷰의 끝은 지휘자가 그 리뷰를 보낼 때 호출 줄에 쓴 끝 커밋이다(PR 본문 `## qg 리뷰` 에 적어 둔다) — 돌려준 `reviewed_head` 는 그 값과 같은지 견주는 데만 쓴다(의도 점검이 꺼졌거나 리뷰 트리를 만들지 못한 실행은 그 칸이 비어 온다). 그 사이 지휘자가 에픽 브랜치에 커밋한 기록(설계문서의 지휘 기록 · 기록 파일)이 범위에 들 수 있다 — 따로 빼지 않는다(레포의 문서 경로 설정이 거르면 리뷰 diff 에서 빠지고, 아니면 리뷰어가 본다). 범위에 기본 브랜치를 합친 커밋이 끼어 있으면(§2 의 미루기를 지키지 못한 때) 좁게 보지 않고 그 PR 을 처음부터 다시 보며, 재리뷰 한 번으로 세고 이유를 PR 본문에 적는다. 범위에 구현 담당자의 고친 커밋이 하나도 없으면 보내지 않는다. 호출 줄의 꼴 · 담당자 틀 · 보관 · 「이미 보낸 것」 확인은 첫 리뷰와 같다.
- **두 번까지.** 좁은 재리뷰는 PR 하나에 두 번까지다. 첫 재리뷰를 보내기 전에 멈출 조건을 PR 본문에 적는다. 두 번째 재리뷰에도 막는 지적이 남으면 멈추고 사용자에게 묻는다 — 선택지는 「한 번 더 돌려보낸다」 · 「남은 지적을 적고 머지 준비로 간다」 · 「이 에픽을 멈춘다」 이고 설명은 얻음 · 내줌 한 줄씩이다. 통합 리뷰의 좁은 재리뷰 횟수와는 따로 센다.
- **좁은 재리뷰의 의도 점검.** qg 호출 줄에 인자를 더하지 않으므로 좁은 재리뷰에서도 intent-critic 단계가 돈다. 돌아온 질문은 거르지 않는다 — 정체가 앞 리뷰와 같아도 지금 규칙대로 묻고, 「같은 대상에 전에 물은 것」(앞 리뷰의 질문 글과 답)을 앞 글에 함께 보인다. 정체는 출처 · 대상 · 종류로만 만들어져 내용이 다른 새 의심일 수 있고, 질문 글은 리뷰어가 실행마다 새로 써서 글자로 견주는 거르기는 발동하지 않는다(사용자 결정 — 결정 기록 D31. D11 · D25 를 바꿨다). 같은 의심을 다시 답하는 비용은 qg 가 지휘 경유 답을 알게 되는 R6 이 줄인다(`## 미룸`). qg 의 입력과 스크립트는 바뀌지 않고, 적는 곳은 qg 의 답 자리가 아니라 지휘자의 기록 파일이다.
- **PR 본문.** `## qg 리뷰` 절에 첫 리뷰의 범위와 판정 줄, 돌아온 막는 지적 목록(돌아온 즉시 적는다)과 그 가운데 돌려보낸 것, 좁은 재리뷰마다 범위와 판정 줄, 멈출 조건, 고치지 않은 막는 지적의 사유와 사용자 답, 남긴 지적을 적는다. 사용자가 남기기로 한 막는 지적은 `## 통합 리뷰 인계` 절에도 받는 에픽과 함께 적는다 — 뒤 에픽의 통합 리뷰 묶음이 싣는 절이 그 절뿐이다(작성자 제안 — spec 리뷰 1라운드의 참고 지적). 고치는 쪽은 지휘자다(지금 통합 리뷰 인계 절을 적는 것과 같은 길) — 첫 리뷰가 돌아온 뒤와 좁은 재리뷰가 돌아올 때마다 고친다.

### §4 머지 앞의 「잘못 골랐다」

머지 앞 리뷰의 의도 점검 질문은 지금 틀의 라벨 셋과 순서 그대로 묻는다. 「잘못 골랐다」 의 선택지 설명이 「머지를 멈추고 이 에픽 안에서 고친다」 로 바뀌고, 질문 글이 짧아진다(U11).

- **묻는 틀을 줄인다.** 질문 창의 질문 문장에는 대상 이름(에픽 이름 또는 「로드맵」)과 리뷰어가 쓴 질문 한 문장만 싣는다. 의심하는 인용 · 근거의 종류와 관찰 · 같은 대상에 전에 물은 것 · 「이유를 남기려면 직접 입력 칸에」 안내는 질문 앞의 따로 된 글에 질문 번호와 함께 둔다. 지휘자의 틀(`qg-review.md` 의 `## 묻기`)과 qg 가 직접 물을 때의 틀(`references/intent-critic.md`) 둘 다 같게 줄인다 — 자리 넷 모두에 적용된다.
- **리뷰어의 질문 글은 질문 한 문장과, 있으면 직접 확인 한 줄이다.** 리뷰어 정의(`agents/intent-critic.md`)의 `question` 칸 지시를 「한두 문장」 에서 「질문 한 문장 — 직접 확인해 볼 자리가 있으면 그 뒤에 『여기는 직접 확인해 보세요』 한 줄」 로 줄인다. 묻는 틀(지휘자 · qg 직접)이 그 글의 첫 문장만 질문 창에 싣고 나머지 줄은 앞 글에 싣는다. 배경은 따로 쓰게 하지 않는다 — 앞 글에 싣는 근거 줄과 읽은 인용이 배경이다. 리뷰어의 출력 칸 · 스크립트 · 돌려주는 꼴의 칸, 무엇을 의심하고 어떤 근거로 묻는지의 규칙은 바꾸지 않는다(사용자 결정 — 결정 기록 D29. `observation` 은 리뷰어가 쓰는 칸이 아니라 스크립트가 근거 줄과 읽은 인용으로 채우는 칸이다).

- 하나라도 있으면 그 PR 의 머지 명령 줄을 내지 않는다. 열린 PR 은 닫지 않고 둔다.
- 그 에픽의 설계 대화로 돌아가 그 질문과 답을 입력으로 설계문서를 고친다(에픽 브랜치에서). 그 뒤는 지금 길이다 — spec 승인 앞 qg 리뷰 → spec 리뷰 → 승인 → 고친 범위의 계획 → 구현 → 다시 머지 앞 리뷰.
- 그 다시 받는 머지 앞 리뷰는 새 리뷰다 — PR 전체(그 PR 의 바탕부터 새 끝까지)를 처음부터 보고, 좁은 재리뷰 「두 번까지」 도 새로 센다(사용자 결정 — 결정 기록 D33). 「이미 보낸 것」 확인이 이 리뷰를 막지 않게, 설계 대화로 돌아가기 전에 머지 앞 자리의 다시 보내기 표지를 적는다 — spec 승인 앞 자리의 다시 보내기 표지(§6 행 28)와 같은 꼴로 사건의 정체(돌아가게 한 질문의 정체)를 적어 같은 사건은 한 번만 센다. 앞 리뷰와 겹치지 않는 보관 폴더 · 기록 파일의 이름은 계획이 정한다.
- 고칠 것이 그 에픽의 범위(다른 에픽의 경계 · 예약 파일)를 넘으면 설계를 고치지 않고 재분해 신호로 사용자에게 보인다.
- 「의도다」 · 「지금은 모르겠다」 는 기록만 하고 머지 준비를 잇는다.
- 담당자 보고에 「이미 『잘못 골랐다』 답이 있어 거른 질문」 목록이 있으면 지휘자는 그 질문을 「앞서 잘못 골랐다고 답한 것이 아직 그대로다」 로 보이고 같은 행선을 적용한다(넘겨받은 행 24).

### §5 직접 부른 qg

지휘자 없이 부른 실행도 §1 그대로다 — 고칠 목록을 내고 끝나며 「고칠까요」 를 묻지 않는다. 고치려면 그 세션에서 따로 시키고, 고친 뒤 qg 를 다시 부른다.

- 그 실행의 intent-critic 끝 안내(할 일 줄)는 지금 「잘못 골랐다」 답이 새로 나왔을 때만 「같은 브랜치에서 이어 고친다」 를 낸다. 이미 그 답이 있어 거른 질문이 있을 때도 그 질문을 가리켜 같은 줄을 낸다(넘겨받은 행 4). 돌려주는 꼴의 판은 바꾸지 않는다.
- push 할 일 줄의 「게시된 판정」 문구는 게시를 건너뛴 실행에서 나오지 않게 한다(넘겨받은 행 7).

### §6 지휘 절차 문서의 남은 가장자리

§2–§4 가 `qg-review.md` 와 `conducting.md` 의 qg 문장을 다시 쓴다. 같은 파일에 앞 에픽이 미뤄 둔 여덟 행을 함께 닫는다(작성자 제안 D14 — 정확한 문장은 계획이 정한다). 여덟 행 모두 절차 문서(모델이 따르는 글)의 문장과 그 락이다 — 스크립트를 고치지 않는다. 테스트 파일을 고치는 것은 행 21 의 하한 하나다. 행 30 이 보는 agent 목록은 걸음 1 의 맞추기 순서가 이미 조회하는 것이다.

| 행 | 무엇 | 닫는 길 |
|---|---|---|
| 21 | 구현 리뷰가 미룬 잔손질 | `qg-review.md` 가 `<SD>` 를 스스로 정의한다 · 「설치돼 있지 않으면」 규칙은 `qg-review.md` 한 곳에만 둔다 · 다시 쓰는 문장의 락은 본문에만 있는 글로 묶는다 · 처분 줄 테스트의 「에이전트 도출」 하한을 내장 agent 이름을 뺀 수로 센다 |
| 22 | 걸음 1 이 기다리는 질문 절을 읽는 길을 가리키지 않는다 | 걸음 1 의 그 문장에 읽는 길(에픽 줄은 상태 보기, 로드맵 단위 줄은 기계 상태 파일의 그 절)을 한 구절로 더한다. 명령을 새로 만들지 않는다 |

이름으로 청한 R3 리뷰(머지된 PR #313)의 막는 지적 가운데 `qg-review.md` 의 둘도 같은 PR 에서 닫는다(사용자 결정 — 결정 기록 D27). 둘 다 절차 문서의 문장과 그 락이다.

- 「같은 대상에 전에 물은 것」 찾기에서 질문의 정체를 셸 따옴표 안에 넣지 않는다 — 정체를 파일로 쓰고 찾는 명령에 그 파일로 넘긴다(`git grep -F -f <파일>` · `grep -x -F -f <파일>`). 정체는 리뷰 대상의 글에서 온 값이라 셸이 풀어 읽으면 안 된다.
- 「이미 보낸 것」 확인은 보관 폴더 이름과 쌓인 기록 줄의 자리 글자를 앞자리가 아니라 통째로 견준다 — 자리 글자 바로 뒤가 구분 글자(`-`)이거나 끝일 때만 같은 것으로 본다(PR 3번과 31번을 가른다). 머지 앞 자리의 자리 글자에도 같은 규칙을 쓴다.

## Acceptance Criteria

- **AC1** qg 본문에 고치기 반복이 없다 — `## Fix-loop` 절, 분류표, 「고치고 다시 돌기」 · 「한 번 더 돌기」 선택지, 범위로 부른 실행의 끝내기 질문이 없고, Flow 그림이 한 번 지나는 흐름이다.
- **AC2** 막는 지적이나 차등 결함으로 끝난 실행은 그 일로 사용자에게 질문하지 않고 판정 줄 · 고칠 목록 · 「고친 뒤 다시 부른다」 한 줄로 끝난다. 고칠 목록은 막는 지적 · 제안 · 차등 회귀로 갈려 `result.md` 에 남는다. 열린 PR 이 있는 브랜치에서 직접 부른 실행이면 그 판정이 PR 코멘트로 게시된다.
- **AC3** 본문의 Law 2 문단이 저장소에 쓰는 자리를 intent-critic 답 파일과 그 커밋 하나로 말한다.
- **AC4** e2e 걷기 직후 게이트에 코드를 고치거나 리뷰를 다시 도는 선택지와 「멈추기」 가 없다. 걷는 사이 코드가 바뀐 걷기는 e2e 칸에 무효로 남는다.
- **AC5** 판정 줄에 제외 패치 · 반복 번호 칸이 없다. 판정 스크립트에 그 두 인자를 주면 받지 않는다는 사유와 함께 사용법 오류로 끝난다. 게시에 `skipped: aborted` 갈래가 없다.
- **AC6** qg 의 본문 · reference · 스크립트 어디도 `excluded.md` · `extra-iterations.md` · `classification.md` 를 쓰거나 읽지 않는다.
- **AC7** `security-reviewer.md` 의 변경이 `iteration` 입력 칸 선언을 지우는 데 그치고, 그 칸을 채우던 dispatch 줄이 qg 본문에 없다(입력 칸 선언과 전달의 짝을 재는 검사가 통과한다). `code-recritic.md` 의 변경이 반복을 가리키는 낱말에 그친다. 두 파일 모두 규칙 · 임계치 · 처방 문장의 diff 가 없다.
- **AC8** `qg-review.md` 의 자리 표에 「머지 앞」 줄이 있고(언제 · 시작 · 끝 · 원문 · 「잘못 골랐다」 · 기록 자리) 「에픽 머지 뒤」 자동 자리가 없다. 담당자 틀의 미리 받은 답에 끝내기 질문 줄이 없다.
- **AC9** `conducting.md` 지휘 순환 걸음 5 와 손 절차의 맞은편 걸음에 머지 앞 리뷰로 들어가는 문장이 있고 스위트 대조보다 앞이다. 걸음 6 과 그 맞은편에 머지 뒤 qg 를 보내는 문장이 없다.
- **AC10** 머지 앞 리뷰가 막는 지적이나 차등 결함을 돌려주면 절차는 사용자에게 묻지 않고 구현 길로 돌려보내게 하고(지적 목록을 글자 그대로 실어), 제안은 보이기만 하게 한다. 사용자가 되올린 낮춘 지적은 다음 되돌리기에 원래 심각도로 들어간다. 담당자가 돌아오면 질문을 묻기 전에 막는 지적 목록을 PR 본문 `## qg 리뷰` 절(team 형식은 검수 결과 파일)에 글자 그대로 적고, 돌려보내는 글은 거기서 싣게 한다. 막는 지적 없이 끝난 리뷰에서 사용자가 제안을 고르거나 낮춘 지적을 되올리면 되돌리기를 새로 열고 그 좁은 재리뷰를 두 번에 세게 한다. 같은 리뷰가 의도 점검 질문을 함께 돌려주면 질문을 먼저 묻고, 「잘못 골랐다」 가 하나라도 있으면 돌려보내지 않게 한다. team 형식에서는 지적 목록이 검수 결과 파일로 간다고 절차가 말한다.
- **AC11** 좁은 재리뷰는 지휘자가 지난 리뷰를 보낼 때 쓴 끝 커밋부터 고친 뒤의 끝까지의 범위로 qg 를 부르고 PR 하나에 두 번까지다(team 형식도 같은 두 번이고 PR 이 열리기 전에는 검수 결과 파일의 기록으로 센다고 절차가 말한다). 돌려준 `reviewed_head` 가 비어 와도 그 범위를 만들 수 있다. 범위에 기본 브랜치를 합친 커밋이 끼면 처음부터 다시 보고 재리뷰 한 번으로 센다고 절차가 말하고, 머지 앞 리뷰를 보낸 뒤 되돌리기가 끝날 때까지 그 브랜치에 기본 브랜치를 합치지 않게 한다(걸음 4 와 걸음 6 의 합치기 둘 다). 두 번째 뒤에도 막는 지적이 남으면 선택지 셋(얻음 · 내줌 설명)으로 사용자에게 묻는다. 좁은 재리뷰가 돌려준 의도 점검 질문은 거르지 않고, 같은 대상에 전에 물은 것과 답을 앞 글에 함께 보이게 한다.
- **AC19** 되돌리기에 보내는 글이 마지막 보고에 지적마다 처리(고친 커밋 · 반박과 사유 · 손대지 않음)를 적게 한다. 반박했거나 손대지 않은 막는 지적이 있으면(고친 커밋이 하나도 없이 돌아온 때 포함) 절차는 좁은 재리뷰의 판정과 무관하게 선택지 셋(다시 돌려보낸다 · 반박을 받아들이고 남긴 지적으로 적는다 · 이 에픽을 멈춘다 — 얻음 · 내줌 설명)으로 사용자에게 묻게 하고, 결과를 PR 본문 `## qg 리뷰` 에 적게 한다. 사용자가 남기기로 한 막는 지적은 `## 통합 리뷰 인계` 절에도 받는 에픽과 함께 적게 한다. team 형식에서는 지적별 처리를 다음 시도의 구현 결과 파일에 적게 한다.
- **AC20** 의도 점검 질문의 질문 문장이 대상 이름과 리뷰어의 질문 한 문장만 싣는다 — 지휘자의 묻기 틀과 qg 가 직접 묻는 틀 둘 다. 의심하는 인용 · 근거 · 전에 물은 것 · 이유 남기는 안내는 질문 앞의 글에 있다. 리뷰어 정의의 `question` 칸 지시가 「질문 한 문장과, 있으면 직접 확인 한 줄」 이고 출력 예시의 `question` 이 모두 질문 한 문장이며, 그 파일의 diff 가 그 지시와 출력 예시의 `question` 줄에 그친다. 묻는 틀 둘이 그 글의 첫 문장만 질문 창에 싣고 나머지 줄을 앞 글에 싣는다.
- **AC21** `qg-review.md` 가 자동 자리의 단위를 에픽(설계 한 번 · 에픽 PR 마다 한 번)으로 말하고, 지휘자가 스스로 여는 PR 에는 자동으로 걸지 않는다고 말한다. 통합 리뷰 뒤 반영의 고침은 qg 를 다시 거치지 않는다고 말한다.
- **AC12** 머지 앞 의도 점검에서 「잘못 골랐다」 가 하나라도 있으면 절차는 그 PR 의 머지 명령 줄을 내지 않고 그 에픽의 설계 대화로 돌아가게 하며, 범위를 넘으면 재분해 신호로 보이게 한다. 그 질문의 「잘못 골랐다」 선택지 설명이 이 행선을 말한다. 담당자 보고의 거른 「잘못 골랐다」 목록도 같은 행선이다. 설계를 고친 뒤 다시 받는 머지 앞 리뷰는 PR 전체를 처음부터 보고 재리뷰 횟수를 새로 센다고 절차가 말하고, 다시 보내기 표지를 설계 대화로 돌아가기 전에 적게 한다.
- **AC13** 기본 걸음표의 「검수」 행 도구 칸에 qg 가 있고 걸음표 검사가 그 표를 맞다고 낸다. team 형식 절차가 qg 의 막는 지적을 검수 결과 파일의 반려 줄과 지적 목록에 싣게 한다.
- **AC14** 직접 부른 실행에서 이미 「잘못 골랐다」 답이 있어 거른 질문이 있으면 끝 안내가 그 질문을 가리켜 「같은 브랜치에서 이어 고친다」 를 낸다. 돌려주는 꼴의 `contract` 는 2 그대로다. 게시를 건너뛴 실행의 push 안내에 「게시된 판정」 이 없다.

## Rejected Alternatives

- **반복 번호와 상한을 남기고 「고치기」 선택지만 뺀다.** 고칠 파일은 줄지만 모델이 읽는 본문에 늘 1 인 반복 · 닿지 않는 상한 갈래가 남아 오독을 부른다.
- **구현 담당자가 끝에 qg 를 스스로 부른다.** 지휘자가 옮길 것은 줄지만 부르는 입구가 둘이 되고(S28 과 부딪친다), 백그라운드 담당자는 qg 의 질문에 답할 수 없다.
- **머지 뒤 리뷰를 그대로 두고 머지 앞을 더한다.** 같은 코드를 두 번 본다.
- **고칠 때마다 qg 전체를 다시 돈다 · 다시 보지 않는다.** `## Approaches` 의 1 · 3.
- **좁은 재리뷰에서 의도 점검을 끄는 인자를 qg 에 더한다.** 비용은 줄지만 호출 줄의 꼴이 둘이 된다. 거르지 않고 전에 물은 것과 답을 함께 보이는 지침으로 받고, qg 가 답을 알게 하는 일은 R6 이 받는다.
- **좁은 재리뷰에서 같은 정체의 질문을 거른다(정체만으로, 또는 정체와 질문 글이 모두 같을 때).** 다시 답할 일은 줄지만, 정체만으로 거르면 내용이 다른 새 의심을 버리고, 글자까지 견주면 질문 글이 실행마다 새로 쓰여 발동하지 않는다. 거르지 않는다(D31).
- **qg 쪽과 지휘 쪽을 PR 둘로 나눈다.** 리뷰는 가벼워지지만 로드맵 블록의 브랜치를 하나 더 예약해야 하고, 그 사이 담당자 틀이 없어진 질문을 가리킨다. 한 PR 에서 qg 쪽 과제를 먼저 두는 순서로 받는다.
- **지휘자가 스스로 여는 PR 까지 자동으로 건다(PR 마다).** 리뷰 없이 머지되는 PR 은 없어지지만, 문서만 바뀐 로드맵 수정 PR 도 qg 한 번(담당자 하나에 수십만 토큰)을 기다린다. 단위를 에픽으로 둔다(U10).
- **좁은 재리뷰에 앞 리뷰의 지적 목록을 넘겨 qg 가 남은 지적을 판정하게 한다.** 일부만 고친 경우를 qg 가 잡지만 호출 줄에 새 입력이 생긴다(D13 과 부딪친다). 구현 담당자의 지적별 처리 보고와 지휘자의 견줌으로 받는다(D21).
- **걸러진 「잘못 골랐다」 를 돌려주는 꼴의 새 칸으로 싣는다.** 지휘자가 읽는 계약의 판이 오른다. 담당자 보고의 목록(지휘 경유)과 끝 안내(직접 호출)로 받는다.

## Handoff Context

계획 담당자가 이 문서만 읽고 이어 가는 데 필요한 것이다.

- **먼저 읽을 것.** `## 결정 기록`(뒤 줄이 앞 줄을 바꾼다 — D24 가 D15 를, D31 이 D11 · D25 를 바꿨다) → `## 설계` §1–§7 → `## Acceptance Criteria` → `## 미룬 행 대조`.
- **다시 뽑을 것.** 고치기 반복을 읽는 자리의 목록(락 · reference · 스크립트 · agent 정의). 조사 보고는 git 이 추적하지 않는 폴더에 있어 없을 수 있다 — 그때의 기본 브랜치에서 `git grep -n -e 'Fix-loop' -e 'iteration' -e 'excluded.md' -e 'extra-iterations.md' -e 'classification.md' -e 'accepted with findings' -e 'aborted' -- plugins/quality-gates shared/tests` 로 다시 뽑는다.
- **첫 과제가 확인할 것.** 은퇴하는 kill switch 가 없는지 · 옆 에픽과 겹치는 자리의 그때 글(둘 다 Constraints) · 검수 결과 파일의 형식이 qg 리뷰 기록을 받는지(§2).
- **이 PR 에서 못 하는 것.** 머지 앞 리뷰 → 되돌리기 → 좁은 재리뷰의 실제 한 바퀴(`## 미룸` — 손 확인은 R8 이 받는다).
