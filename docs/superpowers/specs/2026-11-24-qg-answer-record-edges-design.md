# R8 — qg 답 기록 · 다른 팀 읽기 뒤처리 · Design

> 의도 점검이 받은 답을 남기고 읽는 길과 다른 팀 작업을 읽는 길에서, 조용히 사라지거나 틀린 말로 남는 가장자리를 닫는다 — 직접 쓴 답은 버려지지 않고, 읽지 못한 것은 맞는 이유와 함께 「확인 못 함」 으로 남고, 올리지 않은 작업의 글은 git 에 실리지 않는다.

## Context / Why

앞 에픽들(R1 · R2 · R4 · R5 · R6)과 그 리뷰가 qg 의 의도 점검 스크립트 넷에 남긴 가장자리가 스물다섯 개쯤 있고, 기본 브랜치 a60ede94 에서 모두 그대로다(설계 전 조사 — 지휘 자원 `report/R8/design-prep.md`). 성격은 셋이다.

- **조용히 사라진다.** 답을 받아 적을 때 질문 표시가 어긋나면 사용자가 직접 쓴 글이 어디에도 남지 않는다. 읽지 못한 다른 팀 문서는 시간 초과가 아니면 사유 없이 버려진다. 머리를 읽지 못한 바뀐 문서는 「의도 문서 아님」 으로 세어지지도 않는다. 답 폴더를 읽지 못하면 아무 말 없이 「답 없음」 이다.
- **틀린 말로 남는다.** 시간이 모자라 못 읽은 원문이 「링크 거부」 로, 브랜치 목록을 못 읽은 실행의 열린 PR 이 모두 「그 브랜치가 이 리포에 없다」 로, 답은 커밋됐는데 그 뒤 기록에 실패한 실행이 「묻지 않음」 으로 나온다. 물을 것이 없던 리뷰와 이미 답해(「잘못 골랐다」 포함) 걸러진 질문만 있던 리뷰가 같은 「질문 없음」 이다.
- **넘친다.** 내 컴퓨터에만 있는 브랜치의 설계 글이 근거 줄로 인용돼 답 파일과 리뷰 기록을 타고 PR 로 올라갈 수 있다. 답 파일을 크기 상한 없이 읽는다. 직접 쓴 답이 선택지 글자로 시작하기만 해도 그 선택지로 읽힌다. 답 파일의 라벨 칸만 절 머리 무력화를 거치지 않는다.

테스트 품질 리뷰가 낸 빠진 테스트 일곱과 R6 머지 뒤 리뷰의 제안 열다섯도 같은 파일에 있다.

## Goals

- G1. 답 입력에 든 글은 답으로 실리지 않더라도 조용히 사라지지 않는다 — 답 파일에 실리지 않은 답 입력의 글은 모두 원문으로 남는다.
- G2. 읽지 못한 것(답 폴더 · 답 파일 · 다른 팀 문서 · 머리를 못 읽은 문서 · 표지 없는 옛 원문)은 사유와 함께 알려진다.
- G3. 사유 문구가 실제 일어난 일과 맞는다(시간 한도 · 브랜치 목록 · 커밋 뒤 기록 실패).
- G4. 올리지 않은 브랜치의 글이 근거에 들어오지 않는다 — git 에 남는 자리(답 파일 · 돌려주는 꼴 · 기록 파일)에 실릴 길이 없다.
- G5. 답 파일 쪽 읽기가 넘겨받은 답 파일과 같은 방어(크기 상한 · 값의 종류 · 열쇠의 글자)를 갖는다.
- G6. 빠진 테스트 일곱을 채우고 R6 머지 뒤 리뷰의 제안 열다섯을 받는다 — 묶음의 범위 목록 밖이라 받는다는 결정을 결정 기록에 두고 로드맵 R8 의 범위에도 올린다. 열다섯은 §6 의 표에 한 줄씩 있다.

## Non-goals

- 옆 로드맵의 과제 폴더 구조에 맞추기(답 자리를 과제 폴더에 · `INTENT.md` 읽기) — 그 구조를 쓰는 로드맵이 레포에 아직 없다(D1).
- 다른 팀 기록의 상한과 싣는 차례 — 사용자가 두 번 「의도다」 로 답했다(2026-11-22 · 2026-11-24 리뷰 기록).
- 돌려주는 꼴의 판 올리기 — 이 에픽은 칸을 더하지 않는다(§3).
- 넘겨받는 답 파일 경로에 빈칸이 든 경우를 받게 하기 — 호출 방식을 바꿔야 한다. 멈출 때의 문구와 README 만 고친다(§1).
- 올리지 않은 브랜치의 의도 문서를 읽어 의도의 갈라짐을 짚기 — 올린 뒤의 리뷰가 짚는다(D9).
- 넘겨받는 답 기록의 진위 · 지휘 절차 쪽 뒤처리(R9) · 리뷰어 입력 칸과 잠금(R7) · 쓴소리 리뷰어 본체.
- 앞 조사가 받는 곳 없이 남긴 것 가운데 이 문서가 이름으로 들지 않은 것(근거 판정 기본값 · 읽기 총량 상한 등).

## Anti-goals

- 답을 살리려다 정체를 믿을 수 없는 답을 답 파일로 확정하는 것 — 어긋난 답은 원문을 남기되 답으로 세지 않는다.
- 알림이 늘어 매번 뜨는 것 — 새 줄은 그 일이 일어난 실행에만 나온다. 다른 작업이 0개인 실행에 붙던 「묶었다」 줄은 뺀다 — 「갈라져 있다」 줄은 읽지 않은 원격 사본의 하나뿐인 알림이라 남긴다(§4).
- 지난 답 파일을 고쳐 쓰는 것.

## Constraints

- 돌려주는 꼴은 3판이고 지휘자가 그 칸을 읽는다 — 칸을 더하거나 뜻을 바꾸지 않는다. 결과 줄(`result_line`)의 글과 이미 있는 칸의 값만 달라진다.
- 열린 PR #332 가 같은 파일 여섯(`intent_origin.py` · `other_teams.py` · 의도 점검 reference · README · 테스트 셋)을 고친다 — 뒤에 머지되는 쪽이 기본 브랜치를 합친다.
- R7 이 `intent_origin.py`(출처 표지) · 의도 점검 reference(칸 조립) · `setup-qg.sh`(새 인자)를 고친다 — 이 에픽이 그 파일에서 고치는 자리와 다르다.
- 새 훅 · 새 진입 skill · 새 kill switch 가 없다.
- 리뷰어 정의(`agents/intent-critic.md`)는 고치지 않는다.

## Approaches

항목마다 고치는 방향이 하나라 갈림이 작다. 묶는 방식만 셋을 견줬다.

1. **스크립트 넷을 한 PR 로(고름).** 답 기록(`intent_critic.py` · `intent_answers.py`)과 다른 팀 읽기 · 의도 출처(`other_teams.py` · `intent_origin.py`)를 한 에픽으로. 내줌: PR 이 크다 — 과제를 파일 묶음 둘로 나눠 리뷰한다.
2. **답 기록과 다른 팀 읽기를 두 PR 로.** 얻음: PR 이 작다. 내줌: 테스트 파일과 README · CHANGELOG · 판이 겹쳐 뒤 PR 이 다시 합치고, #332 와의 순서 맞추기가 두 번 든다.
3. **막는 지적 여섯만.** 얻음: 가장 작다. 내줌: 나머지가 다시 받는 곳 없는 미룸이 된다.

1 을 골랐다 — 로드맵이 한 에픽으로 잡았고 파일 주인이 하나다. 계획이 PR 을 나눠야 한다고 보면 2 로 갈 수 있다.

## 설계

### §1 답을 받아 적는 길

**어긋난 머리 아래 직접 쓴 답.** 답 입력의 머리(`=== n: · id: · pick:`)는 오케스트레이터가 옮겨 적는다. 번호나 정체가 질문과 맞지 않는 머리는 지금 번호와 고른 라벨만 남기고 그 아래 글을 버린다.

- 번호는 맞고 정체가 틀린 머리 — 그 질문은 지금처럼 「답 기록 실패」 다. 달라지는 것: 고른 것과 그 아래 글 원문을 그 질문의 실패 기록에 함께 남긴다(돌려주는 꼴의 그 질문 `answer_text` 와 결과 파일). 그 글이 「잘못 골랐다」 로 읽히면 그 질문의 `wrong_choice` 를 세운다 — 읽는 규칙은 다른 답과 같은 하나(아래 「직접 쓴 답의 라벨 읽기」)다: 「잘못 골랐다」 바로 뒤가 글의 끝이거나 구분 글자일 때만. 「잘못 골랐다 — 이유」 는 세우고 「잘못 골랐다고 보진 않는다」 는 세우지 않는다.
- 규칙은 하나다: **답 파일에 실리지 않은 답 입력의 글은 모두 남긴다.** 위의 경우 말고 이 규칙이 닿는 경우 — 어느 질문에도 붙일 수 없는 머리와 그 아래 글, 같은 번호에 맞는 머리가 이미 있을 때의 틀린 정체 머리와 그 아래 글, 더 나온 같은 번호 머리와 그 아래 글, 첫 머리 앞의 글, 번호 · 정체는 맞는데 고른 것(`pick`)을 읽지 못한 머리 아래 글(지금은 그 질문만 「답 기록 실패」 가 되고 글은 버려진다), 받은 답이지만 기록하지 않는 갈래(kill switch · 준비 파일이나 설정을 읽지 못함)나 답 파일 쓰기 실패로 답 파일이 생기지 않은 질문의 답 아래 글 — 은 모두 결과 파일의 「답 기록 실패」 에 원문으로 남긴다. 직접 쓴 답이 이미 그 질문의 `answer_text` 에 남는 것(지금 동작)은 그대로다.
- **남기는 길 — 열거하지 않고 도출한다.** 남긴 글은 답 기록 걸음이 나르지 않는다. 결과를 짓는 걸음이 세션 폴더의 답 입력 파일(의도 점검 reference 가 `record` 에 `--answers "$RD/intent-answers.txt"` 로 넘기는 그 파일)을 직접 다시 읽어 `record` 와 같은 읽기로 가르고, 질문 기록에서 「답함」 인 질문의 답(받아들여 답 파일이 된 머리 줄과 그 아래 글)을 뺀 나머지 빈 줄 아닌 줄을 남긴다. 위에 든 경우는 이 도출의 예이고, 질문 기록을 읽거나 쓰지 못한 갈래(거르기 결과를 읽지 못한 실행 · 질문 기록 쓰기가 실패한 실행)도 같은 길로 덮인다.
  - 질문 기록을 읽지 못하면 어느 답이 답 파일이 됐는지 가를 수 없다 — 답 입력의 빈 줄 아닌 줄을 모두 남긴다(빠뜨리기보다 겹쳐 싣는 쪽).
  - 답 입력 파일을 읽어야 하는데 읽지 못하면(답 기록 걸음이 돈 실행인데 파일이 없거나, 있는데 읽다 실패) 남긴 글을 0줄로 내지 않고 `남긴 글을 확인하지 못했다 — 답 입력 파일(<경로>)을 읽지 못함` 을 결과 파일의 의도 점검 절에 싣는다. 질문 창을 띄우지 않은 실행(범위 모드 · 물을 질문 없음 · 꺼짐)은 답 입력 파일이 없는 것이 정상이라 아무 줄도 내지 않는다.
- **싣는 꼴.** 남긴 글은 결과 파일 의도 점검 절의 공시 줄 아래 `답 기록 실패 — 답 파일에 실리지 않은 답 입력의 글:` 줄 밑에 원래 줄 차례대로, 줄마다 앞에 `> ` 를 붙여 싣는다. 줄 앞 표지가 있어 여러 줄 원문 속의 절 머리 줄(`## `) · 표 줄(`|`) · 목록 줄(`- `)이 결과 절의 절 머리 · 질문 표 · 공시 줄을 끊거나 흉내 내지 못한다 — 답 파일 칸에 쓰는 절 머리 무력화(`intent_answers.py` 의 `_defang` — `## ` 로 시작하는 줄을 한 칸 들여 쓴다)와 같은 목적이고, 결과 파일은 표 줄까지 막아야 해 줄마다 표지를 붙인다. 견주는 잣대는 AC2 와 같은 문장이다: 받아들여 답 파일이 된 머리 줄은 빼고, 나머지 빈 줄 아닌 줄마다 답 파일의 답 원문이나 남긴 원문에 있다 — 절 머리 무력화를 거친 줄은 무력화된 꼴로 견준다(결과 파일의 남긴 줄은 줄 앞 표지를 단 꼴이다).
- **길이 상한.** 남긴 글은 한 실행에 4000자까지 싣는다. 넘으면 4000자에서 자르고 `남긴 글 <전체>자 가운데 <실은>자만 실었다 — 전문은 세션 폴더의 답 입력 파일(<절대 경로>)에 있다` 를 붙인다. 「모두 남긴다」 는 결과 파일에 싣거나, 상한을 넘는 몫은 전문이 있는 자리를 알려 남긴다는 뜻이다 — 세션 폴더는 같은 세션의 다음 qg 시작이나 정리 기한 뒤에 지워지므로 그 자리는 그때까지다.
- 남긴 글로 답 파일을 쓰지는 않는다 — 어느 질문의 답인지나 무엇을 골랐는지 믿을 수 없거나, 답 파일을 쓰지 않는 갈래다.
- 의도 점검 reference 의 「그 줄과 아래 글은 어느 답에도 실리지 않고」 를 이 동작에 맞게 고치고, `record` 출력 표에 아래 「커밋 뒤 기록 실패」 의 두 줄(커밋 앞 쓰기 실패 · 커밋 결과 덧쓰기 실패)의 행을 더한다.

**커밋 뒤 기록 실패.** 답 파일을 커밋한 뒤 질문 기록을 쓰다 실패하면 지금은 예외로 죽고, 결과는 「묻지 않음(묻기 전에 끝남)」 · `commit: -` 로 나간다. 지금 코드는 답 · 상태 · 직접 쓴 글을 메모리에 든 채 커밋 뒤에 질문 기록을 한 번만 쓴다 — 행의 상태(「답함」)는 커밋 앞에 이미 정해지고, 커밋으로 달라지는 것은 `commit` 값과 커밋 줄뿐이다. 그래서 따로 표지 파일을 두지 않고 쓰는 차례를 바꾼다(D12 · D19 의 커밋 표지 파일은 2026-11-25 리뷰 1라운드에서 없앴다 — 「답 기록 실패」 를 커밋된 질문 행에만 붙이던 규칙도 함께 없어진다. 행이 처음부터 맞기 때문이다).

- **차례.** 답 파일을 쓴 뒤, 커밋 앞에 질문 기록을 한 번 쓴다 — 답 · 상태(「답함」 · 「답 기록 실패」 와 그 `failed_answer` · `failure`) · 직접 쓴 글(`answer_text` — 어긋난 머리 아래 글을 그 질문에 남긴 것 포함) · 공시 줄 · 답 기록 걸음이 돌았다는 표시를 모두 싣고, 커밋 결과(`commit` · 커밋 줄)는 비워 둔다. 커밋한 뒤에는 그 기록에 커밋 결과만 덧쓴다. 결과 파일에 남길 글은 결과를 짓는 걸음이 답 입력 파일에서 도출하므로(위 「남기는 길」) 질문 기록에 따로 싣지 않는다. 답 파일이 하나도 생기지 않아 커밋하지 않는 실행은 지금처럼 한 번만 쓴다.
- **원자 쓰기.** 질문 기록은 늘 같은 폴더의 임시 파일에 쓴 뒤 바꿔치기한다(`os.replace`) — 쓰다 실패해도(디스크가 찬 경우 등) 앞 기록(거르기 결과, 또는 커밋 앞에 쓴 기록)이 그대로 남는다. 임시 파일은 링크를 따라가지 않고 새로 만들고, 실패하면 지운다. 질문 기록을 쓰는 자리는 하나(`_write_questions`)라 거르기 걸음의 쓰기도 같은 길을 탄다. 그래도 질문 기록을 읽지 못한 실행(지워졌거나 꼴이 깨짐)은 지금처럼 「셀 수 없음」 이다 — 결과 줄 `intent-critic — 리뷰어 출력을 읽지 못함(셀 수 없음)` · 질문 행 없음 · `commit: -` 이고, 남긴 글은 위 규칙대로 답 입력의 빈 줄 아닌 줄을 모두 싣는다.
- **커밋 앞 쓰기가 실패하면.** 답을 커밋하지 않고 멈춘다 — 사용자가 받아들인 내줌이다. 답 파일은 작업 트리의 답 자리에 커밋되지 않은 채 남는다. 화면에는 `질문 기록을 쓰지 못해 답 파일 <n>개를 커밋하지 않았다 — <사유>(파일은 남겼다)` 를 내고 0 이 아닌 종료 코드로 끝난다. 질문 기록은 원자 쓰기라 거르기 결과 그대로 남아 답 기록 걸음이 돌았다는 표시가 없고, 결과 줄은 그 기록대로 `intent-critic — 질문 <n>개 묻지 않음(묻기 전에 끝남)` · `commit: -` 다. 사용자가 한 답은 조용히 사라지지 않는다 — 그 기록에는 「답함」 행이 없어 답 입력의 글이 모두 「답 파일에 실리지 않은 글」 이 되고, 위 「남기는 길」 대로 결과 파일의 「답 기록 실패」 에 머리 줄(번호 · 정체 · 고른 것)째 실린다.
- **커밋이 실패하면.** 지금 코드와 같다 — 커밋 앞에 적은 「답함」 행(답 · 답 파일 경로)은 그대로이고, 덧쓰기가 `commit: failed — <사유>` 와 커밋 줄 `답 파일을 커밋하지 못했다 — <사유>(파일은 남겼다)` 를 싣는다. 결과 줄은 보통의 `intent-critic — 질문 <n>개를 물었다 · 답 <m>개(잘못 골랐다 <k>개)` 다. 「답함」 은 답 파일이 생겼다는 뜻이고 커밋했는지는 `commit` 칸이 말한다.
- **커밋 결과 덧쓰기가 실패하면.** 예외로 죽지 않는다. 화면에는 커밋 줄(`답 파일 <n>개를 커밋했다(<해시>)` 또는 `답 파일을 커밋하지 못했다 — …`) 뒤에 `질문 기록에 커밋 결과를 적지 못했다 — <사유>` 를 내고 0 이 아닌 종료 코드로 끝난다. 질문 기록은 커밋 앞에 쓴 것이 남아 행이 정확하다 — 답한 질문은 「답함」 · 고른 답 · 「잘못 골랐다」 표시 · 직접 쓴 글을 갖고, 답하지 않은 질문은 「답하지 않음」 이며, 「답 기록 실패」 행의 고른 답과 「잘못 골랐다」 표시도 커밋 앞 기록의 `failed_answer` 에서 그대로 나온다. 비는 것은 커밋 결과뿐이다. 결과를 짓는 걸음은 「답함」 행이 있는데 커밋 결과가 비어 있으면 git 을 다시 읽지 않고, 결과 줄 끝에 ` · 커밋 해시 확인 못 함` 을 붙이고 돌려주는 꼴의 `commit` 칸에 `unknown — 커밋 해시 확인 못 함` 을 싣는다. 해시는 답 기록 걸음의 화면 줄에 남아 있다. 새 상태 값은 만들지 않는다.

**직접 쓴 답의 라벨 읽기.** 지금은 글이 선택지 글자로 시작하기만 하면 그 선택지로 읽는다(「의도다만 아닌 것 같다」 가 「의도다」). 선택지 글자 바로 뒤가 글의 끝이거나 구분 글자(빈칸 · 줄바꿈 · `—` · `-` · `:` · `,` · `.`)일 때만 그 선택지로 읽는다. 아니면 라벨 없는 글로 본다 — 지금의 라벨 없는 글 처리(「지금은 모르겠다」 쪽, 원문은 남는다) 그대로다.

**답 파일의 라벨 칸.** 답 파일을 지을 때 라벨 칸도 다른 칸(질문 · 인용 · 관찰 · 답 원문)과 같은 절 머리 무력화를 거친다.

**넘겨받는 답 파일 경로의 빈칸.** 경로에 빈칸이 있으면 뒷부분이 모르는 인자로 읽혀 시작에서 멈춘다. 받게 하지는 않는다. 그 멈춤의 문구가 「`--answered` 의 경로에 빈칸이 있으면 받지 못한다」 를 말하게 하고 README 에 한계를 적는다.

### §2 답 파일을 읽는 길

- **크기 상한.** 같은 브랜치의 답 파일을 읽을 때 파일마다 크기 상한을 둔다 — 넘겨받은 답 파일의 상한과 같은 값이다. 넘는 파일은 읽지 못한 답 파일로 세고 알린다.
- **값의 종류.** 답 파일 머리의 `answered_at` · `target` 이 글이 아니면(목록 · 사전) 그 파일을 읽지 못한 답 파일로 센다 — 지금은 글로 바꿔 읽는다.
- **답 폴더.** 답 폴더 자체를 읽지 못하면 지금은 공시 없이 「답 없음」 이다. 「답 폴더를 읽지 못함 — 전에 한 답을 확인 못 함」 을 알림에 싣는다.
- **넘겨받은 답의 열쇠.** 열쇠의 파일 이름 몫에 제어 글자가 있으면 그 항목을 받지 않는다.
- **읽기 실패의 사유.** 넘겨받은 답 파일을 열다 난 입출력 오류가 「꼴이 맞지 않음」 으로 접히지 않게 한다 — 읽지 못함과 꼴이 틀림을 가른다. 크기 확인과 여는 사이의 틈은 연 뒤에 읽은 크기로 다시 본다.

### §3 결과 줄

돌려주는 꼴의 칸은 그대로 두고 글만 고친다.

| 실행 | 지금 | 바뀐 뒤 |
|---|---|---|
| 물을 질문이 없었고 이미 답해 거른 질문도 없다 | `outcome: none` · 「질문 없음」 | 그대로 |
| 물을 질문이 없었고 이미 답해 거른 질문이 있다 | `outcome: none` · 「질문 없음」 | `outcome: none` · 결과 줄 끝에 거른 까닭을 둘로 갈라 붙인다 — 이미 「잘못 골랐다」 답이 있어 거른 질문만 있으면 「— 이미 「잘못 골랐다」 답이 있는 질문은 다시 묻지 않았다」, 그 밖에 이미 답한 질문만 있으면 「— 이미 답한 질문은 다시 묻지 않았다」, 둘 다 있으면 「— 이미 「잘못 골랐다」 답이 있는 질문과 그 밖에 이미 답한 질문은 다시 묻지 않았다」. 수는 결과 줄에 싣지 않는다 — 이미 있는 칸(`answered_filtered`)에 있고 지휘자가 그 칸으로 수를 보인다(결과 줄에도 실으면 같은 수가 두 번 보인다) |
| 답 커밋 뒤 질문 기록 실패(커밋 결과 덧쓰기 실패) | 「묻지 않음(묻기 전에 끝남)」 · `commit: -` | 보통의 결과 줄(`intent-critic — 질문 <n>개를 물었다 · 답 <m>개(잘못 골랐다 <k>개)`) 끝에 ` · 커밋 해시 확인 못 함` · `commit: unknown — 커밋 해시 확인 못 함` · 행은 커밋 앞 기록대로(§1) |
| 커밋 앞 질문 기록 실패 | 없는 갈래 — 지금은 질문 기록을 커밋 뒤에만 쓴다 | 커밋하지 않는다. 결과 줄은 거르기 결과대로 「질문 <n>개 묻지 않음(묻기 전에 끝남)」 · `commit: -` · 답 입력의 글은 「답 기록 실패」 의 남긴 글로(§1) |

**두 거름을 가르는 자리.** 새 칸 없이 가른다. 거르기 결과의 질문 레코드가 거른 상태를 셋으로 이미 가진다 — `answered-filtered` · `wrong-choice-filtered` · `deferred-filtered`(`intent_critic.py` 의 `FILTERED_STATES`). 결과 줄은 이 레코드 상태로 짓는다.

- 「이미 「잘못 골랐다」 답이 있어 거른 것」 은 `wrong-choice-filtered` 다 — 답 폴더에 같은 정체의 「잘못 골랐다」 답이 있어 거른 질문이고, 결과 파일의 `이미 「잘못 골랐다」 답이 있어 거른 질문:` 목록과 같은 집합이다.
- 「그 밖에 이미 답한 것」 은 `answered-filtered`(답 폴더의 「의도다」 답이 있어 거름 · 넘겨받은 답 가운데 「잘못 골랐다」 가 아닌 것)와 `deferred-filtered`(넘겨받은 「잘못 골랐다」 가운데 이 에픽 밖으로 미뤄 둔 의심)다. 넘겨받은 「잘못 골랐다」 는 미뤄 둔 것만 걸러진다 — 그 밖은 지금도 다시 묻는다.
- `answered_filtered` 칸의 수는 지금처럼 세 상태를 합친 수다. 칸 이름과 판은 바뀌지 않는다.

### §4 다른 팀 읽기

**올리지 않은 브랜치.** 다른 팀 읽기는 로컬 브랜치도 읽는다. 같은 이름의 원격 사본을 가른 뒤(아래 「앞선 브랜치」 · 「같은 이름 사본 고르기」) 남은 로컬 브랜치 가운데 끝 커밋이 어느 원격 브랜치에도 들어 있지 않은 것을 「올리지 않은 브랜치」 로 본다.

- 올리지 않은 브랜치는 이름과 이 변경과 겹치는 파일 목록만 싣는다 — 그 브랜치의 의도 문서 본문과 diff 는 읽지 않는다. 내용이 근거에 들어오지 않으니 답 파일 · 돌려주는 꼴 · 지휘자의 기록 파일 어디에도 실릴 수 없다.
- 그 브랜치의 작업 줄에는 `올리지 않은 브랜치 — 내용은 읽지 않았다` 를 붙인다. 리뷰어는 「같은 파일을 고치는 올리지 않은 작업이 있다」 까지 짚을 수 있다.
- 가르는 길 — 로컬 브랜치 끝 가운데 원격 브랜치들에서 닿지 않는 것을 git 에 한 번 묻는다(브랜치마다가 아니라 한 번). 그 물음이 실패하거나 시간 한도에 걸리면 로컬 브랜치를 모두 올리지 않은 것으로 본다 — 싣지 않는 쪽으로 넘어진다.
- **앞선 브랜치.** 로컬이 같은 이름의 원격 사본보다 앞선 브랜치(원격 사본 끝이 로컬 끝의 조상)는 원격 사본 끝에서 의도 문서와 diff 를 읽는다 — 이미 올린 글이다. 로컬에만 있는 커밋은 읽지 않는다 — 그 커밋의 의도 문서 · diff · 바뀐 파일 이름 모두. 그 작업 줄에 `원격보다 앞선 커밋은 읽지 않았다` 를 붙인다. 원격 사본이 없는 브랜치만 위의 「이름과 겹치는 파일만」 이다(D10 의 「원격보다 앞선 브랜치는 통째로 올리지 않은 브랜치다」 를 2026-11-25 리뷰 1라운드에서 고쳤다). 원격 브랜치를 새로 받지 않은 채 가른다 — 지금도 받지 않고 읽으며 그 사실을 알린다.
- **같은 이름 사본 고르기.** `other_teams.py` 의 `_same_name_drops` 는 지금 원격 사본이 로컬의 조상이면(로컬이 앞섬) 원격 사본을 버리고 로컬 끝을 후보로 남긴다. 이 경우만 거꾸로 해 로컬 끝을 버리고 원격 사본 끝을 후보로 남기며, 그 후보에 「원격보다 앞선 커밋은 읽지 않았다」 표시를 단다. 한 작업으로 묶는 것과 묶은 수(「같은 이름의 원격 사본 <n>개를 … 묶었다」 줄)는 지금처럼 센다. 나머지 경우는 지금 코드 그대로 둔다.
  - 로컬이 원격 사본의 조상이면(로컬이 뒤짐) 지금처럼 로컬을 버리고 원격 사본 끝을 읽는다.
  - 둘이 같은 커밋이면 지금처럼 하나로 접는다 — 끝 커밋이 원격에 있어 올린 브랜치다.
  - 서로 조상이 아니면(갈라짐) 지금처럼 원격 사본을 버리고 로컬 끝을 남긴다. 그 로컬 끝은 원격에 없는 커밋을 가져 올리지 않은 브랜치가 되어 이름과 겹치는 파일만 싣고, 버린 원격 사본은 「같은 이름의 원격 사본이 갈라져 있다」 줄로 알린다(아래 「다른 작업이 0개인 실행」).
  - git 이 조상 관계를 답하지 못하면(실패 · 시간 한도) 지금처럼 둘 다 남긴다. 원격 사본은 그대로 읽고, 로컬 끝은 위 가르기에 따라 올리지 않은 브랜치가 될 수 있다.
- 매 실행 「확인 못 함」 에 붙는 줄 「다른 컴퓨터 · 올리지 않은 작업은 볼 수 없음」 을 실제 동작에 맞게 고친다 — `다른 컴퓨터의 작업은 볼 수 없음 · 이 컴퓨터의 올리지 않은 브랜치는 이름과 겹치는 파일만 본다`. README 의 같은 문장도 고친다.

**읽지 못한 문서의 사유.** 다른 브랜치의 문서를 읽지 못했을 때 지금은 시간 초과만 「확인 못 함」 에 남는다. 링크 · 보통 파일이 아님 · 제어 글자(경로 꼴 거부 포함)로 읽지 못하면 문서 이름과 함께 싣고, 그 브랜치 끝에 없는 문서(지웠거나 옮긴 문서)는 읽지 못한 것으로 치지 않는다. 한 줄씩 같은 파일의 기존 줄 꼴(`<브랜치> 의 <문서> 를 읽지 못함 — <사유>`)을 쓴다. 경로 꼴 거부는 `intent_origin.py` 의 경로 검사가 내는 사유(절대 경로 · 상위 경로 · `.git` 아래)다. 그 브랜치 끝에 없는 문서는 `read_tracked` 가 「추적 안 된 파일 또는 없음」 으로 돌려주는 것이다 — 다른 작업의 경로 목록은 그 브랜치 커밋이 건드린 모든 경로(지운 파일 포함)라, 이것까지 실으면 문서를 지우거나 옮길 때마다 할 일 없는 줄이 붙는다.

**브랜치 목록 실패.** 브랜치 목록을 읽지 못한 실행은 열린 PR 마다 「그 브랜치가 이 리포에 없다」 를 붙이지 않는다. `브랜치 목록을 읽지 못해 열린 PR <n>개를 견주지 못했다` 한 줄로 대신한다.

**다른 작업이 0개인 실행.** 다른 작업이 하나도 없으면 「같은 이름의 원격 사본 <n>개를 … 묶었다」 줄을 내지 않는다 — 읽는 사람이 할 일이 없다. 「같은 이름의 원격 사본이 갈라져 있다」 줄은 0개여도 낸다 — 갈라진 원격 사본은 읽지 않고 버려지고(그 커밋이 후보에서 빠진다), 이 줄이 그 사실의 하나뿐인 알림이다.

### §5 의도 출처

- **시간 한도.** 원문 · 로드맵을 시간 한도로 못 읽은 실행의 요약 줄을 「원문 없음 — 시간 한도로 읽지 못함」 · 「로드맵 없음 — 시간 한도로 읽지 못함」 으로 낸다. 「링크 거부」 는 실제로 거부한 경우에만 쓴다.
- **표지 없는 옛 원문.** 원문 절 머리는 찾았는데 직접 쓴 말 · 고른 라벨 표지(🗣 · ☑)가 하나도 없는 묶음 · brief 에도 「직접 쓴 말 · 고른 라벨을 가르지 못함」 을 알린다 — 지금은 절 머리를 못 찾을 때만 알린다.
- **머리를 못 읽은 바뀐 문서.** 넓이를 정할 때 머리를 읽지 못한 바뀐 문서를 「의도 문서 아님」 으로 치지 않고 「의도 문서인지 확인 못 한 문서」 로 센다 — 다른 팀 읽기가 이미 쓰는 줄과 같은 말이다.
- **리뷰 기록 빼기.** 범위로 부른 리뷰가 바뀐 의도 문서를 따라갈 때 종류가 리뷰 기록인 문서는 의도 문서로 싣지 않는다 — R6 이 다른 팀 읽기에 넣은 규칙과 같다.
- **낱말.** 「좁게 본다 — 코드가 바뀐 PR」 은 코드가 바뀐 변경에만 쓴다. 의도 문서 없는 문서 변경에는 「좁게 본다 — 의도 문서가 바뀌지 않았다」 를 쓴다. 설정 값을 보이는 도움말이 실제 값 넷을 모두 말한다.

## Acceptance Criteria

- AC1. 번호는 맞고 정체가 틀린 머리 아래의 글은 그 질문의 실패 기록(돌려주는 꼴의 `answer_text` 와 결과 파일의 「답 기록 실패」)에 원문으로 남는다. 그 글이 AC4 와 같은 라벨 읽기로 「잘못 골랐다」 로 읽힐 때만 그 질문의 `wrong_choice` 가 선다 — 「잘못 골랐다 — 이유」 는 서고 「잘못 골랐다고 보진 않는다」 는 서지 않는다. 답 파일은 쓰이지 않는다.
- AC2. 답 파일에 실리지 않은 답 입력의 글은 모두 결과 파일의 「답 기록 실패」 에 원문으로 남는다 — 결과를 짓는 걸음이 세션 폴더의 답 입력 파일을 다시 읽어 도출한다. 열거한 경우마다(번호는 맞고 정체가 틀린 머리 아래 글 · 붙일 질문이 없는 머리와 그 아래 글 · 같은 번호에 맞는 머리가 이미 있을 때의 틀린 정체 머리와 그 아래 글 · 더 나온 같은 번호 머리와 그 아래 글 · 첫 머리 앞의 글 · 번호 · 정체는 맞는데 고른 것을 읽지 못한 머리 아래 글 · 기록하지 않는 갈래나 답 파일 쓰기 실패로 답 파일이 생기지 않은 질문의 답 아래 글) 테스트가 있고, 거르기 결과(질문 기록)를 읽지 못한 실행과 질문 기록 쓰기가 실패한 실행에서도 남는다. 그와 따로 여러 경우를 섞은 답 입력(상한 아래)에서 「입력의 글 = 답 파일에 실린 글 + 남긴 글」 을 잰다 — 받아들여 답 파일이 된 머리 줄은 빼고, 나머지 빈 줄 아닌 줄마다 답 파일의 답 원문이나 남긴 원문에 있다 — 절 머리 무력화를 거친 줄은 무력화된 꼴로 견준다. 답 입력 파일을 읽어야 하는데 읽지 못한 실행은 「남긴 글을 확인하지 못했다」 를 내고 남긴 글 0줄로 가지 않는다.
- AC3. 질문 기록은 커밋 앞에 한 번(답 · 상태 · 직접 쓴 글 · 「잘못 골랐다」 표시), 커밋 뒤에 커밋 결과만 덧써진다. 커밋 결과 덧쓰기가 실패한 실행은 예외로 죽지 않고 커밋 줄과 「질문 기록에 커밋 결과를 적지 못했다」 를 낸 뒤 0 이 아닌 종료 코드로 끝난다. 그 실행의 행은 커밋 앞 기록대로다 — 답한 질문은 「답함」 · 고른 답 · 「잘못 골랐다」 표시를 갖고, 답하지 않은 질문은 「답하지 않음」 이다. 결과 줄은 보통의 「질문 <n>개를 물었다 · 답 <m>개(잘못 골랐다 <k>개)」 끝에 「 · 커밋 해시 확인 못 함」 이 붙고 — 「묻지 않음(묻기 전에 끝남)」 이 아니다 — 돌려주는 꼴의 `commit` 은 `unknown — 커밋 해시 확인 못 함` 이다. 세션 폴더에 커밋 표지 파일이 생기지 않는다. 상태 값의 종류가 늘지 않았다.

- **올리지 않은 브랜치를 읽되 git 에 남길 때 내용을 가린다.** 줄에서 브랜치로 되짚는 길이 지금 없고, 가릴 자리가 셋(답 파일 · 돌려주는 꼴의 관찰 · 달라진 관찰)이며, 가린 줄 때문에 「근거가 같으면 거른다」 를 견줄 지문까지 지어야 한다 — 설계문서 점검이 짚었고 사용자가 가벼운 쪽을 골랐다(D9).
- **앞선 브랜치를 통째로 올리지 않은 브랜치로 본다(D10 의 앞 안).** 가르는 규칙이 하나로 남지만, PR 을 올린 뒤 로컬에서 작업을 잇는 브랜치(나란히 도는 에픽의 흔한 꼴)마다 이미 올라가 공개된 의도 문서와 diff 까지 리뷰어 입력에서 빠진다 — 사용자가 고른 「올리지 않은 브랜치는 이름과 겹치는 파일만」 보다 넓게 잘리고, 다른 팀과 갈라지는 것을 짚는 일이 그 브랜치가 원격과 똑같은 순간에만 된다.
- **README 로 알리기만 한다.** 올리지 않은 작업의 글이 PR 로 올라가는 것을 그대로 둔다.
- **커밋 직후 표지 파일을 따로 쓴다(D12 · D19 의 앞 안).** 새 파일 하나와 그 수명 · 읽는 조건 · 낡은 행을 고치는 규칙이 더해지는데, 질문 기록을 커밋 앞에 쓰기만 해도 행이 정확한 「답함」 과 「잘못 골랐다」 표시를 가진다. 그 앞 안에서는 그 실행에서 물은 다른 질문이 「묻지 않음」 으로 나오고, 커밋된 「잘못 골랐다」 답이 그 표시 없이 지휘자에게 갔다. 내줌은 커밋 앞 쓰기가 실패하면 커밋하지 않는 것이고 사용자가 받아들였다(2026-11-25).
