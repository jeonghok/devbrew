# R9 — 지휘 절차의 qg 리뷰 뒤처리 — 믿는 자리 · 다시 들어오기 · 답 넘기기 · Design

> 머지 앞 qg 리뷰 한 번의 상태를 지휘자가 쥐는 파일 하나에 모으고 스크립트가 그것을 읽고 쓴다. 무엇을 리뷰했고 무엇이 남았고 머지 준비로 가도 되는지는 그 파일이 답한다 — PR 본문은 사람이 보는 표시로만 남는다.

## Context / Why

R4 가 머지 앞 qg 리뷰와 되돌리기를 지휘 절차에 넣었고 R6 이 답 이어지기를 넣었다. 그 자리는 R4 설계의 리뷰, R4 머지 뒤 리뷰, R6 의 통합 리뷰, R6 머지 뒤 리뷰에서 매번 새 막는 지적이 나온 곳이다. 이 설계의 첫 초안(문장을 스무 군데 고치는 안)도 설계문서 점검에서 질문 열셋을 받았다(지휘 자원 `report/R9/builder-check.md`).

뿌리는 하나다. 지휘자는 머지 앞 리뷰 한 번의 상태 — 어느 범위를 보냈나 · 돌아왔나 · 돌려보낼 막는 지적 · 사용자 답 · 다시 보내도 되나 — 를 네 곳에 흩어 적고 긴 절차 문장으로 맞춰 읽는다.

| 지금 적는 자리 | 무엇을 | 구멍 |
|---|---|---|
| PR 본문 `## qg 리뷰` | 호출 줄(범위) · 막는 지적 목록 · 돌려보낸 것 · 재리뷰 횟수 · 사용자 답 | 리뷰받는 구현 쪽도 고칠 수 있다 — 범위 줄을 고치면 재리뷰가 비고, 지적 줄을 지우면 그 지적이 사라진 채 머지 준비로 간다 |
| 기계 상태의 쌓인 기록 줄 | 보낸 횟수 · 다시 보내도 되는 표지 | 표지가 「언제의 코드에 쓸 것인가」 를 모른다 — 설계를 고치는 중에 끊기면 옛 코드에 쓴다 |
| 보관 폴더 | 담당자가 옮긴 결과 파일 | 호출 줄과 잇는 고리가 없다 — 보내기 전에 끊긴 리뷰와 돌아오지 못한 리뷰를 가르지 못한다 |
| 기록 파일(에픽 브랜치) | 사용자 답 · 「보관 사본」 표지 | 구현 쪽이 커밋하는 브랜치다 — 가짜 기록이 질문을 거르고 리뷰를 「끝난 것」 으로 만든다 |

team 형식 로드맵은 PR 본문 대신 일꾼이 커밋하는 과제 브랜치의 검수 결과 파일에 같은 것을 적는다 — 같은 구멍이 더 고치기 쉬운 자리에 있다.

그 밖에 답 넘기기 스크립트의 가장자리(읽지 못한 기록 앞에서 덜 묻는다 · 알림 파일 쓰기에 실패하면 알림이 사라진다 — R6 머지 뒤 리뷰의 막는 지적)와 읽기 좋게 고칠 것 둘(머지 직전 승인 기록 다시 보이기가 답만 나열한다 · 같은 알림이 리뷰마다 되풀이된다)이 있다.

## Goals

- G1. 머지 앞 리뷰 한 번의 상태가 지휘자가 쥐는 파일 하나에 있고, 지휘자는 리뷰받는 쪽이 고칠 수 있는 자리(PR 본문 · 에픽 브랜치 · 과제 브랜치)에서 그 상태를 읽지 않는다. 리뷰받는 쪽(구현 · 계획 담당자)에게 보내는 글에는 그 파일과 리뷰 보관 폴더의 경로가 없다.
- G2. 머지 준비로 가도 되는지는 스크립트가 그 파일들을 보고 답한다 — 리뷰가 지적 목록을 내지 못했거나 막는 지적이 남았거나 물을 것이 남았으면 가지 않는다.
- G3. 끊겼다 다시 들어왔을 때 할 일 하나를 스크립트가 답한다 — 보내기 전 · 도는 중 · 묻는 중 · 되돌린 뒤 · 설계를 고치는 중 어디서 끊겼든.
- G4. 좁은 재리뷰의 범위와 횟수를 스크립트가 정한다 — 빈 범위의 리뷰가 생기지 않는다.
- G5. 기록 파일은 리뷰받는 쪽이 커밋하지 않는 자리(기본 브랜치 · 기록 브랜치)에서만 답으로 읽는다 — 에픽 브랜치의 기록은 읽지 않는다.
- G6. 답 넘기기가 가르지 못할 때 더 묻는 쪽으로 가고, 알림이 사라지지 않는다.
- G7. 머지 직전 다시 보이는 승인 기록이 질문과 답을 함께 싣고, 바로 앞 리뷰에서 낸 것과 같은 알림 줄은 한 줄로 접혀 화면에 뜬다(D2 · 2026-11-25 리뷰 1라운드에서 「기록마다 한 번」 의 장치를 줄임 — §8).

## Non-goals

- 같은 컴퓨터 · 같은 사용자 권한으로 도는 담당자가 건네받지 않은 경로(리뷰 보관 폴더 · 상태 파일 · 기계 상태)를 고치는 것 막기 — 상태 파일은 지휘자 기계 상태와 같은 폴더 나무(지휘 자원)에 있고, 구현 담당자에게 건네는 처리 파일 경로(그 에픽의 보고 폴더)의 옆 폴더다(둘 다 지휘 자원의 `report/` 아래). 이 에픽이 끊는 것은 리뷰받는 쪽이 평소 손대는 자리를 믿는 일과 그 담당자에게 상태 파일의 자리를 건네는 일이다. 마지막 확인은 머지 직전의 승인 기록 다시 보이기(§5)다 — 상태 파일의 사용자 답 · 「사용자가 남김」 처리 · 닫힘 사유가 거기 빠짐없이 다시 보여, 꾸민 답이나 남김은 머지 명령 줄 앞에서 보인다. 상태 파일에서 지워진 지적은 거기에도 보이지 못한다. README 에 적는다.
- spec 승인 앞 · 로드맵 끝 · 머지된 에픽을 이름으로 청한 리뷰의 세는 방식 — 지금 문장 그대로 둔다. 바꾸는 것은 둘뿐이다 — 기록을 쓰는 자리(§6)와, spec 승인 앞의 다시 보내기 표지에 그때의 설계문서 커밋을 함께 적고 설계문서가 그 커밋 그대로인 동안에는 그 허용분으로 보내지 않는 것(§4 끝 · AC9 · D6). 상태 파일은 머지 앞 자리(첫 리뷰 · 좁은 재리뷰 · 구현이 끝난 뒤 이름으로 청한 리뷰)만 쓴다.
- 결과 글의 꼴과 그 글을 다시 싣는 규칙(R6) — 그대로다.
- 호출 줄의 꼴과 인자(R7 이 하나를 더한다) · 돌려주는 꼴의 판 · qg 의 스크립트와 본문(R7 · R8).
- 좁은 재리뷰에서 의도 점검을 건너뛰는 길 · 결과 파일 이름의 반복 번호 — 재분해에서 받지 않기로 했다.
- qg 가 리뷰 트리의 답 폴더에서 스스로 읽는 답 파일의 진위 — 사용자가 qg 를 직접 불러 남긴 답이 거기 있다. 한계로 적는다(§6).
- 기록 파일을 스크립트가 쓰게 하기 — 지휘자가 손으로 쓰는 지금 방식을 두고 틀의 규칙과 쓰는 자리(§6 — 기록 브랜치)만 고친다.

## Anti-goals

- 문장을 더 얹어 막는 것 — 이 자리에서 네 번 되풀이됐다.
- 스크립트가 사람 몫을 정하는 것 — 스크립트는 「무엇을 물을 차례인가」 까지 답하고, 묻고 답을 받는 것은 지휘자와 사용자다.
- 못 가를 때 덜 리뷰하고 덜 묻는 것.
- 질문이 늘어 흐름이 서는 것 — 새 질문 창은 §3 의 하나다.
- 지난 기록 파일을 고쳐 쓰는 것.

## Constraints

- 지휘자 기계 상태는 git 밖 파일이고 그 컴퓨터에만 있다 — 다른 컴퓨터나 새 클론에는 없다. 없을 때는 더 리뷰하고 더 묻는 쪽으로 넘어져야 한다.
- 런타임 상태는 마크다운이다(레포 규칙). 상태 파일은 사람이 열어 읽을 수 있어야 한다.
- 지금 지휘 중인 로드맵에는 이 변경 전에 쓴 PR 본문의 줄 · 쌓인 기록 줄 · 기록 파일이 있다 — 옛 흔적을 읽지 못해 조용히 덜 리뷰하는 일이 없어야 한다(§9).
- 스크립트는 하니스의 agent 목록과 skill 목록을 볼 수 없다 — 담당자가 살아 있는지와 quality-gates 가 깔려 있는지(§3)는 지휘자가 넘겨준다.
- R7 이 같은 문서의 호출 줄 · 다시 부르기 · 겹침 문장을 고친다. team 형식 절이 있는 지휘 절차 문서는 옆 로드맵(지휘 절차 쪽)도 고친다 — 뒤에 머지되는 쪽이 기본 브랜치를 합치고, 옆 로드맵에는 이 에픽이 team 형식의 「세는 자리」 를 옮긴다는 것을 알린다.
- 새 훅 · 새 진입 skill · 새 kill switch 가 없다.

## Approaches

1. **리뷰마다 상태 파일 하나와 그것을 읽고 쓰는 스크립트(고름).** 범위 · 단계 · 지적 목록 · 사용자 답을 지휘자가 쥐는 파일에 모으고, 재리뷰 범위 · 머지 관문 · 다시 들어왔을 때 할 일을 스크립트가 답한다. 내줌: 세 에픽 가운데 가장 큰 일이 되고 team 형식의 세는 자리 문장도 바뀐다.
2. **지금 구조에 문장을 더 얹는다.** 얻음: 작다. 내줌: 흩어진 네 자리를 문장으로 맞추는 방식이 그대로라 규칙끼리 부딪히고(점검이 넷을 짚었다) team 형식에 구멍이 남는다.
3. **가장 심각한 셋만 고치고 나머지는 옆 로드맵의 지휘 절차 개편에 넘긴다.** 얻음: 가장 작다. 내줌: 받는 쪽이 정해지지 않은 미룸이 또 생긴다.

사용자가 1 을 골랐다(D3).

## 설계

### §1 리뷰 상태 파일과 스크립트

**상태 파일.** 머지 앞 자리의 리뷰를 보낼 때마다 그 리뷰의 보관 폴더에 상태 파일 하나를 둔다. 보관 폴더는 지금처럼 지휘 자원 아래(git 밖)다. 그 자리는 지휘자 기계 상태와 같은 폴더 나무이고, 구현 담당자에게 건네는 처리 파일 경로(그 에픽의 보고 폴더)의 옆 폴더다 — 같은 컴퓨터 · 같은 사용자 권한의 담당자가 상태 파일을 고치는 것은 막지 못한다. 머지 직전 승인 기록 다시 보이기(§5)는 꾸민 답과 남김은 보이지만, 상태 파일에서 지워진 지적은 보이지 못한다(Non-goals). 파일은 마크다운이고 아래를 담는다.

| 칸 | 내용 |
|---|---|
| 자리 · 대상 | 자리 글자(첫 리뷰 · 좁은 재리뷰 · 이름으로 청함)와 PR(옛 형식은 PR 번호, team 형식은 과제와 계획 번호) |
| 범위 | 호출 줄에 쓴 시작 · 끝 커밋 |
| 단계 | 열림 → 보내는 중 → 보냄 → 돌아옴 → 닫힘. 닫힘에는 사유가 붙는다(아래). 사유 「「잘못 골랐다」 — 설계 대화로」 에는 설계 대화 뒤 다시 구현한 것이 돌아오면 「다시 구현됨」 표시와 그 표시를 적은 때가 붙는다(§4). 사유 「「잘못 골랐다」 — 재분해 신호」 에는 재분해가 끝나 그 PR 을 이어 가기로 하면 「재분해 뒤 이어 감」 표시와 그 표시를 적은 때가 붙는다(§4) — 둘 다 새 칸이 아니다 |
| 담당자 | 보낸 담당자 이름과 보낸 때 |
| 돌아온 결과 | 지적 목록을 얻었나 · 본 범위가 맞나 · 판정 줄 · 의도 점검 결과 줄 |
| 막는 지적 | 막는 지적과 새로 깨진 테스트의 원문, 항목마다 처리 — 처리 없음 · 고친 커밋 <해시> · 반박 · 손대지 않음(「손대지 않음 — 처리 파일 없이 끝남」 · 「손대지 않음 — 적어 낸 커밋이 범위에 없음」 포함 — §4) · 다시 돌려보냄 · 사용자가 남김 · 리뷰 없이 가기로 함(§3). 사용자가 고른 제안과 되올린 낮춘 지적도 그 표시와 함께 이 칸에 든다 — 언제 적든 그 PR 의 마지막 리뷰의 칸이고, 그 제안 · 지적을 낸 리뷰가 그와 다르면 낸 리뷰를 표시로 남긴다 |
| 돌려보냄 | 구현 길로 돌려보낼 때마다 한 줄 — 그 구현 담당자 이름 · 보낸 때 · 처리 파일의 경로 · 그 처리를 옮겼나(옮김 · 아직 · 처리 파일 없이 끝남 · 옮겼으나 범위 밖 커밋 — §4). 처리 파일이 있는지는 그 파일의 `## 지적마다의 처리` 머리 줄로 가린다(아래 「파일에 남아야 하는 것」) |
| 거른 질문 | 두 목록 — 「이미 「잘못 골랐다」 답이 있어 거른 질문」(결과 파일의 `이미 「잘못 골랐다」 답이 있어 거른 질문:` 목록)과 「그 밖에 이미 답해 거른 질문」(결과 파일의 `이미 답한 질문이라 거른 질문:` 에서 「잘못 골랐다」 목록의 질문(같은 id)을 빼 짓는다). 앞 목록의 질문마다 지휘자가 적용한 행선(§4 — 쓰기 전이면 빔) |
| 물을 것 | 아직 답을 받지 못한 질문 — 종류(의도 점검 · 지적 목록을 얻지 못함 · 고치지 않은 막는 지적 · 「두 번까지」 · 담당자가 옮긴 질문)와 질문 글. 「두 번까지」 는 세는 재리뷰가 상한에 닿은 PR 에서 구현 길로 돌려보낼 것이 생길 때마다 「돌아옴」 · 「답 적기」 가 적는다(§2). 의도 점검 질문은 물을 차례인 것만 들고(`상한 넘어 남김` 은 들지 않는다 — 아래 「돌아옴」), 「답하지 않음」(창을 닫았거나 답하지 않음)도 답 값이라 그것을 적으면 물을 것에서 내린다 — 다시 띄우지 않는다(지금 `qg-review.md` 의 의도 점검 질문 절과 같다). 그 밖의 질문 셋(지적 목록을 얻지 못함 · 고치지 않은 막는 지적 · 「두 번까지」)과 담당자가 옮긴 질문은 답을 받을 때까지 남는다 |
| 사용자 답 | 이 리뷰에서 받은 답 전부 — 의도 점검 답은 질문 정체와 답, 그 답을 적은 기록 파일의 경로(쓰기 전이면 빔 · 기록 브랜치를 만들지 못했으면 「기록 브랜치 없음 — <사유>」 — §6) |
| 멈출 조건 | 첫 좁은 재리뷰를 보내기 전에 적는 조건(두 번 뒤에도 남는 지적을 어디에 적고 넘길지) |

닫힘의 사유는 닫힌 꼴이다 — 막는 지적 없음 · 재리뷰로 이어짐 · 사용자가 남김 · 리뷰 없이 감 · 다시 보냄(지적 목록을 얻지 못해) · 「잘못 골랐다」 — 설계 대화로 · 「잘못 골랐다」 — 재분해 신호 · 에픽을 멈춤.

**스크립트.** 스크립트 하나가 상태 파일을 만들고 고치고 읽는다. 지휘자는 상태 파일을 손으로 고치지 않는다. 스크립트가 하는 일은 일곱이다.

| 일 | 무엇을 |
|---|---|
| 열기 | 그 PR 의 상태 파일들을 보고 지금 그 자리의 리뷰를 보내도 되는지 정한다(받는 상태 — §2 「「열기」 가 받는 상태」). 새 리뷰는 이름으로 청한 것을 포함해 그 PR 의 마지막 리뷰가 닫혀 있을 때(또는 상태 파일이 없을 때)만 받는다. 되면 보관 폴더와 상태 파일을 만들고(자원 줄 포함) 호출 줄에 쓸 범위와 보관 폴더 경로를 낸다. 좁은 재리뷰의 범위는 스크립트가 정한다(§2). 안 되면 까닭과 지금 할 일을 낸다 |
| 보냄 | 두 번 부른다 — 보내기 직전에 「보내는 중」 을 적고, 보낸 뒤에 담당자 이름을 적는다 |
| 돌아옴 | 보관 폴더의 파일을 읽어 결과를 가린다(아래) — 막는 지적의 원문과 거른 질문 목록을 상태 파일로 옮기고, 의도 점검의 돌려주는 꼴에서 질문마다의 `state` 가 `묻지 않음` 인 질문만 물을 것에 옮기고(`상한 넘어 남김` 은 옮기지 않는다 — 기록 파일에만 남는다), 세는 재리뷰가 상한에 닿은 PR 에서 막는 지적이 왔으면 「두 번까지」 를 물을 것에 적고(§2), 닫을 수 있으면 닫고, 다음 할 일을 낸다 |
| 답 적기 | 사용자 답(의도 점검 질문의 「답하지 않음」 포함 — 적으면 그 질문을 물을 것에서 내린다) · 구현 담당자의 처리(지적마다 — 지휘자가 처리 파일에서 읽어 넘긴다) · 사용자가 고른 제안과 되올린 낮춘 지적(그 PR 의 마지막 리뷰의 칸에 — 위 「막는 지적」 칸) · 담당자가 옮긴 질문 · 거른 「잘못 골랐다」 목록에 적용한 행선 · 멈출 조건 · 「돌려보냄」(§4) · 「다시 구현됨」 표시(단계 칸의 사유 「「잘못 골랐다」 — 설계 대화로」 에 붙는다 — §4) · 「재분해 뒤 이어 감」 표시(단계 칸의 사유 「「잘못 골랐다」 — 재분해 신호」 에 붙는다 — §4)를 적는다. 세는 재리뷰가 상한에 닿은 PR 에서 고른 제안 · 되올린 지적을 적으면 「두 번까지」 를 물을 것에 적고, 의도 점검 답 「잘못 골랐다」 를 적으면 같은 리뷰의 「두 번까지」 를 물을 것에서 거둔다(§2). 처리를 옮길 때 적어 낸 「고친 커밋」 을 기준 커밋(§2)에 대어 보고, 없는 것은 「처리 없음」 으로 되돌린다(§4). 적을 값 없이 부르면 그 리뷰를 git 과 아래 조건에 대어 다시 가린다(§4). 적은 뒤 닫을 수 있으면 닫는다(아래 「닫는 조건」) |
| 다음 | 그 PR 에서 지금 할 일 하나를 낸다(§4) — 지휘자가 넘긴 살아 있는 담당자 이름과 「qg 없음」 인자(§3)를 받는다. 「열기」 를 내는 것은 「열기」 가 받아들이는 상태에서만이다(같은 기준 — §2) |
| 관문 | 그 PR 이 머지 준비로 가도 되는지와 걸린 까닭(§3 의 여덟 가운데)을 낸다 — 「qg 없음」 인자를 받는다 |
| 글 짓기 | 셋을 낸다 — PR 본문 `## qg 리뷰` 절의 글 · 승인 기록 다시 보이기의 qg 몫 · 구현 담당자에게 돌려보낼 지적 목록(§5). 「qg 없음」 인자를 받으면 상태 파일 없이 승인 기록 다시 보이기의 그 줄(§3)을 짓는다 |

상태를 옮기는 것은 「보냄」 · 「돌아옴」 · 「답 적기」 셋뿐이고, 닫는 것은 「돌아옴」 과 「답 적기」 가 조건이 채워졌을 때 스스로 한다 — 닫기만 하는 명령은 없다. 「열기」 는 새 상태 파일을 만들 뿐 앞 리뷰의 단계를 옮기지 않는다 — 좁은 재리뷰를 열 때 앞 리뷰는 이미 「재리뷰로 이어짐」 으로 닫혀 있다.

**닫는 조건.** 사유마다 닫는 명령과 조건은 아래다. 어느 사유든 의도 점검 답이 있는 리뷰는 그 답마다 「사용자 답」 칸의 기록 파일 경로가 적힌 뒤에만 닫힌다 — 기록 브랜치를 만들지 못한 때(§6)는 그 자리에 「기록 브랜치 없음 — <사유>」 를 적은 것으로 닫힌다. 그 전에는 단계가 「돌아옴」 에 머물러 §4 의 기록 파일 줄이 맞는다.

- 막는 지적 없음 — 「돌아옴」: 지적 목록을 얻었고 막는 지적도 물을 것도 없다. 「답 적기」: 물을 것을 다 적었고 막는 지적이 하나도 없다.
- 재리뷰로 이어짐 — 「답 적기」: 막는 지적마다 처리가 적혔고(처리 없음 · 다시 돌려보냄인 것이 없다), 처리를 아직 옮기지 않은 「돌려보냄」 이 없고, 물을 것이 없고, 기준 커밋(§2 — 적어 낸 해시가 아니라 git 에서 읽는다)이 하나라도 있다. 나머지가 「사용자가 남김」 이어도, 처리가 모두 「사용자가 남김」 이어도 기준 커밋이 있으면 이 사유다 — 올라온 커밋은 재리뷰를 받는다.
- 사용자가 남김 — 「답 적기」: 위와 같되 기준 커밋이 없고 「사용자가 남김」 이 하나라도 있다(고치지 않은 막는 지적의 질문 · 「두 번까지」 의 답). 처리가 「고친 커밋」 인 지적은 그 해시가 기준 커밋에 들어야 남으므로(아니면 「처리 없음」 으로 되돌린다) 기준 커밋이 없는데 「고친 커밋」 이 남는 일은 없다.
- 리뷰 없이 감 · 다시 보냄 — 「답 적기」: §3 의 질문에 「리뷰 없이 머지 준비로 간다」 · 「다시 보낸다」 를 적었다. 「리뷰 없이 머지 준비로 간다」 를 적으면 같은 「답 적기」 가 그 PR 의 앞 리뷰들에서 처리가 「고친 커밋」 인 막는 지적의 처리를 「리뷰 없이 가기로 함」 으로 적는다(§3).
- 「잘못 골랐다」 — 설계 대화로 · 재분해 신호 — 「답 적기」: 의도 점검 답 「잘못 골랐다」 와 그 행선을 적었다 · 또는 「이미 「잘못 골랐다」 답이 있어 거른 질문」 목록의 질문마다 적용한 행선을 적었다(§4).
- 에픽을 멈춤 — 「답 적기」: 어느 질문에든 「이 에픽을 멈춘다」 를 적었다 — 다른 물을 것이 남아도 닫힌다. 사용자가 이어 가자고 해 멈추게 한 그 질문을 다시 띄우고(§4) 다른 답을 받으면, 「답 적기」 가 그 답을 적고 단계를 「돌아옴」 으로 되돌린 뒤 이 조건들로 다시 가린다 — 멈춤의 앞 답은 「사용자 답」 칸에 남는다.

사용자가 고른 제안 · 되올린 낮춘 지적은 그 PR 의 마지막 리뷰의 칸에 적는다. 그 리뷰가 이미 닫혔으면 「답 적기」 가 그 리뷰의 단계를 「돌아옴」 으로 되돌리고 같은 조건으로 다시 가린다 — 처리 없음인 지적이 생겨 닫히지 않으므로 §4 의 「처리 없음」 줄이 구현 길로 돌려보내고(세는 재리뷰가 상한에 닿은 PR 이면 그 전에 「두 번까지」 를 묻는다 — §2), 그 처리를 옮긴 뒤 기준 커밋이 있으면 「재리뷰로 이어짐」 이다. 마지막 리뷰의 칸에 두므로 그 고침은 그 뒤에 여는 리뷰가 본다 — 관문(§3 까닭 7)과 「다음」 표(§4)가 보는 「마지막 리뷰」 가 그대로 맞는다. 닫힌 리뷰에 거른 「잘못 골랐다」 목록의 행선을 적을 때와, 적을 값 없이 불러 다시 가릴 때(§4 의 「기준 커밋이 없다」 줄)도 같은 조건으로 사유를 다시 정한다.

**돌아온 결과를 가리는 법.** 스크립트는 보관 폴더의 파일만 본다 — 대화에 있는 담당자 보고를 근거로 쓰지 않는다.

| 보관 폴더 | 결과 |
|---|---|
| 판정 절이 있는 결과 파일이 있고, 그 결과가 말한 본 범위가 상태 파일의 범위와 맞다 | 지적 목록을 얻음 — 막는 지적은 합쳐지기 전 지적 목록 파일에서(없으면 결과 파일의 고칠 목록에서) 옮긴다. 새로 깨진 테스트는 결과 파일의 차등 회귀에서 옮긴다 |
| 결과 파일이 없거나 판정 절이 없다 | 지적 목록을 얻지 못함 — 사유 「qg 가 끝까지 돌지 못했다 — 보관한 결과에 판정이 없다」 |
| 본 범위가 상태 파일의 범위와 다르다 | 지적 목록을 얻지 못함 — 사유 「결과가 보낸 범위의 것이 아니다」. 지금은 이 경우를 의도 점검만 셀 수 없는 것으로 보는데, 다른 범위의 지적은 이 PR 의 리뷰가 아니다 |
| 결과 파일이 「리뷰할 것 없음」 으로 끝났다(바뀐 코드가 없거나 한 문장 변경) | 리뷰할 것 없음 — 지적 목록을 얻은 것과 같이 다루고 막는 지적 0개로 닫는다 |

- 본 범위는 결과 파일의 범위 절(시작 · 끝)에서 읽는다 — 의도 점검의 돌려주는 꼴이 그 칸을 비워 와도 가를 수 있다.
- 의도 점검의 돌려주는 꼴을 읽지 못했거나 판이 다른 경우는 지금처럼 「의도 점검은 셀 수 없음」 이다 — 지적 목록을 얻었으면 관문을 막지 않는다.
- 돌아온 리뷰에 막는 지적도 물을 것도 없으면 「돌아옴」 이 바로 「막는 지적 없음」 으로 닫는다. 「이미 「잘못 골랐다」 답이 있어 거른 질문」 목록이 있어도 그렇게 닫히고, 관문(§3)이 닫힌 채인 그 리뷰의 할 일은 §4 의 표가 낸다.

**파일에 남아야 하는 것.** 스크립트가 대화 없이 다시 이을 수 있게, 지금 담당자의 마지막 보고에만 있는 것 가운데 상태를 바꾸는 둘을 파일로 남긴다.

- 구현 담당자가 지적마다 적는 처리 — 그 에픽의 보고 폴더(지휘 자원의 `report/<에픽>` — `ledger resource-dir --roadmap <로드맵> --kind report --name <에픽>`) 안의 처리 파일에 쓴다. 처리 파일의 경로는 지휘자가 돌려보낼 때마다 정하고(세션 담당자면 그 세션의 결과 파일이 그 자리다 — 지금도 그 폴더 안이다) 「돌려보냄」 줄에 적는다. 「처리 파일이 있다」 는 그 파일에 `## 지적마다의 처리` 머리 줄이 있다는 뜻이고, 두 형식 모두 보내는 글(team 형식은 시작 묶음과 과제 결정 기록에 싣는 글)이 그 머리 아래에 지적마다의 처리를 쓰라고 싣는다. 되돌리기에서 보내는 글은 그 처리 파일의 절대경로만 싣는다 — 리뷰 보관 폴더와 상태 파일의 경로는 검사받는 쪽(구현 · 계획 담당자)에게 보내는 어떤 글에도 싣지 않는다. 하위 agent 길의 구현 담당자도 같다 — `conductor-dispatch.md` 의 하위 agent 길은 지금 마지막 메시지로 보고하므로, 되돌리기에서 보내는 글이 그 처리 파일의 절대경로와 함께 「worktree 밖이어도 이 경로에 지적마다의 처리를 쓰고 끝낸다」 를 따로 적는다(마지막 메시지의 보고는 그대로다). 지휘자가 그 처리 파일을 읽어 「답 적기」 로 상태 파일에 옮긴다 — 처리 파일이 없어도 하위 agent 의 마지막 메시지가 낸 지적마다의 처리가 대화에 남아 있으면 그것을 옮긴다 — 스크립트는 대화를 보지 않으므로 이 갈림은 지휘자가 가린다(§4). team 형식은 지금처럼 다음 시도의 구현 결과 파일에 있고 같은 길로 옮긴다. qg 담당자는 검사받는 쪽이 아니고 결과를 보관 폴더로 옮겨야 하므로 그 경로를 받는다.
- qg 담당자가 미리 받은 답 밖의 질문에서 멈춰 돌려보낸 요약과 질문 원문 — 지휘자가 받는 즉시 「답 적기」 로 상태 파일의 물을 것에 적는다.

빠진 채 돌았다는 알림 · 미리 받은 답을 쓴 자리처럼 화면에만 쓰이는 줄은 지금처럼 보고에만 있다 — 다시 짓지 않는다(R6 의 규칙).

**지휘 절차 문서에 남는 것.** 머지 앞 자리의 「언제 보내나 · 범위 · 횟수 · 다시 들어왔을 때 · 머지 준비로 가는 조건」 은 문장에서 빠지고 「스크립트를 부르고 그 답대로 한다」 가 된다. 담당자에게 보내는 글 · 결과 글의 꼴 · 묻는 틀 · 선택지의 글자는 문서에 남는다. 기계 상태의 작업 줄 · 기다리는 질문 줄 · 사람 차례 표시는 지금처럼 적는다 — 상태 화면이 읽는 표시이고, 지휘자와 스크립트는 그 줄로 판단하지 않는다. 머지 앞 리뷰가 쌓인 기록에 남기던 두 줄(`qg-review.md` 의 질문이 하나도 없는 리뷰의 한 줄 · 「보내지 못했거나 셀 수 없이 끝난 리뷰」 의 한 줄)도 지금처럼 적는다 — 로드맵을 닫는 PR 본문이 싣는 표시다. 머지 앞 자리에서는 「이미 보낸 것」 확인이 그 줄로 보낸 횟수를 세지 않는다 — 상태 파일이 센다.

### §2 좁은 재리뷰의 범위와 횟수

- **여는 조건.** 브랜치 끝이 움직였다는 것만으로는 열지 않는다 — 리더(지휘자) 자신의 기록 커밋(옛 형식은 설계문서의 지휘 기록 · 구현 대조, team 형식은 검수 결과 파일 · 과제 결정 기록)도 리뷰받는 브랜치의 끝을 옮긴다. 리뷰 기록 파일은 에픽 브랜치에 커밋하지 않지만(§6) 이 커밋들은 남는다. 여는 기준은 구현 담당자가 적어 낸 해시가 아니라 git 이다 — 지적 목록을 얻은 마지막 리뷰의 끝부터 지금의 브랜치 끝 사이에, 리더(지휘자)가 쓰는 기록 파일(아래) 밖의 파일을 바꾼 커밋이 하나라도 있으면 연다. 이 문서는 그 커밋을 「기준 커밋」 이라 부른다. 지금 `qg-review.md` 「좁은 재리뷰」 의 「범위에 구현 담당자의 고친 커밋이 하나도 없으면 보내지 않는다」 와 같은 뜻이다.
  - **리더가 쓰는 기록 파일.** 형식 정본이 리더(지휘자)가 쓴다고 적은 파일 가운데 리뷰받는 브랜치에 커밋되는 것이다. 형식마다 이렇다.
    - 옛 형식 — 그 에픽의 설계문서(지휘 기록 · 판정 · 구현 대조가 거기 있다). 파일째로 뺀다.
    - team 형식 — 그 과제의 검수 결과 파일(`results/` 의 `review` 단계 결과 파일 — `team-files.md` 「검수 결과 파일」 이 리더가 쓴다고 적는다)과 과제 결정 기록이 든 INTENT.md(같은 문서 §1 의 파일 표 · §2 「결정 기록」 — 쓰는 사람은 리더 하나다) 둘이다. 리더가 쓰는 다른 파일(RULES.md 의 고침 · 대기 줄 · STATUS.md · 편지함)은 리더 상태 브랜치에 살아 과제 브랜치에 오지 않는다(같은 문서 §15). 과제의 설계문서(`jobs/<과제>/design.md`)는 빼지 않는다 — 형식 정본이 과제 폴더의 설계 · 계획 · 결과 파일을 「그 단계의 일꾼」 몫으로 적고(같은 문서 §1 의 파일 표), team 형식에서 리더의 지휘 기록 줄은 설계문서가 아니라 INTENT.md 결정 기록으로 간다(`conductor_ledger.py` 의 `write-sections` 는 설계문서를 고치지 않고, `flush` 는 결정 기록에 쓴다). 그 설계문서를 바꾼 커밋은 기준 커밋이다.
  - 구현 담당자가 쓰는 파일은 빼지 않는다 — team 형식의 구현 결과 파일은 처리만 적은 것이어도 담당자의 커밋이라 기준 커밋이다(아래 귀결과 같은 잣대).
  - 내줌 — 리더가 그 기록 파일에 섞어 넣은 고침은 재리뷰를 받지 못한다. 그 파일만 바꾼 구현 쪽 커밋도 같다. 한 커밋이 기록 파일과 다른 파일을 함께 바꾸면 그 커밋은 기준 커밋이다.
  - 뺄 파일은 지휘자가 넘긴다 — 기준 커밋을 읽는 일(열기 · 답 적기 · 다음 · 관문)에 옛 형식은 그 에픽의 설계문서 경로를, team 형식은 그 과제 폴더 경로를 넘기고, 스크립트가 그 폴더의 INTENT.md 와 `results/` 의 `review` 단계 결과 파일(이름이 `review-` 로 시작)을 뺀다.
  - 「재리뷰로 이어짐」 으로 닫는 조건(§1)도 같은 기준이다 — 닫을 때와 열 때가 같은 것을 본다.
  - 적어 낸 「고친 커밋 <해시>」 가 기준 커밋 가운데 없으면(rebase · amend · 오타 · push 전) 「답 적기」 가 그 지적의 처리를 「처리 없음」 으로 되돌리고, 「다음」 이 「적어 낸 고친 커밋 <해시> 가 범위에 없다」 를 보인다(§4).
  - 귀결 — 담당자가 「반박」 · 「손대지 않음」 만 적고 커밋을 올렸어도 그 커밋은 재리뷰를 받는다.
- **시작.** 그 PR 의 상태 파일 가운데 결과가 「지적 목록을 얻음」 인 마지막 리뷰의 범위 끝이다. 열기만 했거나 돌아오지 못했거나 지적 목록을 얻지 못한 리뷰의 끝은 시작이 되지 못한다.
- **끝.** 지금의 브랜치 끝이다. 그 사이 리더가 커밋한 기록 파일이 범위에 들어도 빼지 않는다(지금 그대로 — 기록 파일은 여는 기준에서만 뺀다). 리뷰 기록 파일은 이제 범위에 들지 않는다 — 기록 브랜치에 커밋된다.
- **merge 커밋.** 범위에 merge 커밋이 끼어 있으면 지금처럼 그 PR 을 처음부터 다시 보고 재리뷰 한 번으로 센다.
- **두 번까지.** 좁은 재리뷰는 PR 하나에 두 번까지다 — 지적 목록을 얻은 재리뷰만 센다. 지적 목록을 얻지 못해 다시 보낸 것은 세지 않는다. 그 PR 의 상한은 처음에 둘이고, 「한 번 더 돌려보낸다」 답이 적힐 때마다 그때의 세는 재리뷰 수에 하나를 더한 값이 된다(아래 「여는 쪽」 의 예외로 수가 상한을 넘었어도 다음 하나가 상한 안에 든다). 세는 범위는 관문과 같다(§3 — 「잘못 골랐다」 로 설계 대화에 돌아갔다 왔거나 재분해 뒤 이어 가면 그 표시 뒤에 연 첫 리뷰부터). 세는 재리뷰의 수가 상한보다 적으면 「상한 안」, 그렇지 않으면 「상한에 닿음」 이다.
  - **묻는 때.** 상한에 닿은 PR 에서 구현 길로 돌려보낼 것(막는 지적 · 사용자가 고른 제안 · 되올린 지적)이 생길 때마다 「두 번까지」 의 질문을 묻는다 — 구현 길로 돌려보내기 전이다. 그런 때는 둘이다. 상한에 닿게 한 재리뷰가 막는 지적을 안고 돌아오면 「돌아옴」 이 그 질문을 물을 것에 적는다(지금과 같은 때다). 막는 지적 없이 닫힌 그 재리뷰에 사용자가 제안을 고르거나 낮춘 지적을 되올리면 「답 적기」 가 그것을 마지막 리뷰의 칸에 적고 단계를 「돌아옴」 으로 되돌리면서 그 질문을 물을 것에 적는다(§1). 같은 리뷰에 의도 점검 질문이 함께 남아 있으면 그 답을 먼저 받는다(§4 까닭 4 줄의 차례).
  - **「한 번 더」 뒤.** 사용자가 「한 번 더 돌려보낸다」 를 고르면 상태 파일에 그 답이 적히고 상한이 그때의 세는 수보다 하나 많아진다 — 상한 안이 되어 그 지적들을 구현 길로 돌려보낸다(§4). 그 뒤 연 재리뷰가 지적 목록을 얻으면 상한에 다시 닿으므로, 그 재리뷰가 돌려보낼 것을 안고 오면(막는 지적을 안고 돌아왔든, 닫힌 뒤 고른 제안 · 되올린 지적을 적었든) 다시 묻는다.
  - **「잘못 골랐다」 가 있으면 묻지 않는다.** 같은 리뷰에 의도 점검 답 「잘못 골랐다」 나 「이미 「잘못 골랐다」 답이 있어 거른 질문」 목록이 있으면 「두 번까지」 를 묻지 않는다 — 설계 대화가 먼저이고(§4), 설계 대화 뒤에는 첫 리뷰부터 다시 세어 그 답이 쓰이지 않는다. 그래서 「돌아옴」 은 거른 「잘못 골랐다」 목록이 있으면 그 질문을 물을 것에 적지 않고, 「답 적기」 는 의도 점검 답 「잘못 골랐다」 를 적을 때 같은 리뷰의 물을 것에 있는 그 질문을 거둔다(답으로 적지 않는다).
  - **여는 쪽.** 「다음」 은 상한 안일 때만 좁은 재리뷰의 「열기」 와 구현 길로 돌려보내기를 내고, 「열기」 도 같은 기준으로 받는다(§4). 하나 예외가 있다 — 마지막 리뷰에 「두 번까지」 의 답이 이미 있는데 「재리뷰로 이어짐」 으로 닫혔으면(「남은 지적을 적고 머지 준비로 간다」 를 골랐는데 그 사이 기준 커밋이 올라왔다) 상한에 닿았어도 좁은 재리뷰를 연다 — 올라온 커밋은 재리뷰를 받는다(§1 「재리뷰로 이어짐」). 그 재리뷰가 돌려보낼 것을 안고 오면 위 「묻는 때」 대로 다시 묻는다.
- **이름으로 청한 리뷰.** 구현이 끝난 머지 전 에픽을 이름으로 청한 리뷰도 상태 파일을 쓴다 — 그 리뷰가 막는 지적을 내 되돌린 뒤의 좁은 재리뷰가 그 끝에서 시작한다. 그 리뷰는 머지 앞 첫 리뷰를 대신하지 않는다 — 이름으로 청한 리뷰(와 그 뒤 좁은 재리뷰)의 상태 파일만 있고 첫 리뷰의 상태 파일이 없으면, 그 리뷰들이 닫힌 뒤 「다음」 이 첫 리뷰(PR 전체)를 열고(§4), 관문은 첫 리뷰가 있어야 연다(§3). 이름으로 청한 리뷰는 「두 번까지」 에 세지 않는다 — 그 뒤의 좁은 재리뷰는 센다(지금 `qg-review.md` 「이름으로 청한 뒤의 좁은 재리뷰」 와 같다).
  - **앞 리뷰가 닫힌 뒤에 보낸다.** 「열기」 는 이름으로 청한 리뷰도 그 PR 의 마지막 리뷰가 닫혀 있을 때만 받는다. 마지막 리뷰가 도는 중이거나 「돌아옴」 에 머물러 있으면 「열기」 가 까닭과 지금 할 일(그 상태에서 「다음」 이 내는 줄)을 내고, 지휘자는 그 할 일을 먼저 한 뒤 다시 연다. 지금 `qg-review.md` 「이미 보낸 것」 의 「이름으로 청한 리뷰에는 이 확인을 쓰지 않는다 — 사용자가 청했으므로 이미 보낸 리뷰가 있어도 보낸다」 가 머지 앞 자리(구현이 끝난 머지 전 에픽)에서 이렇게 바뀐다.
  - **보이는 변화.** 이름으로 청해도 앞 리뷰의 남은 일(물을 것 · 돌려보냄 · 기록 파일 쓰기)을 먼저 끝내야 그 리뷰가 나간다.
- **「열기」 가 받는 상태.** 「열기」 는 아래 상태에서만 새 리뷰를 만들고, 「다음」 이 「열기」 를 내는 §4 표의 줄도 이 상태들뿐이다 — 둘이 같은 기준을 본다.
  - 상태 파일이 하나도 없다 — 첫 리뷰(§9).
  - 마지막 리뷰가 「다시 보냄」 으로 닫혔고 그 뒤 새 리뷰가 없다 — 같은 자리 · 같은 범위.
  - 마지막 리뷰가 「재리뷰로 이어짐」 으로 닫혔고 그 뒤 새 리뷰가 없고 기준 커밋이 있고, 상한 안이거나 그 리뷰에 「두 번까지」 의 답이 있다 — 좁은 재리뷰.
  - 마지막 리뷰가 「「잘못 골랐다」 — 설계 대화로」 에 「다시 구현됨」 표시가, 또는 「「잘못 골랐다」 — 재분해 신호」 에 「재분해 뒤 이어 감」 표시가 붙어 닫혔고 그 뒤 첫 리뷰가 없다 — 첫 리뷰(PR 전체).
  - 마지막 리뷰가 막는 지적 없음 · 사용자가 남김 · 리뷰 없이 감 가운데 하나로 닫혔고(거른 「잘못 골랐다」 목록이 없다 — 있으면 §4 까닭 6 의 줄이 먼저다), 세는 범위(§3) 안에 머지 앞 첫 리뷰의 상태 파일이 없다(이름으로 청한 리뷰와 그 뒤 좁은 재리뷰만 있다) — 첫 리뷰(PR 전체).
  - 이름으로 청한 리뷰 — 상태 파일이 없거나 마지막 리뷰가 닫혀 있다(위 「앞 리뷰가 닫힌 뒤에 보낸다」). 이것만은 「다음」 이 내지 않는 「열기」 다 — 사용자가 청한 것이다. 그 밖의 다섯은 「다음」 이 「열기」 를 내는 상태와 같다.

### §3 머지 관문

머지 준비(스위트 대조부터)로 가도 되는지는 스크립트의 관문이 답한다. 관문은 그 PR 의 상태 파일 전부(「잘못 골랐다」 로 설계 대화에 돌아갔다 왔으면 「다시 구현됨」 표시 뒤에 연 첫 리뷰부터, 재분해 신호로 닫혔다가 이어 가면 「재분해 뒤 이어 감」 표시 뒤에 연 첫 리뷰부터 — 거른 「잘못 골랐다」 목록으로 돌아간 경우도 같다)와 git(기준 커밋 — §2)을 보고, 아래 닫히는 까닭이 하나도 없을 때만 연다. 닫혀 있으면 걸린 까닭을 모두 낸다. 까닭마다 그것을 푸는 할 일은 §4 의 표가 정한다. 예외는 하나다 — 상태 파일이 하나도 없고 「qg 없음」 인자가 왔으면 연다(아래 「qg 가 깔려 있지 않을 때」).

1. **리뷰가 도는 중** — 마지막 리뷰의 단계가 열림 · 보내는 중 · 보냄이다.
2. **에픽을 멈춤** — 마지막 리뷰가 「에픽을 멈춤」 으로 닫혔다.
3. **지적 목록을 얻지 못함** — 마지막 리뷰가 지적 목록을 얻지 못했고(리뷰할 것이 없었던 것은 얻은 것이다) 아래 질문의 답이 없거나, 「다시 보냄」 으로 닫혔는데 그 뒤 새 리뷰가 없다. 사용자가 「리뷰 없이 머지 준비로 간다」 를 골랐으면 이 까닭이 아니다.
4. **물을 것이 남음** — 마지막 리뷰의 물을 것에 답을 받지 못한 질문이 있다(담당자가 옮긴 질문은 리뷰가 도는 중의 것이다). 의도 점검 질문은 「답하지 않음」 이 적히면 물을 것에서 내려 이 까닭이 아니고, `상한 넘어 남김` 인 질문은 처음부터 물을 것에 들지 않는다(§1).
5. **기록 파일 경로가 빔** — 의도 점검 답을 적었는데 그 답의 기록 파일 경로 자리가 비었다(§1 「닫는 조건」 — 그 리뷰는 닫히지 않는다).
6. **「잘못 골랐다」** — 의도 점검 답 「잘못 골랐다」 가 있거나, 「이미 「잘못 골랐다」 답이 있어 거른 질문」 목록이 있다. 「그 밖에 이미 답해 거른 질문」(결과 파일의 `이미 답한 질문이라 거른 질문:` 에서 「잘못 골랐다」 목록의 질문을 빼 지은 것)은 관문을 막지 않는다.
7. **열린 막는 지적** — 어느 리뷰의 막는 지적이든 닫히지 않았다. 막는 지적이 닫히는 길은 셋이다 — 처리가 「고친 커밋」 이고 그 고침을 본 리뷰 — 그 지적이 든 리뷰(고른 제안 · 되올린 지적은 적을 때의 마지막 리뷰에 든다 — §1) 뒤에 연 리뷰 — 가 지적 목록을 얻었다(뒤 리뷰의 범위가 기준 커밋을 품는다 — §2) · 사용자가 남기기로 했다 · 사용자가 「리뷰 없이 머지 준비로 간다」 를 골라 「리뷰 없이 가기로 함」 이 됐다(아래). 처리 없음 · 다시 돌려보냄과, 반박 · 손대지 않음인데 사용자가 남기지 않은 것은 열려 있다. 같은 문제가 뒤 리뷰에서 다시 나오면 그것은 뒤 리뷰의 새 막는 지적으로 세어진다 — 리뷰 사이에서 지적의 정체를 맞추지 않는다. 열린 막는 지적은 마지막 리뷰에만 남는다 — 앞 리뷰의 것은 처리가 「고친 커밋」 인 것뿐이고(앞 리뷰가 닫히려면 나머지가 모두 닫혀야 한다), 그것은 뒤 리뷰가 지적 목록을 얻거나 「리뷰 없이 가기로 함」 이 되면 닫힌다.
8. **첫 리뷰 없음** — 머지 앞 첫 리뷰의 상태 파일이 없다(이름으로 청한 리뷰는 첫 리뷰를 대신하지 않는다 — §2).

**리뷰가 지적 목록을 얻지 못했을 때.** 관문이 닫히고 스크립트가 이 질문 차례라고 낸다. 지휘자는 질문 하나로 묻는다 — 질문 문장 앞머리에 에픽 이름과 사유를 두고, 선택지는 아래 셋을 이 차례로 쓴다.

- 「다시 보낸다 (권장)」: 얻음: 리뷰를 받고 머지한다 · 내줌: 리뷰 한 번이 더 든다
- 「리뷰 없이 머지 준비로 간다」: 얻음: 지금 머지 준비로 간다 · 내줌: 이 PR 의 코드가 qg 리뷰 없이 머지된다
- 「이 에픽을 멈춘다」: 얻음: 리뷰 없이 머지되는 일이 없다 · 내줌: 이 에픽이 서고 다시 불러야 이어진다

「다시 보낸다」 는 그 리뷰를 「다시 보냄」 으로 닫고 같은 자리 · 같은 범위의 새 리뷰를 연다 — 「두 번까지」 에 세지 않는다. 「리뷰 없이 머지 준비로 간다」 는 상태 파일에 적히고 표시(§5)와 승인 기록 다시 보이기에 「qg 리뷰 없이 감 — 사용자 결정(<사유>)」 으로 실린다. 좁은 재리뷰에서 이 답을 고르면 앞 리뷰에서 처리가 「고친 커밋」 인 막는 지적(그 고침을 보려던 리뷰가 바로 이 실패한 리뷰다)도 「리뷰 없이 가기로 함」 으로 닫히고, 그 지적들은 승인 기록 다시 보이기 맨 위의 「qg 리뷰 없이 감」 줄 아래에 함께 실린다 — 관문은 그 지적 때문에 닫히지 않는다(까닭 7).

**qg 가 깔려 있지 않을 때.** 지휘자는 skill 목록에 `quality-gates:quality-pipeline` 이 없으면 지금처럼 「품질 게이트 없이 간다 — quality-gates 가 설치돼 있지 않다」 를 알리고, 그 사실을 「qg 없음」 인자로 「관문」 · 「다음」 · 「글 짓기」 에 넘긴다 — 스크립트는 skill 목록을 볼 수 없다(Constraints). 그 PR 에 상태 파일이 하나도 없으면 상태 파일을 만들지 않고, 관문은 「열림 — qg 리뷰 없음(quality-gates 가 설치돼 있지 않다)」 을 내며, 그 줄이 승인 기록 다시 보이기 맨 위에 실린다(§5). 그 PR 에 상태 파일이 이미 있으면 이 인자를 받지 않는다 — 관문과 「다음」 은 「qg 없음 인자를 쓰지 않았다 — 이 PR 에 상태 파일이 있다」 를 함께 내고 상태 파일대로 가린다. 그때 「다음」 이 낸 보내기를 qg 없이 할 수 없으면 지휘자는 그 사유를 사용자에게 보인다(사용자 차례 — 관문은 닫힌 채다). 인자 없이 상태 파일이 하나도 없으면 까닭 8(첫 리뷰 없음)로 닫힌다.

**있는 질문 둘.** 고치지 않은 막는 지적의 질문과 「두 번까지」 의 질문은 글자와 선택지가 지금 그대로다(고치지 않은 막는 지적의 질문은 「다시 돌려보낸다」 · 「반박을 받아들이고 남긴 지적으로 적는다」 · 「이 에픽을 멈춘다」). 달라지는 것은 그 질문이 떠야 하는 때를 스크립트가 내고 답을 상태 파일이 쥔다는 것이다(「두 번까지」 가 뜨는 때는 §2). 고치지 않은 막는 지적의 질문은 처리를 옮길 때 반박 · 손대지 않음이 있으면 뜨고, 돌려보낸 구현 담당자가 쓸 처리 없이 두 번째로 끝났을 때도 뜬다 — 그때 그 지적들의 처리는 「손대지 않음 — 처리 파일 없이 끝남」 · 「손대지 않음 — 적어 낸 커밋이 범위에 없음」 이다(§4). 「다시 돌려보낸다」 를 고른 지적은 처리가 「다시 돌려보냄」 으로 바뀌어 다음 할 일이 돌려보내기가 되고, 그 뒤의 좁은 재리뷰는 지금처럼 「두 번까지」 에 센다.

### §4 다시 들어왔을 때

**원칙.** 머지 관문이 닫히는 까닭(§3 의 여덟)마다 그 까닭을 푸는 할 일이 하나 있다 — 스크립트의 일 하나를 부르는 것이거나 사용자 차례다. 「다음」 은 상태 파일과 git 에서 닫힌 까닭을 읽어 그 할 일을 낸다. 그 할 일을 하면 상태가 나아가거나(단계 · 처리 · 답 · 「돌려보냄」 이 바뀐다) 사용자 차례가 된다 — 같은 할 일만 되풀이되고 상태가 바뀌지 않는 자리가 없다. 「기다린다」 는 상태 파일 밖에서 나아가는 일(살아 있는 담당자 · 설계 대화와 그 뒤 구현)을 기다릴 때만 내고, 그 일이 끝나면 무엇이 바뀌어 다음 줄로 넘어가는지를 같은 줄에 적는다. 아래 표는 이 원칙에서 끌어낸 것이다 — 줄마다 그 줄이 푸는 까닭이 있고, 관문이 열려 있을 때와 리뷰가 도는 중일 때의 줄도 같은 표 안에 있다.

지휘자는 압축이나 새 세션 뒤, 머지 전 확인을 시작할 때, 그리고 담당자가 돌아올 때마다 스크립트의 「다음」 을 부른다. 스크립트는 그 PR 의 상태 파일들 · git(기준 커밋 — §2) · 지휘자가 넘긴 살아 있는 담당자 이름(qg 담당자와 돌려보낸 구현 담당자 — 아직 끝나지 않은 것) · 「qg 없음」 인자(§3)를 보고 할 일 하나를 낸다. 살아 있는지는 지금 `conducting.md` 걸음 1 의 원천 규칙으로 본다 — 하위 agent 는 하니스 agent 목록(「원천」 불릿), hc 로 띄운 세션 담당자는 하니스 목록과 hc 의 내 자식(「세션 담당자의 원천」 불릿)이다. 아래 표를 위에서부터 보고 처음 맞는 줄을 쓴다.

표의 「무엇으로 아는가」 칸은 스크립트가 받는 것 — 상태 파일(과 거기 적힌 경로의 파일 · 보관 폴더) · git · 살아 있는 담당자 이름 · 「qg 없음」 인자 — 으로만 갈린다. 스크립트가 받지 않는 사실(하니스 목록에서 찾은 담당자 · 담당자를 이어 부를 수 있는지 · 대화에 남은 하위 agent 의 처리)로 갈리는 자리에서 「다음」 은 받은 것으로 아는 데까지의 할 일 하나를 내고, 그 대신 다른 명령을 부를지는 지휘자가 가린다 — 표에서 「지휘자가 가린다」 로 적은 자리다. 지휘자가 고르는 명령도 그 줄의 「그 할 일 뒤 상태」 가운데 하나로 상태를 옮긴다. 이 갈림을 스크립트의 인자로 더하지 않는다.

- **표가 덮는 것.** 까닭 1–8 은 저마다 위 줄 가운데 하나 이상에 맞고, 닫힘 사유 여덟(§1)도 그렇다 — 막는 지적 없음 · 사용자가 남김 · 리뷰 없이 감으로 닫힌 리뷰는 다른 까닭(6 · 8)이 없으면 관문 열림 줄, 재리뷰로 이어짐은 까닭 7 의 끝 두 줄, 다시 보냄은 까닭 3, 「잘못 골랐다」 둘은 까닭 6, 에픽을 멈춤은 까닭 2 다. 「돌아옴」 에 머문 리뷰는 까닭 3 · 4 · 5 · 6 · 7 가운데 하나가 걸려 있다 — 아무것도 걸리지 않았으면 「돌아옴」 · 「답 적기」 가 같은 쓰기에서 이미 닫았다(§1). 상한에 닿은 PR 의 마지막 리뷰에 돌려보낼 것이 있으면 물을 것에 「두 번까지」 가 있거나(까닭 4) 「잘못 골랐다」 가 있고(까닭 6), 상한에 닿은 채 「재리뷰로 이어짐」 으로 닫힌 리뷰에는 「두 번까지」 의 답이 있다(§2) — 「돌아옴」 · 「답 적기」 가 그렇게 적기 때문이다. 그래서 끝 줄은 상태 파일이 §1 의 꼴에서 벗어난 경우(읽지 못한 값 · 칸끼리 맞지 않는 값)에만 맞는다.
- **쓸 처리 없이 끝난 「돌려보냄」 세기.** 「돌려보냄」 줄의 값 「처리 파일 없이 끝남」 과 「옮겼으나 범위 밖 커밋」 을 함께 센다. 세는 자리는 같은 상태 파일에서 마지막으로 값이 「옮김」 인 「돌려보냄」 줄이나, 고치지 않은 막는 지적의 질문에 「다시 돌려보낸다」 를 적은 답 가운데 늦은 것의 뒤다. 「답 적기」 가 그런 값을 적을 때 그것이 두 번째면 그 줄에서 쓸 처리가 없는 지적들의 처리를 「손대지 않음 — 처리 파일 없이 끝남」 또는 「손대지 않음 — 적어 낸 커밋이 범위에 없음」 으로 적고 고치지 않은 막는 지적의 질문을 물을 것에 적는다 — 다시 돌려보내는 되풀이가 사용자 차례로 끝난다(D41 의 「두 번째면 상태를 보인다」 를 2026-11-25 리뷰 2라운드에서 이 출구로 고침 — 상태만 보이면 그 PR 을 다시 움직일 명령이 없었다).

- 지금의 「보고 없이 다시 들어왔을 때」 와 「돌아오지 못한 리뷰」 갈래는 머지 앞 자리에서 이 표로 대신한다 — 결과 글을 다시 싣는 규칙(R6)은 그대로이고, 그 글을 싣기 전에 무엇을 할 차례인지를 이 표가 정한다.
- 답을 받으면 먼저 「답 적기」 로 상태 파일에 적고, 그 뒤에 기록 파일을 쓰고 커밋한다 — 그 사이에 끊겨도 다시 묻지 않는다.
- 구현 길로 돌려보내면 보낸 즉시 「답 적기」 로 「돌려보냄」(그 담당자 이름 · 때 · 처리 파일 경로)을 적는다 — 그 뒤에 끊겨도 「다음」 이 그 담당자를 기다린다.
- 「잘못 골랐다」 로 설계 대화에 돌아갈 때 적던 다시 보내기 표지는 머지 앞 자리에서 상태 파일의 닫힘 사유와 거기 붙는 「다시 구현됨」 표시(§1 단계 칸)가 대신한다. spec 승인 앞의 표지는 그대로 두되 그때의 설계문서 커밋을 함께 적고, 설계문서가 그 커밋 그대로인 동안에는 그 허용분으로 보내지 않는다 — 같은 구멍이 그쪽에도 있다.

### §5 표시 — PR 본문 · 승인 기록 다시 보이기

- **PR 본문.** `## qg 리뷰` 절은 스크립트가 지은 글을 지휘자가 그대로 올린다 — 호출 줄 · 판정 줄 · 막는 지적과 처리 · 멈출 조건 · 사용자 답 · 남긴 지적. 호출 줄은 지금 PR 본문의 꼴 `- 호출 · <자리 글자> · <범위>` 까지다 — 리뷰 보관 폴더 · 상태 파일의 경로(qg 를 부르는 호출 줄의 `--answered` 값 포함)는 PR 본문 · team 형식의 펜스 같은 표시 글 어디에도 싣지 않는다(§8 의 다섯째 락). 지휘자는 그 절에서 아무것도 읽지 않는다. 사용자가 남기기로 한 막는 지적을 `## 통합 리뷰 인계` 에 적는 것은 지금 그대로다.
- **돌려보낼 지적 목록.** 구현 담당자에게 보내는 글에 싣는 목록도 스크립트가 상태 파일에서 짓는다 — 처리 없음 · 다시 돌려보냄인 막는 지적과 사용자가 고른 제안 · 되올린 낮춘 지적의 원문이다. 그 글에는 처리 파일의 절대경로(§1 — 그 에픽의 보고 폴더)를 싣고, 리뷰 보관 폴더와 상태 파일의 경로는 싣지 않는다.
- **승인 기록 다시 보이기.** 머지 명령 줄을 내기 전에 보이는 승인 기록의 qg 몫은 스크립트가 상태 파일에서 짓는다 — 기록 파일을 읽지 않는다. 상태 파일을 리뷰받는 쪽이 고쳤을 때 사용자가 볼 마지막 자리라, 관문을 연 근거를 빠짐없이 싣는다 — 꾸민 답과 남김은 여기서 보이지만, 상태 파일에서 지워진 지적은 여기에도 보이지 못한다(Non-goals).
  - 질문마다 질문 글 한 줄 · 답 · 직접 쓴 답 원문(있으면) — 의도 점검 질문만이 아니라 상태 파일의 사용자 답 전부(§3 의 질문 · 고치지 않은 막는 지적 · 「두 번까지」 의 답 포함)다.
  - 그 PR 의 리뷰마다 닫힘 사유 한 줄.
  - 그 PR 의 첫 리뷰 · 좁은 재리뷰에 더해 구현이 끝난 뒤 이름으로 청한 리뷰의 답도 싣는다.
  - 앞 리뷰에서 답해 이번에 묻지 않은 질문은 「앞 리뷰에서 답함」 으로 싣는다 — 상태 파일의 거른 질문 목록에서.
  - 「qg 리뷰 없이 감」 · 처리가 「사용자가 남김」 인 막는 지적은 맨 위에 싣는다. 처리가 「리뷰 없이 가기로 함」 인 막는 지적은 「qg 리뷰 없이 감」 줄 아래에 함께 싣는다(§3).
  - 상태 파일이 없는 PR 에 「qg 없음」 인자로 지으면 맨 위에 「qg 리뷰 없음(quality-gates 가 설치돼 있지 않다)」 한 줄을 싣는다(§3).
- **펜스.** team 형식의 검수 결과 파일에 싣는 표시 글은 스크립트가 바깥 펜스까지 지어 낸다 — 글 안의 가장 긴 백틱 줄보다 긴 펜스를 쓴다. 지적 원문에 펜스가 들어 있어도 그 파일의 펜스가 일찍 닫히거나 열린 채 남지 않는다. 그 글이 싣는 호출 줄도 PR 본문과 같은 꼴이고, 그 글은 보관 폴더 · 상태 파일의 경로를 싣지 않는다.

### §6 답으로 인정하는 기록

기록 파일을 읽는 자리는 둘이다 — 기본 브랜치와 기록 브랜치. 에픽 브랜치의 기록은 답으로 읽지 않는다 — 구현 쪽이 커밋하는 브랜치라 거기 있는 기록을 지휘자가 썼는지 가릴 길이 없다. 지휘자 기계 상태에 경로와 지문을 적어 견주는 길도 기계 상태가 검사받는 하위 agent 도 쓸 수 있는 파일이라 믿는 자리가 되지 못한다(`conductor_ledger.py` 의 「검사받는 하위 agent 도 쓸 수 있는 파일이라」 주석).

- **리뷰 기록의 자리.** 리뷰 기록은 모두 로드맵의 기록 브랜치에 쓰고, 에픽 브랜치에는 리뷰 기록을 쓰지 않는다 — spec 승인 앞 · 머지 앞(좁은 재리뷰 포함) · 이름으로 청한 리뷰 가운데 지금 에픽 브랜치에 쓰는 것(spec 승인 전 에픽 · 구현이 끝난 머지 전 에픽)도 같다. 지금은 spec 승인 앞 · 머지 앞의 기록을 에픽 worktree 에서 에픽 브랜치에 커밋해 에픽 PR 과 함께 머지한다. `qg-review.md` 의 「자리」 표 네 줄의 기록 칸 · 「기록 브랜치」 절 · 기록을 쓰는 걸음들(「이름으로 청함」 의 두 줄 · 「좁은 재리뷰」 · 「좁은 재리뷰의 의도 점검」) · 「이미 답한 것」 의 읽는 자리가 바뀐다. 커밋하고 push 하는 때와 그 PR 을 여는 때는 기록 브랜치의 지금 규칙 그대로다(답을 받은 직후 커밋 · push · 「잘못 골랐다」 가 있으면 바로, 그 밖에는 로드맵을 닫을 때 PR).
- **같은 PR 의 좁은 재리뷰.** 첫 머지 앞 리뷰의 기록이 답을 받은 직후 기록 브랜치에 push 되므로, 같은 PR 의 좁은 재리뷰는 기록 브랜치(`origin/<기록 브랜치>`)의 앞 기록에서 답을 이어받는다.
- **읽는 쪽 둘.** 기록 파일을 읽는 길은 둘이다 — 답 넘기기 스크립트(`--ref` 는 기본 브랜치와 기록 브랜치만)와 spec 승인 앞 자리의 「끝난 리뷰」 판정(기록 파일의 「보관 사본」 표지 — spec 승인 앞 기록도 이제 기록 브랜치에 있어 거기서 읽힌다). 둘 다 위 두 자리만 읽는다. 머지 앞 자리의 「끝난 리뷰」 와 승인 기록 다시 보이기는 상태 파일이 정하므로 기록 파일을 보지 않는다.
- **옛 기록.** 이 변경 전에 에픽 브랜치에 커밋된 기록(이 로드맵의 R7 · R8 · R9 spec 기록 등)은 그 PR 과 함께 기본 브랜치에 머지된 뒤에 읽힌다. 그 전에는 읽지 않아 같은 질문이 다시 물어질 수 있다 — 더 묻는 쪽으로 틀린다.
- **기록 브랜치를 만들지 못했을 때.** 지금 `qg-review.md` 「기록 브랜치」 의 펜스가 브랜치 접두를 정하지 못해 멈추는 것처럼 기록 브랜치를 만들지 못하면, 그 사유를 보이고 「이 답은 다음 리뷰로 넘어가지 않는다」 를 알린 뒤 진행한다 — 에픽 브랜치에 대신 쓰지 않는다. 머지 앞 답은 상태 파일에 남는다 — 「답 적기」 로 그 답의 기록 파일 경로 자리에 「기록 브랜치 없음 — <사유>」 를 적으면 리뷰가 닫힐 수 있고(§1 「닫는 조건」) 「다음」 이 기록 파일 쓰기를 다시 내지 않는다(§4). spec 승인 앞 답은 설계문서의 지휘 기록에 한 줄(질문 정체 · 답 · 「기록 브랜치 없음 — <사유>」)로 남긴다. 다음 리뷰는 그 답을 받지 못해 같은 질문을 다시 물을 수 있고, spec 승인 앞 자리는 「끝난 리뷰」 판정이 기록 파일을 찾지 못해 다시 들어오면 그 질문을 다시 물을 수 있다 — 더 묻는 쪽이다.
- **내줌.** 에픽 PR 에는 리뷰 기록이 하나도 실리지 않는다. 기록은 기록 브랜치의 PR(로드맵을 닫을 때, 또는 「잘못 골랐다」 로 바로 여는 PR)로 기본 브랜치에 들어온다.

**한계.** 에픽 브랜치의 기록을 읽지 않아도, 구현 쪽이 에픽 브랜치에 넣은 가짜 기록이 에픽 PR 의 diff 에 섞여 기본 브랜치로 머지되면 그 뒤로는 기본 브랜치의 기록으로 읽힌다 — 그 diff 는 통합 리뷰와 사용자가 본다. 지휘자는 에픽 브랜치에 리뷰 기록을 쓰지 않으므로, 에픽 PR 의 diff 에 든 리뷰 기록 파일은 지휘자가 쓴 것이 아니다. qg 가 리뷰 트리의 답 폴더에서 스스로 읽는 답 파일도 이 확인 밖이다(Non-goals). README 에 적는다.


### §7 답 넘기기 스크립트

- **읽지 못한 기록.** 기록 파일 하나를 읽지 못하면 그 파일과 같은 대상(파일 이름의 에픽 번호 또는 로드맵)의 답은 넘기지 않는다 — 읽지 못한 파일이 그 답을 뒤집었을 수 있다. 파일 이름조차 틀 밖이면 어느 답도 넘기지 않는다. 읽는 자리(ref) 하나를 통째로 읽지 못하면(그 ref 를 찾지 못했다 · 그 자리의 파일 목록을 읽지 못했다) 그 ref 의 답은 하나도 넘기지 않고 알림 한 줄을 낸다 — 더 묻는 쪽이다.
- **앞 답을 빼는 조건.** 뒤 기록의 「전에 한 답」 줄은 그 뒤 기록의 새 답이 「의도다」 · 「잘못 골랐다」 일 때만 앞 답을 뺀다. 「지금은 모르겠다」 · 「답하지 않음」 · 「묻지 않음」 은 앞 답을 빼지 않는다.
- **여러 줄 답.** 기록 틀에서 직접 쓴 답 원문이 여러 줄이면 둘째 줄부터 들여 쓴다(관찰 줄과 같은 꼴). 스크립트는 들여 쓴 줄을 그 칸의 이어지는 글로 읽는다 — 줄머리가 `## ` 인 답 줄이 질문 절을 끊지 않는다.
- **앞 답 줄의 칸.** 뒤 기록의 「전에 한 답」 값 `<답> · <답한 때> · <열쇠 또는 정체> · <까닭>` 은 구분 글자 ` · ` 의 자리로 칸을 떼지 않고 칸마다 제 꼴로 읽는다. 지금 `qg_answered.py` 의 `_prior_key` 는 `value.split(" · ", 2)` 로 앞 두 칸을 왼쪽에서 떼고 끝 칸을 오른쪽에서 떼어, 「답한 때」 에 ` · ` 가 들면 그 뒷부분을 열쇠의 앞머리로 잘못 읽는다 — 앞 답이 빠지지 않아 그 질문을 덜 묻는다(R6 머지 뒤 리뷰의 제안 26). 맞게 읽는 법은 이렇다 — 첫 칸은 답의 값(「의도다」 · 「잘못 골랐다」), 둘째 칸은 기록 틀의 「답한 때」 꼴(`YYYY-MM-DD HH:MM` 이나 `-`)이어야 하고, 끝 칸은 까닭이며, 그 사이가 열쇠 또는 정체다(정체에는 ` · ` 가 들어도 된다). 둘째 칸이 그 꼴이 아니면 열쇠를 짐작하지 않고 그 기록을 읽지 못한 기록으로 센다 — 같은 대상의 답을 넘기지 않는다(위 「읽지 못한 기록」, 더 묻는 쪽). 그 값의 출처인 기록의 `- 답한 때:` 줄도 같다 — 그 꼴이 아니면 그 기록을 읽지 못한 기록으로 센다(그 값이 qg 를 거쳐 다음 기록의 「전에 한 답」 둘째 칸으로 되돌아온다).
- **이름에 구분 글자가 든 기록 파일.** 이름에 ` · ` 가 든 기록 파일은 이름 틀 밖으로 센다(위 「읽지 못한 기록」 의 「파일 이름조차 틀 밖」). 그 이름에서 지은 열쇠(`<이름>#<번호>`)는 qg 가 칸을 ` · ` 로 나눠 읽어 맞출 수 없다 — 지휘자의 기록 이름에는 ` · ` 가 들지 않는다. 지금 그런 이름을 정상 열쇠로 굳힌 테스트(`test_qg_answered.py` 의 `test_prior_cell_identity_with_separator` 의 열쇠 몫 — 제안 31)는 이 동작을 재게 고쳐 쓰고, 정체에 ` · ` 가 든 「전에 한 답」 을 읽는 몫은 그대로 둔다.
- **같은 이름의 기록 파일.** 기록 파일 이름 끝의 번호(-2, -3 …)는 쓰는 기록 브랜치만이 아니라 기본 브랜치도 보고 붙인다 — 읽는 자리 둘을 모두 본다.
- **알림이 사라지지 않게.** 알림 줄은 파일에 쓰기 전에 화면(표준 오류)에 먼저 낸다. 답 파일은 썼는데 알림 파일만 쓰지 못한 경우를 따로 가른다 — 답 파일을 그대로 쓰되 다른 종료 코드와 「알림 파일을 쓰지 못했다 — 알림은 위 줄뿐이다」 한 줄로 알린다. 답 파일을 쓰지 못한 경우는 지금의 종료 코드 그대로다.
- **종료 코드 표.** 지휘 절차의 종료 코드 표에 그 행과 「그 밖」 행(스크립트가 죽은 경우 포함 — 답 없이 보내고 알린다)을 더하고, 스크립트가 기대는 파이썬 패키지를 의존 표에 적는다.
- **R6 머지 뒤 리뷰의 제안 열다섯**(지휘 자원 `report/qg-R6-merged-pr331-2026-11-24/handler-report.md` 의 제안 목록 22–36번). 줄마다 번호 · 파일 · 요지 · 가름이다. 가름은 셋이다 — 「들어감」(이 설계의 그 절 · AC 가 받는다) · 「계획이 가림」(동작이 바뀌지 않는 주석 · 테스트 · 안쪽 고침이라 계획이 받거나 이유를 적어 남긴다) · 「남김(받는 곳 없음)」(이 설계에 없는 동작 변경이라 계획이 골라 받지 않는다). 남긴 것은 PR 본문에 적는다.
  - 22 · `spec-distill/dependencies.md` · PyYAML 행이 없다 — 들어감(§7 「종료 코드 표」 의 의존 표 · AC22)

### §8 알림 · 지휘 기록 · 락

- **앞 리뷰와 같은 알림 줄은 접는다.** 답 넘기기 스크립트는 지금처럼 리뷰마다 모든 알림(읽지 못한 기록 · 읽지 못한 자리 · 틀 밖의 답)을 표준 오류와 알림 파일(그 리뷰의 보관 폴더의 `qg-answered-notices.txt`)에 낸다 — 스크립트는 접지 않는다. 접는 곳은 지휘자의 리뷰 글이고, 견주는 것도 지휘자다. 지휘자는 이번 알림 파일의 줄을 바로 앞 리뷰의 보관 폴더(`## 자원` 에 이번 보관 폴더보다 먼저 적힌 qg 보관 폴더 가운데 마지막 것)에 남아 있는 알림 파일의 줄과 글자 그대로 견주고, 같은 줄은 리뷰 글에서 「전에 알린 알림 <n>줄 — 자세히는 알림 파일」 한 줄로 접는다(<n> 은 접은 줄의 수 — 알림 줄 하나가 「읽지 못한 기록 5개」 여도 1줄로 센다. D42 의 글자 「전에 알린 기록 n개」 는 n 이 기록 수로 읽혀 2026-11-25 리뷰 2라운드에서 고침). 다른 줄은 그대로 싣는다. 기계 상태에 알린 기록을 적지 않고 원장 명령도 두지 않는다(접는 곳은 D18 그대로 · D2 의 「기록마다 한 번」 은 2026-11-25 리뷰 1라운드에서 장치를 줄임).
  - 귀결 — 알림 줄은 「읽지 못한 기록 N개: a · b」 처럼 묶음 줄이라, 새 기록 하나가 더해지면 그 줄이 달라져 앞 기록도 함께 다시 뜬다.
  - 앞 보관 폴더나 그 알림 파일이 없는 자리(다른 컴퓨터 · 자원 정리 뒤 · 로드맵의 첫 리뷰)에서는 접지 못하고 다 싣는다.
  - 알림 파일 쓰기가 실패한 실행(§7)은 접지 않고 그 실행의 표준 오류 줄을 그대로 싣는다.
- **여러 줄 지적을 지휘 기록에.** 보인 지적의 원문을 설계문서의 지휘 기록에 올릴 때 여러 줄이면 첫 줄만 싣고 끝에 「…(전문: <보관 폴더 이름>의 지적 목록)」 을 붙인다. 접은 글을 원문이라고 부르지 않는다.
- **락.**
  - 머지 관문 — 지휘 절차 문서의 머지 전 확인이 스위트 대조 앞에서 스크립트의 관문을 부른다는 문장(옛 형식과 team 형식 둘 다)과, 다시 들어오는 자리(지휘 순환의 맞추기 걸음 · 손으로 따르는 절차)가 「다음」 을 부른다는 문장. 관문의 조건 자체는 스크립트의 테스트가 잰다.
  - team 형식 문장 — 「두 번까지」 가 옛 형식과 같다는 것 · 기본 브랜치 합치기를 하지 않는다는 것 · 자리 글자의 꼴.
  - 두 플러그인이 함께 쓰는 낱말 — 리뷰어가 「전에 물은 것」 에 붙이는 까닭 낱말 둘이 qg 스크립트와 지휘 절차 문서에서 같다.
  - 스크립트와 지휘자가 읽는 qg 파일의 꼴 — 결과 파일의 절 이름(판정 · 범위 · 고칠 목록 · 차등 회귀 · 거른 질문 목록 둘 — 실제 머리 `이미 답한 질문이라 거른 질문:` · `이미 「잘못 골랐다」 답이 있어 거른 질문:`)과 합쳐지기 전 지적 목록의 키, 그리고 「돌아옴」 이 읽는 의도 점검 돌려주는 꼴의 칸 이름(질문마다의 `state` 와 그 값 `묻지 않음` · `상한 넘어 남김`). 그 키를 qg 의 세션 파일 꼴 문서에 적고, 읽는 쪽이 쓰는 이름이 그 문서에 있는지 잰다.
  - 검사받는 쪽에 보내는 글과 표시 글 — 되돌리기에서 구현 담당자에게 보내는 글과 team 형식의 다음 시도에 싣는 글이 처리 파일의 절대경로를 싣고(양), 리뷰 보관 폴더 · 상태 파일의 경로를 싣지 않는다(음). 지휘 절차 문서의 PR 본문 호출 줄 꼴이 `- 호출 · <자리 글자> · <범위>` 이고, 스크립트가 짓는 표시 글(PR 본문 `## qg 리뷰` 절의 글 · team 형식의 펜스 글)에 리뷰 보관 폴더 · 상태 파일의 경로(`--answered` 값 포함)가 없다(음 — 글은 스크립트의 테스트가 잰다).
- **지금 있는 락.** 지휘 절차 문서의 문장을 핀한 지금 테스트 가운데 PR 본문에서 읽기 · 호출 줄 적기 · 다시 보내기 표지를 잠근 것은 지우거나 새 문장으로 다시 쓴다 — 계획이 그 목록을 짓고, 지운 락마다 같은 뜻을 스크립트의 테스트가 잰다는 것을 적는다.


### §9 이 변경 전에 시작한 PR 과 team 형식

**이 변경 전에 시작한 PR · 다른 컴퓨터.** 그 PR 의 상태 파일이 하나도 없는데 머지 앞 리뷰의 옛 흔적(PR 본문의 `## qg 리뷰` 절 · 그 자리 글자의 보관 폴더 · 쌓인 기록 줄)이 있으면, 스크립트는 옛 흔적에서 범위나 횟수를 읽지 않는다 — 「옛 흔적이 있다 — PR 전체를 처음부터 리뷰한다」 를 내고 첫 리뷰를 연다. 옛 PR 본문에 적힌 막는 지적과 사용자 답은 지휘자가 사용자에게 한 번 보인다(새 리뷰가 같은 지적을 다시 낼 수 있다).

**team 형식.** 검수 걸음의 머지 앞 리뷰도 같은 스크립트와 상태 파일을 쓴다 — 대상이 PR 번호 대신 과제와 계획 번호다.

- 지금 검수 결과 파일의 펜스 안에 「적고 거기서 세던」 것(범위 · 지난 리뷰의 끝 · 돌려보낼 막는 지적 · 재리뷰 횟수 · 멈출 조건)은 상태 파일이 쥔다. 펜스는 스크립트가 지은 표시 글을 싣는 자리로 남는다 — 지휘자는 거기서 읽지 않는다.
- 돌려보내는 길(반려와 시작 묶음의 다음 시도) · 지적마다의 처리를 다음 시도의 구현 결과 파일에 적게 하는 것 · PR 이 열리면 펜스 내용을 본문으로 옮기는 것은 그대로다. 구현 결과 파일의 처리는 지휘자가 읽어 스크립트의 「답 적기」 로 옮긴다 — 시작 묶음과 과제 결정 기록에 싣는 글이 그 파일의 `## 지적마다의 처리` 머리 아래에 쓰라고 싣는다(§1).
- 반려로 다음 시도를 보낼 때도 「돌려보냄」 을 적는다 — 처리 파일 자리는 그 시도의 구현 결과 파일이다. 시작 묶음과 과제 결정 기록에 싣는 글에도 리뷰 보관 폴더 · 상태 파일의 경로를 싣지 않는다.
- 「qg 리뷰 없이 감」 은 PR 이 아직 없으면 펜스에 싣고, PR 이 열릴 때 본문으로 옮겨진다.
- 좁은 재리뷰를 여는 기준 커밋(§2)에서 리더가 쓰는 기록 파일 — 그 과제의 검수 결과 파일과 INTENT.md(과제 결정 기록) — 만 바꾼 커밋은 빠진다. 리더가 검수 결과를 적거나 결정 줄을 옮긴 커밋만 더해진 과제 브랜치에서는 좁은 재리뷰가 열리지 않는다. 다음 시도의 구현 결과 파일은 처리만 적은 것이어도 구현 담당자의 커밋이라 빠지지 않고, 과제의 설계문서(`design.md`)를 바꾼 커밋도 빠지지 않는다(§2).

## Acceptance Criteria

- AC1. 머지 앞 자리의 리뷰마다 보관 폴더에 상태 파일이 하나 있고 §1 의 칸 열하나를 담는다. 지휘 절차 문서에 PR 본문 `## qg 리뷰` 나 team 형식의 펜스에서 범위 · 횟수 · 막는 지적 · 답을 읽으라는 문장이 없다. 상태를 옮기는 명령은 셋(보냄 · 돌아옴 · 답 적기)이고 닫힘 사유는 §1 의 여덟 가운데 하나다.
- AC2. 스크립트의 「돌아옴」 은 §1 의 표대로 가른다 — 판정이 있고 본 범위가 맞으면 지적 목록을 얻음, 결과 파일이 없거나 판정이 없거나 본 범위가 다르면 얻지 못함(사유 문장이 표와 같다), 리뷰할 것이 없었으면 막는 지적 0개로 닫힘. 의도 점검의 돌려주는 꼴이 범위 칸을 비워 와도 결과 파일의 범위 절로 가른다.
- AC3. 막는 지적과 새로 깨진 테스트의 원문 · 거른 질문 목록 둘이 보관 폴더의 파일에서 상태 파일로 옮겨지고, 의도 점검 질문은 `state` 가 `묻지 않음` 인 것만 물을 것에 옮겨진다(`상한 넘어 남김` 은 옮겨지지 않는다) — PR 본문이나 대화의 담당자 보고가 없어도 돌려보낼 목록이 같다. 구현 담당자의 지적마다 처리는 그 에픽 보고 폴더의 처리 파일에서 지휘자가 읽어 「답 적기」 로 옮기고, 사용자가 고른 제안과 되올린 낮춘 지적은 그 PR 의 마지막 리뷰의 막는 지적 칸에 들어(그것을 낸 리뷰가 다르면 표시로 남는다) 관문이 센다.
- AC4. 좁은 재리뷰는 기준 커밋(§2 — 지적 목록을 얻은 마지막 리뷰의 끝부터 브랜치 끝 사이에 리더(지휘자)가 쓰는 기록 파일 — 옛 형식은 그 에픽의 설계문서, team 형식은 그 과제의 검수 결과 파일과 INTENT.md — 밖의 파일을 바꾼 커밋)이 하나라도 있을 때만 열린다 — 리더의 기록 파일만 바꾼 커밋으로 브랜치 끝이 움직인 경우(team 형식에서 검수 결과 파일 · 결정 기록 커밋만 더해진 과제 브랜치 포함)에는 열리지 않고, 구현 담당자가 「반박」 · 「손대지 않음」 만 적고 올린 커밋(team 형식의 처리만 적은 구현 결과 파일 포함)이나 team 형식에서 과제의 설계문서를 바꾼 커밋이 있으면 열린다. 「재리뷰로 이어짐」 으로 닫는 조건도 같은 기준이다. 「답 적기」 는 적어 낸 「고친 커밋」 해시가 기준 커밋에 없으면 그 지적을 「처리 없음」 으로 되돌리고, 「다음」 이 「적어 낸 고친 커밋 <해시> 가 범위에 없다」 를 보이며 돌려보내기를 낸다. 「재리뷰로 이어짐」 으로 닫은 뒤 기준 커밋이 없어진 리뷰(브랜치가 다시 쓰였다)에서 「다음」 은 「열기」 를 내지 않고 적을 값 없는 「답 적기」 로 다시 가리기를 낸다 — 「다음」 이 낸 「열기」 를 「열기」 가 거절하는 상태가 없다. 시작은 지적 목록을 얻은 마지막 리뷰의 끝이다. merge 커밋이 끼면 PR 전체다. 세는 재리뷰가 상한(처음 둘 — 「한 번 더 돌려보낸다」 답마다 그때의 세는 수에 하나를 더한 값, §2)에 닿은 PR 에서 구현 길로 돌려보낼 것이 생기면 돌려보내기 전에 「두 번까지」 의 질문 차례가 나오고, 「한 번 더」 답이 있어야 상한을 넘는 재리뷰가 열린다(예외와 그 밖의 경우는 AC32). 지적 목록을 얻지 못해 다시 보낸 리뷰는 그 수에 들지 않는다.
- AC5. 구현이 끝난 뒤 이름으로 청한 리뷰도 상태 파일을 쓰고, 그 뒤 좁은 재리뷰가 그 끝에서 시작한다. 그 리뷰는 머지 앞 첫 리뷰를 대신하지 않는다 — 이름으로 청한 리뷰(와 그 뒤 좁은 재리뷰)의 상태 파일만 있으면 그 리뷰들이 닫힌 뒤 「다음」 이 첫 리뷰(PR 전체)를 열고, 그 사이 관문은 닫혀 있다. 이름으로 청한 리뷰는 「두 번까지」 에 들지 않고, 그 뒤의 좁은 재리뷰는 든다.
- AC6. 관문은 그 PR 의 상태 파일 전부와 git 을 보고 §3 의 닫히는 까닭 여덟(리뷰가 도는 중 · 에픽을 멈춤 · 지적 목록을 얻지 못함 · 물을 것이 남음 · 기록 파일 경로가 빔 · 「잘못 골랐다」(거른 목록 포함) · 열린 막는 지적 · 첫 리뷰 없음) 가운데 하나도 없을 때만 열고, 닫혀 있으면 걸린 까닭을 모두 낸다. 열린 막는 지적은 처리가 「고친 커밋」 인데 그 고침을 본 리뷰(그 지적이 든 리뷰 뒤에 연 리뷰 — 고른 제안 · 되올린 지적은 적을 때의 마지막 리뷰에 든다)가 지적 목록을 얻지 않았거나, 반박 · 손대지 않음인데 사용자가 남기지 않은 것이다 — 「리뷰 없이 머지 준비로 간다」 를 고른 PR 에서는 앞 리뷰에서 처리가 「고친 커밋」 인 막는 지적이 「리뷰 없이 가기로 함」 으로 닫혀 관문을 막지 않는다. 상태 파일이 하나도 없는 PR 에 「qg 없음」 인자를 주면 관문은 「열림 — qg 리뷰 없음(quality-gates 가 설치돼 있지 않다)」 을 내고 상태 파일이 생기지 않는다. 상태 파일이 있는 PR 에서는 그 인자를 쓰지 않고 그렇다고 알린다. 인자 없이 상태 파일이 하나도 없으면 「첫 리뷰 없음」 으로 닫힌다.
- AC7. 리뷰가 지적 목록을 얻지 못하면 §3 의 질문 차례가 나오고, 지휘 절차 문서의 선택지 셋이 글자와 차례까지 §3 과 같다. 「다시 보낸다」 는 같은 범위의 새 리뷰를 열고, 「리뷰 없이 머지 준비로 간다」 는 관문을 열며 표시와 승인 기록 다시 보이기에 실린다 — 좁은 재리뷰에서 고르면 앞 리뷰에서 처리가 「고친 커밋」 인 막는 지적도 「리뷰 없이 가기로 함」 으로 닫히고, 그 지적들이 승인 기록 다시 보이기 맨 위의 「qg 리뷰 없이 감」 줄 아래에 실린다(AC6). 의도 점검만 셀 수 없는 리뷰에는 이 질문이 나오지 않는다.
- AC8. 「다음」 은 §4 의 표를 위에서부터 보고 줄마다 그 할 일로 답한다 — 열림은 같은 상태 파일로 다시 보내기이고 새 상태 파일이 생기지 않는다. 「보내는 중」 에서 끊긴 리뷰에서 「다음」 은 보관 폴더에 결과 파일이 있으면 「돌아옴」, 없으면 「보냄」 을 내고, 지휘자가 하니스 목록에서 그 리뷰의 살아 있는 담당자를 찾으면 그 대신 「보냄」 으로 그 이름을 적어 다시 보내지 않는다(지휘자가 가리는 갈림 — §4). 묻다가 끊긴 질문(답 값이 아직 적히지 않은 것)은 다시 나오고, 「답하지 않음」 으로 적힌 의도 점검 질문은 다시 나오지 않으며, 의도 점검 결과에서 `상한 넘어 남김` 인 질문은 물을 것에 들지 않아 나오지 않는다. 답은 적었는데 기록 파일을 쓰기 전에 끊긴 경우는 다시 묻지 않고 기록 파일 쓰기가 나온다. 담당자가 옮긴 질문이 있는 리뷰에서 「다음」 은 그 질문(사용자 차례)을 내고 「지적 목록을 얻지 못함」 으로 떨어지지 않는다. 답을 적은 뒤 지휘자가 그 담당자를 이어 부르면 그 담당자가 살아 있는 이름에 들어 「기다린다」 가 나오고, 이어 부를 수 없어 「돌아옴」 을 부르면 보관 폴더의 파일로 가려 결과 파일이 없을 때 「지적 목록을 얻지 못함」 이 되고 「다음」 이 §3 의 질문을 낸다.
- AC9. 「잘못 골랐다」 로 설계 대화에 돌아간 PR 은 단계 칸의 그 닫힘 사유에 「다시 구현됨」 표시가 붙기 전에는 새 리뷰가 열리지 않는다 — 고친 설계문서 커밋으로 브랜치 끝이 움직여도 같다. spec 승인 앞의 다시 보내기 표지는 설계문서 커밋을 싣고 그 커밋 그대로인 동안 쓰이지 않는다. 「에픽을 멈춤」 · 「재분해 신호」 로 닫힌 PR 에서 「다음」 은 멈춰 있다고 답한다. 재분해 신호로 닫힌 PR 은 단계 칸의 그 닫힘 사유에 「재분해 뒤 이어 감」 표시가 붙으면 「다음」 이 첫 리뷰(PR 전체)를 새로 여는 「열기」 를 내고 「열기」 가 그것을 받으며, 관문과 「두 번까지」 가 그 리뷰부터 센다 — 표시가 붙기 전에는 새 리뷰가 열리지 않는다.
- AC10. PR 본문 `## qg 리뷰` 절의 글 · 승인 기록 다시 보이기의 qg 몫 · 구현 담당자에게 돌려보낼 지적 목록을 스크립트가 상태 파일에서 짓는다 — 둘째는 질문 글 · 답 · 답 원문(상태 파일의 사용자 답 전부) · 이름으로 청한 리뷰의 답 · 「앞 리뷰에서 답함」 · 「qg 리뷰 없이 감」(그 아래에 처리가 「리뷰 없이 가기로 함」 인 막는 지적) · 처리가 「사용자가 남김」 인 막는 지적 · 리뷰마다 닫힘 사유를 싣고, 상태 파일에 있는 그 셋(사용자 답 · 「사용자가 남김」 · 닫힘 사유) 가운데 빠지는 것이 없다. 상태 파일이 없는 PR 에 「qg 없음」 인자로 지은 둘째는 맨 위에 「qg 리뷰 없음(quality-gates 가 설치돼 있지 않다)」 을 싣는다. 첫째의 호출 줄은 `- 호출 · <자리 글자> · <범위>` 꼴까지이고, 첫째와 team 형식의 펜스 글에 리뷰 보관 폴더 · 상태 파일의 경로(`--answered` 값 포함)가 없다. 셋째는 처리 파일의 절대경로를 싣고 리뷰 보관 폴더 · 상태 파일의 경로를 싣지 않는다. team 형식의 펜스에 싣는 글은 지적 원문에 백틱 펜스가 들어 있어도 바깥 펜스가 한 번 열리고 한 번 닫힌다.
- AC11. 기록 파일을 읽는 두 길(답 넘기기 · spec 자리의 「끝난 리뷰」 판정)은 기본 브랜치와 기록 브랜치만 읽는다 — 지휘 절차 문서의 답 넘기기 호출 꼴에 에픽 브랜치의 `--ref` 가 없고, 에픽 브랜치에만 있는 기록의 답은 넘어가지 않는다. 리뷰 기록(spec 승인 앞 · 머지 앞 · 좁은 재리뷰 · 이름으로 청한 리뷰)은 모두 기록 브랜치에 커밋되고 에픽 브랜치에는 커밋되지 않는다 — 지휘 절차 문서의 「자리」 표 네 줄의 기록 칸이 모두 기록 브랜치다. spec 승인 앞 기록의 「보관 사본」 표지가 기록 브랜치에서 읽혀 끝난 리뷰를 다시 보내지 않고, 같은 PR 의 좁은 재리뷰는 첫 머지 앞 리뷰의 답을 기록 브랜치에서 이어받는다.
- AC12. 없앰 — 등록부를 없앴다(D23). 에픽 브랜치의 기록을 답으로 읽지 않아 등록할 것이 없다.
- AC13. 읽지 못한 기록 파일이 있으면 같은 대상의 답이 넘어가지 않는다. 파일 이름이 틀 밖이면 어느 답도 넘어가지 않는다. 읽는 자리 하나를 통째로 읽지 못하면 그 자리의 답은 하나도 넘어가지 않고 알림 한 줄이 남는다.
- AC14. 뒤 기록의 새 답이 「지금은 모르겠다」 · 「답하지 않음」 · 「묻지 않음」 이면 앞 답이 그대로 넘어간다. 「의도다」 · 「잘못 골랐다」 면 앞 답이 빠진다.
- AC15. 여러 줄 답(줄머리 `## ` 포함)이 든 기록 파일이 읽히고 그 답이 넘어간다. 기록 틀이 들여 쓰는 규칙을 적는다. 기록 파일 이름의 번호 규칙이 읽는 자리 둘(쓰는 기록 브랜치 · 기본 브랜치)을 모두 본다.
- AC16. 알림 줄은 알림 파일 쓰기가 실패해도 화면에 남고, 그 경우가 답 파일을 쓰지 못한 경우와 다른 종료 코드 · 다른 줄로 갈린다. 지휘 절차의 종료 코드 표가 그 행과 「그 밖」 행을 갖는다.
- AC17. 바로 앞 리뷰의 보관 폴더에 남은 알림 파일과 글자가 같은 알림 줄은 지휘자의 리뷰 글에서 「전에 알린 알림 <n>줄 — 자세히는 알림 파일」 한 줄로 접히고(<n> 은 접은 줄의 수), 다른 줄(새 기록이 더해진 묶음 줄 포함)은 그대로 실린다 — 접는 규칙은 지휘 절차 문서에 있고 답 넘기기 스크립트는 매번 모든 알림을 표준 오류와 알림 파일에 낸다. 앞 보관 폴더나 그 알림 파일이 없으면 접지 않고, 알림 파일 쓰기가 실패한 실행도 접지 않는다. 기계 상태에 알린 기록 목록이 없고, 그것을 적고 읽는 원장 명령도 없다.
- AC18. 여러 줄 지적을 지휘 기록에 올리는 문장이 첫 줄과 전문 자리를 싣게 적혀 있고, 그 꼴의 줄을 기록 명령이 받는다.
- AC19. 상태 파일이 없고 옛 흔적만 있는 PR 에서 스크립트는 옛 흔적에서 범위 · 횟수를 읽지 않고 PR 전체 리뷰를 연다.
- AC20. team 형식의 머지 앞 리뷰가 같은 스크립트와 상태 파일을 쓴다 — 대상이 과제와 계획 번호이고, 지휘 절차 문서의 team 형식 절이 펜스를 「표시」 로 적는다. 계획이 다른 두 리뷰의 상태 파일이 섞이지 않는다.
- AC21. §8 의 락 다섯이 있고, 각각 그 문장 · 낱말 · 이름을 지우거나 바꾸는 변이에서 실패한다.
- AC22. R6 머지 뒤 리뷰의 제안 열다섯은 §7 의 가름대로 PR 본문에 가려져 있다 — 「들어감」 은 그 AC 로 재고, 「계획이 가림」 은 「받음 · 남김(이유)」 으로, 「남김(받는 곳 없음)」 은 그대로 적는다. 「남김(받는 곳 없음)」 인 것의 동작은 바뀌지 않는다. spec-distill 의 판 · CHANGELOG · README · 의존 표(PyYAML 행 — 판 칸은 측정이 쓴다)가 이 변경을 싣고, README 가 §6 의 한계와 Non-goals 의 한계(상태 파일은 지휘자 기계 상태와 같은 폴더 나무에 있고 구현 담당자에게 건네는 처리 파일 경로의 옆 폴더라, 같은 컴퓨터 · 같은 사용자 권한의 담당자가 고치는 것은 막지 못한다. 마지막 확인은 §5 의 승인 기록 다시 보이기이고, 꾸민 답과 남김은 거기서 보이지만 상태 파일에서 지워진 지적은 보이지 못한다)를 적는다.
- AC23. 구현 · 계획 담당자에게 보내는 지휘 절차의 글(되돌리기의 보내는 글 · team 형식의 시작 묶음과 과제 결정 기록에 싣는 글)에 리뷰 보관 폴더와 상태 파일의 경로가 없고, 되돌리기의 글은 그 에픽 보고 폴더 안 처리 파일의 절대경로를 싣는다. qg 담당자에게 보내는 글은 지금처럼 보관 폴더 경로를 싣는다.
- AC24. 구현 길로 돌려보내면 상태 파일에 「돌려보냄」(담당자 이름 · 때 · 처리 파일 경로)이 적힌다. 처리를 옮기기 전에 「다음」 을 부르면 그 담당자가 살아 있을 때 「기다린다」 를 내고 다시 돌려보내지 않는다. 담당자가 없으면 처리 파일이 있을 때(하위 agent 길이면 그 마지막 메시지가 낸 지적마다의 처리가 대화에 남아 있을 때도) 「답 적기」 로, 없을 때 그 줄에 「처리 파일 없이 끝남」 을 적고 다시 돌려보내기로 간다. 쓸 처리 없이 끝난 「돌려보냄」(처리 파일 없이 끝남 · 옮겼으나 범위 밖 커밋 — §4)이 두 번째면 다시 보내지 않는다 — 「답 적기」 가 그 지적들의 처리를 「손대지 않음 — 처리 파일 없이 끝남」 (또는 「— 적어 낸 커밋이 범위에 없음」)으로 적고 고치지 않은 막는 지적의 질문을 물을 것에 적어, 「다음」 이 그 질문(지휘 절차 문서의 지금 선택지 셋 그대로 — 새 질문 창이 없다)을 낸다. 그 질문에 「다시 돌려보낸다」 를 적으면 세는 수가 처음부터 다시 시작돼, 그 뒤 처음 쓸 처리 없이 끝난 것은 다시 돌려보내기로 간다. 하위 agent 길과 세션 담당자 길 모두 같고, 되돌리기에서 하위 agent 길로 보내는 글도 처리 파일의 절대경로와 그 파일에 쓰고 끝내라는 문장을 싣는다.
- AC25. 「다음」 은 닫혔는데 관문이 닫힌 리뷰에도 할 일을 낸다 — 「이미 「잘못 골랐다」 답이 있어 거른 질문」 목록이 있으면 그 행선을 「답 적기」 로 적어 설계 대화로(단계 칸에 「다시 구현됨」 표시가 붙은 뒤에는 첫 리뷰), 사용자가 고른 제안이나 되올린 낮춘 지적을 적으면 「답 적기」 가 그것을 마지막 리뷰의 칸에 적고 단계를 「돌아옴」 으로 되돌려 구현 길로(상한에 닿았으면 먼저 「두 번까지」 — AC32), 「다시 보냄」 으로 닫힌 뒤 새 리뷰가 없으면 다시 보내기다. 어느 줄에도 맞지 않는 상태 파일에는 아무것도 하지 않고 그 지금 값을 보인다.
- AC26. 리뷰는 §1 「닫는 조건」 의 사유별 조건이 채워질 때만 「돌아옴」 이나 「답 적기」 로 닫힌다 — 「재리뷰로 이어짐」 은 「답 적기」 가 막는 지적의 처리를 다 적고 기준 커밋(§2)이 하나라도 있을 때 적고, 「열기」 는 앞 리뷰의 단계를 바꾸지 않는다. 의도 점검 답이 있는 리뷰는 그 답의 기록 파일 경로(또는 「기록 브랜치 없음 — <사유>」)가 적히기 전에는 닫히지 않아, 막는 지적 없이 질문만 온 리뷰에서 답을 적은 직후 끊겨도 「다음」 이 기록 파일 쓰기를 낸다. 「에픽을 멈춤」 으로 닫힌 리뷰에서 다시 띄운 질문에 다른 답을 적으면 단계가 「돌아옴」 으로 돌아가 그 답대로 다시 가려진다.
- AC27. 기록 브랜치를 만들지 못하면 사유와 「이 답은 다음 리뷰로 넘어가지 않는다」 가 보이고 흐름이 이어진다 — 에픽 브랜치에 리뷰 기록이 커밋되지 않는다. 머지 앞 답은 상태 파일의 기록 파일 경로 자리에 「기록 브랜치 없음 — <사유>」 로 남고, 그 뒤 「다음」 이 기록 파일 쓰기를 다시 내지 않는다. spec 승인 앞 답은 설계문서의 지휘 기록에 한 줄로 남는다.
- AC28. 머지 앞 리뷰에서도 쌓인 기록의 두 줄(질문이 하나도 없는 리뷰의 한 줄 · 보내지 못했거나 셀 수 없이 끝난 리뷰의 한 줄)이 지금 꼴대로 적혀 로드맵을 닫는 PR 본문에 실리고, 머지 앞 자리의 보낸 횟수는 그 줄이 아니라 상태 파일로 센다.
- AC29. 리뷰 상태 스크립트는 상태 파일을 `nofollow_write` 의 임시 파일 + 바꿔 놓기로 쓴다 — 상태 파일 자리에 심볼릭 링크가 있으면 그 링크가 가리키는 파일은 바뀌지 않고, 쓰다 끊겨도 상태 파일은 앞 내용이나 새 내용 둘 가운데 하나다. 답 넘기기 스크립트의 답 파일 · 알림 파일 쓰기도 지금처럼 임시 파일 + 바꿔 놓기라 쓰다 실패하면 반쯤 쓴 파일이 남지 않는다.
- AC30. 답 넘기기 스크립트는 「전에 한 답」 값을 칸마다 제 꼴로 읽는다(§7 「앞 답 줄의 칸」) — 「답한 때」 칸에 ` · ` 가 든 「전에 한 답」 이 있는 기록에서 열쇠를 잘못 읽어 앞 답을 넘기는 일이 없고, 그 기록은 읽지 못한 기록으로 세어 같은 대상의 답이 넘어가지 않으며 알림이 남는다. 기록의 `- 답한 때:` 가 `YYYY-MM-DD HH:MM` 이나 `-` 가 아닌 기록도 같다. 셋째 칸(정체)에 ` · ` 가 든 「전에 한 답」 은 지금처럼 읽혀 앞 답을 뺀다. 이름에 ` · ` 가 든 기록 파일은 이름 틀 밖으로 세어 그 이름의 열쇠가 넘어가지 않는다 — `test_qg_answered.py` 에 그 이름을 정상 열쇠로 기대하는 단언이 없고, 위 셋을 재는 테스트가 있다.
- AC31. 관문을 닫는 까닭 여덟 각각에 대해, §4 표에서 그 까닭의 줄마다 그 줄에 맞는 상태(상태 파일 · git · 살아 있는 담당자 이름)를 지어 「다음」 을 부르면 그 줄의 할 일 — 스크립트의 일 하나 또는 사용자 차례 — 이 나오고 끝 줄(「어느 줄에도 맞지 않는다」)이 나오지 않는다. 그 할 일을 스크립트 명령으로 한 뒤(사용자 차례면 그 답을 「답 적기」 로 적은 뒤 · 「기다린다」 면 기다린 담당자를 살아 있는 이름에서 뺀 뒤 · 설계 대화면 단계 칸의 그 사유에 「다시 구현됨」 표시를, 재분해면 「재분해 뒤 이어 감」 표시를 붙인 뒤) 다시 부르면 같은 할 일이 같은 상태로 다시 나오지 않는다 — 상태가 나아갔거나 사용자 차례다. 닫힘 사유 여덟으로 닫힌 리뷰도 같은 꼴로 재고, 「qg 없음」 인자 · 「리뷰 없이 감」 으로 관문이 열린 상태에서는 「머지 준비로 간다」 가 나온다. 「다음」 이 「열기」 를 낸 상태에서 「열기」 는 거절하지 않는다.
- AC32. 세는 재리뷰가 상한에 닿은 PR 에서 「두 번까지」 의 질문은 구현 길로 돌려보낼 것이 생길 때마다 나온다 — (가) 막는 지적 없이 닫힌 마지막 리뷰에 사용자가 고른 제안이나 되올린 지적을 「답 적기」 로 적으면 그 리뷰가 「돌아옴」 으로 돌아가고 물을 것에 「두 번까지」 가 적혀, 「다음」 이 구현 길로 돌려보내기 전에 그 질문을 낸다. (나) 「한 번 더 돌려보낸다」 로 연 재리뷰가 막는 지적을 안고 돌아오면 「돌아옴」 이 「두 번까지」 를 다시 물을 것에 적는다. 두 경우 모두 「두 번까지」 의 답이 없는 동안 「다음」 은 돌려보내기도 좁은 재리뷰의 「열기」 도 내지 않고, 「열기」 도 상한에 닿은 PR 의 좁은 재리뷰를 받지 않는다 — 예외는 「두 번까지」 의 답이 있는 마지막 리뷰가 그 사이 올라온 기준 커밋 때문에 「재리뷰로 이어짐」 으로 닫힌 때 하나이고, 그때는 「다음」 이 「열기」 를 내고 「열기」 가 받는다. 같은 리뷰에 의도 점검 답 「잘못 골랐다」 나 거른 「잘못 골랐다」 목록이 있으면 물을 것에 「두 번까지」 가 남지 않아(「돌아옴」 이 적지 않고, 「답 적기」 가 「잘못 골랐다」 를 적을 때 거둔다) 그 질문이 나오지 않고 「다음」 이 까닭 6 의 줄을 낸다.
- AC33. 「열기」 는 이름으로 청한 리뷰를 포함해 새 리뷰를 그 PR 의 마지막 리뷰가 닫혀 있을 때(또는 상태 파일이 없을 때)만 받는다 — 마지막 리뷰가 열림 · 보내는 중 · 보냄 · 돌아옴이면 상태 파일을 만들지 않고 까닭과 지금 할 일(그 상태에서 「다음」 이 내는 줄)을 낸다. 지휘 절차 문서에 「이름으로 청한 리뷰에는 이 확인을 쓰지 않는다 — … 이미 보낸 리뷰가 있어도 보낸다」 가 머지 앞 자리에서 남아 있지 않다. 「열기」 가 받는 상태는 §2 「「열기」 가 받는 상태」 의 여섯이고, 이름으로 청한 리뷰 하나를 빼면 「다음」 이 「열기」 를 내는 상태와 같다.

## Rejected Alternatives

- **지금 구조에 문장을 더 얹는다.** 이 설계의 첫 초안이다 — 점검이 규칙끼리 부딪히는 곳 넷과 team 형식에 남는 구멍을 짚었다(Approaches 2).
- **가장 심각한 셋만 고친다.** 받는 쪽이 정해지지 않은 미룸이 또 생긴다(Approaches 3).
- **PR 본문을 계속 믿고 편집 흔적을 본다.** 지휘자 자신이 그 절을 계속 고쳐 흔적이 가려지고, team 형식에는 PR 이 아직 없다.
- **상태를 에픽 브랜치에 커밋한다.** 구현 쪽이 커밋하는 브랜치다.
- **상태를 기계 상태의 줄들로 둔다.** 리뷰 하나의 상태가 여러 줄에 흩어져 지금과 같은 꼴이 된다 — 리뷰마다 파일 하나가 읽기도 쉽다.
- **모든 자리(spec · 로드맵 끝)에 상태 파일을 쓴다.** 머지를 막는 관문이 없는 자리까지 옮기면 이 에픽이 다시 커지고 지금 도는 로드맵의 옛 흔적을 더 많이 다뤄야 한다.
- **이름으로 청한 리뷰는 지금처럼 바로 보낸다.** 앞 리뷰가 돌아옴 · 도는 중이어도 보내면, 앞 리뷰의 남은 질문과 돌려보냄을 새 리뷰와 잇는 규칙(어느 리뷰의 물을 것이 관문을 막나 · 돌려보낸 처리를 어느 리뷰에 옮기나 · 어느 리뷰가 「마지막 리뷰」 인가)이 더 든다 — 사용자가 앞 리뷰가 닫힌 뒤에 보내는 길을 골랐다(리뷰 4라운드).
- **스크립트가 질문을 띄우고 답을 고른다.** 사람 몫이다 — 스크립트는 차례만 낸다.
- **에픽 브랜치의 기록을 아예 읽지 않는다.** 첫 판에서 기각했다 — 설계 승인 앞에서 한 답이 같은 에픽의 머지 앞 리뷰에 넘어가지 않는다. 지금은 고른 길이다(D23 · D31) — 리뷰 기록을 모두 기록 브랜치에 써서 그 까닭을 없앴다.
- **머지 앞 기록은 에픽 브랜치에 두고, 같은 PR 의 좁은 재리뷰에서 다시 묻는 것을 받아들인다.** 기록이 에픽 PR 과 함께 머지되지만, 에픽 브랜치를 읽지 않으니 첫 머지 앞 리뷰에서 「의도다」 로 답한 질문이 같은 PR 안에서 다시 물어질 수 있다 — 사용자가 「기록 브랜치에 쓴다 (권장)」 를 골랐다(D31).
- **에픽 브랜치의 기록을 지휘자 기계 상태의 등록부(경로 + blob 해시)와 맞을 때만 읽는다.** 첫 판의 길이다(D9) — 기계 상태는 검사받는 하위 agent 도 쓸 수 있는 파일이라, 꾸민 기록을 커밋하고 그 해시를 등록부에 더할 수 있다(spec 승인 앞 qg 리뷰의 지적).
- **구현 담당자에게 처리를 리뷰 보관 폴더에 쓰게 한다.** 첫 판의 길이다(D16) — 머지 관문이 읽는 상태 파일이 같은 폴더에 있어, 그 경로를 받은 담당자가 상태 파일을 고치면 리뷰도 사용자 결정도 없이 관문이 열린다(spec 승인 앞 qg 리뷰의 지적).
- **리뷰가 못 끝나면 자동으로 한 번 다시 보낸다.** 사용자가 「멈추고 묻는다」 를 골랐다(D1).
- **관문이 기대는 것(막는 지적과 처리 · 사용자 답)을 기록 브랜치에도 남기고 관문이 그것과 견준다.** 리뷰 상태가 바뀔 때마다 커밋과 push 가 든다 — 사용자가 자리는 두고 한계 문장을 사실대로 적는 길을 골랐다(2026-11-25 리뷰 1라운드).
- **이름으로 청한 리뷰가 머지 앞 첫 리뷰를 대신한다.** 그 리뷰 뒤에 올라온 커밋이 리뷰받지 않는다 — 사용자가 지금 동작(그 뒤에도 첫 리뷰를 한 번 보낸다)을 지키는 길을 골랐다(2026-11-25 리뷰 1라운드).
- **알린 기록 목록을 기계 상태에 두고 원장 명령으로 적고 읽는다.** 첫 판의 길이다 — 읽기 편의 하나에 새 객체 · 명령 · 테스트가 늘고 지휘자가 기록마다 지문을 견준다. 앞 리뷰의 알림 파일과 줄을 견주는 길로 줄였다 — 내줌은 §8 의 귀결(묶음 줄이라 새 기록이 더해지면 앞 기록도 다시 뜨고, 앞 보관 폴더가 없으면 접지 못한다)이다(2026-11-25 리뷰 1라운드).
- **읽지 못한 기록이 하나라도 있으면 어느 답도 넘기지 않는다.** 상관없는 에픽의 답까지 다시 묻는다.
- **좁은 재리뷰를 구현 담당자가 적어 낸 「고친 커밋」 해시로 연다.** 첫 판의 길이다 — 해시가 브랜치에 없으면(rebase · amend · 오타 · push 전) 리뷰는 「재리뷰로 이어짐」 으로 닫혔는데 「열기」 가 거절해 서고, 「반박」 만 적고 올린 커밋은 재리뷰 없이 간다. git 의 기준 커밋으로 바꿨다(2026-11-25 리뷰 2라운드).
- **team 형식에서는 리더 커밋도 재리뷰를 받는다고 한계로 적는다.** 리더가 검수 결과 파일을 쓰거나 결정 줄을 옮길 때마다 과제 브랜치 끝이 움직여, 리뷰할 구현 커밋이 없는데도 좁은 재리뷰가 열리고 리뷰 한 번과 「두 번까지」 의 한 자리를 쓴다 — 사용자가 형식마다 리더가 쓰는 기록 파일을 빼는 길을 골랐다(리뷰 3라운드).
- **처리 파일 없이 두 번 끝나면 상태만 보인다.** 1라운드의 길이다(D41) — 그 뒤 그 PR 을 다시 움직일 명령이 없어 지휘자가 상태 파일을 손으로 고치는 수밖에 없다. 있는 질문(고치지 않은 막는 지적)으로 사용자 차례를 내는 길로 바꿨다(2026-11-25 리뷰 2라운드).
