# R9 — 지휘 절차의 qg 리뷰 뒤처리 — 믿는 자리 · 다시 들어오기 · 답 넘기기 · Design

> 머지 앞 qg 리뷰 한 번의 상태를 지휘자가 쥐는 파일 하나에 모으고 스크립트가 그것을 읽고 쓴다. 무엇을 리뷰했고 무엇이 남았고 머지 준비로 가도 되는지는 그 파일이 답한다 — PR 본문은 사람이 보는 표시로만 남는다.

## Context / Why

R4 가 머지 앞 qg 리뷰와 되돌리기를 지휘 절차에 넣었고 R6 이 답 이어지기를 넣었다. 그 자리는 R4 설계의 리뷰, R4 머지 뒤 리뷰, R6 의 통합 리뷰, R6 머지 뒤 리뷰에서 매번 새 막는 지적이 나온 곳이다. 이 설계의 첫 초안(문장을 스무 군데 고치는 안)도 설계문서 점검에서 질문 열셋을 받았다(지휘 자원 `report/R9/builder-check.md`).

뿌리는 하나다. 지휘자는 머지 앞 리뷰 한 번의 상태 — 어느 범위를 보냈나 · 돌아왔나 · 돌려보낼 막는 지적 · 사용자 답 · 다시 보내도 되나 — 를 네 곳에 흩어 적고 긴 절차 문장으로 맞춰 읽는다.

| 지금 적는 자리 | 무엇을 | 구멍 |
|---|---|---|
| PR 본문 `## qg 리뷰` | 호출 줄(범위) · 막는 지적 목록 · 돌려보낸 것 · 재리뷰 횟수 · 사용자 답 | 리뷰받는 구현 쪽도 고칠 수 있다 — 범위 줄을 고치면 재리뷰가 비고, 지적 줄을 지우면 그 지적이 사라진 채 머지 준비로 간다 |
| 기계 상태의 쌓인 기록 줄 | 보낸 횟수 · 다시 보내도 되는 표지 | 표지가 「언제의 코드에 쓸 것인가」 를 모른다 — 설계를 고치는 중에 끊기면 옛 코드에 쓴다 |
| 보관 폴더 | 담당자가 옮긴 결과 파일 | 호출 줄과 잇는 고리가 없다 — 보내기 전에 끊긴 리뷰와 돌아오지 못한 리뷰를 가르지 못한다 |
| 기록 파일(에픽 브랜치) | 사용자 답 · 「보관 사본」 표지 | 구현 쪽이 커밋하는 브랜치다 — 가짜 기록이 질문을 거르고 리뷰를 「끝난 것」 으로 만든다 |

team 형식 로드맵은 PR 본문 대신 일꾼이 커밋하는 과제 브랜치의 검수 결과 파일에 같은 것을 적는다 — 같은 구멍이 더 고치기 쉬운 자리에 있다.

그 밖에 답 넘기기 스크립트의 가장자리(읽지 못한 기록 앞에서 덜 묻는다 · 알림 파일 쓰기에 실패하면 알림이 사라진다 — R6 머지 뒤 리뷰의 막는 지적)와 읽기 좋게 고칠 것 둘(머지 직전 승인 기록 다시 보이기가 답만 나열한다 · 같은 알림이 리뷰마다 되풀이된다)이 있다.

## 원문 대조

묶음(`R9.md`)이 배정받은 사용자 원문은 S1 · S19 · S20 이다. 이 에픽의 항목은 사용자 문장이 아니라 앞 에픽의 리뷰에서 왔다.

| 원문 | 이 설계에서 |
|---|---|
| S1 「새 리뷰어의 질문은 qg 판정을 바꾸지 않고, 질문과 사용자의 답은 따로 남는다」 | §6 · §7 — 따로 남긴 답을 다음 리뷰로 넘기는 길을 믿을 수 있게 한다. 판정 규칙은 건드리지 않는다 |

| S20 「본체 먼저, 입구는 옆에 맞춰」 | 그대로다 — 지휘자가 qg 를 부르는 호출 줄의 꼴은 바꾸지 않는다 |

| 설계 대화 「가자」 | 달라지는 넷과 화면이 그대로인 것 — D2 |
| 설계문서 점검 뒤 「너가 보기에는 어때」 → 지휘자 제안 → 「그래」 | 리뷰마다 상태 파일 하나와 스크립트 하나로 모은다(§1) — D3 |

## Goals

- G1. 머지 앞 리뷰 한 번의 상태가 지휘자가 쥐는 파일 하나에 있고, 지휘자는 리뷰받는 쪽이 고칠 수 있는 자리(PR 본문 · 에픽 브랜치 · 과제 브랜치)에서 그 상태를 읽지 않는다.
- G2. 머지 준비로 가도 되는지는 스크립트가 그 파일들을 보고 답한다 — 리뷰가 지적 목록을 내지 못했거나 막는 지적이 남았거나 물을 것이 남았으면 가지 않는다.
- G3. 끊겼다 다시 들어왔을 때 할 일 하나를 스크립트가 답한다 — 보내기 전 · 도는 중 · 묻는 중 · 되돌린 뒤 · 설계를 고치는 중 어디서 끊겼든.
- G4. 좁은 재리뷰의 범위와 횟수를 스크립트가 정한다 — 빈 범위의 리뷰가 생기지 않는다.
- G5. 에픽 브랜치의 기록 파일은 지휘자가 쓴 것으로 확인될 때만 읽는다.
- G6. 답 넘기기가 가르지 못할 때 더 묻는 쪽으로 가고, 알림이 사라지지 않는다.
- G7. 머지 직전 다시 보이는 승인 기록이 질문과 답을 함께 싣고, 같은 알림은 기록마다 한 번만 화면에 뜬다.

## Non-goals

- 같은 계정으로 도는 프로세스가 지휘자의 파일을 고치는 것 막기 — 이 에픽이 끊는 것은 리뷰받는 쪽이 평소 손대는 자리를 믿는 일이다.
- spec 승인 앞 · 로드맵 끝 · 머지된 에픽을 이름으로 청한 리뷰의 세는 방식 — 지금 문장 그대로 둔다. 상태 파일은 머지 앞 자리(첫 리뷰 · 좁은 재리뷰 · 구현이 끝난 뒤 이름으로 청한 리뷰)만 쓴다.
- 결과 글의 꼴과 그 글을 다시 싣는 규칙(R6) — 그대로다.
- 호출 줄의 꼴과 인자(R7 이 하나를 더한다) · 돌려주는 꼴의 판 · qg 의 스크립트와 본문(R7 · R8).
- 좁은 재리뷰에서 의도 점검을 건너뛰는 길 · 결과 파일 이름의 반복 번호 — 재분해에서 받지 않기로 했다.
- qg 가 리뷰 트리의 답 폴더에서 스스로 읽는 답 파일의 진위 — 사용자가 qg 를 직접 불러 남긴 답이 거기 있다. 한계로 적는다(§6).
- 기록 파일을 스크립트가 쓰게 하기 — 지휘자가 손으로 쓰는 지금 방식을 두고 틀의 규칙만 고친다.

## Anti-goals

- 문장을 더 얹어 막는 것 — 이 자리에서 네 번 되풀이됐다.
- 스크립트가 사람 몫을 정하는 것 — 스크립트는 「무엇을 물을 차례인가」 까지 답하고, 묻고 답을 받는 것은 지휘자와 사용자다.
- 못 가를 때 덜 리뷰하고 덜 묻는 것.
- 질문이 늘어 흐름이 서는 것 — 새 질문 창은 §3 의 하나다. §6 의 등록 확인은 질문 창이 아니라 리뷰 글의 알림 한 줄이다.
- 지난 기록 파일을 고쳐 쓰는 것.

## Constraints

- 지휘자 기계 상태는 git 밖 파일이고 그 컴퓨터에만 있다 — 다른 컴퓨터나 새 클론에는 없다. 없을 때는 더 리뷰하고 더 묻는 쪽으로 넘어져야 한다.
- 런타임 상태는 마크다운이다(레포 규칙). 상태 파일은 사람이 열어 읽을 수 있어야 한다.
- 지금 지휘 중인 로드맵에는 이 변경 전에 쓴 PR 본문의 줄 · 쌓인 기록 줄 · 기록 파일이 있다 — 옛 흔적을 읽지 못해 조용히 덜 리뷰하는 일이 없어야 한다(§9).
- 스크립트는 하니스의 agent 목록을 볼 수 없다 — 담당자가 살아 있는지는 지휘자가 넘겨준다.
- R7 이 같은 문서의 호출 줄 · 다시 부르기 · 겹침 문장을 고친다. team 형식 절이 있는 지휘 절차 문서는 옆 로드맵(지휘 절차 쪽)도 고친다 — 뒤에 머지되는 쪽이 기본 브랜치를 합치고, 옆 로드맵에는 이 에픽이 team 형식의 「세는 자리」 를 옮긴다는 것을 알린다.
- 새 훅 · 새 진입 skill · 새 kill switch 가 없다.

## Approaches

1. **리뷰마다 상태 파일 하나와 그것을 읽고 쓰는 스크립트(고름).** 범위 · 단계 · 지적 목록 · 사용자 답을 지휘자가 쥐는 파일에 모으고, 재리뷰 범위 · 머지 관문 · 다시 들어왔을 때 할 일을 스크립트가 답한다. 내줌: 세 에픽 가운데 가장 큰 일이 되고 team 형식의 세는 자리 문장도 바뀐다.
2. **지금 구조에 문장을 더 얹는다.** 얻음: 작다. 내줌: 흩어진 네 자리를 문장으로 맞추는 방식이 그대로라 규칙끼리 부딪히고(점검이 넷을 짚었다) team 형식에 구멍이 남는다.
3. **가장 심각한 셋만 고치고 나머지는 옆 로드맵의 지휘 절차 개편에 넘긴다.** 얻음: 가장 작다. 내줌: 받는 쪽이 정해지지 않은 미룸이 또 생긴다.

사용자가 1 을 골랐다(D3).

## 설계

### §1 리뷰 상태 파일과 스크립트

**상태 파일.** 머지 앞 자리의 리뷰를 보낼 때마다 그 리뷰의 보관 폴더에 상태 파일 하나를 둔다. 보관 폴더는 지금처럼 지휘 자원 아래(git 밖)다. 파일은 마크다운이고 아래를 담는다.

| 칸 | 내용 |
|---|---|
| 자리 · 대상 | 자리 글자(첫 리뷰 · 좁은 재리뷰 · 이름으로 청함)와 PR(옛 형식은 PR 번호, team 형식은 과제와 계획 번호) |
| 범위 | 호출 줄에 쓴 시작 · 끝 커밋 |
| 단계 | 열림 → 보내는 중 → 보냄 → 돌아옴 → 닫힘. 닫힘에는 사유가 붙는다(아래) |
| 담당자 | 보낸 담당자 이름과 보낸 때 |
| 돌아온 결과 | 지적 목록을 얻었나 · 본 범위가 맞나 · 판정 줄 · 의도 점검 결과 줄 |
| 막는 지적 | 막는 지적과 새로 깨진 테스트의 원문, 항목마다 처리 — 처리 없음 · 고친 커밋 <해시> · 반박 · 손대지 않음 · 다시 돌려보냄 · 사용자가 남김. 사용자가 고른 제안과 되올린 낮춘 지적도 그 표시와 함께 이 칸에 든다 |
| 거른 질문 | 결과가 실은 「이미 답해 거른 질문」 · 「이미 「잘못 골랐다」 답이 있어 거른 질문」 목록 |
| 물을 것 | 아직 답을 받지 못한 질문 — 종류(의도 점검 · 지적 목록을 얻지 못함 · 고치지 않은 막는 지적 · 「두 번까지」 · 담당자가 옮긴 질문)와 질문 글 |
| 사용자 답 | 이 리뷰에서 받은 답 전부 — 의도 점검 답은 질문 정체와 답, 그 답을 적은 기록 파일의 경로(쓰기 전이면 빔) |
| 멈출 조건 | 첫 좁은 재리뷰를 보내기 전에 적는 조건(두 번 뒤에도 남는 지적을 어디에 적고 넘길지) |

닫힘의 사유는 닫힌 꼴이다 — 막는 지적 없음 · 재리뷰로 이어짐 · 사용자가 남김 · 리뷰 없이 감 · 다시 보냄(지적 목록을 얻지 못해) · 「잘못 골랐다」 — 설계 대화로 · 「잘못 골랐다」 — 재분해 신호 · 에픽을 멈춤.

**스크립트.** 스크립트 하나가 상태 파일을 만들고 고치고 읽는다. 지휘자는 상태 파일을 손으로 고치지 않는다. 스크립트가 하는 일은 일곱이다.

| 일 | 무엇을 |
|---|---|
| 열기 | 그 PR 의 상태 파일들을 보고 지금 그 자리의 리뷰를 보내도 되는지 정한다. 되면 보관 폴더와 상태 파일을 만들고(자원 줄 포함) 호출 줄에 쓸 범위와 보관 폴더 경로를 낸다. 좁은 재리뷰의 범위는 스크립트가 정한다(§2). 안 되면 까닭과 지금 할 일을 낸다 |
| 보냄 | 두 번 부른다 — 보내기 직전에 「보내는 중」 을 적고, 보낸 뒤에 담당자 이름을 적는다 |
| 돌아옴 | 보관 폴더의 파일을 읽어 결과를 가린다(아래) — 막는 지적의 원문과 거른 질문 목록을 상태 파일로 옮기고, 닫을 수 있으면 닫고, 다음 할 일을 낸다 |
| 답 적기 | 사용자 답 · 구현 담당자의 처리(지적마다) · 사용자가 고른 제안과 되올린 낮춘 지적 · 담당자가 옮긴 질문 · 멈출 조건 · 「다시 구현됨」(§4)을 적는다. 적은 뒤 닫을 수 있으면 닫는다 |
| 다음 | 그 PR 에서 지금 할 일 하나를 낸다(§4) |
| 관문 | 그 PR 이 머지 준비로 가도 되는지와 까닭을 낸다(§3) |
| 글 짓기 | 셋을 낸다 — PR 본문 `## qg 리뷰` 절의 글 · 승인 기록 다시 보이기의 qg 몫 · 구현 담당자에게 돌려보낼 지적 목록(§5) |

상태를 옮기는 것은 「보냄」 · 「돌아옴」 · 「답 적기」 셋뿐이고, 닫는 것은 「돌아옴」 과 「답 적기」 가 조건이 채워졌을 때 스스로 한다 — 닫기만 하는 명령은 없다.

**돌아온 결과를 가리는 법.** 스크립트는 보관 폴더의 파일만 본다 — 대화에 있는 담당자 보고를 근거로 쓰지 않는다.

| 보관 폴더 | 결과 |
|---|---|
| 판정 절이 있는 결과 파일이 있고, 그 결과가 말한 본 범위가 상태 파일의 범위와 맞다 | 지적 목록을 얻음 — 막는 지적은 합쳐지기 전 지적 목록 파일에서(없으면 결과 파일의 고칠 목록에서) 옮긴다. 새로 깨진 테스트는 결과 파일의 차등 회귀에서 옮긴다 |
| 결과 파일이 없거나 판정 절이 없다 | 지적 목록을 얻지 못함 — 사유 「qg 가 끝까지 돌지 못했다 — 보관한 결과에 판정이 없다」 |
| 본 범위가 상태 파일의 범위와 다르다 | 지적 목록을 얻지 못함 — 사유 「결과가 보낸 범위의 것이 아니다」. 지금은 이 경우를 의도 점검만 셀 수 없는 것으로 보는데, 다른 범위의 지적은 이 PR 의 리뷰가 아니다 |
| 결과 파일이 「리뷰할 것 없음」 으로 끝났다(바뀐 코드가 없거나 한 문장 변경) | 리뷰할 것 없음 — 지적 목록을 얻은 것과 같이 다루고 막는 지적 0개로 닫는다 |

- 본 범위는 결과 파일의 범위 절(시작 · 끝)에서 읽는다 — 의도 점검의 돌려주는 꼴이 그 칸을 비워 와도 가를 수 있다.
- 의도 점검의 돌려주는 꼴을 읽지 못했거나 판이 다른 경우는 지금처럼 「의도 점검은 셀 수 없음」 이다 — 지적 목록을 얻었으면 관문을 막지 않는다.
- 돌아온 리뷰에 막는 지적도 물을 것도 없으면 「돌아옴」 이 바로 「막는 지적 없음」 으로 닫는다.

**보관 폴더에 남아야 하는 것.** 스크립트가 대화 없이 다시 이을 수 있게, 지금 담당자의 마지막 보고에만 있는 것 가운데 상태를 바꾸는 둘을 파일로 남긴다.

- 구현 담당자가 지적마다 적는 처리 — 되돌리기에서 보내는 글이 「지적마다의 처리를 그 리뷰의 보관 폴더에 파일로도 쓴다」 를 싣는다(team 형식은 지금처럼 다음 시도의 구현 결과 파일에 있다). 「답 적기」 는 그 파일에서 읽는다.
- qg 담당자가 미리 받은 답 밖의 질문에서 멈춰 돌려보낸 요약과 질문 원문 — 지휘자가 받는 즉시 「답 적기」 로 상태 파일의 물을 것에 적는다.

빠진 채 돌았다는 알림 · 미리 받은 답을 쓴 자리처럼 화면에만 쓰이는 줄은 지금처럼 보고에만 있다 — 다시 짓지 않는다(R6 의 규칙).

**지휘 절차 문서에 남는 것.** 머지 앞 자리의 「언제 보내나 · 범위 · 횟수 · 다시 들어왔을 때 · 머지 준비로 가는 조건」 은 문장에서 빠지고 「스크립트를 부르고 그 답대로 한다」 가 된다. 담당자에게 보내는 글 · 결과 글의 꼴 · 묻는 틀 · 선택지의 글자는 문서에 남는다. 기계 상태의 작업 줄 · 기다리는 질문 줄 · 사람 차례 표시는 지금처럼 적는다 — 상태 화면이 읽는 표시이고, 지휘자와 스크립트는 그 줄로 판단하지 않는다.

### §2 좁은 재리뷰의 범위와 횟수

- **여는 조건.** 브랜치 끝이 움직였다는 것만으로는 열지 않는다 — 지휘자 자신의 커밋(기록 파일 · 지휘 기록)도 끝을 옮긴다. 상태 파일의 막는 지적 가운데 처리가 「고친 커밋 <해시>」 인 것이 하나라도 있고 그 커밋이 범위에 들 때만 연다.
- **시작.** 그 PR 의 상태 파일 가운데 결과가 「지적 목록을 얻음」 인 마지막 리뷰의 범위 끝이다. 열기만 했거나 돌아오지 못했거나 지적 목록을 얻지 못한 리뷰의 끝은 시작이 되지 못한다.
- **끝.** 지금의 브랜치 끝이다. 그 사이 지휘자가 커밋한 기록이 범위에 들어도 빼지 않는다(지금 그대로).
- **merge 커밋.** 범위에 merge 커밋이 끼어 있으면 지금처럼 그 PR 을 처음부터 다시 보고 재리뷰 한 번으로 센다.
- **두 번까지.** 좁은 재리뷰는 PR 하나에 두 번까지다 — 지적 목록을 얻은 재리뷰만 센다. 지적 목록을 얻지 못해 다시 보낸 것은 세지 않는다. 둘째 재리뷰가 막는 지적을 안고 돌아오면 「돌아옴」 이 바로 「두 번까지」 의 질문 차례를 낸다 — 구현 길로 돌려보내기 전이다(지금과 같은 때다). 사용자가 「한 번 더 돌려보낸다」 를 고르면 상태 파일에 그 답이 적히고 그 PR 의 상한이 하나 는다.
- **이름으로 청한 리뷰.** 구현이 끝난 머지 전 에픽을 이름으로 청한 리뷰도 상태 파일을 쓴다 — 그 리뷰가 막는 지적을 내 되돌린 뒤의 좁은 재리뷰가 그 끝에서 시작한다.

### §3 머지 관문

머지 준비(스위트 대조부터)로 가도 되는지는 스크립트의 관문이 답한다. 관문은 그 PR 의 상태 파일 전부를 본다(「잘못 골랐다」 로 설계 대화에 돌아갔다 왔으면 그 뒤에 연 첫 리뷰부터). 여는 조건은 아래를 모두 채우는 것이다.

- 마지막 리뷰가 지적 목록을 얻었다(또는 리뷰할 것이 없었다) — 아니면 사용자가 「리뷰 없이 머지 준비로 간다」 를 골랐다.
- 어느 리뷰의 막는 지적도 열려 있지 않다. 막는 지적이 닫히는 길은 둘이다 — 처리가 「고친 커밋」 이고 그 커밋을 범위에 품은 뒤 리뷰가 지적 목록을 얻었다 · 사용자가 남기기로 했다. 같은 문제가 뒤 리뷰에서 다시 나오면 그것은 뒤 리뷰의 새 막는 지적으로 세어진다 — 리뷰 사이에서 지적의 정체를 맞추지 않는다.
- 물을 것이 남아 있지 않다.
- 의도 점검의 「잘못 골랐다」 가 없고, 「이미 「잘못 골랐다」 답이 있어 거른 질문」 목록이 비어 있다.

**리뷰가 지적 목록을 얻지 못했을 때.** 관문이 닫히고 스크립트가 이 질문 차례라고 낸다. 지휘자는 질문 하나로 묻는다 — 질문 문장 앞머리에 에픽 이름과 사유를 두고, 선택지는 아래 셋을 이 차례로 쓴다.

- 「다시 보낸다 (권장)」: 얻음: 리뷰를 받고 머지한다 · 내줌: 리뷰 한 번이 더 든다
- 「리뷰 없이 머지 준비로 간다」: 얻음: 지금 머지 준비로 간다 · 내줌: 이 PR 의 코드가 qg 리뷰 없이 머지된다
- 「이 에픽을 멈춘다」: 얻음: 리뷰 없이 머지되는 일이 없다 · 내줌: 이 에픽이 서고 다시 불러야 이어진다

「다시 보낸다」 는 그 리뷰를 「다시 보냄」 으로 닫고 같은 자리 · 같은 범위의 새 리뷰를 연다 — 「두 번까지」 에 세지 않는다. 「리뷰 없이 머지 준비로 간다」 는 상태 파일에 적히고 표시(§5)와 승인 기록 다시 보이기에 「qg 리뷰 없이 감 — 사용자 결정(<사유>)」 으로 실린다.

**qg 가 깔려 있지 않을 때.** 지금처럼 「품질 게이트 없이 간다」 를 알리고 건너뛴다 — 상태 파일을 만들지 않고 관문은 그 PR 에 리뷰가 없다는 것과 건너뛴 까닭을 낸다.

**있는 질문 둘.** 고치지 않은 막는 지적의 질문과 「두 번까지」 의 질문은 글자와 선택지가 지금 그대로다. 달라지는 것은 그 질문이 떠야 하는 때를 스크립트가 내고 답을 상태 파일이 쥔다는 것이다. 「다시 돌려보낸다」 를 고른 지적은 처리가 「다시 돌려보냄」 으로 바뀌어 다음 할 일이 돌려보내기가 되고, 그 뒤의 좁은 재리뷰는 지금처럼 「두 번까지」 에 센다.

### §4 다시 들어왔을 때

지휘자는 압축이나 새 세션 뒤, 머지 전 확인을 시작할 때, 그리고 담당자가 돌아올 때마다 스크립트의 「다음」 을 부른다. 스크립트는 그 PR 의 상태 파일들과 지휘자가 넘긴 살아 있는 담당자 이름(하니스 목록에 있고 아직 끝나지 않은 것)을 보고 할 일 하나를 낸다. 아래 표를 위에서부터 보고 처음 맞는 줄을 쓴다.

| 마지막 리뷰의 상태 | 내는 할 일 |
|---|---|
| 상태 파일이 없다 | 첫 리뷰를 연다(이 변경 전의 흔적이 있으면 §9) |
| 열림 | 같은 상태 파일 · 같은 범위로 보낸다 — 새로 열지 않는다 |
| 보내는 중 · 담당자 이름 없음 | 지휘자가 하니스 목록에서 그 리뷰의 설명과 맞는 살아 있는 담당자를 찾아 이름을 적고 기다린다. 없고 보관 폴더에 담당자가 옮긴 파일이 있으면 「돌아옴」 을 부르고, 그것도 없으면 다시 보낸다 |
| 보냄 · 물을 것에 담당자가 옮긴 질문이 있다 | 그 질문을 띄우고 답을 같은 담당자에게 이어 부른다 — 이어 부를 수 없으면(담당자의 자리가 지워졌다) 「돌아옴」 을 부른다 |
| 보냄 · 담당자가 살아 있다 | 기다린다 |
| 보냄 · 담당자가 없다 | 「돌아옴」 을 부른다 — 보관 폴더의 파일로 결과를 가린다 |
| 돌아옴 · 지적 목록을 얻지 못함 · 답 없음 | §3 의 질문을 띄운다 |
| 돌아옴 · 물을 것이 남음 | 그 질문을 띄운다(의도 점검 질문 · 「두 번까지」 · 고치지 않은 막는 지적 — 이 차례로) |
| 돌아옴 · 의도 점검 답을 적었는데 기록 파일 경로가 비어 있다 | 기록 파일을 쓴다 — 다시 묻지 않는다 |
| 돌아옴 · 막는 지적에 처리 없음 · 다시 돌려보냄이 있다 | 구현 길로 돌려보낸다 — 돌려보낼 목록은 스크립트가 지은 것이다 |
| 돌아옴 · 고친 커밋이 범위에 있다 | 좁은 재리뷰를 연다(§2) |
| 닫힘 · 「잘못 골랐다」 — 설계 대화로 | 기다린다. 고친 설계가 승인되고 구현 담당자가 돌아온 것을 지휘자가 「다시 구현됨」 으로 적은 뒤에만 첫 리뷰를 새로 연다(PR 전체, 「두 번까지」 도 새로 센다) — 브랜치 끝이 움직였다는 것만으로는 열지 않는다 |
| 닫힘 · 「잘못 골랐다」 — 재분해 신호 | 멈춰 있다 — 재분해 신호를 사용자에게 보인다 |
| 닫힘 · 에픽을 멈춤 | 멈춰 있다 — 사용자가 이어 가자고 하면 멈추게 한 그 질문을 다시 띄운다 |
| 닫힘 · 관문 통과 | 머지 준비로 간다 |

- 지금의 「보고 없이 다시 들어왔을 때」 와 「돌아오지 못한 리뷰」 갈래는 머지 앞 자리에서 이 표로 대신한다 — 결과 글을 다시 싣는 규칙(R6)은 그대로이고, 그 글을 싣기 전에 무엇을 할 차례인지를 이 표가 정한다.
- 답을 받으면 먼저 「답 적기」 로 상태 파일에 적고, 그 뒤에 기록 파일을 쓰고 커밋하고 등록한다(§6) — 그 사이에 끊겨도 다시 묻지 않는다.
- 「잘못 골랐다」 로 설계 대화에 돌아갈 때 적던 다시 보내기 표지는 머지 앞 자리에서 상태 파일의 닫힘 사유와 「다시 구현됨」 이 대신한다. spec 승인 앞의 표지는 그대로 두되 그때의 설계문서 커밋을 함께 적고, 설계문서가 그 커밋 그대로인 동안에는 그 허용분으로 보내지 않는다 — 같은 구멍이 그쪽에도 있다.

### §5 표시 — PR 본문 · 승인 기록 다시 보이기

- **PR 본문.** `## qg 리뷰` 절은 스크립트가 지은 글을 지휘자가 그대로 올린다 — 호출 줄 · 판정 줄 · 막는 지적과 처리 · 멈출 조건 · 사용자 답 · 남긴 지적. 지휘자는 그 절에서 아무것도 읽지 않는다. 사용자가 남기기로 한 막는 지적을 `## 통합 리뷰 인계` 에 적는 것은 지금 그대로다.
- **돌려보낼 지적 목록.** 구현 담당자에게 보내는 글에 싣는 목록도 스크립트가 상태 파일에서 짓는다 — 처리 없음 · 다시 돌려보냄인 막는 지적과 사용자가 고른 제안 · 되올린 낮춘 지적의 원문이다.
- **승인 기록 다시 보이기.** 머지 명령 줄을 내기 전에 보이는 승인 기록의 qg 몫은 스크립트가 상태 파일에서 짓는다 — 기록 파일을 읽지 않는다.
  - 질문마다 질문 글 한 줄 · 답 · 직접 쓴 답 원문(있으면).
  - 그 PR 의 첫 리뷰 · 좁은 재리뷰에 더해 구현이 끝난 뒤 이름으로 청한 리뷰의 답도 싣는다.
  - 앞 리뷰에서 답해 이번에 묻지 않은 질문은 「앞 리뷰에서 답함」 으로 싣는다 — 상태 파일의 거른 질문 목록에서.
  - 「qg 리뷰 없이 감」 · 사용자가 남긴 막는 지적은 맨 위에 싣는다.
- **펜스.** team 형식의 검수 결과 파일에 싣는 표시 글은 스크립트가 바깥 펜스까지 지어 낸다 — 글 안의 가장 긴 백틱 줄보다 긴 펜스를 쓴다. 지적 원문에 펜스가 들어 있어도 그 파일의 펜스가 일찍 닫히거나 열린 채 남지 않는다.

### §6 답으로 인정하는 기록

기록 파일을 읽는 자리는 셋이다 — 기본 브랜치 · 기록 브랜치 · 열린 에픽 브랜치(로컬). 앞의 둘은 지금처럼 읽는다. 에픽 브랜치의 기록 파일은 지휘자가 쓴 것으로 확인될 때만 읽는다.

- **등록부.** 지휘자는 에픽 브랜치에 기록 파일을 커밋할 때마다 그 파일의 경로와 내용 지문(git 의 blob 해시)을 기계 상태의 등록부에 적는다. 그 파일을 나중에 고쳐 다시 커밋하면 다시 적는다.
- **읽는 쪽 둘.** 에픽 브랜치의 기록 파일을 읽는 길은 둘이 남는다 — 답 넘기기 스크립트와 spec 승인 앞 자리의 「끝난 리뷰」 판정(기록 파일의 「보관 사본」 표지). 둘 다 경로와 지문이 등록부와 맞는 파일만 읽는다. 머지 앞 자리의 「끝난 리뷰」 와 승인 기록 다시 보이기는 상태 파일이 정하므로 기록 파일을 보지 않는다.
- **맞지 않는 파일.** 등록부에 없는 에픽 브랜치 기록은 읽지 않고 리뷰를 그대로 보낸다 — 그 기록의 답은 넘어가지 않아 그 질문이 다시 물어질 수 있다. 지휘자는 그 목록(경로 · 날짜 · 질문 글 · 답)을 리뷰 글의 알림 자리에 한 번 보이고 「하신 답이 맞으면 말해 달라 — 등록한다」 를 붙인다. 질문 창을 띄우지 않는다. 사용자가 맞다고 하면 등록한다 — 어느 컴퓨터에서든 같은 길이다.
- **차례.** 등록부 확인이 먼저다 — 등록되지 않은 파일은 §7 의 「읽지 못한 기록」 규칙에 세지 않는다. 구현 쪽이 깨진 파일 하나를 넣어 다른 답까지 넘어가지 않게 만들 수 없다.

**한계.** 가짜 기록이 에픽 PR 의 diff 에 섞여 기본 브랜치로 머지되는 것은 막지 않는다 — 그 diff 는 통합 리뷰와 사용자가 본다. qg 가 리뷰 트리의 답 폴더에서 스스로 읽는 답 파일도 이 확인 밖이다(Non-goals). README 에 적는다.


### §7 답 넘기기 스크립트

- **읽지 못한 기록.** (등록부 확인을 지난) 기록 파일 하나를 읽지 못하면 그 파일과 같은 대상(파일 이름의 에픽 번호 또는 로드맵)의 답은 넘기지 않는다 — 읽지 못한 파일이 그 답을 뒤집었을 수 있다. 파일 이름조차 틀 밖이면 어느 답도 넘기지 않는다.
- **앞 답을 빼는 조건.** 뒤 기록의 「전에 한 답」 줄은 그 뒤 기록의 새 답이 「의도다」 · 「잘못 골랐다」 일 때만 앞 답을 뺀다. 「지금은 모르겠다」 · 「답하지 않음」 · 「묻지 않음」 은 앞 답을 빼지 않는다.
- **여러 줄 답.** 기록 틀에서 직접 쓴 답 원문이 여러 줄이면 둘째 줄부터 들여 쓴다(관찰 줄과 같은 꼴). 스크립트는 들여 쓴 줄을 그 칸의 이어지는 글로 읽는다 — 줄머리가 `## ` 인 답 줄이 질문 절을 끊지 않는다.
- **같은 이름의 기록 파일.** 기록 파일 이름 끝의 번호(-2, -3 …)는 그 브랜치만이 아니라 읽는 자리 셋을 모두 보고 붙인다.
- **알림이 사라지지 않게.** 알림 줄은 파일에 쓰기 전에 화면(표준 오류)에 먼저 낸다. 답 파일은 썼는데 알림 파일만 쓰지 못한 경우를 따로 가른다 — 답 파일을 그대로 쓰되 다른 종료 코드와 「알림 파일을 쓰지 못했다 — 알림은 위 줄뿐이다」 한 줄로 알린다. 답 파일을 쓰지 못한 경우는 지금의 종료 코드 그대로다.
- **종료 코드 표.** 지휘 절차의 종료 코드 표에 그 행과 「그 밖」 행(스크립트가 죽은 경우 포함 — 답 없이 보내고 알린다)을 더하고, 스크립트가 기대는 파이썬 패키지를 의존 표에 적는다.
- **R6 머지 뒤 리뷰의 제안 열다섯**(지휘 자원 `report/qg-R6-merged-pr331-2026-11-24/handler-report.md` 의 제안 목록 22–36번). 위에 넣은 것 말고는 계획이 하나씩 받거나 이유를 적어 남긴다 — 남긴 것은 PR 본문에 적는다.

### §8 알림 · 지휘 기록 · 락

- **같은 알림은 기록마다 한 번.** 답 넘기기 스크립트는 지금처럼 리뷰마다 모든 알림(읽지 못한 기록 · 틀 밖의 답 · 등록부와 맞지 않는 기록)을 표준 오류와 알림 파일에 낸다 — 스크립트는 접지 않는다. 접는 곳은 지휘자의 리뷰 글이다. 리뷰 글에는 그 기록 파일(경로와 지문)을 처음 알릴 때만 싣고 알린 기록을 기계 상태에 적는다. 그 뒤 리뷰의 리뷰 글에는 「전에 알린 기록 <n>개 — 자세히는 알림 파일」 한 줄만 싣는다. 알림 파일 쓰기가 실패한 실행(§7)은 접지 않고 그 실행의 표준 오류 줄을 그대로 싣는다.
- **여러 줄 지적을 지휘 기록에.** 보인 지적의 원문을 설계문서의 지휘 기록에 올릴 때 여러 줄이면 첫 줄만 싣고 끝에 「…(전문: <보관 폴더 이름>의 지적 목록)」 을 붙인다. 접은 글을 원문이라고 부르지 않는다.
- **락.**
  - 머지 관문 — 지휘 절차 문서의 머지 전 확인이 스위트 대조 앞에서 스크립트의 관문을 부른다는 문장(옛 형식과 team 형식 둘 다)과, 다시 들어오는 자리(지휘 순환의 맞추기 걸음 · 손으로 따르는 절차)가 「다음」 을 부른다는 문장. 관문의 조건 자체는 스크립트의 테스트가 잰다.
  - team 형식 문장 — 「두 번까지」 가 옛 형식과 같다는 것 · 기본 브랜치 합치기를 하지 않는다는 것 · 자리 글자의 꼴.
  - 두 플러그인이 함께 쓰는 낱말 — 리뷰어가 「전에 물은 것」 에 붙이는 까닭 낱말 둘이 qg 스크립트와 지휘 절차 문서에서 같다.
  - 스크립트와 지휘자가 읽는 qg 파일의 꼴 — 결과 파일의 절 이름(판정 · 범위 · 고칠 목록 · 차등 회귀 · 거른 질문 목록 둘)과 합쳐지기 전 지적 목록의 키. 그 키를 qg 의 세션 파일 꼴 문서에 적고, 읽는 쪽이 쓰는 이름이 그 문서에 있는지 잰다.
- **지금 있는 락.** 지휘 절차 문서의 문장을 핀한 지금 테스트 가운데 PR 본문에서 읽기 · 호출 줄 적기 · 다시 보내기 표지를 잠근 것은 지우거나 새 문장으로 다시 쓴다 — 계획이 그 목록을 짓고, 지운 락마다 같은 뜻을 스크립트의 테스트가 잰다는 것을 적는다.


### §9 이 변경 전에 시작한 PR 과 team 형식

**이 변경 전에 시작한 PR · 다른 컴퓨터.** 그 PR 의 상태 파일이 하나도 없는데 머지 앞 리뷰의 옛 흔적(PR 본문의 `## qg 리뷰` 절 · 그 자리 글자의 보관 폴더 · 쌓인 기록 줄)이 있으면, 스크립트는 옛 흔적에서 범위나 횟수를 읽지 않는다 — 「옛 흔적이 있다 — PR 전체를 처음부터 리뷰한다」 를 내고 첫 리뷰를 연다. 옛 PR 본문에 적힌 막는 지적과 사용자 답은 지휘자가 사용자에게 한 번 보인다(새 리뷰가 같은 지적을 다시 낼 수 있다).

**team 형식.** 검수 걸음의 머지 앞 리뷰도 같은 스크립트와 상태 파일을 쓴다 — 대상이 PR 번호 대신 과제와 계획 번호다.

- 지금 검수 결과 파일의 펜스 안에 「적고 거기서 세던」 것(범위 · 지난 리뷰의 끝 · 돌려보낼 막는 지적 · 재리뷰 횟수 · 멈출 조건)은 상태 파일이 쥔다. 펜스는 스크립트가 지은 표시 글을 싣는 자리로 남는다 — 지휘자는 거기서 읽지 않는다.
- 돌려보내는 길(반려와 시작 묶음의 다음 시도) · 지적마다의 처리를 다음 시도의 구현 결과 파일에 적게 하는 것 · PR 이 열리면 펜스 내용을 본문으로 옮기는 것은 그대로다. 구현 결과 파일의 처리는 지휘자가 읽어 스크립트의 「답 적기」 로 옮긴다.
- 「qg 리뷰 없이 감」 은 PR 이 아직 없으면 펜스에 싣고, PR 이 열릴 때 본문으로 옮겨진다.

## Acceptance Criteria

- AC1. 머지 앞 자리의 리뷰마다 보관 폴더에 상태 파일이 하나 있고 §1 의 칸 열을 담는다. 지휘 절차 문서에 PR 본문 `## qg 리뷰` 나 team 형식의 펜스에서 범위 · 횟수 · 막는 지적 · 답을 읽으라는 문장이 없다. 상태를 옮기는 명령은 셋(보냄 · 돌아옴 · 답 적기)이고 닫힘 사유는 §1 의 여덟 가운데 하나다.
- AC2. 스크립트의 「돌아옴」 은 §1 의 표대로 가른다 — 판정이 있고 본 범위가 맞으면 지적 목록을 얻음, 결과 파일이 없거나 판정이 없거나 본 범위가 다르면 얻지 못함(사유 문장이 표와 같다), 리뷰할 것이 없었으면 막는 지적 0개로 닫힘. 의도 점검의 돌려주는 꼴이 범위 칸을 비워 와도 결과 파일의 범위 절로 가른다.
- AC3. 막는 지적과 새로 깨진 테스트의 원문 · 거른 질문 목록 둘이 보관 폴더의 파일에서 상태 파일로 옮겨진다 — PR 본문이나 대화의 담당자 보고가 없어도 돌려보낼 목록이 같다. 구현 담당자의 지적마다 처리는 보관 폴더의 처리 파일에서 읽히고, 사용자가 고른 제안과 되올린 낮춘 지적은 막는 지적 칸에 들어 관문이 센다.
- AC4. 좁은 재리뷰는 처리가 「고친 커밋」 인 막는 지적이 있고 그 커밋이 범위에 들 때만 열린다 — 지휘자의 커밋만으로 브랜치 끝이 움직인 경우에는 열리지 않는다. 시작은 지적 목록을 얻은 마지막 리뷰의 끝이다. merge 커밋이 끼면 PR 전체다. 둘째 재리뷰가 막는 지적을 안고 돌아오면 「두 번까지」 의 질문 차례가 바로 나오고, 「한 번 더」 답이 있어야 셋째가 열린다. 지적 목록을 얻지 못해 다시 보낸 리뷰는 그 수에 들지 않는다.
- AC5. 구현이 끝난 뒤 이름으로 청한 리뷰도 상태 파일을 쓰고, 그 뒤 좁은 재리뷰가 그 끝에서 시작한다.
- AC6. 관문은 그 PR 의 상태 파일 전부를 보고 §3 의 네 조건을 모두 채울 때만 연다 — 지적 목록을 얻지 못한 마지막 리뷰 · 어느 리뷰에든 열려 있는 막는 지적(고친 커밋을 본 뒤 리뷰가 없거나, 반박 · 손대지 않음인데 사용자가 남기지 않았다) · 남은 물을 것 · 「잘못 골랐다」 · 「이미 「잘못 골랐다」 답이 있어 거른 질문」 가운데 하나라도 있으면 닫히고 까닭을 낸다.
- AC7. 리뷰가 지적 목록을 얻지 못하면 §3 의 질문 차례가 나오고, 지휘 절차 문서의 선택지 셋이 글자와 차례까지 §3 과 같다. 「다시 보낸다」 는 같은 범위의 새 리뷰를 열고, 「리뷰 없이 머지 준비로 간다」 는 관문을 열며 표시와 승인 기록 다시 보이기에 실린다. 의도 점검만 셀 수 없는 리뷰에는 이 질문이 나오지 않는다.
- AC8. 「다음」 은 §4 의 표를 위에서부터 보고 줄마다 그 할 일로 답한다 — 열림은 같은 상태 파일로 다시 보내기이고 새 상태 파일이 생기지 않는다. 「보내는 중」 에서 끊긴 리뷰는 살아 있는 담당자가 있으면 다시 보내지지 않는다. 묻다가 끊긴 질문은 다시 나오고, 답은 적었는데 기록 파일을 쓰기 전에 끊긴 경우는 다시 묻지 않고 기록 파일 쓰기가 나온다. 담당자가 옮긴 질문이 있는 리뷰는 「지적 목록을 얻지 못함」 으로 떨어지지 않는다.
- AC9. 「잘못 골랐다」 로 설계 대화에 돌아간 PR 은 「다시 구현됨」 이 적히기 전에는 새 리뷰가 열리지 않는다 — 고친 설계문서 커밋으로 브랜치 끝이 움직여도 같다. spec 승인 앞의 다시 보내기 표지는 설계문서 커밋을 싣고 그 커밋 그대로인 동안 쓰이지 않는다. 「에픽을 멈춤」 · 「재분해 신호」 로 닫힌 PR 에서 「다음」 은 멈춰 있다고 답한다.
- AC10. PR 본문 `## qg 리뷰` 절의 글 · 승인 기록 다시 보이기의 qg 몫 · 구현 담당자에게 돌려보낼 지적 목록을 스크립트가 상태 파일에서 짓는다 — 둘째는 질문 글 · 답 · 답 원문 · 이름으로 청한 리뷰의 답 · 「앞 리뷰에서 답함」 · 「qg 리뷰 없이 감」 을 싣는다. team 형식의 펜스에 싣는 글은 지적 원문에 백틱 펜스가 들어 있어도 바깥 펜스가 한 번 열리고 한 번 닫힌다.
- AC11. 에픽 브랜치의 기록 파일을 읽는 두 길(답 넘기기 · spec 자리의 「끝난 리뷰」 판정)은 경로와 지문이 등록부와 맞는 파일만 읽는다. 기본 브랜치 · 기록 브랜치의 기록은 지금처럼 읽는다. 등록부에 없는 기록은 리뷰 글의 알림 자리에 목록으로 한 번 보이고, 그 리뷰는 그 답 없이 그대로 보내진다 — 질문 창이 뜨지 않는다.
- AC12. 지휘자가 에픽 브랜치에 기록 파일을 커밋하는 자리마다 등록부에 적는 줄이 있다. 등록되지 않은 에픽 브랜치 파일은 「읽지 못한 기록」 규칙에 세어지지 않는다.
- AC13. 읽지 못한 기록 파일이 있으면 같은 대상의 답이 넘어가지 않는다. 파일 이름이 틀 밖이면 어느 답도 넘어가지 않는다.
- AC14. 뒤 기록의 새 답이 「지금은 모르겠다」 · 「답하지 않음」 · 「묻지 않음」 이면 앞 답이 그대로 넘어간다. 「의도다」 · 「잘못 골랐다」 면 앞 답이 빠진다.
- AC15. 여러 줄 답(줄머리 `## ` 포함)이 든 기록 파일이 읽히고 그 답이 넘어간다. 기록 틀이 들여 쓰는 규칙을 적는다. 기록 파일 이름의 번호 규칙이 읽는 자리 셋을 모두 본다.
- AC16. 알림 줄은 알림 파일 쓰기가 실패해도 화면에 남고, 그 경우가 답 파일을 쓰지 못한 경우와 다른 종료 코드 · 다른 줄로 갈린다. 지휘 절차의 종료 코드 표가 그 행과 「그 밖」 행을 갖는다.
- AC17. 같은 기록의 알림은 지휘자의 리뷰 글에 한 번만 실리고 그 뒤로는 한 줄 요약만 실린다 — 접는 규칙은 지휘 절차 문서에 있고 답 넘기기 스크립트는 매번 모든 알림을 표준 오류와 알림 파일에 낸다. 알림 파일 쓰기가 실패한 실행은 접지 않는다.
- AC18. 여러 줄 지적을 지휘 기록에 올리는 문장이 첫 줄과 전문 자리를 싣게 적혀 있고, 그 꼴의 줄을 기록 명령이 받는다.
- AC19. 상태 파일이 없고 옛 흔적만 있는 PR 에서 스크립트는 옛 흔적에서 범위 · 횟수를 읽지 않고 PR 전체 리뷰를 연다.
- AC20. team 형식의 머지 앞 리뷰가 같은 스크립트와 상태 파일을 쓴다 — 대상이 과제와 계획 번호이고, 지휘 절차 문서의 team 형식 절이 펜스를 「표시」 로 적는다. 계획이 다른 두 리뷰의 상태 파일이 섞이지 않는다.
- AC21. §8 의 락 넷이 있고, 각각 그 문장 · 낱말 · 이름을 지우거나 바꾸는 변이에서 실패한다.
- AC22. R6 머지 뒤 리뷰의 제안 열다섯은 하나씩 「받음 · 남김(이유)」 으로 PR 본문에 가려져 있다. spec-distill 의 판 · CHANGELOG · README · 의존 표가 이 변경을 싣고, README 가 §6 의 한계를 적는다.

## Rejected Alternatives

- **지금 구조에 문장을 더 얹는다.** 이 설계의 첫 초안이다 — 점검이 규칙끼리 부딪히는 곳 넷과 team 형식에 남는 구멍을 짚었다(Approaches 2).
- **가장 심각한 셋만 고친다.** 받는 쪽이 정해지지 않은 미룸이 또 생긴다(Approaches 3).
- **PR 본문을 계속 믿고 편집 흔적을 본다.** 지휘자 자신이 그 절을 계속 고쳐 흔적이 가려지고, team 형식에는 PR 이 아직 없다.
- **상태를 에픽 브랜치에 커밋한다.** 구현 쪽이 커밋하는 브랜치다.
- **상태를 기계 상태의 줄들로 둔다.** 리뷰 하나의 상태가 여러 줄에 흩어져 지금과 같은 꼴이 된다 — 리뷰마다 파일 하나가 읽기도 쉽다.
- **모든 자리(spec · 로드맵 끝)에 상태 파일을 쓴다.** 머지를 막는 관문이 없는 자리까지 옮기면 이 에픽이 다시 커지고 지금 도는 로드맵의 옛 흔적을 더 많이 다뤄야 한다.
- **스크립트가 질문을 띄우고 답을 고른다.** 사람 몫이다 — 스크립트는 차례만 낸다.
- **에픽 브랜치의 기록을 아예 읽지 않는다.** 설계 승인 앞에서 한 답이 같은 에픽의 머지 앞 리뷰에 넘어가지 않는다.
- **리뷰가 못 끝나면 자동으로 한 번 다시 보낸다.** 사용자가 「멈추고 묻는다」 를 골랐다(D1).
- **읽지 못한 기록이 하나라도 있으면 어느 답도 넘기지 않는다.** 상관없는 에픽의 답까지 다시 묻는다.
