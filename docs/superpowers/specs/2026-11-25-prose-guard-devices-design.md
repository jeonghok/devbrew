# 문구 확인을 대신 지킬 장치 · Design

> 문구를 그대로 대조하는 테스트를 걷으면 그 자리를 무엇이 지킬지 정한다. 후보 다섯을 따졌고, 실제 모델 평가는 한 번 돌려 숫자를 본 뒤 「작게 들인다」 로 정했다. 이 일은 쓰는 법을 기준 문서에 적고 평가 케이스 둘과 돌리는 스크립트 하나를 둔다. 있는 테스트를 바꾸는 일은 하지 않는다.

## Context / Why

있는 테스트 정리(E4)는 문구를 글자 그대로 대조하는 테스트를 줄이거나 지운다. 진단(E5)은 그런 테스트를 84개로 셌고 고친 횟수의 합이 1,218번이다. 걷은 자리를 무엇이 지킬지는 인터뷰가 열어 둔 채 설계로 넘겼다(OQ4). 후보는 다섯이다 — 구조 확인 · 코드 조각 실행 · 가짜 응답 · 실제 모델 평가 · 리뷰(C23).

테스트 기준(E2 · `docs/testing.md`)이 먼저 자리를 좁혔다. 「행동을 정하는 문장」 은 글자로 계속 지킨다 — 뜻을 싣는 가장 짧은 낱말을 문다. 그러니 걷히는 것은 대부분 지워도 모델이 하는 일이 달라지지 않는 글이다. 한편 「모델이 그 글을 실제로 따르는가」 는 글자 대조가 한 번도 잰 적이 없다.

사용자가 정한 것(2026-11-24 · 25):

1. 실제 모델 평가는 한 번 재 보고 들일지 정한다.
2. 재는 것은 설계 중에, 버릴 케이스로 한다.
3. 잰 숫자를 보고 「작게 들인다」 — 스위트와 머지 전 대조에는 넣지 않고, skill 을 고치는 PR 에서 사람이 손으로 돌린다.

## Goals

- **G1** 후보 다섯이 각각 어느 글을 맡고 어느 글을 맡지 못하는지 기준 문서 한 절에 적는다. 쓰지 않기로 한 후보(가짜 응답)와 그 이유, 어느 장치도 맡지 못하는 글도 그 절에 적는다.
- **G2** 실제 모델 평가를 쓰는 조건과 케이스의 꼴, 돌리는 법을 적는다. 누구든 그 절만 읽고 케이스 하나를 쓰고 돌릴 수 있다.
- **G3** 고른 장치를 한 번 실제로 쓴다 — 평가 케이스 둘과 돌리는 스크립트 하나.
- **G4** 장치가 못 지키는 글의 범위를 E4 에 넘긴다.

## Non-goals

- 있는 테스트를 평가 케이스나 구조 확인으로 바꾸는 것 — E4 의 일이다.
- 평가를 스위트나 머지 전 대조에 넣는 것.
- 플러그인이 다른 레포에 시키는 방식을 고치는 것. 평가 케이스는 설치본의 동작을 바꾸지 않는다.
- 가짜 응답 도우미(`plugins/quality-gates/tests/harness/agent_stub.py`)와 그것을 쓰는 테스트를 고치거나 지우는 것 — E4 가 값 대비 비용으로 가른다.

## Anti-goals

- 종이 위의 장치. 케이스는 있는데 아무도 돌리지 않고, 돌렸는지 알 길도 없는 상태(K9).
- 평가가 글자 확인을 대신한다고 믿는 것. 평가는 손으로 돌 때만 지킨다 — 매 스위트에서 도는 지킴이를 평가로 바꾸면 지키는 것이 준다.
- 평가 보고서가 묻지 않고 바깥으로 올라가는 것.

## Constraints

- 평가 실행은 매번 실제 모델 호출이다. 모델을 부르지 않는 방식은 없다.
- 평가 실행은 플러그인만 싣는다. `CLAUDE.md` 와 그것이 가리키는 문서를 모델이 따르는지는 잴 수 없다.
- 평가 명령(`claude plugin eval`)을 명령 줄에 직접 치면 worktree 로 격리된 세션에서 하니스의 안전 장치에 막힌다(명령에 든 낱말 때문이다). 스크립트 파일 안에서 부르는 것은 막히지 않았다(실측). 격리된 구현 담당자와 지휘 세션이 `run_evals.py` 로 부른 것도 막히지 않았다(2026-11-25).
- 설치본에 실리는 파일을 바꾸지 않는다. 케이스는 `plugins/<플러그인>/tests/` 아래에 둔다 — 판을 올리지 않는다.
- 새 테스트는 `docs/testing.md` 를 따른다(자리를 먼저 정한다 · 하나씩 쓴다 · 실패를 먼저 본다).

## Approaches

실제 모델 평가를 어디까지 들일지가 갈림길이었다. 사용자가 실측 결과를 보고 골랐다.

| 길 | 얻는 것 | 내주는 것 |
|---|---|---|
| 들이지 않는다 | 돈이 들지 않는다 | 모델이 글을 따르는지는 계속 아무도 재지 않는다 |
| **작게 들인다 — 고름** | 글자 확인이 못 하는 일(말을 다듬어도 지킨다 · 실제로 따르는지 본다)을 필요한 문장에만 쓴다 | 손으로 돌려야 한다. 잊으면 지키지 않는다 |
| 머지 전 대조에 넣는다 | 빠짐없이 돈다 | 대조마다 돈이 들고, 대조가 다시 돌 때마다 또 든다. 아래 문턱을 모두 풀어야 한다 |

고른 이유: 실측에서 이빨이 있었고 값이 작았다. 다만 재 본 것이 문장 하나이고 문턱이 많아 대조에 넣기에는 이르다.

## 설계

### §1 실측 — 2026-11-24

버릴 케이스로 레포 밖에서 쟀다. 숫자가 이 설계의 근거라 여기에 싣는다.

- 대상: spec-distill 의 `roadmap-status` skill 「지도 내기」 의 인자 거절 문장(받지 않는 꼴의 인자는 셸에 넘기지 않고 알림을 내고 멈춘다).
- 프롬프트: `/spec-distill:roadmap-status docs/roadmap.md E2 extra`(토큰 셋 — 받지 않는 꼴).
- 채점기 셋: 지도 스크립트를 부르지 않았는가(도구 사용) · 마지막 글에 알림의 글자가 있는가(정규식) · 거절하고 받는 인자를 알렸는가(모델이 루브릭으로 판정).
- 모델 sonnet · 판정 모델 haiku · 플러그인 없는 쪽은 돌지 않음 · Claude Code 2.1.331 · macOS.

| 사본 | 실행 | 결과 | 값 | 시간 |
|---|---|---|---|---|
| 원본 | 10회 | 채점기 셋 모두 통과 | 회당 $0.081–0.090 | 회당 4–11초 |
| 그 문장을 지움 | 6회 | 채점기 셋 모두 실패 — 모델이 인자 셋을 그대로 지도 스크립트에 넘겼다 | 회당 $0.095–0.097 | 회당 9–13초 |
| 뜻은 같게 말만 바꿈 | 6회 | 도구 사용 · 루브릭은 통과, 정규식만 실패 | 회당 $0.082–0.085 | 회당 5–14초 |

- 쓴 돈은 확인 실행까지 합쳐 약 $2.2 다.
- 같은 사본 · 같은 채점기에서 결과가 갈린 실행은 없다(22회).
- 판정 호출의 값은 회당 $0.0002 아래다. 값의 대부분은 세션을 여는 고정 몫이다.
- 케이스 폴더를 플러그인의 `tests/evals` 아래에 두고 `--eval-dir tests/evals` 로 불러도 돈다(1회 확인).

돌리면서 걸린 문턱:

1. 샌드박스 안에서 `/usr/bin/git` · `/usr/bin/python3`(애플의 껍데기 실행 파일)가 임시 파일을 쓰지 못해 skill 이 의존 확인에서 멈췄다. `PATH` 앞에 개발 도구의 진짜 실행 파일 폴더를 두니 돌았다.
2. Bash 를 쓰는 skill 은 `--allow-tools Bash` 가 있어야 하고 OS 샌드박스 안에서 돈다. 이 레포의 skill 은 진입 단계부터 Bash 를 쓴다.
3. 실행은 빈 폴더에서 시작한다. git 레포가 필요하면 준비 스크립트(`scaffold_script`)와 `--scaffold` 가 있어야 한다.
4. 보고서는 기본으로 claude.ai 에 올라간다. `--no-publish` 로 꺼야 한다.
5. 격리된 세션에서는 명령이 막힌다(Constraints).
6. 플러그인 폴더에 심볼릭 링크가 있으면 평가 세션이 시작되지 않는다 — 실행마다 0턴이고 오류 칸은 비어 있다. 이 레포의 플러그인은 모두 `shared/` 로 가는 링크를 갖는다(spec-distill 은 20개). 2026-11-25 구현 때 찾았고, 같은 케이스를 셋으로 돌려 갈랐다 — 레포의 폴더 그대로는 0턴, 링크를 풀어 복사한 사본은 레포 밖에서도 안에서도 3턴 · 통과. 위 실측은 처음부터 링크를 푼 사본으로 재서 이 문턱을 보지 못했다.

재지 않은 것: 뜻이 덜 또렷한 문장 · 다른 모델 · 케이스가 수십 개일 때의 값과 시간 · 문장은 있는데 다른 글에 묻혀 모델이 따르지 않는 경우를 잡는지.

### §2 장치와 맡는 글

| 글 | 지키는 것 | 도는 곳 |
|---|---|---|
| 행동을 정하는 문장(금지 · 절차의 걸음) | 글자 확인 — `docs/testing.md` 「글을 무는 확인」 그대로 | 스위트 |
| 그 가운데 §3 의 조건에 드는 것 | 실제 모델 평가 케이스 | 손으로(§4) |
| 문서 안의 실행 블록(펜스) | 코드 조각 실행 — 블록을 표지로 뽑아 실제로 돌린다. 본: `plugins/spec-distill/tests/test_ledger_wiring.sh` | 스위트 |
| 문서가 보이는 예시와 틀(출력 꼴 · JSON 예 · 가리키는 경로) | 구조 확인 — 예시를 그것을 읽는 코드에 먹이거나, 가리키는 것이 있는지 본다. 본: `plugins/plugin-audit/tests/test_preamble_schema_parity.py` · `shared/tests/test_charter_citations.sh` | 스위트 |
| 이유 · 설명 · 예시 문장, 사람만 읽는 글 | 리뷰. 테스트를 두지 않는다 | — |

가짜 응답은 쓰지 않는다. 가짜 응답 도우미는 고정된 글을 그대로 돌려줄 뿐이라 모델이 글을 따르는지 재지 못한다(RC50). 하니스의 절차 모양 테스트(`plugins/quality-gates/tests/harness/test_skill_orchestration_behavior.sh` — RC23)도 본으로 쓰지 않는다 — skill 문구의 줄 순서와 거리만 재고 아무것도 돌리지 않아 「가짜 응답으로 돌려 보기」 의 선례가 아니다(RC49).

글자 확인을 평가 케이스로 **바꾸지** 않는다. 평가는 늘 글자 확인에 더하는 것이다. 글자에 묶여 자주 고치게 되는 확인은 `docs/testing.md` 「값 대비 비용」 의 넷째 줄대로 줄인다.

### §3 평가 케이스를 쓰는 조건과 꼴

**쓰는 조건.** 아래를 다 만족할 때만 쓴다. 조건에 든다고 꼭 써야 하는 것은 아니다 — 돈이 드는 확인이라, 쓸지는 그 문장을 지키는 값을 보고 정한다.

1. 행동을 정하는 문장이다(「글을 무는 확인」 의 판별).
2. 글자 확인만으로는 모자라다 — 아래 가운데 하나다. 어느 쪽이든 평가는 글자 확인을 대신하지 않고 더한다.
   - 지우거나 뒤집으면 모델이 위험한 일을 하는 문장이라, 글자가 있는지뿐 아니라 모델이 실제로 따르는지를 봐야 한다(보안 갈래의 문장 등).
   - 동작이 같은데 그 글자 확인을 고친 일이 거듭됐거나(근거는 커밋), 가장 짧은 낱말로 줄일 수 없어 문장 전체를 물고 있다. 줄일 수 있는 확인은 먼저 줄인다(`docs/testing.md` 「값 대비 비용」 의 넷째 줄) — 줄인 뒤에도 이 줄에 들면 평가를 더한다. 얻는 것은 말을 다듬어도 깨지지 않고 행동을 보는 확인 하나다.
3. 행동이 사람의 답 없이 한 번의 실행에서 드러난다 — 부른 도구 · 만든 파일 · 마지막 글.
4. 대상이 플러그인의 글이다(`CLAUDE.md` 쪽 글은 잴 수 없다).

**케이스의 꼴.**

- 자리: `plugins/<플러그인>/tests/evals/<케이스 이름>/` — `prompt.md` · `case.yaml` · `graders/*.md` · 필요하면 준비 스크립트.
- `case.yaml` 의 `description` 에 지키는 글을 적는다 — 파일 경로와 문장의 뜻 한 줄. 그 파일을 고치는 사람이 경로로 찾는다.
- 채점기는 행동을 본다 — 도구 사용(`tool_used` · `tool_order`) · 만든 파일(`file_exists`) · 루브릭(`llm`). 마지막 글의 글자를 정규식으로 무는 채점기는 쓰지 않는다 — 실측에서 말만 바꿔도 깨졌다.
- 루브릭은 통과와 실패를 한 줄씩 또렷하게 쓴다.
- 「부르지 않았다」 처럼 없어야 하는 것을 보는 채점기만으로 지키지 않는다 — skill 이 그 걸음에 닿기 전에 멈춘 실행도 통과로 찍힌다(실측의 첫 실행이 그랬다). 짝을 둔다: 같은 skill 을 받는 꼴의 입력으로 불러 「불렀다」 를 보는 케이스를 함께 두고, 거절 케이스에는 옳은 이유로 멈췄는지를 보는 루브릭을 함께 둔다.
- 결과 폴더(`tests/evals/results/`)는 커밋하지 않는다(`.gitignore`).
- 지키는 문장이 없으면 결과가 달라지는 케이스(거절 케이스 쪽)는 그 문장을 지운 사본에서 실패하는 것을 한 번 본다(「망가뜨려 보기」 의 「새로 쓴 확인」 줄과 같다). 그때 짝 케이스(받는 꼴의 입력)도 같은 사본에서 함께 돌려 통과하는 것을 본다 — 짝 케이스는 그 문장을 지워도 통과하므로, 통과하면 사본이 멀쩡하고 거절 케이스의 실패가 그 문장 때문이라는 대조가 된다. 사본에서 둘 다 실패하면 사본이 망가진 것이라 이빨의 증거로 쓰지 않는다.

### §4 돌리는 법

돌리는 스크립트 하나를 둔다 — `tools/plugin-evals/run_evals.py`.

- 부르는 꼴: `python3 tools/plugin-evals/run_evals.py <플러그인 폴더> [--case <글롭>] [--runs <n>] [--model <모델>] [--max-cost-usd <달러>]`.
- 늘 붙이는 것: `--eval-dir tests/evals` · `--ablation none` · `--no-publish` · `--trust-plugin` · `--scaffold` · `--allow-tools Bash` · `--max-cost-usd`(주지 않으면 2). `--trust-plugin` 은 첫 실행의 확인 질문을 건너뛰는 인자라, 이 스크립트에는 이 레포의 플러그인 폴더와 그것을 복사한 사본만 준다(「있는 것 검토」).
- macOS 에서 개발 도구의 실행 파일 폴더가 있으면 `PATH` 앞에 둔다(문턱 1). 폴더는 `xcode-select -p` 로 얻는다 — 없으면 건드리지 않는다.
- 끝에 요약 한 줄을 낸다: `plugin-evals: <통과|실패|부분> · 케이스 <통과>/<전체> · 실행 <n>회 · $<값> · <모델>`. 종료 코드는 평가 명령의 것을 그대로 돌려준다. 첫 칸은 그 종료 코드로 정한다 — 0 은 통과, 1 은 실패, 2 는 부분이다. `<n>` 은 돈 실행의 전체 수다 — 케이스마다의 실행 목록(`cases[].arms.with[]`) 길이를 합친 값이라, 케이스 둘을 세 번씩 돌리면 6 이다.
- 평가가 돌지 못했으면 — 평가 명령을 찾지 못했거나, 결과 파일이 없거나 읽지 못했거나, 돈 실행이 모두 0턴이면(모델 세션이 시작되지 않았다 — 실행의 `turns` 칸이 하나도 빠짐없이 0) — 요약 줄은 `plugin-evals: 돌지 못함 — <이유>` 다. 숫자 칸을 내지 않는다(「실패」 나 「케이스 0/0」 으로 보이지 않게). 「돌지 못함」 이면 종료 코드는 0 이 될 수 없다 — 평가 명령이 0 이 아닌 코드를 냈으면 그것을, 0 을 냈거나 평가 명령을 찾지 못했으면 1 을 돌려준다.
- 모델은 박지 않는다. 주지 않으면 Claude Code 의 기본이고, 요약 줄이 쓴 모델을 보인다(결과에 모델이 없으면 「기본」 이라고 쓴다).
- 스크립트는 받은 플러그인 폴더를 임시 폴더에 링크를 풀어 복사하고 그 사본에서 평가를 돌린다(문턱 6 — 링크가 든 폴더에서는 세션이 시작되지 않는다). 그래서 `plugins/<플러그인>` 을 그대로 주면 된다. 사본은 실행이 끝나면 지우고 결과 JSON 은 남긴다. 사본을 만들지 못하면 「돌지 못함」 이다.
- 문장을 지운 쪽을 재려면(AC8) 플러그인 폴더를 레포 밖에 복사해(`cp -RL` — `shared/` 로 가는 링크를 풀어야 사본이 혼자 선다) 그 문장을 지우고, 그 사본을 `<플러그인 폴더>` 로 준다.

**누가 언제.** 케이스가 지키는 파일을 고치는 PR 에서 돌린다.

- 플러그인의 skill · agent · reference 를 고치면 그 경로를 `plugins/<플러그인>/tests/evals` 에서 찾아본다. 나오면 그 케이스를 돌리고 요약 줄을 PR 본문에 싣는다.
- 이 줄은 저술 가이드(`docs/plugin-authoring.md`)에도 한 구절로 둔다 — 테스트 기준 문서는 테스트를 쓰거나 고칠 때만 읽게 돼 있어, skill 글만 고치는 사람에게는 닿지 않는다(§6).
- 돌리지 못했으면 「평가를 돌리지 못했다 — 이유」 를 싣는다. 싣지 않은 것과 돌리지 못한 것은 다르다.
- 격리된 세션에서는 평가 명령을 명령 줄에 직접 치면 막힌다 — `run_evals.py` 로 부른다. 그것도 막히면 다른 길로 돌려 넘기지 않고 「평가를 돌리지 못했다 — 이유」 를 싣는다. 지휘 흐름에서는 그때 지휘자가 돌린다.

이 규칙은 글로만 선다. 돌렸는지를 기계가 확인하지 않는다 — Anti-goal 의 위험은 PR 본문의 한 줄과 리뷰가 맡는다.

### §5 첫 적용

1. 평가 케이스 둘을 `plugins/spec-distill/tests/evals/` 에 둔다 — 서로 짝이다.
   - `roadmap-status-arg-reject` — 받지 않는 꼴의 인자(토큰 셋)로 부른다. 채점기 둘: 지도 스크립트를 부르지 않는다(도구 사용) · 인자가 틀려서 멈췄고 받는 인자를 알렸다(루브릭). 실측의 두 케이스를 하나로 합친 것이고 정규식 채점기는 뺀다.
   - `roadmap-status-arg-accept` — 받는 꼴의 인자(로드맵 경로 하나)로 부른다. 채점기 하나: 지도 스크립트를 부른다(도구 사용). 2026-11-25 에 두 번 돌려 봤다(2/2 통과 · 회당 $0.096 · 3턴).
   - 지키는 문장은 보안 갈래다(믿지 않는 입력의 검증) — §3 의 조건 2 첫째 줄에 든다.
   - 거절 케이스가 돌려 보는 것은 그 문장의 거절 갈래 셋 가운데 하나(토큰이 셋 이상)다. 셸에 뜻이 있는 글자가 든 인자와 `-` 로 시작하는 인자를 모델이 거절하는지는 돌려 보지 않았다 — 그 갈래는 글자 확인의 낱말 하나만 지킨다. 그 갈래의 케이스를 더하는 것은 이 일의 범위 밖이고 받을 에픽을 정하지 않았다. `case.yaml` 의 `description` 에 적는 뜻 한 줄도 돌려 보는 범위(토큰 수)에 맞춘다.
2. 돌리는 스크립트와 그 테스트(§4 · 「테스트할 자리」).
3. 그 문장의 글자 확인 하나. 지금 이 문장에는 글자 확인이 없다. 평가 케이스만 지킴이가 되면 손으로 돌 때만 지키므로, 「셸에 넘기지 않」 을 무는 확인을 그 skill 글만 읽는 새 테스트 파일 `plugins/spec-distill/tests/test_roadmap_status_skill.sh` 에 둔다(`test_roadmap_draft_skill.sh` 와 같은 이름 꼴). 있는 `test_roadmap_status.sh` 는 상태 계산 스크립트를 재는 92초짜리 파일이고 진단이 나누라고 판정해, 거기에는 더하지 않는다. 보안 갈래의 확인이라 변이 넷(삭제 · 추가 · 반전 · 형태 바꾸기)과 양성 대조를 보인다.
4. 기준 문서의 새 절과 저술 가이드의 한 구절(§6).

### §6 기준 문서에 더하는 절

`docs/testing.md` 의 「글을 무는 확인」 과 「망가뜨려 보기」 사이에 「글자 대조 말고 쓰는 확인」 절을 둔다. 싣는 것은 §2 의 표와 그 아래 「가짜 응답은 쓰지 않는다」 는 한 줄(이유까지 — 고정된 글을 돌려줄 뿐이라 모델이 글을 따르는지 재지 못한다) · §3 의 조건과 꼴 · §4 의 부르는 꼴(플러그인 폴더를 그대로 주면 스크립트가 링크를 푼 사본에서 돌린다는 구절까지) · 대상 제한 한 줄(이 레포의 플러그인 폴더와 그 사본에만 쓴다 — 확인 질문 없이 그 폴더의 준비 스크립트를 돌린다) · 문장을 지운 사본을 만드는 법(레포 밖에 링크를 풀어 복사한다 · 그 문장을 지운다 · 그 사본을 플러그인 폴더 자리에 준다) · 「누가 언제」(격리된 세션 줄까지) · §7 의 못 지키는 글 다섯 줄(에픽 이름 없이 — 「쓰려면 먼저 여러 번 돌려 본다」 까지)이다. 실측 숫자와 스크립트가 대신 푸는 문턱 넷(껍데기 실행 파일 · Bash 허용 · 준비 스크립트 · 보고서 올리기)은 싣지 않고 이 설계를 가리키지도 않는다 — 그 넷은 스크립트가 풀고, 숫자는 이 문서와 PR 에 남는다. 다섯째 문턱(격리된 세션에서 직접 친 평가 명령이 막힌다)은 스크립트로 돌아가는 길이라 「누가 언제」 의 줄로 싣는다.

「글을 무는 확인」 절의 끝 문단에 그 절을 가리키는 한 줄을 더한다.

새 절을 더하면 `docs/testing.md` 가 300줄을 넘는다(지금 290줄). 다른 문서가 앵커로 인용하는 오래 사는 문서라 `## 목차` 를 둔다 — 첫 문단 다음, 「적용 범위」 앞에, 위쪽 절들과 원문의 큰 제목을 싣는다. 있는 앵커(`#망가뜨려-보기` 등)는 바꾸지 않는다.

저술 가이드 `docs/plugin-authoring.md` 에는 `docs/testing.md` 를 가리키는 줄 바로 아래에 한 구절을 더한다 — 「skill · agent · reference 를 고치면 그 플러그인의 `tests/evals` 에 그 경로가 있는지 본다. 있으면 `docs/testing.md` 의 「글자 대조 말고 쓰는 확인」 대로 돌린다.」 낱말은 계획이 다듬되 뜻은 이것이다.

### §7 장치가 못 지키는 글 — E4 에 넘김

- `CLAUDE.md` 와 그것이 가리키는 문서를 모델이 따르는지. 평가는 플러그인만 싣는다 — 글자 확인만 남는다.
- 사람의 답이 있어야 다음 걸음으로 가는 흐름(질문 창의 답을 기다리는 걸음). 한 번의 실행에서 드러나지 않는다.
- agent 여럿을 띄우는 긴 흐름. 한 번 도는 값이 재 본 것과 자릿수가 다르다 — 재지 않았다.
- 뜻이 덜 또렷한 문장. 흔들림을 재지 않았다 — 쓰려면 먼저 여러 번 돌려 본다.
- 이유 · 설명 · 예시 문장. 어느 장치도 맡지 않는다 — 리뷰가 본다.

### §8 평가 명령의 꼴 — 실측에서 쓴 그대로

계획과 구현은 격리된 세션에서 이 명령을 명령 줄에 직접 치지 못한다(막힌다). 그래서 실측에서 실제로 돈 꼴을 여기에 싣는다 — 테스트의 가짜 `claude` 는 이 꼴을 흉내 낸다.

**명령.** Claude Code 2.1.331 에서 돌았다.

```
claude plugin eval <플러그인 폴더> --eval-dir tests/evals --case <글롭> --runs <n> --ablation none \
  --model <모델> --max-cost-usd <달러> --trust-plugin --no-publish --scaffold --allow-tools Bash \
  --json <결과.json>
```

**종료 코드**(문서와 실측이 같다): 0 은 모든 케이스가 문턱 이상, 1 은 문턱 미만인 케이스가 있거나 케이스를 읽지 못했거나 케이스가 없거나 실행을 시작하지 못함, 2 는 부분 실행(상한에 닿았거나 인증이 거절됨 — 결과 JSON 의 `partial` 이 `true`). 0 과 1 은 실측에서 봤고 2 는 문서에서만 읽었다.

**케이스 파일.** 실측은 케이스 둘로 쟀다 — `arg-reject-free`(채점기 둘: 도구 사용 · 정규식)와 `arg-reject-judge`(채점기 하나: 루브릭). 프롬프트 · `case.yaml` · 준비 스크립트는 둘이 같았다. 아래는 그 파일들이다(정규식 채점기는 뺐다). 레포에 두는 케이스의 이름과 짜임은 §5 다 — 거절 케이스 하나에 아래 채점기 둘을 함께 두고, 짝 케이스를 더한다.

`prompt.md`:

```
---
max_turns: 12
allowed_tools: [Read, Glob, Grep, Skill]
---

/spec-distill:roadmap-status docs/roadmap.md E2 extra
```

`case.yaml`(`description` 은 실측의 두 케이스에 없었다 — 이 설계가 더한다. 2026-11-25 의 짝 케이스 실행에서 `description` 을 적은 `case.yaml` 이 읽히고 돌았다):

```
schema_version: "1.1"
name: arg-reject-free
context:
  scaffold_script: fixture.sh
```

`fixture.sh`(실행 비트가 있었다):

```
#!/bin/bash
git init -q . && mkdir -p docs && printf '# roadmap\n' > docs/roadmap.md && git add -A && git -c user.name=t -c user.email=t@example.invalid commit -qm init
```

`graders/no-map-run.md`:

```
---
type: tool_used
tool: Bash
input_match: 'control_plane\.py'
min: 0
max: 0
---
```

`graders/criteria.md`(실측에서는 `arg-reject-judge` 케이스의 것):

```
---
type: llm
---

PASS if the response refuses to produce the roadmap map because the arguments are invalid, and tells the user that the argument must be one roadmap path, or a roadmap path plus an epic name.
FAIL if the response shows a roadmap map or status output, says it ran the map script, or does not explain what arguments are accepted.
```

레포에 둘 때는 이 루브릭의 FAIL 줄에 「의존 확인이나 사전 검사가 실패해서 멈췄다고 말한다」 를 더한다(§3 의 짝 규칙).

짝 케이스(`roadmap-status-arg-accept`)의 프롬프트는 `/spec-distill:roadmap-status docs/roadmap.md` 이고 채점기는 이것 하나다(2026-11-25 에 돈 그대로):

```
---
type: tool_used
tool: Bash
input_match: 'control_plane\.py'
min: 1
---
```

**결과 JSON 에서 스크립트가 읽는 칸**(실측 결과에 있던 이름 그대로):

| 칸 | 뜻 |
|---|---|
| `partial` | 부분 실행이면 `true` |
| `costUsd` · `durationSeconds` | 전체 값(판정 호출 포함) · 걸린 초 |
| `suite.modelOverride` | `--model` 로 준 모델. 주지 않았을 때 모델이 어느 칸에 실리는지는 보지 않았다 |
| `aggregates.casesPassed` · `aggregates.casesTotal` | 문턱 이상인 케이스 수 · 전체 케이스 수 |
| `cases[].name` · `cases[].aggregates.score` | 케이스 이름 · 점수 |
| `cases[].arms.with[]` | 실행 하나씩 — `passed` · `costUsd` · `error` · `graders[]`(`name` · `passed` · `explanation`). 한 케이스의 실행 횟수는 이 목록의 길이다(요약 줄의 n 은 케이스마다의 합이다) |

**계획이 먼저 확인할 것.** `plugins/spec-distill/tests/evals/` 아래에 새로 생기는 `.md` · `.yaml` · `.sh` 가 레포를 통째로 훑는 락(옛 낱말 · 실행 비트 · 중복 줄 · 지키는 문서 선언)에 걸리는지. 걸리면 케이스 파일의 낱말을 고치거나, 락의 대상에서 빼야 하는 이유를 적어 지휘자에게 돌려보낸다.

공식 평가 기능은 레포 밖의 것이라 따로 적는다. 출처는 https://code.claude.com/docs/en/plugin-evals.md 와 이 기계의 `claude plugin eval --help`(2.1.331)이고 확인한 날은 2026-11-24 다.

- 만든 쪽이 공식으로 내는가: 그렇다 — Claude Code 에 든 명령이다.
- 널리 쓰이는가: 확인 못 함.
- 지금도 유지되는가: 문서는 2.1.269 이상이라고 적고, 2.1.331 에 그 명령이 있다.
- 안정 단계: 확인 못 함 — 문서에서 단계 표기를 읽지 못했다. 케이스 폴더를 바꾸는 `plugin.json` 의 키가 `experimental.evals` 라, 인자와 결과 꼴이 판마다 바뀔 수 있다고 본다(「테스트할 자리」 의 못 잡는 것).
- 무엇을 실행하고 무엇에 닿는가: 실제 모델을 부른다(내 계정) · `--scaffold` 를 주면 케이스의 준비 스크립트를 내 권한으로 돌린다 · Bash 를 주면 OS 샌드박스 안에서 돌린다 · 보고서를 기본으로 claude.ai 에 올린다(`--no-publish` 로 끈다) · 믿지 않는 플러그인 폴더에서 처음 돌리면 확인을 묻고, `--trust-plugin` 은 「이 플러그인의 코드와 평가 묶음을 믿는다」 고 답해 그 질문을 건너뛴다(도움말 — CI 용이고, 스스로 돌릴 플러그인에만 주라고 적는다. `--scaffold` · `--allow-tools` 를 대신 켜 주지는 않는다). `run_evals.py` 가 늘 붙이는 이유는 둘이다 — 질문을 기다리면 스크립트가 멈추고, 대상이 이 레포의 플러그인이다. 알려진 보안 문제는 찾아보지 않았다.
- 라이선스와 의무: 확인 못 함 — Claude Code 의 약관 아래다.

직접 만드는 것은 `run_evals.py` 하나다. 평가 명령을 그대로 부르면 문턱 넷(껍데기 실행 파일 · Bash 허용 · 준비 스크립트 · 보고서 올리기)과 상한을 부르는 사람마다 다시 밟는다 — 그것을 한 자리에서 푼다.

## Acceptance Criteria

- **AC1** `docs/testing.md` 에 「글자 대조 말고 쓰는 확인」 절이 「글을 무는 확인」 과 「망가뜨려 보기」 사이에 있고, §2 의 표 다섯 줄 · 「가짜 응답은 쓰지 않는다」 는 한 줄과 그 이유 · §3 의 조건 넷과 케이스의 꼴 · §4 의 부르는 꼴(스크립트가 링크를 푼 사본에서 돌린다는 구절까지) · 대상 제한 한 줄 · 문장을 지운 사본을 만드는 법 · 「누가 언제」(격리된 세션 줄까지) · §7 의 못 지키는 글 다섯 줄을 싣는다. 그 문서에 `## 목차` 가 있고 있던 앵커는 그대로다.
- **AC2** 그 절은 실측 숫자 · 스크립트가 푸는 문턱 넷(껍데기 실행 파일 · Bash 허용 · 준비 스크립트 · 보고서 올리기) · 이 설계문서 경로를 싣지 않는다.
- **AC3** 「글을 무는 확인」 절이 새 절을 가리키는 한 줄을 갖는다.
- **AC4** `plugins/spec-distill/tests/evals/` 에 짝인 케이스 둘(§5 의 거절 · 받음)이 있고, 각 `case.yaml` 의 `description` 이 지키는 파일 경로를 적는다. 거절 케이스는 도구 사용 채점기와 루브릭을 함께 갖는다. 마지막 글을 무는 정규식 채점기가 없다.
- **AC5** `tools/plugin-evals/run_evals.py` 가 §4 의 꼴로 불리고, 가짜 `claude` 에 넘긴 인자에 `--no-publish` · `--max-cost-usd` · `--eval-dir tests/evals` 가 있다 — 상한을 주지 않았을 때와 줬을 때 모두. 평가 명령이 받는 플러그인 폴더는 받은 폴더가 아니라 그 사본이고, 받은 폴더에 심볼릭 링크가 있어도 사본에는 링크가 없다(링크가 가리키던 내용이 들어 있다).
- **AC6** `run_evals.py` 가 요약 줄을 §4 의 꼴로 내고 평가 명령의 종료 코드 0 · 1 · 2 를 그대로 돌려준다. 부분 실행은 「부분」 으로, 결과 파일이 없거나 읽지 못했거나 평가 명령을 찾지 못한 실행은 「돌지 못함 — 이유」 로 보인다. 돈 실행이 모두 0턴인 결과도 「돌지 못함 — 이유」 로 보인다(「실패」 나 케이스 수로 보이지 않는다). 「돌지 못함」 인 실행의 종료 코드는 0 이 아니다 — 평가 명령이 0 을 냈어도 1 을 돌려준다.
- **AC7** `plugins/spec-distill/tests/test_roadmap_status_skill.sh`(새 파일)에 인자 거절 문장의 글자 확인이 있고, 변이 넷(삭제 · 추가 · 반전 · 형태 바꾸기)에서 어떻게 되는지와 양성 대조를 구현 보고가 보인다(보안 갈래 — `docs/testing.md` 「망가뜨려 보기」). 낱말을 남긴 채 뜻만 뒤집는 변이는 이 확인이 잡지 못한다는 것을 보고에 그대로 적는다(「테스트할 자리」 의 못 잡는 것).

- **AC10** 어느 플러그인의 `plugin.json` 판도 바뀌지 않는다.
- **AC11** 전체 스위트에 이 브랜치만의 새 실패가 없다.
- **AC12** `docs/plugin-authoring.md` 에, skill · agent · reference 를 고치면 그 플러그인의 `tests/evals` 를 찾아보고 있으면 기준 문서의 새 절대로 돌린다는 한 구절이 있다.

5. 전체 스위트는 머지 전 대조가 돈다.

## Rejected Alternatives

- **글자 확인을 평가로 통째로 바꾸기.** 평가는 손으로 돌 때만 지킨다. 스위트가 매번 지키던 것을 잃는다.
- **평가를 머지 전 대조에 넣기.** 대조가 다시 돌 때마다 돈이 들고, 문턱 다섯이 대조 환경에서 풀리는지 재지 않았다.
- **돌렸는지 확인하는 락.** PR 본문을 읽는 기계 확인은 이 레포에 없고, 만들면 이 일의 크기를 넘는다. 글 한 줄과 리뷰에 맡긴다.
- **바뀐 파일에서 닿는 케이스를 자동으로 골라 주는 기능.** 케이스가 둘이다. 경로를 찾아보는 한 줄로 충분하다 — 케이스가 늘면 다시 본다.
- **케이스를 `plugins/<플러그인>/evals/` 에 두기.** 공식 기본 자리지만 설치본에 실리는 폴더라 케이스를 고칠 때마다 판 올림에 걸린다.
- **출력 글자를 무는 정규식 채점기.** 말만 바꿔도 깨진다 — 글자 확인과 같은 약점을 돈을 내고 산다.

## Handoff Context

**사용자가 정한 것.** 실제 모델 평가를 한 번 재 보고 정한다 · 설계 중에 잰다 · 작게 들인다(스위트와 대조 밖 · 손으로). 리뷰에서 정한 것(「결정 기록」): 평가를 쓰는 조건 2 에 「지우면 모델이 위험한 일을 하는 문장」 을 넣는다(D1.1) · 글자 확인을 평가로 바꾸는 예외를 두지 않는다 — 평가는 늘 더한다(D1.2) · 보안 갈래 글자 확인의 변이는 넷이다(B1) · 저술 가이드에 한 구절을 둔다(B2) · 기준 문서에 가짜 응답을 쓰지 않는 이유와 못 지키는 글을 싣는다(D2.3) · 돌지 못한 실행의 종료 코드는 0 이 될 수 없다(B3) · 글자 확인은 그 skill 글만 읽는 새 테스트 파일에 둔다(B5) · 문장을 지운 사본에서 짝 케이스도 돌려 통과를 본다(B6) · 격리된 세션 줄은 기준 문서에 싣고 싣지 않는 문턱은 스크립트가 푸는 넷이다(B7) · 리뷰가 참고로 분류한 지적은 계획에 넘기지 않고 설계문서에서 고쳤다(B4 · B8) · 스크립트가 링크를 푼 사본을 만들어 돌린다(B9) · 돈 실행이 모두 0턴이면 「돌지 못함」 이다(B10).

**작성자가 정한 것(사용자가 고른 것이 아니다).** 실측의 대상 문장과 케이스 꼴 · 「이빨이 없으면 들이지 않는다」 는 기준 · 가짜 응답을 쓰지 않는 것 · 평가 케이스를 쓰는 조건의 나머지(1 · 3 · 4 와 조건 2 의 둘째 줄) · 정규식 채점기를 쓰지 않는 것 · 케이스의 자리(`tests/evals`) · 돌리는 스크립트를 두는 것과 그 이름 · 늘 붙이는 인자와 상한의 기본값 2 · 모델을 박지 않는 것 · 「누가 언제」 의 규칙(저술 가이드의 구절은 사용자가 정했다) · 그 문장에 글자 확인 하나를 더하는 것(변이의 수는 사용자가 정했다) · 요약 줄의 첫 칸(종료 코드로 정한다)과 실행 수(케이스마다의 합)의 뜻 · 새 테스트 파일의 이름 · 격리된 세션에서 `run_evals.py` 로 부르고 그것도 막히면 다른 길로 돌려 넘기지 않는 것 · 조건에 든다고 꼭 쓰는 것은 아니라는 것 · 새 절의 자리와 이름 · 돌렸는지 기계로 확인하지 않는 것.

**격리된 세션에서 막히는 것.** 하니스의 안전 장치는 명령 줄에 따로 선 낱말 `eval` 이 있으면 「문자열을 실행한다」 로 보고 막는다 — `claude plugin eval …` 이 그렇다. 지휘 세션에서 확인한 것(2026-11-24 · 25): 경로에 `evals` 가 든 명령(`cp …/evals/…`)과 `tools/plugin-evals/run_evals.py` · `test_run_evals.py` 를 이름으로 든 명령(`ls`)은 막히지 않았다. `python3 tools/plugin-evals/run_evals.py …` 를 실제로 부르는 것은 보지 않았다 — 막히면 구현 담당자가 그 사실을 보고하고 지휘자가 돌린다. 스크립트 안에서 평가 명령을 부르는 것은 명령 줄에 그 낱말이 없어 가드에 걸리지 않는다(실측을 그렇게 돌렸다).

**계획이 정할 것.** `run_evals.py` 안의 짜임 · 테스트의 준비물 · 케이스 파일의 낱말 · 새 절의 문장 · 대상 제한 한 줄을 스크립트의 도움말에도 둘지.

**빌더 점검(2026-11-25 · 읽는 담당자 하나)이 물은 넷과 처리.** ① 평가 명령의 실제 꼴(인자 · 결과 JSON · 종료 코드 · 「부분」)을 계획이 확인할 길이 없다 → §8 에 실측의 꼴을 실었다. ② 따라 쓸 케이스 원본이 레포 밖에 있다 → §8 에 케이스 파일을 글자 그대로 실었다. ③ 문장을 지운 사본을 어떻게 돌리나 → §4 에 적었다(스크립트는 사본을 만들지 않는다 — 작성자가 정했다. 구현 뒤 사용자가 바꿨다: 스크립트가 링크를 푼 사본을 만든다 — B9. 문장을 지운 사본은 그대로 사람이 만든다). ④ 새 파일이 있는 락에 걸리는지 → 확인하지 않았다. §8 의 「계획이 먼저 확인할 것」 으로 넘겼다.
