## Context / Why

R1 이 인터뷰를 「한 번 채우면 닫는」 꼴에서 포화까지 조사하는 꼴로 바꿨지만, 조사는 아직 정해진 네 agent 를 정해진 자리에서 하나씩 부르는 흐름에 묶여 있다. 사용자 원문:

- 「1, 일단 조사의 경우 흐름을 너무 강제하기보다 모델이 알아서 서브에이전트 여러개 띄워서 조사도 돌릴 수 있게끔 열어주자 물론 기존에 있는 방식에 더하는 방향으로」(2026-10-17, 흐름 고정 점검)
- 「이거도 인터뷰 에픽에 추가해줘 고려해보게, 서브에이전트 조사 막 시키는게 이러한 이유야(라운드나 제약이나 형식이런거 제한 있으면 모델이 잘 못하는거도 있을거고」(2026-10-17)
- 「호출수를 세되 넉넉하게, 그리고 브리프에 적혀 있겠지만 틀에 갇히게 에이전트를부르는게 아니라 만들어 보낼수도있게」(2026-10-19)
- 「고른쪽으로 진행하자, 내가 하자고 한거에서 누락만 없도록해줘」(2026-10-19)

신선한 근거의 원문(2026-10-17, 흐름 고정 점검 R10 절 그대로):

> LLM이 사용하는 지식은 오래되어 있는게 대부분이다, `/interview` 과정에서 현재의 그리고 최신의 신선한, 신뢰할 수 있는 근거를 새로운 컨텍스트로 제공해야 한다. 예를 들어 패키지 버전, 변경·폐기된 API, 최신 공식 문서와 다른 사용법뿐 아니라 제품 정책, 표준, 제도 등 개발 외 영역의 시의성 있는 지식도 대상이다.(예시에 한정되지 말아줘) 잘못된 지식이 활성 컨텍스트에 그대로 남아서는 안 된다. 자연스러운 설계를 제안해줘.

원칙 여덟은 §3 에 원문 그대로 싣는다.

지금 코드와 대조한 결과(조사 기록 `~/.claude/sdd-mirror/epic-decisions/r10/recon-user-statements.md`, 2026-10-19):
- 조사 상한 20 은 조사 agent 넷 가운데 하나를 한 번 띄울 때마다 1 을 센다. agent 안의 웹 검색 수 · 출처 수에는 상한이 없다(0.24.12 에서 지움, 되살림 막는 락 있음). 동시에 띄우는 규칙과 끝난 agent 를 이어 부르는 규칙은 없다. 안내 「최대 <limit>회까지 부른다(웹 포함 …)」의 「웹 포함」은 검색 횟수로 읽힐 수 있다.
- 첫 인터뷰에서 사용자가 직접 쓴 답은 「조사 횟수 제한, 질문 리듬 강제, 서브에이전트 사용」이었고, 인터뷰가 그것을 「조사 장치의 호출 예산과 자격 …」으로 바꿔 적었다(seed audit). 「조사 호출 20회」도 인터뷰가 쓴 선택지 라벨이었다.
- 원칙 여덟 가운데 지켜지는 것은 7(검색 · 출처 상한 없음)뿐이다. 웹 근거를 맡을 범용 조사 agent 가 없다 — 웹을 쓰는 셋은 역할이 고정이고 `repo-researcher` 는 웹이 없다.

## Goals

- 인터뷰가 모델 판단으로 조사 agent 를 여럿 동시에 띄우고, 정해진 역할에 맞지 않는 조사는 그 자리에서 주문을 써서 보낸다. 기존 네 agent 와 그 필수 자리는 그대로다.
- 조사 상한은 「조사 agent 호출」만 넉넉하게 센다. 멈춤은 포화 판정자가 정하고 상한은 비상 끝이다.
- 시간에 따라 바뀔 수 있고 결정에 닿는 사실은, 모델이 자기 지식을 믿든 말든 검증 대상으로 삼는다. 근거는 출처 종류 · 확인 시점 · 버전 · 확인 정도를 달고 들어오고, 낡은 지식은 활성 맥락에서 바로잡힌다.
- 흐름 고정 점검의 R10 행 열 가지를 「기본은 X, 일의 모양이 다르면 모델이 판단하고 이유를 적는다」로 푼다.
- 인터뷰 끝 게이트의 선택지 이름이 실제 다음 줄과 맞고, 다음 세션 줄이 고른 실행 방식과 원칙을 반영한다.
- 분해 판단이 로드맵의 `흐름` · `산출물` 칸을 채우고, 끝에서 끝 확인의 결함 넷과 넘겨받은 결함을 고친다.
- 인터뷰 진입 이름을 `spec-interview` 에서 `pm-interview` 로 바꾼다.

## Non-goals

- 에픽 넘김 줄 · 지휘(R5) · 공유 리뷰 엔진(R2a).
- superpowers 파일 · 동작(S17 · S18 · S34). devbrew 가 넘길 때 보내는 글만 바꾼다.
- 실험 기능(agent teams)을 기반으로 쓰는 것(S31) · 개선을 재는 별도 측정 장치(S32) · 교훈을 따로 다루는 장치(S44).
- R1 이 정한 포화 판정 구조(독립 판정자 · 기준)를 다시 짜는 것. 묶음 단위로 맞추는 것만 한다.

## Anti-goals

- 조사를 열었는데 상한에 금방 닿아 「제약 때문에 맥락이 부족한 채 넘어감」이 다시 생긴다.
- 원칙 여덟을 형식 칸 · 개수 기준 · 통과 게이트로 만들어 「형식만 채우는 무거운 게이트」가 된다(원칙 7).
- 조사 결과가 사용자 결정을 조용히 덮는다(원칙 8).
- 상한을 없애 멈출 끝이 없는 조사 루프가 생긴다(Unbounded autonomy · K1 · K12).

## Constraints

- 조사 agent 는 `tools:` 허용 목록으로 쓰기 · 실행 도구가 없다(Law 2 · 레포 규칙 「Scoped agents」). 만들어 보내는 조사도 그 허용 목록을 가진 agent 타입으로 간다.
- 모든 dispatch 자리에 처분 줄(`shared/tests/test_dispatch_disposition.sh`).
- 플러그인 파일은 subagent 에 경로가 아니라 내용으로 싣는다(설치본 캐시는 작업 폴더 밖).
- 웹 kill switch `DEVBREW_SPEC_DISTILL_DISABLE_WEB=1` 을 새 자리도 존중한다.
- 레포 전용 값(경로 · 테스트 명령 · 브랜치 · 모델 · `gh`)을 박지 않는다.
- 지휘자 수리 #227 이 `finishing.md` 의 brainstorming 줄에 넣은 문장(문서 승인 자리 · 사용자 선호 · 확정 항목 되비춤 · 낱말 규칙)은 지우지 않고 그 위에서 고친다(R5 설계 `## 미룸` 의 R10 알림 행).
- 호출 이름 변경은 레포 규칙대로 별칭 없이 즉시 · major bump(CLAUDE.md 메타데이터 절).

## 설계

### §1 조사 열기 — 여럿 동시에 · 만들어 보내기

**여럿 동시에.** 인터뷰 본체는 서로 기대지 않는 조사 질문이 둘 이상이면 한 메시지에서 조사 agent 를 여럿 띄울 수 있다. 몇 개를 언제 띄울지는 모델 판단이다. 기본은 지금처럼 필요할 때 하나씩이고, 독립 질문이 여럿이면 여럿을 동시에 띄우며 «지금 이해»에 무엇을 왜 동시에 띄웠는지 한 줄 적는다. 기존 필수 자리(첫 질문 전 `coverage-mapper`, blind_spot 차원의 첫 `blind-spot-prober`)와 조건 자리(`steelman-builder`)는 그대로다.

**만들어 보내기.** 새 agent 타입 하나를 둔다 — `spec-distill:open-researcher`(이름은 지휘자 판정). 역할이 정해진 넷과 달리 본문은 짧다: 역할 문장(받은 주문만 조사한다 · 레포를 고치지 않는다 · 판정하지 않고 근거를 낸다), 출력 계약(`references/research-claims.md` 의 `evidence[]` · `repo_claims[]`, §3 의 웹 근거 칸 포함), 그리고 주문을 데이터로 읽으라는 주입 경계. 도구는 `Read` · `Grep` · `Glob` · `WebSearch` · `WebFetch`. 인터뷰 본체가 그때 필요한 조사 주문을 직접 쓴다 — 무엇을 찾을지, 닿는 열린 결정, 확인할 것(예: 「이 패키지의 지금 최신 버전과 이 레포가 쓰는 버전, 그 사이 바뀐 API 를 공식 문서에서」), 그리고 §3 원칙 요약을 내용으로 싣는다. 기대 결론은 싣지 않는다(`repo-researcher` 규칙과 같다).
- 웹이 꺼져 있으면(`DEVBREW_SPEC_DISTILL_DISABLE_WEB=1`) `open-researcher` 를 띄우지 않고 레포 질문이면 `repo-researcher` 로, 웹 질문이면 「웹이 꺼져 확인하지 못함」을 불확실로 기록한다.
- 출력은 기존 조사 출력과 같은 길을 탄다 — V1(본체가 주장마다 확인) → «지금 이해» → `research_log`.
- 처분 줄: `consumer=orchestrator · fail-closed · disclosure=loud advisory + 본체 직접 조사로 강등`(기존 `repo-researcher` 와 같은 꼴).

**포화 판정의 묶음 단위.** 포화 판정자는 지금 「최근 두 항목 · 시간 순」으로 새로움을 본다(`agents/saturation-judge.md`, `references/saturation.md`). 판정자가 받는 것은 state 본문의 `### 조사 <n> — <장치> · R<round>` 블록뿐이고 `research_log` 는 받지 않으므로, 묶음 표지는 그 블록 머리에 싣는다 — 꼴 `### 조사 <n> — <장치> · R<round> · 묶음 <b>`(정확한 꼴은 계획이 정한다). 동시에 띄운 조사는 같은 `<b>` 를 갖고, 하나만 띄운 조사는 그 하나가 한 묶음이다. 본체 직접 조사 블록(`device: orchestrator`)은 각자 한 묶음이다. 판정자의 「최근 두 항목」은 「최근 두 묶음」으로, 규칙 4 「두 항목 미만이면 `not_saturated`」는 「두 묶음 미만이면」으로 읽는다 — 판정자 persona 편집이므로 보안 리뷰 대상이다(레포 규칙 「Persona 파일은 보안-민감 코드」). `research_log` 항목에도 같은 표지를 둬 상한 계수와 맞춘다.

### §2 호출 세기 · 넉넉한 비상 끝

- **세는 것:** 조사 agent 를 한 번 띄울 때마다 1. 동시에 띄우면 띄운 수만큼. 끝난 agent 를 `SendMessage` 로 이어 부르면 새 조사이므로 1(지휘자 판정). `research_dispatches` 에 `open_researcher` 칸을 더한다.
- **세지 않는 것:** agent 안의 검색 횟수 · 출처 수(원칙 7) · 본체 직접 조사 · 포화 판정자 호출(따로 상한 5).
- **기본값:** `DEVBREW_SPEC_DISTILL_RESEARCH_LIMIT` 의 기본을 20 에서 60 으로(지휘자 판정 — 이유: 필수 자리 둘에 라운드마다 독립 질문 2~4개를 동시에 띄우면 보통 인터뷰가 25~35 회를 쓴다고 보고, 그 두 배쯤의 여유를 둔다. 비상 끝 구실은 하되 조사를 아끼게 만들지 않는 값). 닿으면 멈추고 알리고 그 자리에서 사용자가 연장하는 지금 방식(연장마다 시작값만큼 더함)은 그대로다.
- **안내 문구:** 첫 dispatch 직전 한 줄에서 「웹 포함」을 빼고 「조사 agent 호출」로 쓴다. 꼴: `[spec-distill] 이 인터뷰는 조사 agent 를 최대 <limit>번까지 부른다(agent 안의 검색 · 출처 수는 세지 않는다 · 멈춤은 포화 판정이 정하고 이 수는 비상 끝 · 승인 없이 진행 · 닿으면 연장을 묻는다).` 정확한 문구는 계획이 정한다.
- 숫자 상한 문장을 막는 거버넌스 락(`plugins/quality-gates/tests/test_governance_no_capability_caps.sh` 등)과 부딪히지 않게, 문면은 「기본값 · 비상 끝 · 사용자가 연장」으로 쓴다.

### §3 신선한 근거 — 원칙 여덟

새 reference 파일 `references/fresh-evidence.md` 에 둔다(새 책임은 별도 모듈 · 기존 skill 에는 진입 한 줄). 인터뷰 본체가 조사 주문을 쓸 때와 웹 근거를 받을 때 읽고, `open-researcher` 주문에는 요약을 내용으로 싣는다. 형식 칸을 채우라는 게이트가 아니라 기본 행동이다 — `check_brief` 에 새 실패 조건을 더하지 않는다.

| 원칙(원문) | 설계 |
|---|---|

**웹 근거 칸.** `research-claims.md` 의 `evidence[]` 에 선택 칸 넷을 더한다 — `source_kind: primary | secondary` · `checked_at: <날짜>` · `version: {used, latest}`(기술 주장일 때) · `certainty: confirmed | uncertain`. 없어도 실패하지 않는다. brief §4 항목 줄은 있으면 확인 시점과 출처 종류를 함께 적는다.

**낡은 지식 바로잡기.** 조사가 모델의 앞선 믿음 · 앞 라운드 «지금 이해»를 뒤집으면, 다음 «지금 이해»에 바로잡은 사실을 명시하고 audit 에 앞 믿음을 「대체됨」으로 남긴다 — 잘못된 지식이 활성 맥락에 그대로 남지 않게.

### §4 있는 것 먼저 — 인터뷰 조사의 재사용 검토

무엇을 만들자는 결정이 열리면, 인터뷰는 레포 안의 있는 것(같은 일을 하는 스크립트 · skill · 모듈)을 먼저 찾고, 바깥의 성숙한 것(패키지 · 프레임워크 · 도구)을 웹으로 찾는다. 레포 안 후보는 레포 주장(RC)으로, 바깥 후보는 §4 웹 항목으로 brief 에 싣는다. 바깥 것은 사용자 검토 뒤에만 쓴다 — 인터뷰는 후보와 차이를 보이고 묻는다. 기본은 이렇게 하고, 만들 것이 없는 일(조사 · 결정만)이면 건너뛰고 이유를 적는다.

### §7 분해 판단 · 로드맵 칸 · 끝에서 끝 결함

- **`흐름` · `산출물` 칸.** 분해 판단 표(`finishing.md`)에 `흐름` · `산출물` 칸을 더해 로드맵 생성기가 그 칸을 에픽 블록에 쓰게 한다. 칸의 뜻과 종류별 필수 · 금지는 R5 의 로드맵 모델(`references/roadmap-ontology.md` · `roadmap_model.py` 의 `REQUIRED` · `FORBIDDEN`)을 따른다.
- **조사만 하는 에픽.** 분해 판단의 종류가 묶음 · 브랜치 · 결정뿐이라 조사 에픽이 묶음이 되고 결정은 산출물이 없다. 조사 에픽은 `흐름` 에 조사, `산출물` 에 결과 경로를 적는 꼴로 쓴다. R5 모델에 새 종류가 필요하면 그 모델의 꼴대로 더한다(계획이 모델을 읽고 정한다).
- **위험 번호(K)가 줄 순서라 다시 만들면 엉뚱한 에픽으로 간다(높음).** Step A 에서 brief §5 위험 줄에 `K<n>` 을 박고, `roadmap_model.py` 는 박힌 번호를 읽는다. 박히지 않은 옛 brief 는 줄 순서로 읽되 그 사실을 한 줄 알린다(지휘자 판정 — 이유: 번호는 글 안의 정체여야 지워지거나 옮겨져도 다른 위험에 붙지 않는다).
- **§4 의 레포 주장(RC)을 배정할 수 없다.** `brief_universe` · `index_brief` 가 §4 항목 첫 줄의 `[RC<n> → …]` 도 색인한다(지휘자 판정 — 분해 판단이 배정하라고 하는데 생성기가 거부하는 모순을 없애는 쪽).
- **같은 주제 · 같은 날짜의 새 인터뷰가 끝난 인터뷰의 상태 파일 자리에 내려앉는다.** `state_path.py interview-state` 가 그 자리에 끝난 인터뷰가 있으면 rc 0 이 아닌 값이나 구별되는 줄을 낸다.

### §8 넘겨받은 결함

- **brief §4 의 «».** `check_brief.py` 의 `landscape_unkeyed()` · `landscape_keys_declared()` 가 §4 안의 모든 «» 를 출처 키로 읽어, 강조로 쓴 «» 가 「키를 선언하라」 실패를 낸다 — 사람이 audit §7 에 단어를 키로 더하는 잘못된 수정으로 간다. 키 자리만 읽게 좁히거나, 실패 메시지가 「강조라면 「」로」를 먼저 말하게 한다(어느 쪽인지는 계획이 정한다). 템플릿 §4 에도 한 줄.
- **brief 묶음 rc 3 오탐.** `build_brief_bundle.py` · `build_brief_inline_blob.py` 의 audit 이름 잔존 검사(rc 3)가 다른 인터뷰의 `*.audit.md` 경로 인용에도 발화한다. 자기 audit 파일만 잡게 고친다.
- **request-framing seed 기록 펜스의 zsh 실패.** 펜스가 bash 배열을 써서 zsh 에서 `pairs: assignment to invalid subscript range` 로 멈춘다(R2a 계획 2 담당자 재현). 그 펜스는 기본 브랜치에 없고 R2a 계획 2(`feature/shared-review-engine-core`)에만 있으며, 그 브랜치의 커밋이 이미 배열을 없애고 zsh · bash 3.2 락을 더했다(설계문서 점검이 확인). R10 은 그 브랜치가 머지된 뒤 펜스가 zsh 와 bash 3.2 에서 도는지 확인만 하고, 다시 생겼으면 고친다.

### §10 위험에 대한 답

- **D21(숨은 가정 7 · 실패 양식 7).** 이 에픽이 닿는 것은 K1 · K12 다(위). 나머지는 각 에픽 설계가 답했다.

- **만든 주문이 결론을 유도한다.** 주문에 기대 결론을 싣지 않는다(§1). V1 이 주장마다 확인한다.
- **이름 변경이 다른 에픽과 부딪힌다.** 마지막 계획으로 두고, 머지 직전 기본 브랜치를 합쳐 참조를 다시 찾는다.

## Rejected Alternatives

- **호출을 세지 않고 비상 끝만** — 비상 끝도 무언가를 세야 하고, 「새 사실 없는 호출 연속 N 번」은 포화 판정과 같이 고장 난다. 사용자가 「호출수를 세되 넉넉하게」를 골랐다.
- **검색 횟수 · 출처 수를 세기** — 원칙 7 위반.
- **상한 20 그대로** — 동시 조사에서 금방 닿아 Anti-goal 첫째가 생긴다.
- **내장 `general-purpose` agent 로 만들어 보내기** — 쓰기 · 실행 도구가 있어 레포 규칙(Scoped agents)과 Law 2 에 어긋난다.
- **역할 고정 넷 가운데 하나를 넓히기** — 그 agent 의 계약이 흐려지고, 사용자가 말한 「틀에 갇히게 에이전트를부르는게 아니라」와 맞지 않는다.
- **원칙 여덟을 `check_brief` 게이트로** — 원칙 7 「형식만 채우는 무거운 게이트」.
- **질문 묶기에 본체 직접 조사 상한을 따로 두기** — 라운드 호출이 하나로 남아 라운드 규약이 이미 묶고, 새 상한은 원칙 7 과 부딪힌다.
