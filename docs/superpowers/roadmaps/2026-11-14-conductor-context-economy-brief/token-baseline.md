## 요약

- 이 문서의 표는 세션 기록의 assistant 줄에 적힌 사용량이다. 실제로 쓴 토큰이 아니라 그 하한이다 — 하니스가 스스로 쌓은 누계(`cost-state` 줄)는 같은 세션에서 캐시 읽기가 1.21–1.26배, 새 입력이 약 280배, 출력이 A 에서 2.5배다(«기록에 줄이 없는 사용량»).
- 백업에서 지휘자 skill(`spec-distill:epic-conductor`)을 부른 세션은 셋이고 모두 로드맵 `2026-10-11-persistent-explore-pm-decompose` 의 것으로 골랐다(근거는 «고른 세션»). 셋을 합치면(message.id 로 한 번만 셈) 캐시 읽기 117.6억 · 캐시 쓰기 5.35억 · 새 입력 11.7만 · 출력 2,305만이다.
- 하위 agent 가 입력계(새 입력+캐시 쓰기+캐시 읽기)의 74.9%, 캐시 쓰기의 92.3%, 출력의 72.4% 를 쓴다(출력 몫은 A 의 하위 출력이 덜 적혀 낮게 나온 값이다 — 추정으로는 약 87%, «셀 수 없는 것» 2). 캐시 읽기 비율은 지휘 본체 98.66%, 하위 94.64% 다.
- 지휘 본체는 응답 하나에 평균 약 52만 토큰을 입력으로 다시 읽는다(로드맵 합 522,106 · 지휘자 skill 구간만 보면 534,001). 하위 agent 는 약 18만이다(로드맵 합 184,965).
- 하위 agent 의 캐시 쓰기는 5분 넘게 기다린 뒤의 응답에 몰려 있다. A 하위는 응답의 1.91% 가 캐시 쓰기의 57.4%, C 하위는 0.94% 가 25.4% 다(«5분 넘는 기다림 뒤의 캐시 쓰기»).
- 2.1.296 · 2.1.302 판 하위 기록의 출력은 덜 적혀 있다(아래 «셀 수 없는 것»). 그래서 세션 A 의 하위 출력은 assistant 줄 기준으로도 하한값이다. 판 영향이 없는 세션 C(2.1.310)를 깨끗한 비교 기준으로 쓴다.

### 5분 넘는 기다림 뒤의 캐시 쓰기

하위 agent 의 캐시는 5분, 지휘 본체의 캐시는 1시간 유지된다(위 캐시 TTL). 그보다 오래 기다린 뒤의 응답이 캐시 쓰기를 얼마나 차지하는지 쟀다.

규칙:

1. 단위는 기록 파일 하나다(지휘 본체, 또는 하위 agent 하나). 파일 안의 응답을 그 응답 첫 줄의 timestamp 순으로 놓는다. 시각이 같으면 기록에 먼저 나온 응답이 앞이다.
2. 이 응답의 첫 줄 시각에서 바로 앞 응답의 첫 줄 시각을 뺀 값이 문턱을 넘으면 «기다림 뒤 응답» 이고, 그 응답의 캐시 쓰기를 더한다. 파일의 첫 응답은 앞 응답이 없어 넣지 않는다.
3. 분모는 그 묶음 전체다 — 응답 비율은 묶음의 응답 수(첫 응답 포함), 캐시 쓰기 비율은 묶음의 캐시 쓰기 합.
4. 문턱은 캐시 TTL 에 맞춘다. 하위는 300초, 지휘 본체는 3,600초다.

| 묶음 | 문턱 | 기다림 뒤 응답 | 응답 비율 | 그 응답의 캐시 쓰기 | 묶음 캐시 쓰기의 |
|---|---|---|---|---|---|
| A 하위 | 300초 | 859 / 44,891 | 1.91% | 264,192,694 | 57.4% |
| C 하위 | 300초 | 46 / 4,897 | 0.94% | 8,569,081 | 25.4% |
| A 지휘 본체 | 3,600초 | 39 / 4,688 | 0.83% | 17,903,009 | 56.2% |
| C 지휘 본체 | 3,600초 | 11 / 1,228 | 0.90% | 6,090,031 | 64.4% |

문턱을 바꿔 잰 값: 하위를 3,600초로 재면 A 34개 · 14,662,165(3.2%), C 2개 · 657,462(1.9%)다. 지휘 본체를 300초로 재면 A 359개 · 19,447,698(61.1%), C 90개 · 6,375,964(67.4%)다. B 는 응답 4개에 기다림이 없다.

읽을 때 주의:

- 기다림의 대부분은 끝낸 agent 를 다시 깨운 것으로 읽힌다. A 하위의 기다림 뒤 응답 859개를 바로 앞 응답이 부른 도구로 나누면, 도구를 부르지 않은 경우(그 응답으로 agent 의 차례가 끝났다고 본다)가 350개 · 캐시 쓰기 146,089,460(A 하위 캐시 쓰기의 31.8%), SubagentHandback 만 부른 경우가 153개 · 44,676,221(9.7%)이다. 둘을 합치면 503개 · 190,765,681 로 기다림 뒤 캐시 쓰기의 72.2% 다. 도구가 오래 돈 쪽인 Bash 만 부른 경우는 303개 · 60,776,126(13.2%)이다. C 하위는 도구 없음 14개 · 3,973,229(11.8%), Bash 16개 · 2,609,695(7.7%), SubagentHandback 5개 · 893,396(2.6%)이다.
- 시각은 요청을 보낸 때가 아니라 응답 첫 줄이 기록된 때다. 그래도 A 하위의 859개 가운데 797개는 캐시 읽기가 캐시 쓰기보다 작고(캐시를 거의 못 읽었다) 그 캐시 쓰기 합이 263,890,373 이다. 앞 응답의 마지막 줄 시각부터 재도 A 는 842개 · 261,234,792(56.8%), C 는 45개 · 8,564,833(25.3%)이라 결론이 같다.
- agent 가 새로 뜰 때의 캐시 쓰기는 이 값에 없다. 파일 첫 응답의 캐시 쓰기는 A 47,263,731(A 하위의 10.3%) · C 6,228,554(18.4%)이고, 첫 응답이 캐시에서 아무것도 읽지 못한 agent 가 A 1,411개 중 465개 · C 157개 중 131개다.
- 응답의 2% 가 캐시 쓰기의 절반을 넘는 것은 A 하위에만 맞는다. C 하위는 0.94% 가 25.4% 다.
- 이 값도 assistant 줄에 적힌 캐시 쓰기다(«기록에 줄이 없는 사용량»).

## 기록에 줄이 없는 사용량

세션 본체 기록에는 `cost-state` 줄이 있다. 하니스가 그 세션에서 쓴 사용량을 스스로 쌓은 누계다(`modelUsage` — 모델별, 하위 agent 포함). 그 마지막 값을 이 문서의 값(지휘 본체+하위의 assistant 줄 합)과 견줬다. sdk 세션은 별도 세션이라 assistant 줄 쪽에 넣지 않았다.

A 의 `cost-state` 는 값이 셋이다. 첫 값은 지휘자 skill 첫 호출 직전(2026-10-18T14:06:38Z)이라 «지휘 전» 구간의 하니스 누계가 된다 — 캐시 읽기 4,683,354,440 · 캐시 쓰기 200,753,203 · 새 입력 9,252,299 · 출력 16,595,511. 같은 때까지의 assistant 줄 합(A 지휘 전의 지휘+하위)은 3,758,616,428 · 193,853,127 · 35,784 · 5,868,563 이다. 캐시 읽기 배수는 세 값에서 1.246 · 1.260 · 1.255 다.

이 대조의 뜻:

- 이 문서의 모든 표는 세션 기록의 assistant 줄에 적힌 사용량이다. 기록에 줄이 남지 않은 사용량은 들어 있지 않다. 그래서 실제 사용량의 하한이다.
- B 는 네 칸이 정확히 같다. message.id 로 한 번만 세고 되풀이 줄의 큰 값을 쓰는 규칙이 하니스의 셈과 맞는다는 데이터 쪽 근거다.
- 차이는 일의 양을 따라 간다. 도구 호출 하나당 캐시 읽기 차이가 A 의 세 값에서 44,280 · 45,039 · 43,853, C 에서 39,186 이다. 새 입력 차이는 A 441 · 436 · 473, C 553 이다. 출력 차이는 C 에서 도구 호출당 9.2 다(A 는 하위 출력이 덜 적힌 것과 섞여 449.5 다).
- 모델별 캐시 읽기 배수는 A 에서 opus 1.249 · sonnet 1.315 · haiku 1.249 다. C 의 하니스 누계에는 지휘 본체와 하위 기록 어디에도 assistant 줄이 없는 모델(claude-haiku-5-5 — 새 입력 1,872 · 출력 345)이 있다. 기록에 줄을 남기지 않는 요청이 있다는 것까지는 이것으로 확인된다.
- 원인은 확인하지 못했다. 추측(확인 안 함): 도구 호출마다 붙는, 기록에 assistant 줄을 남기지 않는 곁 요청이 있다. 그것이 무엇인지는 모른다. 참고로 C 의 기록에는 요청 줄(`api-request`)이 지휘 본체 1,322 · 하위 4,954 개, 응답이 1,228 · 4,897 개다.
- sdk 세션이 하니스 누계에 드는지도 확인하지 못했다. C 에서는 캐시 쓰기 · 출력의 차이(1,360,609 · 68,870)가 C 에 붙은 sdk 세션의 값(1,311,588 · 63,004)과 비슷하다. A 에서는 맞지 않고(캐시 쓰기 차이 29,102,626 대 sdk 21,775,613), 캐시 읽기와 새 입력의 차이는 어느 세션에서도 sdk 값으로 설명되지 않는다.

영향:

- 요약의 합계는 기록된 줄의 합이다. 새 입력 칸은 응답당 약 2 토큰이라 실제 새 입력에 대해 알려 주는 것이 거의 없다.
- 줄이 없는 부분은 지휘와 하위로 가를 수 없다. 하위 몫과 캐시 읽기 비율도 그만큼 불확실하다.
- 차이가 도구 호출 수를 따라가므로, 재설계가 도구 호출 수를 바꾸면 이 부분은 기록 밖에서 움직인다. 그래서 R5 는 두 값(assistant 줄 합 · 하니스 누계)을 함께 재서 견준다(`harness_total.py`).
- 하니스 누계도 하한일 수 있다. 비정상 종료 때 `cost-state` 가 사용량을 잃는지 확인하지 못했다. 누계가 든 `cost-state` 줄이 없는 세션은 견줄 수 없어 스크립트가 멈춘다.

## 측정 방법

### 집계 규칙

1. 단위: 응답 하나 = assistant 줄의 `message.id`. 같은 id 는 범위 전체(지휘 본체 · 하위 · sdk 파일)에서 한 번만 센다 — 세션 기록은 content block 마다 같은 usage 를 되풀이 적는다(«cc-issue-87303»).
2. 되풀이 줄의 usage 가 서로 다르면 칸마다 큰 값을 쓴다. 실측에서 다른 칸은 `output_tokens` 하나뿐이었고(범위 전체의 되풀이 줄 54,943개 가운데 값이 달랐던 줄이 7,369개) 큰 값은 늘 마지막 줄의 값과 같았다.
3. 네 종류: 최상위 `usage` 의 `input_tokens`(새 입력) · `cache_creation_input_tokens`(캐시 쓰기) · `cache_read_input_tokens`(캐시 읽기) · `output_tokens`(출력).
4. 지휘 본체 = 세션 jsonl 하나. 하위 = `<세션 id>/subagents/agent-*.jsonl` 전부(중첩 포함). sdk = 위 «따로 센 것» 의 규칙. 이 규칙은 «세션 jsonl 하나 + 그 세션의 `subagents/` 폴더» 구조를 전제한다(«이 기준선을 쓸 때»).
5. 세지 않는 것: model `<synthetic>` 줄(usage 0, 2줄). usage 는 있는데 message.id 가 없는 줄 · usage 가 없는 assistant 줄 · JSON 으로 읽히지 않는 줄은 0줄이었고, 0 이 아니면 스크립트가 멈춘다.
6. 캐시 읽기 비율 = 캐시 읽기 / (새 입력+캐시 쓰기+캐시 읽기).
7. 세션 고르기: 본체 jsonl 의 user 줄에 `<command-name>/spec-distill:epic-conductor</command-name>` 가 있거나 assistant 의 Skill 도구 입력 `skill` 이 그 이름인 세션(백업에서 Skill 도구 호출은 0 이었다). 지휘 표지 보조 검사로 `conductor_state.py` · `conductor_ledger.py` Bash 호출과 `attributionSkill` 도 훑었다(«뺀 것»).
8. A 의 지휘 전 · 뒤는 응답 timestamp 가 첫 호출 시각(2026-10-18T14:07:47Z)보다 앞인지로 가른다.

중복 제거의 효과: A+B+C 본체+하위를 줄마다 그냥 더하면 108,415줄에서 캐시 읽기 23,039,715,167 · 출력 42,532,601 이 나온다. 중복 제거 값(55,708 응답)의 1.96배 · 1.84배다.

### 실행 방법

스크립트는 이 문서 옆 `token-baseline/` 폴더에 있다. 플러그인 코드가 아니라 이 측정을 다시 하기 위한 것이다. 모두 백업을 읽기만 하고 결과를 표준 출력에 JSON 으로 낸다(`table.py` 만 표를 낸다). 출력 파일은 레포에 두지 않는다 — 아래처럼 레포 루트에서 돌려 레포 밖 임시 폴더에 받는다.

```
B=~/.claude/transcript-backup/devbrew-2026-11-14
S=docs/superpowers/roadmaps/2026-11-14-conductor-context-economy-brief/token-baseline
O="$(mktemp -d)"
python3 -I "$S/select_sessions.py" --backup "$B" --needle 2026-10-11-persistent-explore-pm-decompose > "$O/select_sessions.json"
python3 -I "$S/measure.py" --backup "$B" > "$O/measure.json"
python3 -I "$S/table.py" "$O/measure.json" > "$O/table.md"
python3 -I "$S/extra.py" --backup "$B" > "$O/extra.json"
python3 -I "$S/naive.py" --backup "$B" > "$O/naive.json"
python3 -I "$S/ver.py" --backup "$B" > "$O/ver.json"
python3 -I "$S/branch.py" --backup "$B" --session C > "$O/branch.json"
python3 -I "$S/gap.py" --backup "$B" > "$O/gap.json"
python3 -I "$S/gap_tools.py" --backup "$B" > "$O/gap_tools.json"
python3 -I "$S/harness_total.py" --backup "$B" > "$O/harness_total.json"
```

| 파일 | 내는 값 |
|---|---|
| `sessions.json` | 설정 — 지휘자 skill 이름, 세션 기호와 세션 id, 첫 호출에서 가를 세션, 하위 출력이 덜 적힌 판 범위, 보조 표지 스크립트 이름. 프로젝트 폴더는 적지 않는다(세션 id 로 백업에서 찾는다) |
| `baseline_lib.py` | 스크립트가 함께 쓰는 읽기 규칙(규칙 1–5 · 7)과 가드 |
| `select_sessions.py` | 규칙 7 로 고른 세션(`selected`)과 보조 표지 — «고른 세션» 의 호출 수 · 폴더 이름이 든 줄 수, «뺀 것» 의 표지 수. 명령 인자는 길이만 낸다 |
| `measure.py` | 세션별 지휘 · 하위 · sdk 집계, 지휘 전 · 뒤, 직접 대 중첩(중첩 캐시 읽기 합 포함), agent 종류별, agent 하나당 입력계, «(지정 없음)» 이 실제로 돈 종류, 모델, 판, TTL, 압축 수 |
| `table.py` | measure 출력으로 «세션별» · «로드맵 합» · 하위 몫 · sdk · 종류별 표와 «하위 agent 의 결» 의 한 줄 값들 |
| `extra.py` | 되풀이 줄에서 다른 칸과 큰 값 = 마지막 줄 여부(규칙 2), 백업 전체의 분류별 파일 수와 합(«뺀 것» 의 수), 뺀 sdk 세션이 돈 worktree |
| `naive.py` | 중복 제거 없는 합, 가른 세션의 지휘 전 · 뒤 skill 귀속 |
| `ver.py` | 판별 응답당 출력 · 출력 5 이하 비율 · stop_reason 빈 비율(«셀 수 없는 것» 2) |
| `branch.py` | 한 세션의 gitBranch 별 합(C 의 8개) |
| `gap.py` · `gap_tools.py` | «5분 넘는 기다림 뒤의 캐시 쓰기» 의 표와 «읽을 때 주의» 의 값 |
| `harness_total.py` | «기록에 줄이 없는 사용량» 의 표와 도구 호출당 차이 · 모델별 배수 |

조용히 틀릴 수 있는 자리에서는 스크립트가 멈춘다. 아래 가운데 하나라도 0 이 아니면 그 수를 표준 오류에 내고 종료 코드 3 으로 끝나며 결과를 내지 않는다.

- JSON 객체로 읽히지 않는 줄(잘린 마지막 줄 포함) · UTF-8 이 아닌 파일. 줄을 문자열로 먼저 거르지 않고 모두 JSON 으로 읽는다.
- usage 가 없는 assistant 줄 · usage 는 있는데 message.id 가 없는 줄.
- usage 의 네 칸 가운데 없거나 숫자가 아닌 칸. 칸이 있고 값이 0 인 것은 정상이다.
- 두 파일에 걸친 message.id.
- `<세션 id>/subagents/agent-*.jsonl` 이 아닌 자리의 하위 기록(더 깊은 폴더 · 다른 이름), 백업 안 모르는 자리의 jsonl.
- 어느 Agent 결과에도 연결되지 않은 하위 agent.
- 지휘자 skill 호출을 찾지 못한 설정 세션, timestamp 가 없는 호출 줄.
- 캐시 쓰기가 1시간 몫 + 5분 몫과 다른 줄.
- agent worktree 폴더의 세션인데 entrypoint 가 `sdk-py` 가 아닌 것.
- timestamp 가 없는 응답 줄. 시각으로 지휘 전 · 뒤와 기다림을 가르므로 시각이 없으면 조용히 «지휘 전» 으로 떨어진다.
- `harness_total.py`: 누계가 든 `cost-state` 줄이 없는 세션, 응답이 이미 있는데 `modelUsage` 가 빈 `cost-state` 줄, 모델별 누계의 네 칸 가운데 없거나 숫자가 아닌 칸.

재측정(R5) 때는 `--backup` 과 `sessions.json` 의 세션 id · 가를 세션을 바꾼다. 세션 구조가 바뀌었으면 먼저 귀속 규칙을 다시 정한다(«이 기준선을 쓸 때»).

## 셀 수 없는 것

없는 것(0)과 못 센 것을 가른다.

1. 2026-10-15 이전에 끝난 이 로드맵의 세션 — 로드맵은 2026-10-11 에 시작했다. 기록이 정리 기간(cleanupPeriodDays 기본 30일)에 지워져 몇 개인지 셀 수 없다. A 만 마지막 수정이 10-25 라 10-12 부터 남았다. 백업 파일의 가장 이른 수정 날짜는 2026-10-12(현지 날짜로 14개)로, RC151 의 「가장 오래 남은 세션 기록은 2026-10-15」 와 다르다. 그때 무엇을 기준으로 셌는지는 확인하지 못했다.
2. A 하위 출력의 참값 — 2.1.296 · 2.1.302 판 하위 응답 41,427개(A 하위의 92.3%)는 stop_reason 이 빈 비율이 72–79%, 출력 5 이하 비율이 17–18% 이고 응답당 출력이 224–261 이다. 같은 기록 형식의 2.1.310 하위는 이 비율이 0%, 응답당 출력이 770.5 다. 조사 14 의 「2.1.293–2.1.306 하위 출력 과소」 가 이 백업에서도 보인다(이 백업의 지휘 본체 · 하위 기록에서 그 범위에 드는 판은 2.1.296 · 2.1.302 둘이다). 그래서 A 하위 출력 12,646,930 은 하한값이다. 같은 판의 지휘 본체는 stop_reason 빈 비율 0% 로 영향이 보이지 않는다. 새 입력 · 캐시 칸은 영향이 없다는 것이 공식 cost-tracking 문서의 설명이다(조사 14). 이 백업에서는 따로 검증하지 않았다. 참고 추정 둘(기준선 값으로 쓰지 않는다):
   - 하니스 누계에서 빼기 — A 의 하니스 누계 출력 44,885,078 에서 지휘 본체 출력 5,119,642 와 줄이 없는 요청의 몫 약 56만을 빼면 A 하위 출력은 약 3,920만이다. 줄이 없는 요청의 몫은 C 의 도구 호출당 출력 차이 9.2 를 A 의 도구 호출 60,337번에 곱한 값이다. 가정은 둘이다 — 지휘 본체의 출력은 줄에 적힌 그대로이고, 줄이 없는 요청의 출력은 A 에서도 C 와 같은 비율이다. 이 추정으로는 로드맵 합의 하위 출력 몫이 72.4% 가 아니라 약 87% 다.
   - 2.1.310 평균으로 채우기 — 덜 적힌 응답 41,427개가 2.1.310 하위의 응답당 출력 770.5 를 따랐다면 약 3,430만이다. A 자신의 누계에서 나온 위 값보다 낮아서, 이 방법은 낮게 잡는다고 본다.
3. 기록에 줄이 없는 사용량 — 하니스 누계와의 차이만큼이 assistant 줄에 없다. 지휘와 하위로 가를 수 없고 원인도 확인하지 못했다(«기록에 줄이 없는 사용량»).
4. 다른 모델(codex) 호출의 토큰 — 지휘 중 리뷰가 codex 를 불러도 그 사용량은 Claude 세션 기록에 없다. 이 조사의 재료로는 셀 수 없다.
5. 비용(USD) — `cost-state` 에 하니스가 셈한 비용(`totalCostUSD`)이 있지만 청구액인지 확인하지 않았고, 단가 환산은 이 조사의 범위가 아니라 내지 않았다.

없는 것(0 으로 확인): message.id 없는 usage 줄 0 · usage 없는 assistant 줄 0 · JSON 깨진 줄 0 · 파일 사이 같은 id 겹침 0 · 연결 안 된 하위 agent 0 · `subagents/agent-*.jsonl` 밖의 하위 기록 0 · 캐시 쓰기가 1시간 몫 + 5분 몫과 다른 줄 0 · usage 네 칸이 없거나 숫자가 아닌 줄 0 · timestamp 없는 응답 줄 0 · usage 가 하나도 없는 하위 파일 0 · advisor 등 여러 번 돈 `usage.iterations` 0. 마지막 둘을 뺀 나머지는 0 이 아니면 스크립트가 멈춘다.

## 이 기준선을 쓸 때

- 표의 값은 assistant 줄에 적힌 사용량이고 실제 사용량의 하한이다. 전후를 견줄 때는 assistant 줄 합끼리, 하니스 누계끼리 따로 견주고, 둘 사이의 배수가 달라졌는지도 본다(«기록에 줄이 없는 사용량»).
- 판 · 날짜 · 범위가 붙은 값이다. 2026-10 의 Claude Code 2.1.296–2.1.310 에서 지휘한 로드맵 하나다. 근거로 쓰기 전에 비교 대상의 판과 범위가 같은지 먼저 확인한다(C22).
- 세션 구조를 전제한 값이다. 규칙 4 · 7 은 «지휘 세션 jsonl 하나 + 그 세션의 `subagents/` 폴더» 를 전제한다. 일꾼이 별도 세션으로 뜨는 구조로 바뀌면 같은 규칙으로 재도 일꾼 몫이 빠져 가짜 절감이 나온다. 그때는 어느 세션이 이 로드맵의 것인지 정하는 귀속 규칙을 먼저 다시 정하고 잰다. 이 조사도 같은 문제를 한 번 겪었다 — sdk 세션은 지휘 세션 id 와 연결되지 않아 cwd 로 붙였다(«따로 센 것»).
- 재설계 뒤 비교는 같은 규칙으로 잰다. 출력은 C 나 2.1.307 이상 판끼리만 비교하고, A 를 포함한 합은 입력계와 캐시 칸으로 비교한다.
- 일의 양이 로드맵마다 다르므로 합계보다 응답당 입력계(지휘는 로드맵 합 약 52만 · 지휘자 skill 구간 약 53만, 하위는 로드맵 합 약 18만 · C 약 16만) · 하위 몫 · 캐시 읽기 비율 · agent 하나당 입력계(«하위 agent 의 결») · 5분 넘는 기다림 뒤의 캐시 쓰기 비율을 함께 본다.
- 응답당 입력계의 분모는 기록에 남은 응답 수라서 도구 걸음이 잘게 많은 agent 일수록 값이 작아지고, 캐시 읽기 비율은 걸음이 많을수록 오른다(B 의 77.37% 는 응답이 4개라서다). 둘 다 품질 지표가 아니다.
- 원시 토큰 수는 리프레시 문턱이 아니다(D11). 이 문서는 문턱을 정하지 않는다.

## Acceptance Criteria

- AC1: 로드맵 지휘 세션을 기록의 호출 흔적으로 고르고, 고른 기준 · 뺀 것을 숫자와 함께 적는다 — «고른 세션» · «집계 규칙» 7 · «뺀 것».
- AC2: 지휘 본체와 하위 agent 를 갈라 네 종류 토큰과 캐시 읽기 비율을 세션별 · 로드맵별로 낸다 — «세션별 · 지휘 대 하위» · «로드맵 합».
- AC3: 응답은 message.id 로 한 번만 세고, 되풀이 수와 불일치 처리를 공시한다 — «집계 규칙» 1–2 · 중복 제거의 효과.
- AC4: 없는 것(0)과 셀 수 없는 것을 가른다 — «셀 수 없는 것». 표의 값이 실제 사용량의 하한이라는 것도 여기에 든다(«기록에 줄이 없는 사용량»).
- AC5: 재현할 수 있게 집계 규칙과 실행 방법을 적되 측정 도구를 제품화하지 않는다 — «측정 방법». 스크립트는 플러그인 코드가 아니고 이 문서 옆 `token-baseline/` 에 둔다(사용자 결정 2026-11-14: 레포에 남긴다).
- AC6: 백업 폴더는 읽기만 한다 — 스크립트는 읽기 모드로만 연다. 측정 뒤에도 파일 2,579개 · 3.5G 그대로다.
- AC7: 세션 기록에서 온 사용자 원문 · 대화 내용 · 비밀을 싣지 않는다 — 기록에서 가져온 것은 세션 id · 날짜 · 숫자 · 레포 식별자(worktree · 브랜치 · skill · agent 종류 이름)뿐이다. 꺾쇠 인용은 이미 추적되는 묶음(P1.md)의 글이다. 스크립트도 사용자가 친 글을 내지 않는다(명령 인자는 길이만).
- AC8: 레포 안 토큰 측정 수단을 지금 코드에서 다시 확인한다 — «있는 것 검토».
- AC9: 묶음 ids 19개를 모두 대조한다 — «번호 대조».
