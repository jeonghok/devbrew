# P1 — 토큰 기준선

재설계 전 로드맵 지휘 세션과 그 하위 agent 의 토큰을 갈라 잰 값이다. 재설계 뒤(R5) 같은 규칙으로 다시 재어 이 표와 비교한다.

## 요약

- 백업에서 지휘자 skill(`spec-distill:epic-conductor`)을 부른 세션은 셋이고 모두 같은 로드맵 `2026-10-11-persistent-explore-pm-decompose` 를 지휘했다. 셋을 합치면(message.id 로 한 번만 셈) 캐시 읽기 117.6억 · 캐시 쓰기 5.35억 · 새 입력 11.7만 · 출력 2,305만이다.

## 측정 방법

### 집계 규칙

1. 단위: 응답 하나 = assistant 줄의 `message.id`. 같은 id 는 범위 전체(지휘 본체 · 하위 · sdk 파일)에서 한 번만 센다 — 세션 기록은 content block 마다 같은 usage 를 되풀이 적는다(«cc-issue-87303»).
2. 되풀이 줄의 usage 가 서로 다르면 칸마다 큰 값을 쓴다. 실측에서 다른 칸은 `output_tokens` 하나뿐이었고(되풀이 줄 7,369개) 큰 값은 늘 마지막 줄의 값과 같았다.
3. 네 종류: 최상위 `usage` 의 `input_tokens`(새 입력) · `cache_creation_input_tokens`(캐시 쓰기) · `cache_read_input_tokens`(캐시 읽기) · `output_tokens`(출력).
4. 지휘 본체 = 세션 jsonl 하나. 하위 = `<세션 id>/subagents/agent-*.jsonl` 전부(중첩 포함). sdk = 위 «따로 센 것» 의 규칙.
5. 세지 않는 것: model `<synthetic>` 줄(usage 0, 2줄), usage 는 있는데 message.id 가 없는 줄(0줄), JSON 으로 읽히지 않는 줄(0줄).
6. 캐시 읽기 비율 = 캐시 읽기 / (새 입력+캐시 쓰기+캐시 읽기).
7. 세션 고르기: 본체 jsonl 의 user 줄에 `<command-name>/spec-distill:epic-conductor` 가 있거나 assistant 의 Skill 도구 입력 `skill` 이 그 이름인 세션. 지휘 표지 보조 검사로 `conductor_state.py` · `conductor_ledger.py` Bash 호출과 `attributionSkill` 도 훑었다(«뺀 것»).
8. A 의 지휘 전 · 뒤는 응답 timestamp 가 첫 호출 시각(2026-10-18T14:07:47Z)보다 앞인지로 가른다.

중복 제거의 효과: A+B+C 본체+하위를 줄마다 그냥 더하면 108,415줄에서 캐시 읽기 23,039,715,167 · 출력 42,532,601 이 나온다. 중복 제거 값(55,708 응답)의 1.96배 · 1.84배다.

## 셀 수 없는 것

없는 것(0)과 못 센 것을 가른다.

1. 2026-10-15 이전에 끝난 이 로드맵의 세션 — 로드맵은 2026-10-11 에 시작했다. 기록이 정리 기간(cleanupPeriodDays 기본 30일)에 지워져 몇 개인지 셀 수 없다. A 만 마지막 수정이 10-25 라 10-12 부터 남았다. 백업 파일의 가장 이른 수정 시각은 2026-10-12(14개)로, RC151 의 「가장 오래 남은 기록 2026-10-15」 와 다르다. 그때 무엇을 기준으로 셌는지는 확인하지 못했다.
2. A 하위 출력의 참값 — 2.1.296 · 2.1.302 판 하위 응답 41,427개(A 하위의 92.3%)는 stop_reason 이 빈 비율이 72–79%, 출력 5 이하 비율이 17–18% 이고 응답당 출력이 224–261 이다. 같은 기록 형식의 2.1.310 하위는 이 비율이 0%, 응답당 출력이 770.5 다. 조사 14 의 「2.1.293–2.1.306 하위 출력 과소」 가 이 백업에서도 보인다. 그래서 A 하위 출력 12,646,930 은 하한값이다. 참고 추정: 그 응답들이 2.1.310 평균을 따랐다면 A 하위 출력은 약 3,430만이다(기준선 값으로 쓰지 않는다). 같은 판의 지휘 본체는 stop_reason 빈 비율 0% 로 영향이 보이지 않는다. 새 입력 · 캐시 칸은 영향이 없다는 것이 공식 cost-tracking 문서의 설명이다(조사 14). 이 백업에서는 따로 검증하지 않았다.

## 이 기준선을 쓸 때

- 판 · 날짜 · 범위가 붙은 값이다. 2026-10 의 Claude Code 2.1.296–2.1.310 에서 지휘한 로드맵 하나다. 근거로 쓰기 전에 비교 대상의 판과 범위가 같은지 먼저 확인한다(C22).
- 재설계 뒤 비교는 같은 규칙으로 잰다. 출력은 C 나 2.1.307 이상 판끼리만 비교하고, A 를 포함한 합은 입력계와 캐시 칸으로 비교한다.
- 일의 양이 로드마다 다르므로 합계보다 응답당 입력계(지휘 약 53만 · 하위 약 16–18만) · 하위 몫 · 캐시 읽기 비율 · agent 하나당 입력계를 함께 본다.

## Acceptance Criteria

- AC1: 로드맵 지휘 세션을 기록의 호출 흔적으로 고르고, 고른 기준 · 뺀 것을 숫자와 함께 적는다 — «고른 세션» · «집계 규칙» 7 · «뺀 것».
- AC2: 지휘 본체와 하위 agent 를 갈라 네 종류 토큰과 캐시 읽기 비율을 세션별 · 로드맵별로 낸다 — «세션별 · 지휘 대 하위» · «로드맵 합».
- AC3: 응답은 message.id 로 한 번만 세고, 되풀이 수와 불일치 처리를 공시한다 — «집계 규칙» 1–2 · 중복 제거의 효과.
- AC4: 없는 것(0)과 셀 수 없는 것을 가른다 — «셀 수 없는 것».
- AC5: 재현할 수 있게 집계 규칙과 실행 방법을 적되 측정 도구를 제품화하지 않는다 — «측정 방법». 스크립트는 레포 밖 일회용이다.
- AC6: 백업 폴더는 읽기만 한다 — 스크립트는 읽기 모드로만 연다. 측정 뒤에도 파일 2,579개 · 3.5G 그대로다.
- AC7: 사용자 원문 · 대화 내용 · 비밀을 싣지 않는다 — 세션 id · 날짜 · 숫자 · 레포 식별자만 실었다.
- AC8: 레포 안 토큰 측정 수단을 지금 코드에서 다시 확인한다 — «있는 것 검토».
- AC9: 묶음 ids 19개를 모두 대조한다 — «번호 대조 표».
