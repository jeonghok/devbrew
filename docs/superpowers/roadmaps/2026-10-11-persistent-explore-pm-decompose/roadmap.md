## 지휘 절차

R5 전까지 지휘 세션이 따르는 절차다. 장치가 아니라 절차다 — 지휘자 skill 은 R5 가 만든다. 지휘 세션은 `/new` 뒤 첫 줄에 `@docs/superpowers/roadmaps/2026-10-11-persistent-explore-pm-decompose/roadmap.md` 를 붙여 연다.

1. `git fetch origin` → `python3 plugins/spec-distill/scripts/control_plane.py show --tasks docs/superpowers/roadmaps/2026-10-11-persistent-explore-pm-decompose/roadmap.md` → 작업 목록을 결과에 맞춘다. 줄마다 `<제목><탭><작업 상태>` 이고 에픽 하나에 작업 하나다 — 제목은 그대로 쓰고, 상태가 `keep` 이면(알 수 없음) 작업 상태는 바꾸지 않고 제목만 바꾼다. 종료 코드가 3 이면 작업 목록을 바꾸지 않고 표준 오류의 「검사 불가」 사유를 사용자에게 그대로 보인다 — 일부 단계가 계산돼 보여도 믿지 않는다. 로드맵이 아직 origin/main 에 없으면(방금 분해해 머지 전) `python3 plugins/spec-distill/scripts/roadmap_status.py --roadmap-file <로드맵 경로>` 로 대신 계산하고, 대기 · 준비는 시작 전, 설계 중 · 계획은 진행 중, 머지됨 · 끝남은 완료로 맞춘다.
2. 준비 단계 에픽을 고른다. 블록의 `브랜치:` 이름으로 `origin/main` 에서 브랜치와 worktree 를 먼저 만들고, 그 에픽의 설계문서 · 계획은 모두 그 브랜치에 커밋한다. 설계 흐름의 에픽이면 설계 단계(brainstorming → 설계문서 → spec-review 승인)는 이 세션에서 한 에픽씩 돈다(흐름을 고르는 일과 어느 세션에서 여는지는 3) — spec 승인은 사용자가 에픽마다 한다. 상태를 git 에서 계산하므로 에픽마다 세션을 따로 열어 설계(brainstorming)도 병렬로 할 수 있다 — 한 세션 안에서는 한 에픽씩이다(실측 M1).
3. 에픽의 흐름은 기본이 설계 흐름(brainstorming → spec-review → 계획 → 구현)이다. 조사 · 측정 · 결정처럼 그 흐름과 맞지 않는 에픽은 모델이 맞는 흐름을 고르되, 시작하기 전에 고른 흐름 · 이유 · 산출물을 사용자에게 보이고 `AskUserQuestion` 으로 승인을 받는다 — 설계 흐름의 spec 승인을 대신하는 자리이고, 거절되면 설계 흐름으로 돌아간다(「이게 앞으로의 원칙이야」 — 흐름 고정 점검 문서). 설계 흐름의 에픽은 그 에픽의 worktree 에서 `/new` 로 연 세션이 `plugins/spec-distill/references/epic-handoff.md` 의 에픽 넘김 줄(자리표를 채우고, `${CLAUDE_PLUGIN_ROOT}` 는 `<에픽 worktree>/plugins/spec-distill`)로 시작한다 — 그 줄이 그 세션을 spec 승인 · 계획 · 구현 · PR 까지 끌고 간다. 지휘 세션이 직접 설계할 때는 spec 승인까지만 하고, 승인 게이트가 낸 다음 세션 줄은 에픽 worktree 의 새 세션으로 보낸다 — 지휘 세션은 계획 · 구현으로 들어가지 않는다(5). 설계문서를 커밋한 뒤 spec-review 를 설계문서 경로 뒤에 `--bundle <묶음>` 을 붙여 부른다 — `<묶음>` 은 설계문서 frontmatter `source_interview` 와 같은 레포 상대경로다. 그 값이 다르거나 읽을 수 없으면 spec-review 는 리뷰하지 않고 끝난다. 같으면 진입에서 번호 대조를 보이고 리뷰를 계속한다 — 빠진 번호 · 얕은 답 · 받드는 에픽 없는 발화 · 검사 불가는 막지 않고 승인 게이트의 「경고 N개」에 더해지며, 고칠지는 그 게이트에서 사용자가 정한다. 계획을 쓴 뒤 `python3 plugins/spec-distill/scripts/check_bundle_coverage.py --plan <설계문서> <계획>` 을 돌려 계획에 없는 AC 를 계획에 더한다. 고른 실행 방식의 마지막 전체 리뷰가 AC 마다 한 줄(`AC1: 구현됨 — 근거` 꼴, 판정은 구현됨 · 미룸 · 빠짐)로 보고하게 해 그 보고를 git 이 추적하지 않는 파일(실행 방식의 작업 폴더)에 적고, 미룸 · 빠짐과 리뷰 후속으로 미룬 것은 설계문서 `## 미룸` 표(항목 · 이유 · 받는 곳)에 올린 뒤, PR 을 만들기 전에 `python3 plugins/spec-distill/scripts/check_bundle_coverage.py --impl <설계문서> <그 보고 파일>` 을 돌려 경고를 사용자에게 보인다.
4. superpowers 가 묻는 세 자리는 미리 받은 답으로 간다(S36 재결정 「미리 답해 둠 (권장)」) — 계획 검토는 계획 경로를 보이되 기다리지 않고, 실행 방식은 writing-plans 가 계획을 마치며 권하는 방식이고, 머지 메뉴는 Push 후 PR 이다(실행 방식 — 사용자 「…subagent driven이라고 되어있는걸 권장 구현 방식으로 간다고 해둬」). spec 승인은 에픽마다 사용자가 한다. 사용자가 그 자리에서 다르게 말하면 그 말을 따른다.
5. 구현은 에픽마다 worktree 에서 돌리고 그동안 다음 에픽의 설계를 진행하는 것이 목표다. 백그라운드 실행이 되는지는 실측 M1 이 정한다 — 안 되면 구현도 순차로 하고 그 사실을 알린다. 실행 방식(SDD 등)이 마지막 메시지로 내는 판정 목록(「Rulings I made」 등)은 그대로 사용자에게 보이고 멈추지 않는다.
6. 에픽이 머지될 때마다 남은 에픽을 재평가하고, 바뀔 때만 사용자 승인 뒤 로드맵 수정을 전용 작은 브랜치(`feature/roadmap-<요지>`)와 PR 로 올린다. 머지는 사용자가 한다.
7. 구현 커밋에는 `Spec: <에픽 설계문서 레포 상대경로>` 트레일러를 단다.
8. 머지를 요청하기 전에 PR 마다 아래 셋을 한다. 하나라도 건너뛰면 무엇을 왜 건너뛰었는지 사용자에게 적는다.
   - **스위트 대조.** 그 시점 origin/main 위에 브랜치를 합친 사본에서, PR 이 건드린 모든 플러그인과 `shared/` 의 테스트(셸 · python · node)를 돌려 실패 «이름» 을 main 기준선과 대조한다. 문서만 고친 PR 도 같다. 스위트 둘을 같은 시각에 돌리지 않는다 — 공유 임시 자원 경합이 거짓 실패를 낸다. main 이 움직이면 다시 돈다.
   - **통합 리뷰.** 쓰기 도구가 없는 리뷰어를 사용자가 정한 리뷰 모델(이 레포는 opus — fable 금지)로 부른다 — 하나로 충분하면 하나, 이음매가 여럿이면 여럿을 동시에. qg 로 돌릴 수도 있으나 지금 qg 는 브랜치 diff 하나만 받고(합친 사본 · 다른 에픽 diff 는 따로 줘야 한다) 열린 PR 에 코멘트를 자동으로 단다(`DEVBREW_QUALITY_GATES_DISABLE_PUBLISH=1` 로 끈다) — qg 를 통합 리뷰에 맞추는 일은 R5 가 정한다. 합친 사본 · 이 PR 의 diff · 아직 열린 다른 에픽의 diff · 앞선 통합 리뷰가 이 PR 에 넘긴 항목을 주고, 에픽 사이 이음매를 묻는다: 옮겨진 이름의 import, 같은 파일을 고친 에픽들의 순서와 문구, 상태 · 경로 규약, 줄 상한 · 버전 같은 합계 제약, 테스트가 못 잡는 되살아난 옛 문구, 리뷰어 프로필의 규칙 제거 · 기준 완화(사용자 결정이 있는지). 지적은 「이 PR 이 머지 전 고침」과 「뒤에 머지되는 에픽이 고침」으로 나눠, 지휘자가 이 PR 본문의 `## 통합 리뷰 인계` 절에 담당 에픽과 함께 적는다. 뒤 에픽의 통합 리뷰에는 앞서 머지된 PR 과 아직 열린 PR 의 그 절을 모아 주고(블록의 `브랜치:` 로 `gh pr list --state all --head <브랜치>`) 실제로 고쳐졌는지 확인시킨다. 문서만 고친 PR(모델이 읽는 skill · reference · 템플릿 · 리뷰어 프로필은 문서로 치지 않는다)은 스위트 대조와 그 문서를 읽는 테스트로 대신할 수 있다 — 그렇게 했다고 적는다.
   - **리뷰 뒤 반영.** 리뷰 지적을 고친 수정은 같은 리뷰어로 좁게 한 번 다시 본다. 그 뒤 동작을 바꾸지 않는 수정(문구 · 주석 · 번호 — 단 모델이 읽는 파일의 문구 수정은 동작을 바꾸는 수정이다)은 다시 돌지 않고 PR 본문에 「리뷰 뒤 반영(리뷰 라운드를 거치지 않았다)」으로 적는다. 동작을 바꾸는 수정, 그리고 락 · 보안 경계 · 리뷰어 프로필을 바꾼 수정은 매번 좁은 재리뷰를 한 번 받는다. 좁은 재리뷰는 첫 리뷰 뒤부터 세어 PR 하나에 두 번까지다 — 첫 재리뷰를 보내기 전에 멈출 조건(그 뒤에도 남는 지적을 잔여로 공시하고 넘길 곳)을 정해 PR 본문에 적는다. 두 번째 재리뷰 뒤 남는 지적은 고치지 않고 멈출 조건대로 넘기거나, 고치려면 사용자에게 묻는다.
   릴리스 번호는 이때 정한다 — 먼저 머지되는 쪽이 낮은 번호다. 머지는 사용자가 한다.
9. 로드맵의 에픽이 모두 머지되면 처음부터 끝까지 실제 명령으로 걸어 본다 — 기본 경로(인터뷰 → 분해 → 에픽 넘김 → spec-review → 계획 · 구현 대조 → 작업 목록 · 상태줄)와, 설계 흐름이 아닌 에픽(조사 · 측정 · 결정)이 있으면 그 경로도 한 흐름으로 이어지는지. 끊긴 곳은 사용자에게 보이고 로드맵 수정이나 다음 일로 넘긴다.

- K1 — 위험 — 숨은 가정: 장치를 없애면 늘 의도를 지키는 쪽으로만 작동한다 — 멈춤 판정의 주인이 조사하는 모델 자신으로 옮겨 무한 조사·조기 「충분」 선언이 사용자 모르게 열린다 — 근거 포화 개념의 불안정·조기 종료 실패 양식·무한 루프 사례
- K2 — 위험 — 숨은 가정: plan·구현을 쭉 가는 것과 왜곡 장치 제거가 서로 맞는다 — 실행 중 혼자 판정(Ruling)은 쭉 가게 하는 장치이고 plan 검토 게이트는 PM 이 plan 을 볼 마지막 자리 — 근거 superpowers SDD·brainstorming 원문
- K3 — 위험 — 숨은 가정: 사용자 말 그대로가 하류에서도 그대로 읽힌다 — brainstorming 은 자기 이해 요약을 새 정본으로 삼아 조각 N개면 N번 재해석 — 근거 Cognition 병렬 에이전트·brainstorming 원문
- K4 — 위험 — 숨은 가정: 인터뷰 시점에 나눈 경계가 맞고 하류가 따른다 — 하류의 2차 분해와 충돌하고 승인된 분해가 봉인되기 쉽다 — 근거 ADaPT·brainstorming 분해 문구
- K5 — 위험 — 숨은 가정: 한 세션이 압축을 여러 번 겪어도 의도와 조각 지도를 잃지 않는다 — 근거 Anthropic 장시간 하니스
- K6 — 위험 — 숨은 가정: 조각이 늘어도 spec 승인이 실질 검토로 남는다 — 도장 찍기로 쇠퇴 — 근거 승인 피로(근거 약함)
- K7 — 위험 — 숨은 가정: 찾은 장치 목록이 완전하고 전부 왜곡이다 — 사용자 자신의 통제 자리가 섞여 있고 모델은 사용자 말에 맞추는 경향 — 근거 Sycophancy 연구
- K8 — 위험 — 실패 양식: 병렬 조각의 암묵 결정 충돌과 버전·CHANGELOG 같은 공유 파일 겹침 — 근거 Cognition·Anthropic 멀티에이전트
- K9 — 위험 — 실패 양식: 압축 뒤 조각 지도·결정 내력 소실 또는 덮어쓰기로 「한 곳」이 실제와 어긋남 — 근거 Anthropic 장시간 하니스
- K10 — 위험 — 실패 양식: 두꺼운 brief 의 역설 — 가운데 묻힌 조사·위험·열린 질문을 하류가 덜 씀 — 근거 Lost in the Middle
- K11 — 위험 — 실패 양식: 외부 문구가 바뀌면 devbrew 쪽 넘김 글이 조용히 무력화됨(설치본과 최신본이 이미 다름) — 근거 superpowers 원문 비교
- K12 — 위험 — 실패 양식: 무한 조사 또는 포화를 가장한 조기 종료 — 근거 무한 루프 사례·조기 종료 실패 양식
- K13 — 위험 — 실패 양식: spec 승인 하나만 남은 통제점이 도장 찍기로 무너지고 실행 판정이 보이지 않음 — 근거 승인 피로(근거 약함)
- K14 — 위험 — 실패 양식: 승인된 분해가 봉인돼 조각 사이를 되돌릴 경로가 없음 — 근거 ADaPT·재결정 규약이 확정 항목 단위뿐
- K15 — 위험 — 리뷰 참고 | [overdesign] #2-제약 — 번호로 추적하는 장치가 다섯 결정(D24·D40·D41·D42·D45)에 나뉘고 번호 체계가 셋이다(D24·D42 의 빠짐 경고는 같은 검사) — 사용자 발화 S 번호에 매단 원장 하나와 spec 리뷰 검사 하나로 합치는 쪽을 설계에서 검토한다(판정은 모두 남기고 구조만 합침) (리뷰 41df26ba#r1.1)
