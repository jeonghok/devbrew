# 테스트 값 대비 비용 진단

> 이 레포의 테스트 422단위를 하나씩 읽어, 쓰는 시간과 지키는 것을 나란히 적었다. 시간의 4분의 3은 「없어도 되는 테스트」가 아니라 「비싸게 짜인 테스트」에 있고, 「덕지덕지」는 1초 안팎의 싼 테스트 쪽에 있다 — 그쪽의 비용은 초가 아니라 유지이고, 이 진단은 그것을 고친 횟수(상한)와 읽은 사람이 본 거짓 실패 위험(추정)으로만 댔다. 이 문서는 진단이다 — 지우거나 고친 것은 없고, 판정은 모두 후보다.

- 로드맵: `docs/superpowers/roadmaps/2026-11-20-test-method-rework-brief/roadmap.md` 의 E5 · 묶음: 같은 폴더 `E5.md`
- 흐름: 조사(설계 흐름이 아니다). 받는 곳: E2(기준) · E4(정리)
- 자료 폴더: 같은 폴더 `test-value-audit/` — 단위별 행 · 종합 · 재독 결과 · 판정 표 · 시간 기록

## 무엇을 왜

사용자가 목표를 넓혔다 — 「속도 말고도 test가 지금 최적인지 아님 덕지덕지 붙어 있는건지」, 「값 대비 비용이 제일 거슬려 그리고 꼭 필요한 테스트인지 테스트쪽 리팩토링하면 더 좋아질지」. 그 물음에 답하려면 테스트마다 세 가지를 알아야 한다: 쓰는 시간만큼 지키는 것이 있나 · 꼭 있어야 하나 · 테스트 쪽 짜임을 고치면 나아지나.

이 진단은 그 근거를 만든다. 기준을 정하는 일(E2)과 실제로 지우고 고치는 일(E4)은 하지 않는다.

## 어떻게 읽었나

- **단위.** 셸 · node 는 파일 하나, python 은 모듈 하나. 422단위다(셸 314 · node 2 · python 모듈 106).
- **시간.** 스위트 러너의 시간 기록에서 가져왔다(`test-value-audit/timing-round.tsv`). 이 바퀴는 다른 스위트 하나와 겹쳐 돈 바퀴라 초는 실제보다 길 수 있다 — 순위와 비율로 읽는다. 겹침이 모든 테스트를 고르게 늘리지는 않는다: 프로세스를 띄우거나 git 을 부르는 테스트는 많이 늘고 고정 대기는 거의 늘지 않으므로, 고정 대기 꼴(179초)은 실제 몫보다 작게 보일 수 있다.
- **깊이 둘.** 시간의 90%를 쓰는 87단위는 테스트 안의 확인까지 읽어 「시간을 쓰는 곳」과 「구조 고치기 여지」를 적었고, 나머지 335단위는 파일 단위로 적었다. 싼 쪽도 「꼭 필요한가」를 판정할 만큼은 끝까지 읽었다.
- **읽은 사람.** 묶음 23개를 서로 다른 읽는 agent 23이 따로 읽었다(깊은 쪽 12 · 얕은 쪽 11). 같은 지침 하나를 받았다(`test-value-audit/brief.md`).
- **다시 읽은 사람.** 처음 읽은 사람과 다른 agent 5가 92단위를 다시 읽었다 — 지움 · 합침 후보 48개 전부, 가장 비싼 16개, 「둠」과 보안 표시의 무작위 표본 28개. 묶음 사이의 겹침은 또 다른 agent 1이 모았다.
- **실행하지 않았다.** 아무 테스트도 돌리지 않았다. 「시간을 쓰는 곳」은 모두 코드를 읽고 반복문과 호출 자리를 센 추정이다.

## 칸과 가져온 곳

「있는 스위트를 시간 대비 가치로 감사하는」 하나로 된 방법론은 찾지 못했다. 칸은 흩어진 방법에서 가져왔다(조사 원문: `test-value-audit/methods-research.md`).

| 칸 | 뜻 | 가져온 곳 |
|---|---|---|
| 초 · 줄 수 · 고친 횟수 | 비용 — 시간 기록과 git 이력 | Khorikov 의 fast feedback · maintainability, 유지 비용(churn) |
| 크기 | 쓰는 자원: 작음 · 중간 · 큼 | 구글의 테스트 크기 분류(«swe-google-ch12» 와 같은 책 11장) |
| 종류 | 동작 · 구조 · 글자 · 변이 | 이 레포에 맞춰 정했다 |
| 지키는 것 | 「깨지면 쓰는 사람에게 무엇이 잘못되나」 한 문장 | Khorikov 의 protection against regressions · Test Desiderata 의 Behavioral |
| 거짓 실패 위험 | 동작은 그대로인데 테스트만 깨지기 쉬운 정도 | Khorikov 의 resistance to refactoring · Test Desiderata 의 Structure-insensitive |
| 겹침 | 같은 것을 지키는 다른 테스트 | Fowler 의 테스트 피라미드(더 낮은 층이 이미 잡는가) |
| 보안 갈래 | 보안 경계를 지키는가 | 로드맵의 「보안 갈래의 글자 확인은 지우지 않는다」 |
| 판정 후보 | 둠 · 줄임 · 합침 · 지움 · 구조를 고침 | 이 진단이 정했다 |

맞지 않아 쓰지 않은 것: 커버리지 · 변이 도구로 스위트를 줄이는 연구. 이 레포의 테스트는 문서와 스크립트를 글자로 확인하는 것이 많아 「실행된 줄」이라는 단위가 서지 않고, 결함을 놓치는 손실도 보고돼 있다.

## 결과 — 판정 후보

첫 판정과, 재독 결과를 얹어 바로잡은 판정이다. 재독한 것은 92단위뿐이다 — 나머지 330단위는 첫 판정 그대로다.

| 판정 후보 | 첫 판정 | 바로잡은 판정 | 한 바퀴 대비(바로잡은 쪽) |
|---|---|---|---|
| 구조를 고침 | 122개 · 2,854초 | 123개 · 2,949초 | 78% |
| 둠 | 184개 · 551초 | 194개 · 549초 | 14% |
| 줄임 | 68개 · 346초 | 70개 · 270초 | 7% |
| 합침 | 36개 · 43초 | 28개 · 27초 | 1% |
| 지움 | 12개 · 2초 | 7개 · 1초 | 0% |

판정별 초는 반올림한 값이라 더하면 3,796초로, 전체 3,795초와 1초 다르다.

「구조를 고침」 2,949초가 얼마나 확인된 것인지는 이렇게 갈린다.

| 갈래 | 단위 | 초 | 한 바퀴 대비 |
|---|---|---|---|
| 재독해서 선 것 | 16 | 1,679 | 44% |
| 재독해서 「구조를 고침」으로 바뀐 것 | 3 | 102 | 3% |
| 깊게 읽었지만 재독하지 않은 것 | 35 | 976 | 26% |
| 얕게 읽고 재독하지 않은 것 | 69 | 192 | 5% |

재독으로 확인된 것만 세면 한 바퀴의 47%, 깊게 읽은 것까지 세면 73%다. 얕게 읽은 쪽(확인 전으로 본다)을 다 빼도 결론은 바뀌지 않는다.

읽는 법 셋.

1. **시간은 짜임에 있다.** 한 바퀴의 4분의 3이 「지키는 것은 두고 짜임만 바꾸면 싸진다」다. 지움 후보는 다 합쳐 1~2초라, 지워서 얻는 시간은 없다.
2. **「덕지덕지」는 싼 쪽에 있다.** 지움 · 합침 · 줄임 후보 105개 가운데 82개가 1초 미만이고 중앙값은 0.2초다. 10초를 넘는 것은 여섯뿐이다 — 줄임 다섯(`test_human_gate_e2e.sh` 139.0 · `test_epic_conductor_skill.sh` 28.3 · `test_workspace_invariance.sh` 20.2 · `test_check_verbatim_coverage.sh` 16.7 · `test_run_own_tests.py` 12.7)과 합침 하나(`test_docreview_gate_plain.sh` 11.9)이고, 줄임 270초 가운데 217초가 그 다섯이다. 이쪽의 비용은 시간이 아니라 유지다 — 읽은 사람이 거짓 실패 위험을 「높음」으로 본 단위가 99개(그 가운데 74개가 1초 미만)이고, 가장 많이 고쳐진 테스트(2.1초)는 141번 고쳐졌다. 다만 고친 횟수는 거짓 실패를 센 것이 아니다 — 동작이 바뀌어 정당하게 고친 것도 들어 있어 상한으로 읽는다. 거짓 실패 위험도 관찰이 아니라 읽은 사람의 추정이다(실패 이력은 보지 않았다).
3. **비용은 두 잣대다.** 비싼 테스트의 비용은 초, 싼 테스트의 비용은 유지다(고친 횟수 — 그 가운데 얼마가 문구만 다듬다 깨진 것인지는 세지 않았다). 한 잣대로 순위를 매기면 한쪽이 안 보인다.

단위마다의 판정은 `test-value-audit/verdicts.tsv`, 근거는 `test-value-audit/rows.md` 에 있다.

## 결과 — 시간이 드는 여섯 꼴

읽는 사람 23이 서로 모르는 채 같은 꼴을 짚었다. 초는 그 꼴에 든 테스트 전체의 시간이고, 한 테스트가 여러 꼴에 들어 겹쳐 셌다. 여섯 꼴 가운데 하나라도 든 테스트는 209개 · 3,606초(전체 3,795초)다.

| 꼴 | 테스트 | 초 | 고치는 길(행에 적힌 것) |
|---|---|---|---|
| 확인 · 케이스마다 스크립트(대개 python)를 새 프로세스로 띄운다 | 124 | 2,528 | 단언을 묶어 한 번에 판정 · 스크립트를 import 해 프로세스 안에서 부르기 |
| 케이스마다 임시 git 레포 · 원격 · 클론을 새로 세운다 | 116 | 2,418 | 한 번 지어 복사 · setUpClass · 읽기 전용 케이스는 레포 하나를 함께 |
| 변이 · 비교용 사본을 통째로 복사한다 | 26 | 681 | 한 사본에서 변이하고 되돌리기 · 메모리 안에서 판정 |

| 문서 리뷰 원장 도우미(케이스마다 원장을 처음부터) | 15 | 671 |
| 로드맵 상태 계산을 상태마다 다시 실행 | 7 | 415 |
| 가짜 질문 창 세션 기록 | 4 | 350 |

꼴마다의 테스트 목록과 행에 적힌 규모는 `test-value-audit/synthesis.md` 의 「되풀이되는 꼴」 절에 있다.

## 결과 — 글자에 묶인 테스트

- 「지키는 것」을 한 문장으로 쓸 수 없어 「글자만 지킴」으로 적힌 단위가 25개다.
- 거짓 실패 위험이 「높음」이고 문구를 그대로 대조하는 단위까지 합치면 84개이고, 고친 횟수의 합이 1,218번이다(동작이 바뀌어 고친 것도 들어 있는 상한이다).
- 둘 이상의 테스트가 겹쳐 재는 문서가 35개다. 지휘 · 마무리 절차 문서와 품질 게이트의 README · SKILL 이 대표다.

재독이 여기서 가장 큰 잘못을 찾았다. 「글자만 지킴」이라 지워도 된다고 적힌 것 가운데 다섯은 **모델이 읽는 글**(감사 agent 의 질문 · SKILL 의 안내 표 · 사용자 레포에 깔아 주는 규칙 템플릿)을 지키고 있었다. 이 레포에서는 그런 글이 곧 동작이다. 「글자 확인」을 「동작을 정하는 글자」와 「그렇지 않은 글자」로 가르는 규칙 없이는 이 갈래를 판정할 수 없다 — E2 의 몫이다.

문서별 묶음은 `test-value-audit/synthesis.md` 의 「글자에 묶인 테스트」 절에 있다.

## 결과 — 작업 트리를 건드리는 테스트

추적 파일을 고쳤다 되돌리거나 레포 안에 폴더를 만들었다 지워, 함께 돌거나 중간에 죽으면 서로 부딪치는 테스트가 8개다(작업 트리 안 6 · 밖 2).

- 실제 agent 파일을 고쳤다 되돌리는 것 1 · 실제 체크아웃의 심볼릭 링크를 잠깐 지우는 것 1 · 레포 안 폴더를 만들고 지우는 것 1 · 추적되는 설정 파일을 덮었다 복원하는 것 3.
- 작업 트리 밖: 사용자의 실제 설정 파일(`~/.claude/…`)을 옮겼다 되돌리는 것 1 · 고정 경로 `/tmp/…` 에 쓰는 것 1.

스위트를 함께 돌리는 길(E1 이 미뤄 둔 것)을 열려면 이 여덟과 아래 덧붙임의 하나가 먼저 걸린다. 목록은 `test-value-audit/synthesis.md` 의 같은 이름 절에 있다.

덧붙임 — 이 진단과 따로, E1 의 머지 전 대조에서 같은 갈래가 하나 더 나왔다: 임시 폴더가 git 레포 밖이라고 가정한 테스트 하나가, 대조가 임시 폴더를 메인 레포 안에 두는 탓에 메인 레포에 실제 사본을 만든다(`plugins/plugin-audit/tests` 의 `test_default_helper_is_the_sibling_script_not_cwd` — E1 의 PR 에 든 설계문서 `docs/superpowers/specs/2026-11-21-suite-time-cut-design.md` 의 「지휘 기록」 절).

## 재독이 바로잡은 것

92단위를 다시 읽어 25단위에서 판정이 서지 않았다.

| 다시 읽은 것 | 본 수 | 서지 않음 | 무엇이 틀렸나 |
|---|---|---|---|
| 지움 후보(전부) | 12 | 5 | 모델이 읽는 글을 「동작을 정하지 않는 글자」로 분류했다 |
| 합침 후보(전부) | 36 | 12 | 모양은 비슷하지만 지키는 대상이 달랐다. 선 것 가운데도 일부만 겹치는 것이 여럿이다 |
| 가장 비싼 16 | 16 | 1 | 시간을 쓰는 곳은 16개 모두 자릿수가 맞았다. 다만 10개는 적힌 대로 고치면 잃는 확인이 있다 |
| 「둠」 · 보안 표시 무작위 28 | 28 | 7 | 「둠」 19개 가운데 2개만 틀렸다. 나머지 5개는 겹침을 이름으로 짐작한 줄임 · 구조 후보였다 |

되풀이된 잘못 넷.

1. **겹침을 이름으로 짐작하고 열지 않았다.** 이름이 비슷한 형제 테스트를 겹침으로 댔는데, 실제 겹침은 레포 전체를 훑는 스윕 테스트에 있었다. 반대로 「겹친다」며 줄임을 권한 테스트가 열어 보니 유일한 락이었던 경우가 있다.
2. **「X 만 옮기고 Y 만 남긴다」 처방이 그 파일에만 있는 확인을 조용히 버린다.** 합침 계획에 남는 확인 일부가 빠져 있었다.
3. **「한 번 지어 복사」가 깨지는 조건을 적지 않았다.** 상태 안에 절대 경로나 수정 시각이 박혀 있으면 복사본이 원본을 가리킨다. 변이 매트릭스와 함께 쓰는 도우미에 캐시를 두면 변이가 이빨을 잃는다.
4. **보안 표시가 파일 단위라 넓다.** 422단위 가운데 222단위가 「예」다. 보안 경계 확인이 아예 없는데 「예」인 것은 표본의 「예」 20개 가운데 2개(경계 사례 둘까지 넣으면 4개)였다. 더 큰 것은 「예」가 맞는 18개 가운데 7개에서 보안 확인이 파일 확인의 약 10% 이하인데 파일 전체가 「지우지 않음」으로 보호받는다는 점이다. 표시는 확인(줄 범위) 단위로 다는 것이 맞다.

단위마다의 재독 결과는 `test-value-audit/rereads.md` 에 있다.

## E2 에 넘기는 것

기준을 쓸 때 이 진단에서 근거로 쓸 것이다.

- **「동작을 정하는 글자」의 경계가 먼저다.** 지움 후보의 잘못 다섯이 모두 이 경계에서 나왔다. 모델이 읽고 따르는 글(SKILL · agent 프로필 · reference · 깔아 주는 템플릿)은 동작으로 친다는 것부터 적어야 한다.
- **비용의 잣대는 둘이다.** 초(비싼 쪽)와 유지 비용(싼 쪽). 값 대비 비용의 기준은 두 잣대를 따로 다뤄야 한다. 유지 비용을 이 진단은 고친 횟수(상한)와 읽은 사람이 본 거짓 실패 위험(추정)으로만 댔다 — 기준의 근거로 쓰려면 실제 실패 이력이나 커밋 표본으로 다시 재야 한다.
- **겹침은 상대 테스트를 열어 본 것만 겹침이다.** 이름이 비슷하다는 것은 근거가 아니다. 합침 · 줄임의 승인 조건으로 적을 만하다.
- **보안 갈래 표시는 확인 단위로.** 파일 단위 표시는 무관한 문장 핀까지 보호한다.
- **테스트는 작업 트리와 사용자 파일을 건드리지 않는다.** 여덟이 어기고 있고, E1 의 머지 전 대조가 하나를 더 찾았다([결과 — 작업 트리를 건드리는 테스트](#결과--작업-트리를-건드리는-테스트)의 덧붙임).
- **새 테스트가 이 꼴로 쌓이지 않게 할 것.** 케이스마다 레포를 새로 세우기 · 단언마다 프로세스 띄우기 · 다른 테스트를 통째로 다시 돌리기.

## E4 에 넘기는 것

- 단위마다의 판정 후보와 근거(`verdicts.tsv` · `rows.md`). 재독한 92단위는 바로잡은 판정을 쓰고, 근거도 `verdicts.tsv` 의 재독 근거 칸과 `rereads.md` 가 `rows.md` 보다 앞선다 — `rows.md` 는 처음 읽은 그대로라, 판정이 서지 않은 25단위에서는 바로잡은 판정과 반대를 말한다.
- 재독하지 않은 지움 · 합침 · 줄임 후보는 손대기 전에 겹침 상대를 열어 확인한다(위 「믿어도 되는 것」).
- 「구조를 고침」은 준비물 단위로 묶어 하는 것이 싸다 — 팀 레포 · 지휘 상태 레포 · 문서 리뷰 원장 도우미 셋이 합쳐 37개 테스트 · 약 2,250초에 걸친다(겹쳐 셈). 고칠 때의 조건은 `rereads.md` 의 「고치면 잃는 것」 줄에 있다.
- 겹침 묶음 59개(`synthesis.md` 의 「같은 것을 지키는 묶음」)와 행끼리 어긋나는 곳 17항목(같은 파일의 「행끼리 어긋나는 곳」).

## E1 에 알리는 것

- E1 이 조건부로 남긴 느린 넷(`test_human_gate.sh` · `test_human_gate_e2e.sh` · `test_team_status.sh` · `test_roadmap_status.sh`)은 모두 이 진단의 비싼 16개에 들었고 재독까지 받았다. 셋은 「구조를 고침」, 하나는 「줄임」이다. 넷 가운데 셋이 팀 레포 준비물을 쓴다 — 넷만 따로 고치기보다 준비물 단위로 고치는 쪽이 같은 일을 그 준비물을 쓰는 다른 열두 테스트에도 준다(준비물을 쓰는 테스트는 15개다).
- 「함께 돌리기」를 열려면 작업 트리를 건드리는 여덟과 E1 의 머지 전 대조가 찾은 하나가 먼저 걸린다.

## 확인하지 못한 것

- 아무 테스트도 실행하지 않았다. 시간을 쓰는 곳 · 고치면 얼마나 주는지는 모두 추정이다.
- 시간은 다른 스위트와 겹친 바퀴의 것이다. 겹침이 꼴마다 다르게 늘렸을 수 있어, 꼴 사이의 비율도 어림이다.
- 330단위는 재독하지 않았다.
- 처음 읽은 사람이 끝까지 읽지 못했다고 적은 파일이 셋이다(`test_conducting_interview_stage.sh` 의 뒤 3분의 2 · `test_control_plane.py` · `test_first_cell_check.py` 의 픽스처). 문서 리뷰 테스트들의 케이스 본문이 사는 공유 파일(`cases.sh` 4,773줄)은 쓰이는 도우미만 읽었다.
- 「이 테스트가 진짜 버그를 잡은 적이 있나」(실패 이력)는 보지 않았다. 고친 횟수는 git 이력으로 셌고 이름 변경 앞의 이력은 빠졌을 수 있다.
- 방법론 조사에서 열어 보지 못한 것: Khorikov 책 원문(2차 요약으로 확인) · 스위트 축소 논문 본문 둘 · 테스트 냄새 원전 사이트.
- 읽는 사람 23이 같은 지침을 받았으므로, 지침이 「구조를 고침」 쪽으로 기울어 있었을 가능성은 남는다. 재독은 그 판정이 코드에 근거가 있는지를 봤고 대부분 섰다.
