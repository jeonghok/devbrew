# 지휘 — 로드맵의 에픽을 끝까지 이끄는 절차

## 손으로 따르는 절차

로드맵 하나를 따라 에픽들을 지휘하는 세션의 절차다. 걸음마다 기본값이다 — 일의 모양이 다르면 다르게 하고, 무엇을 왜 다르게 했는지 그 에픽 설계문서에(에픽에 매이지 않은 판단은 다음 로드맵 수정 PR 본문에) 적는다. 정석 흐름(brainstorming → 계획 → 구현)의 뜻은 지킨다.

- `<SD>` 는 spec-distill 플러그인 폴더의 절대경로, `<로드맵>` 은 로드맵 파일의 레포 루트 기준 경로다. `<SD>` 를 모르면 추측하지 말고(cwd 포함) 멈춰 사용자에게 묻는다.
- 레포마다 다른 값은 박지 않고 읽는다 — 기본 브랜치는 `origin/HEAD`, 브랜치 이름은 로드맵 블록의 `브랜치:`, 설계문서 · 계획 폴더 · 테스트 명령 · 리뷰 모델은 로드맵 frontmatter 의 `specs_dir` · `plans_dir` · `test_command` · `review_model` 이다. 없으면 각각 superpowers 기본 폴더 · 레포 파일에서 찾은 러너 · 세션 모델을 쓰고, 한 번 물어 정한 값은 다음 로드맵 수정 PR 에 frontmatter 로 올린다.
- 각 칸의 주인과 갱신 길은 같은 폴더의 `roadmap-ontology.md` 에 있다.

1. **맞추기.** `git fetch origin` 뒤 `python3 "<SD>"/scripts/control_plane.py show --tasks <로드맵>` 을 돌려 작업 목록을 결과에 맞춘다. 줄마다 `<제목><탭><작업 상태>` 이고 에픽 하나에 작업 하나다 — 제목은 그대로 쓰고, 상태가 `keep`(알 수 없음)이면 작업 상태는 두고 제목만 바꾼다. 종료 코드 3 이면 작업 목록을 바꾸지 않고 표준 오류의 「검사 불가」 사유를 사용자에게 그대로 보인다 — 일부 단계가 보여도 믿지 않는다. 종료 코드 4(로드맵이 아직 기본 브랜치에 없다 — 방금 나눠 머지 전)면 `python3 "<SD>"/scripts/roadmap_status.py --roadmap-file <로드맵>` 으로 대신 계산하고, 대기 · 준비는 시작 전, 설계 중 · 계획 · 구현 중 · 구현 끝 · PR · 일부 머지는 진행 중, 머지됨 · 끝남은 완료로 맞춘다. 살아 있는 agent 를 확인한다 — 끝났는데 보고하지 않은 것은 거두고 놀고 있는 것은 내린다. 압축 · 새 세션 뒤에도 여기서 시작한다 — 무엇이 끝났는지 기억에 기대지 않는다.
2. **에픽과 브랜치.** 준비 단계 에픽을 고른다. 블록의 `브랜치:` 이름으로 기본 브랜치에서 브랜치와 worktree 를 먼저 만들고(`superpowers:using-git-worktrees`), 그 에픽의 설계문서 · 계획은 모두 그 브랜치에 커밋한다. `브랜치:` 가 여럿이면 적힌 순서가 그 에픽 설계문서가 나눈 계획의 순서다 — 다음 계획의 브랜치는 앞 계획이 머지됐으면 기본 브랜치에서, 아직이면 앞 계획의 브랜치에서 만든다. 사람에게 묻는 단계(brainstorming 의 질문 · 절별 승인 · spec 승인)는 사람이 보는 세션에서 한 번에 한 에픽씩, 의존 사슬의 앞쪽부터 한다 — 백그라운드 agent 에는 질문 도구가 없다. spec 승인은 사용자가 에픽마다 한다. 지휘 세션은 어느 worktree 에도 속하지 않은 메인 체크아웃(`git worktree list` 의 첫 줄)에 머문다 — worktree 격리로 시작됐으면 시작할 때 그 사실을 알리고, 그 worktree 를 떠날 수 있는지(하니스의 worktree 나가기)를 먼저 재 본다. 떠날 수 없으면 다른 에픽의 spec 리뷰는 그 에픽 담당 agent 를 거쳐(4 의 두 부분 반환) 하고 그 사실을 알린다 — 사용자에게 다른 세션을 열라고 하지 않는다. 한 에픽의 spec 리뷰가 도는 동안(진입부터 승인 게이트까지) 다른 에픽에서 돌아온 질문 · 멈춤은 받은 원문을 git 이 추적하지 않는 파일에 적어 두기만 하고, 그 리뷰 게이트 질문에 섞지 않고 게이트와 게이트 사이나 리뷰가 끝난 뒤 묻는다. 질문마다 첫 줄에 에픽 이름을 쓴다.
3. **흐름과 설계.** 에픽의 흐름은 기본이 설계 흐름(brainstorming → spec-review → 계획 → 구현)이다. 조사 · 측정 · 결정처럼 맞지 않는 에픽은 맞는 흐름을 고르되, 시작하기 전에 고른 흐름 · 이유 · 산출물을 보이고 `AskUserQuestion` 으로 승인받는다 — 설계 흐름의 spec 승인을 대신하는 자리이고, 거절되면 설계 흐름으로 간다. 승인된 흐름 · 산출물은 로드맵 블록의 `흐름:` · `산출물:` 칸에 같은 폴더 `redecompose.md` 의 재분해 절차로 적는다. 지휘 세션은 사람에게 묻는 부분(brainstorming 의 질문 · 절별 승인 · spec 승인)을 한 번에 한 에픽씩, 의존 사슬의 앞쪽부터 직접 하고 설계문서도 직접 써서 에픽 브랜치에 커밋한다 — brainstorming 의 입력과 지시는 같은 폴더 `epic-handoff.md` 의 에픽 넘김 줄이 싣는 것(묶음 첨부 · 번호째 읽기 · 번호 대조 표 · frontmatter · AC 번호 · 있는 것 검토 · 상류 · 하류 연계 · 레포 전용 값)과 같다. spec-review 도 지휘 세션이 직접 돌린다 — 부르기 전에 그 에픽 worktree 로 옮겨 가(셸의 작업 폴더를 그 worktree 로) `pwd` 와 `git rev-parse --show-toplevel` 이 그 worktree 인지 보고, 설계문서 절대경로 뒤에 `--bundle <묶음 절대경로>`(설계문서 frontmatter `source_interview` 와 같은 파일)를 붙여 `/spec-distill:spec-review` 를 부른다. 진입 사전 검사 줄의 `root=` 가 그 worktree 가 아니면 멈춘다 — 메인 체크아웃에서 그냥 부르면 묶음과 코드를 메인 쪽 사본으로 조용히 읽고, 리뷰 반영 커밋이 메인 브랜치로 간다. `--bundle` 값이 설계문서 frontmatter `source_interview` 와 다르거나 읽을 수 없으면 리뷰하지 않고 끝나고, 같으면 진입에서 번호 대조를 보인 뒤 계속한다(빠진 번호 · 얕은 답 · 받드는 에픽 없는 발화 · 검사 불가는 막지 않고 승인 게이트의 「경고 N개」에 더해진다). 리뷰 내내 그 worktree 에 머물고 커밋도 거기서 한다. 리뷰 도중 압축되면 같은 설계문서 경로로 spec-review 를 다시 부른다 — 리뷰 원장이 라운드 · 상한을 잇는다. 승인 게이트의 ① · ② · 기타 칸 「여기서 계속」 은 선택지를 그대로 보이되, 무엇을 골라도 지휘 세션은 다음 세션 줄의 writing-plans 를 직접 따르지 않고 그 줄을 계획 agent 에게 넘긴다 — 게이트를 보일 때 사용자에게 그 줄은 계획 agent 의 입력이니 붙여 넣지 않아도 된다고 알린다. 승인한 날짜와 고른 선택지 원문은 미커밋 확인 뒤 그 에픽 worktree 에서 설계문서 `## 지휘 기록` 에 한 줄로 커밋한다. 그다음 메인 체크아웃으로 돌아온다. ① · ② 면 거기서 턴을 끝낸다 — ① 이면 이 세션의 `/compact` 를 권하고, ② 를 골라도 이 세션에서 ① 과 같이 처리한다고 알린다. 계획 agent 는 사용자의 다음 말에 보내거나, `/compact` 뒤 걸음 1 이 승인 줄은 있고 계획은 없는 에픽을 찾을 때 보낸다. 「여기서 계속」 은 사용자가 이어 가기를 고른 것이라 같은 턴에 계획 agent 를 보내도 된다. 사용자에게 다른 세션을 열라고 하지 않는다 — 사용자가 에픽을 자기 세션에서 따로 진행하겠다고 하면 그 세션의 첫 줄로 에픽 넘김 줄(자리표를 채우고, 줄 안의 플러그인 루트 변수는 `<SD>`(이 세션이 쓰는 spec-distill 플러그인 폴더의 절대경로)로 — 레포 자체에 그 플러그인 소스가 있으면 그 에픽 worktree 의 사본을 써도 된다)을 준다. spec 이 승인되면 지휘 세션은 계획 · 구현으로 들어가지 않고 그 에픽 worktree 의 백그라운드 agent 에 계획을 보낸 뒤 다음 에픽의 설계로 간다.
4. **superpowers 가 묻는 자리.** 사람이 보는 세션에서 만난 자리는 사용자가 그 자리에서 답한다. 백그라운드 agent 가 만나는 자리는 보낼 때 적어 준 답으로 간다. 적어 준 답이 없는 자리(writing-plans 가 끝에 묻는 계획 검토 등)에서 agent 는 멈추고 (a) 사람에게 보일 쉬운 요약(무엇을 정하나 · 고르면 무엇이 달라지나 · 배경, 내부 기호는 괄호에만)과 (b) skill 이 낸 문면 · 선택지 원문을 함께 돌려보낸다. 지휘 세션은 배경을 먼저 쉬운 말로 쓰고 질문만 봐도 결정할 수 있게 묻는다 — 선택지의 수 · 순서 · 라벨(돌려줄 값) · skill 자신의 「(권장)」 표시와 사용자 답은 글자 그대로 두고, 각 선택지 설명은 원문의 「고르면 무엇이 달라지나」(그대로 두면 · 고치면)를 빠뜨리지 않으며, 지휘 세션의 의견은 선택지 밖 「지휘자 의견:」 한 줄로만 쓰고, 원문은 늘 붙인다. 사용자 답은 글자 그대로 같은 agent 에 돌려보내 이어 가게 한다. 선택지로 받을 수 없는 답(사용자가 직접 써야 하는 것)은 게이트 밖에서 따로 묻고 그 사실과 이유를 적는다. 그대로 전할 수 없는 자리는 지휘 세션이 그 자리를 직접 돌리고 이유를 설계문서에 적는다. 실행 방식은 writing-plans 가 권하는 방식이다. 계획 검토는 지휘 세션이 계획을 읽고 설계에 없던 결정(범위 · 인터페이스 · 파일 배치 등)이 있는지 가린다 — 있으면 그 결정들을 배경과 함께 사용자에게 묻고 답 전에는 그 에픽의 구현을 보내지 않으며, 없으면 계획 경로만 보이고 구현을 보낸다. 가른 결과와 이유는 그 에픽 설계문서에 적는다. 머지 메뉴는 「브랜치 그대로 두기」다 — Push 와 PR 은 지휘 세션이 구현 대조(5) 뒤에 한다. 보낼 때 기준 브랜치도 적어 준다. 사용자가 그 자리에서 다르게 말하면 그 말을 따른다.
5. **계획 · 구현.** 계획 agent 는 writing-plans 로 계획을 쓰고 커밋한 뒤 `python3 "<SD>"/scripts/check_bundle_coverage.py --plan <설계문서> <계획>` 을 돌려 계획에 없는 AC 를 계획에 더한다 — 설계가 계획을 여럿으로 나눴으면 `--acs` 뒤에 그 계획이 맡은 AC 목록을 준다. 구현은 에픽마다 그 worktree 의 백그라운드 agent 가 하고, 그동안 다음 에픽의 설계를 진행한다. 의존 · 같은 파일 겹침이 없는 에픽은 동시에 보내되 띄우기 전에 규모를 알린다. 고른 실행 방식의 마지막 전체 리뷰가 AC 마다 한 줄(`AC1: 구현됨 — 근거` 꼴, 판정은 구현됨 · 미룸 · 빠짐)로 보고하게 하고, agent 의 마지막 보고에 판정 목록 전체와 그 AC 보고 내용 전체를 싣게 한다 — 실행 방식이 작업 폴더를 지울 수 있다. 판정 목록은 멈추지 않고 그대로 사용자에게 보인다. 다만 판정이 승인된 설계의 수용 기준 · 의도를 바꾸거나 구현이 막히면 그 에픽만 멈추고 배경과 함께 묻는다 — 다른 에픽은 계속한다. 돌아오면 AC 보고를 git 이 추적하지 않는 파일에 두고, 미룸 · 빠짐과 리뷰 후속으로 미룬 것을 설계문서 `## 미룸` 표(항목 · 이유 · 받는 곳)에 올린 뒤 `python3 "<SD>"/scripts/check_bundle_coverage.py --impl <설계문서> <그 보고 파일>`(계획이 여럿이면 같은 `--acs`)을 돌려 경고를 사용자에게 보인다. 그다음 설계문서에 `## 판정` 절(판정 목록 그대로 — 절이 이미 있으면 그 아래 `### <계획 경로>` 로 잇는다. 앞 계획의 판정 줄이 하위 머리 없이 있으면 먼저 그 줄들을 `### <앞 계획 경로>` 아래로 옮긴다 — 같은 머리가 둘이거나 머리 단계가 섞이면 상태 계산이 그 절을 읽지 못한다)과 `## 구현 대조 — <계획 경로>` 절(대조 첫 줄 · AC 판정 수)을 에픽 브랜치에 커밋하고 Push · PR 을 연다. `gh` 가 없으면 PR 을 열 명령을 사용자에게 준다.
6. **머지 뒤.** 에픽이 머지될 때마다 남은 에픽을 재평가하고, 바뀔 때만 같은 폴더 `redecompose.md` 의 재분해 절차로 사용자 승인 뒤 로드맵 수정 PR 을 올린다. 열린 에픽 브랜치에는 기본 브랜치를 merge 하고 대조(8)를 다시 돈다 — 그 브랜치에서 agent 가 일하는 중이면 직접 merge 하지 않고 돌아올 때까지 기다린다. merge 가 충돌하면 그 에픽만 멈추고 알린다. 받는 에픽이 머지되면 넘긴 항목이 처리됐는지 그 설계문서의 번호 대조 · AC 보고로 확인한다. 머지는 사용자가 한다.
7. **`Spec:` 트레일러.** 구현 커밋에는 `Spec: <에픽 설계문서 레포 상대경로>` 트레일러를 단다 — 보내는 글에 적어 준다.
8. **머지 전 확인.** PR 마다 아래 셋을 한다(문서만 고친 PR 도 — 모델이 읽는 skill · reference · 템플릿 · 리뷰어 프로필은 문서로 치지 않는다). 하나라도 건너뛰면 무엇을 왜 건너뛰었는지 적는다.
   - **스위트 대조.** 그 시점 기본 브랜치에 이 브랜치를 merge 한 별도 worktree(합친 사본)와 기본 브랜치 사본에서 그 레포의 스위트를 돌려 실패 «이름» 을 양방향으로 대조한다 — 이 브랜치에만 있는 실패와 기본 브랜치에만 있는 실패. 무엇을 돌리나: 로드맵 frontmatter `test_command` 가 있으면 그것, 없으면 레포 파일에서 찾은 러너(pytest · unittest · 셸 · node 등)의 전체 스위트다. 스위트가 너무 오래 걸리는 레포에서만 범위를 좁히고 이유를 적는다. 이름은 러너 출력에서 뽑는다(pytest `-rf` 의 `FAILED` 줄 · unittest 의 `FAIL:` · `ERROR:` 줄 · node `--test-reporter=tap` 의 `not ok` 줄 · 셸 테스트의 실패 표시 줄) — 뽑을 수 없으면 「이름 대조 불가 — 파일 단위만」 이라고 적는다. 사본을 만들기 전에 남은 merge 를 abort 하고, `git fetch` 뒤 대조할 브랜치의 SHA 를 한 줄로 남긴다. 스위트 둘을 같은 시각에 돌리지 않는다(잠금 — 예: `mkdir` 잠금과 종료 시 해제) — 공유 임시 자원 경합이 거짓 실패를 낸다. 실행 중인 스크립트 파일은 고치지 않는다. 기본 브랜치가 움직이면 다시 돈다. 테스트가 없는 레포면 「스위트 대조 없음」을 적고 통합 리뷰만 한다.
   - **통합 리뷰.** 쓰기 도구가 없는 리뷰어를 로드맵 frontmatter `review_model`(없으면 세션 모델)로 부른다(`superpowers:requesting-code-review`) — 하나로 충분하면 하나, 이음매가 여럿이면 여럿을 동시에. 합친 사본 · 이 PR 의 diff · 아직 열린 다른 에픽의 기본 브랜치 대비 diff · 앞선 통합 리뷰가 이 PR 에 넘긴 항목을 주고 에픽 사이 이음매를 묻는다: 옮겨진 이름의 import, 같은 파일을 고친 에픽들의 순서와 문구, 상태 · 경로 규약, 줄 상한 · 버전 같은 합계 제약, 테스트가 못 잡는 되살아난 옛 문구, 리뷰어 프로필의 규칙 제거 · 기준 완화(사용자 결정이 있는지). 충돌은 실제 merge 없이 `git merge-tree` 로 미리 본다. 지적은 「이 PR 이 머지 전 고침」과 「뒤에 머지되는 에픽이 고침」으로 나눠 이 PR 본문의 `## 통합 리뷰 인계` 절에 담당 에픽과 함께 적는다. 뒤 에픽의 통합 리뷰에는 앞서 머지된 PR 과 아직 열린 PR 의 그 절을 모아 주고(블록의 `브랜치:` 마다 `gh pr list --state all --head <브랜치>`) 실제로 고쳐졌는지 확인시킨다. `gh` 가 없거나 GitHub 레포가 아니면 PR 본문 대신 설계문서 `## 미룸` 표와 `## 지휘 기록` 절에 적고 그 사실을 알린다.
   - **리뷰 뒤 반영.** 리뷰 지적을 고친 수정은 같은 리뷰어로 좁게 한 번 다시 본다(`superpowers:receiving-code-review`). 그 뒤 동작을 바꾸지 않는 수정(문구 · 주석 · 번호 — 단 모델이 읽는 파일의 문구 수정은 동작을 바꾸는 수정이다)은 다시 돌지 않고 PR 본문에 「리뷰 뒤 반영(리뷰 라운드를 거치지 않았다)」으로 적는다. 동작을 바꾸는 수정, 그리고 락 · 보안 경계 · 리뷰어 프로필을 바꾼 수정은 매번 좁은 재리뷰를 한 번 받는다. 좁은 재리뷰는 첫 리뷰 뒤부터 세어 PR 하나에 두 번까지다 — 첫 재리뷰를 보내기 전에 멈출 조건(그 뒤에도 남는 지적을 잔여로 공시하고 넘길 곳)을 정해 PR 본문에 적는다. 두 번째 재리뷰 뒤 남는 지적은 고치지 않고 멈출 조건대로 넘기거나, 고치려면 사용자에게 묻는다.
   끝으로 `superpowers:verification-before-completion` 을 따른다. 릴리스 번호는 머지 직전에 정한다 — 먼저 머지되는 쪽이 낮은 번호다. 머지 명령 줄만 준비하고 머지는 사용자가 한다.
9. **끝.** 로드맵의 에픽이 모두 머지되면 처음부터 끝까지 실제 명령으로 걸어 본다(끝에서 끝 확인) — 기본 경로(인터뷰 → 분해 → 에픽 설계 → spec-review → 계획 · 구현 대조 → 작업 목록 · 상태줄)와, 설계 흐름이 아닌 에픽(조사 · 측정 · 결정)이 있으면 그 경로도 한 흐름으로 이어지는지 본다. 넘긴 항목이 모두 처리됐는지 확인하고, 지휘 세션과 agent 가 만든 worktree · 사본 · 잠금 · 임시 폴더를 정리한다 — 브랜치는 지우지 않는다. 지우기 전에 수정 · 추적 안 된 파일이 있으면 보이고 묻는다. 끊긴 곳은 사용자에게 보이고 로드맵 수정이나 다음 일로 넘긴다.

**/compact.** 에픽 하나의 spec 리뷰가 끝나 계획 agent 를 보낸 직후처럼 끊기 좋은 자리에서 맥락이 무거우면, 기록을 커밋한 뒤 `/compact` 를 권하고, 압축 뒤 이 세션에 칠 이어 갈 줄을 함께 준다 — 「`<SD>` 의 references 폴더에 있는 이 절차 파일(conducting.md)을 다시 읽고 `<로드맵>` 지휘를 걸음 1 부터 잇는다」(`<SD>` · `<로드맵>` 은 채워서). 압축은 사용자가 하고, 압축 뒤에는 1 부터 다시 한다.
