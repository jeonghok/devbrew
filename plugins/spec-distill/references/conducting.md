# 지휘 — 로드맵의 에픽을 끝까지 이끄는 절차

## 지휘 순환

지휘자 skill(`/spec-distill:epic-conductor`)이 불릴 때마다 걸음 1 부터 차례로 돈다. 걸음마다 다섯 칸(기본값 · 판단 · 부를 skill · 기록 · 기계 상태)이고, 기본값과 다르게 하면 무엇을 왜 다르게 했는지 그 에픽 설계문서 `## 지휘 기록` 에 적는다(에픽에 매이지 않은 판단은 다음 로드맵 수정 PR 본문의 `## 지휘 기록` 절에). 설계문서 없이 산출물만 내는 에픽이면 같은 절(지휘 기록 · 판정 · 구현 대조)을 그 산출물 파일에 둔다. 정석 흐름(brainstorming → 계획 → 구현)의 뜻은 지킨다. superpowers 는 부르기만 하고 고치지 않는다.

- `<SD>` 는 spec-distill 플러그인 폴더의 절대경로, `<로드맵>` 은 로드맵 파일의 레포 루트 기준 경로, `<세션>` 은 `python3 "<SD>"/scripts/state_path.py session-id` 의 값이다. `ledger <명령>` 은 `python3 "<SD>"/scripts/conductor_ledger.py <명령>` 을 줄인 것이다. `<설계문서>` 는 그 에픽 worktree 안 설계문서의 절대경로다 — `ledger record` · `ledger write-sections` · `ledger flush` 는 상대경로를 지금 작업 폴더 기준으로 풀어서, 메인 체크아웃에서 부르면 다른 사본을 고친다. 기계 상태 자원 폴더는 `ledger resource-dir --roadmap <로드맵> --kind tmp|relay|report --name <이름>` 이 만들고 경로를 낸다 — 만든 것은 `## 자원` 에 적고, 끝나면 `ledger cleanup` 이 확인 없이 지운다. 「에픽 worktree」 는 그 에픽 브랜치가 지금 서 있는 worktree 다 — 하위 agent 가 자기 격리 worktree 에서 그 브랜치에 섰으면(걸음 3 의 「하위 agent 의 자리」) 그 worktree 다.
- 레포마다 다른 값은 박지 않고 읽는다 — 기본 브랜치는 `origin/HEAD`, 브랜치 이름은 로드맵 블록의 `브랜치:`, 설계문서 · 계획 폴더 · 테스트 명령 · 리뷰 모델(`specs_dir` · `plans_dir` · `test_command` · `review_model`)은 해결자(`repo_defaults.py get`)가 로드맵 · 레포 설정 파일 · 기본값에서 낸다.
- 하위에게 보내는 글은 같은 폴더 `conductor-dispatch.md` 의 틀이다. 각 칸의 주인은 같은 폴더 `roadmap-ontology.md` 에 있다.
- 에픽 PR 번호는 PR 을 열 때(걸음 4)와 쌓인 PR 의 바탕을 기본 브랜치로 바꾼 직후(걸음 5)에만 `ledger pr-record` 로 적는다 — 번호 없는 PR 을 찾아 적는 걸음은 없고, 그 밖의 PR(손으로 연 PR · 이 판 전에 연 PR)은 지휘 세션이 `ledger pr-record --roadmap <로드맵> --session <세션> --epic <에픽> --pr <번호>` 를 한 번 부른다(번호는 숫자만). `ledger pr-refresh` 가 「적은 PR #N 이 <브랜치> 와 맞지 않는다」 경고를 내면 그 줄의 두 명령 가운데 하나를 부른다 — 이 에픽의 PR 이면 다시 적고, 아니면 `--drop` 으로 번호 기록을 지운다.

### 1. 맞추기
- 기본값: `git fetch origin` → `python3 "<SD>"/scripts/control_plane.py show --tasks <로드맵>` 으로 작업 목록을 맞춘다(종료 코드 3 · 4 의 뜻은 손 절차 1 과 같다) → `ledger claim --roadmap <로드맵> --session <세션>` 으로 표지를 잡는다 → `ledger pr-refresh --roadmap <로드맵> --session <세션>` 으로 기계 상태의 PR 캐시를 주인(GitHub)과 맞춘다 → 아래 맞추기 순서로 살아 있는 agent 와 작업을 원천에서 다시 센다.
- 판단: 표지를 다른 세션이 쥐었으면 쓰지 않고 읽기 전용으로 보이며, 넘겨받을지(`ledger takeover`)는 사용자에게 묻는다. 기계 상태가 깨졌으면 사유를 보이고 덮어쓰지 않는다 — 다시 만들 수 있는 것(PR 캐시(`## PR`) · 자원 · 기다리는 질문)은 주인에서 다시 모은다. `## 에픽 PR` 은 다시 모으지 않고 그대로 둔다 — 잃은 번호는 지휘 세션이 위 머리의 번호 적기 불릿대로만 다시 적는다. 캐시는 「PR 열림」인데 GitHub 은 머지면 주인을 믿고 캐시를 고친 뒤 알린다. `ledger claim` · `ledger takeover` · `ledger pr-refresh` 가 옛 판이 쓴 PR 캐시 줄이라고 멈추면(claim · takeover 는 표지를 잡은 뒤 멈춘다) 그 줄이 보인 `--reset` 명령으로 PR 절만 비우고 다시 채운 뒤 `ledger release` → `ledger claim` 으로 표지를 다시 잡는다. 끝났는데 보고하지 않은 agent 는 결과를 거두고 놀고 있는 agent 는 내린다. 기다릴 때는 끊어서 기다리고 사이마다 살아 있는 하위를 다시 센다(superpowers SDD 의 「Waiting on dispatched subagents」 방식) — 기다리기만 하지 않는다. agent 를 보내거나 거둘 때마다 상태 계산의 동시 가능 목록과 승인된 설계의 남은 계획을 훑어, 의존 · 같은 파일 겹침 · 기다리는 답이 없는 일은 규모를 알리고 바로 보낸다 — 동시에 돌리는 큰 작업의 권장 수는 기본 3(레포 설정 파일이나 로드맵 머리말의 `parallel_default` 로 바꾼다)이고 상한이 아니다(사용자가 늘린다). 압축 · 새 세션 뒤에도 여기서 시작한다 — 무엇이 끝났는지 기억에 기대지 않는다. 이 세션에서 처음 부를 때는 `ledger orphans --roadmap <로드맵>` 의 「주인 모름」 worktree(고른 것만 지운다)와 `ledger version --plugin-json "<SD>"/.claude-plugin/plugin.json` 의 판 차이를 보인다. 상태가 「spec 승인됨(…) · 계획 없음」 인 에픽(승인 뒤 계획 agent 를 보내기 전에 끊겼거나 압축하고 다시 부른 경우)에는 걸음 3 의 보내기대로 계획 agent 를 보내되 먼저 아래를 본다 — `ledger live-agent --roadmap <로드맵> --epic <에픽> --work 계획` 이 1(없음)일 때만 계획 agent 를 보낸다 — 0 이면 이미 돌고 있어 보내지 않고 기다려 거두고, 3 이면 사유를 보이고 보내지 않는다. 보낼 때는 `ledger add --roadmap <로드맵> --session <세션> --section "살아 있는 agent" --cells "<이름> · <에픽> · 계획 · <worktree> · <때>"` 로 적는다.
  - 맞추기 순서(보낼 때 · 돌아올 때 · 진행 상황을 말할 때마다 같은 턴에): ① 하니스 agent 목록(`ListAgents`)을 조회해 `## 살아 있는 agent` · `## 작업` 표를 맞춘다 ② 상태 계산(위 `show --tasks`) ③ 돌고 있는 큰 작업 수 대 권장 수 ④ 모자라면 채우기 · 제안 ⑤ 「HH:MM 기준」(① 을 조회한 시각)을 붙여 보고한다.
  - 원천: 돌고 있는 agent 는 하니스 agent 목록, 에픽 단계는 git 상태 계산, 과제 진행은 각 구현의 실행 방식 원장(`ledger progress --roadmap <로드맵>` 이 원장마다 마지막 고친 시각 · 마지막 줄을 보인다)이다 — 기계 상태의 「살아 있는 agent」 · 「작업」 표는 사본이다. 표에만 있고 원천에 없는 줄은 지우고(`ledger drop`), 끝났는데 보고하지 않은 agent 는 거두거나 깨운다(`SendMessage`). 이름 없는 agent(하위 agent 가 띄운 agent)는 세지 않는다. 상태 · 개수는 이 턴에 조회한 것만 말한다 — 조회하지 않은 숫자는 말하지 않는다.
  - 완료 표시는 일이 끝났다는 뜻이 아니다(2026-10-19 실측): agent 가 자기 백그라운드 일(잠금 대기 스크립트 등)을 걸어 두고 턴을 끝내도 agent 목록에는 completed 로 보이고, 원장 거울도 늦게 갱신될 수 있다. completed 만으로 멈춤을 단정하지 않는다 — 원장의 마지막 줄 · 시각과 그 agent 알림의 「waiting on its own background work」 를 함께 본다. completed 인데 원장 마지막 줄이 오래됐고(얼마면 오래인지는 지휘자가 정해 보고에 밝힌다) 그 알림도 없거나, 판단이 모호하면 그 agent 에 한 줄 묻는다(`SendMessage` — 깨워 잇게 하는 것과 같은 길).
  - 잠금 대기는 멈춤이 아니라 줄이다: `ledger suite-lock --roadmap <로드맵>` 이 공유 스위트 잠금(지휘자의 스위트 대조와 하위 agent 의 전체 스위트가 같이 쓰는 잠금)의 경로 · 주인 · 잡은 시각을 낸다 — 상태를 말할 때 그 줄을 함께 보인다.
  - 병렬 권장 수: 세는 것은 지휘자가 돌리는 큰 작업(계획 · 구현 담당자 · 수리 구현처럼 오래 도는 일)이다 — 짧은 리뷰어와 하위 agent 가 띄운 agent 는 세지 않는다. 권장 수는 기본값이지 상한이 아니다 — 사용자가 늘리고, 파일이 겹치지 않거나 문서만 고치는 일이라 늘려도 품질이 괜찮아 보이면 지휘자가 이유와 함께 늘리자고 제안한다. 병목은 개수가 아니라 공유 스위트 잠금의 줄 · 같은 파일 겹침 · 지휘자의 옮김 부하다.
  - 모자라면 채우기: 돌고 있는 큰 작업이 권장 수보다 적으면 동시 가능 목록 · 승인된 설계의 남은 계획 · 정리 일 · 설계문서 `## 미룸` 에서 이 로드맵이 받는 행 가운데 의존 · 겹침 · 기다리는 답이 없는 일을 찾아 보내거나 제안한다.
  - 로드맵 밖 일도 한 곳에: 지휘자 수리 PR · 정리 일처럼 에픽에 매이지 않은 일도 `## 작업` 표(종류 · 이름 · 에픽 또는 「로드맵 밖」 · 단계 · 담당 agent · 근거 경로)에 적는다 — `ledger add --roadmap <로드맵> --session <세션> --section "작업" --cells "<종류> · <이름> · <에픽|로드맵 밖> · <단계> · <담당|없음> · <근거 경로>"`. 에픽 계획 · 구현도 같은 표에 적는다. 끝난 일은 단계 칸에 「끝」 으로 적거나 그 줄을 지운다(`ledger drop`) — 상태 보기는 단계가 「끝」 · 「끝남」 · 「머지됨」 인 줄만 끝으로 세고, 「완료」 · 「PR 머지됨」 같은 다른 낱말은 돌고 있는 일로 센다. 담당 agent 가 돌아오면(거두거나 내리면) 그 줄의 담당 칸을 「없음」 으로 바꾼다 — 상태 보기는 담당으로 돌고 있는 수를 센다. 수리 구현처럼 에픽에 매이지 않은 agent 는 이 표의 담당 칸에 이름을 적는다 — 상태 보기(`control_plane.py show <로드맵>`)는 `## 살아 있는 agent` 와 끝나지 않은 작업 줄의 담당을 합쳐 돌고 있는 수로 세고, 이 표와 권장 수 · 스위트 잠금을 함께 보이고, 작업 목록(`show --tasks`)은 「로드맵 밖」 줄을 더한다.
- 부를 skill: 없음.
- 기록: 없음 — 주인과 캐시를 맞춘 사실은 알림으로만.
- 기계 상태: `## PR`(캐시 고침) · `## 살아 있는 agent`(거둔 것 · 내린 것 빼기) · `## 작업`(로드맵 밖 일 포함 — 원천과 맞춤) · `## 실행 원장`(읽은 줄).

### 2. 사람 몫 모으기
- 기본값: 열린 결정마다 「지금 답할 수 있나」를 판정해, 답할 수 있는 것만 배경과 함께 하나씩 묻는다. 배경을 붙여 묻는 것은 지휘자가 정할 질문(흐름 승인 · 감사 · 계획 검토 · 옮긴 질문 · spec 승인)이다 — brainstorming 대화의 질문은 brainstorming 이 정한 모양 그대로다. 지휘자 질문은 질문 문장 앞머리에 에픽 이름을 쓴다(따로 된 첫 줄로 쓰지 않는다).
- 판단: 앞 에픽의 결과를 봐야 답할 수 있는 것은 아직 묻지 않는다. 답을 기다리는 동안 그 답에 기대는 일(같은 에픽의 다음 단계 · 의존 에픽 · 같은 파일을 고치는 에픽)은 진행하지 않는다 — brief · 설계 · 계획처럼 방향을 정하는 단계면 특히 그렇다. 계속 가는 것은 그 답과 무관한 일뿐이고 무관하다고 본 이유를 적는다. 판단이 서지 않으면 기다린다. 한 에픽의 설계 대화(brainstorming 의 첫 메시지부터 spec 리뷰의 승인 게이트까지)가 도는 동안 다른 에픽의 소식 · 돌아온 질문 · 멈춤은 받은 원문을 `ledger resource-dir --roadmap <로드맵> --kind relay --name <에픽>` 폴더의 파일(`relay-<순번>.md`)에 적어 두기만 하고, 그 대화의 메시지와 그 리뷰 게이트의 질문 호출에 섞지 않고 따로 된 메시지로 — 게이트와 게이트 사이, 대화가 끊긴 자리, 리뷰가 끝난 뒤 — 알리거나 묻는다. 사용자 몫 감사는 `ledger audit --roadmap <로드맵> --epic <에픽>` 의 후보 가운데 실제로 사용자가 정할 것만 모델이 골라 묻는다 — spec 승인 게이트 · 머지 전 확인 · 지휘자를 다시 불렀을 때. 에픽에 새 항목을 넣을 때는 기존 결정 · 원칙의 수리면 바로 넣고, 사용자에게 보이는 동작 · 새 요구 · 다른 에픽의 경계에 닿으면 (작으면 채팅 안의 짧은 설계로) brainstorming 을 거친다 — 고른 쪽과 이유를 한 줄로 보인다.
- 부를 skill: 없음(지휘자가 정할 질문은 `AskUserQuestion`. brainstorming 대화는 brainstorming 대로 열린 문장 질문이고 선택지는 막혔을 때만이다).
- 기록: 무관하다고 보고 계속 간 일과 그 이유 · 감사에서 물은 것과 답 → 그 에픽 설계문서 `## 지휘 기록`.
- 기계 상태: `## 기다리는 질문`(에픽 · 기대는 일 · 질문) · 받은 원문 파일은 `## 자원` 에 「질문 원문」 으로.

### 3. 다음 일 고르기와 보내기
- 기본값: 다음 에픽을 고르기 직전에 `ledger pr-refresh --roadmap <로드맵> --session <세션>` 으로 PR 캐시를 새로 채운 뒤 상태 계산(`python3 "<SD>"/scripts/control_plane.py show --tasks <로드맵>`)으로 준비된 에픽을 센다. 준비된 에픽마다 설계 흐름(brainstorming → spec-review → 계획 → 구현)이다. 사람에게 묻는 단계(brainstorming 의 질문 · 설계문서 점검의 질문 · spec 승인)는 이 세션이 한 번에 한 에픽씩, 의존 사슬의 앞쪽부터 직접 한다. 사용자에게 다른 세션을 열라는 줄을 주지 않는다 — 같은 세션의 `/compact` 뒤 이어 갈 줄만 준다.
- 판단: 조사 · 측정 · 결정처럼 설계 흐름이 맞지 않으면 고른 흐름 · 이유 · 산출물을 보이고 `AskUserQuestion` 으로 승인받는다(거절이면 설계 흐름). 승인된 흐름 · 산출물은 같은 폴더 `redecompose.md` 의 재분해 절차로 로드맵 `흐름:` · `산출물:` 칸에 적는다. brainstorming 의 입력과 지시는 같은 폴더 `epic-handoff.md` 의 에픽 넘김 줄이 싣는 것과 같다 — 그 줄을 사용자에게 주지 않고 이 세션의 입력으로 쓴다. brainstorming 대화는 superpowers 의 brainstorming 이 정한 모양(첫 메시지 · 열린 문장 질문 하나 · 되비춤)이고, 지휘 소식(상태 · 목록 · 다른 에픽 소식)은 그 메시지에 얹지 않는다. 묶음의 확정 항목은 다시 묻지 않고 되비춤으로 확인한다.
  - 에픽 worktree: 브랜치나 worktree 가 이미 있으면(압축 뒤 다시 부른 경우 등) 새로 만들지 않고 그것을 쓴다 — 그 브랜치를 체크아웃한 worktree 가 둘 이상이면 쓰지 않고 멈춰 보인다. 없으면 블록의 `브랜치:` 이름으로 먼저 만든다 — `git worktree add "$(python3 "<SD>"/scripts/conductor_ledger.py worktree-path --name <이름>)" -b <브랜치> origin/HEAD`. 하니스가 옮겨 갈 수 있는 폴더에 만들고, worktree 안에 있는 세션은 하니스의 새 worktree 만들기를 쓸 수 없어서 `git worktree add` 로 만든다. `브랜치:` 가 여럿이면 적힌 순서가 계획 순서이고, 다음 계획의 브랜치는 앞 계획이 머지됐으면 기본 브랜치에서, 아직이면 앞 계획의 브랜치에서 만든다(그 PR 을 쌓을 때의 주의는 걸음 5).
  - 옮겨 가는 길(2026-10-18 실측): 하니스의 worktree 옮겨 가기(`EnterWorktree`, 경로 지정)로 그 worktree 에 들어가 할 일을 하고 앞 자리로 돌아온다(앞 자리도 경로 지정으로, 메인 체크아웃이면 하니스의 worktree 나가기 `ExitWorktree` keep). 옮기기 전에 지금 자리의 쓰기(커밋 포함)를 끝낸다 — 옮긴 뒤 앞 자리는 다시 들어가기 전까지 읽기 전용이다. 세션이 옮기면 격리 없이 띄운 하위 agent 도 따라 옮긴다 — agent 가 일하는 동안 옮겨 다니려면 아래 「하위 agent 의 자리」 의 기본으로 보낸다. 하니스로 옮겨 갈 수 없으면(하니스 worktree 폴더 밖의 worktree 등) 메인 체크아웃에서 Bash 로 셸의 작업 폴더를 옮기고, 그것도 안 되면 그 에픽 담당 agent 가 두 부분으로 돌려보내는 길로 하고 그 사실을 알린다.
  - spec 리뷰: 설계문서는 이 세션이 brainstorming 끝에 써서 에픽 worktree 에서 커밋하고, spec 리뷰도 이 세션이 같은 skill(`/spec-distill:spec-review <설계문서 절대경로> --bundle <묶음 절대경로>`)로 직접 돌린다. 옮겨 간 뒤 `pwd` 와 `git rev-parse --show-toplevel` 이 그 worktree 인지 보고, 진입 사전 검사 줄의 `root=` 가 그 worktree 인지 확인한 뒤 리뷰한다 — 아니면 멈춘다. 리뷰 반영 커밋도 그 worktree 에서 한다. 리뷰 도중 압축되면 같은 설계문서 경로로 다시 부른다 — 리뷰 원장이 라운드 · 상한을 잇는다.
  - 승인 게이트: 지휘 세션이 돌린 리뷰라 spec-review 의 승인 게이트는 질문 하나다 — 「승인 — 계획 담당자에게」 · 「수정 필요」 · 「멈춤」. 승인이면 이 세션은 writing-plans 를 따르지 않고 게이트가 낸 writing-plans 줄을 계획 agent 의 입력 줄로 넘긴다 — 미커밋 확인 → 승인 줄 기록(`ledger record --spec <설계문서> --approval --date <YYYY-MM-DD> --choice "<고른 선택지 원문>"`) · 그 에픽 worktree 에서 커밋 → 기계 상태 저장(계획 agent 의 입력 줄은 `ledger resource-dir --roadmap <로드맵> --kind relay --name <에픽>` 폴더의 `plan-input.md` 에 두고 `## 자원` 에 적는다) → 같은 턴에 아래 보내기대로 계획 agent 를 보낸다. 「수정 필요」 는 spec-review 의 ③ 갈래로 가고, 「멈춤」 은 그 에픽만 멈춘다. 압축은 아래 `/compact 시점` 의 판단이다.
  - 보내기: 계획 agent 는 승인을 고른 에픽(같은 턴)과 걸음 1 이 「spec 승인됨(…) · 계획 없음」 으로 센 에픽(끊김 · 압축 뒤)에 보낸다 — 자리는 아래 「하위 agent 의 자리」, 글은 `conductor-dispatch.md` 의 계획 틀이고, 입력 줄은 위 relay 폴더의 `plan-input.md` 나 이 턴의 게이트에서, 파일이 없으면 spec-review 의 다음 세션 줄 틀로 다시 만든다. `ledger live-agent --roadmap <로드맵> --epic <에픽> --work 계획` 이 1(없음)일 때만 계획 agent 를 보낸다 — 0 이면 이미 돌고 있어 보내지 않고 기다려 거두고, 3 이면 사유를 보이고 보내지 않는다. 보낼 때는 `ledger add --roadmap <로드맵> --session <세션> --section "살아 있는 agent" --cells "<이름> · <에픽> · 계획 · <worktree> · <때>"` 로 적고 `## 작업` 표의 그 에픽 줄도 맞춘다. 하위에게 보내는 글에는 `ledger suite-lock --roadmap <로드맵>` 의 첫 줄(공유 스위트 잠금 경로)을 싣는다. 보낸 뒤는 끊기 좋은 자리다 — 맥락이 무거우면 `/compact 시점` 대로 압축을 권하고, 아니면 같은 턴에 다음 에픽의 설계로 간다. 의존 · 같은 파일 겹침(상태 계산의 동시 가능 목록)이 없으면 동시에 보낸다 — 띄우기 전에 규모(몇 agent · 무엇)를 알린다.
  - 하위 agent 의 자리(2026-10-15 · 10-18 실측): 세션이 worktree 격리 중이면 격리 없이 띄운 agent 는 세션의 «지금» worktree 에 묶이고, 세션이 옮기면 따라 옮긴다. agent 는 스스로 다른 worktree 로 옮겨 갈 수 없다(경로 지정 들어가기는 격리 agent 도 거절된다). 기본은 `isolation: "worktree"` 로 띄운 agent 가 자기 새 worktree 에서 `git switch --ignore-other-worktrees <에픽 브랜치>` 로 그 에픽 브랜치에 서는 것이다 — 앞 agent 의 작업 기록(실행 방식의 작업 폴더 — git 이 추적하지 않는다)이 있으면 백업에서 되살린다. 그동안 지휘 세션은 자유롭게 옮겨 다닌다. 지휘자 자신의 worktree 는 origin 기본 브랜치에 detached 로 두어 어느 에픽 브랜치도 쥐지 않는다. 보내기 전에 그 브랜치를 체크아웃한 에픽 worktree 가 깨끗한지 보고 `git -C <에픽 worktree> switch --detach` 로 그 브랜치를 놓는다(브랜치는 그대로다) — 같은 브랜치를 쥔 worktree 가 둘이면 옛 쪽 index 로 한 커밋이 agent 의 커밋을 조용히 되돌린다. 깨끗하지 않으면 보내지 않고 보인다. agent 가 일하는 동안 그 에픽의 기록은 `ledger add --section "쌓인 기록"` 으로 쌓았다가 돌아온 뒤 `ledger flush` 로 옮기고, 놓은 옛 worktree 에서는 커밋하지 않는다(브랜치를 놓은 자리의 커밋은 브랜치에 닿지 않는다). 돌아오면 agent 가 쓴 worktree 를 `## 자원` 의 그 에픽 worktree 로 바꿔 적고 그 브랜치에 쓸 때(기록 · PR)는 거기서 한다 — 놓은 옛 worktree 는 `ledger cleanup-check` 뒤 정리한다. 다른 길은 지휘 세션이 그 에픽 worktree 에 머문 채 격리 없이 보내는 것이다 — 그 agent 가 돌아올 때까지 그 worktree 를 떠나지 않는다. 격리된 자리(세션 · agent)의 셸은 복합 명령을 막으므로 스크립트 파일로 돌리고, 공유 체크아웃 쪽 파일(리뷰 엔진 원장 · 지휘 자원 폴더)은 Write 도구가 막혀 임시 파일에 쓴 뒤 `cp` 로 옮긴다.
- 부를 skill: `superpowers:brainstorming` · `superpowers:using-git-worktrees`(만들기는 위 `git worktree add`) · `/spec-distill:spec-review` · `superpowers:dispatching-parallel-agents`.
- 기록: 고른 흐름과 이유 · spec 승인 줄 → 그 에픽 설계문서 `## 지휘 기록`(에픽 worktree 에서 커밋).
- 기계 상태: `## PR`(새로 채움) · `## 자원`(에픽 worktree · 질문 원문 파일 · 계획 agent 의 입력 줄 파일 · agent 몫 임시 폴더 — 폴더는 `ledger resource-dir`) · `## 살아 있는 agent`(계획 agent) · `## 작업`.

### 4. 돌아오기
- 기본값: 백그라운드 agent 가 끝나면 알림이 온다 — 걸음 1 로 가서 맞추기 순서(① agent 목록 → ② 상태 계산 → ③ 돌고 있는 수 대 권장 수 → ④ 채우기 → ⑤ 기준 시각 붙여 보고)대로 다시 세고 작업 목록을 갱신한다. 실행 방식은 writing-plans 가 권하는 방식이고, 계획 검토는 계획에 설계에 없던 결정이 있을 때만 기다린다.
- 판단: 계획 agent 가 돌아오면 이 세션이 계획을 읽고 「설계에 없던 결정(범위 · 인터페이스 · 파일 배치 등)」 이 있는지 가른다 — 계획을 쓴 agent 가 스스로 가르지 않는다. 없으면 계획 경로만 보이고 새 구현 agent 를 보낸다(writing-plans 가 권한 실행 방식을 미리 받은 답으로). 있으면 그 결정들을 배경과 함께 사용자에게 묻고(걸음 2), 답 전에는 그 에픽의 구현을 보내지 않는다. 구현 중에는 맞추기마다 실행 방식 원장(SDD 면 그 worktree 작업 폴더의 `progress.md`)의 `Ruling:` 줄을 읽어 화면의 판정 줄에 올린다. 판정이 승인된 설계의 수용 기준 · 의도를 바꾸거나 구현이 막히면(SDD 의 BLOCKED 포함) 그 에픽만 멈추고 배경과 함께 묻는다 — 다른 에픽은 계속한다. 설계 안의 판정은 멈추지 않고 끝에 목록 전체를 보인다. 같은 자리(한 메커니즘의 보안 리뷰 등)가 라운드마다 새 막는 지적을 내면 라운드를 더하지 않고 설계의 대안 갈래로 일찍 옮긴다 — 설계 의도가 바뀌면 사용자에게 묻는다. 계획 중간에 돌아온 구현 agent 를 새 agent 로 바꿀 때는 먼저 옛 agent 가 띄워 아직 도는 하위 agent 를 하니스의 작업 멈추기(`TaskStop`)로 내린다 — 같은 브랜치에 두 writer 가 커밋하지 않게. agent 를 보내거나 거둘 때마다 상태 계산의 동시 가능 목록과 승인된 설계의 남은 계획을 훑어, 의존 · 같은 파일 겹침 · 기다리는 답이 없는 일은 규모를 알리고 바로 보낸다 — 동시에 돌리는 큰 작업의 권장 수는 기본 3(레포 설정 파일이나 로드맵 머리말의 `parallel_default` 로 바꾼다)이고 상한이 아니다(사용자가 늘린다).
  - 구현 agent 가 돌아오면 보고에서 판정 전체와 AC 보고 내용 전체를 거둔다(작업 폴더는 지워질 수 있어 경로에 기대지 않는다): 보고를 `ledger resource-dir --roadmap <로드맵> --kind report --name <에픽>` 폴더의 파일로 두고 → `ledger rulings --report <보고 파일> --ledger <원장 사본> --out <판정 파일>`(보고에도 원장에도 판정이 없으면 「판정 줄 — 셀 수 없음」 을 보인다) → 에픽 브랜치에 기본 브랜치를 merge 해 받는 곳 규칙이 최신 로드맵을 보게 한 뒤 `python3 "<SD>"/scripts/check_bundle_coverage.py --impl <설계문서> <AC 보고 파일>`(계획을 나눴으면 `--acs`)의 경고를 사용자에게 보인다 → `ledger write-sections --spec <설계문서> --plan <계획> --rulings <판정 파일> --impl-line "<대조 첫 줄>" --counts "<AC n개 중 …>"` → 에픽 worktree 에서 커밋 · push → `gh pr create -R "$(python3 "<SD>"/scripts/gh_repo.py slug)"` 로 PR 을 열고 그 출력의 마지막 줄(PR URL)로 `ledger pr-record --roadmap <로드맵> --session <세션> --epic <에픽> --pr <그 URL>` 을 부른 뒤 `ledger pr-refresh --roadmap <로드맵> --session <세션> --epic <에픽>` 으로 PR 캐시를 채운다. PR 이 이미 있어 `gh pr create` 가 실패하면 그 PR 의 번호를 `--pr <번호>`(숫자만)로 적고 그 판단과 이유를 보인다. `pr-record` 의 종료 코드 4 는 출력 줄 `PR #<번호> 이 에픽 <에픽> 와 맞지 않는다(…) — 아무것도 적지 않았다` 의 괄호 안 어긋난 칸이 `baseRefName` 하나뿐일 때만(앞 계획의 브랜치를 바탕으로 연 쌓인 PR) 예상된 결과이고 멈출 오류가 아니다 — 적지 않고 넘어가고 걸음 5 가 바탕을 바꾼 직후에 적는다. 그 밖의 0 아닌 종료 코드(다른 칸 — `headRefName` · `isCrossRepository` · `number` — 가 어긋났거나 PR URL 의 레포가 origin 이 아닌 4, 번호를 읽지 못한 2, 기계 상태 · gh · origin · 기본 브랜치를 확인하지 못한 3, 표지를 쥐지 않은 5)는 그 줄의 사유를 그대로 보이고 이 에픽의 번호 적기를 멈춘다 — `pr-refresh` 는 그대로 부른다.
- 부를 skill: writing-plans 가 권한 실행 방식(`superpowers:subagent-driven-development` · `superpowers:executing-plans`) — 구현 agent 안에서.
- 기록: 「설계에 없던 결정」 을 가른 결과와 이유 → 설계문서 `## 지휘 기록` · 판정 보관본(`## 판정` 아래 `### <계획>`) · `## 구현 대조 — <계획>` → 설계문서. 리뷰가 열려 있는 문서의 `## 결정 기록` 에 손으로 쓴 줄은 다음 리뷰에서 「허가 없이 바뀜」 으로 돌아온다. 사용자 결정 원문을 설계문서 `## 결정 기록` 에 남겨야 하면 갈래가 셋이다 — ① 그 문서의 리뷰가 열려 있으면 그 리뷰의 결정 줄 펜스(`decision-line` — 엔진 `log-decision`)로 쓴다 ② 리뷰 원장이 없으면(리뷰 전) 손으로 쓴다 — 첫 라운드가 기준선으로 받는다 ③ 리뷰가 닫혔으면 `## 결정 기록` 절 끝(마지막 계수 줄 아래)에 손으로 쓴다 — 다음 재리뷰가 그 줄을 기록으로 읽는다(재리뷰를 시작한 뒤에 쓴 줄은 다시 묻는다). 끝맺음을 건너뛰어 계수 줄이 없거나 계수 줄에 표지가 없는 옛 원장이면 재리뷰가 그 줄을 한 번 묻는다 — 「고친 대로 둠」으로 닫는다. 하위가 그 브랜치에서 일하는 중이면 바로 쓰지 않고 `ledger add --section "쌓인 기록"` 으로 쌓았다가 돌아온 뒤 `ledger flush` 로 한 번에 옮겨 커밋한다 — 같은 worktree 에 두 writer 를 두지 않는다.
- 기계 상태: `## 실행 원장`(에픽 · 계획 · 원장 경로 · 읽은 줄) · `## PR` · `## 에픽 PR`(적은 번호) · `## 살아 있는 agent`(구현 agent) · `## 작업` · `## 쌓인 기록`.

### 5. 머지 전 확인
- 기본값: PR 마다(문서만 고친 PR 도 — 모델이 읽는 skill · reference · 템플릿 · 리뷰어 프로필은 문서로 치지 않는다) `ledger pr-refresh --roadmap <로드맵> --session <세션> --epic <에픽>` 으로 PR 캐시를 새로 채운 뒤 스위트 대조 → 통합 리뷰 → 리뷰 뒤 반영 → 완료 전 확인을 한다. 건너뛴 확인은 무엇을 왜 건너뛰었는지 적는다.
- 판단:
  - 스위트 대조: `python3 "<SD>"/scripts/merge_check.py run --roadmap <로드맵> --branch <브랜치> --keep-merged`. 종료 코드 1(새 실패)이면 `superpowers:systematic-debugging` 으로 원인을 찾아 고치거나 이유를 적고, 4(이름으로 가르지 못한 단위)면 그 줄을 사용자에게 보이고, 5(다른 스위트가 공유 스위트 잠금을 쥐고 있다 — 하위 agent 의 전체 스위트와 같은 잠금이다)면 그 줄의 주인 · 잡은 시각을 보이고 끝난 뒤 다시 돌거나 `--wait <초>` 를 붙여 줄을 서고, 6(테스트 명령을 모른다)이면 사용자에게 한 번 물어 기계 상태 `## 레포 설정` 에 임시로 둔 뒤(`ledger add --roadmap <로드맵> --session <세션> --section "레포 설정" --cells "test_command · <명령>"` — 스위트 대조는 로드맵 · 레포 설정 파일에 없는 키를 이 줄에서 읽고 출처 「기계 상태(임시)」 로 알린다)(같은 키를 바꿀 때는 drop 뒤 add 한다) 레포 설정 파일에 올리자고 알리고, 7(테스트 없음)이면 「스위트 대조 없음」 을 알리고 통합 리뷰만 한다. 3(검사 불가)이면 사유를 그대로 보이고 그 PR 의 머지 준비를 멈춘다 — 충돌이면 걸음 6 의 충돌 처리와 같이 그 에픽만 멈추고 알린다. 하위가 본 실패가 이 대조에서 사라지면 경합으로 보고 알린다.
  - 통합 리뷰: `ledger review-pack --roadmap <로드맵> --epic <에픽> --branch <브랜치> --merged <합친 사본>` 이 이 PR diff · 열린 다른 에픽 diff · 충돌 미리 보기 · 앞선 인계 절 · 함께 진행된 에픽의 설계문서 전문(`intents.md`)을 한 폴더에 모은다. 그 폴더와 `superpowers:requesting-code-review` 의 리뷰 요청 틀로, 쓰기 도구가 없는 통합 리뷰어(지휘자 skill 본문의 dispatch 자리)를 해결자 `repo_defaults.py get review_model --roadmap <로드맵>` 의 값(모델 칸이 받는 이름일 때만 — 종료 코드 1 이면 세션 모델로 가며 알리고, 3 이면 사유 줄을 보이고 세션 모델로 간다)으로 부른다 — 이음매가 여럿이면 여럿을 동시에. 지적은 「이 PR 이 고침」 · 「뒤 에픽이 고침」으로 나눠 PR 본문 `## 통합 리뷰 인계` 절에 담당 에픽과 함께 적는다. 뒤 에픽의 통합 리뷰는 앞선 인계 절의 항목이 실제로 고쳐졌는지 확인한다. 리뷰어는 일곱째 이음매로 함께 진행된 에픽의 설계 의도(Goals · Non-goals · 결정 기록 · 판정)와 이 PR 이 어긋나는지 본다 — 경로가 겹치지 않아도 보고, 이 PR 이 앞 에픽의 의도를 망가뜨렸다는 지적은 「이 PR 이 고침」 이다.
  - 리뷰 뒤 반영: 고침은 `superpowers:receiving-code-review` 로 받는다. 동작 · 락 · 보안 경계 · 리뷰어 프로필을 바꾼 수정은 매번 좁은 재리뷰를 받고, 좁은 재리뷰는 PR 하나에 두 번까지다 — 첫 재리뷰를 보내기 전에 멈출 조건(남는 지적을 잔여로 공시하고 넘길 곳)을 PR 본문에 적는다. 동작을 바꾸지 않는 수정은 PR 본문에 「리뷰 뒤 반영(리뷰 라운드를 거치지 않았다)」 으로 적는다.
  - 쌓인 PR: 다음 계획의 PR 을 앞 계획 브랜치를 바탕(base)으로 열었으면 앞 PR 부터 머지하고, 머지 뒤 그 바탕 브랜치를 지우기 전에 위 PR 의 바탕을 기본 브랜치로 바꾼다 — 바탕 브랜치를 지우면 위 PR 이 닫히고 다시 열 수 없다. 바탕을 기본 브랜치로 바꾼 직후, 머지 명령을 준비하기 전에 `ledger pr-record --roadmap <로드맵> --session <세션> --epic <에픽> --pr <번호>` → `ledger pr-refresh --roadmap <로드맵> --session <세션> --epic <에픽>` 을 부른다.
  - 끝으로 `superpowers:verification-before-completion`. 릴리스 번호는 이때 정한다(먼저 머지되는 쪽이 낮은 번호). 머지 명령 줄만 준비하고 머지는 사용자가 한다. 리뷰가 끝나면 합친 사본과 리뷰 묶음을 `ledger cleanup` 으로 지운다.
- 부를 skill: `superpowers:systematic-debugging` · `superpowers:requesting-code-review`(틀) · `superpowers:receiving-code-review` · `superpowers:verification-before-completion`.
- 기록: 건너뛴 확인과 이유 · 「리뷰 뒤 반영」 → PR 본문과 그 에픽 설계문서 `## 지휘 기록`.
- 기계 상태: `## PR`(새로 채움) · `## 에픽 PR`(쌓인 PR 의 바탕을 바꾼 뒤 적은 번호) · `## 자원`(합친 사본 · 리뷰 묶음 · 통합 리뷰어) · `## 레포 설정`(물어 얻은 값).

### 6. 머지 뒤
- 기본값: 머지를 확인하면(상태 계산의 「머지됨」) 열린 에픽 브랜치마다 기본 브랜치를 merge 하고 스위트 대조를 다시 돈다. 남은 에픽을 재평가하고, 바뀔 때만 재분해 절차(`redecompose.md`)로 사용자 승인 뒤 로드맵 수정 PR 을 연다. 지휘자가 스스로 여는 PR(로드맵 수정 · 지휘자 수리)도 머지 전에 걸음 5 의 스위트 대조를 거친다. 머지된 에픽의 worktree 는 `ledger cleanup-check` 뒤 `ledger cleanup` 으로 지운다 — 남은 것이 있으면 보이고 묻는다. 브랜치는 지우지 않는다.
- 판단: 그 브랜치에서 agent 가 일하고 있으면 직접 merge 하지 않는다 — 돌아올 때까지 기다리거나, 다음 task 경계에서 merge 하라고 그 agent 에 전한다. merge 가 충돌하면 그 에픽만 멈추고 알린다. 받는 에픽이 머지되면 넘긴 항목이 처리됐는지 받은 쪽 설계문서의 번호 대조 · AC 보고 · 통합 리뷰로 확인한다. 넘김의 받는 곳이 `없음` 이거나 로드맵에 없는 이름이면(화면의 「받는 곳 없음」) 맡을 에픽을 제안하고, 그 에픽 범위에 없으면 재분해 절차로 사용자 승인 뒤 로드맵에 넣는다. 맡을 에픽이 없으면 GitHub 이슈(`#<n>`)를 받는 곳으로 쓸 수 있으나, 이슈를 새로 만드는 것은 그때마다 묻는다.
- 부를 skill: 없음.
- 기록: 넘김 확인은 `- 넘김 확인 · <준 에픽> · <키> · <근거>` 꼴(키는 `conductor_state.confirm_line` 이 만든다)로 — 받는 에픽이 아직 머지 전이면 그 설계문서 `## 지휘 기록` 에, 이미 머지됐으면 `ledger add --section "쌓인 기록"` 으로 쌓아 다음 로드맵 수정 PR 본문 `## 지휘 기록` 절에 싣는다(`ledger pending`). PR 본문에 실은 줄은 `ledger drop --roadmap <로드맵> --session <세션> --section "쌓인 기록" --where "글=<실은 글>"` 로 한 줄씩 뺀다 — 아직 설계문서로 옮길(`ledger flush`) 줄은 두고.
- 기계 상태: `## 쌓인 기록` · `## 자원`(지운 worktree 빼기).

### 7. 끝
- 기본값: 모든 에픽이 머지되면 끝에서 끝 확인 — 기본 경로(인터뷰 → 분해 → 에픽 설계 → spec-review → 계획 · 구현 대조 → 작업 목록 · 상태줄)와 설계 흐름이 아닌 에픽의 경로를 실제 명령으로 걷는다. 그때 품질 게이트(`/quality-gates:quality-pipeline`)를 한 번, 로드맵 시작 커밋부터 지금 기본 브랜치까지 돌린다.
- 판단: skill 목록에 `quality-gates:quality-pipeline` 이 없으면 「품질 게이트 없이 간다 — quality-gates 가 설치돼 있지 않다」를 알리고 진행한다. 품질 게이트가 범위 입력을 받는지는 그 skill 의 인자 안내로 정한다 — 받지 않으면 품질 게이트 없이 가고 그 사실을 알린다. 지적은 후속 PR 하나로. 넘김이 모두 처리됐는지 `python3 "<SD>"/scripts/control_plane.py show <로드맵> <에픽>` 의 열린 넘김으로 확인하고, 쌓인 기록이 남았으면 기록만 담은 로드맵 수정 PR 로 싣고 실은 줄은 걸음 6 처럼 뺀다. 쓴 자원을 `ledger resources` · `ledger orphans` 로 보고 정리한 뒤 표지를 푼다(`ledger release`).
- 부를 skill: `/quality-gates:quality-pipeline`(범위 입력이 있을 때).
- 기록: 끝에서 끝으로 걸어 본 결과 · 품질 게이트를 건너뛴 사실 → 마지막 로드맵 수정 PR 본문 `## 지휘 기록`.
- 기계 상태: `## 에픽 PR` 은 남기고 나머지를 비운다(남은 자원 · agent · 쌓인 기록이 없을 때) — 에픽 PR 번호 기록은 다시 만들 수 없고, 정리 뒤에도 상태 계산이 같은 번호로 머지를 판정한다.

### /compact 시점
승인 뒤 계획 agent 를 보낸 직후처럼 끊기 좋은 자리에서 맥락이 무거우면, 기록(설계문서 절)을 커밋하고 기계 상태를 저장한 뒤 두 줄을 준다 — `/compact` 와 `/spec-distill:epic-conductor <로드맵>`. 압축은 사용자만 한다. 압축 뒤에는 걸음 1 부터 한다.

### 알림
사람 답이 없어 에픽이 멈췄을 때와 모두 끝났거나 더 갈 일이 없을 때만 알림 도구(`PushNotification`)를 보낸다. 알림 도구가 없으면 멈춘 사실을 다음 응답 첫 줄에 쓴다.

## 손으로 따르는 절차

로드맵 하나를 따라 에픽들을 지휘하는 세션의 절차다. 걸음마다 기본값이다 — 일의 모양이 다르면 다르게 하고, 무엇을 왜 다르게 했는지 그 에픽 설계문서 `## 지휘 기록` 에(에픽에 매이지 않은 판단은 다음 로드맵 수정 PR 본문에) 적는다. 정석 흐름(brainstorming → 계획 → 구현)의 뜻은 지킨다.

- `<SD>` 는 spec-distill 플러그인 폴더의 절대경로, `<로드맵>` 은 로드맵 파일의 레포 루트 기준 경로다. `<SD>` 를 모르면 추측하지 말고(cwd 포함) 멈춰 사용자에게 묻는다.
- skill 목록에 `superpowers:` 로 시작하는 skill 이 하나도 없으면 이 절차를 시작하지 않는다 — `[spec-distill] 지휘 절차 멈춤 — superpowers 가 필요하다 — Claude Code 의 /plugin 에서 superpowers 를 설치한 뒤 다시 부른다` 를 보이고 멈춘다. superpowers skill 을 처음 불러온 직후 `python3 "<SD>"/scripts/check_deps.py superpowers --plugin-root "<SD>" --base "<그 skill 의 기준 폴더>"` 를 한 번 돌려 「다르다」 · 「확인하지 못했다」 줄(뒤의 이유 줄까지)을 그대로 보인다 — 판 확인 결과로는 멈추지 않는다.
- 레포마다 다른 값은 박지 않고 읽는다 — 기본 브랜치는 `origin/HEAD`, 브랜치 이름은 로드맵 블록의 `브랜치:`, 설계문서 · 계획 폴더 · 테스트 명령 · 리뷰 모델(`specs_dir` · `plans_dir` · `test_command` · `review_model`)은 해결자(`repo_defaults.py get`)가 로드맵 · 레포 설정 파일 · 기본값에서 낸다. 없으면 각각 superpowers 기본 폴더 · 레포 파일에서 찾은 러너 · 세션 모델을 쓰고, 한 번 물어 정한 값은 레포 설정 파일에 올리자고 알린다.
- 각 칸의 주인과 갱신 길은 같은 폴더의 `roadmap-ontology.md` 에 있다.

1. **맞추기.** `git fetch origin` 뒤 `python3 "<SD>"/scripts/control_plane.py show --tasks <로드맵>` 을 돌려 작업 목록을 결과에 맞춘다. 줄마다 `<제목><탭><작업 상태>` 이고 에픽 하나에 작업 하나다 — 제목은 그대로 쓰고, 상태가 `keep`(알 수 없음)이면 작업 상태는 두고 제목만 바꾼다. 종료 코드 3 이면 작업 목록을 바꾸지 않고 표준 오류의 「검사 불가」 사유를 사용자에게 그대로 보인다 — 일부 단계가 보여도 믿지 않는다. 종료 코드 4(로드맵이 아직 기본 브랜치에 없다 — 방금 나눠 머지 전)면 `python3 "<SD>"/scripts/roadmap_status.py --roadmap-file <로드맵>` 으로 대신 계산하고, 대기 · 준비는 시작 전, 설계 중 · 계획 · 구현 중 · 구현 끝 · PR · 일부 머지는 진행 중, 머지됨 · 끝남은 완료로 맞춘다. 살아 있는 agent 를 확인한다 — 하니스 agent 목록이 원천이고 지휘 세션이 적어 둔 표는 사본이다. 끝났는데 보고하지 않은 것은 거두고 놀고 있는 것은 내린다. 목록의 완료 표시는 일이 끝났다는 뜻이 아니다 — 자기 백그라운드 일을 걸어 두고 턴을 끝낸 agent 도 그렇게 보이니 원장의 마지막 줄 · 시각을 함께 보고, 모호하면 그 agent 에 한 줄 묻는다. 상태 · 병렬 수를 사용자에게 말하기 직전 같은 턴에 목록을 다시 조회하고 「HH:MM 기준」 을 붙인다 — 조회하지 않은 숫자는 말하지 않는다. 로드맵 밖 일(수리 PR · 정리 일)도 에픽 일과 같은 목록에 둔다. agent 를 보내거나 거둘 때마다 상태 계산의 동시 가능 목록과 승인된 설계의 남은 계획을 훑어, 의존 · 같은 파일 겹침 · 기다리는 답이 없는 일은 규모를 알리고 바로 보낸다 — 동시에 돌리는 큰 작업의 권장 수는 기본 3(레포 설정 파일이나 로드맵 머리말의 `parallel_default` 로 바꾼다)이고 상한이 아니다(사용자가 늘린다). 돌고 있는 큰 작업이 권장 수보다 적으면 남은 계획 · 정리 일 · 미룸 행 가운데 기다리는 답이 없는 일을 찾아 보내거나 제안한다. 압축 · 새 세션 뒤에도 여기서 시작한다 — 무엇이 끝났는지 기억에 기대지 않는다.
2. **에픽과 브랜치.** 준비 단계 에픽을 고른다. 블록의 `브랜치:` 이름으로 기본 브랜치에서 브랜치와 worktree 를 먼저 만들고(`superpowers:using-git-worktrees` — 이미 있으면 그것을 쓰되, 그 브랜치를 체크아웃한 worktree 가 둘 이상이면 쓰지 않고 멈춰 보인다), 그 에픽의 설계문서 · 계획은 모두 그 브랜치에 커밋한다. `브랜치:` 가 여럿이면 적힌 순서가 그 에픽 설계문서가 나눈 계획의 순서다 — 다음 계획의 브랜치는 앞 계획이 머지됐으면 기본 브랜치에서, 아직이면 앞 계획의 브랜치에서 만든다. 사람에게 묻는 단계(brainstorming 의 질문 · 설계문서 점검의 질문 · spec 승인)는 사람이 보는 세션에서 한 번에 한 에픽씩, 의존 사슬의 앞쪽부터 한다 — 백그라운드 agent 에는 질문 도구가 없다. spec 승인은 사용자가 에픽마다 한다. 지휘 세션의 기본 자리는 어느 worktree 에도 속하지 않은 메인 체크아웃(`git worktree list` 의 첫 줄)이다. worktree 안에서 시작됐으면 시작할 때 그 사실을 알린다 — 그 자리에서도 지휘한다. 에픽 worktree 로는 하니스의 worktree 들어가기(경로 지정)로 옮겨 가고, 볼 일을 마치면 앞 자리로 돌아온다 — 옮기기 전에 지금 자리의 쓰기(커밋 포함)를 끝낸다. 하니스로 옮겨 갈 수 없으면(하니스 worktree 폴더 밖 등) 메인 체크아웃에서 셸의 작업 폴더를 옮기고, worktree 를 떠날 수 있는지(하니스의 worktree 나가기 · 들어가기)마저 막히면 다른 에픽의 spec 리뷰는 그 에픽 담당 agent 를 거쳐(4 의 두 부분 반환) 하고 그 사실을 알린다 — 사용자에게 다른 세션을 열라고 하지 않는다. 에픽 worktree 는 하니스 worktree 폴더 아래에 `git worktree add` 로 만든다(worktree 안에 있는 세션은 하니스의 새 worktree 만들기를 쓸 수 없다). 한 에픽의 설계 대화(brainstorming 의 첫 메시지부터 spec 리뷰의 승인 게이트까지)가 도는 동안 다른 에픽의 소식 · 돌아온 질문 · 멈춤은 받은 원문을 git 이 추적하지 않는 파일에 적어 두기만 하고, 그 대화의 메시지와 그 리뷰 게이트 질문에 섞지 않고 따로 된 메시지로 게이트와 게이트 사이, 대화가 끊긴 자리, 리뷰가 끝난 뒤 알리거나 묻는다. 지휘자가 정할 질문(흐름 승인 · 감사 · 계획 검토 · 옮긴 질문 · spec 승인)은 `AskUserQuestion` 으로 배경과 함께 묻고 질문 문장 앞머리에 에픽 이름을 쓴다 — brainstorming 대화는 brainstorming 대로 열린 문장 질문이고 선택지는 막혔을 때만이다.
3. **흐름과 설계.** 에픽의 흐름은 기본이 설계 흐름(brainstorming → spec-review → 계획 → 구현)이다. 조사 · 측정 · 결정처럼 맞지 않는 에픽은 맞는 흐름을 고르되, 시작하기 전에 고른 흐름 · 이유 · 산출물을 보이고 `AskUserQuestion` 으로 승인받는다 — 설계 흐름의 spec 승인을 대신하는 자리이고, 거절되면 설계 흐름으로 간다. 승인된 흐름 · 산출물은 로드맵 블록의 `흐름:` · `산출물:` 칸에 같은 폴더 `redecompose.md` 의 재분해 절차로 적는다. 지휘 세션은 사람에게 묻는 부분(brainstorming 의 질문 · 설계문서 점검의 질문 · spec 승인)을 한 번에 한 에픽씩, 의존 사슬의 앞쪽부터 직접 하고 설계문서도 직접 써서 에픽 브랜치에 커밋한다 — brainstorming 의 입력과 지시는 같은 폴더 `epic-handoff.md` 의 에픽 넘김 줄이 싣는 것(묶음 첨부 · 번호째 읽기 · 번호 대조 표 · frontmatter · AC 번호 · 있는 것 검토 · 상류 · 하류 연계 · 레포 전용 값 · 계층 · 온톨로지 · 크기 선호 · 확정 항목 되비춤)과 같다 — 지휘 소식은 brainstorming 메시지에 얹지 않는다. spec-review 도 지휘 세션이 직접 돌린다 — 부르기 전에 그 에픽 worktree 로 옮겨 가(2 의 길 — 하니스의 들어가기, 안 되면 셸의 작업 폴더) `pwd` 와 `git rev-parse --show-toplevel` 이 그 worktree 인지 보고, 설계문서 절대경로 뒤에 `--bundle <묶음 절대경로>`(설계문서 frontmatter `source_interview` 와 같은 파일)를 붙여 `/spec-distill:spec-review` 를 부른다. 진입 사전 검사 줄의 `root=` 가 그 worktree 가 아니면 멈춘다 — 메인 체크아웃에서 그냥 부르면 묶음과 코드를 메인 쪽 사본으로 조용히 읽고, 리뷰 반영 커밋이 메인 브랜치로 간다. `--bundle` 값이 설계문서 frontmatter `source_interview` 와 다르거나 읽을 수 없으면 리뷰하지 않고 끝나고, 같으면 진입에서 번호 대조를 보인 뒤 계속한다(빠진 번호 · 얕은 답 · 받드는 에픽 없는 발화 · 검사 불가는 막지 않고 승인 게이트의 「경고 N개」에 더해진다). 리뷰 내내 그 worktree 에 머물고 커밋도 거기서 한다. 리뷰 도중 압축되면 같은 설계문서 경로로 spec-review 를 다시 부른다 — 리뷰 원장이 라운드 · 상한을 잇는다. 지휘 세션이 돌린 리뷰라 승인 게이트는 질문 하나(「승인 — 계획 담당자에게」 · 「수정 필요」 · 「멈춤」)다. 승인이면 지휘 세션은 게이트가 낸 다음 세션 줄의 writing-plans 를 직접 따르지 않고 그 줄을 계획 agent 에게 넘긴다. 승인한 날짜와 고른 선택지 원문은 미커밋 확인 뒤 그 에픽 worktree 에서 설계문서 `## 지휘 기록` 에 한 줄로 커밋한다. 그다음 메인 체크아웃으로 돌아온다(worktree 안에서 시작한 세션이면 앞 자리로 — 다른 길로 그 에픽 worktree 에 머문 채 보낼 때는 돌아오지 않는다). 그리고 같은 턴에 계획 agent 를 보낸다 — 압축은 아래 **/compact.** 의 판단이고, 끊김 · 압축 뒤에는 걸음 1 이 승인 줄은 있고 계획은 없는 에픽을 찾아 보낸다. 「수정 필요」 는 spec-review 의 ③ 갈래로 가고, 「멈춤」 은 그 에픽만 멈춘다. 사용자에게 다른 세션을 열라고 하지 않는다 — 사용자가 에픽을 자기 세션에서 따로 진행하겠다고 하면 그 세션의 첫 줄로 에픽 넘김 줄(자리표를 채우고, 줄 안의 플러그인 루트 변수는 `<SD>`(이 세션이 쓰는 spec-distill 플러그인 폴더의 절대경로)로 — 레포 자체에 그 플러그인 소스가 있으면 그 에픽 worktree 의 사본을 써도 된다)을 준다. spec 이 승인되면 지휘 세션은 계획 · 구현으로 들어가지 않고 그 에픽 브랜치의 백그라운드 agent 에 계획을 보낸 뒤 다음 에픽의 설계로 간다 — 맥락이 무거우면 그 전에 압축을 권한다. 하위 agent 의 자리는 지휘 순환 걸음 3 의 「하위 agent 의 자리」 와 같다 — 기본은 `isolation: "worktree"` 로 띄운 agent 가 자기 worktree 에서 `git switch --ignore-other-worktrees <에픽 브랜치>` 로 그 브랜치에 서는 것이고(보내기 전에 에픽 worktree 는 그 브랜치를 놓는다 — `switch --detach`), 다른 길은 지휘 세션이 그 에픽 worktree 에 머문 채 격리 없이 보내고 agent 가 돌아올 때까지 떠나지 않는 것이다. 계획이 없는 에픽이라도 `python3 "<SD>"/scripts/conductor_ledger.py live-agent --roadmap <로드맵> --epic <에픽> --work 계획` 이 1(없음)일 때만 계획 agent 를 보낸다 — 0 이면 이미 돌고 있어 보내지 않고 기다려 거두고, 3 이면 사유를 보이고 보내지 않는다. 보낼 때는 같은 스크립트의 `add --roadmap <로드맵> --session <세션> --section "살아 있는 agent" --cells "<이름> · <에픽> · 계획 · <worktree> · <때>"` 로 적는다(표지는 `claim` 으로 먼저 잡고 `<세션>` 은 `state_path.py session-id` 의 값).
4. **superpowers 가 묻는 자리.** 사람이 보는 세션에서 만난 자리는 사용자가 그 자리에서 답한다. 백그라운드 agent 가 만나는 자리는 보낼 때 적어 준 답으로 간다. 적어 준 답이 없는 자리(writing-plans 가 끝에 묻는 계획 검토 등)에서 agent 는 멈추고 (a) 사람에게 보일 쉬운 요약(무엇을 정하나 · 고르면 무엇이 달라지나 · 배경, 내부 기호는 괄호에만)과 (b) skill 이 낸 문면 · 선택지 원문을 함께 돌려보낸다. 지휘 세션은 배경을 먼저 쉬운 말로 쓰고 질문만 봐도 결정할 수 있게 묻는다 — 선택지의 수 · 순서 · 라벨(돌려줄 값) · skill 자신의 「(권장)」 표시와 사용자 답은 글자 그대로 두고, 각 선택지 설명은 원문의 「고르면 무엇이 달라지나」(그대로 두면 · 고치면)를 빠뜨리지 않으며, 지휘 세션의 의견은 선택지 밖 「지휘자 의견:」 한 줄로만 쓰고, 원문은 늘 붙인다. 사용자 답은 글자 그대로 같은 agent 에 돌려보내 이어 가게 한다. 선택지로 받을 수 없는 답(사용자가 직접 써야 하는 것)은 게이트 밖에서 따로 묻고 그 사실과 이유를 적는다. 그대로 전할 수 없는 자리는 지휘 세션이 그 자리를 직접 돌리고 이유를 설계문서 `## 지휘 기록` 에 적는다. 실행 방식은 writing-plans 가 권하는 방식이다. 계획 검토는 지휘 세션이 계획을 읽고 설계에 없던 결정(범위 · 인터페이스 · 파일 배치 등)이 있는지 가린다 — 있으면 그 결정들을 배경과 함께 사용자에게 묻고 답 전에는 그 에픽의 구현을 보내지 않으며, 없으면 계획 경로만 보이고 구현을 보낸다. 가른 결과와 이유는 그 에픽 설계문서 `## 지휘 기록` 에 적는다. 리뷰가 열려 있는 문서의 `## 결정 기록` 에는 손으로 쓰지 않는다(다음 리뷰에서 「허가 없이 바뀜」 으로 돌아온다). 사용자 결정 원문을 설계문서 `## 결정 기록` 에 남겨야 하면 갈래가 셋이다 — ① 그 문서의 리뷰가 열려 있으면 그 리뷰의 결정 줄 펜스(`decision-line` — 엔진 `log-decision`)로 쓴다 ② 리뷰 원장이 없으면(리뷰 전) 손으로 쓴다 — 첫 라운드가 기준선으로 받는다 ③ 리뷰가 닫혔으면 `## 결정 기록` 절 끝(마지막 계수 줄 아래)에 손으로 쓴다 — 다음 재리뷰가 그 줄을 기록으로 읽는다(재리뷰를 시작한 뒤에 쓴 줄은 다시 묻는다). 끝맺음을 건너뛰어 계수 줄이 없거나 계수 줄에 표지가 없는 옛 원장이면 재리뷰가 그 줄을 한 번 묻는다 — 「고친 대로 둠」으로 닫는다. 머지 메뉴는 「브랜치 그대로 두기」다 — Push 와 PR 은 지휘 세션이 구현 대조(5) 뒤에 한다. 보낼 때 기준 브랜치도 적어 준다. 사용자가 그 자리에서 다르게 말하면 그 말을 따른다.
5. **계획 · 구현.** 계획 agent 는 writing-plans 로 계획을 쓰고 커밋한 뒤 `python3 "<SD>"/scripts/check_bundle_coverage.py --plan <설계문서> <계획>` 을 돌려 계획에 없는 AC 를 계획에 더한다 — 설계가 계획을 여럿으로 나눴으면 `--acs` 뒤에 그 계획이 맡은 AC 목록을 준다. 구현은 에픽마다 그 worktree 의 백그라운드 agent 가 하고, 그동안 다음 에픽의 설계를 진행한다. 의존 · 같은 파일 겹침이 없는 에픽은 동시에 보내되 띄우기 전에 규모를 알린다. 고른 실행 방식의 마지막 전체 리뷰가 AC 마다 한 줄(`AC1: 구현됨 — 근거` 꼴, 판정은 구현됨 · 미룸 · 빠짐)로 보고하게 하고, agent 의 마지막 보고에 판정 목록 전체와 그 AC 보고 내용 전체를 싣게 한다 — 실행 방식이 작업 폴더를 지울 수 있다. 판정 목록은 멈추지 않고 그대로 사용자에게 보인다. 다만 판정이 승인된 설계의 수용 기준 · 의도를 바꾸거나 구현이 막히면 그 에픽만 멈추고 배경과 함께 묻는다 — 다른 에픽은 계속한다. 돌아오면 AC 보고를 git 이 추적하지 않는 파일에 두고, 미룸 · 빠짐과 리뷰 후속으로 미룬 것을 설계문서 `## 미룸` 표(항목 · 이유 · 받는 곳)에 올린 뒤 `python3 "<SD>"/scripts/check_bundle_coverage.py --impl <설계문서> <그 보고 파일>`(계획이 여럿이면 같은 `--acs`)을 돌려 경고를 사용자에게 보인다. 그다음 설계문서에 `## 판정` 절(판정 목록 그대로 — 절이 이미 있으면 그 아래 `### <계획 경로>` 로 잇는다. 앞 계획의 판정 줄이 하위 머리 없이 있으면 먼저 그 줄들을 `### <앞 계획 경로>` 아래로 옮긴다 — 같은 머리가 둘이거나 머리 단계가 섞이면 상태 계산이 그 절을 읽지 못한다)과 `## 구현 대조 — <계획 경로>` 절(대조 첫 줄 · AC 판정 수)을 에픽 브랜치에 커밋하고 Push · PR 을 연다(`gh pr create -R "$(python3 "<SD>"/scripts/gh_repo.py slug)"`) — 그 출력의 마지막 줄(PR URL)로 `python3 "<SD>"/scripts/conductor_ledger.py pr-record --roadmap <로드맵> --session <세션> --epic <에픽> --pr <그 URL>` 을 부른 뒤 `python3 "<SD>"/scripts/conductor_ledger.py pr-refresh --roadmap <로드맵> --session <세션> --epic <에픽>` 으로 PR 캐시를 채운다(표지는 `claim` 으로 먼저 잡는다). `pr-record` 의 종료 코드 4 는 출력 줄 `PR #<번호> 이 에픽 <에픽> 와 맞지 않는다(…) — 아무것도 적지 않았다` 의 괄호 안 어긋난 칸이 `baseRefName` 하나뿐일 때만(앞 계획의 브랜치를 바탕으로 연 쌓인 PR) 예상된 결과이고, 걸음 8 이 바탕을 바꾼 직후 적는다. 그 밖의 0 아닌 종료 코드(다른 칸 — `headRefName` · `isCrossRepository` · `number` — 가 어긋났거나 PR URL 의 레포가 origin 이 아닌 4, 번호를 읽지 못한 2, 기계 상태 · gh · origin · 기본 브랜치를 확인하지 못한 3, 표지를 쥐지 않은 5)는 그 줄의 사유를 그대로 보이고 이 에픽의 번호 적기를 멈춘다 — `pr-refresh` 는 그대로 부른다.
6. **머지 뒤.** 에픽이 머지될 때마다 남은 에픽을 재평가하고, 바뀔 때만 같은 폴더 `redecompose.md` 의 재분해 절차로 사용자 승인 뒤 로드맵 수정 PR 을 올린다. 열린 에픽 브랜치에는 기본 브랜치를 merge 하고 대조(8)를 다시 돈다 — 그 브랜치에서 agent 가 일하는 중이면 직접 merge 하지 않고 돌아올 때까지 기다린다. merge 가 충돌하면 그 에픽만 멈추고 알린다. 받는 에픽이 머지되면 넘긴 항목이 처리됐는지 그 설계문서의 번호 대조 · AC 보고로 확인한다. 머지는 사용자가 한다.
7. **`Spec:` 트레일러.** 구현 커밋에는 `Spec: <에픽 설계문서 레포 상대경로>` 트레일러를 단다 — 보내는 글에 적어 준다.
8. **머지 전 확인.** PR 마다 아래 셋을 한다(문서만 고친 PR 도 — 모델이 읽는 skill · reference · 템플릿 · 리뷰어 프로필은 문서로 치지 않는다). 하나라도 건너뛰면 무엇을 왜 건너뛰었는지 적는다.
   - **스위트 대조.** 그 시점 기본 브랜치에 이 브랜치를 merge 한 별도 worktree(합친 사본)와 기본 브랜치 사본에서 그 레포의 스위트를 돌려 실패 «이름» 을 양방향으로 대조한다 — 이 브랜치에만 있는 실패와 기본 브랜치에만 있는 실패. 무엇을 돌리나: 로드맵 frontmatter `test_command` 가 있으면 그것, 없으면 레포 파일에서 찾은 러너(pytest · unittest · 셸 · node 등)의 전체 스위트다. 스위트가 너무 오래 걸리는 레포에서만 범위를 좁히고 이유를 적는다. 이름은 러너 출력에서 뽑는다(pytest `-rf` 의 `FAILED` 줄 · unittest 의 `FAIL:` · `ERROR:` 줄 · node `--test-reporter=tap` 의 `not ok` 줄 · 셸 테스트의 실패 표시 줄) — 뽑을 수 없으면 「이름 대조 불가 — 파일 단위만」 이라고 적는다. 사본을 만들기 전에 남은 merge 를 abort 하고, `git fetch` 뒤 대조할 브랜치의 SHA 를 한 줄로 남긴다. 스위트 둘을 같은 시각에 돌리지 않는다(잠금 — 예: `mkdir` 잠금과 종료 시 해제 · 백그라운드 agent 의 전체 스위트와 같은 잠금 하나) — 공유 임시 자원 경합이 거짓 실패를 낸다. 실행 중인 스크립트 파일은 고치지 않는다. 기본 브랜치가 움직이면 다시 돈다. 테스트가 없는 레포면 「스위트 대조 없음」을 적고 통합 리뷰만 한다.
   - **통합 리뷰.** 쓰기 도구가 없는 리뷰어를 해결자 `repo_defaults.py get review_model --roadmap <로드맵>` 의 값(받는 이름일 때만 — 종료 코드 1 이면 세션 모델로 가며 알리고, 3 이면 사유 줄을 보이고 세션 모델로 간다)으로 부른다(`superpowers:requesting-code-review`) — 하나로 충분하면 하나, 이음매가 여럿이면 여럿을 동시에. 합친 사본 · 이 PR 의 diff · 아직 열린 다른 에픽의 기본 브랜치 대비 diff · 앞선 통합 리뷰가 이 PR 에 넘긴 항목 · 함께 진행된 에픽의 설계문서 전문(`python3 "<SD>"/scripts/conductor_ledger.py review-pack` 의 `intents.md`)을 주고 에픽 사이 이음매를 묻는다: 옮겨진 이름의 import, 같은 파일을 고친 에픽들의 순서와 문구, 상태 · 경로 규약, 줄 상한 · 버전 같은 합계 제약, 테스트가 못 잡는 되살아난 옛 문구, 리뷰어 프로필의 규칙 제거 · 기준 완화(사용자 결정이 있는지), 함께 진행된 에픽의 설계 의도(Goals · Non-goals · 결정 기록 · 판정)와 이 PR 의 어긋남(경로가 겹치지 않아도). 충돌은 실제 merge 없이 `git merge-tree` 로 미리 본다. 지적은 「이 PR 이 머지 전 고침」과 「뒤에 머지되는 에픽이 고침」으로 나눠 이 PR 본문의 `## 통합 리뷰 인계` 절에 담당 에픽과 함께 적는다. 뒤 에픽의 통합 리뷰에는 앞서 머지된 PR 과 아직 열린 PR 의 그 절을 모아 주고(블록의 `브랜치:` 마다 `gh pr list --state all --head <브랜치>`) 실제로 고쳐졌는지 확인시킨다.
   - **리뷰 뒤 반영.** 리뷰 지적을 고친 수정은 같은 리뷰어로 좁게 한 번 다시 본다(`superpowers:receiving-code-review`). 그 뒤 동작을 바꾸지 않는 수정(문구 · 주석 · 번호 — 단 모델이 읽는 파일의 문구 수정은 동작을 바꾸는 수정이다)은 다시 돌지 않고 PR 본문에 「리뷰 뒤 반영(리뷰 라운드를 거치지 않았다)」으로 적는다. 동작을 바꾸는 수정, 그리고 락 · 보안 경계 · 리뷰어 프로필을 바꾼 수정은 매번 좁은 재리뷰를 한 번 받는다. 좁은 재리뷰는 첫 리뷰 뒤부터 세어 PR 하나에 두 번까지다 — 첫 재리뷰를 보내기 전에 멈출 조건(그 뒤에도 남는 지적을 잔여로 공시하고 넘길 곳)을 정해 PR 본문에 적는다. 두 번째 재리뷰 뒤 남는 지적은 고치지 않고 멈출 조건대로 넘기거나, 고치려면 사용자에게 묻는다.
   다음 계획의 PR 을 앞 계획 브랜치를 바탕(base)으로 열었으면(쌓인 PR) 앞 PR 부터 머지하고, 그 바탕 브랜치를 지우기 전에 위 PR 의 바탕을 기본 브랜치로 바꾼다 — 지우면 위 PR 이 닫히고 다시 열 수 없다. 바탕을 기본 브랜치로 바꾼 직후, 머지 명령을 준비하기 전에 `python3 "<SD>"/scripts/conductor_ledger.py pr-record --roadmap <로드맵> --session <세션> --epic <에픽> --pr <번호>` → `python3 "<SD>"/scripts/conductor_ledger.py pr-refresh --roadmap <로드맵> --session <세션> --epic <에픽>` 을 부른다.
   끝으로 `superpowers:verification-before-completion` 을 따른다. 릴리스 번호는 머지 직전에 정한다 — 먼저 머지되는 쪽이 낮은 번호다. 머지 명령 줄만 준비하고 머지는 사용자가 한다.
9. **끝.** 로드맵의 에픽이 모두 머지되면 처음부터 끝까지 실제 명령으로 걸어 본다(끝에서 끝 확인) — 기본 경로(인터뷰 → 분해 → 에픽 설계 → spec-review → 계획 · 구현 대조 → 작업 목록 · 상태줄)와, 설계 흐름이 아닌 에픽(조사 · 측정 · 결정)이 있으면 그 경로도 한 흐름으로 이어지는지 본다. 넘긴 항목이 모두 처리됐는지 확인하고, 지휘 세션과 agent 가 만든 worktree · 사본 · 잠금 · 임시 폴더를 정리한다 — 브랜치는 지우지 않는다. 지우기 전에 수정 · 추적 안 된 파일이 있으면 보이고 묻는다. 끊긴 곳은 사용자에게 보이고 로드맵 수정이나 다음 일로 넘긴다.

**/compact.** 에픽 하나의 spec 리뷰가 끝나 계획 agent 를 보낸 직후처럼 끊기 좋은 자리에서 맥락이 무거우면, 기록을 커밋한 뒤 `/compact` 를 권하고, 압축 뒤 이 세션에 칠 이어 갈 줄을 함께 준다 — 「`<SD>` 의 references 폴더에 있는 이 절차 파일(conducting.md)을 다시 읽고 `<로드맵>` 지휘를 걸음 1 부터 잇는다」(`<SD>` · `<로드맵>` 은 채워서). 압축은 사용자가 하고, 압축 뒤에는 1 부터 다시 한다.
