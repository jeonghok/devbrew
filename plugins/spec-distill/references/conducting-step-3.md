### 3. 다음 일 고르기와 보내기
- 읽을 것: `<SD>/references/conductor-dispatch.md`(이 대화에서 담당자를 처음 보낼 때) · `<SD>/skills/epic-conductor/references/qg-review.md`(spec 승인 앞)
- 남기는 것: 그 에픽 설계문서 `## 지휘 기록`(고른 흐름과 이유 · spec 승인 줄 · 병렬 답 줄 — 에픽 worktree 에서 커밋) · 옮김 폴더의 `plan-input.md` · 기계 상태의 `## PR` · `## 자원` · `## 살아 있는 agent` · `## 작업` · `## 쌓인 기록`.
- 기본값: 다음 에픽을 고르기 직전에 `ledger pr-refresh --roadmap <로드맵> --session <세션>` 으로 PR 캐시를 새로 채운 뒤 상태 계산(`python3 "<SD>"/scripts/control_plane.py show --tasks <로드맵>`)으로 준비된 에픽을 센다. 준비된 에픽마다 설계 흐름(brainstorming → spec-review → 계획 → 구현)이다. 머지 앞 리뷰의 「잘못 골랐다」 로 설계 대화에 돌아간 에픽은 상태 계산이 「구현 끝」 · 「PR」 이어도 이 설계 흐름을 다시 탄다 — 그 길은 `qg-review.md` 의 `## 「잘못 골랐다」 의 행선` 이다. 사람에게 묻는 단계(brainstorming 의 질문 · 설계문서 점검의 질문 · spec 승인)는 이 세션이 한 번에 한 에픽씩, 의존 사슬의 앞쪽부터 직접 한다. 사용자에게 다른 세션을 열라는 줄을 주지 않는다 — 같은 세션의 `/compact` 뒤 이어 갈 줄만 준다. 설계 전 조사는 꼼꼼히(`epic-handoff.md` 의 조사 문장 — 있는 것 검토 절에 적고, 다른 에픽이 예약한 파일이면 재분해 신호), 계획의 첫 과제는 가벼운 다시 확인이다(`conductor-dispatch.md` 계획 틀).
- 판단: 조사 · 측정 · 결정처럼 설계 흐름이 맞지 않으면 고른 흐름 · 이유 · 산출물을 보이고 `AskUserQuestion` 으로 승인받는다(「<고른 흐름>으로 (권장)」 · 「설계 흐름으로」 — 거절이면 설계 흐름). 설명은 이렇게 쓴다 — 「<고른 흐름>으로」: 얻음: 이 에픽에 맞는 흐름으로 바로 간다 · 내줌: 설계 → 리뷰 → 계획 → 구현의 spec 승인을 거치지 않는다 / 「설계 흐름으로」: 얻음: 설계 → 리뷰 → 계획 → 구현의 정해진 길을 탄다 · 내줌: 조사 · 측정 에픽이면 설계문서가 산출물과 안 맞는다. 승인된 흐름 · 산출물은 같은 폴더 `redecompose.md` 의 재분해 절차로 로드맵 `흐름:` · `산출물:` 칸에 적는다. brainstorming 의 입력과 지시는 같은 폴더 `epic-handoff.md` 의 에픽 넘김 줄이 싣는 것과 같다 — 그 줄을 사용자에게 주지 않고 이 세션의 입력으로 쓴다. brainstorming 대화는 superpowers 의 brainstorming 이 정한 모양(첫 메시지 · 열린 문장 질문 하나 · 되비춤)이고, 지휘 소식(상태 · 목록 · 다른 에픽 소식)은 그 메시지에 얹지 않는다. 묶음의 확정 항목은 다시 묻지 않고 되비춤으로 확인한다. 설계를 시작하는 에픽마다 `superpowers:brainstorming` 을 다시 부른다 — 같은 세션에서 앞 에픽 때 부른 것으로 갈음하지 않는다. 설계문서는 사용자가 접근을 고른 뒤에 쓴다 — 묶음의 확정 항목에 대한 되비춤만으로, 조사 결과에 대한 한마디 수락만으로 쓰지 않는다. 답이 추천 수락으로만 이어지면 사용자만 답할 수 있는 물음(무엇을 왜)을 물었는지 다시 본다.
  - 에픽 worktree: 브랜치나 worktree 가 이미 있으면(압축 뒤 다시 부른 경우 등) 새로 만들지 않고 그것을 쓴다 — 그 브랜치를 체크아웃한 worktree 가 둘 이상이면 쓰지 않고 멈춰 보인다. 없으면 블록의 `브랜치:` 이름으로 먼저 만든다 — `git worktree add "$(python3 "<SD>"/scripts/conductor_ledger.py worktree-path --name <이름>)" -b <브랜치> origin/HEAD`. 하니스가 옮겨 갈 수 있는 폴더에 만들고, worktree 안에 있는 세션은 하니스의 새 worktree 만들기를 쓸 수 없어서 `git worktree add` 로 만든다. `브랜치:` 가 여럿이면 적힌 순서가 계획 순서이고, 다음 계획의 브랜치는 앞 계획이 머지됐으면 기본 브랜치에서, 아직이면 앞 계획의 브랜치에서 만든다(그 PR 을 쌓을 때의 주의는 `<SD>/references/conducting-step-5.md`).
  - 옮겨 가는 길(2026-10-18 실측): 하니스의 worktree 옮겨 가기(`EnterWorktree`, 경로 지정)로 그 worktree 에 들어가 할 일을 하고 앞 자리로 돌아온다(앞 자리도 경로 지정으로, 메인 체크아웃이면 하니스의 worktree 나가기 `ExitWorktree` keep). 옮기기 전에 지금 자리의 쓰기(커밋 포함)를 끝낸다 — 옮긴 뒤 앞 자리는 다시 들어가기 전까지 읽기 전용이다. 세션이 옮기면 격리 없이 띄운 하위 agent 도 따라 옮긴다 — agent 가 일하는 동안 옮겨 다니려면 아래 「하위 agent 의 자리」 의 기본으로 보낸다. 하니스로 옮겨 갈 수 없으면(하니스 worktree 폴더 밖의 worktree 등) 메인 체크아웃에서 Bash 로 셸의 작업 폴더를 옮기고, 그것도 안 되면 그 에픽 담당 agent 가 두 부분으로 돌려보내는 길로 하고 그 사실을 알린다.
  - spec 리뷰: spec 리뷰를 부르기 전에 품질 게이트 리뷰를 끝낸다 — `<SD>/skills/epic-conductor/references/qg-review.md` 를 읽고 그 자리(「spec 승인 앞」)의 줄을 따른다. 설계문서는 이 세션이 brainstorming 끝에 써서 에픽 worktree 에서 커밋하고, spec 리뷰도 이 세션이 같은 skill(`/spec-distill:spec-review <설계문서 절대경로> --bundle <묶음 절대경로>`)로 직접 돌린다. 옮겨 간 뒤 `pwd` 와 `git rev-parse --show-toplevel` 이 그 worktree 인지 보고, 진입 사전 검사 줄의 `root=` 가 그 worktree 인지 확인한 뒤 리뷰한다 — 아니면 멈춘다. 리뷰 반영 커밋도 그 worktree 에서 한다. 리뷰 도중 압축되면 같은 설계문서 경로로 다시 부른다 — 리뷰 원장이 라운드 · 상한을 잇는다.
  - 승인 게이트: 지휘 세션이 돌린 리뷰라 spec-review 의 승인 게이트는 질문 하나다(네 선택지 대신 승인 질문 하나 — 같은 호출의 둘째 질문은 아래 병렬 질문뿐이다) — 「승인 — 계획 담당자에게 (권장)」 · 「수정 필요」 · 「멈춤」. 설명은 이렇게 쓴다 — 「승인」: 얻음: 승인을 기록하고 같은 턴에 계획 담당자가 계획을 시작한다 · 내줌: 설계에 남은 결함이 있으면 계획 담당자가 그 위에 계획을 쌓는다 / 「수정 필요」: 얻음: 승인 전에 설계문서를 고친다 · 내줌: 리뷰를 다시 돌아 계획 시작이 늦어진다 / 「멈춤」: 얻음: 지금 상태를 그대로 두고 멈춘다 · 내줌: 계획 담당자가 가지 않아 에픽이 서고 다시 불러야 이어진다. 승인이면 이 세션은 writing-plans 를 따르지 않고 게이트가 낸 writing-plans 줄을 계획 agent 의 입력 줄로 넘긴다 — 미커밋 확인 → 승인 줄 기록(`ledger record --spec <설계문서> --approval --date <YYYY-MM-DD> --choice "<고른 선택지 원문>"`) · 그 에픽 worktree 에서 커밋 → 기계 상태 저장(계획 agent 의 입력 줄은 `ledger resource-dir --roadmap <로드맵> --kind relay --name <에픽>` 폴더의 `plan-input.md` 에 두고 `## 자원` 에 적는다) → 같은 턴에 아래 보내기대로 계획 agent 를 보낸다. 「수정 필요」 는 spec-review 의 ③ 갈래로 가고, 「멈춤」 은 그 에픽만 멈춘다. 압축은 `<SD>/references/conducting-resume.md` 의 판단이다.
  - 병렬 질문: 승인 게이트 직전 `<SD>/references/conducting-step-1.md` 의 작업 목록 끝 줄에서 지금 승인하는 에픽(A)을 짝으로 가진 준비 에픽(B…)이 있으면 같은 `AskUserQuestion` 호출에 둘째 질문 「<A> 다음 — 준비 에픽 <B…> 의 구현을 <A> 구현과 겹칠까?」 를 붙인다. 질문 본문 앞에 배경 한 줄(의존 없음 · 경로 예약이 공유 파일 말고 겹치지 않음)을 쓰고, 선택지는 「병렬 (권장)」(얻음: <B…> 구현이 계획이 끝나는 대로 <A> 구현과 함께 돈다 · 내줌: 두 구현이 겹치는 파일에서 부딪히면 머지 때 한쪽을 다시 맞춘다)과 「차례로」(얻음: <B…> 의 설계 · 계획은 그대로 가고 <A> 가 머지된 뒤 구현을 시작해 부딪힐 일이 없다 · 내줌: <B…> 구현 시작이 <A> 의 머지 때까지 밀린다)다. A 에 닿는 병렬 답이 하나도 없고 A 와 함께 구현할 진행 중 에픽(`control_plane.py show <로드맵> <A>` 의 「동시에 갈 수 있는 에픽」 가운데 경로 예약 겹침이 없고 대기 · 알 수 없음이 아닌 것)이 있으면 짝 조건이 없어도 「<A> 의 구현을 <진행 중 에픽> 구현과 겹칠까?」 를 붙인다 — 그 답은 A 자신의 구현 보내기에 쓰고 기록 줄의 준비 에픽 칸에 A 를 적는다. 이 로드맵 에픽들의 설계문서 `## 지휘 기록`(머지된 에픽은 기본 브랜치에서 읽는다) 가운데 가장 아래 줄(줄은 쌓기만 하고 고치지 않는다) 병렬 답의 준비 에픽 집합에 지금 집합이 모두 들어 있으면 붙이지 않고 승인 질문 본문에 「지난 답: <선택지>(준비 에픽 <…>)」 한 줄을 싣고 그 답을 쓴다 — 지난 답에 없던 에픽이 하나라도 들어왔을 때만 다시 묻는다(지금 집합이 비었으면 이 다시 쓰기를 하지 않고 위 진행 중 에픽 갈래만 본다). 승인을 골랐을 때만 승인 줄과 함께 `ledger record --spec <설계문서> --line "- 병렬 답 · <YYYY-MM-DD> · 「<고른 선택지>」 · 준비 에픽 <B…>"` 를 적어 같은 커밋에 넣고, 「수정 필요」 · 「멈춤」 이면 병렬 답은 버리고 다음 승인 때 다시 묻는다. 둘째 질문으로 흐름을 묻지 않는다.
  - 「차례로」 확인: 구현 담당자를 보내기 전에(이 걸음 · 걸음 4 · 걸음 1 과 4 의 채우기 어디서든) 그 에픽(B)에 닿는 가장 최근 병렬 답을 본다. 고른 선택지는 라벨 끝의 「(권장)」 · 「(Recommended)」 꼬리를 뗀 이름으로 읽는다. 「차례로」 면 B 보다 먼저 승인된 에픽이 모두 상태 계산에서 「머지됨」 이 될 때까지 `## 작업` 의 B 줄을 「구현 기다림 — <에픽> 머지」 로 두고 보내지 않는다. 닿는 답이 없으면 기본(병렬)대로 보낸다. 설계 · 계획은 어느 답이든 그대로 간다. 기다리는 동안 사용자가 생각을 바꾸면 그 말을 따르고 새 병렬 답 줄을 적는다(지난 줄은 고치지 않는다).
  - 보내기: 계획 agent 는 승인을 고른 에픽(같은 턴)과 걸음 1 이 「spec 승인됨(…) · 계획 없음」 으로 센 에픽(끊김 · 압축 뒤)에 보낸다 — 자리는 아래 「하위 agent 의 자리」, 글은 `conductor-dispatch.md` 의 계획 틀이고, 입력 줄은 위 relay 폴더의 `plan-input.md` 나 이 턴의 게이트에서, 파일이 없으면 spec-review 의 다음 세션 줄 틀로 다시 만든다. `ledger live-agent --roadmap <로드맵> --epic <에픽> --work 계획` 이 1(없음)일 때만 계획 agent 를 보낸다 — 0 이면 이미 돌고 있어 보내지 않고 기다려 거두고, 3 이면 사유를 보이고 보내지 않는다. 보낼 때는 `ledger add --roadmap <로드맵> --session <세션> --section "살아 있는 agent" --cells "<이름> · <에픽> · 계획 · <worktree> · <때>"` 로 적고 `## 작업` 표의 그 에픽 줄도 맞춘다. 하위에게 보내는 글에는 `ledger suite-lock --roadmap <로드맵>` 의 첫 줄(공유 스위트 잠금 경로)을 싣는다. 보낸 뒤는 끊기 좋은 자리다 — 맥락이 무거우면 `<SD>/references/conducting-resume.md` 대로 압축을 권하고, 아니면 같은 턴에 다음 에픽의 설계로 간다. 의존 · 같은 파일 겹침(상태 계산의 동시 가능 목록)이 없으면 동시에 보낸다 — 띄우기 전에 규모(몇 agent · 무엇)를 알린다. 구현 담당자를 보낼 때는 먼저 이 걸음의 「차례로」 확인을 한다. hc 가 있으면 계획 · 구현 담당자는 따로 띄운 세션으로 보낸다 — `conductor-dispatch.md` 의 `## 세션 담당자`.
  - 하위 agent 의 자리(2026-10-15 · 10-18 실측): 세션이 worktree 격리 중이면 격리 없이 띄운 agent 는 세션의 «지금» worktree 에 묶이고, 세션이 옮기면 따라 옮긴다. agent 는 스스로 다른 worktree 로 옮겨 갈 수 없다(경로 지정 들어가기는 격리 agent 도 거절된다). 기본은 `isolation: "worktree"` 로 띄운 agent 가 자기 새 worktree 에서 `git switch --ignore-other-worktrees <에픽 브랜치>` 로 그 에픽 브랜치에 서는 것이다 — 앞 agent 의 작업 기록(실행 방식의 작업 폴더 — git 이 추적하지 않는다)이 있으면 백업에서 되살린다. 그동안 지휘 세션은 자유롭게 옮겨 다닌다. 지휘자 자신의 worktree 는 origin 기본 브랜치에 detached 로 두어 어느 에픽 브랜치도 쥐지 않는다. 보내기 전에 그 브랜치를 체크아웃한 에픽 worktree 가 깨끗한지 보고 `git -C <에픽 worktree> switch --detach` 로 그 브랜치를 놓는다(브랜치는 그대로다) — 같은 브랜치를 쥔 worktree 가 둘이면 옛 쪽 index 로 한 커밋이 agent 의 커밋을 조용히 되돌린다. 깨끗하지 않으면 보내지 않고 보인다. agent 가 일하는 동안 그 에픽의 기록은 `ledger add --section "쌓인 기록"` 으로 쌓았다가 돌아온 뒤 `ledger flush` 로 옮기고, 놓은 옛 worktree 에서는 커밋하지 않는다(브랜치를 놓은 자리의 커밋은 브랜치에 닿지 않는다). 쌓는 줄의 글 칸은 `## 지휘 기록` 에 적을 줄 그대로다 — 보기: `ledger add --roadmap <로드맵> --session <세션> --section "쌓인 기록" --cells "<에픽> · 지휘 기록 · - 병렬 답 · <YYYY-MM-DD> · 「<고른 선택지>」 · 준비 에픽 <B…>"`. 돌아오면 agent 가 쓴 worktree 를 `## 자원` 의 그 에픽 worktree 로 바꿔 적고 그 브랜치에 쓸 때(기록 · PR)는 거기서 한다 — 놓은 옛 worktree 는 `ledger cleanup-check` 뒤 정리한다. 다른 길은 지휘 세션이 그 에픽 worktree 에 머문 채 격리 없이 보내는 것이다 — 그 agent 가 돌아올 때까지 그 worktree 를 떠나지 않는다. 격리된 자리(세션 · agent)의 셸은 복합 명령을 막으므로 스크립트 파일로 돌리고, 공유 체크아웃 쪽 파일(리뷰 엔진 원장 · 지휘 자원 폴더)은 Write 도구가 막혀 임시 파일에 쓴 뒤 `cp` 로 옮긴다.
  - 세션 담당자의 자리: 세션 길이면 자리는 띄울 때 `--cwd` 로 정하고 위 격리 · 브랜치 놓기 · 옮겨 가기는 하지 않는다 — `conductor-dispatch.md` 의 `## 세션 담당자`.
