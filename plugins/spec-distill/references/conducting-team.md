## team 형식 로드맵

머리말이 `layout: team` 인 로드맵의 과제를 지휘할 때 지휘 순환 걸음 2 · 3 · 4 · 5 는 이 절을 따른다. 이 절이 말하지 않은 것은 걸음 2 · 3 · 4 · 5 의 문장 그대로다. 옛 형식 로드맵에는 닿지 않는다. 걸음표와 이 절의 문장이 다르면 걸음표를 따른다.

- **걸음 보기 먼저.** 담당자를 보내기 전에 `python3 "<SD>"/scripts/walk_table.py next --roadmap <로드맵> --job <과제>` 를 돌린다. 담당자는 늘 그 출력의 다음 걸음의 칸으로 보낸다 — 누가 → `--role` · 작업 방식 → 틀의 `<작업 방식>`. 다음 걸음 줄에는 단계 · 계획 번호 칸이 없어 둘은 다음 걸음의 이름에서 정한다 — `--stage` 는 계획 → plan · 구현 → implement · 검수 → review · 설계 대화 · 설계 검토 → design · 설계 없는 흐름의 진행 → implement 다. `--plan <n>` 은 이름에 「(계획 n)」 이 붙었으면 그 n, 아니면 `흐름:` 줄의 「계획 n/m」 의 n, 둘 다 없으면 1 이다. 설계 단계 · 설계 없는 흐름이면 `--plan` 을 뺀다(보내는 글 틀의 머리와 같다). `막는 것:` 이 `없음` 이 아니면 보내지 않고 그 사유를 보인다. 걸음 보기가 0 이 아닌 종료 코드로 끝나면(2 사용법 · 3 검사 불가 — PR 캐시를 읽지 못한 경우도 3 이다) 보내지 않고 표준 오류의 사유 줄을 보인다. 지휘 절차의 문장과 걸음표가 다르면 걸음표를 따른다. 같은 걸음을 다시 보내는 것(끊긴 담당자 · 받아지지 않은 시도)은 시작 묶음의 이어 쓰기 · 다음 시도 규칙이 정한다.
- **작업 방식.** 작업 방식은 걸음 보기가 낸 칸이다. 계획 담당자는 writing-plans 끝의 실행 방식 질문에 답하지 않고 계획 검토 질문과 함께 돌려보낸다 — 리더는 그 질문을 사용자에게 띄우지 않는다. 걸음표의 구현 걸음 작업 방식 칸을 보고, 실행 방식은 그 칸으로 답한다.

**사용자 자리 다섯.** 걸음표에서 사람이 맡는 걸음 가운데 넷(방향 확인 · 설계 대화와 승인 · 계획 확인 · PR 전 확인)과 걸음표 밖의 하나(구현 중 물음)다. 머지는 사용자가 직접 하는 걸음이다. 걸음 안의 말투와 순서는 리더가 판단한다. 리더는 이 자리들을 빠뜨리지 않고 만들고, 선택지와 근거를 준비해 가져온다 — 대신 정하지 않는다.

| 자리 | 리더가 보이는 것 | 남는 것 |
|---|---|---|
| 방향 확인 | 과제를 받으면 바로 시작하지 않는다. 사용자 원문의 구조에서 뽑은 대응표와 찾은 것을 먼저 보인다. 설계 없이 갈 과제면 질문 창으로 확인받는다 | 설계 대화의 첫 메시지 · 설계 없는 흐름이면 `흐름 승인` 줄 |
| 설계 대화와 승인 | 접근을 따로 보이고 사용자가 고른 뒤에 설계문서를 쓴다. 리더가 혼자 정해 둔 것이 있으면 문서를 쓰기 전에 목록으로 보이고 하나씩 답을 받는다 | `spec 승인` 줄 |
| 계획 확인 | 계획이 나올 때마다 리더가 검수하고, 검수 결과와 계획 요약, 설계에 없던 결정을 보인다 | `계획 검토` 줄 |
| 구현 중 물음 | 설계에 닿는 물음이 생기면 원문 그대로 보이고 답을 받은 뒤에 움직인다 | 옮긴 기록(지금 절차 그대로) |
| PR 전 확인 | 구현 중 내려진 판정 전부와 설계 대조, 스위트 대조 결과, 승인 뒤 달라진 미룬 항목, 그 과제의 사람 줄 전부를 세션 기록과 대조한 결과(스크립트 출력 그대로)를 보인다 | 없음 — 사용자가 머지로 답한다 |

- **PR 전 확인은 줄로 남기지 않는다.** 그 뒤에 내줄 묶음이 없어 스크립트가 막을 자리가 없고, 마지막 문인 머지를 사용자가 한다. 승인 뒤 달라진 미룬 항목은 리더가 승인 줄의 판과 브랜치 끝 사이에서 설계문서의 미룸 절과 계획으로 미룬 항목 표가 달라진 곳을 git 으로 뽑아 보인다.
- **리더는 직접 만들지 않는다.** 걸음표의 계획 · 구현 걸음은 리더의 것이 아니다. 리더가 코드를 직접 고치는 것은 한 문장으로 설명되는 작은 고침뿐이다.
- **검수의 기준.** 검수 기준은 결과 파일의 칸이 아니라 레포가 자기 `REVIEW.md` 에 적은 기준이다. 검수 걸음과 PR 전 확인이 그 기준에 비춘 결과를 보인다. 검수 두 번은 작업 방식이 과제마다 하는 리뷰와 걸음표의 검수 걸음이다. 반려는 어디서 무엇이 어떤 기준에 걸렸는지 한 줄로 적는다(검수 결과 파일 첫 줄). 기본 걸음표에서 사람이 하는 마지막 걸음은 머지다 — 배포가 있는 레포는 자기 걸음표에 사람 걸음으로 더한다.
- **검수 걸음의 qg.** 리더가 곧 지휘 세션이라 qg 를 부르는 길은 옛 형식과 같다 — 검수 걸음 때 `<SD>/skills/epic-conductor/references/qg-review.md` 를 읽고 그 자리(「머지 앞」)의 줄을 따른다. 걸음표 검수 행의 도구 칸에 통합 리뷰어와 함께 `quality-gates:quality-pipeline` 이 있다. qg 의 막는 지적은 리더가 쓰는 검수 결과 파일의 첫 줄(반려 여부)과 지적 목록에 들어가고, 반려는 시작 묶음의 다음 시도로 구현 걸음에 돌아간다. 지적마다의 처리는 다음 시도의 구현 결과 파일에 적게 한다 — 그 지시는 과제 결정 기록의 한 줄로 적어 시작 묶음이 싣게 한다. 고치지 않은 막는 지적을 사용자에게 묻는 것과 좁은 재리뷰는 옛 형식과 같다. 옛 형식이 PR 본문 `## qg 리뷰` 에 적는 것(리뷰 범위와 판정 줄 · 지난 리뷰의 끝 커밋 · 돌려보낼 막는 지적 목록 · 재리뷰 횟수 · 멈출 조건)은 검수 결과 파일(검수 시도마다 하나)의 지적 목록 아래 펜스 하나 안에 적고 거기서 센다 — 펜스 안 줄은 결과 파일의 기계 줄로 읽히지 않는다. PR 이 열리면 그 내용을 본문 `## qg 리뷰` 로 옮긴다. 「두 번까지」 는 옛 형식과 같고, 시작 묶음의 연속 실패 멈춤을 상한으로 쓰지 않는다 — 그 멈춤은 받음 줄이 없는 시도만 세어 qg 가 반려한 시도를 세지 않는다. 검수 반려로 다시 보낸 시도가 돌아온 때에는 걸음 4 의 기본 브랜치 합치기를 하지 않는다.
- **설계 대화에서 혼자 정한 것.** 리더가 혼자 정해 둔 것이 있으면 문서를 쓰기 전에 목록으로 보이고 하나씩 답을 받는다. 설계문서는 리더가 정한 것을 「작성자 제안」 으로 표시한다.

- **사람 줄이 될 질문.** 질문 창을 띄우기 전에 `ledger ask-head --human <종류> --roadmap <로드맵> --job <과제> [--plan <n>]` 이 낸 머리를 질문 글 맨 앞에 그대로 붙인다. team 형식에서는 이 머리가 지휘 순환 걸음 2 의 「질문 문장 앞머리에 에픽 이름」 규칙을 대신한다. 승인받을 글은 질문 전에 커밋돼 있어야 한다 — `ask-head` 가 1 이면 표준 오류의 사유 줄이 적은 일(커밋하기 · 그 브랜치를 체크아웃한 worktree 에서 부르기)을 하고 다시 돌린다. 3 이면 묻지 않고 그 사유를 보인다. 통과 선택지는 정해진 글자다 — 설계 승인 「승인 — 계획 담당자에게 (권장)」 · 계획 확인 「계획대로 구현한다 (권장)」 · 흐름 승인 「설계 없이 진행 (권장)」 · 건너뛰기 「건너뛴다」 · 멈춘 구현 다시 하기 「다시 시도한다」. 다른 선택지와 설명은 리더가 정한다. 건너뛰기 질문은 건너뛸 관문의 이름 하나만 쓴다. 답을 받으면 같은 세션에서 바로 `ledger record --human <종류> --roadmap <로드맵> --job <과제> [--plan <n>] [--gate "<관문 이름>"]` 을 돌리고, 그 브랜치 worktree 에서 INTENT.md 를 바로 커밋 · push 한다. 같은 머리로 다시 물었을 때 사람이 다른 라벨을 고르면 앞 줄은 더 지나지 않는다 — 가장 뒤 답으로 다시 적는다.
- **계획 확인.** 계획이 나올 때마다 리더가 검수하고, 검수 결과 · 계획 요약 · 설계에 없던 결정을 보인 뒤 위 질문(머리 `<과제> plan <n> @<판>`)을 띄운다. 설계에 없던 결정이 없어도 묻는다.
- **보내기.** 보내는 글은 `conductor-dispatch.md` 의 `### team 형식 — 계획 · 구현 담당자` 펜스 하나다. 덧붙일 말은 과제의 결정 기록에 먼저 적어 묶음이 싣게 한다. 펜스 뒤에 `## 마지막 보고` 절을 붙이지 않는다 — 보고는 결과 파일 줄이다. hc 가 있으면 세션 길로 보낸다 — 띄우기 · 세션 꼬리는 `conductor-dispatch.md` 의 `## 세션 담당자`.
- **멈춘 묶음.** 담당자가 돌려보낸 시작 묶음의 종료 코드를 읽는다 — 세션 길이면 담당자가 멈춤 파일에 쓴 종료 코드와 사유 줄을 읽는다. 1 이면 관문 · 머지된 계획 · 연속 실패 등 사유 줄이 적은 할 일 하나를 한다. 3 이면 읽지 못한 것이라 사유를 보이고 고친 뒤 다시 보낸다(INTENT.md 머리를 읽지 못한 경우 로드맵 블록의 과제는 1 · 로드맵 밖 과제는 3 — 형식 정본(`team-files.md`)의 「시작 묶음」 절). 연속 실패 멈춤은 사용자에게 가서 다시 할지 묻는다(위 「다시 시도한다」).
- **PR 전 확인.** team 형식에서는 담당자가 본 테스트 실패 이름과 쓴 미리 받은 답이 결과 파일의 글(기계가 읽지 않는 줄)에 있어 리더가 머지 전 확인에서 그 글을 읽는다. 구현 중 내려진 판정 전부 · 설계 대조 · 스위트 대조 결과 · 승인 뒤 달라진 미룬 항목(`spec 승인` 줄의 판과 브랜치 끝 사이에서 설계문서 `## 미룸` 절과 계획으로 미룬 항목 표의 `git diff`) · `ledger human-check --roadmap <로드맵> --job <과제>` 의 출력을 고치지 않고 그대로 보인다. 머지 앞 qg 의 사용자 답(`human-check` 은 사람 줄만 낸다)은 걸음 5 「승인 기록 다시 보이기」 의 두 형식 공통 문장대로 함께 보인다. `REVIEW.md` 의 기준에 비춘 결과도 함께 보인다.
- **관문이 정당한 길을 막으면.** 한 걸음이면 건너뛰기 질문을 띄워 `걸음 건너뜀` 줄을 남긴다. 기록의 꼴이 바뀌어 모든 관문이 닫히면 레포 설정 `human_gate: 끔` 을 사용자가 머지한다 — 그동안 줄을 적는 길은 형식 정본(`team-files.md`) §5 의 꺼졌을 때 글을 따른다.
