### 5. 머지 전 확인
- 읽을 것: `<SD>/skills/epic-conductor/references/qg-review.md`(머지 앞) · `<SD>/references/conductor-state-branch.md`(안 올린 규칙 고침을 올릴 때)
- 남기는 것: PR 본문(건너뛴 확인 · 「리뷰 뒤 반영」 · 통합 리뷰 인계 · qg 리뷰 절) · 그 에픽 설계문서 `## 지휘 기록` · 기계 상태의 `## PR` · `## 에픽 PR` · `## 자원`.
- 기본값: PR 마다(문서만 고친 PR 도 — 모델이 읽는 skill · reference · 템플릿 · 리뷰어 프로필은 문서로 치지 않는다) `ledger pr-refresh --roadmap <로드맵> --session <세션> --epic <에픽>` 으로 PR 캐시를 새로 채운 뒤 머지 앞 qg 리뷰와 되돌리기 → 스위트 대조 → 통합 리뷰 → 리뷰 뒤 반영 → 완료 전 확인을 한다. 머지 앞 qg 리뷰는 에픽 PR 에만 건다 — `<SD>/skills/epic-conductor/references/qg-review.md` 를 읽고 그 자리(「머지 앞」)의 줄을 따르고, 막는 지적이 고쳐졌거나 사용자가 남기기로 한 뒤에 스위트 대조로 간다. 건너뛴 확인은 무엇을 왜 건너뛰었는지 적는다. 상태 브랜치의 「안 올린 규칙 고침」 이 있으면 PR 마다 함께 알리고 `conductor_branch.py rules-branch` 로 작은 브랜치를 만들어 지금 절차대로 PR 을 연다(`conductor-state-branch.md`). 에픽 PR 의 판 번호는 `conductor_status.py show` 의 판 번호 줄을 보고 정한다.
- 판단:
  - 스위트 대조: `python3 "<SD>"/scripts/merge_check.py run --roadmap <로드맵> --branch <브랜치> --keep-merged`. 종료 코드 1(새 실패)이면 `superpowers:systematic-debugging` 으로 원인을 찾아 고치거나 이유를 적고, 4(이름으로 가르지 못한 단위)면 그 줄을 사용자에게 보이고, 5(다른 스위트가 공유 스위트 잠금을 쥐고 있다 — 하위 agent 의 전체 스위트와 같은 잠금이다)면 그 줄의 주인 · 잡은 시각을 보이고 끝난 뒤 다시 돌거나 `--wait <초>` 를 붙여 줄을 서고, 6(테스트 명령을 모른다)이면 사용자에게 한 번 물어 그 답을 인자로 붙여 이 대조를 다시 돌리고(`… --keep-merged --test-command "<명령>"` — 실패 이름 정규식도 답했으면 `--test-failure-pattern "<정규식>"`, 출처는 「이 호출의 인자(사용자 답)」 로 보인다. 답은 기계 상태에 적지 않는다 — 검사받는 하위 agent 도 쓸 수 있는 파일이라 스위트 대조가 읽지 않는다. 이 세션의 다음 대조에도 같은 답을 인자로 넘긴다 — 압축 · 새 세션 뒤에는 그 답을 기억하지 못하니 다시 묻는다) 레포 설정 파일(`.devbrew.md`)에 올리자고 알리고, 7(테스트 없음)이면 「스위트 대조 없음」 을 알리고 통합 리뷰만 한다. 3(검사 불가)이면 사유를 그대로 보이고 그 PR 의 머지 준비를 멈춘다 — 충돌이면 `<SD>/references/conducting-step-6.md` 의 충돌 처리와 같이 그 에픽만 멈추고 알린다. 하위가 본 실패가 이 대조에서 사라지면 경합으로 보고 알린다.
  - 통합 리뷰: `ledger review-pack --roadmap <로드맵> --epic <에픽> --branch <브랜치> --merged <합친 사본>` 이 이 PR diff · 열린 다른 에픽 diff · 충돌 미리 보기 · 앞선 인계 절 · 함께 진행된 에픽의 설계문서 전문(`intents.md`)을 한 폴더에 모은다. 그 폴더와 `superpowers:requesting-code-review` 의 리뷰 요청 틀로, 쓰기 도구가 없는 통합 리뷰어(지휘자 skill 본문의 dispatch 자리)를 해결자 `repo_defaults.py get review_model --roadmap <로드맵>` 의 값(모델 칸이 받는 이름일 때만 — 종료 코드 1 이면 세션 모델로 가며 알리고, 3 이면 사유 줄을 보이고 세션 모델로 간다)으로 부른다 — 이음매가 여럿이면 여럿을 동시에. 지적은 「이 PR 이 고침」 · 「뒤 에픽이 고침」으로 나눠 PR 본문 `## 통합 리뷰 인계` 절에 담당 에픽과 함께 적는다. 뒤 에픽의 통합 리뷰는 앞선 인계 절의 항목이 실제로 고쳐졌는지 확인한다. 리뷰어는 일곱째 이음매로 함께 진행된 에픽의 설계 의도(Goals · Non-goals · 결정 기록 · 판정)와 이 PR 이 어긋나는지 본다 — 경로가 겹치지 않아도 보고, 이 PR 이 앞 에픽의 의도를 망가뜨렸다는 지적은 「이 PR 이 고침」 이다.
  - 리뷰 뒤 반영: 고침은 `superpowers:receiving-code-review` 로 받는다. 동작 · 락 · 보안 경계 · 리뷰어 프로필을 바꾼 수정은 매번 좁은 재리뷰를 받고, 좁은 재리뷰는 PR 하나에 두 번까지다 — 첫 재리뷰를 보내기 전에 멈출 조건(남는 지적을 잔여로 공시하고 넘길 곳)을 PR 본문에 적는다. 동작을 바꾸지 않는 수정은 PR 본문에 「리뷰 뒤 반영(리뷰 라운드를 거치지 않았다)」 으로 적는다.
  - 쌓인 PR: 다음 계획의 PR 을 앞 계획 브랜치를 바탕(base)으로 열었으면 앞 PR 부터 머지하고, 머지 뒤 그 바탕 브랜치를 지우기 전에 위 PR 의 바탕을 기본 브랜치로 바꾼다 — 바탕 브랜치를 지우면 위 PR 이 닫히고 다시 열 수 없다. 바탕을 기본 브랜치로 바꾼 직후, 머지 명령을 준비하기 전에 `ledger pr-record --roadmap <로드맵> --session <세션> --epic <에픽> --pr <번호>` → `ledger pr-refresh --roadmap <로드맵> --session <세션> --epic <에픽>` 을 부른다.
  - 승인 기록 다시 보이기: 머지 명령 줄을 내기 전에 그 에픽에서 받은 승인과 담당자 세션에서 들은 사용자 말을 모아 사용자에게 다시 보인다. 옛 형식은 설계문서 `## 지휘 기록` 의 spec 승인 줄과 병렬 답, 옮김 기록의 질문과 답이다. team 형식은 `ledger human-check` 출력이다(고치지 않는다 — `<SD>/references/conducting-team.md` 의 PR 전 확인과 같은 것). 두 형식 모두 리더가 결정 줄로 옮기며 「담당자 세션에서 들음」 표시를 붙여 둔 줄 전부를 그 일의 기록 자리에서 읽어 싣는다. 두 형식 모두 머지 앞 qg 의 사용자 답도 싣는다 — PR 본문 `## qg 리뷰` 의 사용자 답(team 형식은 PR 이 열릴 때 검수 결과 파일의 펜스 내용을 그 절로 옮겨 두었다)과, 그 PR 의 머지 앞 리뷰 기록 파일(자리 글자 `premerge-pr<번호>` · `recheck-pr<번호>`, team 형식은 `premerge-<과제>-plan<n>` · `recheck-<과제>-plan<n>`)의 `- 답:` 줄이다. 끝에 한 문장을 붙인다 — 하신 적 없는 승인이나 말이 있으면 머지하지 말고 알려 달라.
    team 형식이면 표시 없는 `conductor_branch.py confirm` 이 낸 출력(「이 기계가 쓴 것으로 적힌 고침」 목록 줄과 「확인할 끝」 이 한 출력에 나온다)의 목록도 함께 싣는다 — 그 가운데 리더가 쓰지 않은 고침이 있으면 머지 명령 줄을 내지 않고 사용자에게 알린다. 사용자가 머지를 정하면 그 출력의 「확인할 끝」 으로 `conductor_branch.py confirm --confirmed <확인할 끝>` 을 불러 확인한 끝을 기록한다 — 1 로 끝나면 끝이 옮겨진 것이니 새로 낸 목록을 다시 보이고 묻는다. 그 전에는 `sync` 가 그 목록을 접지 않는다.
  - 머지 하나씩: 머지 명령 줄은 이 로드맵의 PR 가운데 한 번에 하나만 낸다 — 낸 PR 이 상태 계산에서 「머지됨」 이 되면 다음 PR 은 머지 뒤 걸음대로 기본 브랜치를 합치고 스위트 대조를 다시 돈 뒤에 낸다. 낸 PR 이 머지되지 않고 닫히거나 사용자가 다른 순서를 말하면 그 명령 줄을 거두고 다음 PR 을 지금 기본 브랜치에 대해 다시 대조한 뒤 낸다. 명령 줄을 내기 직전 스위트 대조 첫 줄의 기본 브랜치 커밋과 지금 origin 기본 브랜치 끝을 견주어 다르면 스위트 대조를 다시 돈다. 통합 리뷰는 다시 돌지 않는 것이 기본이다 — 앞 PR 이 이 PR 의 통합 리뷰 뒤에 바뀌었거나 기본 브랜치를 합칠 때 이 PR 이 고친 파일이 함께 바뀌었으면 다시 돌고, 그 판단과 이유를 PR 본문에 적는다. 공유 파일 · 코퍼스 락이 둘째 PR 에서만 깨지면 둘째 PR 에서 고치고, 앞 에픽과의 조합 때문이라는 근거를 인계 절에 한 문장으로 적는다.
  - 머지 큐: 명령 줄을 내기 전에 그 레포 기본 브랜치의 보호 규칙 · 규칙 집합을 `gh` 로 원격에서 읽는다 — 읽지 못하면 없는 것으로 보고 그 사실을 알린다. 머지 큐가 있거나 「최신 기본 브랜치 반영 필수」 규칙이 있으면 머지 순서는 그것에 맡기고 명령 줄을 하나씩 낼 필요가 없다고 알린다. 기계 재검사는 레포 필수 검사가 스위트 대조와 같은 테스트 명령을 돈다고 CI 설정(워크플로 정의 등)에서 확인될 때만 맡기고, 확인하지 못하면 스위트 대조를 다시 돈다. 통합 리뷰(의도 대조)는 언제나 지휘자 몫이다.
  - 끝으로 `superpowers:verification-before-completion`. 릴리스 번호는 이때 정한다(먼저 머지되는 쪽이 낮은 번호). 머지 명령 줄만 준비하고 머지는 사용자가 한다. 리뷰가 끝나면 합친 사본과 리뷰 묶음을 `ledger cleanup` 으로 지운다.
- team 형식 로드맵이면 `<SD>/references/conducting-team.md` 를 따른다.
- 부를 skill: `superpowers:systematic-debugging` · `superpowers:requesting-code-review`(틀) · `superpowers:receiving-code-review` · `superpowers:verification-before-completion`(품질 게이트는 `qg-review.md` 의 담당자가 부른다).
- 기록: 건너뛴 확인과 이유 · 「리뷰 뒤 반영」 → PR 본문과 그 에픽 설계문서 `## 지휘 기록` · 머지 앞 qg 리뷰 → PR 본문 `## qg 리뷰`.
- 기계 상태: `## PR`(새로 채움) · `## 에픽 PR`(쌓인 PR 의 바탕을 바꾼 뒤 적은 번호) · `## 자원`(합친 사본 · 리뷰 묶음 · 통합 리뷰어).
