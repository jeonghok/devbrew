### 1. 맞추기
- 읽을 것: `<SD>/references/conductor-state-branch.md`(맞추기 명령이 상태 브랜치 구간에 이상을 냈을 때 · 온 글이 있을 때)
- 남기는 것: 기계 상태의 `## PR` · `## 살아 있는 agent` · `## 작업` · `## 실행 원장`(설계문서 기록은 없다).
- 기본값: `python3 "<SD>"/scripts/conductor_sync.py --roadmap <로드맵>` 을 돌리고 그 출력을 본다(세션 번호는 명령이 스스로 읽는다). 명령이 도는 차례는 자리 → 원격 받기(`git fetch origin`) → 작업 목록(`control_plane.py show --tasks <로드맵>` 과 같은 계산) → 표지 → 기본 브랜치 → `ledger pr-refresh --roadmap <로드맵> --session <세션>` 으로 기계 상태의 PR 캐시를 주인(GitHub)과 맞춘다 → 상태 브랜치(`conductor_branch.py ensure` → `conductor_status.py sync` → `conductor_status.py show`) → 세션 담당자 → 스위트 잠금 → 실행 원장 → 이 세션에서 처음일 때만 주인 모를 worktree · 판 차이다. 이상이 없는 구간은 한 줄이고, 이상이 있는 구간만 그 원문을 들여 낸다. 구간이 멈추면 `멈춤 — <구간>: <사유>` 를 내고 그 종료 코드로 끝난다 — 다른 세션이 쥐어 5 로 멈췄고 사용자가 넘겨받기를 고르면 같은 명령에 `--takeover` 를 붙여 다시 부른다. 작업 목록 구간의 종료 코드 3 · 4 의 뜻은 `<SD>/references/conducting-manual.md` 의 1 과 같다. 끝 묶음은 규모 줄 · 끝나지 않은 일마다 서 있는 걸음과 그 지시서 · 머지 뒤 일이 남은 에픽이다 — 그 걸음에 들어설 때 그 지시서를 읽는다. 끝 묶음의 `동시에 갈 수 있는 준비 에픽: …` 줄은 작업이 아니라 병렬 판단 신호다 — 작업 목록에 넣지 않고 `<SD>/references/conducting-step-3.md` 의 승인 게이트에서 쓴다. 상태 브랜치 구간이 이상으로 낸 「다른 로드맵과 닿는 것」 · 기다리는 질문 · 온 글을 보이고, 온 글은 읽고 받음 줄을 남긴다(절차는 `<SD>` 의 references 폴더의 `conductor-state-branch.md`). 명령이 하지 않는 일(하니스 agent 목록 조회 · 표의 줄 지우기 · 거두기)은 리더가 아래 맞추기 순서로 한다 — 살아 있는 agent 와 작업을 원천에서 다시 센다.
- 판단: 표지를 다른 세션이 쥐었으면 쓰지 않고 읽기 전용으로 보이며, 넘겨받을지(`ledger takeover`)는 사용자에게 묻는다(「읽기만 (권장)」 · 「넘겨받기 — 그 세션은 쓰기를 멈춘다」). 설명은 이렇게 쓴다 — 「읽기만」: 얻음: 지휘 중인 다른 세션을 건드리지 않고 지도만 본다 · 내줌: 이 세션은 쓰지 못해 에픽을 보내거나 기록할 수 없다 / 「넘겨받기」: 얻음: 이 세션이 지휘를 이어받아 에픽을 보내고 기록한다 · 내줌: 그 세션의 쓰기가 끊겨 하던 에픽이 어중간하게 남을 수 있다. 기계 상태가 깨졌으면 사유를 보이고 덮어쓰지 않는다 — 다시 만들 수 있는 것(PR 캐시(`## PR`) · 자원 · 기다리는 질문)은 주인에서 다시 모은다. `## 에픽 PR` 은 다시 모으지 않고 그대로 둔다 — 잃은 번호는 지휘 세션이 차례 `<SD>/references/conducting.md` 의 번호 적기 불릿대로만 다시 적는다. 캐시는 「PR 열림」인데 GitHub 은 머지면 주인을 믿고 캐시를 고친 뒤 알린다. `ledger claim` · `ledger takeover` · `ledger pr-refresh` 가 옛 판이 쓴 PR 캐시 줄이라고 멈추면(claim · takeover 는 표지를 잡은 뒤 멈춘다) 그 줄이 보인 `--reset` 명령으로 PR 절만 비우고 다시 채운 뒤 `ledger release` → `ledger claim` 으로 표지를 다시 잡는다. 끝났는데 보고하지 않은 agent 는 결과를 거두고 놀고 있는 agent 는 내린다. 기다릴 때는 끊어서 기다리고 사이마다 살아 있는 하위를 다시 센다(superpowers SDD 의 「Waiting on dispatched subagents」 방식) — 기다리기만 하지 않는다. agent 를 보내거나 거둘 때마다 상태 계산의 동시 가능 목록과 승인된 설계의 남은 계획을 훑어, 의존 · 같은 파일 겹침 · 기다리는 답이 없는 일은 규모를 알리고 바로 보낸다 — 동시에 돌리는 큰 작업의 권장 수는 기본 3(레포 설정 파일이나 로드맵 머리말의 `parallel_default` 로 바꾼다)이고 상한이 아니다(사용자가 늘린다). 구현 담당자를 보낼 때는 먼저 `<SD>/references/conducting-step-3.md` 의 「차례로」 확인을 한다. 압축 · 새 세션 뒤에도 여기서 시작한다 — 무엇이 끝났는지 기억에 기대지 않는다. 이 세션에서 처음 부를 때는 `ledger orphans --roadmap <로드맵>` 의 「주인 모름」 worktree(고른 것만 지운다. 추천을 달지 않는다 — 주인 모를 worktree 를 지울지는 사용자만 안다)와 `ledger version --plugin-json "<SD>"/.claude-plugin/plugin.json` 의 판 차이를 보인다. 상태가 「spec 승인됨(…) · 계획 없음」 인 에픽(승인 뒤 계획 agent 를 보내기 전에 끊겼거나 압축하고 다시 부른 경우)에는 `<SD>/references/conducting-step-3.md` 의 보내기대로 계획 agent 를 보내되 먼저 아래를 본다 — `ledger live-agent --roadmap <로드맵> --epic <에픽> --work 계획` 이 1(없음)일 때만 계획 agent 를 보낸다 — 0 이면 이미 돌고 있어 보내지 않고 기다려 거두고, 3 이면 사유를 보이고 보내지 않는다. 보낼 때는 `ledger add --roadmap <로드맵> --session <세션> --section "살아 있는 agent" --cells "<이름> · <에픽> · 계획 · <worktree> · <때>"` 로 적는다. `## 기다리는 질문` 에 의도 점검 질문 줄이 있으면(에픽 줄은 `control_plane.py show <로드맵> <에픽>` 의 `기다리는 질문:` 칸, 로드맵 단위 줄은 기계 상태 파일 `machine.md` 의 `## 기다리는 질문` 절) `<SD>/skills/epic-conductor/references/qg-review.md` 를 읽고 그 자리(「아직 묻지 못한 질문」 — 그 파일의 `## 묻기`)의 줄을 따른다.
  - 맞추기 순서(보낼 때 · 돌아올 때 · 진행 상황을 말할 때마다 같은 턴에): ① 하니스 agent 목록(`ListAgents`)을 조회하고 hc 로 띄운 담당자가 있으면 hc 의 내 자식도 조회해 `## 살아 있는 agent` · `## 작업` 표를 맞춘다 ② 상태 계산(위 `show --tasks`) ③ 돌고 있는 큰 작업 수 대 권장 수 ④ 모자라면 채우기 · 제안 ⑤ 「HH:MM 기준」(① 을 조회한 시각)을 붙여 보고한다.
  - 원천: 돌고 있는 agent 는 하니스 agent 목록, 에픽 단계는 git 상태 계산, 과제 진행은 각 구현의 실행 방식 원장(`ledger progress --roadmap <로드맵>` 이 원장마다 마지막 고친 시각 · 마지막 줄을 보인다)이다 — 기계 상태의 「살아 있는 agent」 · 「작업」 표는 사본이다. 세션 담당자는 아래 불릿을 따른다. 표에만 있고 원천에 없는 줄은 지우고(`ledger drop`), 끝났는데 보고하지 않은 agent 는 거두거나 깨운다(`SendMessage`). 이름 없는 agent(하위 agent 가 띄운 agent)는 세지 않는다. 상태 · 개수는 이 턴에 조회한 것만 말한다 — 조회하지 않은 숫자는 말하지 않는다.
  - 세션 담당자의 원천: 돌고 있는 담당자의 원천은 둘이다 — 하니스 agent 목록과 hc 의 내 자식(`hc ls` 에서 `parent` 가 내 주소인 것). 표에 있는데 원천에 없는 줄은 지우고 그 일의 결과 파일이 있는지 본다. 내 자식인데 표에 없는 터미널은 무엇인지 보고 닫거나 표에 올린다. 끝난 세션은 스스로 닫히지 않고 「살아 있음 · 끝남」 으로 남는다.
  - 완료 표시는 일이 끝났다는 뜻이 아니다(2026-10-19 실측): agent 가 자기 백그라운드 일(잠금 대기 스크립트 등)을 걸어 두고 턴을 끝내도 agent 목록에는 completed 로 보이고, 원장 거울도 늦게 갱신될 수 있다. completed 만으로 멈춤을 단정하지 않는다 — 원장의 마지막 줄 · 시각과 그 agent 알림의 「waiting on its own background work」 를 함께 본다. completed 인데 원장 마지막 줄이 오래됐고(얼마면 오래인지는 지휘자가 정해 보고에 밝힌다) 그 알림도 없거나, 판단이 모호하면 그 agent 에 한 줄 묻는다(`SendMessage` — 깨워 잇게 하는 것과 같은 길).
  - 잠금 대기는 멈춤이 아니라 줄이다: `ledger suite-lock --roadmap <로드맵>` 이 공유 스위트 잠금(지휘자의 스위트 대조와 하위 agent 의 전체 스위트가 같이 쓰는 잠금)의 경로 · 주인 · 잡은 시각을 낸다 — 상태를 말할 때 그 줄을 함께 보인다.
  - 병렬 권장 수: 세는 것은 지휘자가 돌리는 큰 작업(계획 · 구현 담당자 · 수리 구현처럼 오래 도는 일)이다 — 짧은 리뷰어와 하위 agent 가 띄운 agent 는 세지 않는다. 권장 수는 기본값이지 상한이 아니다 — 사용자가 늘리고, 파일이 겹치지 않거나 문서만 고치는 일이라 늘려도 품질이 괜찮아 보이면 지휘자가 이유와 함께 늘리자고 제안한다. 병목은 개수가 아니라 공유 스위트 잠금의 줄 · 같은 파일 겹침 · 지휘자의 옮김 부하다.
  - 모자라면 채우기: 돌고 있는 큰 작업이 권장 수보다 적으면 동시 가능 목록 · 승인된 설계의 남은 계획 · 정리 일 · 설계문서 `## 미룸` 에서 이 로드맵이 받는 행 가운데 의존 · 겹침 · 기다리는 답이 없는 일을 찾아 보내거나 제안한다.
  - 로드맵 밖 일도 한 곳에: 지휘자 수리 PR · 정리 일처럼 에픽에 매이지 않은 일도 `## 작업` 표(종류 · 이름 · 에픽 또는 「로드맵 밖」 · 단계 · 담당 agent · 근거 경로)에 적는다 — `ledger add --roadmap <로드맵> --session <세션> --section "작업" --cells "<종류> · <이름> · <에픽|로드맵 밖> · <단계> · <담당|없음> · <근거 경로>"`. 에픽 계획 · 구현도 같은 표에 적는다. 끝난 일은 단계 칸에 「끝」 으로 적거나 그 줄을 지운다(`ledger drop`) — 상태 보기는 단계가 「끝」 · 「끝남」 · 「머지됨」 인 줄만 끝으로 세고, 「완료」 · 「PR 머지됨」 같은 다른 낱말은 돌고 있는 일로 센다. 담당 agent 가 돌아오면(거두거나 내리면) 그 줄의 담당 칸을 「없음」 으로 바꾼다 — 상태 보기는 담당으로 돌고 있는 수를 센다. 수리 구현처럼 에픽에 매이지 않은 agent 는 이 표의 담당 칸에 이름을 적는다 — 상태 보기(`control_plane.py show <로드맵>`)는 `## 살아 있는 agent` 와 끝나지 않은 작업 줄의 담당을 합쳐 돌고 있는 수로 세고, 이 표와 권장 수 · 스위트 잠금을 함께 보이고, 작업 목록(`show --tasks`)은 「로드맵 밖」 줄을 더한다.
- 부를 skill: 없음.
- 기록: 없음 — 주인과 캐시를 맞춘 사실은 알림으로만.
- 기계 상태: `## PR`(캐시 고침) · `## 살아 있는 agent`(거둔 것 · 내린 것 빼기) · `## 작업`(로드맵 밖 일 포함 — 원천과 맞춤) · `## 실행 원장`(읽은 줄).
